### 模块 A：API 层

#### 框架 A-1：HTTP 三层入口隔离架构

**设计意图：** 将所有 HTTP 入口点分为三个独立层级。读取状态时不做任何写入操作，写入时使用不同级别的隔离保护。这三个入口分别是：状态查询（只读 GET）、心跳推进（服务器端写入）、命令执行（玩家认证写入）。每个入口对应一个独立的 PHP 文件，有着不同的锁策略和事务策略。

- 状态查询：不使用 MySQL 事务和房间锁 —— 即使数据库表不存在也不会创建，返回虚拟空状态。
- 心跳和命令：使用 MySQL 事务 + 房间锁保护数据一致性。命令额外使用基于文件的玩家锁防止并发操作。
- 所有入口都处理 CORS 预检（OPTIONS）请求和 PHP 致命错误的关闭回调。

**代码锚点：** `oblivions/api/command.php`（命令入口）、`oblivions/api/heartbeat.php`（心跳入口）、`oblivions/api/state.php`（状态入口）

**边界案例：**

- 只读路径遇到不存在的数据库行时，不创建记录而是返回内存中的虚拟行，确保完全无副作用。
- 所有入口在 PHP 错误级别捕获 5 种致命崩溃，输出结构化 JSON 而不是空白页面。

#### 框架 A-2：最小依赖引导链

**设计意图：** 每个入口只加载自己需要的依赖。命令入口不加载状态响应格式，状态入口不加载命令总线。引导文件仅声明函数但不执行 —— 实际的启动调用由入口文件自己做。

**代码锚点：** `oblivions/include/api/obl_api_bootstrap.php`（共用 bootstrap）、`oblivions/include/api/obl_command_api_bootstrap.php`（命令依赖聚合）、`oblivions/include/api/obl_heartbeat_api_bootstrap.php`（心跳依赖聚合）、`oblivions/include/api/obl_state_api_bootstrap.php`（状态依赖聚合）

**边界案例：**

- 心跳入口和命令入口各自有不同的启动参数，控制是否在数据库缺失时自动创建记录。

#### 框架 A-3：状态查询范围分发

**设计意图：** 状态 API 提供了一个路由中心，根据查询参数分发到 14 种不同的处理器。每个处理器负责组合一种特定的前端数据视图（玩家信息、地图数据、敌人列表、背包内容、日志、技能列表等），新增一种视图只需添加一个新的路由分支和对应的处理器函数。

**代码锚点：** `oblivions/include/api/obl_state_handlers.php`（scope 路由中心 + scope 处理器）

**边界案例：**

- 敌人列表处理器在玩家处于战斗状态时，强制将参战成员（NPC）加入列表，即使它们处于迷雾中未被发现 —— 避免战斗 UI 丢失参战者。
- 战斗目标处理器构建了一个复杂的"参与状态机"，将候选对象分为五类（成员、可加入、已离开、其他战斗、被封锁），按优先级排序返回给前端。
- 物品列表处理遇到近视伪装物品时，使用虚拟名称和假 ID 包装后返回，不影响真实道具数据。
- 地图迷雾数据使用稀疏格式返回（仅发出有值的格子），减少传输量。

#### 框架 A-4：结构化视图投影函数集

**设计意图：** 一组专门用于"投影"数据视图的函数 —— 它们将数据库内部状态转换为前端可消费的响应格式。这些函数是纯读取的，不修改任何数据。包括：装备槽映射（平铺的数据库字段转为结构化对象）、角色战斗视图、效果投影（在指定 tick 评估哪些效果将生效）、战斗队列投影（当前先攻顺序与回合状态）、战斗上下文投影（含可提交回合标志与建议目标角色标识等派生字段）。

**代码锚点：** `oblivions/include/api/obl_state_handlers.php`（投影函数实现）

**边界案例：**

- 投影函数通过函数存在性检查来判断某些库是否已加载（如标签查询函数），优雅降级而非硬性依赖。

#### 框架 A-5：调试工具框架

**设计意图：** 调试能力正交于玩法框架：在守卫参数下提供场景构造、瞬态观察、精确定位与现场恢复的跨前后端基础能力。后端以白名单命令和房间级快照准备权威状态，前端以事件账本与轻量抽屉提供可回看 UI 与稳定操作定位。调试入口越过玩法门槛（角色动作、临时槽、死亡、战斗忙碌），但不越过身份认证、负载校验、房间锁、玩家锁与数据库事务——调试权限不等于任意写权限。所有入口只在调试模式下挂载，正常玩家路径不继承调试参数。

**代码锚点：** `oblivions/include/core/obl_debug.php`（后端调试能力核心：命令合约 + 状态查询 + 房间快照）、`oblivions/include/core/obl_runtime.php`（守卫边界：身份/锁/事务由运行时统一强制）、`vex-vue/src/stores/debug-console.ts`（前端 GM 编排与诊断日志拉取）、`vex-vue/src/components/debug/DebugConsole.vue`（轻量调试抽屉与语义摘要）

**边界案例：**

- GM 命令跳过角色动作、临时槽、死亡与战斗忙碌等玩法门槛，但仍完整经过认证、负载校验、房间锁、玩家锁和数据库事务；调试权限不等于任意写权限。
- 房间快照覆盖该房间的全部权威表，恢复后必须重新加载游戏时间全局量与当前玩家上下文，否则旧命令上下文会把恢复结果再次覆盖。
- 临时调试桩必须使用任务唯一标识，不改变业务门控、时序、事务或持久化语义；验证结束后清理并搜索确认零残留，跨任务复用价值明确时才升格为长期调试入口。

**子框架 A-5-2：诊断日志通道**

**设计意图：** 为排查"为什么没触发""为什么走到一半停下"等流程级诊断问题，单独开辟一条与玩家事件日志、运行时错误日志物理隔离的调试期收集通道。诊断条目以结构化参数而非字符串拼接表达，涵盖正常流程节点和异常中断原因，便于前端按分类筛选和精确排序。通道仅在调试模式启用时实例化与累积，正常玩家路径零开销；按房间与玩家隔离持久化，按局保留。严重契约错误（如监听器违反位置约束）走三通道并行告警——运维错误日志保留可见性、错误日志通道保留命令反馈链路、诊断日志通道提供调试期可追溯；但本通道本身不参与命令反馈，避免诊断信息污染用户可见错误。

**实现锚点：** 诊断日志通道由以下文件协同实现（具体角色见框架 A-5 代码锚点）：`oblivions/include/game/log.func.php`（收集器与门面与参数清洗）、`oblivions/include/core/obl_runtime.php`（请求关联字段初始化与 Fatal 兜底）、`oblivions/api/command.php` / `oblivions/api/heartbeat.php`（四路径持久化）、`oblivions/include/core/obl_debug.php`（多维度查询 scope）、`vex-vue/src/stores/debug-console.ts`（前端拉取）、`vex-vue/src/composables/useDebugBus.ts`（前端守卫语义）

**边界案例：**

- 四路径持久化覆盖：诊断日志持久化与游戏事务成功/失败解耦，覆盖正常提交、事务回滚、异常捕获、Fatal Error 四条路径——最需要调试的"失败现场"不再丢日志；持久化幂等，二次调用为空操作。
- 严重错误三通道并行：调用专用门面后框架自动写运维错误日志、错误日志通道、诊断日志通道；其中错误日志通道的条目强制带系统前缀，自动豁免命令反馈规则，避免被翻译成用户可见错误。
- 请求关联字段自动附加：每条诊断条目顶层携带请求内递增序号、请求唯一标识、请求类型、当前命令名，便于跨请求追溯某次前端操作的后端事件链。
- 参数清洗保护日志文件：门面自动限制嵌套深度、字符串长度、数组键数，遇到资源或闭包替换为占位；序列化失败时回退为占位条目，避免整个日志文件损坏。
- 增量查询适配 AI：查询 scope 支持按分类、ID（含前缀通配）、请求标识过滤，并支持增量游标；返回裁剪前总数与下次游标，便于精准拉取而不必每次读取最近 N 条。
- 前端事件账本守卫语义：事件总线始终收集（业务调用点零开销），但查询接口仅在调试模式挂载到全局对象；业务侧用守卫标志避免生产环境下的参数计算开销。

### 模块 B：命令系统

#### 框架 B-1：声明式命令合约

**设计意图：** 每个命令由一个声明式合约完整定义。合约描述了命令的名称空间、允许的 UI 模式、是否推进 tick、是否只读、需要什么能力、战斗状态机要求、负载格式、以及执行后哪些前端范围需要刷新。命令涵盖五大类——地图移动与探索（含单次精确移动 map.move 与多行动导航循环 map.navigate）、POI 互动/拆除、物品拾取/丢弃/使用/装备/整理/合成、战斗开始/提交回合/预览/可达性查询、世界等待。

**代码锚点：** `oblivions/include/command/obl_command_contract.php`（命令合约定义 + 信封/负载校验）

**边界案例：**

- 合约在首次查询时（懒加载，通过静态变量防护）校验所有定义的能力名称是否真实存在，捕获拼写错误而非运行时暴露。
- 四个战斗只读命令标记为只读 —— 其中三个是预览命令（`combat.preview_single`、`combat.preview_targets`、`combat.preview_chain`），一个是可达性查询命令（`combat.can_engage`）。它们走命令管道但不触发保存逻辑、不推进 tick、不执行战斗状态转换。
- 战斗回合提交具有最严格约束：必须处于战斗模式、战斗状态必须是玩家回合、队列行动者必须是自己。
- map.navigate 是唯一标记 internal_tick_advances: true 的命令——handler 内循环逐次推进 tick（每原子移动结算一个完整游戏刻），B-3 save_and_tick 跳过 tick 推进仅做最终保存；幂等通过 operation_key + 单步原子事务保证（每原子移动原子提交，中途失败不回滚已完成步骤）。

#### 框架 B-2：双层负载校验管道

**设计意图：** 外部输入通过两个验证层级。第一层检查整体信封结构（命令名称格式、请求 ID 格式），第二层按照合约的结构定义逐字段校验和规范化。类型系统支持整数、字符串、动作序列、槽位计数、字符串列表、整数列表和通用数组。

**代码锚点：** `oblivions/include/command/obl_command_contract.php`（信封与负载校验）、`oblivions/include/core/obl_json_request.php`（JSON 请求解析）

**边界案例：**

- 动作目标类型支持命名字段和目标解析的向后兼容别名。
- 整数列表会自动去重并限制最大长度。

#### 框架 B-3：命令总线执行管道

**设计意图：** 总线是一个完整的执行管道，编排所有横切关注点：认证、校验、门控、分发、反馈、持久化、tick 推进。处理程序位于管道中心，保持薄层。完整的执行顺序如下：查找合约 → 校验负载 → 认证玩家 → 获取文件锁 → 设置操作标识 → 检查门控（允许动作、预期状态、物品暂存、能力、战斗状态、队列行动者、战斗忙碌）→ 检查存活 → 记录日志快照 → 准备待处理战斗行动者作用域（仅推进 tick 的命令，将当前玩家加入待处理战斗的行动者作用域）→ 分发 → 处理回滚标记 → 计算反馈 → 收集权限变更范围 → 保存并推进 tick → 返回。注意：信封结构校验在获取房间锁和事务之前执行，而负载结构定义校验在事务内、文件锁之前执行——两层校验被锁/事务边界分隔。只读命令跳过战斗状态转换和保存并推进 tick 两个步骤。

**代码锚点：** `oblivions/include/command/obl_command_bus.php`（总线管道编排）、`oblivions/include/command/obl_command_handlers.php`（命令处理程序）

**边界案例：**

- 操作标识生命周期的保护：如果管道的调用者已经设置了标识（嵌套调用场景），最终清理块会恢复前一个值。
- 能力封锁响应包含结构化信息，告诉前端是哪个状态效果阻止了操作。
- 物品使用命令在合约级别放行了 itm0 临时槽检查后，处理程序层又做了二次检查 —— 如果使用非 0 槽位时 itm0 暂存中，仍会被拒绝。

#### 框架 B-4：日志即反馈

**设计意图：** 业务处理程序不直接返回错误信息，而是写入结构化日志条目。总线在执行后比较新的日志条目与预定义的反馈规则，从中推导出结构化错误响应。这种模式解耦了业务逻辑（只管写日志）和错误响应格式化（总线从日志读）。

**代码锚点：** `oblivions/include/command/obl_command_bus.php`（日志反馈推导）

**边界案例：**

- 反馈规则是硬编码的每命令映射 —— 将特定日志条目 ID 映射到错误代码。
- 此模式只在一个请求的生命周期内有效（内存中的日志收集器），不是持久化的日志分析。

#### 框架 B-5：乐观并发控制

**设计意图：** 前端在每个命令中附带它期望的服务端状态（玩家 ID、动作、战斗 ID、战斗状态）。如果实际状态与期望不符，总线拒绝执行而不产生任何副作用。这防止了陈旧客户端覆盖最新状态。

**代码锚点：** `oblivions/include/command/obl_command_bus.php`（乐观并发检查）

**边界案例：**

- 战斗状态的比较需要一次数据库查询 —— 不是简单的字段对比。
- 空期望不做任何检查。

#### 框架 B-6：基于文件的玩家锁

**设计意图：** 用文件锁而非数据库锁来防止同一玩家同时执行多个命令。锁文件以 `(房间 ID, 玩家 ID)` 二元组命名，非阻塞方式获取，失败时返回"命令执行中"错误。锁的获取与释放严格对称——命令总线在获取文件锁后立即将文件句柄存入全局变量，在 finally 块中显式释放（`flock UN` + `fclose`），确保正常返回、业务异常、PHP 致命错误三种路径下锁都被释放。致命错误路径由运行时关闭清理函数兜底，检查全局变量中的文件句柄并释放。获取阶段若 `flock` 失败也显式关闭已打开的文件句柄，避免描述符泄漏。

**代码锚点：** `oblivions/include/command/obl_command_bus.php`（文件锁获取与释放）

**边界案例：**

- 锁目录在第一次使用时惰性创建。
- 锁文件描述符不依赖 PHP 请求结束时的隐式资源清理——在 Windows 环境下隐式清理不可靠，显式释放是唯一可靠路径。

### 模块 C：核心运行时

#### 框架 C-1：拓扑引导加载

**设计意图：** 所有业务文件按严格的拓扑顺序加载，确保依赖先于使用；引导机制同时防止重复加载。整数主层为依赖骨架，半层用于在兄弟层之间插入共享基础设施——如共享战斗状态机先于战斗执行链、Tick 编排器紧随 tick 函数库。半层不破坏主层骨架，只是声明"此处需要插入一层共享依赖"。

**代码锚点：** `oblivions/include/core/obl_bootstrap.php`（拓扑加载编排：require_once 保证不重复加载，半层注释标明插入理由）

**边界案例：**

- Layer 6 在加载 tick 函数库后立即注册技能效果 tick 监听器，把技能效果系统接到 tick 调度的 post 阶段（用于 CD 递减、buff 过期等生命周期管理）。
- Layer 3-4.5 的旧战斗共享文件通过注释明确标记为"共享基础设施"——旧主执行链已删除，保留的文件仅提供数值计算和队列原语供新战斗系统复用，不作为独立执行路径存在。

#### 框架 C-2：独立运行时启动

**设计意图：** 运行时启动独立于旧版 PHPDTS 主入口 —— 自己连接数据库、读取 cookies、加载房间数据、初始化日志器和上下文。不依赖主游戏的公共引导文件。但仍复用旧核心的部分基础工具：全局工具函数库、玩家认证模块、配置加载模块、数据库类。因此更准确的说法是"不依赖旧版公共引导文件但仍与旧核心共享基础设施"，而非"完全独立于旧版核心"。

- 启动参数控制是否在数据库表/行缺失时自动创建它们。

**代码锚点：** `oblivions/include/core/obl_runtime.php`（运行时启动 + 事务原语 + 房间锁）

**边界案例：**

- 调试自动登录（开发环境存在特殊文件时强制设置 cookies）用于跳过正常认证。
- 启动参数控制是否在数据库表/行缺失时自动创建它们。

#### 框架 C-3：事务管理与房间互斥锁

**设计意图：** 提供显式的、可组合的事务边界和房间级别的互斥锁。这些原语由心跳和命令入口使用，但状态查询不使用。事务函数有嵌套保护（已在事务中时抛出异常），房间锁使用 MySQL 命名锁。

**代码锚点：** `oblivions/include/core/obl_runtime.php`（事务边界 + MySQL 命名锁）

**边界案例：**

- 回滚函数优雅处理连接丢失（MySQL 在连接断开时自动释放命名锁）。
- 关闭清理函数在 PHP 致命错误时也能回滚任何打开的事务和释放锁 —— 防御性编程。

#### 框架 C-4：事件批量投递（Presentation 系统）

**设计意图：** 命令或心跳执行期间产生的领域事件，在事务提交前冻结为一个演示批，提交后随响应投递。请求级收集器只维护事件顺序和回滚检查点，不生成回合编号或段落语义；数据库回滚时同步撤销未提交事件，避免播放不存在的回合。

**代码锚点：** `oblivions/include/core/obl_runtime.php`（演示批打包与投递）、`oblivions/include/game/battle_log.func.php`（战斗演出事件收集器）

**边界案例：**

- 如果玩家数据为空（如心跳时玩家尚未生成），状态快照使用全零默认值。
- 批的战斗 ID 通过反向扫描事件确定，而不是从玩家当前战斗 ID 直接取。
- 如果玩家角色标识无效，日志持久化直接跳过。
- `event_seq` 和 `batch_seq` 只承担传输排序，不能替代 `turn_seq` 或 `turn_key`。
- 未显式注入 `$writers['battle']` 时，`obl_runtime_persist_logs` 默认把 BattleLogCollector 事件流追加写入 debug 文件，供 BUG 复现分析。

#### 框架 C-5：Tick 编排器

**设计意图：** 集中决策 tick 推进的逻辑，有三种操作模式。命令执行后推进：保存玩家 → 记录 tick 行为 → 推进 tick → 刷新战斗状态。心跳追赶：补处理已产生但未处理的 tick。卡死恢复：检测并恢复卡死在处理中的战斗。

**代码锚点：** `oblivions/include/core/obl_tick_orchestrator.php`（tick 推进策略集中决策）

**边界案例：**

- 命令的"域"决定了 tick 引擎走什么解决路径 —— 战斗域还是世界域。战斗命令触发战斗域，其他触发世界域。
- 卡死恢复对不同类型发起者做不同处理：如果当前是玩家，重置回玩家回合；如果是 NPC，推进 tick 让 NPC 行动。

#### 框架 C-6：游戏仓库（游戏状态表）

**设计意图：** 将运行时状态从旧版游戏变量 JSON 迁移到专用的单行游戏状态表，包含类型化列。tick 值存储在列中，所有其他变量存储在 JSON 列中。提供创建、加载、保存、重置操作。加载有"是否自动创建缺失行"的参数。

**代码锚点：** `oblivions/include/core/obl_game_repository.php`（游戏状态表 CRUD）

**边界案例：**

- 只读路径遇到不存在的行时，创建一个内存中的"虚拟行"（带缺失标记）而不写入数据库。虚拟行仅存在于运行时全局与旧版游戏变量兼容镜像中，让无锁读路径能拿到默认 tick 值。
- 保存路径的插入/更新决策实际由加载函数的返回值决定 —— 返回缺失标记（表/行缺失）时走重置流程（先删除后插入），返回真实行时走更新流程。代码中虽有检查虚拟行标记并执行插入的分支，但由于加载函数总是直接查库而不读运行时全局，此分支在当前架构下实际不可达，属历史遗留防御代码。
- 生命周期状态同步有一个显式的参数控制 —— 因为错误的同步会破坏房间重启逻辑（旧运行中的状态会被当作新状态）。

#### 框架 C-7：旧版游戏变量兼容镜像

**设计意图：** 旧系统读写旧版游戏变量中的当前刻字段，新系统在游戏状态表的列中存储 tick 值，其他变量在 JSON 列中。这层透明地在两种表示之间同步。

**代码锚点：** `oblivions/include/core/obl_gamevars.php`（新旧变量同步镜像）

**边界案例：**

- 虚拟行路径（不自动从旧版迁移且数据库无行）经过兼容层时，从旧版游戏变量中的当前刻/已处理刻字段提取 tick 值填充虚拟行，而非从数据库 —— 让无锁读路径在不写库的前提下仍能返回有意义的 tick。
- 注释警告生命周期同步会破坏房间重启 —— 所以默认不开启生命周期同步。

#### 框架 C-8：运行时表 schema 自愈机制

**设计意图：** `oblivions/sql/*.sql` 中的 `DROP IF EXISTS + CREATE TABLE` 只在新开局时执行，运行中的表不会因字段新增（如 E-9 `last_refresh_day`、E-12 `placed_by_pid/placed_at_day/ttl_days`）而自动升级，导致 `day_changed` 事件触发的监听器报 `Unknown column`。该框架为运行时表（`oblmapstates` / `oblmappoi` / `oblmapitem`）提供幂等 schema 自愈：缺表则建表、缺字段则补字段、缺索引则补索引，每子函数内防重入。写入口（command / heartbeat）在运行时启动时调用总入口触发自愈；纯读入口 `state.php` 不触发 schema 副作用（参照 C-7 的 no-create 策略）。

**代码锚点：** `oblivions/include/core/obl_schema_ensure.php`（schema 自愈实现与总入口）

**边界案例：**

- `state.php` 是纯读入口，缺字段时自然返回错误状态，由调用方触发 command 路径修复，不在读路径上产生 ALTER 副作用。
- 各 schema_ensure 子函数使用防重入标志，同请求多次调用零开销；总入口同时调用 C-6 的 `obl_game_schema_ensure` 保持单点入口。
- `oblplayers` / `oblqueue` / `oblbattle_state` 暂未纳入（无最近字段变更）；后续若引入新字段，按本框架风格新增对应子函数并注册到总入口即可。

### 模块 D：战斗系统（Combat）

#### 框架 D-1：动作生命周期编排

**设计意图：** 动作层只执行已经由 E-5 开放并原子认领的权威回合，保持排序（终结技最后）→ 校验（AP 成本、标签规则）→ 执行（效果应用、持久化）的单一职责。`battle.start` 先用无副作用投影确定初始战斗名单，正式建场后把整条预提交动作链绑定到首个权威回合；动作层不创建回合、不递增序号、不恢复回合资源。

**代码锚点：** `oblivions/include/game/combat/combat.runtime.php`（动作运行时入口）、`oblivions/include/game/combat/combat.core.php`（动作编排与战斗调试日志桩子）

**边界案例：**

- 排序必须先于校验 —— 终结技必须排到末尾再进行 AP 和位置投影，否则中间动作会被错误移除。
- 行动者终止有四种条件（生命值归零、状态标记、逃离、死亡），会导致所有后续动作中断而非跳过。
- `battle.start` 中位于首个敌对动作之前的移动、增益等意图只在投影阶段预演；正式执行时与敌对动作共享 `turn_seq=1`，保证首回合所有动作事件都有同一个 `turn_key`。
- 调用方未提供已认领的 `EXECUTING` 回合，或行动者、`turn_seq` 与权威记录不一致时，动作入口拒绝执行。
- 战斗观测有两条平行通道：轻量观测桩子（命令级流程跟踪）与结构化事件流（权威投影对账），分别落盘到独立 debug 文件，新局初始化时清空。

#### 框架 D-2：四层预览/预演系统

**设计意图：** 提供无副作用的预校验，对应 4 个只读命令，分四个层级。L0（能否交战查询）：可达性检查 —— 不需要完整战斗上下文，用于前端"能否交战"预判。L1（单动作预览）：单动作校验 —— 用干跑模式检查解决、规则、AP，但不执行效果。L1.5（多目标预览）：多目标可达性预览 —— 在 L0 之上对候选目标集合批量求解，避免前端逐个发起 L0 请求。L2（动作链预览）：完整动作链模拟 —— 模拟整条动作链，含累积 AP 消耗和位置投影。所有四个命令均为只读合约，走命令管道但跳过保存与 tick 推进。

**代码锚点：** `oblivions/include/game/combat/combat.preview.php`（L0/L1/L1.5/L2 四层预校验）

**边界案例：**

- L0 检查的"交战计划"会枚举所有合法可达格子（遍历所有可通行瓦片 × 所有攻击技能），为每个格子生成移动+攻击序列，按总 AP 成本排序 —— 相当于穷举路径查找器。
- L0 的失败原因检查有严格顺序：行动者能力 → 目标可见性 → 目标能力 → 空间可达性。每一阶段可短路返回，前端据此展示最具体的失败原因。
- 能力封锁在空间可达性检查之前执行，返回结构化的"能力失败"信息供前端展示。
- 可见性检查（角色是否被观测到）在空间可达性之前执行 —— 即使目标在射程内但不可见，也返回不可达。
- 错误原因脱敏 —— 内部前缀被去除，只向用户暴露业务层面的原因。

#### 框架 D-3：效果应用器注册表

**设计意图：** 按效果类型注册的应用器注册表。目前有 6 个内置类型：伤害、治疗、移动、逃离、技能效果应用、AP 变更。效果按声明顺序先进先出地对每个目标应用。不可回滚 —— 失败仅记入日志。

**代码锚点：** `oblivions/include/game/combat/combat.effect.php`（效果应用器注册表）

**边界案例：**

- 致命错误（目标不存在）设置失败标记并中断整个动作；非致命失败只记日志，继续执行其余效果。
- 效果支持以行动者自身为作用域 —— 一个技能可以同时对目标造成伤害并治疗施法者自己。
- 移动效果应用器实际上是真正执行位移的入口 —— 内部通过底层移动原语完成坐标更新与日志发射，应用器自身负责目标合法性校验、位移向量解算与战斗上下文记录。代码注释中"应用器仅做验证和记录"的旧描述已过时。
- 逃离目标选择使用"maximin over immediate neighbors"算法 —— 仅对当前位置的相邻安全格子做评估，选择"到最近的其他活跃战斗成员距离最大化"的格子，而非全局搜索"到所有其他成员最远"的格子。这是一种贪心的局部最优策略，复杂度可控。

#### 框架 D-4：结构化战斗事件发射器

**设计意图：** `battlelog.v3` 将请求级传输元数据与领域坐标分离。`turn_opened` 明确陈述控制者、`opening_kind` 和 AP 恢复后的行动者快照；动作、效果、退场和终局事件携带同一权威 `turn_key`，每个动作和效果仍保持单次发射与关联 ID。

**代码锚点：** `oblivions/include/game/combat/combat.log.php`（battlelog.v3 领域事件构造器）

**边界案例：**

- 包含回滚检查点 —— 在目标结算中使用保存点回滚时可以撤销已发射的事件。
- 原因映射：内部使用 `dead` 标记，对外暴露为 `death` 原因。
- 泄露 ID 按类型分组追踪，用于清除事件引用特定效果。
- `turn_opened.event_uid` 由 `qid` 与 `turn_seq` 确定，重试不能生成第二个回合宣告身份。

#### 框架 D-5：目标结算单元

**设计意图：** 每个目标的完整结算循环：绑定最新数据 → 规则校验 → 参与状态判定 → 声明效果 → 投递 → 征召 → 应用效果 → 持久化。每个目标在数据库保存点保护下执行，业务失败时原子回滚到结算前状态，让单个目标失败不污染后续目标。

**代码锚点：** `oblivions/include/game/combat/combat.target_unit.php`（目标结算循环 + 保存点回滚）

**边界案例：**

- 失败回滚覆盖三层：内存上下文快照（防止后续目标读到污染状态）、日志检查点（回收已发射事件）、数据库保存点（撤销已写入行）。
- 空目标策略有两种：无目标时仍执行投递（用于全局效果），或回滚报错。
- 资源预扣和提交都是幂等的 —— 防止重入或混合干跑/真实场景中双倍扣减。

#### 框架 D-6：目标捕获注册表

**设计意图：** 注册表驱动的目标捕获系统，有四种内置策略：直接角色、战斗敌对、格子角色、自我标识。将解析后的瞄准目标转换为有序的结算目标列表。

**代码锚点：** `oblivions/include/game/combat/combat.target_capture.php`（目标捕获策略注册表）

**边界案例：**

- 读取数据有三层回退：运行时内存 > 计划状态内存 > 数据库（按优先级读取确保动作链内的读一致性）。
- 格子角色策略从三个源头合并角色标识后去重，再反向删除空间不一致的条目。
- 结构校验拒绝重复的角色目标。

#### 框架 D-7：战斗上下文

**设计意图：** 单次动作执行的唯一状态载体，通过引用传递消除隐式状态耦合。效果和快照按目标独立存储。

**代码锚点：** `oblivions/include/game/combat/combat.context.php`（战斗上下文状态载体）

**边界案例：**

- 数据通过引用赋值传入，修改会回流到调用方 —— 对跨动作状态共享至关重要但需要仔细跟踪。
- 空目标列表时返回专用的空引用哨兵，防止悬空引用。
- 标签缓存绑定到当前目标索引，切换目标时忘了失效会导致标签使用错误目标的状态。

#### 框架 D-8：标签派生与规则匹配

**设计意图：** 声明式标签系统，将游戏状态派生（纯读）与配置驱动的规则匹配解耦。标签分两类：每次重新计算（如 `self`、`tile_impassable`）和从可变标记读取（如 `dead`、`escaped`）。

**代码锚点：** `oblivions/include/game/combat/combat.tag.php`（标签派生 + 规则匹配）

**边界案例：**

- 特定标签只对特定目标类型生效 —— 格子类标签只在格子目标上返回有效值，其他目标类型上固定为假。
- `self` 标签双重角色：既是技能指定目标为自身时的条件，也可拦截玩家误选了自己作为角色标识目标。
- 规则匹配是纯配置驱动的 —— 遍历禁止标签列表，只要任何一个标签为真就匹配失败。零业务逻辑。

#### 框架 D-9：技能配置校验与模块加载

**设计意图：** 以严格的模式级校验在加载时一次性拒绝非法技能配置——覆盖瞄准与捕获策略的组合、参与策略、关系约束、空目标策略、射程配置、可见性策略及其与瞄准解析器的兼容性、投递类型等维度的兼容性约束。校验失败抛异常阻止配置生效，避免非法配置进入运行时后才暴露。按需加载模块文件。

**代码锚点：** `oblivions/include/game/combat/combat.skill.php`（技能配置校验 + 模块加载）

**边界案例：**

- 四种内置捕获策略各自定义了强制性的瞄准、参与、排序组合，校验时强制执行，违反则抛异常。
- 可见性策略与瞄准解析器有兼容性约束：要求格子揭示的策略必须配格子瞄准，要求角色发现的策略必须配角色标识瞄准。
- 缺失模块不报错——某些技能是纯配置驱动的，不需要 PHP 钩子。

#### 框架 D-10：动作链投影器

**设计意图：** 统一校验和预览链的干跑语义。按执行顺序维护计划状态，通过技能钩子声明效果，再通过效果投影器将其投影到计划状态。

**代码锚点：** `oblivions/include/game/combat/combat.chain.php`（动作链投影器）

**边界案例：**

- 冷却待处理追踪 —— 链内已"使用"的技能被记录，同链内相同技能后续动作会被拒绝。
- 链内行动者终止会中断整个链，后续动作跳过。
- 失败时回滚计划状态 —— 恢复到动作执行前的快照，确保失败不污染后续动作。

#### 框架 D-11：战斗状态管理

**设计意图：** 操作内存中的战斗成员名单和可变标记数据结构。对攻击管道执行三分支死亡检测。清理已退出的参战者。

**代码锚点：** `oblivions/include/game/combat/combat.state.php`（战斗状态管理 + 死亡检测）

**边界案例：**

- 三分支检测的优先级是：`escaped` > 存活 > `dead` —— 已经逃离的角色不能被标记为死亡。
- 退役清理函数有二次调用保护 —— 如果动作已为空，说明已清理过，直接返回。
- 清理操作（无论 `dead` 还是 `escaped`）都会将角色 AP 重置为最大值 —— 虽然对死亡角色无实际意义，但保持世界状态一致性。

#### 框架 D-12：五种射程解析模式

**设计意图：** 基于技能配置的射程模式，支持五种模式：固定值、继承、累加、带上限累加、移动力换算。同时提供空间决策 —— 综合可达性、射程、可负担性的判定。

**代码锚点：** `oblivions/include/game/combat/combat.range.php`（五种射程模式 + 空间决策）

**边界案例：**

- `range.mode` 与 `ap_calc` 是两个独立的配置字段。`range.mode` 为移动力换算时基础射程由移动力决定，而有效射程来自 `ap_calc` 对应的预算投影器（仅移动力距离注册了投影器）。若技能配置 `range.mode` 为移动力换算但 `ap_calc` 为固定值，则有效射程为空，空间决策回退到基础射程。不应将两者混为一谈。
- 空间决策的资源感知：如果资源已被预扣，使用预扣前的 AP；未被预扣时使用当前 AP。

#### 框架 D-13：五态参与分类器

**设计意图：** 将候选目标分为五种参与状态：成员、可加入、已离开、其他战斗、被封锁。处理征召目标入伍。分类决策流依次检查策略、有效性、区域（玩家所在区域组是否与目标可达）、关系、队列成员、能力，每个阶段可能短路返回，避免后续检查产生副作用。

**代码锚点：** `oblivions/include/game/combat/combat.participation.php`（五态参与分类器）

**边界案例：**

- 策略为空时返回"不适用"哨兵——这是短路返回值，不进入五态分类，也不触发征召。
- 敌对/友好关系的计算基于角色类型字段（玩家 vs NPC）—— 跨阵营即为敌对，同阵营为友好。
- 分类器使用行级锁锁定数据库行保证竞态安全。

#### 框架 D-14：效果投影器注册表

**设计意图：** 效果应用器的镜像层，用于干跑/计划状态投影。共享相同的效果类型集合（伤害/治疗/移动/逃离/技能效果应用/AP 变更），设计上运行于模拟状态之上：不发射日志、不写入数据库、不触发钩子。技能效果应用投影器复用真实应用器函数——只要传入的是计划状态角色数组，函数本身无副作用。但共享意味着函数未来若新增副作用，投影路径会自动继承，需建立隔离机制（如标记接口或运行时检查）。

**代码锚点：** `oblivions/include/game/combat/combat.effect_projector.php`（效果投影器注册表）

**边界案例：**

- 数值类效果（伤害、治疗）投影器与应用器共享完全相同的数值公式，但纯内存操作。
- 移动投影器与应用器逻辑存在显著差异：应用器通过底层移动原语执行真实位移（含日志、钩子），投影器仅做空间决策一致性校验后直接修改内存中的位置/区域字段——"镜像"仅适用于无副作用的数值类效果。
- 逃离投影器通过状态管理接口走与应用器不同的状态变更路径。
- 投影后自动同步计划状态中的行动者数据，使链中后续动作可见。

#### 框架 D-15：AP 钱包计算器

**设计意图：** 注册表驱动的 AP 计算，支持静态值和动态值（移动力换算）两种计算器。AP 预算投影器补充计算器，提供可用于射程计算的 AP 预算。

**代码锚点：** `oblivions/include/game/combat/combat.ap.php`（AP 计算器 + 预算投影器）

**边界案例：**

- 未知的计算器 ID 回退到固定值计算器，不影响战斗。
- 预算投影器和计算器是两个独立的注册表，且容错策略不同：计算器对未知计算器标识有兜底（回退到固定值），预算投影器对未知计算器标识没有兜底（直接返回空，空间决策回退到基础射程）。

#### 框架 D-16：瞄准目标解析

**设计意图：** 将前端意图（意图类型和目标 ID）通过四个已注册解析器（`pid`、`tile`、`self`、`none`）转换为后端解析结果。

**代码锚点：** `oblivions/include/game/combat/combat.aim.php`（瞄准目标解析器注册表）

**边界案例：**

- 解析失败时，根据技能配置的可见性策略选择不同的暴露原因：`revealed`/`detected`/`visible` 策略返回"目标不可见"，而 `none`/`controller_known` 策略返回"目标未找到"。这是一种信息安全的考量——只有要求可见性的技能才暴露"不可见"信息。
- 规则检查暂时替换上下文的目标列表为仅含单目标，规则匹配后恢复。

#### 框架 D-17：可见性决策系统

**设计意图：** 基于可见性策略确定目标是否可见。策略是配置枚举，把"谁能看见谁"从硬编码提取为配置项，让玩家迷雾与 NPC 感知走不同路径：玩家行动者受迷雾系统约束，NPC 行动者通过专属策略绕过迷雾检查（迷雾是玩家的地图知识限制，与 NPC 无关）。

**代码锚点：** `oblivions/include/game/combat/combat.observation.php`（可见性决策系统）

**边界案例：**

- 同一战斗的成员始终可见，无论迷雾或距离。
- 策略对目标类型有强约束：要求格子揭示的策略只接受格子目标，要求角色发现的策略只接受角色目标，类型不匹配直接拒绝而非降级。
- 保留枚举值当前未实现，调用时返回策略不可用错误而非降级到其他策略。

### 模块 E：游戏逻辑

#### 框架 E-1：Tick 驱动事件调度

**设计意图：** 游戏的主时钟机制。核心概念是当前刻与已处理刻的对偶。业务系统通过三段监听器注册机制接入：战斗 NPC（串行，最多消费一个高级请求后跳出）、空闲 NPC（顺序执行所有监听器，不提前跳出——"并行"含义是全部执行而非并发）、善后（串行，已用于技能效果生命周期管理如 CD 递减、buff 过期等，非预留）。推进策略与推进机制分离。监听器契约强约束：监听器可修改战斗结果、状态、体力等字段，但不得修改玩家位置（区域/格子）——位置由移动命令的纯净基础操作唯一控制，监听器越权修改位置会破坏时间调度器的权威顺序。Tick 编排器在结算后比对位置快照，发现漂移时记录严重级别错误日志便于运行时监控捕获。

**代码锚点：** `oblivions/include/game/tick.func.php`（Tick 驱动事件调度 + 监听器契约）

**边界案例：**

- 异常处理：异常捕获块记录错误日志后重新抛出异常，异常向上传播而非被吞掉。状态机在异常捕获块中不做任何修改，因此"保持当前状态"成立。
- 同一 tick 内防止同一行动者重复执行 —— 域（战斗/世界）严格限定，冲突时记录到调试日志。
- 战斗域监听器串行化 —— 最多消费一个高级请求后跳出。
- MVP 限制：仅支持单人玩家（通过当前用户单例实现）。
- 监听器修改玩家位置视为契约破裂，编排器不同步位置（避免让监听器越权合法化）；未来需支持陷阱传送等位置修改场景时，需在契约层面显式声明能力并同步位置。

#### 框架 E-2：统一角色数据模型

**设计意图：** 定义了所有游戏实体的共享数据架构和生命周期 —— 玩家与 NPC 使用相同的表（通过角色类型字段区分）。所有非规范数据通过 JSON 字段结构化存储。提供对称的编解码函数，以及按角色标识、名称、批次、区域获取的功能。

**代码锚点：** `oblivions/include/game/player.func.php`（统一角色数据模型）

**边界案例：**

- 背包槽位动态补齐 —— 从索引 0 到最大槽位数，缺失键自动设为空值。
- 装备字段空字符串变为空数组，格式错乱的 JSON 优雅降级。
- NPC 类型触发专门的技能默认值注入。
- 创建玩家记录时从旧 PHP 格式字段映射为新结构化格式 —— 一次性迁移。

#### 框架 E-3：基于图的移动与多行动导航系统

**设计意图：** 基于瓦片邻接表的多行动导航系统承载两层抽象。底层是纯净的移动基础操作（不写库、不写日志、不触发钩子），仅修改内存位置并返回原因；上层是导航循环，一次高层命令内编排多次原子移动，每次移动由 E-1 时间调度器独立结算一个完整游戏刻，导航器依据本刻最终权威状态判断抵达、中断或继续。原子移动语义不可拆分——一次原子移动消耗一个游戏刻、产生一个最终落点、触发一次信息获取（由 E-7 承担），中间路径不形成权威位置、不按格推进时间、不按格触发普通地图事件。玩家指定目标与自动选目标共用同一寻路基础操作；四种移动倾向在目标选择与路径选择两阶段以配置驱动差异化，距离过滤仅在自动选目标阶段生效，玩家指定目标必达。自动目标按"可达未探索 > 未发现 POI > 隐藏敌人搜索位置"三级优先级选择；隐藏敌人搜索位置是命令创建时的位置快照，不向前端泄露敌人实体信息。

**代码锚点：** `oblivions/include/game/move.func.php`（基础操作 + 命令包装器）、`oblivions/include/game/navigation.func.php`（导航循环 + 目标解析 + 中断判断）

**边界案例：**

- 玩家指定的导航锚点与实际落点是两个不可混淆的领域事实：锚点保持玩家原始意图，落点负责执行寻路；目标不可通行或被单位占据时解析为附近合法落点，但结果必须保留原目标、实际落点和全部调整原因；占位反馈只公开图格不可落脚，不借隐藏真值泄露占据者身份。
- 多行动导航中断六类按优先级判定：强制战斗（最高优先级，由外部事件触发）→ 抵达目标 → 敌人发现 → POI 发现 → 移动力耗尽 → 能力丧失。已完成移动与游戏刻是权威事实立即保留；未执行的下一次移动不消耗资源、不推进游戏刻；原目标失效或不再存在可达路线时中断，不静默改选另一个目标。
- 已发现 POI 永久退出自动探索目标池（不论是否已互动）；已发现敌人不是自动移动目标；普通地面道具不进入自动探索目标池；隐藏敌人在导航过程中被击杀或突袭玩家时其搜索位置失效。
- 不自动执行的行为：战斗启动、POI 搜刮/互动/拆除、道具拾取、区域切换、主动位移技能消耗。抵达目标必定停止，不自动从当前目标继续选择下一个目标。
- 单次导航步数上限按区域对角线动态计算并受配置上界约束；达到上限时返回独立终态，前端可断点续导航（续发命令携带实际落点与倾向），自动目标在断点处重新选目标，不丢失已完成移动与游戏刻。

#### 框架 E-4：结构化事件日志系统

**设计意图：** 取代旧的 HTML 字符串日志机制。后端输出结构化事件（ID、类别、参数），前端控制所有视觉呈现。有两个物理隔离的日志系统：游戏事件日志和诊断错误日志。持久化采用"读取-合并-倒序计数裁剪-写回"模式：先读取已有日志文件，追加新条目，从末尾倒序计数保留最新 N 条，最后以正序写回 —— 每个文件独立配额。

**代码锚点：** `oblivions/include/game/log.func.php`（结构化事件日志系统）

**边界案例：**

- 常规日志与调试日志条目有独立配额（200 常规 vs 50 调试），调试条目不会排挤玩家操作反馈。
- 调试 ID 列表标记高频事件（如敌人移动），前端默认不渲染。
- 错误日志固定 50 条，与常规日志物理隔离。

#### 框架 E-5：权威战斗与回合生命周期状态机

**设计意图：** 每个 `qid` 由一行 `oblbattle_state` 持久化当前回合身份和四态边界：`IDLE`、`AWAITING_INPUT`、`AUTO_PENDING`、`EXECUTING`。只有回合开放能递增 `turn_seq`；玩家命令和 NPC tick 都必须先按当前状态、`active_pid`、`turn_seq` 原子认领，再进入动作执行。AP 恢复与回合开始效果在输入开放前完成，关闭当前回合后才向 I-1 请求下一候选者。

**代码锚点：** `oblivions/include/game/battle_state_machine.func.php`（持久状态与原子转换）、`oblivions/include/game/battle_turn.func.php`（回合开放、认领与关闭编排）

**边界案例：**

- 同一 `expected_turn_seq` 第一次认领后状态已进入 `EXECUTING`，重复提交、旧页面提交和错误 PID 均返回陈旧回合。
- 回合开放期间行动者失效时不发布输入状态或普通横幅，关闭该身份并继续选择下一候选者。
- `EXECUTING` 卡死恢复按 `active_pid` 的控制类型回到 `AWAITING_INPUT` 或 `AUTO_PENDING`，保留原回合身份。

#### 框架 E-6：视野与地图认知状态系统

**设计意图：** 提供地图格的认知状态查询与持久化基础。地图认知三态独立——`currently_visible`（运行时计算，不持久化，由 BFS 视野范围派生）、`revealed`（持久化于 `oblmapstates.fog` 字段，迷雾已点亮可见地形）、`explored`（持久化于 `oblmapstates.explored` 字段，玩家曾经以最终位置站上该格的真实空间覆盖状态），三态互不蕴含。视野范围计算基于瓦片图 BFS（不可通行格可见但不再扩展，"你能看到远处的山但不能看穿它"）。迷雾清除采用幂等 UPSERT（`fog=1` 标记 `revealed` 状态）。敌人发现的基础函数定义在本框架（反应式可见性——超出玩家视野或在迷雾格中移动的敌人变为未发现），由 E-7 统一信息获取编排调用。地图拓扑与动态通行四层分离——背景空间（永远不能站立、没有独立游戏内容的区域边界、墙、空洞）不是图格；真实图格拥有动态通行状态，可被破坏为不可通行或修复为可通行；两个真实图格之间的墙属于连接状态，不通过插入假图格表达。已探索图格被破坏后仍保持已探索（历史事实不回退）。单位占位校验（一个图格最多一个单位，玩家与敌人不能重叠）通过查询当前格的其他实体现有。

**代码锚点：** `oblivions/include/game/vision.func.php`（视野范围 BFS + 迷雾清除 + 敌人发现基础函数）；三态字段持久化于数据库表 oblmapstates（fog 字段对应 revealed 状态 / explored 字段对应 explored 状态）

**边界案例：**

- BFS 经过不可通行的瓦片但不会穿越它们：你能看到远处的山但不能看穿它。
- 三态独立——`currently_visible` / `revealed` / `explored` 互不蕴含；清除迷雾、从旁经过、路径预览或远程观察都不能把格子标记为已探索；`explored` 唯一写入入口是 `obl_mark_explored`（仅落点写，由 E-7 调用）。
- 已死亡的敌人保留原有发现状态（方便搜刮）。
- 视野范围大于迷雾清除范围——你会发现敌人但看不清地面细节；发现敌人时一次性点亮敌人所在格，之后不再因敌人移动而点亮新格。
- 敌人移动到迷雾格时变为未发现，不点亮迷雾——发现状态与所在格迷雾状态联动。
- 已探索图格被破坏后仍保持已探索（探索状态是历史事实，不因当前不可通行而回退）；未探索图格暂时不可通行时退出当前移动候选，但不被伪造为已探索。
- 一个图格最多一个单位；被单位占据的图格不是合法落点；隐藏敌人不因占位校验被前端提前显示。
- 迷雾首期只启用"未揭示 / 已揭示"两档，底层允许未来扩展认知等级。

#### 框架 E-7：统一信息获取与探索编排系统

**设计意图：** 提供统一的信息获取原语，按行动类型配置形成差异——移动用基础预算、探索用强化预算（技能化上限）、战斗移动仅点亮迷雾与地图不发现道具/敌人/POI 避免战斗内信息泄漏。原语内部按场景过滤信息类别，依次执行视野计算（复用 E-6）→ 迷雾点亮 → 道具发现（按预算 + 概率修正）→ 敌人发现 → POI 发现（100% 发现）→ 返回结构化结果（含注意力等级）。两个真实消费者：移动后钩子用基础配置、探索命令用强化配置（技能化上限由 G-1 scavenge 决定，技能系统未加载时回退兜底）。探索命令在原语之上承担体力检查（不足时降级为等待，不消耗探索体力）与探索后钩子三段式占位。注意力等级四态单向升级：常规（迷雾/地形）→ 道具（写日志、地图标记，不中断导航）→ 重要（POI/关键道具/敌人，中断导航）→ 强制（陷阱/突袭/战斗，由外部事件触发器追加升级，本原语不直接设置）。机制型 POI 走独立的机制分发框架，与 E-10 三档判定并列；POI 搜刮/互动命令由命令层直接路由到 E-10，不经本框架。

**代码锚点：** `oblivions/include/game/info_acquire.func.php`（统一信息获取原语 + 注意力等级计算）、`oblivions/include/game/explore.func.php`（探索命令编排 + 体力降级 + 探索后钩子）

**边界案例：**

- 移动与探索共用同一原语但配置形成差异——移动基础预算远低于探索；探索上限由 G-1 scavenge 技能等级决定，技能系统未加载时回退兜底不抛异常。
- 注意力等级单向升级——常规 → 道具 → 重要，强制等级由外部事件触发器追加升级，本原语不直接设置。
- POI 100% 发现——进入有效信息范围即发现，不受概率/预算限制；已发现的 POI 永久退出自动导航目标池。
- 道具发现按距离分档——脚下+相邻格正常可见，视野边缘格标记为近视/拟态怪；已发现的不降级，同一格重复探索可继续发现剩余未发现道具。
- 探索降级为等待——体力不足但玩家具备行动资格时降级为等待，不消耗探索体力，玩家可在下一 tick 再次探索。
- 战斗移动边界——仅点亮迷雾与地图，不发现道具/敌人/POI，避免战斗内信息泄漏。
- 同一 tick 内不会出现两次探索调用——探索命令推进 tick；移动后钩子用基础配置，不重复消耗探索体力。

#### 框架 E-8：NPC AI 行为系统

**设计意图：** NPC 通过 tick 监听器机制接入：战斗 NPC 在自己的轮到当前顺位时执行战斗回合，非战斗 NPC 按 AI 类型巡逻/搜寻/发呆。NPC 与玩家共享统一数据模型，可以穿越迷雾。行动前先按优先级通过多检查点短路判定（标识 / 存活 / 能力 / 战斗域占用 / 行为已征召），任一命中即返回原因；战斗技能选择按"可用攻击技能优先 → 逃跑兜底 → 发呆兜底"链式决策。发现状态反应式联动——敌人离开玩家视野或移动到迷雾格时变为未发现（不点亮迷雾），仅在已点亮格内移动时保持发现。

**代码锚点：** `oblivions/include/game/enemy_ai.func.php`（NPC AI 行为系统）

**边界案例：**

- 行动意愿门控：每个 tick 按配置的概率随机判定是否行动，未通过则本 tick 不行动（软门控，区别于硬封锁的能力检查）；非战斗 NPC 战斗中跳过 tick 结算由战斗系统接管。
- 阻塞原因优先级短路——标识无效、死亡或非活跃、能力封锁、战斗域占用、行动者已在某场战斗中、已有待处理行为请求、行为已被其他系统征召，每个检查点可短路返回对应原因字符串。
- 移动检查同时判断可通行性、玩家占用、其他实体占用，三者任一不满足则不移动。

#### 框架 E-9：静态世界生成系统

**设计意图：** 每个区域独立的资源生成。以潮汐区为桶分组，每个桶独立应用 POI 池和散落道具池配置。POI 放置去重（每格一个 POI），道具散落按格概率判定。时间流逝刷新由 E-11 day_changed 事件监听器全局触发——每当天数递增时刷新一次，scatter_pool 分 initial/refresh 双相位，容量计数采用批量 COUNT 方案（不维护冗余字段），潮汐倍率作用于刷新概率（越危险越丰沛）。

**代码锚点：** `oblivions/include/game/generate.func.php`（区域初始化生成）、`oblivions/include/game/wild_refresh.func.php`（按天刷新 + day_changed 事件监听器）

**边界案例：**

- 可用瓦片数可能少于请求的 POI 数量，自动调整。
- 配置驱动 —— 池或表为空时跳过（无硬依赖）。
- 全局扫描所有"已发现过"的图格（`fog=1 OR last_refresh_day>0`）且 `last_refresh_day < 当前天` 的图格刷新，不限当前玩家区域 —— 野生道具刷新是世界行为。
- per-tile 的 `last_refresh_day` 检查确保同格同天最多刷新一次；多 tick 推进跨多天时由 E-11 day_changed 事件触发多次刷新。
- POI 产出道具（`source_iaid>0`）被批量 COUNT 天然过滤，不计入野生容量。

#### 框架 E-10：POI 搜刮三档判定系统

**设计意图：** POI 搜刮的掷骰与结果生成系统。三档判定按优先级依次进行——保底档（pity_timer 跨 POI 共享，达阈值强制掉落）→ 事件档（按 event_pool 配置加权随机选事件，通过命名约定分发到独立事件函数）→ 普通档（调用 F-4 引擎掷骰产出物品实例）→ 空档（前三档均未命中）；前三档任一命中即停止后续判定。POI 状态机采用乐观锁推进，搜刮后状态推进由模板配置驱动。**并发不变式：先原子推进状态机 → 乐观锁成功后再物化 loot**，避免并发搜刮双倍物化；四档共用同一推进函数，任一档乐观锁失败均不物化、不重置 pity_timer、不施加事件伤害。搜刮结果直接物化为可拾取的地图道具实例，玩家通过通用拾取命令取件——与野生道具流程一致，不引入暂存或额外取件命令。概率修正按白名单收集，在概率计算末尾统一收敛到合法区间，不阻塞搜索流程。mechanic 型 POI 走独立的机制分发框架，与三档判定并列存在。

**代码锚点：** `oblivions/include/game/poi/poi.search.func.php`（三档判定主流程）、`oblivions/include/game/poi/poi.event.func.php`（事件池分发框架）

**边界案例：**

- 状态机乐观锁冲突时所有副作用均以状态推进为前置条件——失败时不物化 loot、不重置 pity_timer、不施加事件伤害、不删除已物化道具。
- 保底档优先级最高——pity_timer 达阈值时强制进入保底档，跳过事件档与普通档；保底档完成后 pity_timer 重置。pity_timer 写入 DB 后调用方需同步更新内存缓存以保持本轮后续读一致。
- 概率修正统一收敛——任何来源的概率修正累加后超界时统一收敛到合法区间，搜索流程继续，玩家无感知。
- 事件函数未定义降级——找不到事件处理函数时记录调试日志并返回空结果（无物品、无状态变更），搜索流程继续推进状态机。
- 事件函数返回结构可携带状态变更、删除已物化道具、施加伤害等副作用信号，由主流程统一执行——事件函数本身不直接操作状态机或玩家状态。

#### 框架 E-11：天与昼夜相位派生层

**设计意图：** 在刻（tick）之上建立宏观时间语义层。天与昼夜相位都是从 tick 派生的纯函数——天数由 tick 与每日刻数的比值推导，相位由 tick 在每日周期中的位置与昼相位阈值比较推导。tick 推进后立即检测相位/天数变化，同步触发相位切换事件。监听器机制提供三类事件：昼开始（`day_started`）、夜开始（`night_started`）、天数递增（`day_changed`）——供 POI 耐久衰减、夜间事件、野生道具按天刷新等业务系统订阅。事件在 tick 推进调用栈内同步触发，不引入异步队列。$gamevars 兼容镜像同步 `obl_day` / `obl_phase` 字段，与 `obl_tick` / `obl_pretick` 同模式由 `bra_oblgame` 表持久化。

**代码锚点：** `oblivions/include/game/day_cycle.func.php`（天与相位派生、事件钩子、监听器注册）；tick 推进钩子接入点位于 oblivions/include/game/tick.func.php（归 E-1，本框架仅引用其调用约定）

**边界案例：**

- 刻推进与相位切换是同步原子事件——同一 tick 推进内若同时跨过相位边界和天数边界，两个事件按 day_started → day_changed 顺序触发（夜→昼切换意味着新一天开始）。
- 配置项 `day_length_ticks` 与 `day_phase_ticks` 必须满足 `day_phase_ticks < day_length_ticks`，否则校验失败回退默认值。
- 天数从 1 开始而非 0——游戏开局即处于第 1 天昼相位。
- 战斗域 tick 推进同样触发相位检测——战斗中也可能发生昼夜切换，但不影响战斗流程。
- 监听器异常被捕获防扩散——day_changed 监听器抛异常时记录日志，不阻塞其他监听器或 tick 推进调用栈。

#### 框架 E-12：POI 耐久系统

**设计意图：** POI 实例层通用耐久属性——任何 POI 模板声明 `ttl_days>0` 即纳入到期清理流程，与世界生成 POI 兼容（默认 0=永不过期）。三字段持久化于 `bra_oblmappoi` 实例表：`placed_by_pid`（0=世界生成，>0=玩家放置）、`placed_at_day`（放置时的游戏天）、`ttl_days`（生存期天数）。到期清理由 E-11 `day_changed` 事件监听器批量执行——扫描到期 POI，级联清理其已物化但未拾取的战利品，单次事务完成。E-9 wild_refresh 与 E-12 在 day_changed 监听器层并列，互不依赖。tile_actions 投影扩展耐久字段与 `dismantle_returns`（F-7 拆除返还材料，POI 模板直投）。耐久作为 POI 实例层的通用属性，不耦合于具体模板，任何未来需要"过期自动消失"的 POI 类型（如临时陷阱、召唤物）只需声明 ttl_days 即可。

**代码锚点：** `oblivions/include/game/poi/poi.durability.func.php`（day_changed 事件监听器）；表结构位于 oblivions/sql/oblmappoi.sql（SQL schema 文件不参与 @framework 校验）

**边界案例：**

- 世界生成 POI 默认 ttl_days=0——不参与到期清理；玩家放置 POI（F-7）从模板读 ttl_days 写入实例，参与到期清理。同一模板的两种来源在实例层通过 `placed_by_pid` 区分。
- ttl_days 配置由 POI 模板声明——世界生成器读模板时不复制 ttl_days 到实例（保留默认 0）；F-7 place_poi effect 读模板 ttl_days 写入实例。这是配置层的"读取时机差异"，避免世界生成 POI 被错误标记为短暂存在。
- 到期清理与玩家在线/离线无关——监听器在 day_changed 事件触发时执行，无论放置者是否在线。
- ttl_remaining_days 为派生字段——后端 tile_actions 投影时实时计算，不持久化；null 表示永不过期（ttl_days=0），前端隐藏耐久信息行。
- 监听器异常隔离——抛异常时由 E-11 监听器机制捕获，不阻塞其他监听器或 tick 推进；已删除的 POI 不可恢复。
- 跨天批量推进——多 tick 推进触发多次 day_changed 事件，每次事件独立扫描到期 POI，确保所有到期 POI 都被清理。

#### 框架 E-13：移动方式与轨迹拦截框架

**设计意图：** E-3 的纯净基础操作原本只承载单一"普通移动"语义。本框架在其上引入"移动方式"参数维度——以配置驱动注册表声明每种移动方式的属性（范围、距离计算、是否需真实路径、阻挡规则、落点合法条件、轨迹可拦截性、信息足迹、演出类型），让同一次原子移动可承载普通/飞行/跳跃/传送等不同语义而不必为每种语义复制一套移动系统。同时在原子移动执行前预留一次"轨迹拦截"判定窗口——拦截规则有机会改写最终落点，但事件顺序由 E-1 时间调度器研判，保持"一个游戏刻一个最终落点"的核心不变量。信息足迹三种模式：普通移动合并路径沿途视野范围、传送只用最终落点观察范围、飞行/跳跃预留空中走廊模式。首期只实现普通移动；其余仅作为配置槽位存在；拦截规则注册表首期为空，只建立接口。不破坏 E-3 纯净基础操作契约——本框架的组合原语不写库、不写日志、不触发钩子；不自动消耗主动位移技能（主动技能型位移需玩家明确授权）。

**代码锚点：** `oblivions/include/game/move_types.func.php`（移动方式注册表 + 轨迹拦截接口 + 信息足迹原语）

**边界案例：**

- 寻路允许目标格本身不可通行（仅中间节点必须可通行）——同时支持"绕墙改路"与"迷雾格作为导航锚点"两种语义；落点合法性由落点解析在目标附近搜索合法落点。
- 玩家指定目标的三类语义已由 E-3 导航器支持，本框架不重复实现，仅在测试中验证。
- 轨迹经过不触发中间格事件——只有最终落点才执行落点规则与信息获取；信息足迹三种模式由移动方式声明。

### 模块 F：物品系统

#### 框架 F-1：槽位背包与 itm0 暂存槽协议

**设计意图：** 物品栏是编号槽位系统，有一个特殊的 0 号槽（itm0）用于物品中转。拾取 → itm0 → 自动整理 → 背包。合成产品 → itm0 → 自动整理 → 背包。堆叠合并、拾取、丢弃、整理围绕这个核心协议设计。

**代码锚点：** `oblivions/include/game/item/item.basic.func.php`（槽位读写、堆叠合并、拾取、丢弃、整理）

**边界案例：**

- 无限标志 `∞` 作为一等公民贯穿所有操作（不递减、PHP 原生比较）。
- 堆叠合并要求参数完全相同（序列化为排序后的键字符串比较）。
- 堆叠合并的原子性：两遍算法 —— 先计算容量，不足直接返回 false，不产生变更。
- 拾取操作对近视物品进行揭示，陷阱物品原子删除且不获得任何道具。

#### 框架 F-2：配置驱动的合成系统

**设计意图：** 整个合成系统是配置驱动的 —— 配方是纯数据，引擎是通用的。材料匹配分三层（ID > itmk 类别 > 标签），有三种消耗模式（全部消耗、消耗耐久、不消耗）。工作台材料对消耗模式有约束（只能匹配不消耗类）。

**代码锚点：** `oblivions/include/game/item/item.craft.func.php`（配方匹配引擎、素材消耗、工作台约束、失败诊断）

**边界案例：**

- 堆叠物品展开为多个虚拟占位；非堆叠物品约束为数量=1。
- 所有占位必须被匹配消耗 —— 多余物品导致匹配失败。
- 配方失败时有诊断分析 —— 统计所有配方的失败原因，返回最频繁的一个。

#### 框架 F-3：使用效果分发器

**设计意图：** 一个纯净的注册器模式 —— 框架本身不定义任何具体效果。具体效果函数由所属子系统注册（通过命名约定）。效果从模板查找，不是从实例。

**代码锚点：** `oblivions/include/game/item/item.use.func.php`（use_effect 分发器、耐久消耗、模板查找）、`oblivions/include/game/item/item.use_effects.func.php`（已注册效果函数集合）

**边界案例：**

- 使用效果不存在的函数不是崩溃而是记录警告。
- 耐久消耗仅对有限耐久值操作，无限标志不受影响。
- itms 扣减由框架在 effect 之后统一处理，效果函数内部不自行扣减（与 F-6 同模式）。

#### 框架 F-4：战利品表引擎

**设计意图：** 物品系统的"生成侧入口"——POI 搜刮的物品生成引擎。配置驱动，战利品表是纯数据（loot_tables.php），引擎是通用掷骰函数。表结构为"物品组 + 互斥选项 + 耐久衰减"三层：每组独立掷骰（组级 chance 判定 → 组内 entries 按 weight 加权选一 → 按 count 生成实例），组间互不干扰；表级 durability_decay 开关控制耐久衰减。多件物品配置拆解为多个单件独立掉落，无递归展开，无循环检测。F-4 仅负责掷骰返回物品实例数组，物化（写 oblmapitem、discovered 标记、source_iaid 归属、loot_dropped 响应等）由 E-7 / E-10 调用方负责。物品实例格式与 F-1 itempara 七字段对齐。entries 上限 OBL_LOOT_MAX_ENTRIES。

**代码锚点：** `oblivions/include/game/loot/loot.engine.func.php`（掷骰引擎、加权选择、耐久衰减、物品实例化）。完整设计案见 docs/ 目录下《搜索建筑物与掉落机制重构-模块F-战利品表引擎.md》。

**边界案例：**

- 耐久衰减以 `stack` 字段而非 itms 数值判定适用性——stackable（数量模型）恒跳过，非 stackable（耐久模型）才衰减；itms='∞' 保留，itms=0 或负值防御性保留。
- stackable 物品的 count 直接作为 itms，超 stack_limit 自动分批生成多实例；非 stackable 物品的 count 作为实例数，生成 N 个独立实例。
- weight 全 0 时均匀随机选一个（避免除零）；count 区间反向自动交换；count<=0 兜底为 1；模板不存在 emit error 跳过该组；表 ID 不存在或 entries 超限 emit error 返回空数组。
- 表 ID 即 POI ID——POI 模板与战利品表共用同一命名空间；工具/技能路由通过 loot_table_override 覆盖默认表。
- 物化策略与物化相关边界（物化失败、背包满、并发搜索、未拾取保留等）均由 E-7 / E-10 设计案承担，不属于 F-4 引擎职责。

#### 框架 F-5：装备穿卸与属性加成

**设计意图：** 装备系统是物品系统的衍生层。基于 F-1 槽位背包协议实现穿上/卸下流程，基于 G-1 装备技能注入机制联动技能刷新。属性加成采用"基础值 + 装备加成"的纯函数计算模型——基础值持久化不变，effective 值实时计算（主武器与防具计入对应属性，副武器仅作技能载体不提供数值加成，饰品槽位保留为未来扩展），战斗系统改读 effective 值，API 投影同时返回基础值与 effective 值。穿卸是原子操作，背包满时阻止；穿上时若目标槽位已有装备则先卸下放入背包空位；穿卸后立即剥离并重新注入装备技能（幂等注入，避免延迟到下次格式化）。副武器是第二武器槽而非辅助攻击来源，可与主武器整体互换（不推进 tick，双空时静默返回）。不引入 buff 系统（buff 由 H-1 独立处理），不持久化 effective 值。

**代码锚点：** `oblivions/include/game/item/item.equip.func.php`（itmk→槽位映射、穿上/卸下流程、属性加成计算、主副武器交换）

**边界案例：**

- 装备交换原子性：穿上时目标槽位已有装备 → 自动卸下放入背包；背包满时阻止，新装备不装入。
- 装备技能同步重建：穿卸后立即剥离并重新注入装备技能，幂等注入，避免延迟到下次格式化。
- 副武器双角色：副武器不提供属性加成，但仍可装备、仍参与装备技能注入（如双持武器技能），仅是不提供数值加成；主副武器交换整体互换全部装备字段并重建装备技能。
- itmk 与槽位映射严格——itmk 不匹配或显式指定槽位与 itmk 矛盾时阻止穿上；装备耐久为 0 时阻止穿上，耐久为无限标志时正常穿上。
- 战斗系统对 NPC 安全：NPC 装备字段全为 0，effective 值 = 基础值。

#### 框架 F-6：POI 道具交互系统

**设计意图：** 让 `tag_poi_interactive`（DESIGN.md §1.8 系统钩子 Tag）真实生效——配置驱动的"道具 × POI"交互映射，与 F-3 use_effect 分发器同构的纯分发器模式。框架按 (POI.mechanic × 玩家槽位道具) 反查交互配置，分发到命名约定的效果函数。POI 实例状态字段扩展两个值（locked / ignited），与 E-10 状态机原有四态并列。交互命令与搜刮命令在命令层并列，位置校验复用搜刮路径校验；payload 极简（仅槽位与 POI 实例标识），交互 ID 不传——后端按 (POI.mechanic × 道具) 反查配置，符合"确认函"设计哲学（玩家无需 memorize 配方，系统主动告知可用交互）。tile_actions 投影扩展返回每个 POI 当前可触发的交互列表（含预匹配的可用槽位），前端按字段渲染按钮。效果函数返回布尔决定是否消耗道具——itms 扣减由框架在 effect 之后统一处理（与 F-3 同模式）。并发安全采用乐观锁（先掷骰或计算副作用在内存，再乐观锁推进状态，锁成功后才物化与消耗）。

**代码锚点：** `oblivions/include/game/poi/poi.interact.func.php`（主流程 + 投影查询 + 状态前置校验）、`oblivions/include/game/poi/poi.interact_effects.func.php`（效果函数集合）、`oblivions/gamedata/poi_interactions.php`（交互配置表）

**边界案例：**

- POI 状态扩展——E-10 状态机原有四态，F-6 新增 locked（被锁住需道具解锁）/ ignited（已点燃语义标记，纯事件订阅入口）两个值；不与 E-10 状态重叠。
- 交互配置 vs POI 模板解耦——同一个 mechanic 可对应多条交互配置（如同一道门既可被撬棍撬也可被开锁器开），新增交互类型只需加配置 + 注册效果函数，框架代码不变。
- 道具匹配两种模式——按道具 ID 严格匹配或按 tag 模糊匹配（如同时匹配一类道具），二选一不组合；itm0 暂存槽排除；损坏道具跳过。
- 状态前置校验 + 乐观锁双层防护——主流程在调用 effect 前先按 effect_type 反查所需 POI 状态，不匹配时返回清晰错误；effect 函数内部仍用乐观锁防并发抢占，锁失败时不物化、不消耗。
- 已解锁 POI 的搜刮衔接——解锁门类交互成功后 POI 状态切到可搜刮态，玩家可继续搜刮；开箱类交互成功后 POI 状态切到终态（一次性开箱语义），不再可搜。

#### 框架 F-7：玩家放置 POI 框架

**设计意图：** 让 `tag_poi_placeable`（DESIGN.md §1.8 系统钩子 Tag）真实生效——玩家可通过使用道具主动放置 POI 实例到当前格，复用 F-3 use_effect 分发器作为入口（新增 `place_poi` effect），无需新命令。道具的 itmpara 携带目标 POI 模板 ID，格式错误时按 F-3 "赌博语义"处理（effect 失败仍扣 itms，无回滚机制）。同格同模板上限软约束（默认 1）防止刷屏放置——校验与插入之间接受 TOCTOU 竞态（并发抢占概率低，不引入 UNIQUE INDEX）。POI 模板可声明 `dismantle_returns` 配置（道具 ID × count 数组），由 `poi.dismantle` 命令消费——玩家主动拆除 POI，乐观锁删除 POI 实例并级联清理战利品，按 dismantle_returns 生成返还道具实例物化到玩家背包（背包满则掉到地面兜底）。E-12 耐久系统作为 POI 实例层通用属性自动作用于玩家放置 POI，无需 F-7 显式调用。

**代码锚点：** `oblivions/include/game/item/item.use_effects.func.php`（place_poi effect，F-3 分发器调用，本文件同时归属 F-3）；`oblivions/include/game/poi/poi.dismantle.func.php`（poi.dismantle 主流程）；命令合约位于 oblivions/include/command/obl_command_contract.php（poi.dismantle 合约，归 B-1/B-2 命令系统）；前端 store 位于 vex-vue/src/stores/poi.ts（归 L-9 POI 交互模态框）

**边界案例：**

- itmpara 协议解析严格——格式错误时 emit bad_protocol 并扣 itms；itmpara 为空时跳过 effect 不扣 itms（与 F-3 "无 use_effect 静默跳过"语义一致）。
- 同格同模板软上限——超上限时 emit tile_limit 不放置；校验与插入之间存在 TOCTOU 竞态，接受此竞态不引入 UNIQUE INDEX（同模板 POI 数量少，影响可忽略）。
- 玩家放置 POI 写入耐久三字段——E-12 监听器据此到期清理；世界生成 POI 不写这三字段（取表默认 0），不参与清理。
- 拆除乐观锁——POI 已被其他玩家/系统删除（如 E-12 刚清理）时 emit concurrent_conflict，不返还材料。
- 拆除与 E-12 到期清理并存——玩家放置 POI 在 ttl_days 到期前可主动拆除（返还材料），到期后由 E-12 监听器自动清理（不返还材料，直接级联删除）；两路径互斥，已删除的 POI 不会被另一路径重复处理。

### 模块 K：状态管理层

#### 框架 K-1：战斗回合编排 + 演示播放管道

**设计意图：** 总编排器同时消费两个互不推导的输入源：权威战斗上下文决定玩家回合 UI 与编辑会话身份，演出事件流决定横幅、动作与终局演出。内部承载一套四层职责分离的演出架构，把"原料 → 编排 → 计划 → 执行"切成四个互不越界的层：导演层把后端事件流聚合为四类片段（回合开放宣告、回合主体动作、系统消息、终局演出），计划层拆解播放步骤，执行器串行等待，演员层只通过租约与会话执行动作。回合宣告只投影领域事实——只有回合开放事件能创建回合宣告，动作批次即使与回合开放事件分离也不能补建横幅；前端不建立第二套回合状态机。

**代码锚点：** `vex-vue/src/stores/battle.ts`（权威状态、回合编辑会话、闩锁、演示批编排）、`vex-vue/src/stores/battle-director.ts`（导演层 + 计划层 + 回合宣告投影 + 终局上下文预扫描）、`vex-vue/src/data/battle-templates.ts`（战报文本字典与渲染入口）

**边界案例：**

- 提交成功后用一次性闩锁立即关闭旧会话，但权威已进入不同回合时不遮蔽新回合——闩锁不生成回合身份、不推进状态。
- 终局胜负判定不靠推断玩家身份再比较胜者：预扫描事件流算出幸存、逃跑、胜者三个语义状态，覆盖玩家逃跑、NPC 全逃跑、玩家死亡三个场景。
- 终局横幅只显示模板渲染产物，后端原始字段不直接进 DOM，避免跨层数据污染。
- 页面重连或演示间隙直接重基准到当前权威状态，不补播已经错过的瞬态横幅。
- 演示播放循环达到轮次上限时仅警告不强制终止，会话状态保留，防止死循环的同时不丢失未完成状态。

**设计意图：** 命令队列实现了 5 层 + 1 子层门控检查，所有存储通过此管道执行命令。检查顺序为：HTTP 请求锁 + 冷却 → itm0 暂存锁（非允许命令）→ 模式锁（战斗/探索）→ 演出水位锁（由演示场景阶段决定，播放中阻塞命令）→ 移动导演播放期门控（第 4.5 层，阻塞探索模式推进 tick 命令）→ 处理中锁（仅推进 tick 的命令）。能力检查作为额外的未编号守卫存在，不在 5 层编号内。同样的门控逻辑被可执行检查和执行接口共享，确保 UI 状态和执行路径一致。

**代码锚点：** `vex-vue/src/stores/command-queue.ts`（命令队列 + 第 4.5 层门控）、`vex-vue/src/stores/command-registry.ts`（命令注册表）、`vex-vue/src/stores/battle-ui-policy.ts`（演出水位锁）

#### 框架 K-9：有序批处理消费者 + 间隙检测

**设计意图：** 维护已消费的批序号和未来批次的待处理映射。支持间隙检测 —— 如果观察到的头部大于已消费但下一个序号不在待处理中，说明发生了冷启动刷新。入队时按批次领域区分场景认领：战斗批次必须在后续权威刷新前进入播放相位，冻结当前演员位置；探索批次保持空闲相位，继续允许移动导演即时消费权威投影。

**代码锚点：** `vex-vue/src/stores/presentation-inbox.ts`

#### 框架 K-10：角色动画意图派发

**设计意图：** 状态层只负责发布"意图"（应该发生什么），组合式函数负责动画库执行，二者通过意图序号解耦。意图序号在非抑制触发时递增——同一意图短时内重复触发会被抑制，用于绕过响应式系统对相同值赋值不触发观察者的特性，确保连续同值意图（如连续移动）能被观察者捕获；移动导演连续派发逐次移动意图时强制跳过抑制确保序号递增。异步执行器进入时必须捕获不可变的意图与序号快照，形态中点提交与取消兜底只有在序号仍属于当前意图时才能写入；最新意图通过独立会话抢占旧动画，并将姿态与可见性收敛到最终形态。场景外观交接必须区分"依赖当前演员的动画"与"新场景第一帧必须正确的资源状态"：外观相同时只做轻量姿态与可见性收敛，外观不同时走外观变换并要求序号校验通过后才提交新外观。

**代码锚点：** `vex-vue/src/stores/player-avatar.ts`（意图与目标外观发布、序号管理）、`vex-vue/src/composables/useMapEntities.ts`（意图快照、姿态动画抢占、终态收敛、场景交接双类区分）

**边界案例：**

- 玩家倒地后非倒地意图会被排队，等起身后再派发，避免倒地期间被覆盖。
- 场景退出不能把形态恢复寄托给即将卸载的意图观察者；探索场景挂载前，当前形态与目标形态必须同步恢复为常规形态。
- 快速交替触发战斗入场与退出时，每次回调使用捕获的唯一序号；旧回调不能因目标形态再次相同而越权提交，也不能释放新会话；外观已是目标形态时仍需重置姿态与可见性，清除被抢占动画留下的中间变换。

#### 框架 K-11：三场景所有权

**设计意图：** 以单一真值源承载"探索 / 完整地图 / 战斗"三场景，避免多 bool 组合爆炸。中央工作区所有者派生为探索或战斗（互斥），完整地图是覆盖在探索之上的居中大模态——桌面约占可用画幅九成，打开时探索场景不卸载，仅冻结输入。全局顶栏保持探索内容，完整地图的工具与返回由模态 header 承载；入口和返回都位于右侧，形成稳定往返路径。点击模态外背景可关闭，内部交互不穿透。战斗模式派生自战斗状态，不维护独立模式真值，无双源冲突。K-7 视觉状态过渡机保持战斗专属三态，不扩展为通用场景机；完整地图的进入/退出过渡由本框架独立承载，战斗场景过渡仍由 K-7 承载。

**代码锚点：** `vex-vue/src/stores/scene-store.ts`（三场景所有权单一真源）、`vex-vue/src/App.vue`（场景宿主与完整地图模态覆盖）、`vex-vue/src/components/layout/StatusBar.vue`（完整地图覆盖期间保持探索顶栏与入口稳定）

**边界案例：**

- 战斗场景下直接拒绝打开完整地图（入口在战斗场景隐藏）。
- 导航演出期间拒绝打开完整地图，避免玩家在演出中打开地图、点击图格、无反应的体验问题。
- 进入战斗的单值赋值天然完成"先关地图再进战斗"，无需显式关闭。
- 竖屏只显示旋转提示，不进入任何场景（§13.7 视觉质量验收）。

#### 框架 K-12：移动导演演出框架

**设计意图：** 承载高层导航命令一次返回的多次移动结果序列的逐格演出。核心原则是"权威结果与演出投影分离"——前端不循环发送单次移动请求，而是接收后端一次返回的有序移动结果，由移动导演逐次播放。强制战斗交接是过渡态与终态分离的语义：被突袭时先进入中断过渡态播放已发生移动，再进入已交接终态明确"已移交战斗导演"，避免与"未发生战斗的空闲态"混淆。逐格步进节奏与动画生命周期对齐：步进节奏由动画完成信号驱动，动画完整播放后才推进下一步，超时兜底作为安全网防止组件卸载或动画库异常导致卡死。

**代码锚点：** `vex-vue/src/stores/move-director.ts`（演出会话状态机、断点续行、振荡检测）、`vex-vue/src/composables/useMapEntities.ts`（世界移动动画、跳跃相机跟随编排、动画完成信号发出）、`vex-vue/src/components/map/MoveDirector.vue`（演出 UI 层与逐格播放视觉）

**边界案例：**

- 必达承诺区分：玩家指定目标触发断点续行（续发命令携带实际落点与倾向），自动选目标达步数上限时终止让玩家显式决定，避免在振荡路径上无限续行。
- 后端返回振荡路径时前端在首个振荡模式处截断，连续续行都检测到振荡则熔断停止，作为后端路径偏好缺陷的兜底。
- 视觉中心非空时移动演出持有相机控制权，地图投影、敌人或认知刷新只能更新布局，不得发起通用平滑居中与动画进度争夺滚动位置。
- 断点续行次数有上限保护，避免极端情况下后端误判导致无限续行；续行命令在锁保持期间执行避免锁闪烁。
- 跳过演出时途中摘要（发现、中断原因）合并到抵达反馈，普通播放、零步抵达、断点续行和跳过演出共享同一反馈语义。

#### 框架 L-10：完整地图全屏模态场景

**设计意图：** 完整地图是覆盖在探索场景之上的只读模态——不推进游戏刻、不替换全局探索顶栏，玩家在此浏览区域全貌、规划路线、提交导航目标。视图变换（缩放、平移、初始适配）支持任意区域尺寸和极端长宽比，每次打开默认重置为完整区域适配，玩家定位与目标定位只由显式工具触发。空间覆盖（图格渲染、迷雾隐藏、敌人数显）与认知状态（已探索、已揭示、未揭示）分离——前者随视图变换缩放，后者保持稳定屏幕字号。路线显示分两层：预览路线复用主地图的途经图格高亮与方向箭头（已知精确）或方向虚线（迷雾目标），历史路线作为独立灰虚线图层；提交目标后立即清除预览，历史路线可独立关闭。区域数据派生自底层认知状态投影，不复制真值；不显示正式探索百分比，空间覆盖、迷雾比例、候选目标只在 debug 模式可见。

**代码锚点：** `vex-vue/src/components/map/AtlasScene.vue`（视图变换、初始适配、桌面/手机横屏交互、路线分层渲染）、`vex-vue/src/stores/atlas-store.ts`（视图状态、目标提交、路线状态）、`vex-vue/src/stores/atlas-projection.ts`（区域图格矩阵派生）

**边界案例：**

- 选中与悬停用位置 ID 而非图格对象引用存储——图格矩阵每次刷新都生成新对象，直接持有引用会变陈旧。
- 提交目标后立即清除预览路线，不残留过期预览；历史路线作为独立图层可单独关闭，不与当前目标路线混淆。
- 桌面与手机横屏断点切换时重新执行初始适配并定位玩家，不能沿用另一布局的平移与缩放导致区域被裁切。
- 完整地图浏览与图格选择都是只读视图状态；只有玩家在详情区确认前往时才触发导航命令，由 K-12 移动导演消费结果。

#### 框架 L-11：主操作区

**设计意图：** 始终提供移动、探索、当前移动倾向、当前临时目标四项，并在玩家站于区域出入口时把区域通行作为同组第三主命令，提供认知稳定性——玩家任何时候都知道当前能做什么、当前态度是什么、是否在前往某处。与 L-1 当前格情境操作互补：L-1 是"脚边有什么"，本框架是"要去哪里与如何行动"。移动与探索是并列主命令，区域通行是条件性导航命令，倾向与目标是策略和状态；次级策略默认收纳在移动按钮内，由副标题显示摘要，固定窄宽的贴附按钮只负责展开具体控件。演出期间门控分层——锁定会改变游戏状态的操作（移动、探索、区域通行、目标），但导航设置的展开收起与加速跳过始终可用。探索按钮标签稳定，演出期间改显"扫描中"而非改名"等待"，避免按钮可用性成为探测隐藏信息的旁路。

**代码锚点：** `vex-vue/src/components/actions/MainActionBar.vue`（固定主命令、条件性区域通行、门控分层、布局变体降级、目标三态显示）

**边界案例：**

- 移动按钮委托导航 store 启动移动导演，不直接发命令；移动进度与播放控制由地图叠层独占，本组件不重复承载。
- 区域通行仅在当前格为入口或出口时出现，与移动和探索共享主命令视觉与输入门控，不回落到当前格物件分组。
- 目标三态显示对齐暂停恢复设计：无目标只读、前往中可暂停、暂停态可继续；目标必须来自完整地图或发现结果等明确选择入口，不得由状态控件创建占位目标。

#### 框架 L-12：固定等距战斗场景

**设计意图：** 战斗不再借用探索地图的相机、视野与正交图格，而以独立中央场景承载固定角度的等距投影——逻辑位置仍由区域与图格唯一标识，只有场景投影变化。区域先按真实图格坐标适配，再以较大的默认倍率围绕玩家构图；窄横屏也必须保留最低战术格距，允许裁切远端地图，图格间距与角色尺寸分别受限。场景允许限定缩放、自由拖拽与玩家居中，但不允许旋转；播放期间相机焦点与当前格读取冻结的表现场景，不能被提前到达的权威结果重排。入场演出（图格升起、参战者弹出、玩家形态切换）全部完成才兑现就绪屏障，K-1 战斗动作不得抢在战场成形前播放。战斗地图仍是瞄准输入的当前所有者；命中层随目标类型收敛，非目标演员不能遮断选择，同时不复制技能规则或战斗数值。

**代码锚点：** `vex-vue/src/components/layout/BattleScene.vue`（战斗场景布局与动作区所有权）、`vex-vue/src/components/battle/BattleMap.vue`（固定等距地图、图格入场与战斗交互投影）、`vex-vue/src/utils/isometric-battle.ts`（等距适配与确定性乱序）、`vex-vue/src/composables/isometricBattleGeometry.ts`（战斗场景锚点）

**边界案例：**

- 主动预装填阶段尚无战斗编号时仍显示战场；真正战斗开始后复用同一场景，不重复挂载。
- 容器尺寸或缩放倍率变化时，图格与演员锚点必须在同一投影同步中更新；玩家居中只改变镜头原点，不改变逻辑位置和投影方向。
- 瞄准事件委托从当前场景几何取得交互根节点，不能依赖探索地图固定 DOM 标识。
- 减少动态效果时取消逐格位移与延迟，但保留下一帧就绪屏障，业务时序不变。

### 模块 M：组合式函数

#### 框架 M-1：租赁式动画架构

**设计意图：** 每个地图实体通过角色运行时管理动画，核心概念是"通道租赁" —— 空间、动作、可见性、姿态四个动画通道可以被不同优先级的所有者租赁并获得独占访问权。优先级从低到高：环境 < 世界 < 战斗 < 终点。租赁冲突时优先级仲裁解决。租约释放时区分"完成"与"取消"语义——世界移动动画正常完成时通过独立信号通道向移动导演传播完成事件，移动导演据此推进逐格演出节奏（K-12-B），不通过状态投影或意图通道传播以避免修订号污染与通道语义混淆。空间动画可向场景消费者发布标准化行进进度，使相机等附属表现与变速后的真实动画时间轴保持同源，但消费者不能反向控制租约生命周期。战斗空间命令与探索移动分离，并显式携带事件源锚点和结果锚点；即使权威投影已到达结果位置，租约内仍以事件位置差量重建真实行进轨迹。

**代码锚点：** `vex-vue/src/composables/useActorRuntime.ts`（通道租赁、优先级仲裁、动画生命周期）、`vex-vue/src/composables/actorRegistry.ts`（角色注册表、租约管理）、`vex-vue/src/composables/useMapEntities.ts`（世界与意图动画的租约编排、抢占与释放、完成信号发送）、`vex-vue/src/composables/moveAnimationChannel.ts`（移动动画完成信号独立通道、订阅/发送）

**边界案例：**

- 释放租赁时处理待定锚点的协调。
- 行进进度只描述起终点之间的地面路线，不把跳跃高度、姿态弹性变成附属表现的主轨道；场景可使用独立安全区约束保证主体不出画。
- 释放姿态通道时无其他所有者占据则恢复空闲动画。
- 终点处理：既有终点又倒下的角色走特殊路线。
- 同一 owner 的不同 session 只有显式 `replaceEqualOwner` 才能抢占；被抢占租约后续重复释放必须保持幂等，不影响新租约。取消形态翻转后可通过 `reset-pose` 在 pose 通道内即时收敛到中性变换。
- 命令式动画 class 不得写入由 Vue 动态 `:class` 全量投影的节点；角色朝向 `facing-right` 归属稳定的 pose 节点，瞄准高亮、聚焦和战斗淡化更新实体根节点时不能清除既有朝向。
- 租约被抢占释放（非正常完成）时不发完成信号，移动导演走超时兜底；跳过演出时移动导演不等待完成信号直接同步推进。完成信号携带目标坐标供移动导演过滤过期信号。
- 战斗位移恢复事件源锚点时只能写入演员自己的空间通道，不能清空租约期间积累的待定权威锚点；完成后仍以最新权威投影协调。

#### 框架 M-2：场景差异投影

**设计意图：** 权威实体集合通过场景几何端口投影到当前演示场景，场景跟踪修订号、阶段和实体。当权威集合变化时，计算差异并编排入场、移除、移动与区域登场；探索正交网格和战斗等距网格分别实现坐标投影，但演员运行时只识别统一图格锚点。场景端口同时公开当前交互根节点与显式就绪屏障，使瞄准输入和 K-1 播放管道跟随实际场景所有者，而不是依赖固定 DOM 或挂载时机猜测。

**代码锚点：** `vex-vue/src/composables/useMapEntities.ts`（权威差异、动画编排、首次入场跟踪与几何注入）、`vex-vue/src/composables/useMapBusiness.ts`（地图业务对场景投影的事件接入）、`vex-vue/src/composables/sceneRegistry.ts`（场景注册、世代、交互根与就绪端口）、`vex-vue/src/composables/mapSceneGeometry.ts`（探索正交锚点）、`vex-vue/src/composables/isometricBattleGeometry.ts`（战斗等距锚点）、`vex-vue/src/utils/isometric-battle.ts`（等距投影计算）、`vex-vue/src/components/battle/BattleMap.vue`（等距投影的场景渲染）

**边界案例：**

- 首次入场只播放一次（跟踪已入场集合）。
- 投影移除使用淡出动画，可通过实体重新发现事件取消。
- 玩家实体有特殊处理 —— 外观转换、HP 响应。
- 场景就绪 Promise 完成后必须再次校验注册世代；旧场景转场完成不能放行新场景的播放会话。
- 当前交互根节点随场景注册切换，组件卸载后不得继续接收瞄准事件。
- 多个响应式刷新等待同一个场景阶段时，阶段兑现后必须再次检查首入集合；同一演员不得并发获得多条首次入场序列。
- 场景阶段到达后可显式请求全部演员首入，作为首帧调度受浏览器节流时的恢复路径；幂等性仍由首入集合保证。

#### 框架 M-3：响应式网格渲染

**设计意图：** 单元格是一个计算属性，从地图存储 + 角色存储派生完整区域的二维网格数据。每个格子包含渲染所需的所有派生状态。默认图格尺度按约五乘五的相机窗口计算，区域尺寸只决定可滚动世界大小，不再决定单格缩小比例。叠加层视觉（路径预览、抖动、高亮）均通过响应式状态注入 class，由 Vue `:class` / `v-if` 统一管理，不使用命令式 DOM 操作。

**代码锚点：** `vex-vue/src/composables/useMapRender.ts`（计算属性网格、智能默认缩放、叠加层视觉状态注入）

**边界案例：**

- 迷雾格子隐藏标签，添加 CSS 类禁用交互。
- 出口/入口格子添加前缀符号和特殊 CSS 类。
- 潮汐深水、金属地板、安全区各有不同视觉样式。
- 任意区域尺寸都完整物化为空间锚点；默认相机只展示约视野窗口范围，手动缩放和平移不能改变认知状态或揭示隐藏内容。

#### 框架 M-4：命令式事件处理

**设计意图：** `useMapInteraction` 替代旧的事件绑定 JS，使用事件监听接口处理鼠标/键盘/触摸输入。通过回调注入避免循环依赖。路径预览由本模块持有的响应式状态驱动，通过 getter 注入 useMapRender 消费，避免循环依赖。

**代码锚点：** `vex-vue/src/composables/useMapInteraction.ts`（鼠标/键盘/触摸输入、回调注入、路径预览响应式状态）

**边界案例：**

- Ctrl+滚轮缩放阻止默认行为。
- 触摸双指缩放 + 单指平移由浏览器原生支持。
- 路径预览跳过迷雾中间格子。
- 无效移动尝试播放格子抖动动画。
- 路径预览清理不依赖鼠标离开事件：玩家移动、模式切换、组件卸载均触发清理；后台心跳刷新不清理（玩家位置未变则路径有效）。

#### 框架 M-5：基于 BFS 的可达性缓存

**设计意图：** 纯前端 BFS 寻路和可达性计算，无 DOM 依赖。可达性地图缓存在模块级别，通过重新计算函数刷新。

**代码锚点：** `vex-vue/src/composables/useMapReachability.ts`（BFS 寻路、可达性缓存、迷雾/不可通行过滤）

**边界案例：**

- 入口格始终可达（允许退回前一区域），即使在 BFS 范围外。
- 迷雾格从可达性排除，不可通行格不作为中转也不作为目标。

#### 框架 M-6：覆盖层优先级堆栈

**设计意图：** 多个覆盖层状态按优先级评估以计算单个派生值（如 Toast 定位）。优先级：模态框 > 右侧抽屉 > 左侧抽屉/默认。

**代码锚点：** `vex-vue/src/composables/useToastPosition.ts`（覆盖层优先级堆栈、派生定位）

## 第四部分：跨模块关键模式

### 模式 1：读写隔离阶梯

整个系统有三个清晰的隔离层级：

| 层级    | 入口            | 事务 | 房间锁 | 玩家锁 | 副作用         |
| ----- | ------------- | -- | --- | --- | ----------- |
| 只读    | `state.php`     | 无  | 无   | 无   | 无数据库写入      |
| 服务端写入 | `heartbeat.php` | 有  | 有   | 无   | Tick 处理、恢复  |
| 认证写入  | `command.php`   | 有  | 有   | 有   | 所有以上 + 玩家变更 |

状态 API 被显式设计为纯读取 —— 即使数据库表不存在也不创建。

### 模式 2：双响应协议

系统有两个不同的响应格式（状态协议的简洁格式 vs 命令协议的丰富格式），各有不同的错误码集和 HTTP 状态码映射。命令协议是超集，状态协议是简化子集。

### 模式 3：日志即反馈

业务处理程序不直接返回错误信息，而是写结构化日志。总线比较新旧日志推导反馈。这意味着三个不同的日志流，每个有不同的消费者：游戏事件日志（命令反馈）、错误日志（诊断）、战斗日志（演示批处理投递）。这是单请求内的轻量级事件溯源模式。

### 模式 4：能力系统作为通用访问控制桥梁

能力系统连接三个模块：状态 API 投影玩家可执行的操作，UI 根据此渲染可用操作，命令总线在执行前重新检查。这形成了一个完整的回路：展示可用的 → 展示可用的 → 玩家操作 → 服务端再次检查。

### 模式 5：基于注册表的插件架构

八个子系统使用相同的全局注册表模式：瞄准解析器、目标捕获器、目标捕获验证器（与目标捕获器分开注册，专门校验捕获结果的合法性）、效果应用器、效果投影器、AP 计算器、AP 预算投影器（独立于 AP 计算器，专门用于将可用 AP 投影为有效射程）、标签派生器。大多数业务逻辑扩展只需向这些注册表添加条目。

### 模式 6：效果应用器与投影器平行宇宙

一组函数实现实时应用（写数据库、发射日志），镜像组实现干跑投影（只改内存）。两组共享相同的效果类型集合（伤害/治疗/移动/逃离/技能效果应用/AP 变更）和注册表结构，但实际执行逻辑并非"完全相同"——存在多种不对称（详见 D-14）：移动应用器调用底层移动函数执行真实位移，投影器仅做空间决策一致性校验后改内存字段；逃离应用器用标记变更，投影器通过状态管理接口走不同路径；AP 变更应用器当前为占位实现，投影器已实现；伤害投影器同步标记死亡，应用器由独立阶段处理；技能效果应用投影器实际调用真实技能效果应用函数，违反干跑纯内存契约。代价是保持两组函数同步，且当前存在未同步的实证。

### 模式 7：数据管理器事件总线

存储不直接导入进行事件通知，而是通过中央数据管理器广播/监听。Pinia 中没有直接的跨存储动作调用链 —— 一切都通过事件总线中介。

### 模式 8：前端控制渲染

后端只发送结构化代码（物品 ID、日志 ID、技能 ID、参数），前端完全控制视觉呈现。本地化字典和日志模板都在前端项目中。

### 模式 9：标签作为通用语义胶水

标签在后端多个子系统之间充当通用外键：使用效果、合成材料匹配、装备技能注入、数据规则校验。注：合成系统中的"工作台材料"识别实际通过 `source` 字段（值为 `'workbench'`）区分，而非标签 —— 标签用于材料类别匹配，但工作台来源识别是独立字段。

### 模式 10：itm0 暂存槽协议

0 号槽作为临时中转位，分离"获取"和"存储"操作并防止部分状态更新。拾取和合成都经过 itm0 → 自动整理 → 背包。暂存失败时锁定玩家直到腾出空间。

### 模式 11：计划状态缓存（Planned State / Dry-Run Cache）

动作链投影和目标结算期间，所有对战斗状态的读取和写入都走一层"计划状态"缓存：运行时内存 > 计划状态内存 > 数据库的三层回退读取，确保链内动作看到前序动作的投影结果而非陈旧数据库值。写入先改计划状态，提交阶段才落库；失败时回滚计划状态到快照。这层缓存是 D-5（目标结算单元）、D-6（目标捕获注册表）、D-10（动作链投影器）共享的基础设施，使干跑与真实执行在状态视图上保持一致（尽管效果应用器与投影器之间存在执行差异，详见 D-14）。

### 模式 12：空间决策报价-验证（Spatial Decision Quote/Verify）

移动类效果的空间可达性采用"报价-验证"两阶段协议：预览/投影阶段向空间决策器请求报价（返回目标 AP 成本等可验证字段），实际执行阶段重新计算空间决策并验证报价值与当前值一致。若报价过期（目标移动、AP 变化、迷雾更新等），验证失败并拒绝执行。此模式横跨 D-2（预览系统，发起报价）、D-3（移动效果应用器，验证报价）、D-14（移动效果投影器，验证报价一致性），确保干跑预览的 AP 成本和可达性与实际执行结果一致。代价是客户端必须保留报价值并在提交时回传，增加了协议复杂度。

### 模式 13：字段驱动的前端语义判定（Field-Driven Frontend Semantic Judgment）

当后端配置中存在表达"语义约束"或"展示分类"的字段（如终结性标记、功能分类、优先级、唯一性等），前端必须以该字段为唯一权威数据源，不得维护独立的硬编码判定表。后端值域应与前端需求 1:1 对齐（如需要细分分类时，后端配置就细化值域，而非前端另起映射表）。前端将后端字段派生为响应式集合（computed），供所有调用点统一查询。后端配置变更新增/移除标记或新增技能时，前端自动跟随，零双重同步。典型案例：技能的 `finisher` 字段和 `category` 字段均由后端配置下发，前端分类与约束（排序、唯一、拖拽、标签页筛选）全部派生自这两个字段，而非硬编码技能 ID 到分类的映射表。与模式 8（前端控制渲染）互补——模式 8 解决"渲染决策权归属"，模式 13 解决"语义标记数据源归属"。

### 模式 14：权威回合边界协议

E-5 持久化"现在是谁的第几个回合、处于什么阶段"，I-1 只提供顺位候选，D-1 只执行已认领回合，D-4 用 `battlelog.v3` 陈述同一 `turn_key` 下的领域事实，C-4 只负责排序投递，K-1 只负责演出投影。命令必须引用 `expected_turn_seq`，事件必须引用 `turn_key`，玩家动作编辑会话必须引用同一 `qid + turn_seq`；请求、tick、batch、前端标题和 UI 布尔跳变都不能生成或替代回合身份。该协议把控制权交接、动作执行和视觉宣告拆成可独立验证的边界，同时允许页面重连直接恢复权威状态而不补播瞬态演出。

### 模式 15：浏览器验收证据闭环

网页游戏功能以玩家画面和操作路径为验收起点。AI 助手执行浏览器测试时，必须同时采集玩家可见结果、前端运行状态、HTTP 请求契约和后端权威状态；其中任一层缺失都只能形成待验证假设，不能完成跨层结论。现有观测无法区分假设时，应主动创建低侵入调试桩补齐证据，而不是缩减测试内容。State、Heartbeat、Command 三类请求按只读、服务端写入、认证写入分别归因，后台心跳和状态轮询不得冒充玩家操作触发的请求。身份、代理、场景前置条件、响应式遮罩和浏览器控制失败必须与产品缺陷分开报告。

具体操作流程、场景配方与 GM 工具用法收录于 `vex-vue/docs/前端运行时测试与GM调试操作手册.md`。该手册负责说明测试人员实际如何准备环境、定位操作、构造场景、采集证据与恢复状态；Dian.md 只保留稳定的验收意图与边界。

`oblivions-compass` 将这一证据边界应用到智能体工程导航：框架归属由文档锚点、源码标签与动态图谱互证；视觉、动画和交互结论必须进入浏览器验收流程；流程诊断必须路由到 A-5 既有通道。任务完成后的文档写回与导航分阶段处理，先提炼可用于未来重建的设计理念，再附加代码锚点和真正非显然的边界案例。静态分析只能定位候选实现，不能替代玩家视角验收或通过临时散乱日志补足证据。
