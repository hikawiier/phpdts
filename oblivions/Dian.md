> ▎**阅读说明**

### 模块 A：API 层

#### 框架 A-1：HTTP 三层入口隔离架构

**设计意图：** 将所有 HTTP 入口点分为三个独立层级。读取状态时不做任何写入操作，写入时使用不同级别的隔离保护。这三个入口分别是：状态查询（只读 GET）、心跳推进（服务器端写入）、命令执行（玩家认证写入）。每个入口对应一个独立的 PHP 文件，有着不同的锁策略和事务策略。

- 状态查询：不使用 MySQL 事务和房间锁 —— 即使数据库表不存在也不会创建，返回虚拟空状态。
- 心跳和命令：使用 MySQL 事务 + 房间锁保护数据一致性。命令额外使用基于文件的玩家锁防止并发操作。
- 所有入口都处理 CORS 预检（OPTIONS）请求和 PHP 致命错误的 shutdown 回调。

**边界案例：**

- 只读路径遇到不存在的数据库行时，不创建记录而是返回内存中的虚拟行，确保完全无副作用。
- 所有入口在 PHP 错误级别捕获 5 种致命崩溃（`E_ERROR`、`E_PARSE`、`E_CORE_ERROR`、`E_COMPILE_ERROR`、`E_USER_ERROR`），输出结构化 JSON 而不是空白页面。

#### 框架 A-2：最小依赖引导链

**设计意图：** 每个入口只加载自己需要的依赖。命令入口不加载状态响应格式，状态入口不加载命令总线。引导文件仅声明函数但不执行 —— 实际的启动调用由入口文件自己做。

**边界案例：**

- 心跳入口和命令入口各自有不同的启动参数，控制是否在数据库缺失时自动创建记录。

#### 框架 A-3：状态查询范围分发

**设计意图：** 状态 API 提供了一个路由中心，根据查询参数分发到 14 种不同的处理器。每个处理器负责组合一种特定的前端数据视图（玩家信息、地图数据、敌人列表、背包内容、日志、技能列表等），新增一种视图只需添加一个新的路由分支和对应的处理器函数。

**边界案例：**

- 敌人列表处理器在玩家处于战斗状态时，强制将参战成员（NPC）加入列表，即使它们处于迷雾中未被发现 —— 避免战斗 UI 丢失参战者。
- 战斗目标处理器构建了一个复杂的"参与状态机"，将候选对象分为五类（成员、可加入、已离开、其他战斗、被封锁），按优先级排序返回给前端。
- 物品列表处理遇到近视伪装物品时，使用虚拟名称和假 ID 包装后返回，不影响真实道具数据。
- 地图迷雾数据使用稀疏格式返回（仅发出有值的格子），减少传输量。

#### 框架 A-4：结构化视图投影函数集

**设计意图：** 一组专门用于"投影"数据视图的函数 —— 它们将数据库内部状态转换为前端可消费的响应格式。这些函数是纯读取的，不修改任何数据。包括：装备槽映射（平铺的数据库字段转为结构化对象）、角色战斗视图、效果投影（在指定 tick 评估哪些效果将生效）、战斗队列投影（当前先攻顺序与回合状态）、战斗上下文投影（含可提交回合标志与建议目标 PID 等派生字段）。

**边界案例：**

- 投影函数通过函数存在性检查来判断某些库是否已加载（如标签查询函数），优雅降级而非硬性依赖。

### 模块 B：命令系统

#### 框架 B-1：声明式命令合约

**设计意图：** 每个命令由一个声明式合约完整定义。合约描述了命令的名称空间、允许的 UI 模式、是否推进 tick、是否只读、需要什么能力、战斗状态机要求、负载格式、以及执行后哪些前端范围需要刷新。目前定义了 15 个命令，涵盖移动、探索、搜索、等待、拾取、丢弃、使用、整理、合成、战斗开始、提交回合、以及战斗预览。

**边界案例：**

- 合约在首次查询时（懒加载，通过 static 变量防护）校验所有定义的能力（capability）名称是否真实存在，捕获拼写错误而非运行时暴露。
- 四个战斗只读命令标记为 read\_only —— 其中三个是预览命令（`combat.preview_single`、`combat.preview_targets`、`combat.preview_chain`），一个是可达性查询命令（`combat.can_engage`）。它们走命令管道但不触发保存逻辑、不推进 tick、不执行战斗状态转换。
- 战斗回合提交具有最严格约束：必须处于战斗模式、战斗状态必须是玩家回合、队列行动者必须是自己。

#### 框架 B-2：双层负载校验管道

**设计意图：** 外部输入通过两个验证层级。第一层检查整体信封结构（命令名称格式、请求 ID 格式），第二层按照合约的 schema 逐字段校验和规范化。类型系统支持整数、字符串、动作序列、槽位计数、字符串列表、整数列表和通用数组。

**边界案例：**

- 动作目标类型支持命名字段和目标解析的向后兼容别名。
- 整数列表会自动去重并限制最大长度。

#### 框架 B-3：命令总线执行管道

**设计意图：** 总线是一个完整的执行管道，编排所有横切关注点：认证、校验、门控、分发、反馈、持久化、tick 推进。处理程序位于管道中心，保持薄层。完整的执行顺序如下：查找合约 → 校验负载 → 认证玩家 → 获取文件锁 → 设置操作标识 → 检查门控（允许动作、预期状态、物品暂存、能力、战斗状态、队列行动者、战斗忙碌）→ 检查存活 → 记录日志快照 → 准备待处理战斗行动者作用域（仅 advances\_tick 命令，将当前玩家加入待处理战斗的 actor scope）→ 分发 → 处理回滚标记 → 计算反馈 → 收集权限变更范围 → 保存并推进 tick → 返回。注意：信封结构校验在获取房间锁和事务之前执行，而负载 schema 校验在事务内、文件锁之前执行——两层校验被锁/事务边界分隔。read\_only 命令跳过 `obl_command_after_dispatch`（战斗状态转换）和 `obl_command_save_and_tick`（保存并推进 tick）两个步骤。

**边界案例：**

- 操作标识生命周期的保护：如果管道的调用者已经设置了标识（嵌套调用场景），finally 块会恢复前一个值。
- 能力封锁响应包含结构化信息，告诉前端是哪个状态效果阻止了操作。
- 物品使用命令在合约级别放行了 itm0 临时槽检查后，处理程序层又做了二次检查 —— 如果使用非 0 槽位 while itm0 暂存中，仍会被拒绝。

#### 框架 B-4：日志即反馈

**设计意图：** 业务处理程序不直接返回错误信息，而是写入结构化日志条目。总线在执行后比较新的日志条目与预定义的反馈规则，从中推导出结构化错误响应。这种模式解耦了业务逻辑（只管写日志）和错误响应格式化（总线从日志读）。

**边界案例：**

- 反馈规则是硬编码的每命令映射 —— 将特定日志条目 ID 映射到错误代码。
- 此模式只在一个请求的生命周期内有效（内存中的日志收集器），不是持久化的日志分析。

#### 框架 B-5：乐观并发控制

**设计意图：** 前端在每个命令中附带它期望的服务端状态（玩家 ID、动作、战斗 ID、战斗状态）。如果实际状态与期望不符，总线拒绝执行而不产生任何副作用。这防止了陈旧客户端覆盖最新状态。

**边界案例：**

- 战斗状态的比较需要一次数据库查询 —— 不是简单的字段对比。
- 空期望不做任何检查。

#### 框架 B-6：基于文件的玩家锁

**设计意图：** 用文件锁（`flock`）而非数据库锁来防止同一玩家同时执行多个命令。锁文件以玩家 ID 命名，非阻塞方式获取，失败时返回"命令执行中"错误。

**边界案例：**

- 锁目录在第一次使用时惰性创建。
- 锁文件描述符在整个请求期间保持打开，PHP 关闭时自动释放。

### 模块 C：核心运行时

#### 框架 C-1：拓扑引导加载

**设计意图：** 所有 Oblivions 业务文件按严格的拓扑顺序加载，确保没有文件在其依赖之前被加载。`require_once` 既保证顺序又防止重复加载。整数主层 0–8 共 9 层，中间穿插半层（0.5、2.5、4.7、5.5、6.5），细化为 13 个加载阶段。各层实际内容如下：

- **Layer 0**：公共函数库（`obl_global.func.php`，跨业务域通用函数）
- **Layer 0.5**：游戏仓库与 gamevars 兼容镜像（`obl_game_repository.php` + `obl_gamevars.php`）
- **Layer 1**：独立函数库（14 个文件）—— 日志（`log.func`、`battle_log.func`）、SQL 工具（`sql.func`）、玩家（`player.func`）、移动（`move.func`）、生成（`generate.func`）、战斗数值计算（`battle.calc`）、道具标签（`item.tag.func`）、角色能力（`actor.capability`）、技能系统（`skill.main`、`skill.modules`）、技能效果系统（`skill_effect.main`、`skill_effect.lifecycle`、`skill_effect.projector`）。此层执行两个显式初始化调用：`skill_load_modules()` 与 `skill_effect_register_capability_provider()`。
- **Layer 2**：视野/迷雾/发现系统（`vision.func.php`）
- **Layer 2.5**：共享战斗状态机（`battle_state_machine.func.php`）
- **Layer 3-4.5**：shared battle infrastructure —— 旧 `battle.func.php`、`battle.queue.func.php`、`battle.queue.main.php`。旧主执行链已删除，保留的文件只承担数值、队列原语、队列编排等共享职责。
- **Layer 4.7**：新战斗系统 combat/ 模块（21 个文件）—— 唯一战斗执行入口，包含 runtime、context、planned\_state、observation、aim、target\_capture、participation、target\_unit、core、pipeline、effect、skill、ap、range、tag、queue、state、effect\_projector、chain、preview、log。
- **Layer 5**：探索交互 + 敌人 AI（`explore.func.php`、`enemy_ai.func.php`）
- **Layer 5.5**：道具系统（`item.basic.func`、`item.use.func`、`item.craft.func`）
- **Layer 6**：tick 函数 + 技能效果 tick 监听器注册（`tick.func.php` + `skill_effect_register_tick_listener()`）
- **Layer 6.5**：Tick Orchestrator（`obl_tick_orchestrator.php`，集中调度 command/heartbeat/state 的 tick 策略）
- **Layer 7**：游戏初始化（`init.func.php`，仅在 `obl_rs_game` 调用时执行）
- **Layer 8**：游戏状态机（`state.func.php`，当前主要由旧 Room/Lifecycle 入口调用）

**边界案例：**

- Layer 1 是文件最多的层（14 个），跨越多个业务域但都不依赖战斗基础设施。技能与技能效果系统在此层加载并立即注册能力提供者，使后续层（如命令门控、参与分类器）可直接使用能力决策。
- Layer 6 执行 `skill_effect_register_tick_listener()`，将技能效果系统接入 tick 调度的 post 阶段（用于 CD 递减、buff 过期等生命周期管理）。
- Layer 3-4.5 的旧 battle.\* 文件通过注释明确标记为"共享基础设施"——旧主执行链已删除，保留的文件仅提供数值计算和队列原语供新战斗系统复用，不作为独立执行路径存在。

#### 框架 C-2：独立运行时启动

**设计意图：** 运行时启动独立于旧版 PHPDTS 主入口 —— 自己连接数据库、读取 cookies、加载房间数据、初始化日志器和上下文。不依赖主游戏的 `common.inc.php`。但仍复用旧核心的部分基础工具：`include/core/global.func.php`（全局工具函数）、`include/auth/user.func.php`（玩家认证）、`config.inc.php` 与 `gamedata/system.php`（配置）、`include/db/db_*.class.php`（数据库类）。因此更准确的说法是"不依赖 common.inc.php 但仍与旧核心共享基础设施"，而非"完全独立于旧版核心"。

**边界案例：**

- 调试自动登录（开发环境存在特殊文件时强制设置 cookies）用于跳过正常认证。
- 启动参数控制是否在数据库表/行缺失时自动创建它们。

#### 框架 C-3：事务管理与房间互斥锁

**设计意图：** 提供显式的、可组合的事务边界和房间级别的互斥锁。这些原语由心跳和命令入口使用，但状态查询不使用。事务函数有嵌套保护（已在事务中时抛出异常），房间锁使用 MySQL 命名锁。

**边界案例：**

- 回滚函数优雅处理连接丢失（MySQL 在连接断开时自动释放命名锁）。
- 关闭清理函数在 PHP 致命错误时也能回滚任何打开的事务和释放锁 —— 防御性编程。

#### 框架 C-4：事件批量投递（Presentation 系统）

**设计意图：** 命令或心跳执行期间收集的战斗事件，在响应内联打包为一个"演示批"返回，省去了单独的事件轮询。批包含模式版本、元数据、状态快照和事件列表。前端接收后直接播放。

**边界案例：**

- 如果玩家数据为空（如心跳时玩家尚未生成），状态快照使用全零默认值。
- 批的战斗 ID 通过反向扫描事件确定，而不是从玩家当前战斗 ID 直接取。
- 如果玩家 PID 无效，日志持久化直接跳过。

#### 框架 C-5：Tick 编排器

**设计意图：** 集中决策 tick 推进的逻辑，有三种操作模式。命令执行后推进：保存玩家 → 记录 tick 行为 → 推进 tick → 刷新战斗状态。心跳追赶：补处理已产生但未处理的 tick。卡死恢复：检测并恢复卡死在处理中的战斗。

**边界案例：**

- 命令的"域"（domain）决定了 tick 引擎走什么解决路径 —— `combat` 还是 `world`。战斗命令触发战斗域，其他触发世界域。
- 卡死恢复对不同类型发起者做不同处理：如果当前是玩家，重置回玩家回合；如果是 NPC，推进 tick 让 NPC 行动。

#### 框架 C-6：游戏仓库（oblgame 表）

**设计意图：** 将运行时状态从旧版 `gamevars` JSON 迁移到专用的单行 `oblgame` 表，包含类型化列。tick 值存储在列中，所有其他变量存储在 `vars_json` 中。提供创建、加载、保存、重置操作。加载有"是否自动创建缺失行"的参数。

**边界案例：**

- 只读路径遇到不存在的行时，创建一个内存中的"虚拟行"（标记 `__missing_id`）而不写入数据库。虚拟行仅存在于 `$GLOBALS['obl_game']` 和 `$gamevars` 兼容镜像中，让无锁读路径能拿到默认 tick 值。
- 保存路径的 INSERT/UPDATE 决策实际由 `obl_game_load(false)` 的返回值决定 —— 返回 `false`（表/行缺失）时走 `obl_game_reset`（DELETE + INSERT），返回真实行时走 UPDATE。代码中虽有 `$missing_id` 分支检查虚拟行标记并执行 INSERT，但由于 `obl_game_load(false)` 总是直接查库而不读 `$GLOBALS['obl_game']`，此分支在当前架构下实际不可达，属历史遗留防御代码。
- 生命周期状态同步有一个显式的参数控制 —— 因为错误的同步会破坏房间重启逻辑（旧运行中的状态会被当作新状态）。

#### 框架 C-7：Gamevars 兼容镜像

**设计意图：** 旧系统读写 `$gamevars['obl_tick']`，新系统在 `oblgame` 列中存储 tick 值，其他变量在 `vars_json` 中。这层透明地在两种表示之间同步。

**边界案例：**

- 虚拟行路径（`$create_from_legacy = false` 且 DB 无行）经过兼容层时，从旧 `$gamevars['obl_tick']` / `$gamevars['obl_pretick']` 提取 tick 值填充虚拟行，而非从数据库 —— 让无锁读路径在不写库的前提下仍能返回有意义的 tick。
- 注释警告生命周期同步会破坏房间重启 —— 所以默认不开启生命周期同步。

### 模块 D：战斗系统（Combat）

#### 框架 D-1：动作生命周期编排

**设计意图：** 顶层调度器，编排单回合的完整生命周期。三个阶段：排序（终结技最后）→ 校验（AP 成本、标签规则）→ 执行（效果应用、持久化）。另外提供完整的战斗初始化入口（创建队列 + 首轮执行）和标准回合分发入口。

**边界案例：**

- 排序必须先于校验 —— 终结技必须排到末尾再进行 AP 和位置投影，否则中间动作会被错误移除。
- 行动者终止有四种条件（HP 归零、状态标记、逃离、死亡），会导致所有后续动作中断（break）而非跳过（continue）。
- 战斗初始化有一个"Phase 0"阶段 —— 在战斗名单创建之前先执行非敌对动作（如增益），然后第一个敌对动作构建正式战斗名单。

#### 框架 D-2：四层预览/预演系统

**设计意图：** 提供无副作用的预校验，对应 4 个只读命令，分四个层级。L0（`combat.can_engage`）：可达性检查 —— 不需要完整战斗上下文，用于前端"能否交战"预判。L1（`combat.preview_single`）：单动作校验 —— 用干跑模式检查解决、规则、AP，但不执行效果。L1.5（`combat.preview_targets`）：多目标可达性预览 —— 在 L0 之上对候选目标集合批量求解，避免前端逐个发起 L0 请求。L2（`combat.preview_chain`）：完整动作链模拟 —— 模拟整条动作链，含累积 AP 消耗和位置投影。所有四个命令均为只读合约，走命令管道但跳过保存与 tick 推进。

**边界案例：**

- L0 检查的"交战计划"会枚举所有合法可达格子（遍历所有可通行瓦片 × 所有攻击技能），为每个格子生成移动+攻击序列，按总 AP 成本排序 —— 相当于穷举路径查找器。
- L0 的失败原因检查有严格顺序：行动者能力（capability）→ 目标可见性（observation）→ 目标能力（target\_capability）→ 空间可达性（spatial）。每一阶段可短路返回，前端据此展示最具体的失败原因。
- 能力封锁在空间可达性检查之前执行，返回结构化的"能力失败"信息供前端展示。
- 可见性检查（角色是否被观测到）在空间可达性之前执行 —— 即使目标在射程内但不可见，也返回不可达。
- 错误原因脱敏 —— 内部前缀被去除，只向用户暴露业务层面的原因。

#### 框架 D-3：效果应用器注册表

**设计意图：** 按效果类型注册的应用器注册表。目前有 6 个内置类型：伤害、治疗、移动、逃离、技能效果应用、AP 变更。效果按声明顺序先进先出地对每个目标应用。不可回滚 —— 失败仅记入日志。

**边界案例：**

- 致命错误（目标不存在）设置失败标记并中断整个动作；非致命失败只记日志，继续执行其余效果。
- 效果支持以行动者自身为作用域 —— 一个技能可以同时对目标造成伤害并治疗施法者自己。
- 移动效果应用器实际上是真正执行位移的入口 —— 内部调用底层移动函数 `obl_perform_move_core` 完成坐标更新与日志发射，应用器自身负责目标合法性校验、位移向量解算与战斗上下文记录。代码注释中"应用器仅做验证和记录"的旧描述已过时。
- 逃离目标选择使用"maximin over immediate neighbors"算法 —— 仅对当前位置的相邻安全格子做评估，选择"到最近的其他活跃战斗成员距离最大化"的格子，而非全局搜索"到所有其他成员最远"的格子。这是一种贪心的局部最优策略，复杂度可控。

#### 框架 D-4：结构化战斗事件发射器

**设计意图：** 在收集器之上提供新格式的事件（battlelog.v2），包含类型化事件、唯一关联 ID、通道分离（渲染 vs 调试）。每个动作和效果有且仅发射一次事件（幂等防护）。

**边界案例：**

- 包含回滚检查点 —— 在目标结算中使用保存点回滚时可以撤销已发射的事件。
- 原因映射：内部使用 `dead`，对外暴露为 `death`。
- 泄露 ID 按类型分组追踪，用于清除事件引用特定效果。

#### 框架 D-5：目标结算单元

**设计意图：** 每个目标的完整结算循环：绑定最新数据 → 规则校验 → 参与状态判定 → 声明效果 → 投递 → 征召 → 应用效果 → 持久化。每个目标在数据库保存点保护下执行，业务失败时可回滚。

**边界案例：**

- 回滚恢复 10 个维度的状态：①行动者数据、②战斗缓存、③目标状态、④资源提交标记、⑤动作启动标记（v2\_action\_started）、⑥投递执行标记（delivery\_executed）、⑦效果 UID 列表、⑧按类型分组的效果 UID 映射、⑨日志检查点（如非 null 则调用 rollbackTo）、⑩数据库 SAVEPOINT 回滚。原报告仅列 7 个维度，遗漏了动作启动标记、投递执行标记以及按类型分组的效果 UID 映射。
- 空目标策略有两种模式：`execute`（无目标时仍执行投递，用于全局效果）和 `fail`（回滚报错）。
- 资源预扣和提交都是幂等的 —— 防止重入或混合干跑/真实场景中双倍扣减。

#### 框架 D-6：目标捕获注册表

**设计意图：** 注册表驱动的目标捕获系统，有四种内置策略：直接角色、战斗敌对、格子角色、自我标识。将解析后的瞄准目标转换为有序的结算目标列表。

**边界案例：**

- 读取数据有三层回退：运行时内存 > 计划状态内存 > 数据库（按优先级读取确保动作链内的读一致性）。
- 格子角色策略从三个源头合并 PID 后去重，再反向删除空间不一致的条目。
- 结构校验拒绝重复的角色目标。

#### 框架 D-7：战斗上下文

**设计意图：** 单次动作执行的唯一状态载体，通过引用传递消除隐式状态耦合。效果和快照按目标独立存储。

**边界案例：**

- 数据通过引用赋值传入，修改会回流到调用方 —— 对跨动作状态共享至关重要但需要仔细跟踪。
- 空目标列表时返回专用的空引用哨兵，防止悬空引用。
- 标签缓存绑定到当前目标索引，切换目标时忘了失效会导致标签使用错误目标的状态。

#### 框架 D-8：标签派生与规则匹配

**设计意图：** 声明式标签系统，将游戏状态派生（纯读）与配置驱动的规则匹配解耦。标签分两类：每次重新计算（如 `self`、`tile_impassable`）和从可变标记读取（如 `dead`、`escaped`）。

**边界案例：**

- 特定标签只对特定目标类型生效 —— `tile_*` 标签只在格子目标上返回有效值，其他目标类型上固定为 `false`。
- `self` 标签双重角色：既是技能指定目标为自身时的条件，也可拦截玩家误选了自己作为 PID 目标。
- 规则匹配是纯配置驱动的 —— 遍历禁止标签列表，只要任何一个标签为 `true` 就匹配失败。零业务逻辑。

#### 框架 D-9：技能配置校验与模块加载

**设计意图：** 以严格的模式级校验加载和校验技能配置。校验覆盖多个维度的兼容性约束：瞄准模式（aim）、捕获策略（capture）、参与策略（participation）、排序策略（sort）、关系约束（relation: any/self/hostile/friendly）、空目标策略（empty\_policy: fail/execute）、射程配置（range.mode: fixed/inherit/additive/capped\_additive/move\_power，以及 range.max/bonus 数值合法性）、可见性策略（observation: none/revealed/controller\_known/detected/visible）、可见性与瞄准解析器的兼容性（如 revealed/controller\_known 要求 tile 瞄准，detected 要求 pid 瞄准）、投递类型（delivery.types 必须为非空字符串数组）。按需加载模块文件。

**边界案例：**

- 四种内置捕获策略各自定义了强制性的瞄准、参与、排序组合，校验时强制执行，违反则抛异常。
- 缺失模块不报错 —— 某些技能是纯配置驱动的，不需要 PHP 钩子。

#### 框架 D-10：动作链投影器

**设计意图：** 统一校验和预览链的干跑语义。按执行顺序维护计划状态，通过技能钩子声明效果，再通过效果投影器将其投影到计划状态。

**边界案例：**

- 冷却待处理追踪 —— 链内已"使用"的技能被记录，同链内相同技能后续动作会被拒绝。
- 链内行动者终止会中断整个链，后续动作跳过。
- 失败时回滚计划状态 —— 恢复到动作执行前的快照，确保失败不污染后续动作。

#### 框架 D-11：战斗状态管理

**设计意图：** 操作内存中的战斗成员名单和可变标记数据结构。对攻击管道执行三分支死亡检测。清理已退出的参战者。

**边界案例：**

- 三分支检测的优先级是：逃离 > 存活 > 死亡 —— 已经逃离的角色不能被标记为死亡。
- 退役清理函数有二次调用保护 —— 如果动作已为空，说明已清理过，直接返回。
- 清理操作（无论 dead 还是 escaped）都会将角色 AP 重置为最大值 —— 虽然对死亡角色无实际意义，但保持世界状态一致性。

#### 框架 D-12：五种射程解析模式

**设计意图：** 基于技能配置的射程模式，支持五种模式：固定值、继承、累加、带上限累加、移动力换算。同时提供空间决策 —— 综合可达性、射程、可负担性的判定。

**边界案例：**

- 射程模式（`range.mode`）与 AP 计算器（`ap_calc`）是两个独立的配置字段。`range.mode = 'move_power'` 时 `base_range = obl_get_move_power()`，而 `effective_range` 来自 `ap_calc` 对应的预算投影器（仅 `move_distance` 注册了投影器）。若技能配置 `range.mode = 'move_power'` 但 `ap_calc = 'fixed'`，则 `effective_range = null`，空间决策回退到 `base_range`。不应将两者混为一谈。
- 空间决策的资源感知：如果资源已被预扣，使用预扣前的 AP；未被预扣时使用当前 AP。

#### 框架 D-13：五态参与分类器

**设计意图：** 将候选目标分为五种参与状态：成员、可加入、已离开、其他战斗、被封锁。处理征召目标入伍。注：报告中曾出现"六态（含不适用）"的描述，但"不适用"并非独立的状态分类，而是分类器在某些前置条件不满足时的短路返回值，不构成第六态。

**边界案例：**

- 敌对/友好关系的计算基于 `type` 字段（0=玩家，>0=NPC）—— 跨阵营即为敌对，同阵营为友好。
- 参与状态分类的决策流依次检查 6 个阶段：策略（policy）、有效性（validity）、区域（region，即玩家所在 pgroup 是否与目标可达）、关系（relation）、队列（queue）、能力（capability），每个阶段可能短路返回。原报告遗漏了 region 阶段。
- 分类器使用 `FOR UPDATE` 锁定数据库行保证竞态安全。

#### 框架 D-14：效果投影器注册表

**设计意图：** 效果应用器的镜像层，用于干跑/计划状态投影。共享相同的效果类型集合（damage/heal/move/escape/skill\_effect\_apply/ap\_change），设计上应运行于模拟状态之上，不发射日志、不写入数据库。但实际实现中 `skill_effect_apply` 投影器违反了此契约（详见边界案例），直接调用了真实的 `skill_effect_apply` 函数，可能在干跑期间触发 DB 写入。

**边界案例：**

- 伤害/治疗投影器与应用器共享完全相同的数值公式（HP 扣减/恢复 + mhp 上限），但纯内存操作。
- 移动投影器与应用器逻辑存在显著差异：应用器调用底层移动函数 `obl_perform_move_core` 执行真实位移（含日志发射、钩子触发），而投影器仅做空间决策一致性校验后直接修改内存中的 `pls`/`pgroup` 字段。因此"完全相同的效果逻辑"仅适用于无副作用的数值类效果。
- `skill_effect_apply` 投影器实际调用了与真实应用器相同的 `skill_effect_apply` 函数 —— 这意味着投影路径并非完全无副作用，可能在干跑期间触发 DB 写入和持久化效果实例。这比"语义泄漏"更严重——违反了 dry-run 应为纯内存操作的契约。
- 死亡标记在投影器中是同步的 —— 伤害投影后立即调用 `combat_state_mark_dead` 标记死亡，而真实应用器中死亡检测由独立的 `combat_state_post_check` 阶段处理（不直接在 damage 应用器中调用）。这种不对称可能导致 dry-run 与实际执行之间的状态差异。
- `escape` 应用器手写 `tag_mutations[pid]['escaped']=true` 并调用 `combat_effect_select_retreat_target` 执行位移，而投影器调用 `combat_state_mark_escaped` 走完全不同的状态变更路径。
- `ap_change` 应用器当前为 TODO 占位（仅 emit 日志，未实际修改 AP），而投影器已实现 AP 修改逻辑——这是两组函数未同步的实证，可能导致 dry-run 与实际执行结果不一致。
- 投影后自动同步计划状态（`combat_planned_state_sync_actor`），使链中后续动作可见。

#### 框架 D-15：AP 钱包计算器

**设计意图：** 注册表驱动的 AP 计算，支持静态值和动态值（移动力换算）两种计算器。AP 预算投影器补充计算器，提供可用于射程计算的 AP 预算。

**边界案例：**

- 未知的计算器 ID 回退到固定值计算器，不影响战斗。
- 预算投影器和计算器是两个独立的注册表，且容错策略不同：计算器对未知 calc\_id 有兜底（回退 fixed），预算投影器对未知 calc\_id 没有兜底（直接返回 null，空间决策回退到 base\_range）。

#### 框架 D-16：瞄准目标解析

**设计意图：** 将前端意图（意图类型和目标 ID）通过四个已注册解析器（PID、格子、自身、无）转换为后端解析结果。

**边界案例：**

- 解析失败时，根据技能配置的可见性策略选择不同的暴露原因：`revealed`/`detected`/`visible` 策略返回"目标不可见"，而 `none`/`controller_known` 策略返回"目标未找到"。这是一种信息安全的考量——只有要求可见性的技能才暴露"不可见"信息。
- 规则检查暂时替换上下文的目标列表为仅含单目标，规则匹配后恢复。

#### 框架 D-17：可见性决策系统

**设计意图：** 基于可见性策略确定目标是否可见。策略有 5 种枚举值：①`none`（无限制，默认对所有人可见）、②`revealed`（已揭示，迷雾已知即可）、③`controller_known`（控制者已知 —— 用于 NPC 绕过迷雾检查，因 NPC 不持有玩家迷雾知识但需要感知其控制的角色）、④`detected`（已检测 —— 对玩家 actor 检查目标 NPC 的 `discovered` 字段，对 NPC actor 则使用基于 `vision_range` 的距离感知而非 `discovered` 字段）、⑤`visible`（保留枚举值，当前未实现）。

**边界案例：**

- 同一战斗的成员始终可见，无论迷雾或距离。
- 玩家的可见性检查基于迷雾系统；NPC 通过 `controller_known` 策略绕过迷雾检查（迷雾是玩家的地图知识限制，与 NPC 无关）。

### 模块 E：游戏逻辑

#### 框架 E-1：Tick 驱动事件调度

**设计意图：** 游戏的主时钟机制。核心概念是当前 tick（`obl_tick`）与已处理 tick（`obl_pretick`）的对偶。业务系统通过三段监听器注册机制接入：战斗 NPC（串行，最多消费一个高级请求后跳出）、空闲 NPC（顺序执行所有监听器，不提前跳出——"并行"含义是全部执行而非并发）、善后（串行，已用于技能效果生命周期管理如 CD 递减、buff 过期等，非预留）。推进策略与推进机制分离。

**边界案例：**

- 异常处理：catch 块记录错误日志后重新抛出异常（`throw $e`），异常向上传播而非被吞掉。状态机在 catch 块中不做任何修改，因此"保持当前状态"成立。
- 同一 tick 内防止同一行动者重复执行 —— 域（combat/world）严格限定，冲突时记录到调试日志。
- 战斗域监听器串行化 —— 最多消费一个高级请求后跳出。
- MVP 限制：仅支持单人玩家（通过当前用户单例实现）。

#### 框架 E-2：统一角色数据模型

**设计意图：** 定义了所有游戏实体的共享数据架构和生命周期 —— 玩家（`type=0`）和 NPC（`type>0`）使用相同的表。所有非规范数据通过 JSON 字段结构化存储。提供对称的编解码函数，以及按 PID、名称、批次、区域获取的功能。

**边界案例：**

- 背包槽位动态补齐 —— 从索引 0 到最大槽位数，缺失键自动设为 null。
- 装备字段空字符串变为空数组，格式错乱的 JSON 优雅降级。
- NPC 类型触发专门的技能默认值注入。
- 创建玩家记录时从旧 PHP 格式字段映射为新结构化格式 —— 一次性迁移。

#### 框架 E-3：基于图的移动系统

**设计意图：** 基于 `(区域组, 格子)` 组合键的瓦片邻接表图论移动系统。核心是一个纯净的移动基础操作（不写数据库、不写日志、不触发钩子），仅修改内存中的位置数据并返回原因。完整的命令级包装器包含区域切换、体力消耗、日志记录和移动后钩子。

**边界案例：**

- 同格检测有区域切换例外 —— 站在出口或入口格时，同位置可以触发区域切换。
- 占用检查（每格一个实体）通过查询当前格的其他实体现有。
- 多格移动计算广度优先距离，按比例扣除体力。
- 区域切换处理前向和后向切换，以及区域链终止。

#### 框架 E-4：结构化事件日志系统

**设计意图：** 取代旧的 HTML 字符串日志机制。后端输出结构化事件（ID、类别、参数），前端控制所有视觉呈现。有两个物理隔离的日志系统：游戏事件日志和诊断错误日志。持久化采用"读取-合并-倒序计数裁剪-写回"模式：先读取已有日志文件，追加新条目，从末尾倒序计数保留最新 N 条，最后以正序写回 —— 每个文件独立配额。

**边界案例：**

- 常规日志与调试日志条目有独立配额（200 常规 vs 50 调试），调试条目不会排挤玩家操作反馈。
- 调试 ID 列表标记高频事件（如敌人移动），前端默认不渲染。
- 错误日志固定 50 条，与常规日志物理隔离。

#### 框架 E-5：战斗有限状态机

**设计意图：** 简约的三状态机：空闲 → 玩家回合 → 处理中。每个先攻队列独立运作。状态转换表是唯一权威来源，非法转换只记录错误不阻塞流程。

**边界案例：**

- 非法转换记录到错误日志，当前状态不变 —— 不抛出异常，不阻塞流程。
- 状态创建使用 `INSERT IGNORE` —— 记录已存在时不覆盖。
- 卡死检测：处理中状态的默认超时 30 秒。

#### 框架 E-6：视野与感知系统

**设计意图：** 包含三个子系统：视野范围计算（瓦片图 BFS）、迷雾清除（幂等 UPSERT）、敌人发现（反应式可见性 —— 超出视野范围的敌人变为未发现）。

**边界案例：**

- BFS 经过不可通行的瓦片但不会穿越它们：你能看到远处的山但不能看穿它。
- 已死亡的敌人保留原有发现状态（方便搜刮）。
- 视野范围大于迷雾清除范围 —— 你会发现敌人但看不清地面细节。

#### 框架 E-7：探索与交互管道

**设计意图：** 编排探索流程：视野更新 → 迷雾清除 → 道具发现 → 敌人发现 → 钩子。迷雾（格子可见性）和道具发现（可操作性）是两个独立关注点。道具发现按距离区分正常可见和近视伪装。POI 搜索支持首次/重复掉落表和通用机制分发框架。

**边界案例：**

- 从视野内所有未发现道具中随机抽取几个批次发现。
- POI 机制分发使用命名约定查找函数，不存在时发出"机制待实现"日志。
- 掉落表计数支持固定值或随机范围。

#### 框架 E-8：NPC AI 行为系统

**设计意图：** NPC 通过 tick 监听器机制接入。战斗 NPC 在自己的轮到当前顺位时执行战斗回合；非战斗 NPC 按 AI 类型巡逻/搜寻/发呆。NPC 共享统一数据模型，可以穿越迷雾。

**边界案例：**

- 复杂的行动阻塞逻辑：按优先级排列 7 个检查点 —— 无效 ID、死亡或非活跃、能力检查、战斗域、行动中战斗（action\_battle，行动者已在某场战斗中）、已有 bid（bid\_present，已存在待处理行为请求）、行为已征召（actor\_behavior\_claimed，行动者行为已被其他系统占用）。每个检查点可短路返回对应原因字符串。
- 战斗技能选择链：攻击技能射程预判 → 逃跑兜底 → 发呆。
- 移动检查同时判断可通行性、玩家占用、其他实体占用。
- 发现状态反应式更新 —— 离开玩家视野后变为未发现。
- 被发现的敌人移动时会清除其所在格的迷雾。

#### 框架 E-9：静态世界生成系统

**设计意图：** 每个区域独立的资源生成。以潮汐区为桶分组，每个桶独立应用 POI 池和散落道具池配置。POI 放置去重（每格一个 POI），道具散落按格概率判定。

**边界案例：**

- 可用瓦片数可能少于请求的 POI 数量，自动调整。
- 配置驱动 —— 池或表为空时跳过（无硬依赖）。

### 模块 F：物品系统

#### 框架 F-1：槽位背包与 itm0 暂存槽协议

**设计意图：** 物品栏是编号槽位系统，有一个特殊的 0 号槽（itm0）用于物品中转。拾取 → itm0 → 自动整理 → 背包。合成产品 → itm0 → 自动整理 → 背包。堆叠合并、拾取、丢弃、整理围绕这个核心协议设计。

**边界案例：**

- 无限标志 `∞` 作为一等公民贯穿所有操作（不递减、PHP 原生比较）。
- 堆叠合并要求参数完全相同（序列化为排序后的键字符串比较）。
- 堆叠合并的原子性：两遍算法 —— 先计算容量，不足直接返回 false，不产生变更。
- 拾取操作对近视物品进行揭示，陷阱物品原子删除且不获得任何道具。

#### 框架 F-2：配置驱动的合成系统

**设计意图：** 整个合成系统是配置驱动的 —— 配方是纯数据，引擎是通用的。材料匹配分三层（ID > itmk 类别 > 标签），有三种消耗模式（全部消耗、消耗耐久、不消耗）。工作台材料对消耗模式有约束（只能匹配不消耗类）。

**边界案例：**

- 堆叠物品展开为多个虚拟占位；非堆叠物品约束为数量=1。
- 所有占位必须被匹配消耗 —— 多余物品导致匹配失败。
- 配方失败时有诊断分析 —— 统计所有配方的失败原因，返回最频繁的一个。

#### 框架 F-3：使用效果分发器

**设计意图：** 一个纯净的注册器模式 —— 框架本身不定义任何具体效果。具体效果函数由所属子系统注册（通过命名约定）。效果从模板查找，不是从实例。

**边界案例：**

- 使用效果不存在的函数不是崩溃而是记录警告。
- 耐久消耗仅对有限耐久值操作，无限标志不受影响。

### 模块 G：技能系统

#### 框架 G-1：配置驱动的技能清单与三种生命周期

**设计意图：** 技能由两个配置文件不可变定义：身份配置（生命周期、能力拒绝）和战斗配置（战斗机制、AP、射程、瞄准/捕获规则）。技能有三种生命周期。永久型：始终存在。装备型：根据装备注入/移除。效果型：由技能效果创建，携带效果实例状态。持久化前剥离逻辑对两类技能不对称：装备技能无条件剥离（每次持久化都从运行时清单中移除，下次加载时由装备注入器重建）；效果技能仅在效果实例为空时才删除整个条目（非空时保留）。

**边界案例：**

- 装备技能注入通过匹配装备槽位的标签或 itmk 类别来决定是否授予。
- 效果型技能在格式化时如果效果实例为空，整个技能条目被删除。
- 未知技能在持久化时被跳过（未找到定义的技能不写入），而非保留 —— 与"向前兼容"的描述不符，实际是静默丢弃。

#### 框架 G-2：模块化技能钩子

**设计意图：** 模块注册器自动加载所有模块文件，提供装备注入器的钩子注册点。核心引擎不关心具体技能逻辑。

### 模块 H：技能效果系统

#### 框架 H-1：实例化效果生命周期

**设计意图：** 效果实例是一等公民 —— 带 UID、状态（待生效/生效中）、来源元数据、触发边界、延迟、持续时间、堆叠模式。生命周期受 tick 驱动：在边界事件触发时从待生效转为生效中，到期时被垃圾回收。

**边界案例：**

- 当前仅支持"刷新"堆叠模式（替换同状态类的旧实例）。
- 边界为 `immediate` 时直接创建为生效中状态，否则创建为待生效。
- 垃圾回收时比较序列化前后状态检测变更，避免不必要写入。

#### 框架 H-2：能力封锁桥接

**设计意图：** 效果通过能力提供者注册到角色能力系统。生效中的效果实例读取自身定义的能力拒绝列表，告诉能力系统哪些能力被封锁。能力系统再被命令门控和参与分类器调用，形成完整回路。

**边界案例：**

### 模块 K：Pinia 状态管理层

#### 框架 K-1：战斗回合编排 + 演示播放管道

**设计意图：** 一个总编排器，管理整个战斗生命周期 —— 普通/战斗模式切换、守护进程心跳轮询、NPC 自动刷新、演示批处理消费、场景重基准协调。它被设计为非阻塞协调器，将动画委托给执行器，将演示委托给会话，将场景过渡委托给场景存储。

**边界案例：**

- 演示播放循环达到 32 轮上限时仅输出 console.warn 警告，不强制终止会话 —— 会话状态保留，已消费的批次继续处理，防止死循环的同时不丢失未完成的状态。
- 播放间隙检测到战斗 ID 变化时终止旧会话。
- 战斗结束段与普通段区分处理（使用特殊覆盖流程）。

#### 框架 K-2：合成模态状态机 + 防抖预览

**设计意图：** 提供响应式、防抖的合成预览，避免 API 洪泛。支持两种材料来源（背包堆叠和工作台材料）和两种库存模型（堆叠模型和耐久模型）。防抖策略同时考虑领先触发和尾随触发。

**边界案例：**

- 无材料时短路跳过 API 调用，立即返回空结果。
- 陈旧的 API 响应被废弃（通过递增请求 ID 防护）。

#### 框架 K-3：多层命令门控

**设计意图：** 命令队列实现了 5 层门控检查，所有存储通过此管道执行命令。检查顺序为：HTTP 请求锁 + 冷却 → itm0 暂存锁（非允许命令）→ 模式锁（战斗/探索）→ 演出水位锁（由演示场景阶段决定，播放中阻塞命令）→ 处理中锁（仅推进 tick 的命令）。能力检查作为额外的未编号 guard 存在，不在 5 层编号内。同样的门控逻辑被 `canExecute` 和 `execute` 共享，确保 UI 状态和执行路径一致。

**边界案例：**

- 能力封锁响应触发立即刷新玩家信息以获取更新后的能力状态。
- 冷却由后端返回的定时器字段驱动，通过 setTimeout 自动释放。

#### 框架 K-4：事件驱动架构通过数据管理器总线

**设计意图：** 存储相互之间不直接导入进行事件通知。它们通过一个中央数据管理器广播/监听事件。关键事件有 `game:action-completed`（可变操作完成）、`game:tick-advanced`（tick 推进）、`map:loaded`（地图加载）、`battle:started/ended`（战斗开始/结束）、`ui:toast`（消息通知）。这实现了之前由 jQuery 事件完成的解耦。

**边界案例：**

- 事件的广播和监听在存储的 setup 函数中直接注册（不在组件中），跟随存储生命周期。

#### 框架 K-5：角色数据枢纽

**设计意图：** 一个以 PID 为键的统一角色数据存储，整合来自三个 API 范围的数据（敌人、玩家信息、战斗上下文）。提供清晰的写入入口点和派生的只读计算列表。分离关注点 —— 合并敌人补丁 vs 原子替换敌人全量列表。

**边界案例：**

- 替换地图敌人时，清除其他区域的过期角色（非 0 类型、不在新列表中、不同区域、且不在战斗中）。

#### 框架 K-6：不可变原子地图投影 + 修订追踪

**设计意图：** 单组不可变地图投影确保原子更新（无半应用状态）。每次写入递增修订号，允许观察者廉价检测变化。

**边界案例：**

- 并发加载保护 —— 如果新加载请求启动，旧响应被丢弃。

#### 框架 K-7：视觉状态过渡机

**设计意图：** 管理"播放战斗动画"和"显示权威世界投影"之间的视觉边界。状态有三阶段：空闲（场景稳定）、播放中（战斗播放激活，权威更新排队）、重基准中（战斗后移交，应用权威数据并播放动画）。

**边界案例：**

- 播放中阶段收到权威更新时，更新排队但不应用。
- 重基准移动允许多个动画注册，最后统一作为屏障执行。

#### 框架 K-8：日志增量获取 + 智能 Toast 分发

**设计意图：** 增量获取日志条目，使用最后时间戳检测新条目。仅当覆盖层打开时才触发 Toast。智能合并相邻的同类条目。

**边界案例：**

- 多条 `item.to_bag` 条目合并为"把 N 件道具放进了背包"。
- 调试条目从 Toast 和未读计数中过滤掉。

#### 框架 K-9：有序批处理消费者 + 间隙检测

**设计意图：** 维护已消费的批序号和未来批次的待处理映射。支持间隙检测 —— 如果观察到的头部大于已消费但下一个序号不在待处理中，说明发生了冷启动刷新。

#### 框架 K-10：角色动画意图派发

**设计意图：** 存储只负责发布"意图"（应该发生什么），组合式函数负责 GSAP 动画执行。意图序列号始终递增即使意图值相同，确保观察者能触发重复的同值意图。

**边界案例：**

- 玩家倒地后非倒地意图会被排队，等起身后再派发。
- 战斗结束时特殊处理逃逸状态：派发 `enter` 而非 `battle-end`，然后连锁到 `battle-end`。

#### 框架 L-1：统一交互列表模式

#### 框架 L-3：战斗装填模式编排器

**设计意图：** PreloadArea 实现战斗装填 UI —— 技能列表 + AP 进度条 + 装填队列 + 执行/清空按钮。支持战前和战中两种模式。终结技始终排在队列末尾，非终结技插入到终结技前。二次初始化通过 sessionKey 去重防护。

**边界案例：**

#### 框架 L-4：异步播放编排器

**设计意图：** BattleModal 使用 async/await + sleep Promise 结构按顺序驱动播放。支持取消（标志 + unmount 清理），使用 CSS transitionend 等待覆盖过渡完成。

**边界案例：**

#### 框架 L-5：附加后演出效果

**边界案例：**

## 第四部分：跨模块关键模式

### 模式 1：读写隔离阶梯

整个系统有三个清晰的隔离层级：

| 层级    | 入口            | 事务 | 房间锁 | 玩家锁 | 副作用         |
| ----- | ------------- | -- | --- | --- | ----------- |
| 只读    | state.php     | 无  | 无   | 无   | 无数据库写入      |
| 服务端写入 | heartbeat.php | 有  | 有   | 无   | Tick 处理、恢复  |
| 认证写入  | command.php   | 有  | 有   | 有   | 所有以上 + 玩家变更 |

状态 API 被显式设计为纯读取 —— 即使数据库表不存在也不创建。

### 模式 2：双响应协议

系统有两个不同的响应格式（状态协议的简洁格式 vs 命令协议的丰富格式），各有不同的错误码集和 HTTP 状态码映射。命令协议是超集，状态协议是简化子集。

### 模式 3：日志即反馈

业务处理程序不直接返回错误信息，而是写结构化日志。总线比较新旧日志推导反馈。这意味着三个不同的日志流，每个有不同的消费者：游戏事件日志（命令反馈）、错误日志（诊断）、战斗日志（演示批处理投递）。这是单请求内的轻量级事件溯源模式。

### 模式 4：能力系统作为通用访问控制桥梁

能力系统连接三个模块：状态 API 投影玩家可执行的操作，UI 根据此渲染可用操作，命令总线在执行前重新检查。这形成了一个完整的回路：展示可用的 → 展示可用的 → 玩家操作 → 服务端再次检查。

### 模式 5：基于注册表的插件架构

八个子系统使用相同的全局注册表模式：瞄准解析器、目标捕获器、目标捕获验证器（combat\_target\_capturer\_validators，与目标捕获器分开注册，专门校验捕获结果的合法性）、效果应用器、效果投影器、AP 计算器、AP 预算投影器（combat\_ap\_budget\_projectors，独立于 AP 计算器，专门用于将可用 AP 投影为有效射程）、标签派生器。大多数业务逻辑扩展只需向这些注册表添加条目。

### 模式 6：效果应用器与投影器平行宇宙

一组函数实现实时应用（写数据库、发射日志），镜像组实现干跑投影（只改内存）。两组共享相同的效果类型集合（damage/heal/move/escape/skill\_effect\_apply/ap\_change）和注册表结构，但实际执行逻辑并非"完全相同"——存在多种不对称（详见 D-14）：move 应用器调用底层移动函数执行真实位移，投影器仅做空间决策一致性校验后改内存字段；escape 应用器用 tag\_mutations 标记，投影器调用 combat\_state\_mark\_escaped 走不同路径；ap\_change 应用器当前为 TODO 占位，投影器已实现；damage 投影器同步标记死亡，应用器由独立阶段处理；skill\_effect\_apply 投影器实际调用真实 skill\_effect\_apply 函数，违反 dry-run 纯内存契约。代价是保持两组函数同步，且当前存在未同步的实证。

### 模式 7：数据管理器事件总线

存储不直接导入进行事件通知，而是通过中央数据管理器广播/监听。Pinia 中没有直接的跨存储动作调用链 —— 一切都通过事件总线中介。

### 模式 8：前端控制渲染

后端只发送结构化代码（物品 ID、日志 ID、技能 ID、参数），前端完全控制视觉呈现。本地化字典和日志模板都在前端项目中。

### 模式 9：标签作为通用语义胶水

标签在后端多个子系统之间充当通用外键：使用效果、合成材料匹配、装备技能注入、数据规则校验。注：合成系统中的"工作台材料"识别实际通过 `source` 字段（值为 'workbench'）区分，而非标签 —— 标签用于材料类别匹配，但工作台来源识别是独立字段。

### 模式 10：itm0 暂存槽协议

0 号槽作为临时中转位，分离"获取"和"存储"操作并防止部分状态更新。拾取和合成都经过 itm0 → 自动整理 → 背包。暂存失败时锁定玩家直到腾出空间。

### 模式 11：计划状态缓存（Planned State / Dry-Run Cache）

动作链投影和目标结算期间，所有对战斗状态的读取和写入都走一层"计划状态"缓存：运行时内存 > 计划状态内存 > 数据库的三层回退读取，确保链内动作看到前序动作的投影结果而非陈旧数据库值。写入先改计划状态，提交阶段才落库；失败时回滚计划状态到快照。这层缓存是 D-5（目标结算单元）、D-6（目标捕获注册表）、D-10（动作链投影器）共享的基础设施，使 dry-run 与真实执行在状态视图上保持一致（尽管效果应用器与投影器之间存在执行差异，详见 D-14）。

### 模式 12：空间决策报价-验证（Spatial Decision Quote/Verify）

移动类效果的空间可达性采用"报价-验证"两阶段协议：预览/投影阶段向空间决策器请求报价（返回 `target_ap_cost` 等可验证字段），实际执行阶段重新计算空间决策并验证报价值与当前值一致。若报价过期（目标移动、AP 变化、迷雾更新等），验证失败并拒绝执行。此模式横跨 D-2（预览系统，发起报价）、D-3（效果应用器 move，验证报价）、D-14（效果投影器 move，验证报价一致性），确保 dry-run 预览的 AP 成本和可达性与实际执行结果一致。代价是客户端必须保留报价值并在提交时回传，增加了协议复杂度。
