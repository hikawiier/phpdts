# Oblivions 子系统 — 概念词典、风格、核心原则约束与设计哲学

> 本文档提供概念词典、项目风格、核心原则总体约束与跨任务沉淀的设计哲学

---

## 一、概念词典

> 介绍项目包含的**专有名词**，以下词典中出现的名词具有特定含义，不可按字面意思理解。

### 1.0 tick / 游戏刻

tick 是世界结算的时间单位。1 tick 代表世界上每个角色都能消费 1 时间单位的动作——实际代码语义是 **1 tick 内一个角色不能又战斗又移动**。
tick 由前端心跳驱动推进，后端 tick 编排器按三阶段分发：监听器注册 → 事件调度 → 状态结算。敌人 AI（巡逻/空闲/攻击）、Body Status 衰减、潮汐事件等都以 tick 为节拍。
与"回合 (Turn)"的关系：1 回合 = 1 tick。战斗中的回合是 tick 在战斗域内的别名，强调"单人次一次完整行动"。

### 1.1 区域 (Region) vs 地图格 (Tile)

- **区域**：一个独立的子地图，由多个地图格拼接而成。数据库键 `pgroup`，最多 255 个区域。
- **地图格**：最小的移动单元，数据库键 `pls`（区域内局部索引 1-254）。跨区域时 pls 可重用——区域1的 pls=5 和区域2的 pls=5 是不同的格。
- **组合键**：`(pgroup, pls)` 唯一确定一个地图格。

### 1.2 地板属性 (floor)

地图格的地板属性，**影响玩家交互**（移动消耗修正、技能效果、可破坏性），不是纯装饰：

| 值 | 含义 |
|----|------|
| `standard` | 标准地板 |
| `water` | 含水地板 |
| `vegetation` | 覆植地板 |
| `metal` | 金属地板 |
| `magic` | 富魔力地板 |

### 1.3 潮汐属性 (tide)

**不是海潮涨落，是区域危险等级分区标签。** 潮汐影响资源生成倾向（稀有度权重、敌人生成偏向、事件点类型），不影响玩家移动：

| 值 | 危险等级 | 含义 |
|----|---------|------|
| `shallow` | T-1（低） | 浅滩区，低危险 |
| `deep` | T（中） | 深水区，中危险 |
| `abyss` | T+1（高） | 深海区，高危险 |

> **注意**：`safe` **不是** `tide` 的取值。安全区状态由独立字段 `preset_safe` 标记。

### 1.4 迷雾 (fog) vs 发现 (discovered)

两个**独立**的关注点，不可混淆：

| | 迷雾 (fog) | 发现 (discovered) |
|---|---|---|
| **控制什么** | 地图格的可见性 | 道具的可操作性 |
| **数据位置** | `oblmapstates` 表 `fog` 字段 | `oblmapitem` 表 `discovered` 字段 |
| **如何点亮** | BFS 视野计算，玩家位置扩展 | 玩家进入地图格时自动发现该格所有道具 |
| **效果** | 迷雾格在前端显示为 `░░░` | 未发现的道具不出现在拾取列表中 |

### 1.5 POI vs 散落道具

都是道具来源，但机制不同：

| | POI（建筑物） | 散落道具 |
|---|---|---|
| **位置** | 地图格内的建筑物 | 直接在地图格上 |
| **获取方式** | 需搜索 POI，消耗体力 | 直接拾取 |
| **数据表** | POI 表 | 地图道具表 |
| **搜索次数** | 有搜索次数上限 | 无搜索概念 |
| **生成池** | POI 生成池配置 | 散落道具生成池配置 |

### 1.6 回合 (Turn) vs 轮 (Round)

战斗系统中两个核心时间单位，概念分层：

| | 回合 (Turn) | 轮 (Round) |
|---|---|---|
| **定义** | 单人次一次完整行动（1 tick） | 全队列一轮循环（仅队列操作） |
| **范围** | 1 回合 ⊂ 1 轮 | 1 轮包含多回合 |
| **示例** | 玩家执行技能 / NPC 出手 | 全员 done=1 → 重建队列 |

**命名约定**：
- 代码注释用"回合"指 Turn，"轮"指 Round

### 1.7 战斗中的 Tag 系统（A/B 分类）

战斗目标状态通过 Tag 统一描述。分两类：

**Category A（主视角相关）**：`self`（目标是自己）、`out_of_range`（超出射程）。每次从当前 actor/target 重算，不缓存。

**Category B（绝对状态）**：死亡（角色状态字段为 1）、已逃跑、隐身。通过战斗缓存中的标签变更记录缓存，同一次战斗主调用内跨动作可见，随缓存销毁自动清零。

**配置驱动规则匹配**：技能配置把瞄准规则与捕获规则分开声明。规则匹配对当前瞄准结果或当前目标结算单元的标签集执行；单目标失败只产生跳过标记，其他目标继续。

### 1.8 道具中的 Tag 系统

`item_table.tags` 字段承载两类 Tag：

- **道具性质 Tag**：描述道具的固有属性（`tag_weapon` 武器、`tag_conductor` 导体、`tag_heavy_weight` 重物等），用于合成素材匹配和技能规则匹配
- **系统钩子 Tag**：触发系统行为（如标识道具可被 `obl_use_item` 消费、可被合成系统识别等）

实现方式是**统一读取，各系统自行过滤**——`item.tag.func.php` 统一读写 `tags` 字段，各系统按需过滤自己关心的 Tag ID，不依赖 category 区分。两类 Tag 共享同一字段但语义不同——性质 Tag 是描述性的，钩子 Tag 是指令性的。

### 1.9 PlannedState / Effect Projector / 动作链

玩家一次提交的多个动作是一条动作链，整条动作链属于同一个回合、同一个 tick。动作链内部要能看到前序动作的计划结果，例如 AP 已消费、目标已受伤、角色已移动、目标已逃跑。

因此 dry-run/verify/preview 不应重复读取 DB 当前态当作每一步的真相，而应使用 PlannedState：

- 计划状态缓存保存行动者与目标的计划快照
- 效果投影器把伤害/治疗/移动/逃离/技能效果/AP 变更等效果投影到计划快照
- 动作链投影驱动统一编排链内投影，返回每个动作的成功/失败与效果列表

设计基准：预览与校验必须尽量复用执行语义；差异只在“投影到内存”还是“持久化到 DB”。动作失败是具体规则综合判断结果，不应被压成单一“链失败”概念。

### 1.10 itm0 暂存槽

道具库存的槽位协议。itm0 是玩家库存的第 0 个槽位，承担多种暂存职责：

- **合成产物入 itm0**：合成系统完成素材扣减后，产物先入 itm0，再自动整理到正常槽位
- **拾取暂存**：拾取的道具先入 itm0，再由整理逻辑归位

itm0 的复用设计避免了"产物无处安放"的边界问题，也使合成与拾取共享同一套暂存语义。

### 1.11 ActorRuntime / 角色运行时租约

前端演出基础设施。ActorRuntime 封装角色在演出期间的运行时状态，通过租约（PresentationLease）机制协调角色在战斗场景与世界场景之间的归属。

战斗运行器只操作表现投影与角色运行时租约，不直接操作权威 store。租约机制确保同一角色在同一时刻只被一个场景拥有，避免动画冲突。

### 1.12 CharacterHub / 角色数据枢纽

前端权威 store 的核心节点（实现为 `useCharacterStore`）。CharacterHub 持续接受最新权威快照，不因动画暂停。命令与心跳返回的变更范围进入串行权威刷新 worker，立即合并刷新。
CharacterHub 与表现场景 store 分离，构成"权威投影 vs 演出投影"双投影架构的前端侧。

### 1.13 PresentationLease / 演出租约

演出协议的核心概念。PresentationLease 表示一个场景对角色的临时拥有权：

- 通过 `ActorRuntime.acquire()` 获取租约，返回 `PresentationLease` 实例
- 租约提供 `play()`（播放动画）、`release()`（释放租约）等接口
- 租约释放时可通过 `reconcile` 选项控制是否与权威状态对齐

租约机制解耦了场景切换的时序依赖，使演出过渡更流畅。世界移动、战斗动画等都通过租约协调。

### 1.14 AimIntent vs ResolvedAim

瞄准系统的两层概念：

- **AimIntent（瞄准意图）**：玩家选择的目标表达（如"攻击前方敌人"），对应代码中的 `aim_intent`
- **ResolvedAim（解析后的瞄准结果）**：后端瞄准解析器（AimResolver）根据技能配置将意图解析为具体目标集合，对应代码中的 `resolved_aim`

配置驱动的瞄准解析器把玩家意图转成后端结果，使同一意图可对应不同解析规则（近战 vs 远程 vs 范围）。

### 1.15 TargetResolutionUnit / 目标结算单元

动作捕获的有序结算目标（实现于 `combat.target_unit.php`）。一个动作通过捕获规则捕获多个目标，每个目标构成一个独立的结算单元，携带自己的标签集和参与状态。

单元内的资源提交（AP 扣减）、效果交付（钩子执行）、状态持久化都通过 `dry_run` 标志区分预览与实际执行——dry-run 跳过 DB 写入和钩子调用，只读取计划状态。单目标失败只产生跳过标记，其他目标继续。



## 二、项目风格、核心原则总体约束

> 约束撰写遵循第三节设计哲学：自然语言讲"为什么"（3.1）、保留索引锚点（3.1）、字面贴近意图（3.3）。

### 2.1 数据层独立性

Oblivions 子系统拥有完全独立的数据层，不依赖传统模式的玩家表：

- 玩家与敌人统一存储在 Oblivions 专用玩家表
- 玩家保存函数仅写 Oblivions 专用表，不同步任何数据到传统玩家表
- 游戏信息保存在 Oblivions 模式下跳过传统玩家表查询
- 所有数据通过引用传递，禁止函数内解包到当前作用域

**设计理由**：避免与传统模式的数据结构耦合，允许 Oblivions 独立演进字段结构（如道具参数用 JSON 数组替代传统的多字段编码）。

### 2.2 后端只输出事件结构

结构化日志系统的核心原则：后端只负责"发生了什么 + 参数"，前端完全控制视觉呈现（文案、样式、随机化）。后端 emit 事件时只携带事件 ID、类别与参数字段，不输出任何 HTML 或样式信息。

**设计理由**：
- 视觉呈现是前端职责，后端不应关心 HTML/CSS
- 同一事件可在不同前端上下文呈现不同样式（日志区 vs Toast）
- 前端可独立迭代文案，无需后端发版

### 2.3 权威投影与演出投影分离

- 角色数据枢纽、地图、玩家、战斗目标等权威 store 持续接受最新权威快照，不因动画暂停；命令与心跳返回的变更范围进入串行权威刷新 worker，立即合并刷新。
- 地图网格组件读取表现场景 store；战斗运行器只操作表现投影与角色运行时租约。
- 稳定边界只负责场景重基准、租约协调与游标前移，不再决定网络是否允许刷新。
- 战斗结束遮罩达到覆盖状态时执行战斗场景向世界场景的交接，世界动画可在遮罩下开始。

当前实现已完成双投影闭环：权威 worker 固定按"玩家信息 → 地图/敌人 → 战斗目标"顺序更新真实 stores；表现场景 store 的同步接口在播放中/重基准中阶段只更新待处理权威数据、不改写可见快照，覆盖/稳定边界使用最新权威数据做重基准，动画期间继续到达的权威数据会在重基准完成时自动发布。网络刷新时机不再由表现层边界控制。


### 2.4 属性获取接口为技能系统拓展预留

战斗系统的属性获取函数采用"基础值 + 补正"模式，阶段一返回固定默认值，未来通过技能系统扩展：

- 射程获取：基础射程 1（近战），未来由武器类型 + 技能补正决定
- 先攻获取：基础先攻属性 50，未来由技能提供 buff/补正决定

**关键设计原则**：NPC 的属性差异不通过配置文件硬编码，而是通过技能系统实现。例如想让 NPC 有更多射程、更多先攻，就给该 NPC 配置一个增加射程/先攻的技能，而不是在敌人配置文件中写死属性值。

**设计理由**：
- 技能系统是统一的属性扩展入口，避免属性配置分散在多处
- NPC 与玩家共用同一套属性获取接口，技能效果对双方一致
- 新增 NPC 类型时只需配置技能组合，无需修改属性获取逻辑

### 2.5 新文件必须注册到 obl_bootstrap

Oblivions 子系统通过 obl_bootstrap 集中加载所有函数库。

**强制约定**：
- 新增任何函数库文件，必须在 obl_bootstrap 中注册，按拓扑排序
- 注册时需找到正确的层级：被依赖的文件在前，依赖方在后
- 函数存在性检查 + 条件包含的双保险模式已废弃，统一走 obl_bootstrap 加载

**设计理由**：
- PHP 是动态语言，函数未定义只在运行时报错，编译期无提示
- 集中注册使依赖关系可见，避免散落的条件 include 导致漏加载

> 当前加载层序见 [CODEBASE.md](./CODEBASE.md#三引导加载bootstrap)。

### 2.6 配置驱动而非硬编码

游戏中的规则、属性、行为应通过配置声明，而非硬编码在逻辑中。配置驱动让数据与逻辑分离，新增内容时只需修改配置，无需修改代码。

这一哲学体现在多个子系统：
- 战斗技能由配置文件声明规则，钩子文件提供执行逻辑
- NPC 属性差异通过技能系统实现，而非配置文件硬编码
- 道具行为通过 `use_effect` 钩子分发，而非 switch-case 硬编码
- 合成配方通过 `recipe_table` 配置，素材匹配通过 tag 系统

**判断准则**：如果一类行为会反复出现变体（多个技能、多种道具、多种敌人），就用配置驱动；如果是一次性逻辑，直接写代码更清晰。

### 2.7 钩子模式与纯分发器

复杂系统的入口应是纯分发器，具体行为由注册的钩子实现。`obl_use_item` 是典型示例：命令本身只做参数校验和分发，具体效果（`restore_sp`、`cure_bs`、`gain_resistance`）由独立注册的钩子函数实现。

钩子模式的好处：
- 新增效果类型时只需注册新钩子，无需修改分发器
- 钩子独立测试，互不影响
- 分发器保持简单，避免成为巨大的 switch-case

**约束**：钩子不能直接写数据库或自行查询任意角色 ID，只对当前目标声明效果。这与战斗技能钩子的约束一致（1.10）。

### 2.8 dry-run 契约：预览与执行共享语义

预览（dry-run）、校验（verify）、执行（execute）应共享同一套瞄准、捕获、目标结算语义。差异只在"投影到内存"还是"持久化到 DB"。

这一契约要求：
- 效果投影器（Projector）与效果应用器（Applier）作为镜像函数对，共享相同的效果类型集合
- 投影器纯内存操作，不写库、不发射日志
- 应用器执行真实副作用（写库、发射日志）

**违反契约的后果**：预览结果与实际执行结果不一致，玩家基于预览做出的决策失效。

### 2.9 镜像函数对同步演进

当两个函数互为镜像（如投影器与应用器），任一侧变更必须同步另一侧。镜像对的差异要在文档中显式记录。

这一原则是 2.8 的延伸——dry-run 契约要求镜像对语义一致，但实践中函数对容易随时间漂移。建立强制对齐校验机制（如效果类型集合校验）可防止此类漂移。

## 三、跨任务沉淀的设计哲学

### 3.1 文档撰写的元原则：降低理解成本 + 快速索引目标

撰写文档的最终目的只有两个：**降低读者的理解成本**，以及**让读者快速定位到目标信息**。一切文档结构、内容取舍、术语选择都应以此为衡量标准。

**降低理解成本**要求：
- 文档分层分工，每层只承担一类信息，避免读者在一份文档里同时承受多个抽象层级
- 框架级描述用自然语言讲"为什么这样设计"，不堆砌函数签名与参数释义
- 概念词典解释专有名词的字面外含义，避免读者按字面意思误解

**快速索引目标**要求：
- 保留精确的技术名、字段名、表名作为索引锚点——读者从代码或对话中提到某个术语时，能在文档中直接定位
- 概念词典使用原始术语，便于与代码注释、提交信息、对话上下文对应
- 跨文档引用关系明确，读者知道"代码细节去 CODEBASE.md"、"框架语义去 Dian.md"

**核心反模式——机械翻译**：把技术术语强行中文化（如把技术名译为通称、把字段名译为语义描述）表面上降低了阅读门槛，实际上破坏了文档与代码的索引对应关系。读者无法从文档反查代码，也无法从代码反查文档。技术名、字段名、表名是索引锚点，不是待翻译的英文单词。

**自校准**：每次文档改动后对照两个问题——这次改动让读者更容易理解了吗？让读者更容易找到目标信息了吗？如果两者都没达成，改动是过度加工或方向错误。

### 3.2 概念引入的成本-收益判断

怎么判断要不要引入一个新的概念名词？只要判断解释它的代价更大，还是引入它的代价更大。

- **解释的代价**：读者需要查阅概念词典、理解新概念、建立概念与实体的映射
- **引入的代价**：读者看到原始术语（文件名、函数名、字段名）可能不够抽象，或需要额外上下文

**判断准则**：如果新概念只是对现有实体的中文化翻译，且原始术语本身自解释，保留原始术语更合理——避免造一个需要额外查阅的通称。如果新概念承载了复杂的语义层次（封装了多层含义），引入新概念更合理——用一个术语替代每次的长篇解释。

### 3.3 约束是意图的近似

约束的字面试图捕捉意图，但无法面面俱到——约束是人定的，受制定者认知局限。约束的意图通常是"以最小代价获得最大效益"（如过滤杂音、降低理解成本），但约束的字面可能过于宽泛（误杀索引锚点）或过于狭窄（漏掉某些杂音）。

执行约束时，用成本-收益判断（3.2）寻找意图——遵守约束的代价是什么？获得了什么收益？当代价 > 收益时，字面与意图冲突，回到意图。

**典型场景**：Dian.md 约束"不出现具体函数名或参数"的意图是"过滤实现细节杂音"，但字面没有区分"实现细节杂音"（函数名、参数签名）和"索引锚点"（文件名、标签名、枚举值）。机械执行字面会误杀索引锚点，违反 3.1 的快速索引目标。正确做法是回到意图——过滤杂音，保留索引锚点。

## 四、经验备忘（踩过的坑）

> 本节记录项目中实际遇到的具体问题及其教训，与第二部分的原则约束形成"原则-案例"对照。

### 4.1 跨层命名契约的静默失败

**现象**：后端 emit 的事件 ID 与前端模板字典的 key 命名风格不一致（点号分隔 vs 下划线分隔），导致前端模板匹配失败，事件被静默丢弃，无任何错误日志告警。此类问题在前端模板匹配逻辑默认"未匹配即跳过"时尤为隐蔽。

**教训**：跨层字符串契约必须 1:1 对齐；前端模板匹配失败应视为硬错误并打印警告而非静默跳过；新增日志 ID 时强制同步前端模板，建立契约校验。

### 4.2 注释/文档与代码行为漂移

**现象**：移动效果应用器的代码注释写"仅做验证和记录"，但实际执行真实位移（含日志发射、钩子触发、坐标更新）。注释与代码行为完全相反，导致后续开发者基于注释推断行为时产生误判。

**教训**：描述性注释要随代码同步更新；当注释与代码冲突时，以代码实际行为为准；对"描述性注释"保持警惕，优先信任代码。

### 4.3 干跑契约违反——投影器调用真实函数

**现象**：效果投影器本应纯内存操作（不写库、不发射日志），但其中一类效果（技能效果应用）的投影器直接调用与真实应用器相同的函数，可能在预览期间触发数据库写入和持久化效果实例。这违反了 dry-run 应为纯内存操作的契约。

**教训**：dry-run 路径必须严格隔离副作用；投影器不能调用有副作用的真实函数；建立契约校验机制（如标记接口或运行时检查）防止此类泄漏。

### 4.4 平行宇宙函数未同步演进

**现象**：效果应用器与投影器作为镜像函数对，存在多处未同步——AP 变更应用器为占位实现但投影器已实现；伤害投影器同步标记死亡但应用器由独立阶段处理；逃离走完全不同的状态变更路径。这些不一致可能导致 dry-run 预览与实际执行结果差异。

**教训**：镜像函数对必须同步演进；建立效果类型集合的强制对齐校验；任一侧变更必须同步另一侧；差异要在文档中显式记录。

### 4.5 历史遗留防御代码不可达分支

**现象**：游戏仓库保存路径中有一分支检查虚拟行标记并执行插入操作，但由于加载函数总是直接查库而不读全局缓存，此分支实际不可达，属历史遗留防御代码。这类代码会误导后续开发者以为该分支有实际作用。

**教训**：防御代码要定期审计；不可达分支应删除避免误导；防御代码的触发条件要与实际数据流匹配；对"看起来在防御但实际不可达"的代码保持警惕。

### 4.6 相似独立配置字段的混淆

**现象**：射程模式与 AP 计算器是两个独立配置字段，曾因名称相似被混为一谈。射程模式决定基础射程（固定值/继承/累加/带上限累加/移动力换算），AP 计算器决定预算投影（可用于射程计算的 AP 预算）。两者组合在特定情况下（射程模式为移动力换算但 AP 计算器为固定值）会产生有效射程为空的回退情况。

**教训**：相似但独立的配置字段要明确命名区分；配置组合的所有路径要文档化；字段语义边界要在配置校验阶段强制对齐。

### 4.7 异步播放组件的卸载清理

**现象**：异步播放组件（如战斗模态框）在卸载时如果不立即清理定时器、回调、引用，会产生内存泄漏和回调问题（如组件已销毁但回调仍尝试访问组件状态）。

**教训**：异步播放组件必须在卸载时立即清理所有异步资源；使用取消标志 + 卸载清理双保险；回调执行前检查组件是否仍挂载。
