# Oblivions 子系统 — 概念词典、风格、核心原则约束与设计哲学

> 本文档提供概念词典、项目风格、核心原则总体约束与跨任务沉淀的设计哲学

---

## 一、概念词典

> 介绍项目包含的**专有名词**，以下词典中出现的名词具有特定含义，不可按字面意思理解。

### 1.0 tick / 游戏刻

tick 是世界结算的时间单位。1 tick 代表世界上每个角色都能消费 1 时间单位的动作——实际代码语义是 **1 tick 内一个角色不能又战斗又移动**。
tick 由前端心跳驱动推进，后端 tick 编排器按三阶段分发：监听器注册 → 事件调度 → 状态结算。敌人 AI（巡逻/空闲/攻击）、Body Status 衰减、潮汐事件等都以 tick 为节拍。
与"回合 (Turn)"的关系：1 回合 = 1 tick。战斗中的回合是 tick 在战斗域内的别名，强调"单人次一次完整行动"。

### 1.1 区域 (Region) vs 地图格 (Tile)

- **区域**：一个独立的子地图，由多个地图格拼接而成。数据库键 `pgroup`，最多 255 个区域。
- **地图格**：最小的移动单元，数据库键 `pls`（区域内局部索引 1-254）。跨区域时 pls 可重用——区域1的 pls=5 和区域2的 pls=5 是不同的格。
- **组合键**：`(pgroup, pls)` 唯一确定一个地图格。

### 1.2 地板属性 (floor)

地图格的地板属性，**影响玩家交互**（移动消耗修正、技能效果、可破坏性），不是纯装饰：

| 值 | 含义 |
|----|------|
| `standard` | 标准地板 |
| `water` | 含水地板 |
| `vegetation` | 覆植地板 |
| `metal` | 金属地板 |
| `magic` | 富魔力地板 |

### 1.3 潮汐属性 (tide)

**不是海潮涨落，是区域危险等级分区标签。** 潮汐影响资源生成倾向（稀有度权重、敌人生成偏向、事件点类型），不影响玩家移动：

| 值 | 危险等级 | 含义 |
|----|---------|------|
| `shallow` | T-1（低） | 浅滩区，低危险 |
| `deep` | T（中） | 深水区，中危险 |
| `abyss` | T+1（高） | 深海区，高危险 |

> **注意**：`safe` **不是** `tide` 的取值。安全区状态由独立字段 `preset_safe` 标记。

### 1.4 迷雾 (fog) vs 发现 (discovered)

两个**独立**的关注点，不可混淆：

| | 迷雾 (fog) | 发现 (discovered) |
|---|---|---|
| **控制什么** | 地图格的可见性 | 道具的可操作性 |
| **数据位置** | `oblmapstates` 表 `fog` 字段 | `oblmapitem` 表 `discovered` 字段 |
| **如何点亮** | BFS 视野计算，玩家位置扩展 | 玩家进入地图格时自动发现该格所有道具 |
| **效果** | 迷雾格在前端显示为 `░░░` | 未发现的道具不出现在拾取列表中 |

### 1.5 POI vs 散落道具

都是道具来源，但机制不同：

| | POI（建筑物） | 散落道具 |
|---|---|---|
| **位置** | 地图格内的建筑物 | 直接在地图格上 |
| **获取方式** | 需搜索 POI，消耗体力 | 直接拾取 |
| **数据表** | POI 表 | 地图道具表 |
| **搜索次数** | 有搜索次数上限 | 无搜索概念 |
| **生成池** | POI 生成池配置 | 散落道具生成池配置 |

### 1.6 回合 (Turn) vs 轮 (Round)

战斗系统中两个核心时间单位，概念分层：

| | 回合 (Turn) | 轮 (Round) |
|---|---|---|
| **定义** | 单人次一次完整行动（1 tick） | 全队列一轮循环（仅队列操作） |
| **范围** | 1 回合 ⊂ 1 轮 | 1 轮包含多回合 |
| **示例** | 玩家执行技能 / NPC 出手 | 全员 done=1 → 重建队列 |

**命名约定**：
- 代码注释用"回合"指 Turn，"轮"指 Round

### 1.7 战斗中的 Tag 系统（A/B 分类）

战斗目标状态通过 Tag 统一描述。分两类：

**Category A（主视角相关）**：`self`（目标是自己）、`out_of_range`（超出射程）。每次从当前 actor/target 重算，不缓存。

**Category B（绝对状态）**：死亡（角色状态字段为 1）、已逃跑、隐身。通过战斗缓存中的标签变更记录缓存，同一次战斗主调用内跨动作可见，随缓存销毁自动清零。

**配置驱动规则匹配**：技能配置把瞄准规则与捕获规则分开声明。规则匹配对当前瞄准结果或当前目标结算单元的标签集执行；单目标失败只产生跳过标记，其他目标继续。

### 1.8 道具中的 Tag 系统

`item_table.tags` 字段承载两类 Tag：

- **道具性质 Tag**：描述道具的固有属性（`tag_weapon` 武器、`tag_conductor` 导体、`tag_heavy_weight` 重物等），用于合成素材匹配和技能规则匹配
- **系统钩子 Tag**：触发系统行为（如标识道具可被 `obl_use_item` 消费、可被合成系统识别等）

实现方式是**统一读取，各系统自行过滤**——`item.tag.func.php` 统一读写 `tags` 字段，各系统按需过滤自己关心的 Tag ID，不依赖 category 区分。两类 Tag 共享同一字段但语义不同——性质 Tag 是描述性的，钩子 Tag 是指令性的。

### 1.9 PlannedState / Effect Projector / 动作链

玩家一次提交的多个动作是一条动作链，整条动作链属于同一个回合、同一个 tick。动作链内部要能看到前序动作的计划结果，例如 AP 已消费、目标已受伤、角色已移动、目标已逃跑。

因此 dry-run/verify/preview 不应重复读取 DB 当前态当作每一步的真相，而应使用 PlannedState：

- 计划状态缓存保存行动者与目标的计划快照
- 效果投影器把伤害/治疗/移动/逃离/技能效果/AP 变更等效果投影到计划快照
- 动作链投影驱动统一编排链内投影，返回每个动作的成功/失败与效果列表

设计基准：预览与校验必须尽量复用执行语义；差异只在“投影到内存”还是“持久化到 DB”。动作失败是具体规则综合判断结果，不应被压成单一“链失败”概念。

### 1.10 itm0 暂存槽

道具库存的槽位协议。itm0 是玩家库存的第 0 个槽位，承担多种暂存职责：

- **合成产物入 itm0**：合成系统完成素材扣减后，产物先入 itm0，再自动整理到正常槽位
- **拾取暂存**：拾取的道具先入 itm0，再由整理逻辑归位

itm0 的复用设计避免了"产物无处安放"的边界问题，也使合成与拾取共享同一套暂存语义。

### 1.11 ActorRuntime / 角色运行时租约

前端演出基础设施。ActorRuntime 封装角色在演出期间的运行时状态，通过租约（PresentationLease）机制协调角色在战斗场景与世界场景之间的归属。

战斗运行器只操作表现投影与角色运行时租约，不直接操作权威 store。租约机制确保同一角色在同一时刻只被一个场景拥有，避免动画冲突。

### 1.12 CharacterHub / 角色数据枢纽

前端权威 store 的核心节点（实现为 `useCharacterStore`）。CharacterHub 持续接受最新权威快照，不因动画暂停。命令与心跳返回的变更范围进入串行权威刷新 worker，立即合并刷新。
CharacterHub 与表现场景 store 分离，构成"权威投影 vs 演出投影"双投影架构的前端侧。

### 1.13 PresentationLease / 演出租约

演出协议的核心概念。PresentationLease 表示一个场景对角色的临时拥有权：

- 通过 `ActorRuntime.acquire()` 获取租约，返回 `PresentationLease` 实例
- 租约提供 `play()`（播放动画）、`release()`（释放租约）等接口
- 租约释放时可通过 `reconcile` 选项控制是否与权威状态对齐

租约机制解耦了场景切换的时序依赖，使演出过渡更流畅。世界移动、战斗动画等都通过租约协调。

### 1.14 AimIntent vs ResolvedAim

瞄准系统的两层概念：

- **AimIntent（瞄准意图）**：玩家选择的目标表达（如"攻击前方敌人"），对应代码中的 `aim_intent`
- **ResolvedAim（解析后的瞄准结果）**：后端瞄准解析器（AimResolver）根据技能配置将意图解析为具体目标集合，对应代码中的 `resolved_aim`

配置驱动的瞄准解析器把玩家意图转成后端结果，使同一意图可对应不同解析规则（近战 vs 远程 vs 范围）。

### 1.15 TargetResolutionUnit / 目标结算单元

动作捕获的有序结算目标（实现于 `combat.target_unit.php`）。一个动作通过捕获规则捕获多个目标，每个目标构成一个独立的结算单元，携带自己的标签集和参与状态。

单元内的资源提交（AP 扣减）、效果交付（钩子执行）、状态持久化都通过 `dry_run` 标志区分预览与实际执行——dry-run 跳过 DB 写入和钩子调用，只读取计划状态。单目标失败只产生跳过标记，其他目标继续。

### 1.16 瞬态战斗 (Transient Battle) vs 常态战斗 (Persistent Battle)

按战斗在后端存续的时长划分的两类战斗路径，决定了前端是否需要建立多回合基础设施。

| | 瞬态战斗 | 常态战斗 |
|---|---|---|
| **定义** | `battle.start` 在同一请求内执行完玩家回合并触发 `battle_end` | 战斗跨多个回合，玩家与 NPC 交替行动 |
| **后端状态机** | IDLE → AWAITING_INPUT → EXECUTING → IDLE（一进一出） | IDLE → AWAITING_INPUT / AUTO_PENDING → EXECUTING → 下一回合 → … → IDLE |
| **前端 `enterBattleMode`** | 跳过——`refreshBattle` 读到 `action !== 'battle'`，不建立多回合基础设施 | 被调用——`action === 'battle'` 触发，设置 `currentQid` |
| **battlelog 播放** | 通常在一次命令响应内完整播放（`turn_intro` + turn + battle_end） | 可跨多个 batch；`turn_key` 保持回合身份，`drainBattleTicksToStable` 持续消费 |
| **多回合基础设施** | 不需要（跨批次 session 复用、NPC 轮询、动作面板均不需要） | 需要 |
| **退出** | `applyVerifiedBattleState` → `exitBattleMode` | 同左 |

**设计基准**：前端"战斗被感知"的判据是 battlelog 事件流，不是 `enterBattleMode`。瞬态战斗跳过 `enterBattleMode` 是正确行为——它不需要多回合基础设施，battlelog + 播放架构已完整传递战斗内容（动作动画、文本日志、HP 变化、结束模态框、handoff）。`startBattle` 设的 `currentMode='battle'`（UI 锁定）+ battlelog 播放（内容传递）+ `exitBattleMode`（清理）已完整覆盖瞬态战斗的生命周期，无需为它建立独立概念。

**概念用途**：沟通时说"瞬态战斗"即指"1 回合内结束、`enterBattleMode` 被跳过、单 batch 完整播放"这一完整语义；说"常态战斗"即指"多回合、`enterBattleMode` 正常调用、跨 batch drain 消费"这一完整语义。

### 1.17 BattleTurn / 权威回合身份

BattleTurn 是战场级持久状态，不是请求、tick 或 presentation batch 的别名。`oblbattle_state.turn_seq` 在同一 `qid` 内单调递增并组成稳定 `turn_key=qid:turn_seq`；`round_num` 只表达轮次规则和显示，不承担身份。

回合开放与动作执行是两个边界：`AWAITING_INPUT` / `AUTO_PENDING` 表示控制权已经交给玩家或系统，`EXECUTING` 表示该回合已被原子认领。玩家命令必须提交 `expected_turn_seq`；事件通过 `turn_opened` 和同一组 `qid`、`round_num`、`turn_seq`、`turn_key` 陈述领域事实，前端不得从请求次数或数字组合反推回合身份。



## 二、项目风格、核心原则总体约束

> 约束撰写遵循第三节设计哲学：自然语言讲"为什么"（3.1）、保留索引锚点（3.1）、字面贴近意图（3.3）。

### 2.1 数据层独立性

Oblivions 子系统拥有完全独立的数据层，不依赖传统模式的玩家表：

- 玩家与敌人统一存储在 Oblivions 专用玩家表
- 玩家保存函数仅写 Oblivions 专用表，不同步任何数据到传统玩家表
- 游戏信息保存在 Oblivions 模式下跳过传统玩家表查询
- 所有数据通过引用传递，禁止函数内解包到当前作用域

**设计理由**：避免与传统模式的数据结构耦合，允许 Oblivions 独立演进字段结构（如道具参数用 JSON 数组替代传统的多字段编码）。

### 2.2 后端只输出事件结构

结构化日志系统的核心原则：后端只负责"发生了什么 + 参数"，前端完全控制视觉呈现（文案、样式、随机化）。后端 emit 事件时只携带事件 ID、类别与参数字段，不输出任何 HTML 或样式信息。

**设计理由**：
- 视觉呈现是前端职责，后端不应关心 HTML/CSS
- 同一事件可在不同前端上下文呈现不同样式（日志区 vs Toast）
- 前端可独立迭代文案，无需后端发版

### 2.3 权威投影与演出投影分离

- 角色数据枢纽、地图、玩家、战斗目标等权威 store 持续接受最新权威快照，不因动画暂停；命令与心跳返回的变更范围进入串行权威刷新 worker，立即合并刷新。
- 地图网格组件读取表现场景 store；战斗运行器只操作表现投影与角色运行时租约。
- 稳定边界只负责场景重基准、租约协调与游标前移，不再决定网络是否允许刷新。
- 战斗结束遮罩达到覆盖状态时执行战斗场景向世界场景的交接，世界动画可在遮罩下开始。

当前实现已完成双投影闭环：权威 worker 固定按"玩家信息 → 地图/敌人 → 战斗目标"顺序更新真实 stores；表现场景 store 的同步接口在播放中/重基准中阶段只更新待处理权威数据、不改写可见快照，覆盖/稳定边界使用最新权威数据做重基准，动画期间继续到达的权威数据会在重基准完成时自动发布。网络刷新时机不再由表现层边界控制。


### 2.4 属性获取接口为技能系统拓展预留

战斗系统的属性获取函数采用"基础值 + 补正"模式，阶段一返回固定默认值，未来通过技能系统扩展：

- 射程获取：基础射程 1（近战），未来由武器类型 + 技能补正决定
- 先攻获取：基础先攻属性 50，未来由技能提供 buff/补正决定

**关键设计原则**：NPC 的属性差异不通过配置文件硬编码，而是通过技能系统实现。例如想让 NPC 有更多射程、更多先攻，就给该 NPC 配置一个增加射程/先攻的技能，而不是在敌人配置文件中写死属性值。

**设计理由**：
- 技能系统是统一的属性扩展入口，避免属性配置分散在多处
- NPC 与玩家共用同一套属性获取接口，技能效果对双方一致
- 新增 NPC 类型时只需配置技能组合，无需修改属性获取逻辑

### 2.5 新文件必须注册到 obl_bootstrap

Oblivions 子系统通过 obl_bootstrap 集中加载所有函数库。

**强制约定**：
- 新增任何函数库文件，必须在 obl_bootstrap 中注册，按拓扑排序
- 注册时需找到正确的层级：被依赖的文件在前，依赖方在后
- 函数存在性检查 + 条件包含的双保险模式已废弃，统一走 obl_bootstrap 加载

**设计理由**：
- PHP 是动态语言，函数未定义只在运行时报错，编译期无提示
- 集中注册使依赖关系可见，避免散落的条件 include 导致漏加载

> 当前加载层序见 [Dian.md C-1 拓扑引导加载](./Dian.md#框架-c-1拓扑引导加载)。

### 2.6 配置驱动而非硬编码

游戏中的规则、属性、行为应通过配置声明，而非硬编码在逻辑中。配置驱动让数据与逻辑分离，新增内容时只需修改配置，无需修改代码。

这一哲学体现在多个子系统：
- 战斗技能由配置文件声明规则，钩子文件提供执行逻辑
- NPC 属性差异通过技能系统实现，而非配置文件硬编码
- 道具行为通过 `use_effect` 钩子分发，而非 switch-case 硬编码
- 合成配方通过 `recipe_table` 配置，素材匹配通过 tag 系统

**判断准则**：如果一类行为会反复出现变体（多个技能、多种道具、多种敌人），就用配置驱动；如果是一次性逻辑，直接写代码更清晰。

### 2.7 钩子模式与纯分发器

复杂系统的入口应是纯分发器，具体行为由注册的钩子实现。`obl_use_item` 是典型示例：命令本身只做参数校验和分发，具体效果（`restore_sp`、`cure_bs`、`gain_resistance`）由独立注册的钩子函数实现。

钩子模式的好处：
- 新增效果类型时只需注册新钩子，无需修改分发器
- 钩子独立测试，互不影响
- 分发器保持简单，避免成为巨大的 switch-case

**约束**：钩子不能直接写数据库或自行查询任意角色 ID，只对当前目标声明效果。这与战斗技能钩子的约束一致（1.10）。

### 2.8 dry-run 契约：预览与执行共享语义

预览（dry-run）、校验（verify）、执行（execute）应共享同一套瞄准、捕获、目标结算语义。差异只在"投影到内存"还是"持久化到 DB"。

这一契约要求：
- 效果投影器（Projector）与效果应用器（Applier）作为镜像函数对，共享相同的效果类型集合
- 投影器纯内存操作，不写库、不发射日志
- 应用器执行真实副作用（写库、发射日志）

**违反契约的后果**：预览结果与实际执行结果不一致，玩家基于预览做出的决策失效。

### 2.9 镜像函数对同步演进

当两个函数互为镜像（如投影器与应用器），任一侧变更必须同步另一侧。镜像对的差异要在文档中显式记录。

这一原则是 2.8 的延伸——dry-run 契约要求镜像对语义一致，但实践中函数对容易随时间漂移。建立强制对齐校验机制（如效果类型集合校验）可防止此类漂移。

### 2.10 命名约定作为索引锚点

命名是文档与代码之间索引对应关系的基础。统一的命名前缀和格式约定让开发者能从文档反查代码、从代码反查文档——违反命名等于破坏可检索性。

- **函数前缀 `obl_`**：所有 Oblivions 模式新函数使用 `obl_` 前缀（如 `obl_save_player`、`obl_tick_orchestrator_heartbeat`），与旧 PHPDTS 核心函数区分
- **表命名 `bra_obl{entity}`**：数据表使用 `bra_obl` 前缀连写实体名（如 `bra_oblplayers`、`bra_oblmapstates`、`bra_oblmapitem`），不使用下划线分隔 `obl` 与实体名
- **日志 ID `{category}.{subevent}`**：结构化日志使用点分层级格式（如 `move.success`、`enemy.discovered`、`tick.dispatch.error`），category 对应日志分类，subevent 对应具体事件
- **命令名 `{namespace}.{action}`**：新命令使用点分命名空间格式（如 `map.move`、`item.pickup`、`battle.submit_turn`、`combat.preview_chain`），namespace 对应模块，action 对应操作

### 2.11 并发安全机制

Oblivions 是多请求并发环境（玩家命令 + 心跳 + NPC tick），必须在数据层保证操作的原子性和幂等性，避免竞态条件导致的数据不一致。

- **拾取竞态**：道具拾取使用 `DELETE ... WHERE iid=... AND discovered>0` + `affected_rows()` 检查，返回 0 说明道具已被其他请求拾取，回滚 itm0 暂存
- **搜索计数**：POI 搜索使用 `SET search_count=search_count+1` 原子递增，避免并发搜索导致计数错乱
- **迷雾写入**：视野点亮使用 `INSERT ... ON DUPLICATE KEY UPDATE fog=1` 幂等写入，避免重复插入
- **日志写入**：结构化日志持久化使用 `file_put_contents(..., LOCK_EX)` 排他锁，防止多请求并发写入丢数据
- **命令并发锁**：Command Bus 使用 `flock(LOCK_EX|LOCK_NB)` 玩家级文件锁，同一玩家同时只能处理一个命令，获取失败返回 `COMMAND_IN_PROGRESS`

### 2.12 文档与代码双向锚点契约

Oblivions 后端与 Vex-Vue 前端使用框架编号连接设计语义与代码实现。框架编号（如 `A-1`、`K-3`）是唯一机器主键；中文名称仅用于阅读，不得作为关联关系的唯一依据。

**设计理由**：静态代码索引（如已消除的 CODEBASE.md）会随代码变更滞后；双向锚点将"代码归属"信息内化到代码注释中（随代码同步），将"搜索起点"保留在文档中（相对稳定），MCP 动态查询作为桥梁。框架编号（`A-1`）是唯一机器主键，中文名称只供阅读——ASCII 编号不受中文检索和 MCP 输出编码影响，是可靠的稳定主键。

#### 标签语义

- `@module` 表示文件的主要所有权。属于模块 A-N 的代码文件必须标注一个主要模块。
- 文件不属于现有框架时，仍可且应保留 `@module`。
- `@framework` 表示文件直接实现某项框架语义，不表示调用、依赖或间接使用。
- 一个文件可以直接实现多个框架，但每个框架必须使用独立的 `@framework` 行。
- 不得使用 `/`、逗号或自然语言在一条标签中合并多个框架。
- 依赖文件、调用方和普通消费者不得为了增加覆盖率而标注 `@framework`。
- 标签只负责文件级导航（"哪个文件实现这个框架"）；函数签名、调用链、数据流等结构关系继续由 codebase-memory-mcp 负责。标签不替代图谱工具的结构化查询能力。

推荐格式：

```php
/**
 * @module A API 层
 * @framework A-3 状态查询范围分发
 * @framework A-4 结构化视图投影函数集
 */
```

#### 文档锚点

- `Dian.md` 中每个基准框架必须包含一行 `**代码锚点：**`。
- 锚点只列直接实现该框架的少量核心文件。
- 文件路径必须是从仓库根目录开始的完整相对路径。
- 每个文件使用简短职责说明，如入口、核心实现、配置或状态管理。
- 锚点行不得维护函数名、scope 清单、事件清单或调用关系等易漂移实现细节。
- 函数、调用链和数据流继续由 codebase-memory-mcp 动态查询。

#### 一致性不变量

对任意框架编号 F，必须同时满足：

1. F 在 `Dian.md` 中存在唯一框架章节。
2. `Dian.md` 中 F 的所有锚点路径均指向真实文件。
3. 代码中的每个 `@framework F` 都能反查到 F 的文档章节。
4. `Dian.md` 中 F 的锚点文件集合，必须等于代码中标注 `@framework F` 的文件集合。
5. `@module` 与框架所属模块不一致时，视为校验失败。

#### 变更同步

新增、移动、重命名、删除核心文件，或调整文件的模块/框架职责时，必须在同一项变更中同步更新：

- 文件头 `@module`、`@framework` 标签；
- `Dian.md` 对应框架的代码锚点；
- 双向锚点自动校验结果。

未通过锚点校验的框架调整不得视为完成。

#### 校验入口

- 全项目严格校验：`php oblivions/tools/validate_design_anchors.php`
- 迁移期间模块校验：`php oblivions/tools/validate_design_anchors.php --module=A`（将 `A` 替换为目标模块；局部通过不代表全项目合规）
- 校验器测试：`php oblivions/tools/tests/validate_design_anchors_test.php`
- 生产源码扫描排除 `oblivions/cache/**` 等运行时生成目录；缓存文件即使使用 `.php` 扩展名也不参与模块覆盖率与框架锚点检查。
- 实现与错误模型见[文档与代码双向锚点校验器设计案](./docs/文档与代码双向锚点校验器设计案.md)

严格模式是项目满足本契约的唯一机器验收入口。模块模式只服务迁移过程，不得代替最终严格校验。

### 2.13 Vue v-for 管理子树的持久视觉状态禁止命令式 DOM

Vue v-for 通过 `:key` 复用 DOM 元素，diff 时只 patch 自己声明的 vnode 子树，不清理外部命令式注入的"野 DOM"子节点或命令式叠加的 class。当响应式状态变化触发重渲染时，这些命令式产物残留，导致视觉状态与数据状态不一致。

**约束范围**：在 v-for 管理的 DOM 子树内，**持久视觉状态**（临时 class、装饰子节点、动画状态标记）必须通过响应式状态驱动 `:class` / `v-if`，让 Vue patch 自动增减 DOM。如果某个视觉效果的生命周期由 `setTimeout` 而非响应式状态管理，它就是命令式残留——`setTimeout` 清理依赖定时器执行，而 Vue 重渲染可能在定时器触发前就已发生。

**不在约束范围内的命令式 DOM 操作**（这些操作不产生持久视觉状态，不与 v-for diff 冲突）：
- 只读测量：`getBoundingClientRect`、`offsetWidth`、`querySelector` 读取位置/尺寸
- 滚动定位：`scrollTo`、`scrollLeft`、`scrollTop`
- 焦点管理：`focus`、`blur`
- 事件委托：`addEventListener` / `removeEventListener`（绑定在容器上，不操作子节点）
- 动画库执行：GSAP 等命令式动画库直接操作 `style` / `transform`（瞬态动画，非持久状态）
- Teleport 外的 SVG/overlay 渲染：不在 v-for 子树内，无 diff 冲突

**典型场景**：地图网格的路径预览、抖动动画、高亮动画；战斗界面的瞄准叠加层。这些视觉效果的共同特征是"基于 v-for 渲染的列表项叠加持久临时状态"，必须通过响应式状态注入而非命令式 DOM 操作。

### 2.14 键盘快捷键统一引入策略

前端键盘交互应作为**基础框架的一部分**统一引入，禁止在功能模块中单独注册 `keydown` 监听。

**现状背景**：仓库中已存在 3 处独立的 `keydown` 监听——`App.vue` 全局、`useMapInteraction`、`AimMode`。各模块对 `ESC` / `Enter` / 方向键存在语义重叠。若在每个新功能模块单独引入快捷键，需为每个模块人工设置屏障（如"我在瞄准模式下不响应"），违反"框架先行"原则——模块不应独自决定自己是否响应某个键。

**约束**：

- 在统一的键盘管理层（`useBattleKeyboard` composable 或 `KeyboardManager`）建立前，所有新功能模块的交互均通过鼠标/触摸完成，**不引入键盘快捷键**
- 统一管理层的职责：明确分层优先级 `BattleModal > AimMode > PreloadArea > Map`，由该层统一下派事件，模块只订阅不监听
- 已有的 3 处独立监听在统一层建立后应统一收编，避免监听散落

**设计理由**：

- 键盘事件的"焦点优先级"是跨模块的全局关注点，任何单一模块都不应独自决定自己是否响应某个键
- `ESC` / `Enter` / 方向键在不同上下文（瞄准中 vs 装填中 vs 移动中）有不同语义，需统一仲裁
- 框架先行让后续模块无需关心"我的快捷键会不会和别人冲突"，由统一层负责消解冲突

### 2.15 少即是多的视觉元约束

前端视觉以"少即是多"为元约束：在注意力稀缺的前提下，通过精简的灰阶基底 + 细节化的 UI/UX 设计 + 唯一强调色机制，为用户想象力腾出空间。具体实施细节（禁用彩色粒子/震波、reduced-motion、灰阶冗余编码、瞬时反馈统一 popUp 等）见 [前端美学风格-设计案](./docs/前端美学风格-设计案.md) 与 [前端美学风格-现状审计](./docs/前端美学风格-现状审计-2026-07-11.md)。

**灰阶为基底**：默认配色以灰阶为主，信息通过灰阶亮度、形状、纹理、位置冗余编码，不引入彩色信号色。NPC 红描边、blocked 红、safe-zone 绿、pending 黄等彩色信号色必须清理为灰阶形状编码。

**唯一强调色规则**：当需要快速增强注意力时，允许引入唯一第三方颜色作为注意力锚点（如危险红、治疗绿）。但强调色是例外而非默认，同一场景中同时存在的强调色应严格控制数量——强调色的力量来自稀缺性，泛滥的强调色等同于新的彩色噪声，退化为无强调。

**视觉语言统一性**：精简风格下，不协调、不统一的视觉元素会抢占注意力。战斗反馈、地图表现、UI 容器层次、伤害数字、HP 条等所有视觉子系统必须共享同一套视觉语言（灰阶 + 形状 + 细线），不得绕开建立第二套彩色视觉语言。普通日志已正确降级为灰阶、字重和下划线，战斗弹窗、伤害数字等不得绕开这套规则。

**设计理由**：
- 注意力是稀缺资源，所有视觉元素都在抢占注意力，精简是降低注意力负担的最直接手段
- 画面、颜色是项目弱项，精简风格把弱项转化为风格特征（灰阶即风格，留白即设计）
- 强调色的力量来自稀缺性，泛滥的强调色等同于无强调色
- 视觉语言不统一会让用户在多套语言间切换，等同于注意力税

## 三、跨任务沉淀的设计哲学

### 3.1 文档撰写的元原则：降低理解成本 + 快速索引目标

撰写文档的最终目的只有两个：**降低读者的理解成本**，以及**让读者快速定位到目标信息**。一切文档结构、内容取舍、术语选择都应以此为衡量标准。

**降低理解成本**要求：
- 文档分层分工，每层只承担一类信息，避免读者在一份文档里同时承受多个抽象层级
- 框架级描述用自然语言讲"为什么这样设计"，不堆砌函数签名与参数释义
- 概念词典解释专有名词的字面外含义，避免读者按字面意思误解

**快速索引目标**要求：
- 保留精确的技术名、字段名、表名作为索引锚点——读者从代码或对话中提到某个术语时，能在文档中直接定位
- 概念词典使用原始术语，便于与代码注释、提交信息、对话上下文对应
- 跨文档引用关系明确，读者知道"代码细节用 MCP 动态查询"、"框架语义去 Dian.md"

**核心反模式——机械翻译**：把技术术语强行中文化（如把技术名译为通称、把字段名译为语义描述）表面上降低了阅读门槛，实际上破坏了文档与代码的索引对应关系。读者无法从文档反查代码，也无法从代码反查文档。技术名、字段名、表名是索引锚点，不是待翻译的英文单词。

**自校准**：每次文档改动后对照两个问题——这次改动让读者更容易理解了吗？让读者更容易找到目标信息了吗？如果两者都没达成，改动是过度加工或方向错误。

### 3.2 概念引入的成本-收益判断

怎么判断要不要引入一个新的概念名词？只要判断解释它的代价更大，还是引入它的代价更大。

- **解释的代价**：读者需要查阅概念词典、理解新概念、建立概念与实体的映射
- **引入的代价**：读者看到原始术语（文件名、函数名、字段名）可能不够抽象，或需要额外上下文

**判断准则**：如果新概念只是对现有实体的中文化翻译，且原始术语本身自解释，保留原始术语更合理——避免造一个需要额外查阅的通称。如果新概念承载了复杂的语义层次（封装了多层含义），引入新概念更合理——用一个术语替代每次的长篇解释。

### 3.3 约束是意图的近似

约束的字面试图捕捉意图，但无法面面俱到——约束是人定的，受制定者认知局限。约束的意图通常是"以最小代价获得最大效益"（如过滤杂音、降低理解成本），但约束的字面可能过于宽泛（误杀索引锚点）或过于狭窄（漏掉某些杂音）。

执行约束时，用成本-收益判断（3.2）寻找意图——遵守约束的代价是什么？获得了什么收益？当代价 > 收益时，字面与意图冲突，回到意图。

**典型场景**：Dian.md 约束"不出现具体函数名或参数"的意图是"过滤实现细节杂音"，但字面没有区分"实现细节杂音"（函数名、参数签名）和"索引锚点"（文件名、标签名、枚举值）。机械执行字面会误杀索引锚点，违反 3.1 的快速索引目标。正确做法是回到意图——过滤杂音，保留索引锚点。

### 3.4 少即是多——注意力稀缺与想象力核心

前端视觉设计的元哲学是"少即是多"，其根基是两个核心命题：**用户注意力有限**，**用户想象力是最关键的**。

**注意力稀缺作为设计元前提**：画面、文字、动画、颜色所有元素都会抢占用户有限的注意力。设计的第一要务不是"展示什么"，而是"不展示什么"——每增加一个视觉元素都要问"它值得抢占多少注意力"。这个前提决定了精简风格不是美学偏好，是注意力经济的必然选择。

**弱项认知决定精简必然性**：项目在画面、颜色上是弱项，强行追求精细画面或丰富配色会暴露弱项。精简风格把弱项转化为风格特征——灰阶即风格，留白即设计。这与"用最擅长的工具解决问题"的工程哲学一致：不与强项项目比拼画面精细度，而在注意力经济上做减法。

**协调性即节省注意力**：精简不等于简陋。在简单颜色的基础上，UI/UX 的细节化设计是必要的——但细节化的目的不是装饰，是确保整体画幅协调统一。不协调、不统一的视觉元素会迫使用户在多套视觉语言间切换，等同于额外的注意力税。统一性不是美学偏好，是注意力经济的延伸。

**想象力核心**：文字、画面的设计都要以引发用户联想为核心目标。留白不是空缺，是为想象力腾出的空间——用户脑海中构建的画面比任何精细渲染都更有冲击力。这与 ASCII 终端风格的设计哲学一致：少量字符激发的想象，胜过具象图像的直接呈现。

**与约束的关系**：本节是 [2.15 少即是多的视觉元约束](#215-少即是多的视觉元约束) 的元哲学根基。约束层的"灰阶基底"、"唯一强调色"、"视觉语言统一性"三条规则，都可以从这四个命题中推导出来。当约束的字面与具体场景冲突时，回到本节寻找意图——例如"是否允许某个彩色元素"的判断标准是"它是否值得抢占注意力"以及"它是否破坏视觉统一性"。

## 四、经验备忘（踩过的坑）

> 本节记录项目中实际遇到的具体问题及其教训，与第二部分的原则约束形成"原则-案例"对照。

### 4.1 跨层命名契约的静默失败

**现象**：后端 emit 的事件 ID 与前端模板字典的 key 命名风格不一致（点号分隔 vs 下划线分隔），导致前端模板匹配失败，事件被静默丢弃，无任何错误日志告警。此类问题在前端模板匹配逻辑默认"未匹配即跳过"时尤为隐蔽。

**教训**：跨层字符串契约必须 1:1 对齐；前端模板匹配失败应视为硬错误并打印警告而非静默跳过；新增日志 ID 时强制同步前端模板，建立契约校验。

### 4.2 注释/文档与代码行为漂移

**现象**：移动效果应用器的代码注释写"仅做验证和记录"，但实际执行真实位移（含日志发射、钩子触发、坐标更新）。注释与代码行为完全相反，导致后续开发者基于注释推断行为时产生误判。

**教训**：描述性注释要随代码同步更新；当注释与代码冲突时，以代码实际行为为准；对"描述性注释"保持警惕，优先信任代码。

### 4.3 投影器复用真实函数——共享副作用风险

**现象**：效果投影器本应纯内存操作（不写库、不发射日志），技能效果应用投影器复用真实应用器函数 `skill_effect_apply`。当前该函数仅修改传入的角色数组（`&$actor['skillpara']`），无数据库写入、无日志发射、无钩子触发——只要传入的是计划状态角色数组，函数本身无副作用。但投影器与应用器共享同一函数意味着：函数未来若新增副作用（如持久化、日志、钩子），投影路径会自动继承，违反 dry-run 契约。

**教训**：dry-run 路径复用真实函数时，必须建立隔离机制（如标记接口或运行时副作用检查）防止未来函数演进引入副作用泄漏；共享函数的当前无副作用状态不是长期保证，需契约校验机制兜底。

### 4.4 平行宇宙函数未同步演进

**现象**：效果应用器与投影器作为镜像函数对，存在多处未同步——AP 变更应用器为占位实现但投影器已实现；伤害投影器同步标记死亡但应用器由独立阶段处理；逃离走完全不同的状态变更路径。这些不一致可能导致 dry-run 预览与实际执行结果差异。

**教训**：镜像函数对必须同步演进；建立效果类型集合的强制对齐校验；任一侧变更必须同步另一侧；差异要在文档中显式记录。

### 4.5 历史遗留防御代码不可达分支

**现象**：游戏仓库保存路径中有一分支检查虚拟行标记并执行插入操作，但由于加载函数总是直接查库而不读全局缓存，此分支实际不可达，属历史遗留防御代码。这类代码会误导后续开发者以为该分支有实际作用。

**教训**：防御代码要定期审计；不可达分支应删除避免误导；防御代码的触发条件要与实际数据流匹配；对"看起来在防御但实际不可达"的代码保持警惕。

### 4.6 相似独立配置字段的混淆

**现象**：射程模式与 AP 计算器是两个独立配置字段，曾因名称相似被混为一谈。射程模式决定基础射程（固定值/继承/累加/带上限累加/移动力换算），AP 计算器决定预算投影（可用于射程计算的 AP 预算）。两者组合在特定情况下（射程模式为移动力换算但 AP 计算器为固定值）会产生有效射程为空的回退情况。

**教训**：相似但独立的配置字段要明确命名区分；配置组合的所有路径要文档化；字段语义边界要在配置校验阶段强制对齐。

### 4.7 异步播放组件的卸载清理

**现象**：异步播放组件（如战斗模态框）在卸载时如果不立即清理定时器、回调、引用，会产生内存泄漏和回调问题（如组件已销毁但回调仍尝试访问组件状态）。

**教训**：异步播放组件必须在卸载时立即清理所有异步资源；使用取消标志 + 卸载清理双保险；回调执行前检查组件是否仍挂载。

### 4.8 设计案中"删除/修改"操作未验证完整调用链

**现象**：设计案在编写"删除函数 / 修改事件 / 替换状态字段"类操作时，未 grep 验证完整调用链，导致函数名拼写错误、computed 替换后留下死代码、删除事件但监听端未清理等问题。

**教训**：设计案中所有"删除/修改函数、事件、状态字段、类型成员"的操作，必须 grep 验证完整调用链——函数名拼写、所有调用者、监听端、类型定义、return 导出。删除一个广播事件需同步清理监听端（监听函数 + listen/unlisten 注册 + 联合类型成员）；用 computed 替换函数时检查原函数所有调用者，无调用者则删除函数本身而非保留。
