> 目的：在完整复核当前游戏刻实现、API 入口、战斗队列、普通 NPC AI、移动/探索、前端 heartbeat/refresh 链路后，重新定义“战斗行为与普通世界 NPC 行为的结算顺序”问题。本文修正此前“战斗 tick / 战斗独占 tick”的错误抽象：游戏刻只有一个，战斗和普通 NPC 都在同一个 game tick 内结算；但同一 actor 在同一 tick 内只能执行一次主动行为，且该行为只能属于战斗行为或非战斗行为之一。

## 2. 当前游戏刻真实实现

### 2.1 tick / processed_tick 的语义

当前游戏刻 source of truth 是 `{$tablepre}oblgame`：

1. `tick`：已推进到的游戏刻。
2. `processed_tick`：已结算到的游戏刻。
3. `$gamevars['obl_tick']` / `$gamevars['obl_pretick']` 只是兼容镜像。

`obl_tick_advance()` 只做 `obl_tick++`，不直接解析事件。  
`obl_tick_orchestrator_resolve_pending()` 在发现 `processed_tick < tick` 时：

1. 计算 `delta = tick - processed_tick`。
2. 先执行 `obl_tick_synchronize()`，把 `processed_tick` 追到当前 `tick`。
3. 再调用 `obl_resolve_tick_events($delta)`。
4. 如果 NPC 战斗回合在事件解析中请求推进，则调度末尾再次 `tick++`，留下新的 pending tick。

### 2.2 tick 推进的两条主路径

玩家命令路径：

```text
command.php
  -> Command Bus 执行业务命令
  -> 若 advances_tick=true，obl_tick_orchestrator_after_command()
  -> obl_tick_advance()
  -> 持久化 oblgame.tick
```

heartbeat 路径：

```text
heartbeat.php
  -> obl_tick_orchestrator_heartbeat()
  -> 若 processed_tick < tick，resolve pending tick
  -> tick dispatch 内 NPC 战斗回合可再次请求 tick++
```

State API 是纯读：

```text
state.php
  -> 只同步 gamevars 镜像
  -> 不 heartbeat
  -> 不 resolve pending tick
  -> 不执行 NPC 行动
```

### 2.3 请求级并发边界

当前不是多线程并发模型。

1. `command.php` 和 `heartbeat.php` 都拿房间级 MySQL `GET_LOCK('game_state_{groomid}')`。
2. Command Bus 内部还拿玩家级 `flock`。
3. `state.php` 纯读，不拿写锁，也不推进世界。

因此问题不应表述为“多个 NPC 事件被多线程同时处理”。真实问题是：同一个 pending tick 被 heartbeat 显式解析时，内部阶段顺序和阶段产物没有形成稳定的框架契约。

## 3. 当前 tick dispatch 阶段顺序

当前 `obl_tick_dispatch()` 固定三阶段：

```text
1. battle_npc
2. idle_npc
3. post
```

### 3.1 battle_npc

`obl_tick_phase_battle_npc()` 行为：

1. 查询所有 active battle queue。
2. 找当前顺位者。
3. 如果当前顺位者是玩家：
   - 不执行 NPC 回合。
   - 若战场状态为 `PROCESSING`，转换为 `PLAYER_TURN`。
   - 不请求 tick++。
4. 如果当前顺位者是 NPC：
   - 构造 NPC 战斗动作。
   - 调 `combat_dispatch('npc_turn')`。
   - `battle_manage_queue()` 推进队列与状态机。
   - 调 `obl_tick_request_advance()`。
   - 本次 dispatch 最多处理 1 个 NPC 战斗回合。

### 3.2 idle_npc

`obl_tick_phase_idle_npc()` 行为：

1. 读取当前玩家所在区域所有敌人。
2. 跳过 `action === 'battle'` 的敌人。
3. 非战斗 NPC 按 `action_chance`、`ai_type` 决定是否移动。
4. 移动通过 `obl_enemy_move()` 直接修改 NPC `pls` 并保存数据库。

注意：idle NPC 只跳过“自己在战斗中”的 NPC，不会因为当前区域存在一个玩家战斗而整体暂停。

### 3.3 post

当前只预留 phase，未发现实际内置 post listener。

## 4. 前端推进链路

当前前端已经明确采用“读前先 heartbeat”契约：

1. `commandQueue.execute()` 执行 `advancesTick=true` 命令成功后，会：
   - `await oblHeartbeat()`
   - `await playerStore.loadPlayerInfo(true)`
   - 广播 `game:tick-advanced`
2. `battleStore.refreshBattle()` 每次开始也会：
   - `await oblHeartbeat()`
   - 拉取 `player_info`
   - 播放 `battle_log`
   - 播完后再 `await oblHeartbeat()` + 拉取 `player_info`
3. `battleStore.startDaemonPoll()` 页面挂载后持续 heartbeat：
   - `PROCESSING` 时 300ms。
   - 其他状态 1000ms。

所以玩家命令后的 pending tick 通常会被前端立即解析，而不是等玩家下一次真实操作。

## 5. 必须修正的误判

### 5.1 “后端并发/多线程跑 NPC”是误判

不是。

请求级有房间锁；tick dispatch 内部是同步顺序执行。

### 5.2 “非战斗 NPC 先于已提交的玩家战斗动作执行”也是误判

从当前主路径看，已提交的玩家命令在 Command API 中先执行，随后才推进 tick，之后 heartbeat 才解析 pending tick。

也就是说：

```text
玩家 battle.submit_turn
  -> combat_dispatch('player_turn') 已执行
  -> tick++
  -> heartbeat resolve
  -> battle_npc
  -> idle_npc
```

因此非战斗 NPC 并不会抢在“已经提交到后端的玩家战斗动作”之前执行。

### 5.3 “战斗 tick / 战斗独占 tick”是错误抽象

游戏刻是唯一时间基准，不能拆出战斗 tick。  
如果因为存在战斗就跳过普通 NPC，会让同一个时间单位内的世界行动被吞掉，制造更大的时间不一致。

正确抽象不是“战斗占用一个 tick”，而是：

```text
同一个 game tick 内，有多个结算域。
结算域需要固定顺序、清晰读写边界、统一提交与同步产物。
```

### 5.4 “只要固定域顺序”也是不完整抽象

本轮复核发现，单纯把 TickFrame 拆成 `combat_domain -> world_ai_domain -> post_domain` 仍然不够。

原因是：

1. tick 是全世界时间推进一次。
2. 一个 tick 内，所有具备行动资格的 actor 都可以执行一个主动行为。
3. 但同一 actor 在同一 tick 内只能执行一次主动行为。
4. 战斗行为和非战斗行为共享同一个 actor 行为额度。
5. actor 执行了战斗行为后，本 tick 不能再执行非战斗行为；反过来也一样。

因此正确标准不是“战斗域执行后是否整体跳过世界域”，而是：

```text
同一 tick 内：
  每个 actor 最多执行一个主动行为；
  该主动行为只能属于 combat 或 world 二者之一；
  域顺序只决定行为选择的优先级，不提供额外行动额度。
```

本轮暴露的典型错误链路：

```text
NPC A 在 combat_domain 执行 escape
  -> escape 清空 action / 退出队列
  -> 同一 TickFrame 继续进入 world_ai_domain
  -> world_ai 重新 fetch 到 A，看到 action=''
  -> A 又执行 idle move
```

这违反的不是“战斗域与世界域排序”，而是“同一 actor 同一 tick 只能执行一个主动行为”。

需要框架化的不是临时跳过某个 phase，而是 TickFrame 级 actor 行为账本。

## 6. 当前真实问题

### 6.1 tick phase 顺序虽然看似正确，但没有被框架化

当前代码已经是 `battle_npc -> idle_npc -> post`，表面上满足“战斗域先于普通 NPC”。

但它仍是硬编码监听器顺序，不是显式的 TickFrame Scheduler：

1. 没有“结算域”的一等概念。
2. 没有每个域的读写契约。
3. 没有每个域的输入快照、输出变更集、提交屏障。
4. 没有统一的 tick frame 产物供前端同步。

所以只看顺序无法解决问题。

### 6.2 玩家战斗动作在 command 请求中即时执行，不属于 tick dispatch 内的显式 domain

玩家战斗动作当前发生在：

```text
command.php -> combat_dispatch('player_turn')
```

NPC 战斗动作当前发生在：

```text
heartbeat.php -> tick dispatch -> battle_npc -> combat_dispatch('npc_turn')
```

两者都消耗 game tick，但分布在不同入口、不同阶段。  
这不是必然错误，但它让“一个 game tick 的结算内容”在结构上被拆散，不利于统一表达：

1. 玩家动作的 tick 产物。
2. 战斗 NPC 产物。
3. 普通 NPC 产物。
4. 最终世界快照。

### 6.3 idle_npc 在战斗状态切到 PLAYER_TURN 后仍会继续执行

当 `battle_npc` 发现当前顺位者是玩家时，会把状态从 `PROCESSING` 转为 `PLAYER_TURN`，然后 `idle_npc` 仍继续执行。

这并不必然违反“同一 tick 内普通 NPC 也要结算”的原则；但它要求前端必须在玩家看到下一轮可操作 UI 前，拿到 idle_npc 结算后的世界状态。

当前前端没有稳定做到这一点：

1. `battle.submit_turn` 的 refresh 契约没有 `game_map`。
2. `battleStore.refreshEnemyLocation()` 只更新 `battleStore.enemyLocation`，不更新 `mapStore.enemies`。
3. `PreloadArea` 默认目标与射程仍读 `currentEnemyPid` / `mapStore.enemies`。
4. 地图实体层仍主要从探索态 `mapStore.enemies` 派生。

因此玩家看到的战斗目标、地图实体、射程预判可能是旧世界状态。

### 6.4 连续战斗 NPC 回合会被拆成多个 pending tick

当前 `battle_npc` 每次 dispatch 最多处理 1 个 NPC 战斗回合。NPC 回合结束后 tick++，下一次 heartbeat 再处理下一个 pending tick。

这符合“单人次回合 = 1 game tick”的设计。  
但需要明确：普通 NPC 行动不是因为连续战斗队列存在就被永久跳过；它应在战斗域之后处理，但只能处理本 tick 尚未执行过战斗行为的 actor。

### 6.5 `delta` 当前没有被各 listener 充分消费

`resolve_pending()` 会传入 `delta = tick - processed_tick`。  
但当前 battle_npc / idle_npc 并没有按 delta 循环处理多帧，只是一次 dispatch：

1. battle_npc 最多处理 1 个 NPC 战斗回合。
2. idle_npc 遍历当前区域一次。

这意味着如果 pending tick 积累超过 1，当前实现不是严格的“补跑 N 个 tick frame”，而是“用一个 delta 参数触发一次三阶段 dispatch”。这不是当前 bug 的直接来源，但属于 tick 框架边界风险。

### 6.6 移动占位冲突的真实结构

战斗移动和普通 NPC 移动都写同一张 `oblplayers` 表的 `pgroup/pls`：

1. 战斗移动：
   - verify / execute 阶段通过 `obl_get_pids_in_tile()` 和 `obl_perform_move_core()` 检查占位。
2. 普通 NPC 移动：
   - `obl_enemy_move()` 通过 `obl_is_tile_occupied_by_others()` 检查占位。

在已提交玩家动作这一侧，普通 NPC 不会先于该动作执行。  
但普通 NPC 可能已经在上一轮 heartbeat 之后移动，而前端仍用旧 `mapStore.enemies` / 旧目标进行预判，导致玩家下一次提交时后端发现目标格已占用。

因此“撞车”不能只理解成后端执行顺序错误，更核心是：

```text
tick frame 结算后的世界状态没有成为前端下一次战斗操作的唯一真值源。
```

## 7. 正确框架抽象

### 7.1 GameTick 是唯一时间单位

禁止新增“战斗 tick”概念。

应使用：

1. `GameTick`：唯一游戏时间单位。
2. `TickFrame`：一次 pending tick 的结算过程。
3. `ActorBehaviorLedger`：TickFrame 内每个 actor 是否已经执行过主动行为的账本。
4. `DomainPhase`：TickFrame 内的结算域。
5. `DomainResult`：某个域产生的变更与事件。

### 7.2 ActorBehaviorLedger 是优先级最高的不变量

TickFrame 级行为账本必须比 domain 顺序更基础。

账本规则：

```text
claim_actor_behavior(pid, domain, behavior):
  如果 pid 本 tick 已执行过任何主动行为，返回 false
  否则记录 pid -> {domain, behavior}，返回 true
```

主动行为包括：

1. 玩家 `map.move` / `map.explore` / `poi.search`。
2. 玩家 `battle.start` / `battle.submit_turn`。
3. NPC 战斗行为：攻击、逃跑、战斗移动、发呆兜底等。
4. NPC 非战斗行为：巡逻、追击、搜寻、普通移动等。
5. 未来如果 post/buff/dot 触发 actor 主动执行动作，也必须先 claim。

不属于主动行为的被动结果：

1. 受伤、治疗、死亡标记。
2. 被发现、迷雾清除、道具发现。
3. 队列清理、战斗解散、AP 恢复。
4. battlelog 记录、changedScopes 记录。

因此：

```text
actor 已执行 combat 行为 -> 本 tick 不得执行 world 行为
actor 已执行 world 行为  -> 本 tick 不得执行 combat 行为
actor 只是被动受击/死亡/被发现 -> 不消耗该 actor 行为额度
```

### 7.3 DomainPhase 是一等概念

当前隐式 phase 应升级为显式结算域：

```text
combat_domain
world_ai_domain
post_domain
```

顺序原则：

```text
每个 GameTick 内：
  1. 先结算 combat_domain
  2. 再结算 world_ai_domain
  3. 最后结算 post_domain
```

这不是因为存在战斗就整体跳过 `world_ai_domain`。
`world_ai_domain` 仍可处理本 tick 尚未执行过战斗行为的普通 NPC。

但 `world_ai_domain` 在任何 actor 行动前都必须先检查 `ActorBehaviorLedger`。如果该 actor 已在 `combat_domain` 执行过战斗行为，则本 tick 必须跳过它。

### 7.4 玩家战斗动作和 NPC 战斗动作同属 combat_domain

战斗域内部顺位仍由先攻队列决定：

1. 玩家先动或 NPC 先动，不由 tick 框架硬编码。
2. `battle_calc_initiative()` / `battle_manage_queue()` 仍是战斗内部顺位权威。
3. TickFrame 只保证战斗域行动先 claim 行为账本，不干预战斗域内部先攻规则。

### 7.5 world_ai_domain 必须基于 combat_domain 提交后的状态和行为账本行动

普通 NPC AI 不应该看到战斗域之前的旧占位。  
它应该在战斗域完成并提交玩家/NPC 战斗移动、死亡、逃跑、队列状态后，再读取地图占位。

但普通 NPC AI 的“是否属于战斗域”不能读取 combat_domain 提交后的实时 `action/bid`。
原因是战斗域可能在同一 TickFrame 内清理 `action/bid`：

```text
TickFrame 入口：NPC A action='battle' / bid=1
  -> combat_domain 中 A 逃跑或战斗解散
  -> action/bid 被清理
  -> world_ai_domain 若重新按实时 action/bid 判断，会把 A 当成普通 NPC
```

这违反“action=battle 的 actor 本 tick 不能执行非战斗域 AI”。

因此 TickFrame 初始化时必须先建立 `BattleActorScope`：

```text
BattleActorScope = 本 TickFrame 入口时 action='battle' 或 bid>0 的 actor 集合
```

需要特别注意玩家命令路径的时序：

```text
玩家提交 battle.submit_turn
  -> command handler 先执行 combat_dispatch
  -> combat cleanup 可能清理 NPC 的 action/bid
  -> 后续 heartbeat/resolve 才进入 TickFrame dispatch
```

所以 `BattleActorScope` 不能只在 `resolve_tick_events()` 中实时查库。
对于会推进 tick 的玩家命令，必须在 command handler 执行前先记录一份“命令前战斗域成员快照”，TickFrame 初始化时再与实时快照合并。
否则战斗命令刚刚清理掉 `action/bid` 的 actor 会在同一 tick 被 `world_ai_domain` 当成普通 NPC。

`world_ai_domain` 必须先检查 `BattleActorScope`。只要 actor 在本 TickFrame 入口属于战斗域，即使 combat_domain 已经把它清成普通状态，本 TickFrame 也不能执行 world AI。

同时，它不能仅凭持久状态字段判断行动资格：

1. `action === 'battle'` 只能说明当前处于战斗状态。
2. `bid > 0` 只能说明仍有关联队列或历史队列。
3. `active=0` 只能说明已退出当前队列。

这些都不能替代 TickFrame 行为账本。

world AI 行动资格应收束为单点判断：

```text
actor_can_world_ai(actor, tick_ctx):
  actor 存活
  actor 不在 TickFrame 入口 BattleActorScope 中
  actor 不处于有效战斗行动状态
  actor 不在 active battle queue 中
  actor 本 tick 尚未执行过任何主动行为
```

### 7.6 TickFrame 必须产出可同步的结果

不一定要新建过重的 Combat Frame。更合适的是 TickFrame Result：

```ts
interface TickFrameResult {
  tick: number;
  processedTick: number;
  phases: DomainPhaseResult[];
  actorBehaviors: ActorBehaviorResult[];
  changedScopes: string[];
  battleContext?: CombatViewModel;
  worldSnapshotVersion: number;
}

interface ActorBehaviorResult {
  pid: number;
  domain: 'combat' | 'world';
  behavior: string;
}
```

其中：

1. `battlelog.v2` 仍负责战斗演出事实。
2. `BattleDirector -> PlaybackPlan` 仍负责前端演出。
3. `CombatViewModel` 负责战斗 UI 真值源。
4. `actorBehaviors` 负责解释本 tick 中哪些 actor 已执行过主动行为。
5. `changedScopes` 告诉前端哪些状态必须刷新，比如 `player_info` / `battle_log` / `enemies` / `game_map`。

### 7.7 战斗状态机与先攻队列必须互相授权

`ActorBehaviorLedger` 解决的是同一 TickFrame 内 actor 行为额度问题。
战斗域还必须额外满足“状态机与先攻队列一致授权”：

```text
NPC 战斗行动：
  battle_state 必须是 PROCESSING
  当前队列 actor 必须是 NPC
  NPC 行动前必须 claim combat 行为

玩家战斗提交：
  battle_state 必须是 PLAYER_TURN
  当前队列 actor 必须是当前玩家
  玩家命令成功后必须登记为本 tick 的 combat 行为

切换到 PLAYER_TURN：
  只能发生在 battle_state=PROCESSING 且当前队列 actor 是玩家时
```

因此 `PLAYER_TURN` 不是“玩家处于战斗中”的同义词，而是“先攻队列当前顺位明确轮到该玩家”的授权状态。
同理，`PROCESSING` 不是“随便让 NPC 行动”的同义词，而是“后端可以推进当前队列 actor”的授权状态。

超时恢复也必须遵守这个规则：

1. stale `PROCESSING` 且当前队列 actor 是玩家：可以转换为 `PLAYER_TURN`。
2. stale `PROCESSING` 且当前队列 actor 是 NPC：不能转换为 `PLAYER_TURN`，应补一个待结算 tick 让后端继续处理 NPC 回合。
3. stale `PROCESSING` 但队列没有当前 actor：不能凭空授权玩家，必须记录诊断并等待队列生命周期清理。

## 8. 建议设计方向

### 8.1 第一阶段：建立 TickFrame ActorBehaviorLedger，不改变游戏时间语义

目标不是重做时间系统，而是在现有 tick dispatch 上补齐同一 actor 单 tick 单主动行为的框架基准：

```php
tick_frame_resolve($delta)
  -> init_actor_behavior_ledger()
  -> combat_domain_resolve()     // actor 行动前 claim combat 行为
  -> world_ai_domain_resolve()   // actor 行动前 claim world 行为
  -> post_domain_resolve()
  -> tick_frame_result
```

当前 `obl_tick_dispatch()` 可以先作为实现载体重构，不必立刻大改业务函数。

关键要求：

1. TickFrame 初始化 `actor_behaviors`。
2. 玩家命令路径执行 `advances_tick=true` 命令时，视为玩家本 tick 已执行主动行为；heartbeat 解析该 pending tick 时，应把当前玩家标记为已行动。
3. 会推进 tick 的玩家命令在 handler 执行前记录命令前 `BattleActorScope`。
4. TickFrame 初始化 `BattleActorScope`，合并命令前快照与当前实时 `action='battle'` / `bid>0` actor。
5. `combat_domain` 中 NPC 回合执行前必须 claim actor；claim 失败则不能执行。
6. `world_ai_domain` 中 NPC idle 行为执行前必须先排除 `BattleActorScope`，再 claim actor；claim 失败则跳过。
7. phase 名称从 `battle_npc / idle_npc` 升级为领域名。
8. 每个 domain 明确：
   - 是否读取玩家快照。
   - 是否读取/写入 `oblplayers.pgroup/pls`。
   - 是否可请求 tick++。
   - 会影响哪些前端 scope。
9. world_ai 不整体跳过，但必须排除本 tick 的战斗域成员和已执行战斗行为的 actor。
10. 战斗域执行 NPC 行动前必须验证 `battle_state=PROCESSING`。
11. 玩家提交战斗回合前必须验证当前队列 actor 就是当前玩家。
12. 超时恢复不能把 NPC 当前顺位的 `PROCESSING` 重置成 `PLAYER_TURN`。

### 8.2 第二阶段：集中 world AI 行动资格判断

当前 `obl_tick_phase_idle_npc()` / `obl_enemy_tick()` 分散判断 `state` 与 `action`，边界过窄。

应新增单点规则：

```php
obl_actor_can_world_ai($actor, $ctx)
```

它至少判断：

1. actor 存活。
2. actor 不处于 battle action 状态。
3. actor 不在 active battle queue 中。
4. actor 本 tick 未执行任何主动行为。

这样逃跑、死亡清理、战斗解散后，NPC 不会因为 `action` 被清空就在同一 tick 再执行 world AI。

### 8.3 第三阶段：让 heartbeat 返回 changedScopes / frame 状态

当前 heartbeat 返回 tick 状态与 changedScopes，但 frame 行为结果还不完整。

应让 TickFrameResult 至少表达：

1. 哪些 actor 在本 tick 执行过 combat 行为。
2. 哪些 actor 在本 tick 执行过 world 行为。
3. 是否有 NPC 移动。
4. 是否有 battle state 从 `PROCESSING` 变成 `PLAYER_TURN`。
5. 前端应刷新哪些 scope。

这样 `commandQueue` / `battleStore.refreshBattle()` 不需要凭经验决定刷新 `enemies` 还是 `game_map`。

### 8.4 第四阶段：Combat ViewModel 成为战斗 UI 真值源

沿用 `战斗上下文视图与动作链失败策略设计案.md` 的结论。

Combat ViewModel 解决的是前端战斗视图问题，而不是 tick 顺序问题：

1. 当前战场 qid / state / round / turn。
2. 当前 actor / next actor。
3. 所有 combatants 当前 `pgroup/pls/hp/ap/state/active`。
4. 玩家可选目标、默认目标。
5. 当前是否允许提交 `battle.submit_turn`。
6. 当前按钮“取消”只能取消本地瞄准，不能伪退出战斗。

### 8.5 第五阶段：统一移动意图/占位决议

长期应把三类移动收束到统一移动 resolver：

1. 玩家探索移动。
2. 战斗移动。
3. 普通 NPC 移动。

目标是统一：

1. 占位检查。
2. passable / distance / region 边界。
3. 失败原因。
4. 变更记录。
5. 对前端 scope 的影响。

这不是为了解决“多线程抢格”，而是为了避免三个系统各查各的数据库、各自写位置、各自产生日志和刷新契约。

## 9. 边界情况

### 9.1 当前已提交玩家动作不会被 idle_npc 抢先

这是已确认事实。不要再把问题描述为“idle_npc 先于已提交玩家战斗动作”。

### 9.2 玩家下一轮 UI 可能基于旧世界状态

这是当前真实风险。原因是 heartbeat 可能已经结算 world_ai，但前端战斗 UI 仍混用旧 `mapStore.enemies` 和本地 `currentEnemyPid`。

### 9.3 `battle.submit_turn` refresh 缺少 `game_map`

当前后端 contract：

```php
'battle.submit_turn' => [
  'refresh' => ['player_info', 'battle_log', 'enemies'],
]
```

如果 world_ai 在同一 tick 内移动，并且地图实体依赖 `mapStore.enemies` / `game_map`，前端可能缺少完整刷新。

更好的方式不是简单把所有命令都加 `game_map`，而是由 TickFrameResult/changedScopes 决定。

### 9.4 state.php 不会自动修复 pending tick

任何只读状态都可能读到 `processed_tick < tick` 的窗口。  
这是设计选择，不是 bug。调用方需要先 heartbeat。

### 9.5 旧 `oblivions/include/core/obl_command.php` 是历史兼容路径

旧路径也有 tick 推进逻辑，但当前前端主路径是 `oblivions/api/command.php`。设计与后续实现应以新 API 为准，不应把旧路径作为当前事实混入。

### 9.6 战斗结束后的下一 tick 普通 NPC 行动是预期行为

本轮插桩复核确认：

```text
tick N:
  battle_scope 包含战斗成员
  NPC A 执行 escape
  同一 TickFrame 的 world_ai_domain 因 battle_scope 跳过 A

tick N+1:
  若战斗仍未结束，battle_scope 继续包含剩余战斗成员
  已逃跑但队列/战斗尚未完全清理的 actor 仍会被 battle_scope 或 bid 阻断

tick N+k:
  最后一个 NPC 回合执行 escape
  战斗队列 disband / battle_end
  该 TickFrame 内原战斗成员仍因 battle_scope 被 world_ai_domain 跳过
  NPC 回合结束后按当前系统语义请求推进 1 tick

tick N+k+1:
  battle_scope 已为空
  原战斗成员 action='' / bid=0
  这些 actor 恢复普通 NPC 身份，可参与 world_ai_domain
```

因此，“NPC 逃跑并结束战斗后，在后续下一个 tick 移动一格”不是同 tick 双行动 bug，而是当前 tick 自驱动模型下的预期行为。

判定标准：

1. 如果 actor 在同一 TickFrame 的 `battle_scope` 中，却出现 `world` 行为或 `WORLD_AI_MOVE_SUCCESS`，这是 bug。
2. 如果 actor 在战斗完全结束后的后续 TickFrame 中，`battle_scope=[]` 且 `action='' / bid=0`，world AI 放行移动是当前预期。
3. 如未来业务希望“刚退出战斗的 actor 冷却 1 tick 后才能行动”，应新增 `PostBattleCooldownScope` 或“退出战斗延迟行动”规则，而不是回退为按实时 `action/bid` 打补丁。

## 10. 结论

当前问题不应再抽象为“战斗 tick 独占”或“跳过普通 NPC”。  
正确结论是：

```text
游戏刻只有一个。
战斗与普通 NPC 都是同一个 GameTick 内的结算域。
一个 tick 内所有具备资格的 actor 都可以执行一个主动行为。
但同一 actor 在同一 tick 内只能执行一个主动行为。
战斗行为和非战斗行为共享同一 actor 行为额度。

框架需要显式化 TickFrame / ActorBehaviorLedger / DomainPhase / DomainResult：
  actor 行动前必须 claim 本 tick 行为账本；
  combat_domain 先结算；
  world_ai_domain 后结算；
  post_domain 最后结算；
  world_ai_domain 只能处理本 tick 未执行过战斗行为的 actor；
  每个 domain 产出 changedScopes；
  前端用 Combat ViewModel 和 TickFrameResult 获取结算后的唯一真值源。
```

进一步确认：

```text
战斗结束后的下一 tick 不是“同一 tick 的延续”。
只要 battle_scope 已为空，原战斗 actor 恢复普通 NPC 身份后执行 world AI，是当前系统预期行为。
```

从当前代码看，后端顺序并没有完全反转；真正缺失的是：

1. TickFrame 没有 actor 行为账本。
2. 结算域不是一等概念。
3. `action` / `bid` / queue active 被误用为行动互斥依据，但它们都是持久状态，不是本 tick 行为账本。
4. 玩家命令和 heartbeat 分属不同入口，tick frame 产物不可见。
5. idle_npc 结算后的世界状态没有稳定同步到战斗 UI。
6. 战斗 UI 仍依赖探索态地图数据和单一 `currentEnemyPid`。
7. 移动占位由多个系统各自实时查库，缺少统一移动 resolver。

因此后续推进顺序建议：

1. 先补 TickFrame ActorBehaviorLedger，并接入 combat_domain / world_ai_domain。
2. 同步补齐状态机/先攻队列授权：NPC 行动只在 `PROCESSING`，玩家提交只在 `PLAYER_TURN + 当前 actor=玩家`。
3. 再集中 world AI 行动资格判断，禁止用零散 `action` 判断替代框架规则。
4. 再让 heartbeat 返回更完整的 TickFrameResult / changedScopes。
5. 再落地 Combat ViewModel，前端战斗 UI 从它派生目标、射程、实体位置和按钮语义。
6. 最后统一移动 resolver，收束玩家移动、战斗移动、普通 NPC 移动的占位与失败语义。
