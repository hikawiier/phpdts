> 关联框架：L-9 POI 交互模态框、E-10 POI 搜刮三档判定系统、F-4 战利品表引擎、A-3 状态查询范围分发

> 关联前序设计：oblivions/docs/POI产出预览-设计案-2026-07-19.md（旧设计，已被本案取代）

## 一、研判：旧设计问题

### 1.1 旧设计回顾

前序设计案（POI产出预览-设计案-2026-07-19.md）投影完整 F-4 战利品表结构：

- 后端返回：`{table_name, groups[]:[{chance, entries[]:[{item_id, probability, count_min, count_max}]}]}`
- 前端展示：按"第 N 组 + 组级 chance + 条目列表（物品名 + 组内概率 + 数量范围）"展开

### 1.2 旧设计暴露的问题

| 维度 | 问题 | 违反原则 |
|------|------|---------|
| **信息密度过高** | 玩家需理解"组级 chance → 组内 weight 归一化 → 互斥选一"的掷骰语义，才能正确解读概率 | DESIGN.md §3.1 降低理解成本 |
| **引擎内部结构外泄** | groups/entries/probability/count_min/count_max 是 F-4 引擎实现细节，不应作为玩家可见字段 | 概念引入成本-收益失衡 |
| **决策辅助失效** | 玩家真正需要的是"这个 POI 值不值得搜"（分级判断），而非"每个物品的具体概率是多少"（精确数值） | 偏离原始方案 §4.2 的"列表"语义 |
| **视觉拥挤** | 每组都要展示组级 chance 标签 + 多行条目，与三档概率条争抢注意力 | DESIGN.md §3.4 注意力稀缺 |
| **未折叠默认展开** | 玩家不主动询问时也抢占注意力，违反"不展示什么"原则 | DESIGN.md §3.4 第一要务 |

### 1.3 重构动机

按 DESIGN.md §3.4「少即是多」原则：**第一要务不是"展示什么"，而是"不展示什么"**。

- 玩家决策辅助只需 3 档分级（绝对/大概率/也许），无需精确概率值
- 默认折叠进一步降低注意力占用，玩家需要时主动展开
- 三句话分级比 N 组 × M 条目更符合"留白为想象力腾出空间"

## 三、设计决策

### 3.1 概率分档阈值（硬编码，不引入配置）

| 档 | 标签 | 阈值 | 视觉强调 |
|----|------|------|---------|
| certain | 绝对会有 | p >= 0.95 | `.yellow`（最确定） |
| likely | 大概率会有 | 0.5 <= p < 0.95 | 默认色 |
| maybe | 也许会有 | 0 < p < 0.5 | `.dim`（最不确定） |

**阈值选择理由**（按"避免过度配置"原则硬编码，不新增配置开关）：
- `0.95` ≈ "几乎每次都出"，对应原始方案中"必出组"的直觉边界（chance=1.0 + 单一 entry weight=100% 时 p=1.0 入 certain）
- `0.5` = "过半概率"，是直觉性的"大概率"分界
- `0 < p < 0.5`：稀有掉落，"也许会有"贴切

### 3.2 物品整体出现概率计算公式

每个 entry 的整体出现概率 = `group_chance × entry_probability`

- `entry_probability = weight / Σweight`（与 F-4 引擎 `obl_weighted_pick` 一致）
- weight 全 0 时按均匀分布 `1/count(entries)`（与 `obl_weighted_pick` 兜底一致）

**多组同 item_id 去重**：使用独立事件联合概率 `1 - ∏(1 - p_i)`，p_i 为该物品在各组中的出现概率。

- **假设各组掷骰独立**：与 F-4 引擎语义一致（每组独立掷骰）
- **同组内 entries 互斥**（按 weight 选一），无需联合概率（一个物品在同一组内只贡献一次概率）

### 3.3 后端返回结构

```php
[
    'table_name' => string,           // 索引锚点（调试用）
    'certain'    => ['item_id1', ...], // 已按 p 降序
    'likely'     => ['item_id3', ...],
    'maybe'      => ['item_id5', ...],
]
```

- 各档内 `item_id` 已按整体出现概率降序排序
- 三档全为空时返回 `null`（前端隐藏整个区域）
- `table_name` 保留作为调试索引锚点

### 3.4 前端 UI 设计

**默认折叠**：`lootPreviewExpanded = ref(false)`，默认不显示产出内容。

**切换按钮**（小尺寸灰阶 `term-btn` 风格）：
- 折叠态：`▼ 可能的产出`
- 展开态：`▲ 收起产出`

**展开态三句话分级文案**（按 certain → likely → maybe 顺序分行）：
```
绝对会有：废铁片、生锈齿轮……      ← yellow
大概率会有：AA电池、油布……        ← 默认色
也许会有：电子元件。               ← dim
```

**空档处理**：
- 某档为空（如 `maybe=[]`）则不显示该行（`v-if="lootPreviewText.certain"` 等条件渲染）
- 三档全为空 → 后端返回 `null` → `showLootPreview=false` → 整个区域（含切换按钮）隐藏

**hasLootOverride 提示**：保留"（选择工具可改良掉落表）"提示，**仅展开态显示**，附在三句话之后。

### 3.5 边界处理

| 边界场景 | 后端行为 | 前端行为 |
|---------|---------|---------|
| `searchable=false` | 返回 `null` | 隐藏整个区域 |
| `state='exhausted'` | 返回 `null` | 隐藏整个区域 |
| `loot_table_id` 缺失 | 返回 `null` | 隐藏整个区域 |
| 表不存在 | 返回 `null`（emit error 日志） | 隐藏整个区域 |
| `groups` 为空 | 返回 `null` | 隐藏整个区域 |
| 所有 `group_chance=0` | 所有 entry p=0 → 三档全空 → 返回 `null` | 隐藏整个区域 |
| 某档为空 | 返回空数组 `[]` | 不显示该行 |
| 三档全为空 | 返回 `null` | 隐藏整个区域 |
| 多组同 item_id | 联合概率 `1 - ∏(1-p_i)` | — |
| weight 全 0 的组 | 按均匀分布 `1/count` 计算 entry_probability | — |
| 冷却中（state='cooldown'） | 仍返回预览（决策辅助价值） | 折叠态展示，玩家可主动展开 |

## 四、设计自校准

### 4.1 错误检查

- ✓ `PoiLootPreview` 类型与后端返回字段一一对齐（`table_name` / `certain` / `likely` / `maybe`）
- ✓ 概率分档边界连续无遗漏：`p >= 0.95` 入 certain；`0.5 <= p < 0.95` 入 likely；`0 < p < 0.5` 入 maybe；`p <= 0` 不入档（防御性兜底）
- ✓ 联合概率公式数学正确：独立事件联合 `P(A∪B) = 1 - (1-P(A))(1-P(B))`，推广到 N 个独立事件为 `1 - ∏(1-p_i)`
- ✓ 同组内 entries 互斥语义正确：F-4 引擎按 weight 选一，一个物品在同一组内只贡献一次概率（不重复入 `item_prob_map[$item_id]`）

### 4.2 遗漏检查

- ✓ 同组同物品多次出现：F-4 配置中同组 entries 互斥，不会同组重复（若配置层异常重复，前端展示也只是把同一物品名重复列出，不影响概率计算正确性）
- ✓ 多组同物品：联合概率 `1 - ∏(1-p_i)` 处理
- ✓ 三档全空场景：后端返回 `null`，前端隐藏
- ✓ 某档为空：前端按 `v-if` 跳过该行
- ✓ 冷却中：保留预览（玩家可规划是否值得等冷却到期）
- ✓ 已搜空：隐藏预览（避免误导，引导玩家看 `items[]`）
- ✓ 机制型 POI：`searchable=true` 但走 `obl_execute_mechanic` 分发，`loot_table_id='empty_loot'`，后端检测到空 groups 返回 `null`
- ✓ F-6 交互型 POI：`searchable=false`，后端直接返回 `null`
- ✓ 地标型 POI：`searchable=false`，后端返回 `null`

### 4.3 冲突检查

- ✓ 与 F-6 道具交互区视觉分离：产出预览在中上部交互区（`poi-interaction-zone`），道具操作在中下部（`poi-interact-zone`），由布局天然分隔
- ✓ 与右列"可用工具"语义互补：右列是"玩家有什么"，产出预览是"POI 能出什么"
- ✓ 与 `items[]`（已物化道具列表）语义分离：前者是"可能"，后者是"已搜出"
- ✓ 与三档概率条视觉协调：折叠态不与概率条争抢注意力；展开态三句话用 yellow/默认/dim 三档颜色，与概率条颜色无冲突

### 4.4 冗余检查

- ✓ 删除 `PoiLootPreviewEntry` / `PoiLootPreviewGroup` 类型（不再需要）
- ✓ 删除 `formatGroupChance` / `formatCountRange` 前端函数（不再需要）
- ✓ 删除 `obl_project_loot_group_for_preview` / `obl_normalize_count_range` 后端函数（不再需要）
- ✓ 不重复投影 `count_min/count_max`（玩家决策不需要精确数量，仅需"是否会有"）
- ✓ 不重复投影 `group_chance`（玩家决策不需要组级掷骰概率，仅需物品级整体出现概率）

## 五、设计哲学对齐（DESIGN.md §3）

### 5.1 §3.4 少即是多——注意力稀缺与想象力核心

- **注意力稀缺作为设计元前提**：默认折叠 = "不展示什么"原则的极致体现，玩家不主动询问时不抢占注意力
- **弱项认知决定精简必然性**：三句话比 N 行条目列表更精简，避免暴露概率计算细节
- **协调性即节省注意力**：三档颜色（yellow / 默认 / dim）与现有调色板一致，无新增颜色，视觉语言统一
- **想象力核心**：三句话留白更多想象空间，玩家无需在多个概率数字间做心算

### 5.2 §3.1 降低理解成本

- 玩家无需理解"组级 chance → 组内 weight 归一化 → 互斥选一"的掷骰语义
- 三句话直白表达"绝对/大概率/也许"三档确定性，自然语言无歧义

### 5.3 §3.2 概念引入成本-收益

- 不引入新概念，复用"绝对/大概率/也许"自然语言
- 后端复杂度略增（联合概率计算），但前端复杂度大降（删除 2 类型、2 函数、3 层嵌套结构）

1. L-9 框架语义未变——仍是中部反馈区"可能搜刮出的道具列表"子功能，只是展示形态从详细列表简化为三档分级

4. 前端组件 `PoiInteraction.vue` 仍归属 L-9 框架，`@framework` 标签不变
5. 按 Dian.md 写入约束"普通模块文件同步 `@module`；直接实现框架的核心文件同时同步 `@framework` 与 Dian.md 代码锚点"——本次修改未改变框架归属，无需同步
