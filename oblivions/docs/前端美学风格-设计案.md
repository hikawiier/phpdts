# Oblivions 前端美学风格 — 设计案

> 定下 Oblivions 前端的视觉基调，作为后续所有前端内容（合成 UI、对话框、教程流程、Boss 战演出、支线区域）的风格锚点。
>
> 覆盖范围：纹理系统、天穹层、立绘切换、场景过渡、信号色策略、角色辨识度。
>
> 不覆盖范围：具体动画时序参数（属 actorAnimations.ts 范畴）、具体组件布局（属各组件设计案）。
>
> **与现有文档的关系**：
> - 扩展 [BATTLE_ANIMATION_FUTURE_DESIGN.md §8](../../vex-vue/docs/BATTLE_ANIMATION_FUTURE_DESIGN.md) 的"立绘弹出"原则到天穹层、场景过渡、环境纹理
> - 遵循 [MAP_LAYER_SYSTEM.md](../../vex-vue/docs/归档/MAP_LAYER_SYSTEM.md) 的 z-index 层级表
> - 遵循 [MOVE_ANIMATION_TIERS.md](../../vex-vue/docs/归档/MOVE_ANIMATION_TIERS.md) 的 arriveAnim 区域切换动画

## 一、美学基调定调

### 1.1 核心定位

**剪纸舞台 + ASCII 终端 + 黑白漫画** 三层叠加：

| 层 | 视觉语言 | 承载内容 | 现有实现 |
|----|---------|---------|---------|
| 剪纸舞台 | PNG 立绘 + GSAP 弧线运动 + 分层遮挡 | 角色、天体、关键叙事物件、立绘化反馈 | actorAnimations.ts + useMapEntities.ts |
| ASCII 终端 | 等宽字体 + 灰阶色块 + 边框 | UI 面板、日志、状态条 | terminal.css + input.css |
| 黑白漫画 | 网点纹理 + 交叉影线 + 形状编码 | 地板属性、环境氛围 | **待实现**（本设计案 §二） |

**三者统一于"黑白单色 + 形状优先 + 立绘弹出"**：不依赖色彩区分信息，靠形状、纹理密度、位置、立绘图层序列传达语义。

### 1.2 立绘弹出作为唯一视觉反馈机制

> 本节扩展 [BATTLE_ANIMATION_FUTURE_DESIGN.md §7-§8](../../vex-vue/docs/BATTLE_ANIMATION_FUTURE_DESIGN.md) 已确立的原则。

**核心约束**（已落地，本设计案继承并强化）：
- 禁用 Unicode emoji（OS 着色，颜色不可控）
- 禁用彩色粒子 / 彩色光点 / 彩色震波
- 禁用屏幕闪白 / 屏幕变色 / 全屏 contrast 瞬时提升 / 全屏 overlay 闪现
- 禁用残影（半透明 clone）
- **禁用帧动画 sprite 序列**（所有瞬时反馈必须是单张立绘的 popUp，不做 2-3 帧的序列播放）
- **禁用 CRT 扫描线**（已移除，避免光敏性癫痫；terminal.css 注释已确认净效果为负）

**唯一机制**：所有"特效"和"反馈"都通过**黑白图片素材 + popUp 动画**实现。按素材尺度分两层：

| 层 | 用途 | 资源目录 | 现有状态 |
|----|------|---------|---------|
| 小型图标立绘 | 情绪/意图/瞬时反馈（风纹/加号/光芒/冲击） | `vex-vue/src/assets/illustrations/icons/` | 规划中（BATTLE_ANIMATION_FUTURE_DESIGN §7） |
| 大型场景立绘 | 环境/技能/叙事时刻（土地裂纹/冲击爆发/天穹碎裂） | `vex-vue/src/assets/illustrations/scenes/` | 规划中（BATTLE_ANIMATION_FUTURE_DESIGN §8） |

**关键原则**：所谓"冲击"、"暴击"、"枪口火焰"等，本质都是**一张图标立绘的 popUp**——不做帧序列、不做全屏闪、不做 overlay 扩散。立绘素材本身的美术承担视觉表达，popUp 动画承担时序反馈。

**本设计案的扩展**：天穹层（§三）和场景过渡（§五）也纳入"立绘弹出"语言——太阳/月亮是天穹层的剪纸立绘，场景过渡是全屏立绘图层的推拉/淡入，天穹消解是天穹立绘的碎裂淡出。

### 1.3 与第一幕叙事的契合

第一幕核心是"信息差驱动叙事"——玩家不知道垃圾岛是飞船。美学基调应配合这个反转：

- **日常期**（庇护所、沙盒探索）：剪纸舞台感强，天穹正常循环，纹理细腻温和
- **异常期**（蟑螂、爱丽丝、千年虫）：纹理变粗、glitch 抖动加剧（频率 ≤ 3Hz）、天穹出现微妙摇摆
- **揭星期**（尾声）：天穹消解，剪纸层剥落，露出 ASCII/矢量感的宇宙天幕

天穹层不是纯装饰，是叙事载体——它的"正常"本身就是最大的误导。

### 1.4 可访问性底线

- 所有动画提供 `prefers-reduced-motion` 兜底（关闭循环、缩短过渡）
- **所有循环/闪烁动画频率 ≤ 3Hz**（光敏性癫痫防护，已写入 project_memory）
- 信息不得仅靠颜色传达（形状/纹理/位置必须冗余编码）

## 二、纹理系统规范

### 2.1 技术选型

**主用：CSS 渐变纹理**（`repeating-linear-gradient` / `repeating-radial-gradient` 多层叠加）

理由：
- 零 HTTP 请求，与现有纯 CSS 风格一致
- 可与 `@theme` 灰阶变量直接绑定
- 性能优于 SVG data URI（GPU 加速渲染）
- 可通过 CSS 变量动态调整密度/角度

**辅助：SVG data URI**（仅用于复杂图案如齿轮、电路板）

**禁用**：位图纹理（PNG/JPG 平铺）——与 ASCII 终端风格冲突，且增加资源管理成本。

### 2.2 与现有 .map-background 的关系

现有 `.map-background`（terminal.css L159-165）是纯黑底（`background: #000`），`z-index: 0`，覆盖整个 `#mapGrid`。

**纹理作用对象**：`.map-cell`（`z-index: 1`），不是 `.map-background`。

**理由**：
- `.map-background` 是全局底色，未来可能替换为背景图层（代码注释已预留）
- 地板属性是 per-cell 的语义编码，应作用于 cell 本身
- 纹理通过 cell 的 `background` 实现，叠加在 `.map-background` 黑底之上

### 2.3 地板属性 → 纹理映射表

每个 `floor` 值对应一种纹理编码，应用于 `.map-cell.floor-{value}`：

| floor 值 | 纹理类型 | 实现 | 视觉特征 |
|---------|---------|------|---------|
| `standard` | 无纹理 | 纯黑底 + 细灰边框（现状） | 默认状态，最干净 |
| `water` | 横向波纹 | 双层 `repeating-linear-gradient(0deg)` 不同相位 | 模拟水面涟漪，低对比度 |
| `vegetation` | 点画 | `radial-gradient(circle, #444 0.5px, transparent 1px)` + `background-size: 8px 8px` | 模拟植被颗粒感 |
| `metal` | 细网格（已有边框高亮，扩展为纹理） | 双 `repeating-linear-gradient(0deg, 90deg)` 1px 线 | 机械感、规整 |
| `magic` | 同心圆 | `repeating-radial-gradient(circle at center)` | 富魔力地板，神秘感 |

**纹理透明度**：所有纹理通过 `rgba(255,255,255,0.04~0.08)` 实现，仅作为"地板质感的暗示"，不抢夺 cell 内容的视觉焦点。

**现有 `floor-metal` 处理**：terminal.css L289-291 已有 `border-color: rgba(136,136,136,0.4)`，保留边框高亮，叠加细网格纹理。

### 2.4 潮汐属性 → 纹理密度叠加

潮汐不替换纹理，而是**在地板纹理上叠加密度修正**：

| tide 值 | 叠加效果 | 实现 | 现状 |
|--------|---------|------|------|
| `shallow` | 无叠加 | 保持原纹理 | — |
| `deep` | glitch 抖动 | `animation: glitch 1.5s ease-in-out infinite` | **已实现**（terminal.css L285-287） |
| `abyss` | 纹理对比度增强 + 偶发性 scale 抖动 | `filter: contrast(1.3)` + 周期性 `transform: scale(1.005)` 抖动（频率 ≤ 0.5Hz） | 待实现 |

**说明**：原 v0.2 方案的"间歇性扫描线"已删除——扫描线属 CRT 效果，已在 terminal.css 中移除（避免光敏性癫痫，且净效果为负）。abyss 潮汐的"危险感"通过纹理对比度 + 低频微抖动表达，不依赖扫描线。

### 2.5 实现位置

新增 `vex-vue/src/assets/styles/textures.css`，按 `@layer` 组织：

```css
@layer textures {
  /* 地板纹理 */
  .map-cell.floor-water { ... }
  .map-cell.floor-vegetation { ... }
  .map-cell.floor-metal { 
    /* 保留现有 border-color，叠加网格 */
    border-color: rgba(136,136,136,0.4);
    background-image: 
      repeating-linear-gradient(0deg, rgba(255,255,255,0.04) 0 1px, transparent 1px 8px),
      repeating-linear-gradient(90deg, rgba(255,255,255,0.04) 0 1px, transparent 1px 8px);
  }
  .map-cell.floor-magic { ... }
  
  /* 潮汐叠加 */
  .map-cell.tide-abyss { ... }
}
```

在 `main.ts` 中 `@import` 顺序晚于 `terminal.css`，确保覆盖优先级正确。

### 2.6 半调网点（Halftone）作为立绘素材纹理

半调网点**不作为运行时全屏 overlay 闪现**（违反"禁用屏幕闪"原则），而是作为**特定立绘素材的美术风格**，在资源制作阶段烘焙到 PNG 中：

| 用途 | 立绘素材 | 机制 |
|------|---------|------|
| 战斗受击反馈 | `icons/hit-impact.png`（网点纹理美术） | 小型图标立绘 popUp（§4.3） |
| 暴击强调 | `icons/critical-impact.png`（网点密度更高） | 小型图标立绘 popUp，scale 更大、时长更长 |
| BOSS 登场过场 | `scenes/boss-emerge-crack.png`（网点渐变模拟"土地裂开"） | 大型场景立绘 popUp（先弹出裂纹立绘，再弹出 BOSS 立绘，符合 project_memory 的"标靶弹出立绘"模式） |

**关键约束**：网点纹理是**立绘素材的美术风格**，不是运行时叠加的 CSS overlay。所有"网点扩散"效果必须在美术资源阶段烘焙到 PNG 里，运行时只做 popUp。

## 三、天穹层架构

### 3.1 与 MAP_LAYER_SYSTEM 的关系

> 参考 [MAP_LAYER_SYSTEM.md](../../vex-vue/docs/归档/MAP_LAYER_SYSTEM.md) 的 z-index 层级表。

MAP_LAYER_SYSTEM 定义的 z-index 层级表（`--z-ground-bg:0` / `--z-cell:1` / `--z-cell-current:2` / `--z-ground-deco:3` / Y 排序层 1000+ / `--z-air-occluder:2000` / `--z-overlay-ui:3000`）全部在 `#mapGrid` 的 `isolation: isolate` 层叠上下文内。

**天穹层不在 `#mapGrid` 内**，是其兄弟层，不受这个层级表约束：

```
<div id="app">
  <div class="sky-layer">          ← 新增：天穹层（#mapGrid 之外）
    <div class="sky-sun"></div>    ← 太阳立绘
    <div class="sky-moon"></div>   ← 月亮立绘
    <div class="sky-stars"></div>  ← 星空（夜间）
  </div>
  <div class="main">
    <div class="left-panel">
      <div class="map-container">
        <div id="mapGrid">          ← 现有地图（isolation: isolate）
          <div class="map-background"></div>
          <div class="map-cell">...</div>
          <div class="entity">...</div>
        </div>
      </div>
    </div>
    <div class="right-panel">...</div>
  </div>
</div>
```

**z-index**：天穹层 `z-index: 0`（与 `#mapGrid` 同级，但在 DOM 顺序上靠前，被 `#mapGrid` 的不透明背景遮挡）。天穹层只在 `#mapGrid` 之外的区域可见（地图面板的留白边缘，或通过 `#mapGrid` 的透明区域透出）。

**替代方案（推荐）**：天穹层作为 `body` 的伪元素或独立 fixed 层，覆盖全屏，`z-index: -1`（在所有内容之下，透过 `#mapGrid` 的黑底不可见，只在 UI 面板的留白处可见）。这样天穹层是"舞台背景"，不干扰地图交互。

**pointer-events: none**——天穹层不响应交互。

### 3.2 太阳/月亮循环动画

**美术资源**：剪纸风格 PNG 立绘，与角色立绘同套美术语言，存放于 `vex-vue/src/assets/illustrations/sky/`。

- 太阳：圆形 + 放射状光芒（剪影）
- 月亮：弯月形（剪影），可带细小陨石坑纹理

**运动路径**：GSAP `MotionPathPlugin` 沿 SVG 弧线路径移动。

```
路径：M -10% 80% Q 50% -20% 110% 80%
       左下升起 → 顶部弧顶 → 右下落下
```

**周期**：与游戏 tick 解耦，前端独立定时器。建议单周期 6 分钟（一次完整日升日落），避免过快干扰沉浸感。

**透明度**：日出/日落时段 opacity 0→1 渐变；正午/午夜 opacity 1。

### 3.3 昼夜判定与背景渐变

天穹层不改变颜色（保持黑白），但通过**整体明度**暗示昼夜：

- 白天：天穹层底色 `#0a0a0a`（与 body 一致）
- 夜间：天穹层底色 `#000`（纯黑）+ 星空点阵显现

星空实现：`radial-gradient` 多点白点 + 间歇性 `opacity` 闪烁（频率 ≤ 3Hz）。

### 3.4 尾声消解效果（第一幕结束）

第一幕尾声"天穹完全消失，镜头上摇显露飞船轮廓"是关键叙事时刻，天穹层必须支持消解：

**消解序列**（总时长建议 4-6 秒）：
1. 太阳/月亮运动骤停，opacity 渐降到 0
2. 天穹层立绘整体出现裂纹（叠加 `scenes/sky-crack.png` 裂纹立绘，popUp 出现）
3. 裂纹立绘扩大，天穹碎裂为多块，各块向四周飘散（GSAP `transform` + `opacity`，本质是天穹立绘的图层动画）
4. 底层露出纯黑背景 + 星空（真实宇宙）
5. 镜头上摇：通过 `useMapInteraction` 暴露的受控平移 API 触发，**不直接操作 `#mapGrid` 的 transform**（避免与现有缩放/平移系统冲突）

**镜头上摇的实现选择**（demo 需验证）：
- **方案 a**：扩展 `useMapInteraction` 暴露 `panTo(yOffset)` API，复用现有平移逻辑
- **方案 b（推荐）**：在 `#mapGrid` 外层新增 `<div class="scene-transform-wrapper">`，尾声序列时对其 `transform: translateY()`，不影响内部地图状态——隔离风险，不污染现有地图交互系统

**预留接口**：天穹层暴露 `dissolveSky()` 方法供尾声调用，封装整个消解序列。

**技术实现**：消解序列本质是"大型场景立绘的图层动画"——天穹本身就是一个覆盖全屏的大型立绘，消解就是它的 popUp 反向操作（碎裂 + 淡出）。复用 GSAP timeline + `MotionPathPlugin`。

### 3.5 可访问性

`prefers-reduced-motion: reduce` 时：
- 关闭太阳/月亮循环运动（固定在正午位置）
- 关闭尾声消解动画（直接切换到宇宙背景）
- 关闭星空闪烁

## 四、立绘切换规范（替代信号色）

### 4.1 设计原则

**不引入信号色**。关键叙事状态通过**立绘切换 + 图标立绘 popUp**表达，与现有 PNG 立绘系统完全统一。

> 本节扩展 [BATTLE_ANIMATION_FUTURE_DESIGN.md §7-§8](../../vex-vue/docs/BATTLE_ANIMATION_FUTURE_DESIGN.md) 的立绘弹出机制到"状态立绘切换"领域。

### 4.2 状态立绘分类

每个关键 NPC/BOSS 准备多套立绘：

| 立绘类型 | 用途 | 示例 | 切换机制 |
|---------|------|------|---------|
| 默认态 | 日常/非战斗 | 爱丽丝静立 | 当前 `entity.img` |
| 行动态 | 战斗/特殊动作 | 爱丽丝持枪 | 切换 `entity.img` 或叠加图层 |
| 受击态 | 受击瞬间（可选） | 爱丽丝后仰 | 复用 hitAnim（已有） |
| 倒地态 | 战败/剧情 | 爱丽丝趴地 | 复用 playFall/playFadeOut（已有） |

**切换时机**：由 `actorsStore` 的 `intent` 驱动，与现有 `onAttack` / `onHit` 机制同构。

**实现方式**：
- **方案 A（图片切换）**：`entity.img` 动态绑定，intent 变化时切换图片 URL
- **方案 B（图层叠加，推荐）**：默认立绘 + 行动态立绘叠加显示，通过 GSAP alpha 控制可见性

**方案 B 的 alpha 控制与"禁用残影"的关系**（重要区分）：
- **图层叠加（允许）**：两个**不同**立绘（默认态 + 行动态）同时存在于 DOM，通过 alpha 在两者间切换，任一时刻主要可见的是一个立绘——本质是"状态切换"
- **残影（禁止）**：同一立绘的半透明 clone 叠加在原立绘上，制造"运动模糊"或"视觉残留"效果——本质是"特效"

方案 B 符合 project_memory 已确立的原则："Avatar visibility during animations is controlled by alpha (0=invisible, 1=visible) instead of z-index switching"。

方案 B 优势：
- 不需要预加载切换后的图片（叠加图层预加载）
- 切换瞬时完成（alpha 渐变可选）
- 与"立绘弹出"机制完全统一——行动态立绘本身就是叠加图层

### 4.3 瞬时反馈的立绘化

枪口火焰、刀光、受击冲击等**瞬时反馈**统一为**单张图标立绘的 popUp**：

| 反馈类型 | 立绘资源 | 机制 |
|---------|---------|------|
| 枪口火焰 | `icons/muzzle-flash.png` | 行动态立绘叠加图层的 popUp（与行动态立绘同步触发） |
| 刀光 | `icons/blade-flash.png` | 同上 |
| 受击冲击 | `icons/hit-impact.png` | 受击时叠加在受击者位置的图标立绘 popUp |
| 暴击强调 | `icons/critical-impact.png` | 同受击冲击，但 scale 更大、popUp 时长更长 |

**关键约束**：
- **单张立绘 popUp**，不做 2-3 帧的 sprite 序列帧动画（违反"立绘弹出"统一机制）
- 时序：与 `ActionAnimationSpec.impactAt` 同步触发
- 持续时间：100-200ms 内完成 popUp + 淡出
- 视觉风格：剪影白色 + `drop-shadow` 发光，不引入彩色
- 资源位置：`vex-vue/src/assets/illustrations/icons/`（与 BATTLE_ANIMATION_FUTURE_DESIGN §7.4 统一）

**与现有机制的关系**：瞬时反馈立绘就是 BATTLE_ANIMATION_FUTURE_DESIGN §7 定义的"小型图标立绘"的应用场景。复用 `popIconIllustration()` 机制，不引入新的动画体系。

### 4.4 现有"信号色泄漏"的处理

> terminal.css 实际存在 6 处信号色使用，需逐一审查。

| 位置 | 现状 | 处理方案 | 优先级 |
|------|------|---------|--------|
| `.entity-img`（NPC/敌人默认，L198） | 红色描边 `#701e1e`/`#ac1b1b` | **P0 保留**：NPC/敌人辨识的强信号，灰阶替代方案见 §七 | 高 |
| `.map-cell.blocked`（L264） | 红色 `#c44` + 红边框 | **改为灰阶编码**：`color: #ccc; border-style: double;`（双线边框强化"不可通行"语义） | 中 |
| `.map-cell.safe-zone`（L294） | 绿色边框 `rgba(68, 204, 68, 0.25)` | **改为灰阶编码**：`border-color: rgba(255, 255, 255, 0.4); border-style: dashed;`（虚线白边框） | 中 |
| `.status-tick-debug.pending`（L669） | 暗黄 `#ffaa00` | **保留**：仅 debug 模式可见，不影响正式体验 | 低 |
| `.status-npc-pending`（L682） | 暗黄 `#ffaa00` | **改为灰阶**：`color: #fff; animation: tick-pulse`（白色脉冲，频率 ≤ 3Hz） | 中 |
| `.bar-fill.hp.danger`（L716） | 白色 `#fff` + blink | **保留**：低 HP 闪烁是可访问性必要的强提示，且已是灰阶；**blink 频率必须 ≤ 3Hz** | — |

### 4.5 NPC/敌人红色描边的处理（关键决策点）

现状：`.entity-img` 默认红色描边（`#701e1e`/`#ac1b1b`），`.entity-player .entity-img` 覆盖为白色描边。

**这是当前最大的"信号色"使用**——所有 NPC/敌人都用红色描边区分于玩家的白色描边。

**处理方案（待 demo 验证）**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A. 保留红色 | 维持现状 | 辨识度最强 | 破坏黑白美学，与"无信号色"原则冲突 |
| B. 改为灰阶差异 | 玩家=白色描边，NPC=灰色描边，敌人=黑色加粗描边 | 完全灰阶化 | 辨识度可能下降 |
| C. 改为形状差异 | 玩家=白色描边，NPC=无描边（纯 drop-shadow 投影），敌人=虚线描边 | 形状编码，可访问性好 | 视觉差异较微妙 |
| D. 改为立绘轮廓差异 | 通过美术资源的轮廓形状区分（玩家圆润、敌人尖锐） | 最优雅，无需 CSS | 依赖美术资源，实现成本高 |

**推荐**：先做 B+C 组合的 demo（灰阶差异 + 形状差异），与现有红色描边对比效果。若辨识度可接受则切换，否则保留方案 A 作为"必要例外"。

### 4.6 战斗反馈的立绘化

**原则**：所有战斗反馈通过立绘 popUp 表达，**禁止全屏 overlay 闪现、禁止屏幕变色、禁止 contrast 瞬时提升、禁止 opacity 全屏脉冲**。

| 反馈场景 | 错误做法（违反核心约束） | 正确做法（立绘化） |
|---------|---------|---------|
| 受击反馈 | 白色 opacity 全屏脉冲 | `icons/hit-impact.png` 图标立绘在受击者位置 popUp（§4.3） |
| 暴击强调 | 网点扩散全屏 overlay | `icons/critical-impact.png` 图标立绘 popUp，scale 更大、popUp 时长更长 |
| BOSS 登场 | 全屏 contrast 提升 + 网点渐现 | `scenes/boss-emerge-crack.png` 场景立绘 popUp（土地裂开）→ BOSS 立绘 popUp（钻出），符合 project_memory 的"标靶弹出立绘"模式 |
| 逃跑反馈 | —（已移除 flee 动画） | 维持现状，靠 `isFled` 状态切换 |

**关键约束**：所有反馈都是"立绘出现在某个位置"，不是"全屏发生变化"。立绘素材本身的美术承担视觉冲击力，运行时只做 popUp。

## 五、场景过渡框架

### 5.1 与现有 arriveAnim 的关系

> 参考 [MOVE_ANIMATION_TIERS.md §5.3](../../vex-vue/docs/归档/MOVE_ANIMATION_TIERS.md) 的 arriveAnim 实现。

现有 `arriveAnim`（actorAnimations.ts）已是区域切换的**角色层**动画：淡入弹起（alpha 0→1 + scale 0.3→1 + back.out），无倒下阶段。

**场景过渡是 arriveAnim 的"环境层"扩展**：
- arriveAnim 处理角色：角色在新区域淡入弹起
- 场景过渡处理环境：背景/纹理/天穹的氛围切换

两者**同步触发**，但作用于不同图层。

### 5.2 过渡触发场景清单

第一幕需要场景过渡的硬需求：

| 场景 | 触发 | 角色层（arriveAnim） | 环境层（场景过渡） |
|------|------|---------|---------|
| 庇护所 ↔ 沙盒区 | 玩家走出/进入 | ✓ 已有 | 轻量过渡（区域名卡） |
| 沙盒区 → 深层危险区 | 进入潮汐 deep/abyss | ✓ 已有 | 中等过渡（氛围切换 + 纹理变粗） |
| 千年虫 Boss 三阶段 | 阶段切换 | ✓ 已有 | 强过渡（场景整体切换） |
| 第一幕尾声 | 击败千年虫 | — | 特殊过渡（天穹消解 + 镜头上摇，见 §3.4） |

### 5.3 候选方案（待 demo 研判）

**方案 A：黑屏过场 + 区域名字卡**（电影式）
- 淡出 → 黑屏显示 `—— 区域名 ——` → 淡入新场景
- 适用：庇护所 ↔ 沙盒区、千年虫阶段切换
- 优点：戏剧感强，掩盖资源加载
- 缺点：节奏慢，频繁切换拖沓
- 实现：全屏 overlay div + GSAP opacity timeline
- **边界说明**：此处 overlay 是"过渡用黑幕"，缓慢淡入淡出（数百毫秒级），**不是"特效闪现"**（瞬时闪现），不违反"禁用屏幕闪"原则

**方案 B：剪纸层推拉**（舞台式，与天穹层同源）
- 旧场景整体向左滑出，新场景从右滑入
- 适用：同区域内的子场景切换
- 优点：与剪纸美学统一
- 缺点：实现复杂，需处理地图状态同步
- 实现：`#mapGrid` 的 `transform: translateX` + 背景图层交叉淡入
- **风险**：与 `useMapInteraction` 的平移/缩放状态冲突，需通过受控 API 触发，不直接操作 transform

**方案 C：横向平移 + 背景交叉淡入**（镜头式）
- `#mapContainer` 平移一段距离，背景层 `background-image` 交叉淡入
- 适用：相邻区域切换
- 优点：电影感
- 缺点：与现有地图缩放/平移系统冲突需排查
- 实现：通过 `useMapInteraction` 暴露的受控 API 触发

**方案 D：ASCII 故障立绘过渡**（终端式）
- 旧场景淡出 → `scenes/ascii-glitch.png` 故障立绘 popUp（覆盖过渡期）→ 新场景淡入
- 适用：千年虫阶段切换（机械感强）
- 优点：与 ASCII 终端风格统一
- 缺点：依赖美术资源制作"故障感"立绘
- 实现：将"字符雨/故障感"作为一张**场景立绘素材**烘焙到 PNG，通过 popUp + 淡出实现，**不通过运行时全屏字符动画**
- **边界**：此方案是场景过渡的特例（非战斗特效）；若美术资源制作成本过高可降级为方案 A

**方案 E：简单淡入淡出**（保底）
- 旧场景 fade out → 新场景 fade in
- 适用：所有场景的兜底方案
- 优点：实现最快
- 缺点：缺乏戏剧感

### 5.4 推荐组合

| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 庇护所 ↔ 沙盒区 | 方案 A（字卡） | 节奏适中，强叙事感 |
| 沙盒区子区域切换 | 方案 C（平移） | 镜头连贯，与 arriveAnim 配合 |
| 千年虫阶段切换 | 方案 D（故障立绘） | 机械主题契合 |
| 第一幕尾声 | §3.4 天穹消解 | 特殊叙事时刻 |

### 5.5 实现预留

新增 `vex-vue/src/composables/useSceneTransition.ts`：

```typescript
interface SceneTransitionOptions {
  type: 'card' | 'slide' | 'glitch' | 'dissolve';
  duration?: number;
  label?: string;        // 方案 A 的字卡文字
  onComplete?: () => void;
}

function transitionScene(options: SceneTransitionOptions): Promise<void>
```

**关键技术问题（demo 需验证）**：
1. 过渡期间玩家位置如何锁定？（建议扩展 `playerAvatarStore.lockMove()` 为全局场景锁，或新增 `sceneLock` 标志）
2. 新区域资源预加载时机？（建议过渡开始时并行 fetch，过渡完成时已就绪）
3. 与 `syncActorPosition` 的交接？（建议过渡结束时统一 `syncAllPositions`，与 arriveAnim 协同）
4. 与 `useMapInteraction` 平移/缩放的冲突？（建议过渡期间禁用交互，通过受控 API 触发而非直接操作 transform）
5. `prefers-reduced-motion` 兜底？（直接降级为方案 E）

### 5.6 Demo 优先级

**P0 demo**：方案 A（字卡）+ 方案 D（故障立绘）——分别覆盖日常过渡和叙事高潮，验证最关键的两个方向后再扩展。

## 六、信号色策略（最终定调）

### 6.1 总原则

**Oblivions 前端不引入彩色信号色。**

所有信息通过灰阶 + 形状 + 纹理 + 位置冗余编码。

### 6.2 例外清单

仅以下场景允许使用非灰阶色彩，且必须同时提供形状冗余：

| 场景 | 色彩 | 形状冗余 | 理由 | 处理 |
|------|------|---------|------|------|
| NPC/敌人立绘描边 | 红色 `#701e1e`/`#ac1b1b` | 立绘轮廓本身 | 当前 NPC 辨识的强信号 | **待 demo 验证**（§4.5），可能改为灰阶 |
| 低 HP 危险闪烁 | 白色 `#fff`（已是灰阶） | `blink` 动画（**频率 ≤ 3Hz**） | 可访问性必要的强提示 | 保留 |
| debug 模式标识 | 暗黄 `#ffaa00` | 文字 `[DBG]` 前缀 | 仅 debug 模式可见 | 保留 |
| NPC 待结算提示 | 暗黄 `#ffaa00` | `tick-pulse` 动画 | 玩家需感知后端推进 | **改为白色脉冲**（§4.4），频率 ≤ 3Hz |

### 6.3 日志色码处理

沿用现有 `terminal.css`（L395-405）的色码降级策略：后端日志的 `yellow/red/green/blue` 等一律映射为灰阶（`yellow→#fff`、`red→#ccc + underline`、`green→#bbb` 等）。

**新增规则**：日志的语义优先级通过**字重 + 装饰**区分，而非颜色：

- 关键事件：`font-weight: 700`（已部分实现，如 `.log-yellow`）
- 警告事件：`text-decoration: underline`（已部分实现，如 `.log-red`）
- 普通事件：默认
- 次要事件：`color: #555`

## 七、角色辨识度规范

> 此章节的"立绘轮廓细节"部分留待外部识图工具讨论后回填。
>
> 当前仅记录系统层面的设计原则和预留接口。

### 7.1 辨识维度（系统层面）

角色辨识不依赖单一通道，通过多维度冗余：

| 维度 | 实现方式 | 现状 |
|------|---------|------|
| 立绘轮廓 | 美术设计（待外部讨论） | — |
| 投影描边 | `drop-shadow` 色调/粗细 | 玩家=白色描边，NPC=红色描边（待 §4.5 demo） |
| 动画签名 | GSAP 时序特征 | 待实现（§7.3） |
| 位置上下文 | 出现区域 | 已有（enemies 列表按区域） |
| 名称标签 | cell-name 显示 | 已有（当前格 `[我]` 标识） |

### 7.2 投影描边策略

现有 `terminal.css`：
- 玩家立绘（`.entity-player .entity-img`，L208-215）：白色描边（4 方向 1px `#fff`）+ 黑色投影（`rgba(0,0,0,0.6)`）
- NPC/敌人立绘（`.entity-img`，L197-200）：红色描边（`#701e1e`/`#ac1b1b`）+ 黑色投影（`rgba(0,0,0,0.918)`）

**红色描边是当前唯一的"环境信号色"残留**（区别于 §4.4 的 cell 信号色）。处理方案见 §4.5。

**灰阶化后的投影策略**（若 §4.5 决定改灰阶）：

| 角色 | 描边色 | 投影 | 视觉特征 |
|------|--------|------|---------|
| 玩家 | `#fff`（白色，4方向1px） | `rgba(0,0,0,0.6)` | 最亮，主角光环 |
| 友方 NPC | `#bbb`（浅灰，4方向1px） | `rgba(0,0,0,0.7)` | 中等亮度 |
| 敌人 | `#fff`（白色，4方向2px加粗） | `rgba(0,0,0,0.9)` | 描边更粗，威胁感 |
| BOSS | `#fff`（白色，4方向3px加粗 + 虚线） | `rgba(0,0,0,0.95)` | 最粗 + 虚线，特殊感 |

### 7.3 动画签名（可设计，不依赖识图）

每个关键角色的待机/移动动画应有可辨识的节奏特征：

| 角色 | 动画签名建议 | 实现方式 | 频率约束 |
|------|------------|---------|---------|
| 苹果（玩家） | 稳定的轻微呼吸 | 现有 `startIdle`（scaleY 1.02 yoyo） | 低频（≤ 0.5Hz） |
| 猫 | 偶发性的尾巴摆动 | 扩展 idle：周期性 rotation 微动 | 低频（≤ 0.5Hz） |
| 爱丽丝 | 偶发性的蝴蝶结颤动 | 扩展 idle：周期性 scale 微动 | 低频（≤ 0.5Hz） |
| 千年虫 | 沉重的周期性起伏 | 扩展 idle：低频大幅 scaleY | 低频（≤ 0.3Hz） |
| 兔子 | 间歇性快速颤抖 | 扩展 idle：中频小幅度 rotation | 中频（≤ 2Hz） |
| 蟑螂 | 高频小幅抽动 | 扩展 idle：小幅度 x/y | **≤ 3Hz**（光敏防护上限） |

这些不依赖识图能力，可在 `actorAnimations.ts` 中通过参数化的 `startIdle(el, signature?)` 实现。

**关键约束**：所有动画签名的循环频率必须 ≤ 3Hz，蟑螂的"高频"定义上限为 3Hz，不允许超过。
