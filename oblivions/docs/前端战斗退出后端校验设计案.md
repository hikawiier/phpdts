# 前端战斗退出后端校验设计案

> 目的：把"前端何时退出战斗页面"的判据从前端推断改为后端校验，校验触发时机由导演播完钩子决定。消除快速战斗场景下"没演完就退出"的体验问题，同时避免在前端引入战斗状态机造成的双重维护负担。

---

## 1. 当前触发问题

**快速战斗场景**（玩家预装填秒杀敌人 / 敌人逃跑 / 后端战斗上下文返回 NULL）下，玩家完全看不到战斗演出，预装填界面瞬间跳回探索界面。

具体表现：
1. 玩家在预装填界面装填技能 → 点执行 → 提交 `battle.start`
2. 后端立即结算完战斗 → `action` 切回 `''`
3. 前端 `preload:executed` 事件触发 `refreshBattle`
4. `refreshBattle` 看到 `action !== 'battle'` → `fetchAndPlayBattleLog`（NULL 场景下直接 return）→ `exitBattleMode()`
5. 玩家从预装填界面瞬间跳回探索界面，**装填的技能、敌人的死亡、战斗的结束全部被吞掉**

---

## 2. 已复核事实

### 2.1 后端校验字段：`action` 单字段为唯一判据

后端 [`battle.func.php:26-55`](../../oblivions/include/game/battle/battle.func.php#L26-L55)：

```php
function battle_state_init(&$actor_data) {
    $actor_data['action'] = 'battle';   // 进入战斗只设 action
}

function battle_state_clear(&$actor_data, ...) {
    # 二次调用保护：只检查 action（bid 保留不代表在战斗中）
    if (empty($actor_data['action'])) return;
    $actor_data['action'] = '';          // 退出战斗只清 action
    # bid 不在这清，由队列解散时统一清理
}
```

**关键结论**：
- 后端判据是 `action === 'battle'` 一个字段
- `bid` 是战斗队列 ID，战斗结束后仍可能保留（用于队列解散流程），**不是"是否在战斗中"的判据**
- 注释明确："只检查 action（bid 保留不代表在战斗中）"

Command API 响应的 `server_state` 同时返回三个字段（[oblivions/CODEBASE.md:841](../CODEBASE.md#L841)）：
```json
"server_state": { "action": "battle", "bid": 42, "battle_state": "PROCESSING" }
```
前端做"后端校验"时读 `action` + `battle_state`，可区分"在战斗中"和"战斗中但 NPC 处理中"。

### 2.2 前端已有后端校验逻辑，触发时机错误

[`battle.ts:434-456`](../../vex-vue/src/stores/battle.ts#L434-L456) 这段就是后端校验逻辑：

```typescript
// 播放完成后，根据 action 决定后续状态
if (action === 'battle') {
  const afterHeartbeat = await oblHeartbeat();
  ...
  const afterResult = await dataManager.fetch('player_info', true);
  ...
  if (afterAction === 'battle') {
    // 继续战斗（玩家回合 toast 等）
  } else {
    exitBattleMode();   // ← 后端校验说"不在战斗了"，退出
  }
} else {
  exitBattleMode();
}
```

**这段就是"调用一次后端校验决定退出还是继续"**。它已经存在，问题只是触发时机：
- 当前触发时机：`fetchAndPlayBattleLog` return 后立即执行
- 应有触发时机：导演**真正播完**所有动画后执行

### 2.3 空 entries 裸退路径

[`battle.ts:487`](../../vex-vue/src/stores/battle.ts#L487)：

```typescript
if (entries.length === 0) return;
```

NULL battlelog 场景下，`fetchAndPlayBattleLog` 直接返回，**导演根本没启动，校验就已经发生在外层 `refreshBattle` 末尾**。这是快速战斗 bug 的根因。

### 2.4 F5 刷新入口已正确

[`App.vue:128`](../../vex-vue/src/App.vue#L128)：

```typescript
if (playerStore.isInBattle) {
  await battleStore.refreshBattle();
}
```

`playerStore.isInBattle` 基于 `action` 字段（[`player.ts:30`](../../vex-vue/src/stores/player.ts#L30)）。**F5 时拉一次 player_info 看 action，决定要不要进入战斗页面**——这正是"页面初始化时执行一次后端校验"。这个入口已经存在且正确，无需改。

### 2.5 缺失"播完钩子"

- [`battle-playback-runner.ts:29-32`](../../vex-vue/src/stores/battle-playback-runner.ts#L29-L32) `runBattlePlaybackPlan` for 循环结束就 return，无完成回调
- [`battle.ts:510-514`](../../vex-vue/src/stores/battle.ts#L510-L514) `fetchAndPlayBattleLog` 调用 `markBattleLogPlayed` 后 return，无"播完"钩子触发

这两个 return 点就是天然的"播完钩子"位置——但当前没人调用后端校验，校验逻辑被放在外层 `refreshBattle` 末尾。

### 2.6 `currentMode` 的耦合现状

[`battle.ts:91`](../../vex-vue/src/stores/battle.ts#L91) `currentMode: 'normal' | 'battle'` 一个变量同时承担：
1. UI 视图切换（RightPanel 切换、App.vue 红边光效、地图交互屏蔽）
2. commandQueue 第 4 层"模式锁"判据
3. `refreshBattle` 的退出判断

罪魁是第 3 项——`refreshBattle` 末尾 `exitBattleMode()` 一执行，**同时干了两件事**：切 UI 回探索 + 放弃等待导演。这两件事本没有任何理由绑在一起。

---

## 3. 设计原则

1. **前端不维护战斗状态机**——不引入 preload/playing/exiting 等阶段定义，避免前后端两套逻辑
2. **退出战斗页面唯一判据：后端校验**——读 `action` 字段（可辅以 `battle_state`）
3. **校验触发时机**：
   - 导演和动画系统播放完所有动画时调用一次
   - 玩家 F5 刷新页面时初始化调用一次
4. **导演自治**——导演有 `isPlaying` 状态，期间前端拒绝退出（即使后端已切出战斗）
5. **不破坏现有 UI 切换机制**——`currentMode` 维持二值，由前端事件自主切换；改造只影响"何时退出"的判断

---

## 4. 改造方案

### 4.1 改造点一：`fetchAndPlayBattleLog` 空 entries 兜底

**目标**：空 battlelog 不再裸退，让导演有机会合成最小演出 OR 至少走完"播完钩子"流程。

**当前代码** [`battle.ts:477-534`](../../vex-vue/src/stores/battle.ts#L477-L534)：

```typescript
async function fetchAndPlayBattleLog(): Promise<void> {
  if (isPlayingBattleLog.value) return;
  if (!currentGroomid.value || !currentPid.value) return;

  try {
    dataManager.invalidate('battle_log');
    const result = await dataManager.fetch('battle_log', true);
    if (result.status !== 'success' || !result.data) return;

    const entries = (result.data as { entries?: BattleLogRawEntry[] }).entries || [];
    if (entries.length === 0) return;  // ← 空 entries 裸退，问题点

    isPlayingBattleLog.value = true;
    // ... 导演编排 + 播放 + 标记 ...
  } finally {
    isPlayingBattleLog.value = false;
  }
}
```

**改造后**：

```typescript
async function fetchAndPlayBattleLog(): Promise<boolean> {
  // 返回值：是否真的进入了"播完钩子"流程（true = 已走完，false = 跳过）
  if (isPlayingBattleLog.value) return false;
  if (!currentGroomid.value || !currentPid.value) return false;

  isPlayingBattleLog.value = true;
  try {
    dataManager.invalidate('battle_log');
    const result = await dataManager.fetch('battle_log', true);
    if (result.status !== 'success' || !result.data) return false;

    const entries = (result.data as { entries?: BattleLogRawEntry[] }).entries || [];
    const v2Events = entries.filter(isBattleLogV2Event);

    if (v2Events.length > 0) {
      // 正常路径：导演编排 + 播放
      const scriptV2 = directV2(v2Events);
      if (scriptV2.segments.length > 0) {
        const npcPid = extractNpcPidFromScriptV2(scriptV2);
        await playScriptV2(scriptV2, npcPid);
      }
    } else if (entries.length === 0 && shouldSynthesizeFallback()) {
      // 兜底路径：空 entries 时合成最小演出
      await playFallbackScript();
    }
    // entries 非 v2 历史条目：只标记不播放（维持现状）

    // 播完钩子：标记 + 触发后端校验
    const markResult = await markBattleLogPlayed(
      currentGroomid.value,
      currentPid.value,
      collectAllLogIds(entries),
    );
    if (!markResult.success) {
      console.warn('[Battle] markBattleLogPlayed returned failure:', markResult);
    }

    return true;  // ← 走完播完钩子
  } catch (e) {
    console.error('[Battle] fetchAndPlayBattleLog error:', e);
    useToastStore().showToast('战斗数据异常，请刷新', 'error', 4000, false, 'battle-error');
    return false;
  } finally {
    isPlayingBattleLog.value = false;
  }
}
```

**关键变化**：
- `entries.length === 0` 不再裸退，而是进入 `playFallbackScript()` 分支（条件性）
- 返回值改为 `boolean`，让调用方知道是否走完了播完流程
- `markBattleLogPlayed` 调用统一在末尾，作为"播完钩子"的前置

### 4.2 改造点二：播完钩子触发后端校验

**目标**：把 `refreshBattle` 末尾的后端校验逻辑，搬到 `fetchAndPlayBattleLog` 末尾的"播完钩子"位置。

**新增函数** `verifyBattleStateAndDecide`（提取自 [`battle.ts:434-456`](../../vex-vue/src/stores/battle.ts#L434-L456)）：

```typescript
/**
 * 后端校验：拉取最新 player_info，根据 action 决定退出还是继续战斗
 *
 * 触发时机：
 * - 导演播完所有动画后（fetchAndPlayBattleLog 末尾）
 * - F5 刷新页面初始化时（App.vue onMounted，已有逻辑）
 */
async function verifyBattleStateAndDecide(): Promise<void> {
  const afterHeartbeat = await oblHeartbeat();
  if (isHeartbeatSoftFailed(afterHeartbeat)) return;  // 锁忙，等下一轮
  await applyHeartbeatChangedScopes(afterHeartbeat);

  const afterResult = await dataManager.fetch('player_info', true);
  if (afterResult.status !== 'success' || !afterResult.data) return;

  const afterInfo = afterResult.data as PlayerInfo;
  usePlayerStore().setPlayerInfo(afterInfo);
  combatContext.value = afterInfo.combat_context || null;

  const afterAction = afterInfo.action || '';
  if (afterAction === 'battle') {
    // 继续战斗
    currentEnemyPid.value = resolveEnemyPid(afterInfo.battle_queue || null, combatContext.value);
    if (afterInfo.obl_battle_state === 'PLAYER_TURN') {
      const toastStore = useToastStore();
      toastStore.showToast('你的回合', 'info', YOUR_TURN_TOAST_DURATION);
    }
  } else {
    // 后端校验说"不在战斗了"，退出
    exitBattleMode();
  }
}
```

**`fetchAndPlayBattleLog` 末尾调用**：

```typescript
// 播完钩子：标记 + 后端校验
await markBattleLogPlayed(...);
await verifyBattleStateAndDecide();  // ← 新增：播完后触发后端校验

return true;
```

### 4.3 改造点三：`refreshBattle` 简化

**目标**：`refreshBattle` 不再在末尾做退出判断，退出判断完全由播完钩子负责。

**当前代码** [`battle.ts:387-463`](../../vex-vue/src/stores/battle.ts#L387-L463) 核心结构：

```typescript
async function refreshBattle(prefetchedHeartbeat?) {
  if (isProcessingBattle.value) return;
  isProcessingBattle.value = true;

  try {
    // 1. heartbeat + applyHeartbeatChangedScopes
    // 2. 拉 player_info，setPlayerInfo
    // 3. if (action === 'battle') enterBattleMode else stopNpcTurnRefresh
    // 4. await fetchAndPlayBattleLog()
    // 5. 播放完成后根据 action 决定后续状态  ← 这段是问题
    //    if (action === 'battle') { 二次校验 + 继续或退出 }
    //    else { exitBattleMode() }
  } finally {
    isProcessingBattle.value = false;
  }
}
```

**改造后**：

```typescript
async function refreshBattle(prefetchedHeartbeat?) {
  if (isProcessingBattle.value) return;
  isProcessingBattle.value = true;

  try {
    // 1. heartbeat + applyHeartbeatChangedScopes（不变）
    const heartbeat = prefetchedHeartbeat ?? await oblHeartbeat();
    if (isHeartbeatSoftFailed(heartbeat)) return;
    if (!prefetchedHeartbeat) {
      await applyHeartbeatChangedScopes(heartbeat);
    }

    // 2. 拉 player_info（不变）
    const result = await dataManager.fetch('player_info', true);
    if (result.status !== 'success' || !result.data) return;
    const playerInfo = result.data as PlayerInfo;
    usePlayerStore().setPlayerInfo(playerInfo);

    // 3. 同步基本字段（不变）
    const action = playerInfo.action || '';
    const battleQueue = playerInfo.battle_queue || null;
    const nextCombatContext = playerInfo.combat_context || null;
    const battleState = playerInfo.obl_battle_state;
    currentGroomid.value = parseInt(String(playerInfo.groomid)) || 0;
    currentPid.value = parseInt(String(playerInfo.pid)) || 0;
    combatContext.value = nextCombatContext;

    // 4. 进入/维持战斗模式（不变）
    if (action === 'battle') {
      const enemyPid = resolveEnemyPid(battleQueue, nextCombatContext);
      const playerTurn = battleState === 'PLAYER_TURN';
      enterBattleMode(enemyPid, playerTurn, nextCombatContext);
      if (battleState === 'PROCESSING') {
        startNpcTurnRefresh();
      } else {
        stopNpcTurnRefresh();
      }
    } else {
      stopNpcTurnRefresh();
    }

    // 5. 拉取并播放 battlelog —— 播完钩子内部触发后端校验
    await fetchAndPlayBattleLog();
    // ↑ 改造后：fetchAndPlayBattleLog 内部播完后会调 verifyBattleStateAndDecide
    //   refreshBattle 不再在此处做退出判断

  } catch (e) {
    console.error('[Battle] refreshBattle error:', e);
    useToastStore().showToast('战斗数据异常，请刷新', 'error', 4000, false, 'battle-error');
  } finally {
    isProcessingBattle.value = false;
  }
}
```

**关键变化**：
- 删除末尾的 `if (action === 'battle') { 二次校验 } else { exitBattleMode() }` 整段
- 退出判断完全由 `fetchAndPlayBattleLog` 内部的 `verifyBattleStateAndDecide` 负责
- `refreshBattle` 退化为"拉数据 + 触发播放"，职责更纯粹

### 4.4 改造点四：导演兜底演出合成规则

**目标**：空 entries 场景下，导演合成最小演出，让玩家看到"战斗发生了且已结束"。

**触发条件** `shouldSynthesizeFallback()`：

```typescript
function shouldSynthesizeFallback(): boolean {
  // 仅当当前处于战斗模式（currentMode='battle'）且 entries 完全为空时合成
  // 非 v2 历史条目不触发兜底（避免误合成）
  return currentMode.value === 'battle';
}
```

**合成规则** `playFallbackScript()`：

```typescript
async function playFallbackScript(): Promise<void> {
  // 合成一个最小 battle_end segment
  // 文案来源：根据 combatContext 或 playerStore 推断"敌人被击杀"/"敌人逃跑"
  const fallbackSegment: BattleSegmentV2 = {
    kind: 'battle_end',
    roundNum: null,
    actor: null,
    actions: [],
    notices: [
      {
        rawLogId: 0,
        text: { html: '战斗已结束。' },  // 占位文案，后续可细化
        actor: null,
        combatant: null,
        reason: 'fallback',
      },
    ],
  };

  const script: BattlePlayScriptV2 = { segments: [fallbackSegment] };
  const plan = planPlaybackV2(script);
  await runBattlePlaybackPlan(plan, {
    currentPid: currentPid.value,
    npcPid: 0,
    updateSegmentContext,
    playSegmentInModal,
  });
}
```

**文案细化方向**（后续迭代）：
- 若 `combatContext` 显示敌人 HP=0 → "敌人被击杀"
- 若 `combatContext` 显示敌人逃跑标记 → "敌人逃跑"
- 若 `combatContext` 为 NULL（后端战斗上下文已清空）→ 通用"战斗已结束"

**注意**：兜底演出不依赖后端 battlelog，是前端纯合成。这是导演系统从"battlelog 翻译器"扩展为"战斗演出总编排"的入口点，但**当前仅做最小占位**，不引入复杂合成逻辑。

## 7. 风险与边界

### 7.1 兜底演出文案准确性

`playFallbackScript` 当前用占位文案"战斗已结束"。若 `combatContext` 已被后端清空（NULL），前端无法准确判断"敌人被击杀"还是"敌人逃跑"。

**缓解**：第一版用通用文案，后续迭代可让后端在 `combat_context` 中保留 `last_result` 字段（kill/escape/timeout）供前端读取。这属于后续优化，不阻塞本设计案落地。

### 7.2 `verifyBattleStateAndDecide` 的重复调用

改造后 `verifyBattleStateAndDecide` 在 `fetchAndPlayBattleLog` 末尾调用一次。但 NPC 回合轮询 `startNpcTurnRefresh` 也会调 `refreshBattle` → `fetchAndPlayBattleLog` → `verifyBattleStateAndDecide`。

**这不是问题**：每次播完都校验一次是预期行为。`isProcessingBattle` 锁已防止 `refreshBattle` 重入，`isPlayingBattleLog` 锁已防止 `fetchAndPlayBattleLog` 重入。

### 7.3 空 entries 但仍在战斗中的场景

若后端战斗未结束但 `battle_log` 暂时为空（极端时序），`shouldSynthesizeFallback` 会误触发兜底演出。

**缓解**：`shouldSynthesizeFallback` 仅在 `currentMode === 'battle'` 时合成。若 `verifyBattleStateAndDecide` 后发现 `action === 'battle'`，前端会继续停留在战斗模式等待下一轮 battlelog。兜底演出只是"显示一段文字"，不会错误退出战斗。

### 7.4 `combat_context` NULL 场景下的敌人名显示

兜底演出 segment 无 actor/targets，`BattleHeader` 的 `enemyName` 可能为空。

**缓解**：`playFallbackScript` 可从 `combatContext`（若非 NULL）或上一轮 segment 保留的 `enemyName` 读取。第一版可接受空敌人名，显示通用"战斗已结束"。

### 7.5 不引入状态机的边界

本设计案**不**解决以下问题（超出范围）：
- 预装填阶段和真正战斗的 UI 差异化反馈
- 导演在预装填阶段编排"开场亮相"（敌人出现动画）
- 战斗退出时的"收尾演出"（敌人尸体淡出）

这些是后续可扩展点，但当前快速战斗 bug 的修复不需要它们。本设计案坚持"最小改造解决问题"原则。
