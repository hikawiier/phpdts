# 战斗锁定白名单 — 设计案（占位）

> 本案为**未来任务占位**，仅记录问题背景与重构方向，**不涉及本次任务实施**。
>
> 触发背景：道具系统（U3/U5）与合成系统新增 `obl_use_item` / `obl_craft` / `obl_organize` 三条命令时，发现现有战斗锁定采用黑名单模式，每新增一个功能都需额外加判断。未来应在统一任务中改为白名单模式。

---

## 一、问题背景

### 1.1 现状：黑名单模式

当前战斗锁机制由 [`command-queue.ts`](../../vex-vue/src/stores/command-queue.ts) 的 `isLocked` getter 与 `execute()` 方法实现，包含三层锁：

| 锁类型 | 触发条件 | 阻止范围 |
|--------|---------|---------|
| HTTP 请求锁 | `_locked=true`（单次请求周期） | 所有命令 |
| 战斗演出锁 | `isPlayingBattleLog=true` | 所有命令 |
| 状态机锁 | `oblBattleState==='PROCESSING'` | **仅** `TICK_ADVANCING_COMMANDS` 白名单中的命令 |

`TICK_ADVANCING_COMMANDS`（[command-queue.ts L23-29](../../vex-vue/src/stores/command-queue.ts#L23-L29)）实际上已经是"推进 tick 的命令白名单"，但它解决的是**"哪些命令会触发 NPC 先攻轮"**，而非**"战斗模式下哪些命令可执行"**。

### 1.2 黑名单模式的缺陷

| 缺陷 | 表现 |
|------|------|
| 新功能易遗漏战斗锁 | 道具使用/合成/整理三条新命令均未在战斗模式下做禁用判断（本次会话已确认暂时不补，等待统一重构） |
| 锁定规则散落 | `commandQueue.isLocked` 检查点散布于 `tileAction.ts` / `InventoryList.vue` / `TileActionBar.vue` / `useMapInteraction.ts` 等多个文件 |
| 战斗模式与战斗演出锁语义重叠 | `currentMode==='battle'`（UI 切换）与 `isPlayingBattleLog`（演出期间）概念边界模糊，新功能开发者难以判断应使用哪个 |
| 命令分类无单一真值源 | 哪些命令推进 tick、哪些命令战斗时禁用、哪些命令演出时禁用——三类规则分散在不同代码位置 |

### 1.3 本次会话相关的临时决策

- 本次会话**未**给 `obl_craft` / `obl_use_item` / `obl_organize` 加战斗时禁用判断
- `obl_craft` / `obl_use_item` / `obl_organize` **未**加入 `TICK_ADVANCING_COMMANDS`（不推进 tick，符合后端 `obl_command_advances_tick()` 实现）
- 这意味着玩家在 `currentMode==='battle'` 但 `oblBattleState!=='PROCESSING'` 且非演出期间，**理论上可执行合成/使用道具/整理**——这是已知技术债，等待本案重构统一修复

## 二、目标：白名单模式

### 2.1 核心思路

将"战斗模式下能做什么"从**黑名单**（默认允许，逐个加禁用）翻转为**白名单**（默认禁用，逐个加允许）。

### 2.2 白名单的三层分类

每条命令应明确归属以下分类之一，由统一的注册表（如 `command-registry.ts`）维护：

| 分类 | 何时允许 | 示例命令 |
|------|---------|---------|
| **战斗内命令** | 仅战斗模式下允许 | `obl_battle_action` / `obl_battle_start` |
| **探索内命令** | 仅非战斗模式下允许 | `obl_explore` / `obl_search` / `obl_craft` / `obl_use_item` / `obl_organize` / `move` |
| **通用命令** | 任何模式下都允许 | 心跳、查询类 API（不通过 commandQueue 提交） |

### 2.3 期望的调用形态（待重构时细化）

```typescript
// 伪代码示例，仅表达方向
class CommandQueue {
  execute(params) {
    if (this._locked) return LOCKED;
    if (this._cooldown > Date.now()) return COOLDOWN;
    if (isPlayingBattleLog) return PLAYING_BATTLE_LOG;

    const cmd = params.command;
    const inBattle = useBattleStore().currentMode === 'battle';
    const category = commandRegistry[cmd]?.category;

    // 白名单过滤：战斗模式下仅允许战斗内命令
    if (inBattle && category !== 'battle') {
      return NOT_ALLOWED_IN_BATTLE;
    }
    // 非战斗模式下仅允许探索内命令
    if (!inBattle && category === 'battle') {
      return NOT_ALLOWED_IN_EXPLORE;
    }
    // PROCESSING 状态仅允许特定命令（如查询类，不含推进 tick）
    if (oblBattleState === 'PROCESSING' && !commandRegistry[cmd]?.allowedInProcessing) {
      return PENDING_NPC;
    }
    // ...
  }
}
```

### 3.1 必改文件

| 文件 | 改动类型 |
|------|---------|
| `vex-vue/src/stores/command-queue.ts` | 重构 `execute()` 锁判断顺序，引入命令分类查询 |

| `vex-vue/src/stores/player.ts` | 复核 `isInBattle` computed 的派生来源 |

### 3.2 需复核的 `isLocked` 调用点

以下文件含 `commandQueue.isLocked` 判断，重构后需逐个检查是否仍需保留本地判断（理想情况下应全部移除，由 commandQueue 统一拦截）：

- `vex-vue/src/stores/tileAction.ts`（3 处）
- `vex-vue/src/composables/useMapInteraction.ts`（1 处）
- `vex-vue/src/components/actions/TileActionBar.vue`（3 处）
- `vex-vue/src/components/actions/ExploreButton.vue`（1 处）
- `vex-vue/src/components/inventory/InventoryList.vue`（2 处）
- `vex-vue/src/components/battle/PreloadArea.vue`（1 处）

### 3.3 后端配套

后端 [`oblivions_router.php`](../oblivions_router.php) 已有命令状态过滤（如 `obl_use_item` 在战斗状态下被拒）。重构时应核对前后端白名单一致性，避免前端允许但后端拒绝（或反之）的情况。

## 四、实施前置条件

本案实施前需明确以下设计决策（待未来任务启动时讨论）：

1. **命令分类边界**：`obl_battle_start` 属于战斗内还是探索内？（启动战斗前玩家在探索模式，命令执行后切换到战斗模式）
2. **查询类 API 是否走 commandQueue**：目前 `craft_preview` / `craft_recipes` 等查询直接通过 `gameApi` 调用，不经 commandQueue——白名单是否需要覆盖查询类？
3. **UI 层是否保留本地 disabled 判断**：若 commandQueue 已统一拦截，UI 层的 `:disabled="commandQueue.isLocked"` 是否应改为更精细的 `:disabled="!canExecute"`（用于按钮置灰反馈）？
4. **战斗演出锁是否独立**：`isPlayingBattleLog` 是演出期间锁，与战斗模式本身不同——是否保留为独立锁？
