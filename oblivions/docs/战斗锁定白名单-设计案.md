# 战斗锁定白名单 — 设计案（占位）

> 本案为**未来任务占位**，仅记录问题背景与重构方向，**不涉及本次任务实施**。
>
> 触发背景：道具系统（U3/U5）与合成系统新增 `obl_use_item` / `obl_craft` / `obl_organize` 三条命令时，发现现有战斗锁定采用黑名单模式，每新增一个功能都需额外加判断。未来应在统一任务中改为白名单模式。

---

## 一、问题背景

### 1.1 现状：前端黑名单 + 后端三层白名单的错位

#### 1.1.1 前端锁结构（command-queue.ts）

前端战斗锁机制由 [`command-queue.ts`](../../vex-vue/src/stores/command-queue.ts) 的 `isLocked` getter 与 `execute()` 方法实现，包含**四层锁**：

| 锁类型 | 触发条件 | 阻止范围 | isLocked getter 是否纳入 |
|--------|---------|---------|-------------------------|
| HTTP 请求锁 | `_locked=true`（单次请求周期） | 所有命令 | ✅ 是 |
| 战斗演出锁 | `isPlayingBattleLog=true` | 所有命令 | ✅ 是 |
| PROCESSING 锁 | `oblBattleState==='PROCESSING'` | **仅** `TICK_ADVANCING_COMMANDS` 中的命令 | ⚠️ **是（隐性 bug）**——见下文 |
| itm0 锁 | `inventoryStore.itm0 !== null` | **未在前端 execute() 中拦截**，仅由 CraftModal/InventoryList 等组件本地判断 | ❌ 否 |

`TICK_ADVANCING_COMMANDS`（[command-queue.ts L23-29](../../vex-vue/src/stores/command-queue.ts#L23-L29)）实际上已经是"推进 tick 的命令白名单"，但它解决的是**"哪些命令会触发 NPC 先攻轮"**，而非**"战斗模式下哪些命令可执行"**。

**⚠️ 隐性 bug：`isLocked` 与 `execute()` 行为不一致**

当前 [`isLocked` getter L107-109](../../vex-vue/src/stores/command-queue.ts#L107-L109) 把 PROCESSING 视为完全锁定：
```typescript
get isLocked(): boolean {
  return this._locked || usePlayerStore().oblBattleState === 'PROCESSING' || useBattleStore().isPlayingBattleLog;
}
```

但 [`execute()` L61](../../vex-vue/src/stores/command-queue.ts#L61) 实际**仅拦截 advancesTick 命令**——非 advancesTick 命令在 PROCESSING 时仍会继续提交。

**后果**：UI 层所有 `:disabled="commandQueue.isLocked"` 在 PROCESSING 时把**所有按钮**置灰（包括 use_item/craft/organize），但 execute() 实际放行这些命令。"UI 看起来禁用了"与"execute 实际放行"语义不一致。结果碰巧正确（后端模式锁兜底拒绝），但机制错误。

**详细分析与修复方案详见 §2.8**。

#### 1.1.2 后端锁结构（已实现白名单）

后端在 [`obl_command.php`](../include/core/obl_command.php) 路径中已实现**三层白名单**：

| 层级 | 实现位置 | 规则 | 拦截时机 |
|------|---------|------|---------|
| 状态过滤 | [`obl_command_allowed_by_state()`](../include/game/player.func.php#L298-L309) | `action==='battle'` 时仅允许 `obl_battle_action`；非 `battle` 时禁 `obl_battle_action` | 命令执行前 [C2] |
| 战场忙锁 | [`obl_tick_has_busy_battle()`](../include/game/tick.func.php#L131-L136) + [`obl_command_advances_tick()`](../include/game/tick.func.php#L166-L175) | PROCESSING 时拒绝推进 tick 的命令 | 命令执行前 [C2b] |
| itm0 门控 | [`oblivions_router.php`](../include/command/oblivions_router.php#L28-L32) | `itempara[0]` 非空时仅允许 `obl_organize` / `obl_discard` / `obl_use_item` | 路由分发前 |

后端 `obl_command_allowed_by_state()` 的白名单实现：

```php
function obl_command_allowed_by_state($command, $action) {
    if ($action === 'battle') {
        // 战斗中：只允许战斗动作
        return in_array($command, array('obl_battle_action'), true);
    }
    // 正常状态：不允许战斗中命令（obl_battle_action），
    // 但允许 obl_battle_start（发起战斗）和所有探索命令
    if (in_array($command, array('obl_battle_action'), true)) {
        return false;
    }
    return true;
}
```

#### 1.1.3 前后端错位

| 状态 | 前端 | 后端 | 后果 |
|------|------|------|------|
| `currentMode==='battle'` 时执行 `obl_use_item` | **允许**（无 execute 拦截） | **拒绝**（不在白名单） | 无谓请求 + 错误日志 |
| `currentMode==='battle'` 时执行 `obl_craft` | **允许** | **拒绝** | 同上 |
| `currentMode==='battle'` 时执行 `obl_organize` | **允许** | **拒绝** | 同上 |
| `itm0 !== null` 时执行 `obl_explore` | **允许**（无 execute 拦截） | **拒绝**（itm0 门控） | 仅靠组件本地 disabled 判断，散落多处 |

**澄清（v1.2 修正）**：
- 之前误判"PROCESSING 期间允许 use_item 是隐性技术债"——实际上后端 [`obl_command_allowed_by_state`](../include/game/player.func.php#L298-L309) 在 `action==='battle'` 时**只允许 obl_battle_action**，use_item/craft/organize 在战斗模式下（无论 PLAYER_TURN 还是 PROCESSING）都被后端拒绝
- 真正的问题不是"PROCESSING 锁覆盖不全"，而是**前端 execute() 缺少模式锁（mode 锁）**——后端用 action 字段过滤，前端依赖 UI 切换避免命令提交
- PROCESSING 锁的实际作用是防止玩家在 NPC 行动期间重复提交 obl_battle_action（与后端 [C2b] 一致），与 use_item/craft/organize 无关——详见 §2.5 心跳守护进程机制

### 1.2 黑名单模式的缺陷

| 缺陷 | 表现 |
|------|------|
| 新功能易遗漏战斗锁 | 道具使用/合成/整理三条新命令均未在战斗模式下做禁用判断（本次会话已确认暂时不补，等待统一重构） |
| 锁定规则散落 | `commandQueue.isLocked` 检查点散布于 `tileAction.ts` / `craft.ts` / `InventoryList.vue` / `TileActionBar.vue` / `CraftModal.vue` / `Itm0Modal.vue` / `useMapInteraction.ts` / `PreloadArea.vue` 等多个文件（共 28 处，见 §3.2） |
| 战斗模式与战斗演出锁语义重叠 | `currentMode==='battle'`（UI 切换）与 `isPlayingBattleLog`（演出期间）概念边界模糊，新功能开发者难以判断应使用哪个 |
| 命令分类无单一真值源 | 哪些命令推进 tick、哪些命令战斗时禁用、哪些命令演出时禁用——三类规则分散在不同代码位置 |
| **前端缺少模式锁（核心问题）** | 后端 `obl_command_allowed_by_state` 在 `action='battle'` 时拒绝所有非 obl_battle_action 命令；前端 execute() 没有等价门控，依赖 UI 切换（currentMode='battle' 时隐藏探索/背包/合成按钮）避免命令提交。这是 UX 层差异，非语义漏洞——后端会兜底拒绝，但前端无前置反馈 |
| **前后端白名单不一致** | 后端已用 `obl_command_allowed_by_state` 实现战斗模式白名单，前端依赖 UI 切换避免命令提交，二者无单一真值源，新增命令需在两端分别维护 |
| **`isLocked` 与 `execute()` 行为不一致（v1.3 新发现）** | [`isLocked` getter](../../vex-vue/src/stores/command-queue.ts#L107-L109) 把 PROCESSING 视为完全锁定（所有按钮 :disabled），但 [`execute()`](../../vex-vue/src/stores/command-queue.ts#L61) 实际仅拦截 advancesTick 命令。PROCESSING 时 UI 误置灰 use_item/craft/organize，但 execute() 放行——结果碰巧正确（后端兜底拒绝），但机制错误。详见 §2.8 |

### 1.3 本次会话相关的临时决策

- 本次会话**未**给 `obl_craft` / `obl_use_item` / `obl_organize` 加战斗时禁用判断
- `obl_craft` / `obl_use_item` / `obl_organize` **未**加入 `TICK_ADVANCING_COMMANDS`（不推进 tick，符合后端 `obl_command_advances_tick()` 实现）
- 这意味着玩家在 `currentMode==='battle'` 但 `oblBattleState!=='PROCESSING'` 且非演出期间，**理论上可执行合成/使用道具/整理**——但提交后会被后端 `obl_command_allowed_by_state` 拒绝（无前置反馈，仅产生无谓请求 + 错误日志）
- 这是已知 UX 技术债，等待本案重构统一修复

## 二、目标：白名单模式

### 2.1 核心思路

将"战斗模式下能做什么"从**黑名单**（默认允许，逐个加禁用）翻转为**白名单**（默认禁用，逐个加允许）。

**关键定位**：前端白名单**对齐**后端已有的 `obl_command_allowed_by_state` 语义，但**以前端 `currentMode` 为单一真值源**（理由见 §4 决策 1）。前端白名单不取代后端白名单——两端各司其职，前端负责 UI 即时反馈，后端负责权威校验。

### 2.2 命令的三维度分类

每条命令在注册表中应明确以下三个维度的属性，由统一的 `command-registry.ts` 维护：

| 维度 | 取值 | 含义 | 对应后端 |
|------|------|------|---------|
| **mode** | `battle` / `explore` / `universal` | 命令在哪种 UI 模式下可执行 | `obl_command_allowed_by_state` |
| **advancesTick** | `true` / `false` | 是否推进游戏刻（触发 NPC 先攻轮） | `obl_command_advances_tick` |
| **itm0Allowed** | `true` / `false` | itm0 锁定下是否允许执行 | `oblivions_router.php` 的 itm0 门控 |

### 2.3 命令分类表（与后端对齐）

| 命令 | mode | advancesTick | itm0Allowed | 后端白名单归类 |
|------|------|--------------|-------------|---------------|
| `move` | explore | true | false | 探索内 |
| `obl_explore` | explore | true | false | 探索内 |
| `obl_search` | explore | true | false | 探索内 |
| `obl_pickup` | explore | false | false | 探索内（未在 advancesTick，但 itm0 锁定下被拒） |
| `obl_discard` | explore | false | true | 探索内（itm0 锁定下允许，slot=0 丢弃手持） |
| `obl_use_item` | explore | false | true | 探索内（itm0 锁定下允许，slot=0 使用手持） |
| `obl_organize` | explore | false | true | 探索内（itm0 锁定下允许） |
| `obl_craft` | explore | false | false | 探索内 |
| `obl_battle_start` | battle | true | false | 后端归探索内（非 battle 时允许）——见 §4 决策 1 |
| `obl_battle_action` | battle | true | false | 战斗内 |

### 2.4 期望的调用形态

```typescript
// command-registry.ts（新增）
export interface CommandSpec {
  mode: 'battle' | 'explore' | 'universal';
  advancesTick: boolean;
  itm0Allowed: boolean;  // itm0 锁定下是否允许
}

export const COMMAND_REGISTRY: Record<string, CommandSpec> = {
  move:              { mode: 'explore', advancesTick: true,  itm0Allowed: false },
  obl_explore:       { mode: 'explore', advancesTick: true,  itm0Allowed: false },
  obl_search:        { mode: 'explore', advancesTick: true,  itm0Allowed: false },
  obl_pickup:        { mode: 'explore', advancesTick: false, itm0Allowed: false },
  obl_discard:       { mode: 'explore', advancesTick: false, itm0Allowed: true  },
  obl_use_item:      { mode: 'explore', advancesTick: false, itm0Allowed: true  },
  obl_organize:      { mode: 'explore', advancesTick: false, itm0Allowed: true  },
  obl_craft:         { mode: 'explore', advancesTick: false, itm0Allowed: false },
  obl_battle_start:  { mode: 'battle',  advancesTick: true,  itm0Allowed: false },
  obl_battle_action: { mode: 'battle',  advancesTick: true,  itm0Allowed: false },
};

// command-queue.ts execute() 重构（伪代码）
//
// 关键设计：execute() 复用 _checkLocks()（与 canExecute 共用），
// 保证 UI 查询与实际执行判断完全一致，避免 isLocked 与 execute() 行为分叉（见 §2.8）。
async execute(params): Promise<CommandResult> {
  const cmd = params.command || '';

  // ── 前置检查：复用 _checkLocks（与 canExecute 共用，保证一致） ──
  if (!this._checkLocks(cmd)) {
    return { success: false, error: 'LOCKED', message: '当前状态不可执行此操作' };
  }

  // ── 通过所有锁后，实际执行 ──
  const spec = COMMAND_REGISTRY[cmd];
  this._locked = true;
  try {
    const result = await submitCommand(params);
    if (result.timer) {
      this._cooldown = Date.now() + result.timer * 1000;
    }
    if (result.success && spec?.advancesTick) {
      await this._checkBattleState();
    }
    return result;
  } finally {
    this._locked = false;
  }
}
```

**与原 v1.1/v1.2 伪代码的差异**：
- v1.4 改为复用 `_checkLocks()`（返回 boolean），避免 execute 与 canExecute 逻辑分叉
- `_checkLocks` 不暴露拒绝原因——UI `:disabled` 只需要布尔结果，避免 LockReason 枚举等过度设计
- `_checkLocks` 的具体实现见 §2.7.2

### 2.5 心跳守护进程机制（PROCESSING 实际驱动）

#### 2.5.1 两个独立定时器

前端 [`battle.ts`](../../vex-vue/src/stores/battle.ts) 实现了两个职责分离的定时器：

| 定时器 | 间隔 | 实现 | 职责 |
|--------|------|------|------|
| **心跳守护进程** | **200ms** | [`_daemonBeat`](../../vex-vue/src/stores/battle.ts#L157-L164) → `fetch('/api_v2.php?action=heartbeat')` | fire-and-forget 触发后端 tick 推进 + NPC 行动 |
| **NPC 状态轮询** | **1000ms** | [`startNpcTurnRefresh`](../../vex-vue/src/stores/battle.ts#L130-L137) → `dataManager.fetch('player_info')` | 状态发现——查看是否切回 PLAYER_TURN |

**关键洞察**：心跳守护进程是 PROCESSING 状态实际结束的驱动力，NPC 状态轮询只是"查看是否已结束"。

#### 2.5.2 后端 heartbeat → tick 推进链路

[`api_v2.php`](../../api_v2.php) 第 11 行 `require_once './include/core/common.inc.php'`——所有 API 请求（含 heartbeat）都会加载 common.inc.php。

[common.inc.php 第 337-360 行](../include/core/common.inc.php#L337-L360) 在每次请求末尾检测：

```php
if (oblivions_is_active() && $gamevars['obl_pretick'] < $gamevars['obl_tick']) {
    $delta = $gamevars['obl_tick'] - $gamevars['obl_pretick'];
    obl_tick_synchronize();            // 同步 obl_pretick = obl_tick
    obl_resolve_tick_events($delta);   // 触发 NPC 行动（battle_npc phase）
    // ...战斗状态机超时恢复...
    $ginfochange = true;
}
```

链路：前端心跳（200ms） → common.inc.php 检测 `obl_pretick < obl_tick` → `obl_resolve_tick_events` → `obl_tick_phase_battle_npc` → NPC 行动 → `battle_manage_queue` → 状态机切换（PROCESSING → PLAYER_TURN / self_loop / IDLE）。

#### 2.5.3 PROCESSING 的实际持续时间

PROCESSING 通常在 **200-400ms 内**（一个心跳周期）被处理完：
- 单次 NPC 行动通常很快（毫秒级）
- 前端 1 秒轮询拉取 player_info 时，PROCESSING 大概率已切回 PLAYER_TURN
- 极端场景（多 NPC 连击、self_loop 持续、服务器高负载）会持续多个 200ms 周期

**前端实际感知 PROCESSING 的场景**：
1. 玩家执行 obl_battle_action 后 `_checkBattleState` 立即拉取 player_info——可能在守护进程推动 NPC 行动前看到 PROCESSING（这是 PROCESSING 锁的主要触发场景）
2. 多 NPC 连击时 1 秒轮询拉取到 PROCESSING

#### 2.5.4 PROCESSING 锁的真正作用

前端 commandQueue 的 PROCESSING 锁（拦截 `TICK_ADVANCING_COMMANDS`）：
- **作用**：防止玩家在 NPC 行动期间重复提交 obl_battle_action
- **与 use_item/craft/organize 无关**：这些命令被模式锁（第 4 层）拦截
- **后端 [C2b] 也是同样语义**：拒绝 PROCESSING 期间的推进 tick 命令
- **不需要扩展**：保持现状即可

### 2.6 前后端战斗状态同步与窗口期

#### 2.6.1 进入战斗的两种路径

**路径 A：玩家主动攻击**——前端比后端**早**进入（合理窗口期）：

```
玩家点敌人
  ↓
battleStore.startBattle() → currentMode='battle'（前端先切换，显示装填区）
  ↓
玩家装填 + 点击执行
  ↓
PreloadArea.onExecute → commandQueue.execute({ command: 'obl_battle_start' })
  ↓
后端收到命令：action='normal'（尚未切换）→ obl_command_allowed_by_state 允许
  ↓
后端处理 obl_battle_start → 创建队列（状态=PROCESSING）→ action='battle' → 切到 PLAYER_TURN
  ↓
后续 refreshBattle → enterBattleMode（currentMode 已是 battle，仅更新 isPlayerTurn）
```

**路径 B：被动遭遇**——后端先切换，前端跟随：

```
玩家执行 move/obl_explore/obl_search
  ↓
后端触发遭遇战 → battle_queue_create_and_init → action='battle'，状态=PROCESSING
  ↓
前端 _checkBattleState 拉取 player_info → 看到 action='battle'
  ↓
refreshBattle → enterBattleMode（currentMode 切换到 battle）
```

#### 2.6.2 退出战斗——前端比后端**晚**退出（合理窗口期）

```
后端 battle_end → action='normal'，obl_battle_state=IDLE
  ↓
前端 refreshBattle 拉取 player_info → action !== 'battle'
  ↓
fetchAndPlayBattleLog（先播完积压的 battlelog）← 关键：演出完整性优先
  ↓
播完后 afterAction !== 'battle' → exitBattleMode → currentMode='normal'
```

#### 2.6.3 窗口期合理性边界

| 窗口期 | 方向 | 合理性 | 说明 |
|--------|------|--------|------|
| 主动攻击时前端先切换 currentMode='battle' | 前端比后端早进入 | ✅ 合理 | 玩家需要装填区才能发起 obl_battle_start，UI 必须先切换 |
| 退出战斗时前端等 battlelog 播完 | 前端比后端晚退出 | ✅ 合理 | 演出完整性优先，避免战斗突然结束的突兀感 |
| 被动遭遇时后端先切换 action='battle' | 后端比前端早进入 | ✅ 合理 | 遭遇战由后端判定触发，前端通过 player_info 跟随 |

**反向不合理场景**（应避免）：
- ❌ 前端比后端**早**退出战斗——前端处理有 bug，应修正同步逻辑
- ❌ 前端比后端**晚**进入战斗（玩家主动攻击场景）——不应发生，startBattle 必须立即切换 currentMode

**白名单判断的真值源选择**：以前端 `currentMode` 为准（见 §4 决策 5），因为这些窗口期都是合理的设计选择。前端 `currentMode` 反映"UI 应该处于什么模式"，后端 `action` 反映"逻辑上是否在战斗中"，二者在稳定状态下一致，仅在窗口期有合理偏差。

### 2.7 `canExecute` 方法设计

#### 2.7.1 设计目标

`canExecute(command): boolean` 是 UI 层与 `execute()` 共享的**前置检查接口**，用于 UI `:disabled` 派生——按钮根据命令+当前状态自动置灰，无需各组件本地判断。

**与 `execute()` 的关系**：`canExecute` 是 `execute()` 前置检查的**纯查询版本**——不实际提交命令，只返回布尔结果。`execute()` 内部复用同一私有方法 `_checkLocks`，保证二者判断完全一致，避免重蹈 `isLocked` 与 `execute()` 行为不一致的隐性 bug（详见 §2.8）。

**不设计原因反馈机制**：UI `:disabled` 只需要"能不能执行"的布尔结果，不需要"为什么不能"。当前无"点击置灰按钮显示原因"的交互需求，避免过度设计。若未来确有 toast 反馈需求，再扩展 `_checkLocks` 返回结构化结果。

#### 2.7.2 实现伪代码

```typescript
class CommandQueue {
  /**
   * 私有：统一的前置检查逻辑（execute 与 canExecute 共用）
   * 返回 true 表示通过所有锁，可执行
   */
  private _checkLocks(command: string): boolean {
    // ── 第 1 层：HTTP 请求锁 + 冷却 ──
    if (this._locked || this._cooldown > Date.now()) return false;

    // ── 第 2 层：战斗演出锁 ──
    if (useBattleStore().isPlayingBattleLog) return false;

    const spec = COMMAND_REGISTRY[command];
    if (!spec) return false;  // 未注册命令拒绝

    // ── 第 3 层：itm0 锁 ──
    if (useInventoryStore().itm0 !== null && !spec.itm0Allowed) return false;

    // ── 第 4 层：模式锁（以前端 currentMode 为真值源） ──
    const inBattle = useBattleStore().currentMode === 'battle';
    if (inBattle && spec.mode !== 'battle') return false;
    if (!inBattle && spec.mode === 'battle') return false;

    // ── 第 5 层：PROCESSING 锁（仅拦截推进 tick 命令） ──
    if (spec.advancesTick && usePlayerStore().oblBattleState === 'PROCESSING') return false;

    return true;
  }

  /** UI :disabled 派生用 */
  canExecute(command: string): boolean {
    return this._checkLocks(command);
  }
}
```

#### 2.7.3 UI 使用示例

```vue
<!-- TileActionBar.vue -->
<button :disabled="!commandQueue.canExecute('obl_explore')" @click="onExplore">探索</button>
<button :disabled="!commandQueue.canExecute('obl_craft')" @click="onOpenCraft">合成</button>
```

**注意**：UI 层的 `canExecute` 检查**不取代** `execute()` 内部拦截——`execute()` 仍会再次调用 `_checkLocks` 兜底，防止 UI 层绕过（如键盘快捷键、开发者工具直接调用 `execute()`）。两层职责不同：UI 检查用于"前置反馈"，execute 检查用于"权威拦截"。

### 2.8 `isLocked` 隐性 bug 修复

#### 2.8.1 当前 `isLocked` 的隐性 bug

当前 [command-queue.ts L107-109](../../vex-vue/src/stores/command-queue.ts#L107-L109) 实现：

```typescript
get isLocked(): boolean {
  return this._locked
    || usePlayerStore().oblBattleState === 'PROCESSING'
    || useBattleStore().isPlayingBattleLog;
}
```

**问题**：`isLocked` 把 PROCESSING 视为完全锁定，但 [`execute()` L61](../../vex-vue/src/stores/command-queue.ts#L61) 实际**仅拦截 advancesTick 命令**——非 advancesTick 命令在 PROCESSING 时仍会继续提交。

**后果**：UI 层所有 `:disabled="commandQueue.isLocked"` 在 PROCESSING 时把**所有按钮**置灰（包括 use_item/craft/organize），但 execute() 实际放行这些命令。"UI 看起来禁用了"与"execute 实际放行"语义不一致。结果碰巧正确（后端模式锁兜底拒绝），但机制错误。

**为何之前未被发现**：
- PROCESSING 通常 200-400ms 瞬态（详见 §2.5.3），用户视觉上感知不到"误置灰"
- 后端 `obl_command_allowed_by_state` 在 action='battle' 时拒绝 use_item/craft/organize，所以即使前端放行也会被后端兜底拒绝

#### 2.8.2 修复方案：修正 `isLocked` 语义

`isLocked` **保留**，但**修正语义**为"全局锁"——仅包含"对所有命令都生效的锁"：

```typescript
/**
 * 全局锁：对所有命令都生效的锁
 *
 * 仅包含 HTTP 锁 + 演出锁——这两种锁会阻止所有命令执行。
 * PROCESSING / itm0 / 模式锁是"针对特定命令的锁"，不纳入 isLocked，
 * 应通过 canExecute(command) 查询具体命令是否可执行。
 *
 * 重构后 isLocked 主要用于"全局 UI 反馈"（如全屏遮罩、状态栏指示器），
 * 按钮 :disabled 应改用 canExecute(command) 精细化控制。
 */
get isLocked(): boolean {
  return this._locked || useBattleStore().isPlayingBattleLog;
}
```

**与 v1.2 前的差异**：
- 移除 `oblBattleState === 'PROCESSING'` 判断——PROCESSING 不再纳入 isLocked
- PROCESSING 期间，use_item/craft/organize 按钮不再被 isLocked 置灰
- 但这些按钮会被 `canExecute()` 的模式锁（第 4 层）置灰——因为 PROCESSING 时 action='battle'，模式锁拦截

**不新增语义化 getter**：原 v1.3 设计的 `isHttpLocked` / `isPlayingLog` / `isProcessing` / `isItm0Pending` / `isCoolingDown` 等 5 个 getter 都是对现有 store 状态的简单包装（`battleStore.isPlayingBattleLog` / `playerStore.oblBattleState` 等已存在），增加间接层但无新增价值。UI 需要时直接读对应 store 即可，目的 2（新增按钮时不需要额外判断）也不需要这些 getter——新增按钮时用 `canExecute`，不接触底层 getter。

#### 2.8.3 现有 `isLocked` 调用点迁移策略

§3.2 表格中 28 处 `isLocked` 调用点的迁移规则：

| 调用类型 | 当前代码 | 重构后代码 | 说明 |
|---------|---------|-----------|------|
| 前置判断（17 处） | `if (commandQueue.isLocked) return` | **移除** | 由 `execute()` 内部 `_checkLocks` 拦截 |
| `:disabled` UI 反馈（11 处） | `:disabled="commandQueue.isLocked"` | `:disabled="!commandQueue.canExecute('命令名')"` | 精细化到命令级别 |

**特殊情况**：`pendingNpc` getter（[command-queue.ts L112-114](../../vex-vue/src/stores/command-queue.ts#L112-L114)）保留，用于 [StatusBar.vue L97](../../vex-vue/src/components/layout/StatusBar.vue#L97) 显示"NPC 处理中"指示器、[log.ts L214](../../vex-vue/src/stores/log.ts#L214) 延迟日志刷新——这些是"状态展示"用途，不是"命令拦截"用途。

## 四、实施前置条件

### 4.1 关键设计决策

| # | 决策点 | 推荐答案 | 理由 |
|---|--------|---------|------|
| 1 | `obl_battle_start` 归战斗内还是探索内？ | **前端归战斗内（mode='battle'），后端归探索内** | 前端 `startBattle()` 立即设置 `currentMode='battle'`（用于显示装填区），obl_battle_start 在前端战斗 UI 模式下提交；后端 action 仍为 'normal'，允许执行。两端分类不同但语义自洽：前端按"UI 模式"，后端按"逻辑状态"。详见 §2.6 窗口期边界 |
| 2 | 查询类 API 是否走 commandQueue？ | **不走，不纳入白名单** | `craft_preview` / `player_inventory` / `battle_log` 等查询通过 `dataManager.fetch` 调用 api_v2.php，不修改游戏状态，无需门控。仅命令（command.php 路径）需走白名单 |
| 3 | UI 层是否保留本地 disabled 判断？ | **保留，但改用 `canExecute(command)`** | commandQueue 统一拦截用于"防止非法提交"；UI disabled 用于"按钮置灰反馈"。二者职责不同，前者是保护层，后者是 UX 层。`canExecute` 派生自同一 `COMMAND_REGISTRY`，保证一致 |
| 4 | 战斗演出锁是否独立？ | **保留独立** | `isPlayingBattleLog` 是"演出期间锁"，与"战斗模式"概念不同——演出期间禁止所有命令（含 obl_battle_action），但战斗模式下非演出期间允许 obl_battle_action。两层锁正交，不可合并 |
| 5 | 白名单判断的真值源？ | **以前端 `currentMode` 为准**（已确认） | 前端 UI 反馈需要即时性，不能等待后端 action 同步。窗口期合理性边界见 §2.6.3：前端比后端**早进入**（主动攻击）+ 前端比后端**晚退出**（等 battlelog 播完）都是合理设计；反之则前端处理有 bug，应修正同步逻辑而非迁就后端 |
| 6 | 前端建立白名单的初衷与范围？ | **修正为「UX 反馈与防止未来 UI bug」**（已确认） | 后端已正确拦截 use_item/craft/organize（`obl_command_allowed_by_state` 在 action='battle' 时仅允许 obl_battle_action），不存在语义漏洞。前端建立白名单的目的是：(a) 提供前置 UX 反馈（按钮置灰，避免无谓请求 + 错误日志）；(b) 统一前后端语义边界，防止未来前端 UI bug 导致非法命令提交。保留建立 COMMAND_REGISTRY + canExecute 的核心方向 |
| 7 | PROCESSING 锁是否需要扩展范围？ | **保持现状，仅拦截推进 tick 命令** | 与后端 [C2b] 一致。use_item/craft/organize 已被第 4 层模式锁拦截，PROCESSING 锁无需重复拦截。PROCESSING 实际是瞬态（详见 §2.5 心跳守护进程机制），守护进程 200ms 高频驱动后端 tick 推进，单次 NPC 行动通常在 200-400ms 内完成 |

### 4.2 命令分类边界补充说明

**`obl_battle_start` 的双视角归类**（详见 §2.6.1 路径 A 时序图）：

- 前端 `currentMode='battle'` 是 UI 状态，后端 `action='battle'` 是逻辑状态
- 在 obl_battle_start 提交的窗口期，前端战斗 UI 已显示但后端尚未进入逻辑战斗——这是合理的设计，因为玩家需要装填区才能发起战斗
- 前端白名单按"UI 模式"分类（obl_battle_start 归 battle），后端按"逻辑状态"分类（obl_battle_start 归探索内），两端分类不同但语义自洽
