## 1. 设计目标

本设计案目标是补齐战斗系统的“射程”基础能力，并以【投矛】与【投掷】作为第一组落地样例，为后续图格范围技能（如【爆破拳】）做前置铺垫。

MVP 目标不再采用临时性的 `range_bonus` 单字段模型，而是在现阶段直接完整实现技能射程三维度：

1. `range_mode`：射程计算模式。
2. `range_max`：固定最大射程或最终上限。
3. `range_bonus`：在基础射程上的补正量。

核心目标：

1. 空手攻击不再能攻击任意距离目标，只能攻击 1 格范围内敌人。
2. 新增一种投掷武器：**投矛**。
3. 新增一种攻击技能：**投掷**。
4. 玩家装备投掷武器时可使用【投掷】技能。
5. 【投掷】为单体敌人目标技能，固定最大射程为 4。
6. 敌人默认射程不变，仍只使用空手攻击，射程为 1。
7. 射程不足时，后端通过现有 battle tag / battle log 机制兜底反馈。
8. 前端应尽量提前完成射程非法、目标非法先验，减少非法动作进入后端。

```text
空手攻击可以攻击任意距离的敌人。
```

## 3. 设计原则

### 3.1 现阶段完整实现射程模型

本轮不再把射程做成“暂时只支持 range_bonus”的过渡方案。

原因：

- 射程是战斗技能系统的基础语义；
- 越晚补完整，后续新增技能越可能依赖错误模型；
- 如果先把【投掷】写成 `基础射程 + 3`，以后基础射程被其他技能提高时，【投掷】会被意外放大；
- 如果空手攻击默认继承所有基础射程加成，未来很容易出现“装备远程/长柄/特殊射程加成后，空手也能远距离攻击”的语义污染。

因此现阶段应直接实现：

```text
技能显式声明自己如何计算射程。
```

而不是默认所有技能都走：

```text
actor 基础射程 + skill.range_bonus
```

---

### 3.2 先做单体射程，再做图格范围

【投掷】仍然是单体 PID 目标技能，只是在单体技能上引入射程判断。

它不引入：

- tile target；
- 范围图格；
- 多目标解析；
- 范围动画。

这样可以先打通：

```text
地图距离 → 技能射程 → target tag → 后端兜底日志 → 前端瞄准限制
```

这条链路后，再做【爆破拳】会更稳。

---

### 3.3 道具性质采用 itmk + tag 双维综合判断

道具现在已经通过两个维度控制自己的性质：

1. `itmk`：道具类别，是较强的物理/系统分类。
2. `tags`：道具标签，是可叠加的性质描述。

因此“是否是投掷武器”不应只看一个字段。

推荐判断规则：

```text
如果道具 itmk == WC，则它是投掷武器；
或者，如果道具 tags 包含 tag_weapon_throwing，也可视为投掷武器。
```

这两个维度含义不同：

| 维度 | 含义 | 示例 |
|---|---|---|
| `itmk = WC` | 这个道具类别本身就是投掷武器 | 投矛、飞刀、投斧 |
| `tag_weapon_throwing` | 这个道具虽然属于其他类别，但具备可投掷性质 | 某些锐器、临时投掷物 |

也就是说：

```text
itmk 决定“它是什么类别”；
tag 决定“它还具备哪些性质”。
```

投掷技能的前置条件应使用综合判断，而不是只写死某个 item_id。

---

### 3.4 第一阶段不重构 AP/CD 扣除时机

当前系统在 `battle_verify()` / `skill_act_verify()` 阶段完成：

- 技能存在校验；
- 拥有技能校验；
- CD 校验；
- AP 校验；
- AP 扣除；
- `lstact` 更新。

目标合法性目前在更靠后的 `battle_execute_verify()` 阶段处理。

这确实存在架构上的懒惰点：如果非法目标绕过前端进入后端，理论上可能已经扣除 AP/CD 后才被 `out_of_range` 拦截。

但本设计第一阶段接受这个现实，不优先重构扣费时机，原因是：

1. 前端本应先完成射程非法、目标非法的先验；
2. 后端射程判断主要用于兜底非法前端行为、并保证数据安全；
3. 当前重构 AP/CD 扣除时机会牵涉整个 battle verify / execute 分层，超出本轮目标；
4. 对正常玩家路径，前端会阻止非法动作进入队列，不会触发扣费异常体验。

因此第一阶段策略：

```text
正常路径：前端先验拦截非法目标。
异常路径：后端 out_of_range 兜底拒绝执行，并返回 battle_log。
扣费时机：暂沿用现状，不在本轮重构。
```

后续可作为第二阶段技术债处理：

```text
action target precheck → 通过后再扣 AP/CD → execute
```

---

### 3.5 后端仍然必须是权威

虽然前端会做先验，但后端不能相信前端。

后端必须保证：

- 射程不足的动作不能造成伤害；
- 非法目标不能造成伤害；
- 未装备投掷武器时不能使用【投掷】造成伤害；
- NPC 不应因为前端缺陷或伪造请求获得不应有的远程能力。

---

### 3.6 复核后收口：本轮采用装备技能注入，不保留双方案歧义

复核现有代码后，需要明确一点：`throw` 如果配置为 `lifetime = equipment`，就不适合再作为“所有玩家默认拥有但不可用”的默认技能长期存在。当前 `obl_save_player()` 会调用 `skill_strip_temporary()` 剥离 `lifetime = equipment` 的技能；如果又把 `throw` 加入默认技能注入，就会出现“每次格式化都注入、每次保存又剥离”的循环语义，且 `throw` 的 `lstact`/CD 状态也不适合持久化。

因此本轮执行时采用明确策略：

```text
装备投掷武器 → skill_format_skillpara 阶段临时注入 throw
未装备投掷武器 → skill_list 不返回 throw
伪造请求提交 throw → 后端 verify 仍检查投掷武器并拒绝
保存玩家数据 → skill_strip_temporary 剥离 throw，DB 不持久化装备临时技能
```

也就是说，【投掷】是真正的装备临时技能，而不是默认技能灰显。

前端体验对应调整为：

- 未装备投掷武器时，不显示【投掷】按钮；
- 装备投掷武器后，`skill_list` 返回【投掷】；
- 若未来希望展示“灰色但提示需要投掷武器”的技能，需要另做“可预览但未拥有技能”的 UI/接口，不纳入本轮。
---

### 3.7 复核后补充：具体技能通过模块注册器扩展，不塞进 bootstrap / skill.main

进一步复核后，具体技能逻辑不应直接写入 `skill.main.php`，也不应让 `obl_bootstrap.php` 为每个技能逐条 `require_once`。否则未来技能数量增加后：

- `skill.main.php` 会混入大量具体技能业务；
- `obl_bootstrap.php` 会退化成具体技能清单；
- 新增技能会频繁修改全局加载入口，维护成本持续上升。

因此本轮引入一个轻量的技能模块注册器：

```text
obl_bootstrap.php
  → 只加载 skill.main.php
  → 只加载 skill.modules.php
  → 调用 skill_load_modules()

skill.modules.php
  → 自动扫描/加载 skill/modules/*.skill.php
  → 提供 hook 注册函数

skill/modules/throw.skill.php
  → 保存投掷技能的具体逻辑
  → 注册装备技能注入 hook
  → 提供 throw_verify_check()
```

职责边界：

| 文件 | 职责 |
|---|---|
| `skill.main.php` | 技能系统底层框架、配置读取、通用校验、hook 调度，不包含具体技能业务 |
| `skill.modules.php` | 技能模块加载与 hook 注册/读取 |
| `skill/modules/*.skill.php` | 具体技能逻辑，例如投掷武器判定、装备技能注入、技能 verify 函数 |
| `obl_bootstrap.php` | 统一加载基础系统与模块入口，不逐个加载具体技能 |

模块加载建议采用目录自动发现：

```text
oblivions/include/game/skill/modules/*.skill.php
```

当前技能数量少，全部加载模块的成本可接受；未来如果模块很多，再演进为配置注册表或按需加载。

## 4. 射程三维度设计

当前 `range_bonus` 单字段不足以承载未来技能系统。射程应拆成三个明确维度：

```text
range_mode   = 这个技能如何计算射程
range_max    = 这个技能的固定最大射程或射程上限
range_bonus  = 这个技能对基础射程的补正量
```

这三个字段不是互相替代，而是表达不同语义。

---

### 4.1 第一维：`range_mode`，射程计算模式

`range_mode` 决定技能最终射程如何计算。

建议第一阶段完整支持以下模式：

| range_mode | 公式 | 适用场景 |
|---|---|---|
| `fixed` | `final_range = range_max` | 空手、投掷、枪械、法术、固定距离动作 |
| `inherit` | `final_range = actor_base_range` | 明确继承角色/武器当前基础射程的普通攻击 |
| `additive` | `final_range = actor_base_range + range_bonus` | 突刺、延展攻击、依赖当前武器/身体范围的技能 |
| `capped_additive` | `final_range = min(actor_base_range + range_bonus, range_max)` | 允许加成但需要硬上限的技能 |

#### 为什么必须有 `range_mode`

如果只加 `range_max`，仍然有歧义：

```php
'range_bonus' => 3,
'range_max' => 4,
```

它到底表示：

1. 基础射程 +3，但最多 4？
2. 忽略基础射程，固定 4？
3. 基础射程 +3，同时目标距离不能超过 4？

只有 `range_mode` 能消除歧义。

---

### 4.2 第二维：`range_max`，固定最大射程/上限

`range_max` 表示技能允许的最大射程。

根据 `range_mode` 不同，它有两种语义：

| range_mode | range_max 语义 |
|---|---|
| `fixed` | 技能最终射程就是 `range_max` |
| `capped_additive` | 技能最终射程不能超过 `range_max` |
| `inherit` | 通常不需要 `range_max` |
| `additive` | 通常不需要 `range_max` |

适合使用 `range_max` 的技能：

- 空手攻击：固定 1。
- 投掷：固定 4。
- 枪械：固定或由武器模板决定后的固定值。
- 法术：固定施法距离。
- 爆破拳：如果作为 endpoint 距离，可用 shape length；但更建议走 `target_shape`。

---

### 4.3 第三维：`range_bonus`，射程补正量

`range_bonus` 只表达“在某个基础射程上增加多少”。

它适合：

- 突刺；
- 长柄武器延展技；
- 近战范围强化；
- 当前武器攻击距离 +N；
- 当前身体触及范围 +N。

它不适合表达：

- 投掷固定能打 4 格；
- 空手固定只能打 1 格；
- 枪械固定射程；
- 法术固定施法距离；
- 图格范围技能的范围形状。

因此 `range_bonus` 应被保留，但不能作为所有技能的默认射程机制。

## 5. 基础射程与技能射程的关系

### 5.1 基础射程不等于所有动作的共同射程

`obl_get_range(actor)` 当前返回基础射程 1。这个函数未来可能会受角色状态、武器、被动技能影响。

但必须明确：

```text
actor 基础射程只是一种输入，不代表所有技能都必须继承它。
```

是否继承基础射程，由技能自己的 `range_mode` 决定。

---

### 5.2 空手攻击是否受基础射程加成影响

这是本次设计修订的关键问题。

如果未来玩家通过某种效果把基础射程提高到 3，那么空手攻击是否能打 3 格？

答案取决于该效果的语义：

| 效果语义 | 空手打 3 格是否合理 |
|---|---|
| 手臂变长、身体巨大化、触手化 | 合理 |
| 装备长枪、装备远程武器、投掷技巧强化 | 不合理 |
| 全局所有攻击距离 +2 | 需要谨慎，容易失控 |

所以不能让空手攻击无条件继承 `actor_base_range`。

MVP 推荐：

```text
空手攻击使用 fixed 1。
```

如果以后需要“长臂拳”“巨大化拳击”等效果，应单独做：

```text
unarmed_range_bonus
```

或新增特定技能，而不是污染所有空手攻击。

---

### 5.3 投掷不应使用 `基础射程 + 3`

旧设计曾考虑：

```text
投掷最终射程 = 基础射程 1 + range_bonus 3 = 4
```

但这会导致未来基础射程增加时出现意外：

```text
基础射程变 3
投掷 = 3 + 3 = 6
```

如果设计意图是“投矛投掷距离固定 4”，那么这就是纰漏。

因此修订为：

```text
投掷使用 fixed 4。
```

即：

```php
'range_mode' => 'fixed',
'range_max'  => 4,
```

## 6. 技能配置建议

### 6.1 空手攻击 `unarmed_strike`

建议配置：

```php
'unarmed_strike' => [
    'apcost'        => 1,
    'cd'            => 0,
    'target'        => 'enemy',
    'range_mode'    => 'fixed',
    'range_max'     => 1,
    'lifetime'      => 'permanent',
    'category'      => 'attack',
    'damage_type'   => 'physical',
    'damage_factor' => 1.0,
    'target_rules'  => [
        'forbid' => ['self', 'dead', 'out_of_range'],
    ],
]
```

含义：

```text
空手攻击永远是贴身攻击，射程 1。
```

除非未来明确新增能改变空手攻击距离的特殊效果，否则不应被普通基础射程加成污染。

---

### 6.2 投掷 `throw`

建议配置：

```php
'throw' => [
    'apcost'        => 1,
    'cd'            => 0,
    'target'        => 'enemy',
    'range_mode'    => 'fixed',
    'range_max'     => 4,
    'lifetime'      => 'equipment',
    'category'      => 'attack',
    'damage_type'   => 'physical',
    'damage_factor' => 1.0,
    'target_rules'  => [
        'forbid' => ['self', 'dead', 'out_of_range'],
    ],
]
```

含义：

```text
投掷技能固定最大射程 4，不随 actor 基础射程自动增加。
```

如果未来需要“投掷强化”，应另行设计专门的投掷射程补正，而不是复用通用 actor 基础射程。

---

### 6.3 未来示例：突刺 `thrust`

突刺适合使用 additive：

```php
'thrust' => [
    'target'       => 'enemy',
    'range_mode'   => 'additive',
    'range_bonus'  => 1,
]
```

含义：

```text
在当前基础射程上再延伸 1 格。
```

如果玩家当前武器/身体基础射程为 2，则突刺为 3。

---

### 6.4 未来示例：受限远程强化

```php
'power_throw' => [
    'target'       => 'enemy',
    'range_mode'   => 'capped_additive',
    'range_bonus'  => 3,
    'range_max'    => 6,
]
```

含义：

```text
基础射程 +3，但最高不超过 6。
```

---

### 6.5 爆破拳不使用普通射程字段表达范围

爆破拳属于 tile target / shape resolver 技能，不应只用 `range_max` 或 `range_bonus` 表达。

建议：

```php
'blast_punch' => [
    'target' => 'tile_line',
    'target_shape' => [
        'type' => 'orthogonal_line',
        'length' => 4,
        'include_origin' => false,
    ],
]
```

如果需要限制 endpoint 选择距离，也应该由 `target_shape.length` 或专门的 tile target resolver 处理。

## 7. 射程计算函数设计

### 7.1 新增动作射程计算函数

建议新增函数：

```php
obl_get_action_range(&$actor_data, $act_id)
```

职责：

1. 读取技能配置。
2. 读取 `range_mode`。
3. 根据模式计算最终射程。
4. 返回整数射程。

伪逻辑：

```php
function obl_get_action_range(&$actor_data, $act_id) {
    $config = skill_get_config($act_id);
    $mode = $config['range_mode'] ?? 'fixed';

    $base = obl_get_range($actor_data);
    $bonus = isset($config['range_bonus']) ? (int)$config['range_bonus'] : 0;
    $max = isset($config['range_max']) ? (int)$config['range_max'] : 1;

    switch ($mode) {
        case 'fixed':
            return max(0, $max);
        case 'inherit':
            return max(0, $base);
        case 'additive':
            return max(0, $base + $bonus);
        case 'capped_additive':
            return max(0, min($base + $bonus, $max));
        default:
            return max(0, $max);
    }
}
```

默认模式建议为 `fixed`，默认 `range_max = 1`。

这样老技能即使没有配置射程，也会按近战 1 处理，避免继续出现无限射程。

### 7.2 是否继续保留 `obl_get_range(actor)`


是否使用它，由 `range_mode` 决定。

后续可以进一步拆分为：

```text
obl_get_unarmed_range(actor)
obl_get_weapon_range(actor)
obl_get_global_range_bonus(actor)
```

但本阶段不需要先拆这么细。

## 8. 距离算法

### 8.1 单体战斗技能使用 BFS 图距离

普通单体技能的射程建议使用地图 `neighbors` 关系计算 BFS 距离。

理由：

- 当前移动系统已经基于 `neighbors`；
- 地图可能不是规则矩形；
- 坐标相近不一定代表可达；
- BFS 距离更符合“地图格距离”的现有系统语义。

推荐规则：

```text
distance = obl_get_distance(actor.pgroup, actor.pls, target.pls)

action_range = obl_get_action_range(actor, act_id)

如果 distance <= action_range，则在射程内；
否则 out_of_range。
```

如果双方不在同一区域：

```text
直接 out_of_range。
```

如果无法找到路径：

```text
直接 out_of_range。
```

---

### 8.2 不在本阶段处理弹道/视线

本阶段不引入：

- 直线弹道；
- 障碍遮挡；
- line of sight；
- 抛物线；
- 穿墙/不可穿墙区分。

投掷武器的射程先按 BFS 距离处理。

这与后续【爆破拳】不同：

| 类型 | 目标 | 距离/范围算法 |
|---|---|---|
| 空手攻击 | 敌人 PID | BFS 距离 + fixed 1 |
| 投掷 | 敌人 PID | BFS 距离 + fixed 4 |
| 爆破拳 | 图格 endpoint | 坐标轴直线/shape resolver |

## 9. 后端设计

### 9.1 修改射程判断链路

当前链路：

```text
battle_execute_verify()
  → battle_build_target_tags(actor, target, act_id, cache)
    → battle_tag_out_of_range(actor, target, cache)
      → battle_target_distance_check(actor, target, cache)
```

问题：

- `battle_build_target_tags()` 已经有 `$act_id`。
- 但 `battle_tag_out_of_range()` / `battle_target_distance_check()` 没有接收 `$act_id`。
- 因此当前无法按技能读取 `range_mode`、`range_max`、`range_bonus`。

推荐改为：

```text
battle_execute_verify()
  → battle_build_target_tags(actor, target, act_id, cache)
    → battle_tag_out_of_range(actor, target, act_id, cache)
      → battle_target_distance_check(actor, target, act_id, cache)
```

`battle_target_distance_check()` 应负责：

1. 读取 actor/target 的 `pgroup`、`pls`。
2. 如果不同区域，返回 false。
3. 调 `obl_get_action_range(actor, act_id)` 获取最终射程。
4. 调用 BFS 距离函数。
5. 返回 `distance <= action_range`。

---

### 9.2 技能列表 API 下发射程字段

`skill_get_available_list()` 目前会下发 `range_bonus`。

修订后应下发：

- `range_mode`
- `range_max`
- `range_bonus`
- 可选：`action_range`

建议后端直接下发 `action_range`，前端不需要重复实现完整计算：

```json
{
  "act_id": "throw",
  "range_mode": "fixed",
  "range_max": 4,
  "range_bonus": 0,
  "action_range": 4
}
```

前端仍可保留字段用于展示说明，但实际瞄准最好使用 `action_range`。

---

### 9.3 向后兼容策略

由于旧配置已有 `range_bonus`，实现时需要兼容旧字段。

建议策略：

1. 新配置必须显式写 `range_mode`。
2. 对没有 `range_mode` 的旧技能，默认：

```text
range_mode = fixed
range_max = 1
```

3. 如果旧技能有 `range_bonus > 0` 但没有 `range_mode`，可以临时按旧语义解释为：

```text
range_mode = additive
```

但更推荐在本次改造中直接更新所有现有技能配置，避免隐式规则长期存在。

现有技能建议：

| 技能 | range_mode | range_max | range_bonus |
|---|---|---:|---:|
| `unarmed_strike` | `fixed` | 1 | 0 |
| `escape` | 无需射程或 fixed | 0/1 | 0 |
| `throw` | `fixed` | 4 | 0 |

### 10.1 投掷技能可用性校验


- `wepk`
- `weppara`

- `wep2id`
- `wep2k`
- `wep2para`

### 10.2 投掷武器判定细节

#### 10.2.1 itmk 维度

如果装备槽中的武器类别：

```text
wepk == 'WC'
```

即可视为投掷武器。

#### 10.2.2 tag 维度

如果装备模板 `item_table[wepid].tags` 包含：

```text
tag_weapon_throwing
```

也可视为投掷武器。

#### 10.2.3 综合判断

最终：

```text
is_throwing_weapon = (wepk == 'WC') || item_has_tag(wepid, 'tag_weapon_throwing')
```

这样能支持两类设计：

1. 天然投掷武器：`itmk = WC`。
2. 其他类别但可投掷：如 `itmk = WK` 且带 `tag_weapon_throwing`。

### 10.3 投矛道具模板

```php
'throwing_spear' => [

    'itme'       => 12,
    'itms'       => 10,

```

说明：

- `itmk = WC` 表明它的类别是投掷武器。
- `tag_weapon_throwing` 表明它具备投掷性质。

### 10.4 技能来源：通过技能模块注册装备注入 hook

本轮不再保留“默认拥有但不可用”和“装备注入”两个并行方案，直接采用装备动态注入；同时，具体投掷逻辑不写入 `skill.main.php`，而是放入投掷技能模块。

#### 10.4.1 新增技能模块注册器

新增模块入口文件：

```text
D:\wamp64\www\phpdts\oblivions\include\game\skill\skill.modules.php
```

职责：

1. 维护技能模块 hook 注册表。
2. 提供注册函数，例如：

```php
skill_register_equipment_injector($func)
skill_get_equipment_injectors()
```

3. 自动加载具体技能模块：

```text
D:\wamp64\www\phpdts\oblivions\include\game\skill\modules\*.skill.php
```

4. 不包含任何具体技能判断逻辑。

#### 10.4.2 bootstrap 加载职责

`obl_bootstrap.php` 只加载模块入口，不逐个加载具体技能文件。

推荐顺序：

```text
item.tag.func.php
→ skill.main.php
→ skill.modules.php
→ skill_load_modules()
```

说明：

- `item.tag.func.php` 是道具 tag 数据读取层，具体技能模块可能依赖它。
- `skill.main.php` 是技能底层框架。
- `skill.modules.php` 是模块注册器。
- `skill_load_modules()` 统一加载 `modules/*.skill.php`。
- 不在单独技能文件、verify 文件或 skill.main 内部临时 include 依赖。
- bootstrap 不写 `throw.skill.php` 这种具体技能路径，避免未来技能多时被塞爆。

#### 10.4.3 skill.main.php 的职责

`skill.main.php` 可以提供通用 hook 调度，但不能包含投掷武器判定这类具体逻辑。

例如可新增通用函数：

```php
function skill_inject_equipment(&$skillpara, &$pdata) {
    foreach (skill_get_equipment_injectors() as $func) {
        if (function_exists($func)) {
            $func($skillpara, $pdata);
        }
    }
}
```

这属于通用调度，不知道 `throw`、`WC`、`tag_weapon_throwing` 的具体含义。

#### 10.4.4 投掷技能模块

新增具体技能模块：

```text
D:\wamp64\www\phpdts\oblivions\include\game\skill\modules\throw.skill.php
```

职责：

1. 判断 actor 是否装备投掷武器。
2. 装备投掷武器时注入 `throw`。
3. 提供 `throw_verify_check()` 供通用校验流程调用。
4. 注册自己的装备注入 hook。

示意：

```php
function skill_throw_actor_has_throwing_weapon(&$actor_data): bool {
    $wepk = isset($actor_data['wepk']) ? (string)$actor_data['wepk'] : '';
    $wepid = isset($actor_data['wepid']) ? (string)$actor_data['wepid'] : '';

    if ($wepk === 'WC') return true;
    if ($wepid !== '' && item_has_tag($wepid, 'tag_weapon_throwing')) return true;
    return false;
}

function skill_throw_inject_equipment(&$skillpara, &$pdata): void {
    if (!skill_throw_actor_has_throwing_weapon($pdata)) return;
    if (!isset($skillpara['throw']) || !is_array($skillpara['throw'])) {
        $skillpara['throw'] = ['lstact' => 0];
    }
    if (!isset($skillpara['throw']['lstact'])) {
        $skillpara['throw']['lstact'] = 0;
    }
}

function throw_verify_check(&$actor_data, &$obl_battle_log, &$battle_cache): bool {
    return skill_throw_actor_has_throwing_weapon($actor_data);
}

skill_register_equipment_injector('skill_throw_inject_equipment');
```

#### 10.4.5 注入时机

推荐在 `obl_format_playerdata()` 中：

```text
解析 skillpara
→ skill_format_skillpara 注入永久默认技能
→ skill_inject_equipment 遍历模块注册的装备注入 hook
→ pdata['skillpara'] = skillpara
```

#### 10.4.6 保存规则

`throw` 配置为：

```php
'lifetime' => 'equipment'
```

因此 `obl_save_player()` 中现有 `skill_strip_temporary()` 会在保存前剥离它。DB 不持久化装备临时技能，下一次读取玩家数据时再根据装备重新注入。

#### 10.4.7 verify 机制兼容

当前 `skill_act_verify()` 会尝试加载：

```text
skill/verify/{skill_id}.verify.php
```

引入模块后，建议调整为：

```text
先检查 {act_id}_verify_check() 是否已经由模块提供；
如果不存在，再兼容旧 verify/{act_id}.verify.php；
最后如果函数存在则调用。
```

这样 `throw.skill.php` 可以直接提供 `throw_verify_check()`，无需额外 `verify/throw.verify.php`，具体技能逻辑集中在模块文件中；旧 verify 文件机制仍保留兼容。

#### 10.4.8 CD 状态说明

本轮 `throw.cd = 0`，所以装备临时技能不持久化 `lstact` 没有实际影响。若未来装备技能需要 CD，需要另行设计“装备技能 CD 存放位置”，例如：

- 存入 `oblpara['skill_cd']`；
- 或允许部分 equipment 技能状态持久化；
- 或把 CD 绑定到装备实例 `weppara`。

本轮不处理该扩展。

## 14. 与爆破拳的关系

射程系统和爆破拳有关，但不能完全混用。

| 系统 | 目标类型 | 核心判断 |
|---|---|---|
| 空手攻击 | enemy PID | BFS 距离 <= fixed 1 |
| 投掷 | enemy PID | BFS 距离 <= fixed 4 |
| 爆破拳 | tile endpoint | endpoint 是否在横/纵 4 格直线上 |

射程系统能为爆破拳提供：

- `out_of_range` tag 的经验；
- 前端瞄准合法性高亮的经验；
- battle_log 失败反馈的经验；
- 后端兜底校验的经验；
- 技能配置语义从单字段升级到显式模式的经验。

但爆破拳仍需要独立的 tile target resolver。

## 15. 推荐实施阶段

### 阶段 1：实现射程三维度模型


## 16. 关键决策记录

1. 不再将 `range_bonus` 作为所有技能的默认射程模型。
2. 射程配置采用三维度：`range_mode`、`range_max`、`range_bonus`。
3. 第一阶段完整支持 `fixed`、`inherit`、`additive`、`capped_additive`。
4. 默认基础射程仍为 1，但技能是否继承基础射程由 `range_mode` 决定。
5. 空手攻击使用 `fixed 1`，不默认继承 actor 基础射程。
6. 【投掷】使用 `fixed 4`，不使用 `基础射程 + 3`。
7. `range_bonus` 只用于真正需要“基础射程 + 补正”的技能。
8. `range_max` 在 `fixed` 下表示固定射程，在 `capped_additive` 下表示硬上限。
9. 投掷武器综合判断：`itmk == WC` 或 `tags` 包含 `tag_weapon_throwing`。
10. 投矛建议同时具备 `itmk = WC` 和 `tag_weapon_throwing`。
11. 本轮采用技能模块注册器加载具体技能模块，bootstrap 不逐个加载具体技能。
12. `throw` 的具体逻辑放在 `skill/modules/throw.skill.php`，不放入 `skill.main.php`。
13. 本轮采用装备动态注入 `throw`，未装备时不在 skill_list 显示。
14. 第一阶段不重构 AP/CD 扣除时机，依赖前端先验 + 后端兜底。
15. 单体战斗射程用 BFS 图距离，不做弹道/视线。
16. NPC 第一阶段仍只使用空手攻击，射程为 1。
17. 爆破拳后续仍走独立 tile target resolver，不直接套用普通 PID 射程模型。

## 17. 最小验收用例

### 17.1 射程模型

| 场景 | 预期 |
|---|---|
| `unarmed_strike` 配置为 `fixed 1` | action_range = 1 |
| `throw` 配置为 `fixed 4` | action_range = 4 |
| 某技能配置为 `additive +1`，actor base=2 | action_range = 3 |
| 某技能配置为 `capped_additive +3 max=4`，actor base=3 | action_range = 4 |
| 技能无射程配置 | 默认 fixed 1，不是无限射程 |

---

### 17.2 空手攻击

| 场景 | 预期 |
|---|---|
| 玩家与敌人相邻，使用空手攻击 | 成功造成伤害 |
| 玩家与敌人距离 2，使用空手攻击 | 失败，原因 out_of_range |
| NPC 与玩家相邻，NPC 空手攻击 | 成功造成伤害 |
| NPC 与玩家距离 2，NPC 空手攻击 | 失败，原因 out_of_range |

---

### 17.3 投掷

| 场景 | 预期 |
|---|---|
| 未装备投掷武器 | skill_list 不显示投掷；伪造请求 verify 失败 |
| 装备 itmk=WC 的投矛，使用投掷攻击距离 4 敌人 | 成功造成伤害 |
| 装备带 tag_weapon_throwing 的非 WC 武器，使用投掷 | 成功通过投掷武器判断 |
| 装备普通 WK 锐器但无 tag_weapon_throwing，使用投掷 | 不可用或 verify 失败 |
| 装备投矛，攻击距离 5 敌人 | 失败，原因 out_of_range |
| actor 基础射程被提高到 3，使用投掷 | 仍为 fixed 4，不自动变成 6 |
| actor 基础射程被提高到 3，使用空手攻击 | 仍为 fixed 1，不自动变成 3 |

| 场景 | 预期 |

## 18. 推荐结论

建议将“战斗射程系统 + 投矛/投掷技能”作为【爆破拳】之前的独立小版本，并且本小版本直接完整实现射程三维度模型，而不是继续沿用单一 `range_bonus` 过渡方案。

这个版本的核心价值不是投矛本身，而是建立战斗空间规则的第一条完整链路：

```text
技能射程三维度
→ 武器性质判断
→ 技能可用性
→ 动作最终射程
→ 地图距离
→ out_of_range tag
→ battle_log 反馈
→ 前端瞄准先验
```

打通这条链路后，再实现【爆破拳】的 tile target / line area / multi-target，会更清晰、更安全。
