# 【爆破拳】技能设计研判案

> 状态：信息收集与设计研判完成，尚未进入实现阶段。  
> 保存日期：2026-07-07  
> 范围：Oblivions 后端战斗/技能系统 + vex-vue 前端战斗装填/瞄准/演出系统。

---

## 1. 设计目标

拟设计技能【爆破拳】：

- 这是一个“以图格为单位”的战斗技能。
- 使用后，玩家需要从自己所在格出发，选择横向延伸 4 格或纵向延伸 4 格的目标格。
- 爆破拳对范围图格内的所有敌人单位造成伤害。

这不是单纯新增一条 `skill_config` 的问题。当前项目里的战斗技能基本都是“以 PID 为目标”的单体动作；【爆破拳】首次要求“选择地图格 → 计算范围图格 → 解析范围内多个敌人 → 执行伤害”。因此需要先扩展技能目标模型、前端瞄准模型和后端目标解析模型。

## 2. 当前系统关键发现

### 2.1 地图/图格模型

相关文件：

- `D:\wamp64\www\phpdts\oblivions\DESIGN.md`
- `D:\wamp64\www\phpdts\oblivions\include\game\move.func.php`
- `D:\wamp64\www\phpdts\oblivions\gamedata\tiles\region_*.php`

当前 Oblivions 地图以 `(pgroup, pls)` 唯一确定图格：

- `pgroup`：区域 ID。
- `pls`：区域内局部图格索引。
- 每个图格数据通常包含：`x`、`y`、`neighbors`、`passable`、`floor`、`tide` 等。
- `obl_get_map_data($pgroup)` 可读取区域和图格数据。
- `obl_get_distance()` 当前是基于 `neighbors` 的 BFS 距离，适合移动距离；但爆破拳需求更像“坐标轴直线范围”，不应直接复用 BFS 距离作为核心范围判断。

结论：爆破拳的范围最好基于图格 `x/y` 坐标计算，而不是基于移动邻接距离计算。

### 2.3 当前战斗动作输入模型

相关文件：

- `D:\wamp64\www\phpdts\oblivions\include\command\oblivions_router.php`
- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.entry.php`
- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.main.php`

当前前端提交战斗动作大致为：

```json
[
  { "act_id": "unarmed_strike", "target": 123 }
]
```

`oblivions_parse_actions()` 只是把 POST 中的 JSON 解析为数组，本身可以容纳复杂结构。

但关键阻塞点在 `battle_entry_parse_actions()`：

- 当前会把 `target` 强转为 `(int)`。
- 非正整数目标会被丢弃。
- 因此 `{ type: 'tile_line', pgroup: 1, pls: 10 }` 这类目标结构会在入口处被破坏。

`battle_execute()` 注释上说 target 可以是单个 PID 或 PID 数组，但由于入口解析强制 int，实际上现在前端无法提交非 PID 目标。

结论：爆破拳需要先调整 action target 的数据结构和解析规则，否则无法提交“目标格”。

### 2.4 当前战斗执行模型

相关文件：

- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.main.php`
- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.func.php`
- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.calc.php`
- `D:\wamp64\www\phpdts\oblivions\include\game\skill\skill.main.php`

当前执行流程：

1. `battle_main()`
2. `battle_verify()`
   - 校验技能是否存在、是否拥有、CD、AP。
   - 校验成功后立即扣 AP，并更新 `lstact`。
3. `battle_sort_actions()`
   - 终结技排到最后。
4. `battle_execute()`
   - 把 target 当作 PID 或 PID 数组。
   - 对每个 target 调 `battle_execute_verify()`。
5. `battle_execute_verify()`
   - 根据 PID 获取目标数据。
   - 构建 target tags。
   - 检查 `target_rules`。
6. `battle_once_execute()`
   - emit `once_execute_pre`。
   - 调 `skill_execute()` 执行自定义技能逻辑。
   - 调 `obl_calc_damage()` 计算标准伤害。
   - 调 `battle_apply_damage()` 应用伤害。
   - emit `once_execute_post`。
   - 中段死亡检查。
   - 保存 actor 和 target。

当前 `battle_target_distance_check()` 暂时始终返回 true，尚无真实射程校验。

结论：现有执行管线适合“把一个动作解析成多个 PID 后逐个执行”。爆破拳最稳妥的接入方式，是在执行前新增“tile target → affected target PID array”的解析层，然后复用现有单目标伤害/日志/死亡/队列逻辑。

### 2.5 当前战斗队列与多目标影响

相关文件：

- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.entry.php`
- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.queue.main.php`
- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.queue.func.php`

突袭模式下：

- 战斗开始时 `battle_cache_create()` 默认只把发起者放入 `combatants`。
- 命中的目标会在 `battle_once_execute()` 中 `battle_state_init($target_data)` 并加入战斗状态。
- `battle_state_middle_check()` 会把目标写入 `battle_cache['combatants']`。
- 突袭动作执行后，`battle_queue_setup()` 会从 `combatants` 中取所有存活者来创建先攻队列。

这意味着：如果爆破拳在突袭阶段命中多个敌人，则理论上可以把多个被命中的存活敌人纳入后续先攻队列。

但需要注意：

- 没被爆破拳命中的周边敌人不会自动加入该场战斗，除非另有设计。
- 如果爆破拳一击杀光所有命中敌人，则当前突袭结束逻辑会认为 `ambush_killed_all`。
- 如果目标解析结果为空，当前系统如果已经扣 AP，就可能出现“空放但消耗资源”的情况。这需要设计明确。

结论：多目标后端队列基础有一定承载能力，但需要明确“范围内命中者才入战斗”还是“同区域/同遭遇组敌人都入战斗”。MVP 建议只把实际命中的敌人纳入战斗。

## 3. 核心问题判断

爆破拳引入的是一个新的技能目标范式：

```text
当前范式：技能 → PID 目标 → 单体执行
爆破拳：技能 → 图格端点 → 范围图格 → 多个敌方 PID → 多体执行
```

因此至少需要解决 4 个前置问题：

1. action target 如何表示“目标格”。
2. 后端如何验证目标格是否合法。
3. 后端如何把范围图格解析为敌方单位列表。
4. 前端如何让玩家选择和预览范围图格。

---

## 4. 推荐目标数据结构

建议保持旧技能兼容，同时给 tile 技能引入结构化 target。

### 4.1 旧技能保持不变

```json
{ "act_id": "unarmed_strike", "target": 123 }
```

### 4.2 爆破拳使用结构化 target

建议：

```json
{
  "act_id": "blast_punch",
  "target": {
    "type": "tile_line",
    "pgroup": 1,
    "pls": 37
  }
}
```

其中：

- `type = tile_line` 表示这是一个以端点图格为目标的直线范围技能。
- `pgroup` 为端点所在区域，必须等于 actor 当前 `pgroup`。
- `pls` 为端点图格。

也可以加 `shape` 或 `direction`，但不建议前端直接传 direction 作为可信数据；后端应根据 actor 起点和 endpoint 坐标自行判断方向与范围。

## 5. 推荐技能配置结构

建议在 `skill_config.php` 中为爆破拳增加类似配置：

```php
'blast_punch' => [
    'apcost'        => 2,
    'cd'            => 0,
    'target'        => 'tile_line',
    'range_bonus'   => 0,
    'lifetime'      => 'permanent',
    'category'      => 'attack',
    'damage_type'   => 'physical',
    'damage_factor' => 1.0,
    'target_shape'  => [
        'type'           => 'orthogonal_line',
        'length'         => 4,
        'include_origin' => false,
    ],
    'target_rules'  => [
        'forbid' => ['self', 'dead'],
    ],
]
```

数值如 AP、CD、伤害系数暂未定；这里仅表示结构建议。

建议使用 `target = tile_line` 而不是泛泛的 `tiles`，因为：

- `tiles` 只说明目标是图格，但不说明选择的是端点、中心点还是多个格。
- `tile_line` 更准确表达“玩家选一个端点，后端解析一条线”。

## 6. 后端设计方案

### 6.1 入口解析扩展

需要调整：

- `D:\wamp64\www\phpdts\oblivions\include\game\battle\battle.entry.php`

当前 `battle_entry_parse_actions()` 会把 target 强转 int。需要改为：

- 如果技能配置目标类型是 `self/enemy`，按旧逻辑解析 PID。
- 如果技能配置目标类型是 `tile_line`，保留结构化 target。
- 无效结构直接丢弃并记录错误日志。

注意：入口解析最好基于 `act_id` 查 `skill_get_config()`，不能完全相信前端传入的 `target.type`。

---

### 6.2 目标格验证

建议新增后端 helper，负责验证并计算爆破拳范围。

验证规则建议如下：

1. `target.type` 必须是 `tile_line`。
2. `target.pgroup` 必须等于 actor 当前 `pgroup`。
3. `target.pls` 必须存在于该区域地图数据中。
4. actor 当前 `pls` 必须存在于该区域地图数据中。
5. endpoint 必须与 actor 起点在同一行或同一列。
6. endpoint 与 actor 的坐标距离必须符合技能配置的 `length = 4` 规则。
7. 后端自行计算 line tiles，不信任前端传入的范围列表。

关于“距离规则”存在一个设计歧义：

- 解释 A：必须选择正好第 4 格作为端点。
- 解释 B：可以选择 1~4 格内任意端点。

需求原文是“横向延申4格或纵向延申4格的目标格”，更像“端点正好 4 格”。但从操作手感看，允许 1~4 格可能更灵活。建议在正式实现前确认。

---

### 6.3 范围图格计算

建议后端根据 actor 起点和 endpoint 坐标计算：

```text
actor tile: (x0, y0)
endpoint:   (x1, y1)

合法条件：
- x0 == x1 且 abs(y1 - y0) == 4
  或
- y0 == y1 且 abs(x1 - x0) == 4
```

然后沿方向生成图格坐标：

```text
不含自身格：step = 1..4
含自身格：step = 0..4
```

建议 MVP：

- `include_origin = false`
- 即爆破拳影响从相邻格到端点的 4 个格，不伤害自己所在格。

如果地图是稀疏/不规则坐标，某些中间坐标可能没有图格。建议规则：

- endpoint 必须是存在图格。
- 中间缺失图格时，该缺失坐标不产生图格。
- 是否因中间缺失而判定整条线非法，需要设计选择。

MVP 建议：

- 仅收集实际存在的图格；不因缺格失败。
- 但若 endpoint 不存在，则失败。

---

### 6.4 障碍、通行、迷雾、发现规则

这些是需要产品确认的开放点。

建议 MVP 默认：

- 爆破拳范围按坐标直线计算，不受 `passable` 阻挡。
- 只允许选择前端当前可见/已渲染的图格作为 endpoint。
- 后端只要求图格存在，不依赖前端的可见性。
- 命中范围内所有存活敌人，不以是否 discovered 作为后端硬限制。

备选规则：

- 如果希望“不能隔墙爆破”，需要引入 line-of-effect 阻挡规则，检查中间图格 `passable` 或新增 `blocks_skill` 字段。
- 如果希望“只能打已发现敌人”，后端解析敌人时要加 `discovered=1` 条件。

---

### 6.5 解析受影响敌人

建议新增 resolver：

```text
blast_punch target payload
→ validate endpoint
→ compute affected pls list
→ query living enemies in same pgroup and affected pls
→ return target pid array
```

“敌人单位”的判定需要注意 actor 阵营：

- 当前玩家 `type = 0`，NPC 敌人 `type > 0`。
- 如果爆破拳仅玩家使用，则敌人可简单定义为 `type > 0`。
- 如果 NPC 也能使用，则应定义通用敌对关系：actor type 0 打 type > 0；actor type > 0 打 type 0 或敌对阵营。

MVP 建议：

- 先作为玩家技能，只命中 `type > 0`、`state = 0`、同 `pgroup`、`pls in affected_pls` 的单位。

---

### 6.6 与现有 battle_execute 的接入方式

推荐方式：在 `battle_execute()` 执行每个 action 前先解析 target。

伪流程：

```text
foreach action:
    if actor cannot act: continue

    resolvedTargets = battle_resolve_action_targets(actor, action, battle_cache)

    foreach resolvedTargets as targetPid:
        battle_execute_verify(actor, act_id, targetPid)
        battle_once_execute(actor, act_id, targetData)
```

对于旧技能：

```text
resolvedTargets = [原 PID]
```

对于爆破拳：

```text
resolvedTargets = 范围内所有敌人 PID
```

优点：

- 复用现有伤害计算。
- 复用现有死亡检查。
- 复用现有日志 pre/post 配对。
- 复用现有突袭后补票队列逻辑。
- 避免在 `blast_punch.calc.php` 里手写整套多目标伤害，降低风险。

---

### 6.7 空命中时是否消耗 AP/CD

当前系统在 `battle_verify()` 阶段只校验技能自身，并立即扣 AP、更新 CD；目标有效性在后面的 execute verify 才处理。

爆破拳会引出一个问题：

- endpoint 合法但范围内无敌人：是否消耗 AP/CD？
- endpoint 非法：是否消耗 AP/CD？

建议：

- endpoint 非法：动作无效，不消耗 AP/CD。
- endpoint 合法但范围内无敌人：技能成功释放，消耗 AP/CD，但记录“未命中任何目标”。

为了实现“非法 endpoint 不消耗 AP/CD”，target payload 的基础验证必须前置到 `battle_verify()` 之前或 `skill_act_verify()` 之内。否则会出现先扣 AP 再发现 endpoint 非法的问题。

可选实现：

1. 在 `battle_verify()` 中对每个 action 调用新的 `battle_action_target_precheck()`，通过后再 `battle_act_verify()` 扣 AP。
2. 或在 `skill_act_verify()` 的自定义 verify 文件中读取当前 action target，但当前签名没有传 action target，需要改签名，不推荐作为第一选择。

推荐第 1 种：给 battle 层增加通用 action target precheck。

## 7. 前端设计方案

### 7.1 类型扩展

需要调整：

- `D:\wamp64\www\phpdts\vex-vue\src\types\api.ts`
- `D:\wamp64\www\phpdts\vex-vue\src\components\battle\PreloadArea.vue`

```ts
type SkillTargetType = 'self' | 'enemy' | 'tile_line';
```

### 7.2 装填逻辑扩展

`PreloadArea.vue` 当前把非 self 全部当 enemy。需要改为按 `skill.target` 分流：

```text
self      → target = playerPid
enemy     → enemyPid 或敌人格瞄准
tile_line → 进入图格瞄准模式
```

爆破拳应始终进入 tile aim mode，而不是自动使用当前 `enemyPid`。

---

### 7.3 图格瞄准模式

当前 `AimMode.vue` 只支持 `[data-enemy-pid]`。建议扩展为通用 aim mode，或新增组件，例如 `TileAimMode.vue`。

MVP 功能：

- 从玩家当前格读取起点。
- 基于 mapStore / useMapRender 数据计算四个方向的候选 endpoint。
- endpoint 满足同 x 或同 y，距离为 4 或 1~4（待定）。
- 给候选 endpoint 加高亮。
- 鼠标悬停 endpoint 时，高亮整条影响线。
- 点击 endpoint 后广播：

```ts
battle:aim-target-selected
{
  target: {
    type: 'tile_line',
    pgroup,
    pls
  }
}
```

也可以复用原事件，但 payload 需要兼容 PID 和 tile target。

---

### 7.4 范围预览

前端应该只用于展示和交互，不作为可信来源。

建议：

- 前端根据当前地图数据计算 line cells 并高亮。
- 后端收到 endpoint 后重新计算范围。
- 前后端共用同样的规则描述，例如 `target_shape` 从后端下发，避免写死 4。

当前 `skill_get_available_list()` 尚未下发 `target_shape`。如果希望前端通用化，需要把 `target_shape` 或类似字段加入技能列表 API。

MVP 也可以先在前端对 `blast_punch` 写死 4 格，但长期不推荐。

### 7.5 队列显示

当前队列显示假设 target 是 PID，会调用 `getTargetDisplayText(targetPid)`。

需要改为：

## 9. 需要确认的设计问题

实现前建议确认以下规则：

1. **端点距离**：必须正好 4 格，还是 1~4 格都可？
2. **是否包含自身格**：爆破范围是否包含玩家所在格？建议不包含。
3. **地图缺格**：如果中间坐标没有图格，技能是跳过缺格，还是整条线非法？
4. **障碍阻挡**：`passable = false` 的图格是否阻挡爆破？
5. **迷雾限制**：是否允许选择未发现/迷雾中的 endpoint？
6. **隐藏敌人**：范围内未 discovered 的敌人是否会被命中？
7. **空命中**：合法释放但范围内无敌人时是否消耗 AP/CD？建议消耗。
8. **参战范围**：突袭时，只有被命中的敌人加入战斗，还是范围外同组敌人也加入？建议 MVP 只加入命中者。
9. **NPC 使用**：爆破拳是否只给玩家，还是 NPC 也可能拥有？MVP 建议只给玩家。
10. **伤害数值**：AP、CD、damage_factor 是否要比普通攻击更高/更低？

## 10. 风险与注意事项

### 10.1 最大风险：目标模型变更影响旧技能

`battle_entry_parse_actions()` 是战斗入口关键函数。改它时必须保证旧格式：

```json
{ "act_id": "unarmed_strike", "target": 123 }
```

完全兼容。

---

### 10.2 AP/CD 扣除时机

当前技能验证通过即扣 AP/CD。如果 tile target 合法性校验放得太晚，会导致非法动作也消耗资源。

建议先做 target precheck，再扣 AP。

---

### 10.3 前后端范围规则必须一致

前端高亮只是预览，后端才是权威。但如果两边规则不一致，会造成玩家“看起来能打到，实际没打到”的体验问题。

建议把 `target_shape` 从后端下发给前端，减少硬编码。

---

### 10.4 多目标演出目前只是“能播放”，不是“表现好”

用现有 pre/post 日志，每个命中目标都会形成一个 action。这样能快速打通，但视觉上是多次单体攻击，不是真正的范围冲击波。

这可以作为 MVP 接受，后续再补范围动画。

---

## 11. 推荐结论

【爆破拳】建议作为“tile_line 目标类型”的首个落地技能来做。不要把它写成特殊硬编码技能，否则后续所有范围技能都会重复踩坑。

推荐最小可行路线：

1. 引入 `target = tile_line` 和结构化 target payload。
2. 后端验证 endpoint 并计算 orthogonal line tiles。
3. 后端把范围内敌人解析为 PID 数组。
4. 复用现有 `battle_once_execute()` 对每个 PID 逐个结算。
5. 前端新增 tile aim/highlight，让玩家选择端点。
6. 前端增加基础文案和攻击动作白名单。
7. 范围动画、多敌人 HP 面板、NPC 使用策略后置。

这样可以在不大幅重写战斗核心的前提下，把项目从“PID 单体技能系统”推进到“图格范围技能系统”。
