# 逐目标结算与动态参战框架重构设计案

> 状态：逐目标结算与动态参战主体已完成实现与验收（2026-07-11）。实时演出交付、F5 与双投影语义以 [`战斗演出事件消费与权威投影解耦研判.md`](./战斗演出事件消费与权威投影解耦研判.md) 为后续基准；本文中与其冲突的旧 live battlelog 描述不再适用。
>
> 本设计案以原始战斗规则中的“多目标按 1v1v1v1 依次结算”和“战中加入者排当前先攻队列末尾”为框架基准，重新设计动态参战与前端自由瞄准。
>
> 本文替代 [`CharacterHub与动态参战统一设计案.md`](./CharacterHub与动态参战统一设计案.md) 中关于 ImpactBatch、AOE 成员批量原子性、action-scoped roster batch 和动态参战前置基础设施的设计。旧文关于 CharacterHub 不是后端真值、宽松战斗工作区、自由选择 PID、空演出事件集合不代表战斗结束等结论继续有效。

## 1. 决策摘要

### 1.1 框架基准

目标系统先完成选择对象与结算单位的正式分离：

```text
AimIntent（客户端选择）
→ AimResolver
→ ResolvedAim（后端权威瞄准对象）
→ ResolutionTargetCapturer
→ CapturedResolutionTargetSet
→ 有序 TargetResolutionUnit[]
```

多目标动作不是一次处理一个目标集合，而是：

```text
动作解析
→ 生成有序目标列表
→ 对目标 A 执行完整单目标结算
→ 对目标 B 执行完整单目标结算
→ 对目标 C 执行完整单目标结算
→ 动作结束
```

每个单目标结算单元完整包含：

```text
目标规则
→ Participation 判断
→ 必要时加入战场
→ snapshot_target_state
→ 技能效果
→ reaction
→ 死亡/逃跑检查
→ 保存当前目标
→ 记录当前目标事件
```

### 1.2 动态参战基准

当一个动作实际结算到尚未参战的合法敌人时：

```text
target.action = 'battle'
target.bid = current qid
INSERT queue(active=1, done=0, myorder=tail)
更新 battle_cache
emit combatant_joined
然后结算该目标效果
```

新成员：

- 不重新投掷先攻；
- 不改变已有成员顺位；
- 固定追加在当前队列末尾；
- `done=0`，不会打断当前行动者，但会在当前轮剩余顺位中获得行动机会；
- 不允许从其他 qid 抢队；
- 如果同一目标单元最终未执行，不得加入战场。

### 1.3 明确删除的旧设计

不再采用：

- 先构造整项动作的 `impact_entities` 批次再统一结算；
- 一个 AOE 中任一目标失败就让整个动作失败；
- 同一动作的所有 joinable 目标全部加入或全部不加入；
- action-scoped roster mutation batch；
- 为动态参战专门建立复杂的 action UnitOfWork/checkpoint；
- 把 event outbox、qid 永不复用、全局 domain revision、完整前端 Store 重构作为动态参战前置条件。

请求级数据库事务仍然保留，用于处理 SQL 或进程异常；它不改变“业务上逐目标成功或失败”的语义。

## 2. 设计依据与当前实现

### 2.1 原始规则已经给出答案

原始战斗设定明确规定：

- 初始 1vN 由所有初始参战者生成先攻队列；
- 战斗中闯入的新角色固定排到队列末位；
- AOE 对多个目标造成伤害时，多个目标按先攻队列顺序依次进入防守与反应流程；
- 当前行动者打完动作链后才结束先攻轮和推进游戏刻。

参考：

- [`战斗设定.txt:27`](./原始方案/战斗设定.txt#L27)
- [`战斗设定.txt:29`](./原始方案/战斗设定.txt#L29)
- [`战斗设定.txt:50`](./原始方案/战斗设定.txt#L50)
- [`战斗设定.txt:60`](./原始方案/战斗设定.txt#L60)
- [`战斗设定.txt:68`](./原始方案/战斗设定.txt#L68)

因此，逐目标完整结算不是特殊兼容逻辑，而是战斗系统必须具备的底层能力。

### 2.2 重构前管道不是真正的 per-target

重构前注释把以下阶段称为 per-target（本节行号为实现前审查快照）：

- [`combat.pipeline.php:24`](../include/game/combat/combat.pipeline.php#L24)

但实际执行顺序是：

```text
check_rules(A, B, C)
→ snapshot(A, B, C)
→ execute(A, B, C)
→ resolve_effects(A, B, C)
→ post_check(A, B, C)
→ persist(A, B, C)
```

参考：

- [`combat.pipeline.php:73`](../include/game/combat/combat.pipeline.php#L73)
- [`combat.pipeline.php:140`](../include/game/combat/combat.pipeline.php#L140)
- [`combat.pipeline.php:173`](../include/game/combat/combat.pipeline.php#L173)
- [`combat.pipeline.php:270`](../include/game/combat/combat.pipeline.php#L270)

这种“阶段优先”结构无法自然表达：

- 目标 A 受击后立即反应，再轮到目标 B；
- 目标 A 动态加入后，后续动作读取到新的 roster；
- 目标 A 成功、目标 B 被拒绝、目标 C 继续执行；
- 每个目标在自身效果后独立保存和清理。

### 2.3 重构前目标解析器已经证明可以返回多目标

`target='all'` 已经会展开为多个独立 `target_data`：

- [`combat.target.php:169`](../include/game/combat/combat.target.php#L169)

因此无需新建 ImpactBatch。现有能力应拆成 AimResolver 与 ResolutionTargetCapturer，再把消费方式从“多个阶段分别遍历 targets”改成“一个循环逐个运行完整目标管道”。

### 2.4 重构前 grenade 绕过了目标框架

重构前 grenade 先解析 tile，再在技能 hook 中自行查询 tile 内所有 PID，并通过 `target_pid` 声明跨目标 damage：

- [`skill_grenade.php:15`](../gamedata/combat_skills/skill_grenade.php#L15)

这使真正受伤的角色没有成为 `CombatContext.targets` 中的当前目标，进而绕过：

- 角色规则标签；
- Participation；
- 单目标 snapshot；
- 单目标 reaction；
- 单目标 persist。

grenade 必须改为“tile 只负责 ResolvedAim，ResolutionTargetCapturer 负责把 tile occupants 捕获为多个角色结算单位”。技能 hook 只处理当前角色目标。

### 2.5 队列调度原有能力支持末尾新成员行动

重构前 join 已会把新成员排尾并设置 `done=0`，本次保留这项调度语义：

- [`battle.queue.func.php:217`](../include/game/battle/battle.queue.func.php#L217)

当前行动结束后，`battle_manage_queue()` 会：

1. 把当前 actor 排除出未行动集合；
2. 保留其他 `done=0 && active=1` 行；
3. 只有未行动集合为空时才重建队列；
4. 从未行动集合首行选择下一行动者。

参考：

- [`battle.queue.main.php:184`](../include/game/battle/battle.queue.main.php#L184)
- [`battle.queue.main.php:216`](../include/game/battle/battle.queue.main.php#L216)
- [`battle.queue.main.php:229`](../include/game/battle/battle.queue.main.php#L229)

所以无需重写回合调度。只需保证动态加入发生在 `battle_manage_queue()` 前，且新增行保持 `done=0`。

### 2.6 重构前 join 原语不安全

重构前 `battle_queue_join()` 会先删除 PID 的旧队列行：

- [`battle.queue.func.php:225`](../include/game/battle/battle.queue.func.php#L225)

这会把其他 qid 的成员直接抢入当前战场。新框架必须删除这种“先删除再插入”的接口，改为 Participation 已验证后的安全追加。

### 2.7 重构前 `battle.start` 提前吸收整条动作链目标

重构前初始建战会从整条动作链提取所有 enemy PID，再一次建队：

- [`combat.core.php:267`](../include/game/combat/combat.core.php#L267)
- [`combat.core.php:285`](../include/game/combat/combat.core.php#L285)

这会让后续动作才首次接触的 NPC 提前参与初始先攻。正确语义是：

- 第一项成功 hostile action 的合法目标组成 initial roster；
- 后续动作首次接触的 NPC 按动态参战规则排尾。

## 3. 目标与非目标

### 3.1 本设计必须完成

1. AimResolver 与 ResolutionTargetCapturer 正式分离玩家选择和实际结算单位。
2. 框架按目标逐个完整结算，而不是按阶段批量遍历目标。
3. direct/all/tile AOE 共用同一个 TargetResolutionUnit。
4. 动态参战是 TargetResolutionUnit 中的标准 Participation 阶段。
5. 新成员排尾、`done=0`、不重投先攻。
6. 单个目标失败不影响同动作其他目标。
7. 初始建战只吸收第一项成功 hostile action 的合法角色结算单位。
8. 前端 in-battle enemy 技能始终允许玩家重新选择目标。
9. member 与 joinable 都可以成为 enemy 技能候选，最终合法性由后端重校验。
10. verify/project 与 execute 使用同一套 Aim/Capture/TargetResolutionUnit/Participation 语义；已有战场使用同一 queue order。

### 3.2 本设计不要求同时完成

- battle event 文件存储迁移到数据库 outbox；
- qid 全局永久身份重构；
- State API 全 scope revision；
- CombatDraftStore 全量重构；
- 完整反击、防守策略和递归 AOE；
- 战场合并；
- 多玩家并发输入。

这些内容可以独立演进，不能阻塞逐目标框架与动态参战落地。

## 4. 新的领域模型

### 4.1 ActionExecution

表示一个技能或道具动作的执行上下文：

```php
final class CombatActionExecution
{
    public array $actor_data;
    public string $act_id;
    public array $config;
    public array $battle_cache;
    public array $resolved_aim;
    public array $captured_target_set;
    public array $resolution_targets;
    public array $target_results;
    public int $ap_cost;
    public bool $action_started;
    public bool $any_target_resolved;
    public bool $dry_run;
}
```

动作级状态只保存：

- actor；
- 技能配置；
- AP/CD；
- 后端已经解释完成的瞄准对象；
- 有序目标列表；
- 各目标结果；
- action_start/action_end 状态。

它不保存批量 membership mutation。

### 4.2 AimIntent 与 ResolvedAim

`AimIntent` 是客户端提交的、不可信的玩家选择：

```php
[
    'type' => 'pid|tile|self|none',
    'id' => 1005,
]
```

`AimResolver` 根据技能配置把 AimIntent 解释为后端权威 `ResolvedAim`：

```php
[
    'kind' => 'character|tile|self|none',
    'pid' => 0,
    'pgroup' => 1,
    'pls' => 1005,
    'source_intent' => ['type' => 'tile', 'id' => 1005],
]
```

AimResolver 只负责：

- 校验 intent 类型与技能声明一致；
- 从后端状态解析真实 PID、pgroup、pls；
- 校验瞄准层射程、可达性和图格合法性；
- 生成 action_start、投射物和图格演出需要的权威瞄准信息。

AimResolver 不枚举图格 occupants，不判断 Participation，也不产生 damage targets。

正式接口：

```php
function combat_aim_resolve(
    CombatActionExecution $action,
    array $aim_intent
): array; // ResolvedAim，失败抛/返回 AIM_* reason
```

### 4.3 CapturedResolutionTargetSet

`ResolutionTargetCapturer` 接收 ResolvedAim，在该动作真正执行到达时捕获一次有序结算单位集合：

```php
[
    'resolved_aim' => $resolved_aim,
    'captured_at' => [
        'tick' => 30,
        'action_index' => 2,
    ],
    'targets' => [$resolution_target_a, $resolution_target_b],
    'empty' => false,
]
```

Capturer 负责“选择对象到结算对象”的正式脱离：

- 使用当前动作时刻的后端权威状态；
- 校验捕获器是否允许输出该类实体；
- 对 PID 去重；
- 生成稳定顺序；
- 保存空间捕获事实；
- 一次捕获后固定本动作的 ResolutionTarget 列表。

Capturer 不提前吞掉死亡、免疫、关系、Participation 等单体业务结果；这些仍由各 TargetResolutionUnit 独立判断。

正式接口：

```php
function combat_capture_resolution_targets(
    CombatActionExecution $action,
    array $resolved_aim
): array; // CapturedResolutionTargetSet
```

Capturer registry 的返回值必须经过统一结构校验器；技能模块只能选择已注册 Capturer，不能直接返回未校验的任意 PID 数组。本阶段生产配置只使用 `direct_character`、`battle_hostiles`、`tile_characters`、`identity` 四个内置 Capturer。

结构校验不足以证明角色来自权威图格 occupant 集合。内置 Capturer 必须由框架内核执行权威查询并直接生成候选集；技能配置只能选择 Capturer、关系、排序和规则，不能注入或替换 PID。统一校验器还会按内置 resolver 检查 PID、entity reference、ResolvedAim 和 tile capture facts 的一致性，并拒绝重复 PID、错误 kind 与伪造图格来源。若未来开放新的扩展 Capturer，必须同时注册其 authoritative candidate provenance 校验，不能只注册一个返回任意 PID 的 callable。

### 4.4 ResolutionTarget

Capturer 输出的统一结算单位：

```php
[
    'kind' => 'character|tile|self|none',
    'pid' => 12,
    'entity_ref' => ['pid' => 12],
    'capture_facts' => [
        'pgroup' => 1,
        'pls' => 1005,
    ],
    'order_key' => [3, 12],
]
```

约束：

- 角色效果必须以 `kind='character'` 的具体角色为当前结算单位；
- tile 伤害技能不能把 tile pseudo target 直接交给 damage applier；
- self/none/战斗移动可以继续捕获 pseudo resolution target；
- 同一动作中 PID 去重，保留 Capturer 确定的顺序；
- ResolvedAim 始终保留在 ActionExecution 中，不能在转换为角色后丢失。

ResolutionTarget 冻结的是结算身份与 capture facts，不是角色属性副本。轮到该单位时，`bind current target` 必须从 actor/battle_cache/本命令内存状态取得最新 `target_data` 引用；前序目标或 reaction 已经修改的状态必须可见。

### 4.5 TargetResolutionUnit

TargetResolutionUnit 是框架最小业务结算单元：

```php
final class CombatTargetResolutionUnit
{
    public array $target;
    public array $tags = [];
    public array $participation = [];
    public array $effects = [];
    public ?array $target_state_snapshot = null;
    public ?array $result = null;
    public bool $executable = false;
}
```

它必须独立完成：

```text
rules
→ participation classification
→ pure effect declaration
→ enlist if needed
→ snapshot_target_state
→ apply effects
→ react
→ post_check
→ persist target
→ emit target events
```

真实执行时，每个 TargetResolutionUnit 在 Participation enlist 前建立数据库 SAVEPOINT，并同步记录 actor/battle cache/current target 与 BattleLogCollector checkpoint。该单元在 enlist 或 effect 阶段发生可恢复业务失败时，回滚到本目标 SAVEPOINT、恢复内存状态并丢弃该目标暂存事件，然后继续后续目标；成功后释放 SAVEPOINT。这个机制只保证单个目标的原子性，不是 action-scoped roster batch，也不改变 SQL/PHP 基础设施异常必须回滚整条 command/heartbeat 的请求级事务语义。

`snapshot_target_state` 只保存当前结算单位受效果前的状态：

- character/self：角色 HP/AP/位置/状态；
- tile move：actor 移动前状态以及 ResolvedAim 的目标图格；
- none utility：该效果实际修改的 actor 状态。

它不负责捕获或改变 ResolutionTarget 列表。

### 4.6 ParticipationDecision

```text
member
  已是当前 qid 的 active 成员，可以直接结算

joinable
  当前没有战斗归属，可以在本目标单元中加入当前 qid

left
  当前 qid 中 active=0 的历史成员，本场不得重新加入

other_battle
  属于其他 qid，当前目标单元失败

blocked
  死亡、逃跑、非敌对、跨区域、未发现或数据不一致

not_applicable
  self/none/tile utility，不涉及角色入列
```

### 4.7 TargetResolutionResult

```php
[
    'pid' => 12,
    'status' => 'resolved|skipped|actor_terminated',
    'reason' => null,
    'participation' => 'member|joined|rejected|not_applicable',
    'effects' => [],
]
```

单个目标的 `skipped` 不会让其他 ResolutionTarget 回滚。动作最终是否失败由技能的 `empty_policy` 和是否存在成功 TargetResolutionUnit 共同决定。

## 5. 技能目标配置

### 5.1 Aim Resolution 与 Resolution Target Capture 分离

保留玩家瞄准对象和真正结算对象的区别，但不引入 ImpactBatch：

```php
'aim' => [
    'resolver' => 'pid|tile|self|none',
    'rules' => [],
],
'capture' => [
    'resolver' => 'direct_character|battle_hostiles|tile_characters|identity',
    'relation' => 'hostile|friendly|any|self',
    'participation' => 'join_if_unengaged|members_only|none',
    'order' => 'single|queue|queue_then_pid|pid',
    'rules' => [],
],
'execution' => [
    'empty_policy' => 'fail|execute',
],
'delivery' => [
    'types' => [], // string[]，按播放顺序填写 projectile_to_tile / explosion_at_tile 等 cue
],
```

`aim.resolver + aim.rules` 由 AimResolver registry 消费，生成 ResolvedAim。

`capture.resolver` 由 ResolutionTargetCapturer registry 消费，生成 CapturedResolutionTargetSet。

`capture.rules` 对捕获后的每个具体 ResolutionTarget 单独校验死亡、逃跑、关系、距离和其他角色标签。

`delivery.types` 是有序的动作级投送描述数组，只消费 ResolvedAim 并依次生成语义事件/演出计划，不直接修改任意角色。无独立投送时使用 `types=[]`；同一动作可以声明多个 cue，例如 grenade 先投射到图格，再在图格爆炸。

`execution.empty_policy` 是动作成立策略，不属于 Capturer：

```text
fail
  没有成功 ResolutionTarget 时动作失败，不消费 AP/CD

execute
  ResolvedAim 合法即可完成动作投送和消费资源；ResolutionTarget 可以为空或全部 skipped
```

错误归属固定为：

```text
AimResolver
  AIM_TYPE_MISMATCH / AIM_NOT_FOUND / AIM_OUT_OF_RANGE / AIM_UNREACHABLE
  → 动作级失败，不运行 Capturer

ResolutionTargetCapturer
  CAPTURE_RESOLVER_NOT_FOUND / CAPTURE_INVALID_OUTPUT
  → 技能配置或基础设施失败，动作不执行

TargetResolutionUnit
  TARGET_DEAD / TARGET_IMMUNE / TARGET_IN_OTHER_BATTLE / ...
  → 当前结算单位 skipped，其他单位继续
```

```php
    'capture' => [
        'resolver' => 'tile_characters',
        'relation' => 'hostile',
        'participation' => 'join_if_unengaged',
        'order' => 'queue_then_pid',
        'rules' => ['self', 'dead', 'escaped'],
    ],
    'execution' => ['empty_policy' => 'execute'],
    'delivery' => ['types' => ['projectile_to_tile', 'explosion_at_tile']],
]
```

移动：

```php
'move' => [
    'pipeline' => 'utility',
    'aim' => [
        'resolver' => 'tile',
        'rules' => ['tile_impassable', 'tile_occupied', 'tile_unreachable', 'tile_out_of_range'],
    ],
    'capture' => [
        'resolver' => 'identity',
        'relation' => 'any',
        'participation' => 'none',
        'order' => 'single',
        'rules' => [],
    ],
    'execution' => ['empty_policy' => 'fail'],
    'delivery' => ['types' => []],
]
```

### 5.3 目标排序

ResolutionTargetCapturer 捕获后必须稳定排序：

```text
single
  唯一目标

queue
  按当前 qid 的 myorder

queue_then_pid
  当前 qid 成员按 myorder
  → 非成员按 PID 升序

pid
  PID 升序
```

规则：

- `all/battle_hostiles` 只枚举当前 qid active 成员并按队列顺序；
- `tile_characters` 先列出当前战场成员，再列出未参战角色；
- 同一动作动态加入多个角色时，它们按 Capturer 输出顺序依次追加到队尾；
- 新成员加入后，不重新排序当前动作已经生成的目标列表；
- 后续动作重新解析目标，因此可以看到新的 roster 和目标状态。

### 5.4 捕获时机与冻结语义

CapturedResolutionTargetSet 在动作链真正执行到该动作时生成：

```text
Action 1 move
→ actor 位置变化
Action 2 grenade
→ 按移动后的世界状态运行 AimResolver
→ 捕获此刻目标图格内的角色
```

对当前瞬时技能，捕获完成后本动作的目标集合固定：

- 处理目标 A 时发生的位移不会让后来进入图格的 D 被同一次 grenade 命中；
- B 在轮到自身前被 reaction 位移，也不会抹除“爆炸捕获时 B 位于范围内”的空间事实；
- B 的当前生存、免疫、Participation 和其他实时角色状态仍在自身 TargetResolutionUnit 中重校验；
- 后续动作重新运行 Capturer，不复用前一动作的集合。

持续区域、延迟投射物等需要在未来定义新的 capture timing；本阶段所有已有技能统一在 `action_execute` 时捕获，不提前增加时机配置。

### 5.5 两类图格技能

```text
战斗移动
  AimIntent: tile
  ResolvedAim: authoritative tile
  Capturer: identity
  ResolutionTarget: tile pseudo target
  snapshot_target_state: actor before move

手雷
  AimIntent: tile
  ResolvedAim: authoritative tile
  Capturer: tile_characters
  ResolutionTarget: zero or more characters
  snapshot_target_state: each character before damage
```

手雷即使捕获到空集合，也可以按 `empty_policy='execute'` 完成投掷、爆炸和资源消费；是否允许空图格投掷是技能配置，不是 TargetResolutionUnit 的全局规则。

## 6. 逐目标管道

### 6.1 动作级流程

```text
load/validate skill
→ validate ownership and CD
→ AimResolver: resolve and validate ResolvedAim
→ ResolutionTargetCapturer: capture ordered ResolutionTargetSet
→ evaluate empty_policy
→ calculate action AP cost
→ reserve AP once in ActionExecution
→ emit action_start / action delivery when action becomes executable
→ for each ResolutionTarget: resolve TargetResolutionUnit
→ finalize by empty_policy and target results
→ emit action_end
```

动作级 AP/CD 不能按目标重复扣除。

本设计不改变动作链 wallet 的总体语义，只规定一个多目标动作无论命中几个目标都只消费一次该动作的 AP/CD。

AP reservation 只保存 `ap_before/ap_after` 两个动作级数值：

- target rule、技能 hook 和 dry-run 都读取 `ap_after` 的 actor 视图；
- `empty_policy='fail'` 时在第一个目标成功后确认 reservation，所有目标 skipped 时恢复 `ap_before`；
- `empty_policy='execute'` 时在 ResolvedAim 合法且 action delivery 开始时确认 reservation；
- reservation 不包含 roster、targets 或 effects，不是 action UnitOfWork。

### 6.2 单目标流程

建议入口：

```php
function combat_resolve_target_unit(
    CombatActionExecution $action,
    array $resolution_target
): array;
```

内部顺序：

```text
1. execute 模式锁定并 bind current target/player/queue latest state；dry-run bind planned latest state
2. rebuild target tags
3. check target rules
4. 基于同一锁定版本 classify Participation
5. skill hook 纯声明当前目标 effects
6. effects 为空或声明失败：skip，不加入
7. member：继续
8. joinable：安全追加队列并 emit joined
9. snapshot_target_state 当前结算单位
10. apply 当前目标 effects
11. resolve 当前目标 reactions
12. post_check 当前目标死亡/逃跑
13. persist actor + 当前目标
14. 记录 TargetResolutionResult
```

参考骨架：

```php
combat_action_begin_if_empty_policy_execute($action);

foreach ($action->resolution_targets as $resolution_target) {
    $unit = combat_target_unit_create($action, $resolution_target);

    $rules = combat_target_unit_check_rules($action, $unit);
    if (!$rules['pass']) {
        $action->target_results[] = combat_target_unit_skipped($unit, $rules['reason']);
        continue;
    }

    $unit->participation = combat_participation_classify($action, $unit);
    if (combat_participation_rejected($unit->participation)) {
        $action->target_results[] = combat_target_unit_skipped($unit, $unit->participation['reason']);
        continue;
    }

    combat_target_unit_declare_effects($action, $unit);
    if (!$unit->executable) {
        $action->target_results[] = combat_target_unit_skipped($unit, 'NO_EXECUTABLE_EFFECT');
        continue;
    }

    combat_action_start_once($action);
    combat_participation_enlist_if_needed($action, $unit);
    combat_target_unit_snapshot_target_state($action, $unit);
    combat_target_unit_apply_effects($action, $unit);
    combat_target_unit_react($action, $unit);
    combat_target_unit_post_check($action, $unit);
    combat_target_unit_persist($action, $unit);

    $action->any_target_resolved = true;
    $action->target_results[] = combat_target_unit_result($unit);

    if (combat_actor_terminated($action->actor_data, $action->battle_cache)) {
        break;
    }
}

combat_action_finalize($action);
```

关键约束：

- skill hook 在入列前只声明 effects，不写 DB、不直接修改其他 PID；
- effects 只能默认作用于 actor 或当前 target；
- 跨目标效果必须产生新的 TargetResolutionUnit，不能直接携带任意 `target_pid` 绕过管道；
- 一个目标业务失败只 skip 自身；
- actor 在目标反应中死亡/逃跑时，当前动作剩余目标和后续动作全部停止；
- 基础设施异常抛出，由外层事务回滚整条命令。
- 不允许在 rules 后才重新加载另一版本的 target 并直接入列；若 enlist 阶段因防御性重载发现版本变化，必须重跑所有依赖可变字段的 target rules 后才能继续。

### 6.3 action_start、Action Delivery 与 AP 时机

`empty_policy='fail'` 时，第一个 TargetResolutionUnit 通过规则、Participation 分类和 effect declaration 后：

```text
emit action_start（仅一次）
→ 开始第一个目标单元真实结算
```

`empty_policy='fail'` 且所有目标都 skipped 时：

- 不发正常 action_start/action_end；
- 返回 `NO_VALID_TARGET`；
- 不扣 AP；
- 不设置 CD；
- 不加入任何角色。

`empty_policy='execute'` 时，只要 ResolvedAim 合法，动作就可以在没有成功角色目标的情况下执行：

```text
emit action_start(resolved_aim)
→ execute action delivery（例如手雷飞行与图格爆炸）
→ 可选逐个结算 ResolutionTarget
→ commit AP/CD
→ emit action_end
```

Action Delivery 表示发生在瞄准对象上的动作级投送或演出，不直接修改任意角色：

- grenade：投射物飞向 ResolvedAim tile、产生爆炸 cue；
- move：由唯一 tile ResolutionTarget 的 move effect 完成，不额外产生角色 targets；
- direct attack：通常没有独立 delivery effect，使用 action_start 动画即可。

如果至少一个目标已执行，后续目标失败：

- 已执行目标结果保留；
- AP/CD 正常按动作结算一次；
- 失败目标产生 target skipped/failure cue；
- 继续后续目标或动作。

### 6.4 Persist 边界

“每个目标单独保存”定义为：

- 每个 TargetResolutionUnit 独立调用角色 repository 保存 actor 和当前 target；
- battle_cache 在该目标完成后立即更新；
- 该目标事件在同一顺序位置进入 collector；
- 后续目标读取前序目标已经产生的内存状态。

所有这些写入仍位于同一个 command/heartbeat 数据库事务中：

- 业务失败：只跳过当前目标，不回滚前面成功目标；
- SQL/进程异常：整个数据库事务回滚，防止 action/bid/queue/player 半写。

不需要为每个 action 再建立 PHP checkpoint 或 roster batch UnitOfWork。

### 6.5 Dry-run 与 Preview

`combat_chain_project()` 使用相同的 AimResolver、ResolutionTargetCapturer 和 TargetResolutionUnit 循环，但：

- actor、resolved aim、captured target set、battle_cache 使用副本；
- AimResolver 与 Capturer 优先读取 planned_state overlay，再读取基础角色/地图状态，确保前序 move/push 对后序捕获可见；
- joinable 只在模拟 cache 中追加，不写 DB；
- 每个目标依次投影 HP/位置/死亡/成员关系；
- 后续目标和后续动作读取更新后的模拟状态；
- 返回每个 action 的 `target_results`。
- 不修改数据库 player/queue/battle state，不写文件日志，不污染真实 collector、全局 battle cache 或动作 UID 序列；
- preview 不消费战斗 RNG。pre-battle 初始先攻顺序只返回 `pending_initiative`，真实顺序由 execute 建队后确定。

这样无需新建另一套 ImpactPlan 语义。

pre-battle 的 initial roster 在真实 `battle.start` 前尚未投掷先攻，因此 preview 不能伪造精确的初始多目标处理顺序：

- preview 返回合法 initial target set，并标记 `targetOrder='pending_initiative'`；
- 不在 preview 中消费随机数或创建真实 queue；
- `battle.start` 事务创建初始 queue 后，按实际 myorder 重新排列首个 hostile action targets 并强校验；
- 当前阶段 react 为空，所以顺序不确定只影响演出顺序，不改变基础 damage 合法性；未来启用顺序相关 reaction 时，再引入可复现的战斗 RNG seed，而不是让 preview 和 execute 各掷一次先攻。

## 7. Participation 与安全入列

### 7.1 分类规则

角色目标进入效果声明后、真实结算前分类。

`member`：

```text
queue row exists
queue.qid == current qid
queue.active == 1
target.bid == current qid
target.action == 'battle'
```

`joinable`：

```text
target alive and not escaped
target action is empty
target bid == 0
no queue row
same region / relation allowed
skill participation == join_if_unengaged
```

`left`：

```text
queue.qid == current qid
queue.active == 0
```

`other_battle`：

```text
queue row belongs to another qid
OR target.bid points to another active qid
OR target.action == 'battle' with another bid
```

其他 action/bid/queue 组合全部视为 `blocked:membership_inconsistent`，fail closed。

### 7.2 新增安全队列接口

新增：

```php
function battle_queue_append_tail(
    array &$target_data,
    int $qid,
    array &$battle_cache,
    $log
): array;
```

职责固定为：

1. 再次确认目标没有其他队列归属；
2. 读取当前 qid 最大 `myorder`；
3. 插入 `active=1, done=0, myorder=max+1`；
4. `battle_state_init($target_data)`；
5. 设置 `target_data.bid=qid`；
6. 保存目标；
7. `battle_cache.combatants[pid]=1`；
8. emit `combatant_joined`。

核心实现必须是 compare-and-append，不是 delete-and-insert：

```php
$decision = combat_participation_classify_locked($target_data, $qid);

if ($decision['state'] === 'member') {
    return ['ok' => true, 'joined' => false];
}
if ($decision['state'] !== 'joinable') {
    return ['ok' => false, 'code' => $decision['reason']];
}

$myorder = obl_queue_next_myorder_locked($qid);
obl_queue_insert_entry($target_data['pid'], $qid, $target_data['type'], $myorder);
battle_state_init($target_data);
$target_data['bid'] = $qid;
obl_save_player($target_data);
$battle_cache['combatants'][(int)$target_data['pid']] = 1;
combat_log_v2_combatant_joined($log, $target_data, $qid, $myorder);
```

`classify_locked()` 必须重新加载并回写当前锁定版本的 `target_data`，不能拿进入 target unit 时的旧数组覆盖数据库新值。它与 `next_myorder_locked()` 必须在 room lock + InnoDB transaction 中读取 queue/player；实现阶段使用 `SELECT ... FOR UPDATE`，避免未来出现不经同一 PHP 调用栈的并发写入。

禁止：

- 调用 `obl_queue_delete_by_pid()`；
- 修改其他 qid；
- 重投先攻；
- 设置 `done=1`；
- 立即调用 `battle_manage_queue()`；
- 在 effect declaration 成功前加入目标。

### 7.3 幂等与失败

- 已是同 qid active member：幂等返回 `member`，不重复插入或发 joined；
- 当前 qid active=0：返回 `TARGET_LEFT_BATTLE`；
- 其他 qid：返回 `TARGET_IN_OTHER_BATTLE`；
- queue/action/bid 不一致：返回 `TARGET_MEMBERSHIP_INCONSISTENT`；
- SQL 失败：抛基础设施异常，由外层事务整体回滚。

### 7.4 多个新成员的顺位

假设当前最大 `myorder=4`，动作按顺序结算 B、C、D：

```text
B → myorder=5, done=0
C → myorder=6, done=0
D → myorder=7, done=0
```

当前 actor 完成后：

- 已有尚未行动成员先按原顺位行动；
- B、C、D 随后依次行动；
- 如果旧成员均已行动，B 直接成为下一行动者；
- 因为存在新的 `done=0` 行，不触发 round rebuild。

### 7.5 死亡与退出

新成员可以在加入它的同一个 TargetResolutionUnit 中死亡：

```text
combatant_joined
→ effect_applied
→ combatant_cleared(dead)
→ queue.active=0
→ target.action=''
```

保留 queue row 和 bid 的策略沿用当前队列生命周期，由 disband cleanup 统一处理。

## 8. 初始建战

### 8.1 初始 roster 的定义

`battle.start` 不再扫描整条动作链目标。

新的流程：

```text
normalize 后先且仅先执行一次 canonical `combat_sort_actions()`
→ 按排序后动作顺序执行合法 pre-battle utility/空投送动作
→ 到达 hostile action
→ AimResolver 生成 ResolvedAim
→ ResolutionTargetCapturer 捕获 targets
→ 对每个目标做规则、Participation 与纯 effect declaration 可执行性预检查
→ 过滤 other_battle/dead/out_of_range 等目标
→ 第一项至少有一个合法 character ResolutionTarget 的 hostile action 定义 initial roster
→ actor + 该 action 全部具有可执行效果的合法目标创建初始队列
→ 对 projected initial membership overlay 重跑同一套规则/Participation/effect declaration，证明建队后仍可执行
→ actor + initial targets 全部执行 battle_state_init，写入 action='battle'/bid
→ 使用现有初始先攻算法
→ 按初始队列顺序结算该 hostile action 的目标单元
→ 后续动作按动态参战规则执行
```

### 8.2 初始 AOE

如果第一项成功 hostile action 是 grenade，合法命中 A、B、C：

- initial roster 是 actor + A + B + C；
- 四人按现有建战规则生成初始先攻；
- grenade 的 A、B、C 目标结算顺序采用生成后的 queue order；
- 不把 A、B、C 当作“战中追加成员”。

初始队列继续复用现有 `battle_queue_create_and_init()` 的先攻/ambush 政策；本设计只修正 initial roster 来源，不改变发起者是否获得首动等既有规则。

初始 roster 预检查不得缓存最终 damage 数值。建队完成后，每个 TargetResolutionUnit 仍按当时 actor/target 状态重新声明 effects；预检查只证明该目标存在可执行的 hostile 效果，避免把无效果目标提前拉入 initial roster。

预检查使用 projected initial membership overlay，使 membership/roster 派生语义与建队后一致。若建队后的强校验仍与预检查不一致，视为 `INITIAL_ROSTER_DIVERGED`，整条 `battle.start` 回滚；不能保留已经入队但最终没有可执行效果的成员。

`empty_policy='execute'` 不能凭空创建战场。空图格 grenade 可以作为动作完成投送语义，但 `battle.start` 只有捕获到至少一个合法 character ResolutionTarget 时才能建立 initial roster；否则继续寻找后续 hostile action，最终仍无参战目标则返回 `NO_BATTLE_STARTED`。

如果动作链后面存在可以建立 initial roster 的 hostile action，前面的空图格 grenade 与 utility 一样在 pre-battle transaction context 中按顺序执行并缓冲事件；如果整条命令最终没有建立战场，其 AP/道具/事件与其他 pre-battle 写入一并回滚。

如果 grenade 同时找到属于其他 qid 的 D：

- D 单目标预检查失败；
- D 不进入 initial roster；
- A、B、C 继续建战和结算；
- 不因 D 让整个 grenade 失败。

### 8.3 后续动作目标

动作链：

```text
Action 1: attack A
Action 2: attack B
Action 3: all
```

执行：

```text
Action 1
  actor + A 建立 initial roster
  结算 A

Action 2
  B classify=joinable
  B 排当前队列末尾 done=0
  结算 B

Action 3
  重新解析 current battle hostiles
  按队列顺序结算 A、B 中仍 active 的成员
```

### 8.4 pre-battle utility

move/heal 等 utility 可以位于首个 hostile action 之前：

- 按动作顺序修改 actor 的计划与真实状态；
- hostile action 使用更新后位置重新解析射程和目标；
- 整个 `battle.start` 位于一个外层事务；
- 最终没有任何成功 hostile action 时返回 `NO_BATTLE_STARTED` 并回滚本命令中的 utility 写入。
- Command Bus 将该结果标记为 rollback-only；请求结束前即使内存 actor 已被 utility 修改，也不得 commit、落 collector 或推进 tick。

这样保留动作链语义，又不需要 pending battle identity 或 action UnitOfWork。

## 9. 数据库事务边界

### 9.1 最低要求

动态加入同时修改 player、queue 和 battle state；同时 command/heartbeat 的外层事务还可能包含 world/item/tick 写入。因此所有 Oblivions 可写业务表必须支持事务，至少包括：

```text
oblplayers       → InnoDB
oblqueue         → InnoDB
oblbattle_state  → InnoDB
oblmapstates     → InnoDB
oblmappoi        → InnoDB
oblmapitem       → InnoDB
```

重构前多份建表脚本声明为 MyISAM；当前 Oblivions 可写表模板已统一为 InnoDB。部署验收仍必须检查实际房间表的 `information_schema.tables.ENGINE='InnoDB'`，仅修改 SQL 模板而未转换或重建实际表不视为完成。

Oblivions 写路径已在事务中启用 DB adapter 的 throw-on-error mode，避免旧 `halt()/die()` 路径绕过外层 rollback；API shutdown guard 在事务仍 active 且请求未正常收口时执行兜底 rollback。

实时演出交付已经由后续设计迁移为响应直带 `presentation.v1`。文件或数据库 archive 仅是可选的历史/诊断能力，不参与在线播放、确认或命令正确性。

### 9.2 Command 与 heartbeat

玩家命令和 NPC heartbeat 都使用同一写事务结构：

```text
acquire room GET_LOCK
→ BEGIN
→ reload actor/battle state
→ execute action chain and target units
→ manage queue
→ freeze render events and advance presentation head
→ COMMIT
→ attach presentation.v1 to response
→ optional best-effort archive/diagnostic persistence
→ release room lock
```

事务边界必须有明确状态机：`begin` 设置 request-local transaction active；正常路径只允许一次 commit；异常路径只允许一次 rollback；shutdown 时若仍 active 则 rollback。释放 room lock 放在 `finally`/shutdown 兜底路径，不能依赖业务函数走到末尾。

collector 在事务内只积累内存事件；数据库 commit 失败时丢弃本次 collector 内容。当前在线协议要求：

- 领域状态与 queue/player 写入先保证一致；
- collector 只接收已经完成的目标事件；
- render events 与房间级 `obl_presentation_head_seq` 在事务内冻结，只有 COMMIT 成功后才附加到 response；
- rollback 不消耗 `batch_seq`，也不得投递本次事件；
- 在线 delivery 不写 mutable played JSON，不存在 mark/ack；
- 可选 archive writer 只能在 COMMIT 后 best-effort 执行，失败可返回 `BATTLELOG_PERSIST_FAILED` warning，但不得回滚领域状态或触发命令重放；
- outbox/immutable replay archive 另立任务，不阻塞动态参战。

TargetResolutionUnit 的 SAVEPOINT 位于上述请求级事务内部，只处理 enlist/effect 之后的可恢复单目标失败。SQL 异常、commit 异常、PHP exception 或事务 active 阶段的 fatal 不得降级成目标 skipped，仍由最外层事务 rollback 和 shutdown guard 收口。COMMIT 成功后发生的 fatal 已越过可回滚边界，只能通过 State reconcile 收口；当前没有 request-id 去重账本，客户端不得自动重放，仍存在用户手动重试导致重复执行的残余风险。

这意味着 COMMIT 后、HTTP response 发出前仍可能发生响应丢失。前端必须以 State API reconcile 当前角色和 membership，通过 `presentation_head_seq` 识别 gap 并快进，不能把 presentation events 当作领域真值，也不能自动重放不确定结果的命令。

### 9.3 业务失败与基础设施失败

```text
单目标规则失败
  → skip 当前目标，事务继续

单动作无合法目标
  → action 失败，事务继续执行后续 action

actor terminated
  → 停止剩余目标和动作，进入 cleanup/queue manage

SQL/PHP infrastructure failure
  → ROLLBACK 整条 command/heartbeat
```

## 10. Battlelog 与播放语义

### 10.1 事件层级

一个多目标动作建议输出：

```text
action_start(actor, act_id, resolved_aim)
→ optional action_delivery(resolved_aim)
→ target A events
→ target B events
→ target C events
→ action_end
```

每个目标内部：

```text
optional combatant_joined
→ effect_applied
→ optional combatant_cleared
→ optional target_failed/target_skipped
```

`action_start` 不再假设整个动作只有一个 target。投射物、移动目的地和图格爆炸读取 ResolvedAim；伤害、治疗和受击动画读取每个 effect 的 ResolutionTarget PID。

`event_uid` 与 `action_uid` 必须在跨请求范围内唯一。禁止继续只使用“秒级时间 + 请求内序号”或 pre-battle `qid=0 + action_seq`；每次 command/heartbeat 生成 request/command UID，action/event UID 均以此为前缀，`source_action_uid`、Director 分组和去重全部使用该稳定身份。

grenade 事件示例：

```text
action_start(actor, grenade, aim_tile)
→ action_delivery(projectile_to_tile)
→ action_delivery(explosion_at_tile)
→ effect_applied(target=A)
→ effect_applied(target=B)
→ action_end
```

即使 CapturedResolutionTargetSet 为空，`empty_policy='execute'` 的 grenade 仍保留前两项 delivery 事件。

### 10.2 `combatant_joined`

```json
{
  "schema": "battlelog.v2",
  "event_type": "combatant_joined",
  "qid": 12,
  "payload": {
    "combatant": {},
    "source_actor_pid": 1,
    "source_action_uid": "...",
    "myorder": 5,
    "done": 0
  }
}
```

要求：

- 只对真正从 joinable 转为 member 的目标发出；
- 必须先于该目标的 effect；
- 同 qid member 不重复发出；
- 前端 Director 按正常语义事件准备 actor，不用普通文本替代。

### 10.3 Partial Target Result

AOE 中某个目标失败时，不发整个 action_failed。返回并可选播放：

```json
{
  "event_type": "target_skipped",
  "payload": {
    "action_uid": "...",
    "target_pid": 12,
    "reason": "TARGET_IN_OTHER_BATTLE"
  }
}
```

是否向玩家显示取决于原因和情报权限；调试日志必须保留完整原因。

### 11.4 AimMode 候选

AimMode 必须拆分展示候选和可提交候选：

```ts
const displayCandidates = combatTargets.candidates;
const selectableCandidates = displayCandidates
  .filter(item => item.selectable === true)
  .filter(item => item.relation === 'hostile')
  .filter(item => item.participation === 'member' || item.participation === 'joinable')
  .map(item => characterStore.getCharacter(item.pid))
  .filter(isPresent);
```

AimMode 不自行推导 Participation，也不能因为当前已有 member target 就屏蔽 joinable NPC。blocked/left/other_battle 可以出现在 `displayCandidates`，但不能进入 `selectableCandidates`；点击确认瞬间必须对最新 candidate 再校验一次。

### 11.5 角色实体瞄准

enemy 瞄准锚点迁移到独立角色实体：

```html
<div
  class="entity entity-enemy"
  data-character-pid="..."
  data-entity-id="enemy-..."
>
```

- enemy target 使用 `[data-character-pid]`；
- tile target 继续使用 `[data-pls]`；
- Aim 激活期间只给合法角色实体打开 pointer events；
- 同格多个 NPC 按 PID 分别存在；
- 点击重叠实体时按该 tile 的候选列表弹出消歧菜单；
- 与玩家同格的 NPC 仍可被选择；
- joinable 可以保持 dimmed，但 Aim 时必须显示可选轮廓；
- joined 只在后端响应/reconcile 后改变视觉 membership。

### 11.6 宽松战斗工作区

前端仍允许：

- 后端 `action=''` 时打开 pre-battle 工作区；
- 后端已经结束时，让当前 JS runtime 内已接收的 `PresentationBatch` 完成或显式快进；
- 权威状态持续作为命令权限来源，表现层在稳定边界 rebase 后决定是否关闭战斗工作区。

空 `presentation.events` 只表示本次响应没有新的演出事件，不表示战斗结束；战斗结束只由后端 `action/battle_state/capability` 判断。

本阶段不要求先重构所有 Store。可以在现有 `battleStore + PreloadArea` 上完成自由选择，但必须删除 `enemyPid` 自动入队和 combatContext 重复初始化清空目标的错误语义。

## 12. API 与返回结果

### 12.1 Command payload

动作 payload 保持每项独立 target：

```json
{
  "command": "battle.submit_turn",
  "payload": {
    "actions": [
      { "act_id": "unarmed_strike", "target": { "type": "pid", "id": 8 } },
```

### 12.2 后端结果

```json
      "index": 0,

      "apCost": 1,
      "resolvedAim": { "kind": "character", "pid": 8 },
      "capturedTargetCount": 1,
      "targets": [
        {
          "pid": 8,
          "status": "resolved",
          "participation": "member",
          "reason": null
        }
      ]
    },
    {
      "index": 1,
      "actId": "grenade",
      "status": "partial",
      "apCost": 2,
      "resolvedAim": { "kind": "tile", "pgroup": 1, "pls": 1005 },
      "capturedTargetCount": 2,
      "targets": [
        {
          "pid": 9,
          "status": "resolved",
          "participation": "joined",
          "reason": null
        },
        {
          "pid": 10,
          "status": "skipped",
          "participation": "rejected",
          "reason": "TARGET_IN_OTHER_BATTLE"
        }
      ]
    }
    ]
  }

```

Command Bus 对 handler 返回的领域数据做扁平合并，禁止再生成 `response.data.data.actions`。前端 typed client 从 `response.data.actions` 读取 `CombatActionResult[]`。

动作状态：

```text
resolved  action delivery 已执行，且所有实际目标成功；optional capture 为空也属于 resolved
partial   action delivery 已执行，且至少一个捕获目标 skipped
failed    action delivery 未执行，且没有 TargetResolutionUnit 成功
stopped   actor terminated，后续未执行
```

对 `empty_policy='execute'` 的动作，合法完成 delivery 且没有 ResolutionTarget 时仍返回 `resolved`，`capturedTargetCount=0`、`targets=[]`。

## 16. 验收测试

### 16.1 Aim 与 Capture

1. tile 技能收到 pid AimIntent 时由 AimResolver 拒绝。
2. 客户端伪造 pgroup/pls 时，ResolvedAim 只使用后端解析结果。
3. direct_character Capturer 把角色 ResolvedAim 转为同一角色 ResolutionTarget。
4. tile_characters Capturer 保留 ResolvedAim tile，同时输出零到多个角色 ResolutionTarget。
5. CapturedResolutionTargetSet 在同一动作中只生成一次，后续 TargetResolutionUnit 不重新查询 occupants。
6. 捕获结果 PID 去重且顺序稳定。
7. snapshot_target_state 不得添加、删除或替换 ResolutionTarget。
8. action_start/action_delivery 使用 ResolvedAim，effect_applied 使用 ResolutionTarget。
9. Capturer 后前序目标修改了某角色状态，轮到该 ResolutionTarget 时绑定最新内存状态，而不是 capture 时的角色属性副本。

### 16.2 逐目标顺序

1. whirlwind 命中 A、B、C，A 的 effect/post_check/persist 全部发生在 B 前。
2. A 死亡后，B 仍按自己的当前状态结算。
3. B 规则失败只产生 skipped，C 继续执行。
4. actor 在 A 的 reaction 中死亡时，B/C 不再执行。
5. 同一多目标动作只扣一次 AP、设置一次 CD。
6. `empty_policy='fail'` 的动作所有目标失败时不扣 AP、不设置 CD。

### 16.3 tile AOE

1. grenade tile 上多个角色全部成为独立 ResolutionTarget。
2. grenade hook 不调用任意 PID 查询。
3. 当前 qid 成员按 myorder 结算。
4. 非成员按 PID 稳定排序。
5. 死亡/友方/不受影响角色单独 skipped。
6. other_battle 目标不受伤，其他目标继续。
7. 前序 move 后执行 grenade，Capturer 读取移动后的世界状态。
8. Capturer 完成后，新进入图格的 D 不加入本次 grenade 目标集合。
9. 测试 harness 在 Capturer 完成后修改 planned/current-state overlay 中 B 的位置，再执行 B unit；B 仍保留本次爆炸的 capture fact。正式跨目标 reaction/嵌套 unit 调度留待 reaction 阶段实现后再增加集成场景。
10. 空图格 grenade 按 `empty_policy='execute'` 消费 AP/CD并产生投射与爆炸事件，`targets=[]`。
11. `snapshot_target_state` 只记录各角色受伤前状态，不改变 CapturedResolutionTargetSet。
12. move 的 ResolvedAim 与 ResolutionTarget 都是 tile，snapshot_target_state 记录 actor 移动前状态。
13. Capturer 返回重复 PID、错误 entity kind 或非权威图格 occupant 时拒绝该捕获结果。

### 16.4 动态参战

1. 空闲 NPC 首次被有效攻击时先入队再受伤。
2. 新成员 `myorder=tail, active=1, done=0`。
3. 不重投已有队列先攻。
4. 新成员不打断当前 actor。
5. 当前 actor 结束后，新成员在当前轮获得行动机会。
6. 同一动作加入 B、C 时，顺位按目标处理顺序排列。
7. 已是 member 的目标幂等，不重复 joined。
8. active=0 的 left 成员不能重新加入。
9. 其他 qid 目标不会被删除旧队列或修改源战场。
10. action/bid/queue 不一致时 fail closed。
11. 加入后同一目标立即死亡，最终 active=0/action=''。

### 16.5 初始建战

1. Action 1 攻击 A、Action 2 攻击 B：initial roster 只有 actor+A。
2. B 在 Action 2 动态排尾，不参加初始先攻。
3. 第一项 grenade 合法命中 A/B/C：三者都参加初始先攻。
4. grenade 中 D 属于其他 qid：D 被过滤，A/B/C 正常建战。
5. 前序 move 改变位置后，hostile action 使用新位置校验射程。
6. 最终无成功 hostile action 时不创建战场并回滚本命令 utility。
7. 空图格 grenade 即使 `empty_policy='execute'` 也不能单独建立 initial roster。

### 16.6 事务

1. queue INSERT 失败时 player.action/bid 不留下半写。
2. player save 失败时 queue row 不留下。
3. 第三个目标 SQL 异常时整条命令数据库写入回滚。
4. 第二个目标业务拒绝时，第一个目标成功结果保留。
5. heartbeat NPC 动态拉入目标时使用相同事务语义。
6. target rule 与 skill hook 在 dry-run/execute 中都读取相同的 AP reservation 后 actor 状态。
7. 实际 Oblivions 可写业务表（包括 `oblplayers/oblqueue/oblbattle_state/oblmapstates/oblmappoi/oblmapitem`）引擎均为 InnoDB。
8. SQL 失败、commit 失败、PHP exception，以及事务仍 active 时发生的 fatal shutdown，均 rollback 并释放 room lock；commit 完成后的 fatal 不可能回滚已提交领域状态，客户端必须先 State reconcile 且不得自动重放。当前 request_id 只做格式校验，不提供服务端去重。
9. rollback 后 collector 不产生 `PresentationBatch` 且不消耗 sequence；commit 后可选 archive 写失败只返回 warning，领域状态保留且客户端不重放。
10. preview 前后数据库、可选 archive/诊断文件、真实 collector、全局 cache、UID 序列和 RNG 状态均无变化。

### 16.7 前端

1. in-battle 有 suggested A 时，点击 enemy 技能仍进入 AimMode。
2. 玩家选择 B 后 QueueItem 和 payload 保存 B。
3. 同一动作链可分别选择 A、B、C。
4. member 与 joinable 可选，blocked 不可选。
5. suggested target 只高亮、不自动入队。
6. 同格多个 NPC 可分别选择。
7. 与玩家同格 NPC 可选择。
8. joinable dimmed 但 Aim 时可识别。
9. 后端确认 joined 后实体原地切换为 active，不因 PID key 重建。
10. 空 `presentation.events` 不触发前端自行结束战斗，F5/冷启动也不补播历史动画。

## 17. 最终框架基准

1. Action 决定“做什么以及消耗多少 AP”。
2. AimResolver 决定“玩家选择在后端具体指向什么”。
3. ResolutionTargetCapturer 决定“该动作在执行时捕获哪些有序结算单位”。
4. TargetResolutionUnit 决定“一个目标从校验到保存如何完整结算”。
5. Participation 决定“这个角色能否在当前目标单元中加入战场”。
6. Queue 决定“成员何时取得下一次行动机会”。
7. CharacterHub 决定“前端如何读取角色当前状态”。
8. AimMode 决定“玩家本次动作显式选择哪个 PID 或图格”。
9. 后端始终对 ResolvedAim 和每个 ResolutionTarget 重新校验，前端候选不构成安全权威。

动态参战的最终定义是：

> 当一个有序 TargetResolutionUnit 即将对空闲敌人执行合法战斗效果时，后端先把该敌人以 `done=0` 追加到当前先攻队列末尾，再完成这个目标自己的效果、反应、状态保存和事件；其他目标随后继续独立结算。
