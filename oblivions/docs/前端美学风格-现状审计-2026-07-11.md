# Oblivions 前端美学风格现状审计

> 审计日期：2026-07-11（v2 文风修订：2026-07-16）
> 范围：`oblivions/docs/前端美学风格-设计案.md`、`oblivions/docs/demos/`、当前 `vex-vue` 源码与本地运行态页面。
> 性质：只读调研，不包含实现修改。
> 文风说明：本文档以引导型语言撰写，描述优化方向与设计意图，而非命令式整改清单。文中"宜"、"可"、"建议"表述的是设计方向的倾向性，具体落地时仍需结合场景权衡。

## 一、结论摘要

当前前端已经形成稳定的灰阶 ASCII 终端底盘，地图角色也采用真实 PNG 立绘和 GSAP 位姿动画，基础方向与"剪纸舞台 + ASCII 终端"一致。美学设计案确立的框架基准可概括为：**黑白单色、形状优先、立绘 popUp 作为瞬时反馈主通道、全动画 reduced-motion 兜底**。

对照这个基准，当前实现可从四个方向观察优化空间：

1. 战斗主视觉仍较多使用红色传统 VFX，包括全屏红光、红色弹丸、红色扩散爆炸和红色瞄准 HUD，与设计案的核心方向存在冲突。
2. 设计案列入高优先级的地图纹理、信号色清理和天穹层尚未完成，"黑白漫画"和环境剪纸舞台两层基本缺席。
3. 战斗弹窗、HP、伤害数字等仍采用红/蓝/绿/黄语义色，形成与普通终端 UI 不同的第二套视觉语言。
4. 循环动画、GSAP Actor 动画与战斗演出的 `prefers-reduced-motion` 覆盖已从单点扩展到多处，但尚未形成全局策略。

综合来看，现状可视为：**基础 UI 风格已经对齐约六成，战斗反馈框架与设计案方向存在差异，环境表现层尚未落地。**

## 二、审计基准

本次以设计案中的以下核心约束作为观察参照：

- 三层语言：剪纸舞台、ASCII 终端、黑白漫画（设计案 §1.1）。
- 避免彩色粒子、彩色震波、屏幕变色、全屏瞬时 overlay、残影、sprite 帧序列和 CRT 扫描线（§1.2）。
- 瞬时反馈建议统一为黑白单张立绘 popUp（§1.2、§4.3、§4.6）。
- 所有动画宜提供 reduced-motion，循环或闪烁频率不宜超过 3Hz（§1.4）。
- 避免引入彩色信号色，信息宜通过灰阶、形状、纹理、位置冗余编码（§6）。
- demo 的融合方案作为控件层次参考：细线 ASCII 骨架、灰阶硬投影、堆叠纸片层次、明确的按钮 hover/active 状态，避免反色 hover、粗重边框或不规则圆角。

## 三、重点优化方向

### 3.1 高优先级：远程弹丸与爆炸仍是彩色 DOM VFX

`vex-vue/src/stores/battle-overlay-executor.ts:9-39` 以 DOM 几何体创建红色发光弹丸和红色圆形扩散爆炸；`vex-vue/src/stores/battle-actor-executor.ts:124-138` 在真实 delivery 流程中调用它们。

这与"避免彩色粒子/震波""避免 overlay 扩散"和"瞬时反馈建议使用单张黑白立绘 popUp"三项核心约束存在冲突。问题不在于局部配色，而在于战斗反馈机制仍属于传统网页 VFX，与设计案方向的 illustration popup executor 存在差异。

宜优先考虑移除几何弹丸/扩散圆环。若需保留投射过程，可使用单张黑白弹道或投射物立绘做位移；命中使用 `hit-impact` / `critical-impact` 单图 popUp。

### 3.2 高优先级：战斗状态使用全屏红光和地图整体滤镜

`vex-vue/src/App.vue` 在战斗态挂载 `.battle-active` 类；`vex-vue/src/assets/styles/battle.css:16-38` 绘制 fixed 全屏红色脉冲边框；同文件对地图施加整体色调/饱和度/亮度滤镜。

这使战斗持续态依赖红色编码，并造成全屏视觉状态变化，压过黑白终端和剪纸角色。宜考虑改为灰阶形状编码，例如固定双线、断裂边框或明确的 `[BATTLE]` 状态构件；进入战斗的瞬时强调可交给黑白场景立绘 popUp，而非持续红光。

### 3.3 高优先级：战斗瞄准系统仍是红/黄战术 HUD

`vex-vue/src/components/battle/AimMode.vue` 使用红色路径、端点、目标框和红光；用黄色表示越界；用红色表示 focused。`vex-vue/src/assets/styles/battle.css:379-424` 还有一套重复的全局规则。

瞄准本身已有实线、虚线、点线和暗遮罩等形状冗余，这是可保留的正确基础；问题是颜色仍成为最强信号。宜统一为：可选目标白色实线 + 十字准星，越界灰色虚线，阻挡点线 + 暗遮罩，focused 加粗或增加角标。

### 3.4 高优先级：全局 reduced-motion 策略仍在推进中

截至 2026-07-16 核实，`prefers-reduced-motion` 覆盖已从单点（CraftModal）扩展到 5 处：`terminal.css`、`components/battle/PreloadArea.vue`、`components/craft/CraftModal.vue`、`animations/actorAnimations.ts`、`components/battle/AimMode.vue`。Actor 永久 idle、移动、跳跃、到达、受击、攻击动画已有 GSAP `matchMedia` 降级；瞄准线 dash 动画已有 CSS media 关闭。

但仍有未覆盖区域：`battle.css` 的战斗边框红色脉冲、HP blink、伤害数字动画、地图 pulse/glitch、抽屉过渡等尚未纳入统一降级。现有循环频率大多没有超过 3Hz，但"低于 3Hz"和"允许用户关闭动画"是两条独立要求。宜建立统一 motion policy：CSS media 关闭 infinite 动画和 dash；JS `matchMedia` 让 GSAP 降级为立即 set 或极短淡入。

## 四、设计案高优先级项尚未落地

### 4.1 地图黑白漫画纹理缺失

设计案 §2 和 demo 已定义 water、vegetation、metal、magic、abyss 的纹理规则。当前 `vex-vue/src/assets/styles/terminal.css:299-305` 仅实现 tide-deep glitch 与 metal 边框；仓库不存在 `textures.css`，`vex-vue/src/main.ts:5-7` 也没有纹理样式导入。

结果是"三层叠加"中的黑白漫画层没有进入真实地图，floor/tide 语义主要仍停留在数据层。宜按设计案使用低对比 CSS 渐变纹理，避免位图平铺。

### 4.2 正式界面的信号色清理不完整

截至 2026-07-16 核实，以下信号色仍存在：

- `vex-vue/src/assets/styles/terminal.css:299-302`：blocked 使用红色 `#c44` / `rgba(204,68,68,0.3)`。
- `terminal.css:329-330`：safe-zone 使用绿色 `rgba(68,204,68,0.25)`。
- `terminal.css:765-767`：状态效果 chip 使用暗黄 `#f0c36a`。
- `terminal.css:807-815`：NPC pending 使用暗黄。
- `terminal.css` 相关位置：NPC/敌人仍使用红色描边。

设计案和融合 demo 已给出替代语法：blocked 用灰阶双线 + `x` 形标记，safe-zone 用白色虚线 + 菱形，pending 用白色脉冲。NPC 红描边属于设计案明确记录的待 demo 决策点，可作为暂时例外；其余三项宜视为未完成的高优先级清理。

### 4.3 天穹层完全缺失

`vex-vue/src/App.vue` 没有 SkyLayer，`src` 内也没有 `sky-layer` / `SkyLayer` 实现。当前剪纸舞台语言只存在于角色立绘，没有扩展到环境和第一幕的日常、异常、揭星叙事阶段。

这属于规划缺口，不是现有功能回归，但它会阻止设计案所描述的完整美术风格成立。实现时宜置于地图外的背景层，`pointer-events:none`，并同时提供 reduced-motion。

## 五、中等优化项

### 5.1 战斗弹窗形成独立的彩色 UI 体系

`vex-vue/src/assets/styles/battle.css` 中战斗弹窗相关规则使用了红边红光、敌红/玩家蓝/HP 绿红、黄/红日志色等彩色编码，与普通日志的灰阶体系并行存在。

普通日志已经在 `terminal.css` 中正确降级为灰阶、字重和下划线，战斗弹窗目前绕开了这套规则。宜考虑将战斗 UI 也纳入同一视觉语言：角色双方可通过左右位置和对齐区分，HP 使用灰阶亮度/纹理表达，战斗日志复用普通日志的语义样式。

### 5.2 伤害数字承担了彩色特效角色

`vex-vue/src/components/battle/DamageNumber.vue` 在战斗弹窗关闭后会显示约 2 秒残留数字；其颜色和动画样式位于 `battle.css` 中，伤害为红、治疗为绿。

数字作为精确数值信息可以保留，宜考虑改为白/灰表达，并通过 `-` / `+`、字重、边框形状区分伤害与治疗。冲击感的传递可由与 `impactAt` 同步的黑白图标立绘承担，避免数字本身成为第二套 VFX。

### 5.3 弹层、Toast、Drawer 的剪纸层次尚不明显

融合 demo 为 Modal、Toast、Drawer 定义了灰阶硬投影、堆叠纸片边缘和侧边结构。当前 `terminal.css` 中弹层相关样式主要还是细边框、轻发光和 translate，视觉上以 ASCII 终端层为主，剪纸容器层次尚未充分体现。

这不属于核心方向冲突，但会让"剪纸舞台 + 终端"的融合只发生在地图角色层，未延伸到 UI 层级。宜考虑将 demo 的硬投影和堆叠边缘抽为通用弹层样式，继续保持直角、灰阶和细线框的视觉语言。

### 5.4 按钮主次与按压反馈可进一步加强

`terminal.css` 中按钮 hover 主要改变背景，active 仅降低 opacity；`components/actions/TileActionBar.vue` 的等待、探索、合成等按钮视觉权重较为接近。

宜考虑补齐 primary 变体、`focus-visible`、active 下压和 inset shadow，并按动作优先级进行视觉分层。该方向影响操作扫读和手感，但不影响核心黑白基调。

### 5.5 窄屏布局依赖强制压缩，存在裁切风险

`vex-vue/src/App.vue` 根节点和 main 块采用固定视口高度 + `overflow-hidden`；`terminal.css` 在窄屏下将主区改为两行布局，但未打开页面纵向滚动。

运行态在 390×844 视口下能够显示地图、日志和动作区，但各区高度被明显压缩；较矮视口或内容扩张时，第二行缺乏页面级滚动兜底。宜明确移动端策略：考虑页面纵向滚动，或为两行使用稳定的 `minmax()` 并保证各面板内部可滚动。

## 六、较低优先级观察点

- `components/actions/TileActionBar.vue` 中机制效果使用 Unicode 星形 `✦` 表示。它通常不是彩色 emoji，但平台字形不可控，且未遵循图标立绘语言。可考虑改为 ASCII `[FX]` 或真正的黑白图标 popUp。
- `animations/actorAnimations.ts` 中所有角色共用同一 idle 呼吸，尚未实现设计案 §7.3 所述的角色动画签名。宜将 signature 放入 actor visual profile，而不是在动画函数中按角色硬编码。
- `src/assets/illustrations/icons/` 下尚无 hit、muzzle、critical 等完整素材/API。它属于核心表现缺口，但设计文档仍将部分内容标为规划中，难以简单归类为历史回归。

## 七、符合设计案的部分

- Actor 的移动、攻击、受击、倒地直接作用真实立绘 pose/action 层，没有半透明 clone 残影，也没有 sprite 帧序列：`animations/actorAnimations.ts`。
- 近战在 impact cue 后触发受击，AOE 可同时触发多目标 hit，演出时序结构清晰：`stores/battle-actor-executor.ts`。
- 长距离到达使用 alpha + scale 的 `arriveAnim`，符合区域切换语言：`actorAnimations.ts`。
- 死亡 fall 和逃离 fade 都是立绘本体变化，不依赖彩色特效：`actorAnimations.ts`。
- 普通日志已把历史颜色类映射为灰阶、字重和下划线：`assets/styles/terminal.css`。
- 地图、背包、装备和状态区保持紧凑、直角、等宽字体和灰阶细边框，ASCII 终端底盘稳定。
- CRT 扫描线确已移除，只保留静态暗角：`terminal.css`。
- 瞄准交互除颜色问题外，已有实线/虚线/点线、cursor、亮度和菜单状态等冗余编码，键盘操作也完整。
- BattleModal 的黑幕是缓慢过渡，不是瞬时闪屏，属于设计案允许的场景过渡边界：`battle.css`。
- v0.4 第一版按钮样式已恢复，Header 状态栏按钮保持 1px 灰边 + 深底 + 11px 字号的视觉权重：`terminal.css` 中 `.status-nav-btn`。
- 抽屉已迁移为 push 模式持久抽屉，作为 flex 子项参与主布局挤压：`components/layout/PlayerDrawer.vue`、`components/layout/InventoryDrawer.vue`。

## 八、建议迭代路径

1. **先收敛框架冲突**：宜优先移除红色 DOM 弹丸/爆炸、全屏红光和地图滤镜，建立 illustration popup executor 作为瞬时反馈主通道。
2. **统一战斗 UI**：瞄准、BattleModal、HP、日志、伤害数字宜回归灰阶 + 形状语义，与普通日志体系对齐。
3. **建立 motion policy**：CSS 与 GSAP 共用 reduced-motion 决策，覆盖所有 infinite 动画和主要过渡。
4. **补齐设计案高优先级项**：textures.css、blocked/safe/pending 灰阶化、SkyLayer 骨架。
5. **吸收 demo 的容器与按钮层次**：硬投影、纸片堆叠、primary/active/focus 状态。
6. **再扩展角色性格与叙事素材**：动画签名、状态立绘、天穹消解、关键场景插画。

## 九、当前判断与方向

当前最值得保留的是 ASCII 终端信息架构、真实立绘 Actor 系统和 impact cue 编排；最需要避免继续扩展的是红色 CSS/DOM 战斗 VFX。后续若继续在现有 `battle.css` 上叠加弹丸、爆炸、发光和全屏滤镜，实现会与设计案方向渐行渐远。可作为参照的框架基准是：**UI 负责灰阶信息，Actor 负责位姿，所有瞬时冲击统一进入黑白立绘 popUp 管线。**

## 十、补充观察（基于 DESIGN.md §2.15 / §3.4）

> 本节基于"少即是多"视觉元约束与注意力稀缺哲学，对当前前端进行二次审阅，记录可进一步优化或迭代的方向。所列项不构成强制整改清单，而是供后续设计权衡的观察锚点。

### 10.1 已推进的部分

- `prefers-reduced-motion` 覆盖已从单点扩展到 5 处（`terminal.css`、`PreloadArea.vue`、`CraftModal.vue`、`actorAnimations.ts`、`AimMode.vue`），方向与 §3.4 "协调性即节省注意力"一致。
- 抽屉已迁移为 push 模式持久抽屉（`PlayerDrawer.vue` / `InventoryDrawer.vue`），作为 flex 子项参与主布局挤压，避免了 fixed overlay 对地图注意力的二次抢占。
- Header 状态栏按钮已恢复 v0.4 第一版 `.status-nav-btn` 视觉权重（1px 灰边 + 深底 + 11px 字号），三按钮独立分布，与终端灰阶基底保持一致。

### 10.2 新增可优化观察

#### 10.2.1 强调色稀缺性仍被多处稀释

§2.15 提出"唯一强调色规则"——允许引入唯一第三方颜色作为注意力锚点。当前实现中红色被同时用于：战斗边框脉冲、BattleModal 敌方名 / HP critical、DamageNumber 伤害数字、AP 预测扣除段、aim-targetable / aim-focused、aim-disambiguation.focused、battle-banner-line 装饰线、battle-mode 地图 hue-rotate 色调、NPC 立绘红色描边、blocked 格红色、status-effect-chip 暗黄等。

红色被分散到十数处语义不同的位置，使"强调色"失去锚点功能。宜考虑将红色收敛为"瞬时单一锚点"（如关键命中 popUp），其余场景退回灰阶 + 形状编码。

#### 10.2.2 视觉语言存在多套并行体系

- **日志体系割裂**：普通日志（`terminal.css` 中 `.log-*` 类）已统一为灰阶/字重/下划线；战斗日志（`battle.css` 中 `.battle-log-entry .yellow/.red`）仍保留彩色；状态效果 chip 使用暗黄。三套语义并行存在。
- **按钮体系割裂**：`.term-btn`（普通按钮）、`.obl-btn`（战斗按钮）、`.status-nav-btn`（导航按钮）、`.aim-disambiguation-item`（瞄准菜单项）四套按钮语言共存，hover/active/focus 反馈规则各不相同。
- **容器装饰不统一**：PlayerDrawer 头部使用 `┌─ SURVIVOR` ASCII 装饰；InventoryDrawer 头部使用纯文本 + tab 按钮；Modal 头部使用纯文本 + `[X]`。同为弹层容器，但视觉装饰语法不一致。

宜考虑以"灰阶 + 形状 + 字重"为统一基底，将多套体系收敛为同一视觉语言的不同强度档位。

#### 10.2.3 留白实践与想象力空间不足

§3.4 提出"留白不是空缺，是为想象力腾出的空间"。当前实现信息密度普遍较高：

- `PlayerDrawer.vue` 内部 `├─`/`└─` 树形符号已用，但各 section 之间仅 8px padding-top + 1px border-top，缺乏呼吸感。
- `StatusBar.vue` 三行横排（区域 + tick + HP / 位置 + SP + 状态 chip / 三按钮），每行塞满信息，第二行在状态效果较多时容易拥挤。
- `RightPanel.vue` Log 与 Actions 以 flex:4/6 分割，LogPanel 内部日志行间距 1px 较紧。
- 战斗 BattleModal 420px 固定宽度内同时承载双方名 + HP 条 + 逐条 battlelog，停留 1.2s 后立即关闭，用户难以沉淀印象。

宜评估是否可在关键面板引入受控留白（如 section 间距、关键状态前后的空白行、BattleModal 的延长停留），为想象力留出余地。

#### 10.2.4 弱项转化（颜色 → 形状）尚不充分

§3.4 "弱项认知决定精简必然性"提示：颜色是弱项，宜以形状、纹理、位置冗余编码。当前若干关键状态仍以颜色为最强信号：

- HP critical 状态：`battle.css` 中 `.battle-modal-hp-fill.critical` 使用 `#aa3a3a` 红色 + 0.6s 闪烁，颜色承担主要警示功能。可考虑改用条形断裂、虚线段、`!` 角标等形状冗余。
- 敌我区分：BattleModal 中敌方名 `#ff6b6b`、玩家名 `#6bbbff`，颜色仍是主要区分维度。虽然已有 enemy 左 / player 右 的位置冗余，但颜色权重压过位置。
- NPC 红描边：`terminal.css` 中 `.entity-img` 默认 filter 给 NPC 加红色 drop-shadow 描边。这属于"颜色为弱项"的典型反例。
- blocked 格：使用红色 `#c44` + 红色 border-color，未辅以形状标记（如 `×` 形、双线、阴影纹）。

宜优先以形状/纹理/位置作为信息主通道，颜色仅作辅助强化。

#### 10.2.5 注意力经济下的循环动画密度

§3.4 "协调性即节省注意力"提示：循环动画会持续抢占注意力。当前并存的循环动画包括：

- `battle-border-pulse`（2s 全屏红光脉冲）
- `hp-critical-blink`（0.6s HP 闪烁）
- `aim-pulse`（1.5s 敌人格脉冲）
- `turn-glow`（2.5s 玩家回合按钮呼吸）
- `glitch`（1.5s tide-deep 抖动）
- `pulse-white`（2s 当前格名脉冲）
- `aim-line-flow`（0.9s 瞄准线 dash 流动）
- `log-new-flash`（1.5s 新日志高亮，非循环但持续）

这些动画在战斗态下可能同时存在 4-5 个循环，持续抢占用户注意力。宜考虑建立"同时活跃循环数上限"策略，或按场景优先级让低优先级循环让位。

#### 10.2.6 字号与字重层级未充分对齐

跨组件字号分布较为散乱：StatusBar 内 `status-tick-debug` 10px、`status-location` 未显式设定、`status-effect-chip` 未显式设定；PlayerDrawer 内容统一 11px；BattleModal 名字 12px / HP 文字 10px / 日志 12px；LogPanel / TileActionBar 各自又有不同字号。

字重层级也未形成统一档位：`.battle-modal-combatant-name` 700、`.term-btn` 600、`.tile-name` 默认、`.log-yellow` 700、`.log-red` 700，跨组件字重规则不一致。

宜考虑建立全局字号/字重档位（如 9/10/11/12/14px 五档；400/600/700 三档），让各组件从中选取，避免散乱。

#### 10.2.7 抽屉与主区的视觉过渡尚未充分表达

PlayerDrawer / InventoryDrawer 已迁移为 push 模式 flex 子项，但 `terminal.css` 中 `.player-drawer-push` / `.inv-drawer-push` 的过渡样式（flex-basis 0↔300px）细节未在本次审计范围内完整核实。若过渡时长/缓动函数与主区收缩节奏不匹配，可能出现抽屉"突然让位"或"滞后挤压"的视觉割裂。宜在后续迭代中核实过渡曲线与 reduced-motion 降级是否完整覆盖。

### 10.3 不确定性与待决策点

#### 10.3.1 NPC 红色描边的去留

设计案明确记录 NPC 红描边为"待 demo 决策点"，目前仍保留红色 drop-shadow。从 §2.15 视角看，红描边稀释了强调色稀缺性；但从游戏可读性看，红描边是当前区分 NPC 与玩家的最强信号。该决策点宜在 demo 阶段以形状替代方案（如 NPC 底座几何、轮廓角标）进行对比验证后再定。

#### 10.3.2 战斗持续态的视觉表达

当前战斗持续态依赖全屏红光 + 地图 hue-rotate 滤镜。从 §3.4 视角，"持续态"不应依赖持续动画抢占注意力；但从游戏反馈看，用户需要明确的"我在战斗中"状态锚点。宜探索静态状态构件（如固定双线边框、`[BATTLE]` 状态标签、地图角标）作为持续态表达，将动态效果让位给瞬时反馈。

#### 10.3.3 SkyLayer 与天穹消解的优先级

§4.3 已记录 SkyLayer 完全缺失。从 §3.4 "想象力核心"视角，天穹层是环境叙事与想象力承载的关键载体；但从基础体验看，战斗 UI 与日志体系收敛可能更紧迫。宜在迭代路径中明确 SkyLayer 的引入时机——是否在战斗 UI 收敛后再启动，或并行推进。

#### 10.3.4 字号/字重档位建立的边界

10.2.6 提出字号字重档位建议，但是否需要建立全局 CSS 变量/Token 体系，还是仅在组件级保持一致性，涉及设计系统层面的决策。宜在后续设计案中明确档位边界与适用范围。
