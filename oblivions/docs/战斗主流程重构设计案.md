# 战斗主流程重构设计案

> 对战斗主流程进行状态机 SQL 统一封装 + 消除重复 + 命名清理。
>
> **状态**：设计阶段，未实施
> **前置**：队列系统内部重构设计案（已实施）

---

## 一、问题

| # | 问题 | 表现 |
|---|------|------|
| 1 | 状态机 SQL 不统一 | `battle_state_machine.func.php` 中 7 个函数直接使用 `global $db, $tablepre` 裸 SQL，与队列重构后 `sql.func.php` 的封装体系不一致 |
| 2 | `battle_cache` 构建重复 | 同样的 `['combatants'=>[...], 'last_qid'=>0, 'is_ambush'=>...]` 结构在 5 个入口/命令函数中重复 |

| 4 | 命名拼写错误 | `battle_excute` / `battle_once_excute` 缺少字母 `e`，应更正为 `battle_execute` / `battle_once_execute` |

## 二、方案

### 2.1 状态机 SQL 封装到 sql.func.php

将 `battle_state_machine.func.php` 中对 `bra_oblbattle_state` 表的所有读写操作迁移到 `sql.func.php`，与队列写操作统一管理。

新增函数：

```php
// ── 状态机读写 ──
obl_state_get($qid)                                    // SELECT state WHERE qid=
obl_state_set($qid, $state)                            // UPDATE state WHERE qid=
obl_state_create($qid, $initial_state, $now)            // INSERT IGNORE
obl_state_destroy($qid)                                 // DELETE WHERE qid=
obl_state_get_all_active()                              // SELECT WHERE state!='IDLE'
obl_state_has_npc_acting()                              // SELECT 1 WHERE state='NPC_ACTING'
obl_state_find_stale($cutoff, $state)                   // SELECT WHERE state= AND updated_at<
```

迁移后 `battle_state_machine.func.php` 中对应函数改为调用 `sql.func.php` 函数，消除裸 SQL。

### 2.2 `battle_cache` 工厂函数

新增 `battle_cache_create()` 统一构建战斗上下文：

```php
function battle_cache_create($initiator_pid, $is_ambush = false, $combatants = null) {
    if ($combatants === null) {
        $combatants = [$initiator_pid => 1];
    }
    return [
        'combatants' => $combatants,
        'last_qid'   => 0,
        'is_ambush'  => $is_ambush,
    ];
}
```

替换以下 5 处：
- `battle.entry.php` 中 4 个入口函数的 `$battle_cache` 赋值
- `oblivions_commands.php` 中 `cmd_handle_obl_battle_action` 的 `$battle_cache` 赋值

### 2.3 统一 actions 解析

- `cmd_handle_obl_battle_start` 中 actions 解析（L81-96）改为调用 `battle_entry_parse_actions`
- `cmd_handle_obl_battle_action` 中 actions 解析（L189-197）改为调用 `battle_entry_parse_actions`

### 2.4 拼写修正

| 当前名 | 新名 | 说明 |
|--------|------|------|
| `battle_excute` | `battle_execute` | 补充缺失字母 e |
| `battle_once_excute` | `battle_once_execute` | 补充缺失字母 e |

所有调用点同步更新（`battle.main.php` 内部 + 其他文件引用）。

## 五、深度分析

### 5.1 战斗生命周期完整性评估

**当前生命周期**（以玩家突袭 → 多轮次 → 结束为例）：

```
命令 1: obl_battle_start
  → battle_entry_player_ambush
  → battle_main(verify → excute)          # 先执行动作
  → battle_manage_queue                    # 后补票建队列
  → tick advance → state: PLAYER_ACTING → NPC_ACTING

命令 2+: obl_battle_action (玩家回合)
  → state: WAITING_PLAYER → PLAYER_ACTING  # 状态机转换
  → battle_main(verify → excute)
  → battle_manage_queue
    → mark_done → 解散/重建 → try_end → AP提前恢复
  → tick advance → state: PLAYER_ACTING → NPC_ACTING

tick 调度: obl_tick_phase_battle_npc (NPC 回合)
  → NPC 行动 → state: NPC_ACTING → WAITING_PLAYER / NPC_ACTING(循环)
```

**评估**：生命周期完整，四个阶段（发起→执行→推进→结束）均有覆盖。但有两个语义模糊点：
- AP 恢复在玩家行动**末尾**（先于 NPC 回合），而非在玩家下一回合**开始**。功能正确但行为反直觉
- `battle_cache['combatants']` 在突袭入口初始化为仅含自己（`[$pid => 1]`），目标由 `battle_once_excute:L120` 在执行阶段**隐式加入**。初始时 `battle_get_alive_pids` 只返回自己，逻辑等价但不易读

### 5.2 大函数拆分评估

| 函数 | 行数 | 结论 |
|------|------|------|
| `battle_once_excute` | 57 | 每步 1-3 行，注释清晰，复杂度和耦合是执行逻辑固有的，不拆分 |
| `battle_queue_create` | 102 | 刚重构完，不在本次范围 |
| `obl_tick_phase_battle_npc` | 70 | 单一循环遍历活跃战场，逻辑连贯，不拆分 |

**结论**：无需要拆分的大函数。

### 5.3 过度设计评估（合并候选）

| 候选 | 现状 | 结论 |
|------|------|------|
| `battle_state_init`(1行) vs `battle_state_clear` | 职责相反（init vs clear） | 不合并 |
| `battle_target_alive_check` + `battle_target_distance_check` + `battle_target_check` | 组合模式，分解恰当 | 不合并 |
| `battle_ap_recover` 单调用点 | 有且仅被 `battle_queue_prepare_next_round` 调用 | 保留；函数名是对逻辑的显式表达，内联会损失可读性 |

**结论**：无过度设计。所有拆分合理的函数应保持。

### 5.4 潜在逻辑问题

**问题 A — 状态机死转换表条目**：`battle_state_machine.func.php:127-129`

```php
OBL_BS_ENDED => array(
    'cleanup' => OBL_BS_IDLE,
),
```

`ENDED → cleanup → IDLE` 转换从未被触发。`obl_battle_state_destroy` 直接 DELETE 状态记录，`obl_battle_state_get` 在记录不存在时返回 `IDLE`。该转换表条目是死代码。

**问题 B — `battle_cache['combatants']` 隐式填充脆弱**：

`battle_once_excute:L119-126` 在执行阶段通过以下方式添加目标到 `combatants`：
```php
$battle_cache['combatants'][$target_data['pid']] = 1;
```

这是"后补票"模型的核心机制——队列创建时 `combatants` 必须已包含所有参战者。如果 future 重构调整了 `battle_main` → `battle_manage_queue` 的执行顺序或在 `battle_once_excute` 中提前 return，`combatants` 可能不完整 → **队列丢失参战者**。

当前功能正确，但此隐式依赖是设计约束，未来重构时需特别注意。

**问题 C — 注释过期**：`enemy_ai.func.php:112` 注释引用 `battle_finish_check`（旧名），实际函数已重命名为 `battle_queue_try_end`。
