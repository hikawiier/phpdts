# 道具系统设计案 - 执行拆分方案

> 配套文档：[道具使用与合成系统-设计案.md](./道具使用与合成系统-设计案.md)
>
> 本案将设计案的§十"实施顺序"（4 步）细化为 6 个可独立验证的执行单元，明确每个单元的输入、产出、依赖与验证方式。

---

## 一、拆分原则

1. **数据层先行**——所有代码依赖数据结构，数据层必须最先完成
2. **Tag 系统独立**——Tag 是 use 系统和 craft 系统的共同基础，需独立完成和验证
3. **use 系统先于 craft 系统**——craft 的 `item_consume_materials` 调用 use 的 `item_consume_itms`（耐久扣减逻辑）
4. **匹配算法与命令入口分离**——匹配算法是 craft 的核心逻辑，需独立验证各种边界 case；命令入口和 API 是接口层，依赖匹配算法正确
5. **前端独立**——设计案已明确前端 UI 独立成设计案，不在本案执行范围。前端类型定义（`vex-vue/src/types/craft.ts`）和 API 端点常量（`vex-vue/src/api/endpoints.ts`）随前端模块一并处理，但后端 API 响应结构需与设计案§四/§六保持一致

## 二、单元总览

| 单元 | 名称 | 依赖 | 核心产出 | 验证方式 |
|------|------|------|---------|---------|
| **U0** | 数据层 - 道具表 | 无 | `item_table.php` 扩展（新增字段 + 新建道具条目） | 配置可加载，新字段有默认值，新道具可查询 |
| **U1** | 数据层 - 配方/POI/Config/Locale | U0 | `recipe_table.php` / `poi_table.php` / `obl_config.php` / locale 文件 | 配方可读取，POI 可加载，locale 文件可导入 |
| **U2** | Tag 系统 | U0 | `item/item.tag.func.php` + bootstrap 注册 | Tag 查询函数可调用 |
| **U3** | 使用系统 | U2 | `item/item.use.func.php` + 命令路由 + handler + API 扩展 | `obl_use_item` 命令可调用 |
| **U4** | 合成系统 - 匹配与消耗 | U1, U2, U3 | `item/item.craft.func.php`（核心匹配算法） | 匹配算法单元测试通过 |
| **U5** | 合成系统 - 命令与 API | U4 | `item/item.craft.func.php`（命令入口）+ 命令路由 + 3 个 API 端点 | `craft_preview` → `obl_craft` 全流程通过 |

> **前端模块**（CraftModal / InventoryList / 工作台入口 / `types/craft.ts` / `api/endpoints.ts`）独立成设计案，不在本案执行范围。

## 三、依赖关系图

```
U0 (道具表)
├──→ U1 (配方/POI/Config/Locale)
│       └──→ U4 (合成-匹配与消耗)   [U4 的 item_get_recipe 依赖 U1 的 recipe_table]
└──→ U2 (Tag 系统)
      ├──→ U3 (使用系统)
      │     └──→ U4 (合成-匹配与消耗) ──→ U5 (合成-命令与API)
      └──────────────────────────────────→ U4
```

**关键依赖说明**：
- **U1 → U4**：U4 的 `item_get_recipe` / `item_get_all_recipes` 读取 U1 创建的 `recipe_table.php`。U4 的匹配算法验证需要配方数据驱动。
- **U3 → U4**：craft 的 `item_consume_materials` 在 `consume='durability'` 模式下调用 use 的 `item_consume_itms`。若要 U3、U4 并行开发，需先将 `item_consume_itms` 移至 `item.tag.func.php` 作为通用道具操作函数——但不推荐，耐久扣减语义上属于使用系统。

  - `item_consume_materials(&$pdata, $materials, $slots, $workbench_materials=[])` — 素材消耗（§5.5.8，含 `$slot_map` 槽位映射）

**验证**（可用 PHP 测试脚本或断言，建议放 `oblivions/tests/` 下）：
- `item_resolve_material_mapping` 基础 case：
  - `[cloth×3]` → 匹配 `craft_bandage`，返回 mapping
  - `[cloth×2]` → 不匹配 `craft_bandage`（数量不足），返回 null
  - `[cloth×4]` → 不匹配（多放导致无法完全消耗），返回 null
- `item_can_consume` 约束：
  - 工作台素材（`source='workbench'`）+ `consume='all'` → 返回 false
  - 工作台素材 + `consume='none'` → 返回 true
  - 背包素材 + 任意 consume → 返回 true
- `min_level` 检查：
  - `tool_level=2` 的素材 + `min_level=1` 的槽位 → 匹配
  - `tool_level=1` 的素材 + `min_level=2` 的槽位 → 不匹配
- **同一素材不能同时匹配 item_id 槽位和 tag 槽位**（§5.5.7 规则 6）：
  - 配方 `[{item_id: 'cloth', count:1}, {tag: 'tag_combustible', count:1}]`，放置 `[cloth×2]` → 匹配（两个 cloth 分别消耗到两个槽位）
  - 配方 `[{item_id: 'cloth', count:1}, {tag: 'tag_combustible', count:1}]`，放置 `[cloth×1]` → 不匹配（同一 cloth 不能同时满足两个槽位）
- `item_consume_materials` 槽位映射：
  - `$slots=[1,3,5]`，槽位 3 为空 → 跳过空槽位后仍正确扣减槽位 1 和 5 的道具

7. 多放素材（`cloth×4`）→ `craft_preview` 返回 `match_count=0, craftable=false`（素材无法完全消耗导致不匹配，非指向性不明确场景）
8. 放入模糊组合（如同时匹配多个配方）→ `craft_preview` 返回 `match_count>=2, craftable=false`（指向性不明确）

## 五、执行顺序建议

```
U0 → U1 → U2 → U3 → U4 → U5
```

严格串行。理由：
- U1 依赖 U0（配方的 `item_id` 引用 `item_table`）
- U2 依赖 U0（Tag 系统读取 `item_table.tags`）
- U3 依赖 U2（use 系统调用 `item_get_tags`）
- U4 依赖 U1 + U2 + U3（craft 调用 `item_get_recipe` 读取 recipe_table / `item_get_tags` / `item_get_tool_level` / `item_consume_itms`）
- U5 依赖 U4（命令入口调用匹配算法）

**不可并行的关键约束**：
- U3 必须先于 U4 完成，因为 `item_consume_materials`（U4）调用 `item_consume_itms`（U3）
- U1 必须先于 U4 完成，因为 `item_get_recipe` / `item_get_all_recipes`（U4）读取 `recipe_table.php`（U1 产出）
