# NPC 逃跑动画与半透明状态 — 设计案

> 日期：2026-07-14
> 范围：vex-vue 前端战斗演出（逃跑动画顺序修正 + 逃跑 NPC 半透明视觉提示）
> 后端：无改动（复用现有 `active` 字段链路）

---

## 1. 问题描述

NPC 在自己回合执行逃跑动作时，演出顺序为：先播放**战报回放**（modal_text 阶段），然后才播放**逃跑动画**。玩家先看到战斗日志文字，再看到 NPC 逃跑的视觉表现，顺序割裂。

## 2. 根因

战斗回放的 turn segment 6 阶段顺序为：

```
segment_context → prepare_map → action_choreography → combatant_cleared → modal_text → damage_linger
```

`combatant_cleared` 阶段（处理逃跑退场）在 `modal_text`（战报回放）**之前**。理论上逃跑动画应先于战报回放播放，但当前 `playCombatantCleared` 对 `visual_policy === 'retreat'` 的逃跑 NPC 返回 `completedTask()`——即不播任何动画，直接放行。

结果：逃跑 NPC 的退场动画被推迟到战斗结束后的 handoff 阶段（`startCommit` 中播放 `move`），而战报回放在 `modal_text` 阶段就已播放。玩家先看到文字，后看到动画。

`visual_policy === 'settle-in-place'`（NPC 退到同格）的路径正常——它在 `combatant_cleared` 阶段直接播 `fade`，不推迟。

## 3. 与 world rebase "打架"问题的历史

此前 retreat 模式不在 `combatant_cleared` 播动画，是为了避免与 world rebase 动画打架。旧实现的三段视觉跳变：

```
fade（消失）→ reset-visible（在原格重新出现）→ move（移动到新格）
```

玩家看到"敌人消失 → 在原格重新出现 → 又移动一格"。

**但经代码验证**，这个"打架"的根因不是 world rebase 本身——`deriveRebaseMoveActorIds` 已排除退出战斗的 actor，world rebase 不操作逃跑 NPC。真正原因是 `startCommit` 的 retreat 路径在 `move` 之前错误地播了 `reset-visible`（在旧位置重新出现）。

当前 `startCommit` 的 retreat+lease+target 路径已通过 `continue` 跳过 `reset-visible`，只播 `move`。因此在 `combatant_cleared` 阶段补播逃跑动画，不会重演历史"打架"。

## 4. 设计方案

### 4.1 核心思路

放弃"逃跑 = 单纯移动"的视觉语义，改为"逃跑 = 淡出 + 在退避格弹起 + 持续半透明"。

- **淡出**：NPC 在当前格 fade out（alpha 1→0），传达"离开战斗"的语义
- **弹起**：NPC 在退避格 arrive（alpha 0→1 + scale 0.3→1），传达"出现在新位置"
- **半透明**：弹起后 NPC 保持半透明（filter opacity 0.5），传达"已逃跑，不再是战斗成员"

三层语义叠加，玩家无需阅读战报就能直观感知"这个 NPC 逃跑了"。

### 4.2 半透明机制：复用现有 `active` 字段

#### 现有半透明机制

非战斗 NPC 在战斗中的半透明通过 CSS 实现：

```css
.entity.entity-dimmed { filter: opacity(0.5); }
```

触发条件（`MapGrid.vue` `entityClass`）：
- `currentMode === 'battle'`（战斗模式）
- `hasActiveCombat === true`（场上至少有一个 `inCombat===true` 的实体）
- `entity.inCombat === false`（NPC 不在 combatants 中）

用 `filter: opacity()` 而非 CSS `opacity`，因为 GSAP alpha 直接写 inline `opacity`，会覆盖 class 上的 `opacity`；`filter` 是独立属性，最终效果 = GSAP opacity × filter opacity。

#### 逃跑 NPC 的字段链路

后端链路（无需改动，已正确实现）：
1. `combat_effect_escape` → `combat_state_clear` → `battle_queue_exit` → `obl_queue_set_active(pid, qid, 0)`：逃跑 NPC 队列行标 `active=0`，**不删行**
2. `obl_state_build_combat_context` 从 `obl_fetch_queue_all_by_qid` 取所有队列行（含逃跑 NPC），`obl_state_combatant_view` 正确构建 `active=false`

前端链路（问题所在）：
3. `mergeCombatContext`（`character.ts`）：逃跑 NPC 仍在 combatants 数组 → `inCombat=true`（硬编码），`active=false`（正确传递到 `CombatState.active`）
4. `entities.ts`：只映射 `inCombat`，**丢弃 `active`**
5. `MapGrid.vue`：`entity-dimmed` 只看 `inCombat`，不看 `active` → 逃跑 NPC 永远不半透明

#### 修复：让 `entity-dimmed` 纳入 `active`

`active=false` 这个信号已从前端传到视图层门口，只差最后一步纳入条件：

- `MapEntity` 类型加 `active?: boolean` 字段
- `entities.ts` 映射 `active: c.combat?.active`
- `MapGrid.vue` `entity-dimmed` 条件改为：`inBattle && hasActiveCombat && (entity.inCombat === false || entity.active === false)`

这样逃跑 NPC（`inCombat=true, active=false`）会触发半透明，与非战斗 NPC（`inCombat=false`）共用同一套 `filter: opacity(0.5)` 机制。

### 4.3 逃跑动画：新增 `escape-relocate` kind

#### 动画语义

`escape-relocate` = fade out（当前格）→ teleport anchor（退避格）→ arrive（弹起）。

三段串行：
1. `fadeOut(elements.visibility)`：alpha 1→0，duration 0.35
2. `gsap.set(elements.anchor, { x: target.x, y: target.y })`：瞬间移动 anchor 到退避格
3. `arriveAnim(elements)`：alpha 0→1 + scale 0.3→1，弹起效果

这与现有 `playMoveAction` 的 tier='long' 路径类似（`gsap.set` + `arriveAnim`），只是前置了一个 `fadeOut`。

#### 通道需求

`escape-relocate` 操作 `spatial`（anchor 位置）、`pose`（scale）、`visibility`（alpha），需要租约 `['spatial', 'pose', 'visibility']`。

`requiredChannels`（`useActorRuntime.ts`）加映射：`escape-relocate` → `['spatial', 'pose', 'visibility']`。

#### 与 handoff 的衔接

`playCombatantCleared` 中 retreat 模式改为播 `escape-relocate`（替代 `completedTask()`）。动画完成后，NPC 的 anchor 已在退避格，alpha=1（arrive 恢复），但 `filter: opacity(0.5)` 让它视觉上半透明。

`startCommit` 的 retreat 路径需要跳过 `move`（动画已在 `combatant_cleared` 完成），直接 `release({ reconcile: true })` 释放租约。`releaseLease` 不重置 visibility，alpha=1 保持，配合 `filter: opacity(0.5)` 维持半透明。

### 4.4 半透明生命周期

| 阶段 | `inCombat` | `active` | `currentMode` | `hasActiveCombat` | 半透明 |
|------|-----------|----------|--------------|-------------------|-------|
| 逃跑动画期间 | true | false | battle | true | 是（filter 0.5 × GSAP alpha） |
| 动画结束→战斗继续 | true | false | battle | true | 是（持续） |
| 战斗结束 | undefined | undefined | 非 battle | false | 否（`inBattle=false`） |

逃跑 NPC 在战斗期间一直 `active=false` → 一直半透明。战斗结束后 `mergeCombatContext(null)` 清空所有 combat 字段，`currentMode` 离开 battle，半透明自然消失。无需额外的标记清理逻辑。

#### 动画期间的视觉细节

`mergeCombatContext` 在收到后端响应时同步执行，早于 battlelog 异步播放。因此逃跑动画开始时，NPC 已经是 `active=false`，`filter: opacity(0.5)` 已生效：

- fade out 阶段：GSAP alpha 1→0，filter 0.5 → 视觉 0.5→0（半透明地淡出）
- arrive 阶段：GSAP alpha 0→1，filter 0.5 → 视觉 0→0.5（半透明地弹起）
- 动画结束：alpha=1，filter 0.5 → 视觉 0.5（持续半透明）

"半透明地淡出"比"不透明地淡出"更自然——NPC 已经不活跃了，半透明地淡出符合"它已经不是战斗的一部分"的语义。

## 5. 实现锚点

### 5.1 前端改动（6 文件）

| 文件 | 改动 |
|------|------|
| `types/map-entity.ts` | 加 `active?: boolean` 字段 |
| `stores/entities.ts` | `entities` computed 映射 `active: c.combat?.active` |
| `components/map/MapGrid.vue` | `entityClass` 中 `dimmed` 条件纳入 `entity.active === false` |
| `composables/useActorRuntime.ts` | `play` 加 `escape-relocate` case（fadeOut + set anchor + arriveAnim）；`requiredChannels` 加映射 |
| `stores/battle-actor-executor.ts` | `playCombatantCleared` retreat 模式播 `escape-relocate`（替代 `completedTask()`） |
| `stores/battle-presentation-session.ts` | `startCommit` retreat 路径跳过 `move`，直接 `release`（动画已完成） |

### 5.2 后端改动

无。`active` 字段链路已完整实现。

### 5.3 `escape-relocate` 动画实现

在 `useActorRuntime.ts` 的 `play` 方法中新增 case，复用现有 `fadeOut` 和 `arriveAnim`（`actorAnimations.ts`）：

```
case 'escape-relocate':
  gsap.set(elements.anchor, { width, height, xPercent, yPercent })  // 锚定格子尺寸
  setFacing 根据 target 方向
  animation = gsap.timeline()
    .add(fadeOut(elements.visibility))           // 当前格淡出
    .set(elements.anchor, { x: target.x, y: target.y })  // teleport 到退避格
    .add(arriveAnim(elements))                   // 弹起
  onCompleted = () => { this.currentAnchor = command.target }
```

`arriveAnim` 内部会 `gsap.set(visibility, { alpha: 0 })` 再 to alpha 1，所以 fade out 后的 alpha=0 状态不会冲突。

### 5.4 `startCommit` retreat 路径调整

当前 `startCommit`（`battle-presentation-session.ts`）的 retreat+lease+target 路径：

```
if (handoff.visualPolicy === 'retreat') {
  // 计算 tier，播 move 动画
  animations.push(lease.play({ kind: 'move', target, tier }));
  continue;  // 跳过 reset-visible
}
```

改为：retreat 路径直接 `release({ reconcile: true })`，不播任何动画（`escape-relocate` 已在 `combatant_cleared` 完成）。`reconcile: true` 让 anchor reconcile 到 `pendingAnchor`（已是退避格），alpha 保持 1，`filter: opacity(0.5)` 维持半透明。

## 6. 边界案例

### 6.1 `settle-in-place` 模式（退到同格）

不受影响。`playCombatantCleared` 中 `settle-in-place` 路径仍播 `fade`，NPC 在原地淡出。`active=false` 后也会半透明，但 fade 已经让 alpha→0，视觉上 NPC 消失。`startCommit` 的 `settle-in-place` 路径（非 retreat）走 `reset-visible`，恢复 alpha=1 + filter 0.5 = 0.5 半透明。

### 6.2 战斗中多个逃跑 NPC

每个逃跑 NPC 独立走 `escape-relocate`，互不干扰。`active=false` 独立标记，半透明独立应用。

### 6.3 逃跑 NPC 被玩家追上再次进入战斗

新一轮战斗时 `mergeCombatContext(newContext)` 重建 combat 字段。如果 NPC 再次加入 combatants，`active=true`，半透明消失。如果 NPC 未加入，`inCombat=false`，仍半透明（与非战斗 NPC 一致）。

### 6.4 `escape-relocate` 期间 lease 被取消

`createTask` 的 `scope.cancelled` 机制会取消所有 handle。GSAP timeline 的 `cancel` 会停止动画，NPC 停在当前帧。`releaseLease` 不重置 visibility，alpha 保持当前值。如果取消时 alpha=0，NPC 不可见——但 `startCommit` 的 `release({ reconcile: true })` 会让 anchor reconcile 到退避格，下一帧 world rebase 时 NPC 会在退避格以 alpha=0 出现，`filter: opacity(0.5)` 生效但 alpha=0 仍不可见。

这是一个边界风险。缓解方案：`startCommit` 的 retreat 路径在 `release` 前检查 alpha，如果 alpha<1 则补一个 `reset-visible`（alpha→1）。但这会增加复杂度。考虑到取消是异常路径（如战斗被服务器中断），暂不处理，后续观察是否需要补。

## 7. 设计哲学自校准

- **3.1 降低理解成本**：方案用自然语言讲"为什么逃跑要淡出+弹起+半透明"，不堆砌函数签名。实现锚点表只列文件名和改动方向，不列参数。
- **3.1 快速索引目标**：保留 `escape-relocate`、`active`、`entity-dimmed`、`filter: opacity()`、`playCombatantCleared`、`startCommit` 等索引锚点，读者可从文档反查代码。
- **3.2 概念引入**：`escape-relocate` 是新动画 kind，承载"淡出+teleport+弹起"三段语义，比每次长篇解释更高效，引入合理。
- **3.3 约束是意图的近似**：复用 `active` 字段而非新增 `fled` 标记，因为 `active=false` 已准确表达"不再是战斗成员"的意图，无需额外标记。
