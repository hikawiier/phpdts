# Oblivions 框架优先级推导表

> 本文档是**决策工具**，用于从设计案内容反推框架优先级，决定"接下来该做哪个框架、做之前需要准备哪些资源层内容"。
> 与 [已有功能与差距分析](./已有功能与差距分析.md) 的分工：后者是代码库现状的静态快照（"有什么、没什么"），本文档是动态决策推导（"接下来该做什么"）。
>
> 依据：
> - [第一幕-垃圾岛设计案](./第一幕-垃圾岛设计案.md) v0.1
> - [第一幕-庇护所与新手区资源案](./第一幕-庇护所与新手区资源案.md) v0.6
> - [第一幕-扫雷与死亡捡尸机制-设计案](./第一幕-扫雷与死亡捡尸机制-设计案.md) v0.3

## 一、目的与使用方法

### 1.1 目的

根据现有设计案，回答两个问题：
1. **接下来该进行哪方面的框架设计？**（优先级排序）
2. **框架设计之前应该提供哪些资源层的内容参考？**（前置内容清单）

### 1.2 核心机制：双向推导

- **从内容反推框架优先级**：内容项 A 依赖框架 X，内容项 B 依赖框架 X，内容项 C 依赖框架 Y 而 Y 依赖 X → X 的依赖密度 = 3，优先做 X
- **从框架反推资源层准备**：框架 X 需要内容项 A、B 作为最小验证集；A 当前只有名字没有 Tag/属性 → 做框架 X 前先把 A 的设计补全

### 1.3 使用方式

1. 设计案新增内容项时，按 [§六 编写规范](#六设计案编写规范约束) 给它打 ID、标注依赖框架、标注完整度
2. 定期重新聚合第二层框架清单（更新被依赖数）
3. 跑优先级算法得出 Top 框架，查看其资源层准备清单
4. 补全清单里"名字/概念"级的内容项到"完整"级，再启动框架实现

## 四、优先级推导结论（第三层）

### 4.1 优先级算法

```
优先级分数 = 被依赖数 × 10 + (前置框架已全部满足 ? 100 : 0) - 前置未满足数 × 20
```

- 前置框架已全部满足 = 可立即启动（+100）
- 前置框架未满足 = 被阻塞（-20 × 未满足数）
- **已实现框架不参与排序**（见 §3.0）

## 五、关键发现

### 5.1 遗漏的框架

1. **被动技能系统**：资源案§4.2"抗性跃迁"机制依赖被动技能系统（tag_arc_resistance）。需向 obl_use_item 注册 gain_resistance 效果函数。设计要点：被动技能如何存储、如何触发、如何与战斗系统交互。

2. **环境击杀机制**：垃圾岛案§5.5 远古豆腐 Boss 需要"不接触"击杀方式（环境击杀/引到特定区域/特殊道具），现有战斗系统不支持。这是支线 Boss 的实现瓶颈。

3. **剧情导演层**：非战斗演出导演，对称于战斗演出的 `battle-director.ts`。把后端 emit 的扁平对话节点序列编排成 DialogScript。**被推导表原版遗漏**，因为原版只统计了"对话框组件"的直接被依赖数（3），未识别出"导演层"是独立的框架。实际被依赖数 8+（所有非战斗演出事件）。

### 5.2 关键瓶颈

1. **兔子敌人属性是教程的硬性前置**：4 个兔子变体全是"概念/名字"级，无属性数值。兔子是 P0 教程的核心敌人（event_rabbit_tutorial 依赖它），且阻塞教程流程控制器、爱丽丝 Boss、蟑螂拟态事件（→ 千年虫 Boss）。**建议立即补全 enemy_rabbit_sword 和 enemy_rabbit_tutorial 的属性表。**

2. **对话节点数据结构是非战斗演出的硬性前置**：对话节点类型（Top 5 第 5 名）未定义，阻塞了对话框组件、剧情导演层、教程流程控制器。**建议立即设计对话节点数据结构（分支/顺序/条件/立绘/表情/选项）。**

3. **千年虫 Boss 战是 P1 的关键缺口**：垃圾岛案§3.7 明示"待完善"，但它是第一幕结尾 Boss，是千年虫 Boss 框架（被依赖数 3）的核心验证场景。

4. **~~配方素材列表是 P0 的硬性前置~~**（已解决）：合成系统已实现，recipe_table 已有基础/工作台/高级三档配方。

## 六、设计案编写规范（约束）

> 本节作为硬约束加入设计案编写流程。每次新增内容项时必须遵守。

### 6.1 内容 ID 命名规范

| 类别 | 前缀 | 示例 |
|------|------|------|
| 道具 | `item_` | item_physics_sword |
| Tag | `tag_` | tag_tool_lever |
| 配方 | `recipe_` | recipe_thick_shoes（xxx 用产物名）|
| Body Status | `bs_` | bs_foot_hurt |
| 敌人 | `enemy_` | enemy_rabbit_sword |
| POI | `poi_` | poi_workbench |
| 区域 | `region_` | region_metal_plain |
| 剧情事件 | `event_` | event_rabbit_tutorial |

### 6.2 新增内容项必填字段

每次在设计案里新提一个内容项，必须标注：

```markdown
| 内容 ID | 名称 | 来源（设计案+章节）| 依赖框架 | 完整度 |
```

- **依赖框架**：列出该内容项依赖的所有框架（已有/待建都要标）
- **完整度**：三档之一
  - **名字**：只有名字/概念，没有具体属性/Tag/配方链
  - **概念**：有基本描述（用途、触发条件），但缺关键参数（Tag 列表、素材列表、数值）
  - **完整**：有完整的设计参数，可以直接进入框架验证

### 6.3 更新流程

1. 设计案新增内容项 → 立即打 ID + 标注依赖框架 + 标注完整度
2. 定期（每个开发迭代）重新聚合本文档第二章内容清单
3. 重新跑优先级算法（§4.1），更新 Top 框架排序
4. 启动框架实现前，先查看其资源层准备清单（§4.4），补全"名字/概念"级内容项到"完整"级
