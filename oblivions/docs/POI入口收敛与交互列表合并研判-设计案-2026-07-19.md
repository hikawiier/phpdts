# POI 入口收敛与道具/技能交互合并研判 设计案

> 关联框架：L-9 POI 交互模态框、F-6 POI 道具交互系统、E-10 POI 搜刮三档判定
> 关联原始方案：oblivions/docs/原始方案/搜索建筑物与掉落机制设计案.md §3.1 §3.2 §4.1 §4.2

## 一、任务背景

E-11 昼夜系统、E-12 POI 耐久、F-7 POI 放置/拆除框架已落地。前端 POI 交互模态框（L-9）已实现双态切换（列表态 + 交互态），其中：

- **搜刮型 POI**：通过 `PoiToolSelector` 选择工具/技能，写入 `poiStore.selectedToolId`，由 `poi.search` 透传到后端，影响 E-10 三档判定（base_loot_chance / base_good_event_chance / base_bad_event_chance）与 `loot_table_overrides` 路由。
- **交互型 POI**：通过 `currentPoiInteractions` 列表展示 F-6 配置驱动的可用交互（如打火机点燃火堆），每个 interaction 含 `required_item` / `required_tag` + `available_slots`，点击槽位按钮发送 `poi.interact` 命令。

需解决两个关联问题：

1. 上述两套交互在前端是 PoiToolSelector（右列）vs PoiInteraction 中列"道具交互区"两套独立呈现，研判是否应合并。
2. 当前 `TileActionBar.vue` 直接以 v-for 列出每个 POI 一行，与原始方案"所有 POI 收纳在一个[POI交互]按钮入口"的设计要求不符。

## 二、任务1：搜刮型 / 交互型 POI 道具技能交互合并研判

### 2.1 现状分析

| 维度 | 搜刮型（PoiToolSelector） | 交互型（F-6 道具交互） |
|------|---------------------------|------------------------|
| **语义** | 工具是"修饰符"，最终动作是 `poi.search` | 道具是"动作主体"，`poi.interact` 直接消耗道具产生效果 |
| **后端配置** | POI 模板 `prob_mods_source` 白名单 + `loot_table_overrides` 路由表 | `poi_interactions.php` 配置 `{poi_mechanic × required_item/tag → effect_type + consume_item}` |
| **后端入口** | `poi.search.func.php`（E-10 三档判定） | `poi.interact.func.php`（F-6 分发器） |
| **命令** | `poi.search`（payload: `{iaid, tool_id, skill_id}`，单值字符串） | `poi.interact`（payload: `{slot, iaid}`，整数槽位） |
| **数据投影** | POI 模板字段直投（`prob_mods_source` / `loot_table_overrides`） | tile_actions scope 中 `interactions` 字段（含 `available_slots` 预匹配） |
| **前端组件** | `PoiToolSelector.vue`（右列，单选 + 自动失效） | `PoiInteraction.vue` 中列"道具交互区"（多按钮组） |
| **触发后状态** | 工具不消耗（耐久模型未来扩展）；POI state 进入 searched/cooldown/exhausted | 工具按 `consume_item` 配置消耗（itms-1）；POI state 进入 ignited/exhausted/idle |
| **重复交互** | 同一 POI 可重复搜索（受 `repeatable`/`repeat_limit`/`repeat_cooldown` 限制） | `repeatable=false` 默认；effect_type 内部用乐观锁防重复触发 |

### 2.2 研判问题

#### Q1：前端是否应合并这两套列表？

**结论：不合并。**

理由：

1. **语义本质不同**：搜刮工具是"前置准备 + 修饰符"——玩家选工具改善概率/路由到改良版表，最终动作是 `poi.search`；F-6 道具是"动作主体"——玩家用道具直接触发效果（点燃、开锁、开宝箱），独立于 `poi.search`。语义重合度为零，合并后玩家无法区分"选了工具还要点搜索"vs"直接点道具即触发"。

2. **命令合约不同**：`poi.search` payload 接收 `tool_id`（字符串单值）；`poi.interact` payload 接收 `slot`（整数槽位）。两者在前端的状态管理也不同——`selectedToolId` 是单选 ref；`available_slots` 是后端预匹配的多按钮列表。强行合并会导致 store 状态语义混乱。

3. **注意力分配不同**（DESIGN.md §3.4 注意力稀缺原则）：
   - 搜刮型工具选择是"**参考信息**"——玩家在搜索前评估可用改良路径，UI 容器需要长列表 + 单选高亮。
   - F-6 道具交互是"**直接操作**"——玩家明确知道要用某道具触发效果，UI 容器需要明显的操作按钮。
   两者视觉密度、交互模式、注意力占用本质不同，合并会破坏视觉语言统一性。

4. **当前布局已合理**：PoiToolSelector 在右列（参考区），F-6 道具交互在中列（操作区），这是按"参考 vs 操作"视觉分工的自然结果，并非"两套列表并列在同一处"。

#### Q2：后端是否应统合数据结构？

**结论：不统合。**

理由：

1. **配置驱动模式不同**：
   - 搜刮型走 POI 模板字段（`prob_mods_source` / `loot_table_overrides`），属于"POI 自身属性"——这个 POI 接受哪些工具改良。
   - F-6 走独立配置表 `poi_interactions.php`，属于"道具 × POI mechanic 映射"——某种 mechanic 的 POI 与某种道具的交互规则。
   两者是不同的关注点（"POI 接受什么工具"vs"道具能触发什么效果"），强行合并会破坏配置驱动的清晰语义。

2. **效果分发机制不同**：
   - 搜刮型是"概率修正 + 路由改良版表"——非破坏性，影响 `poi.search` 的掷骰结果。
   - F-6 是"effect_type 分发到命名函数"——破坏性，直接消耗道具 + 改变 POI state + 触发副作用（物化掉落、emit 事件）。
   两者在 effect 投影、并发安全、状态机推进上的实现完全不同，合并需重写两套已稳定的执行管道。

3. **F-6 框架的"确认函"设计哲学**（Dian.md F-6）：玩家无需 memorize 配方，系统主动告知可用交互——这是 F-6 独有的语义，搜刮型不需要这种语义（搜刮型只关心"哪些工具能改良"，由前端按 prob_mods_source 过滤即可）。

#### Q3：是否需要前端 UI 微调？

**结论：在两个区域的标题文案上明确语义差异，避免玩家混淆。**

当前两个区域标题：

- 右列 PoiToolSelector：`可用工具/技能`（语义模糊）
- 中列 F-6 道具交互区：`道具交互`（语义模糊）

调整为：

- 右列：`可用工具（搜刮辅助）` —— 明确是用于搜刮的修饰符
- 中列 F-6 区：`道具操作（直接触发）` —— 明确是直接触发效果

**这是唯一的前端 UI 改动**，不涉及组件合并、数据结构变更、命令合约变更。

### 2.3 设计决策汇总

| 决策点 | 决策 | 理由 |
|--------|------|------|
| 前端列表合并 | ❌ 不合并 | 语义本质不同、命令合约不同、注意力分配不同 |
| 后端数据结构统合 | ❌ 不统合 | 配置驱动模式不同、效果分发机制不同、F-6 确认函语义独有 |
| 前端 UI 微调 | ✅ 区域标题语义化 | `可用工具（搜刮辅助）` vs `道具操作（直接触发）`，避免玩家混淆 |

## 三、任务2：POI 按钮总入口重设计

### 3.1 现状分析

`TileActionBar.vue` 当前的"统一交互列表"区：

```
┌─ 常驻按钮区 ──────────────────
[E] 探索周围  [合成]  [区域切换]
┌─ 统一交互列表（2列网格） ─────
[脚边道具 ×N]
[POI 名称 1] [POI 名称 2]
[POI 名称 3] ...
```

每个 POI 一行，点击 → `poiStore.openModal()` → 打开 PoiModal 列表态（再次显示所有 POI 卡片）。

**问题**：

1. **不符合原始方案 §3.1 §4.1**：原始方案要求"在[脚边道具]右侧出现[POI交互]按钮"——单按钮入口，而非多行展开。
2. **冗余渲染**：列表态 PoiModal 与 TileActionBar 重复呈现 POI 列表，玩家在两层 UI 看到相同信息。
3. **操作路径过长**：从 TileActionBar 点击 POI → PoiModal 列表态 → 再点击 [检查] → 交互态。

### 3.2 重设计方案

#### 3.2.1 TileActionBar 入口收敛

将"统一交互列表"区改为：

```
┌─ 常驻按钮区 ──────────────────
[E] 探索周围  [合成]  [区域切换]
┌─ 行动入口区 ─────────────────
[脚边道具 ×N]    [POI 交互 ×N]    ← 仅当对应内容存在时显示
```

**实现要点**：

- 删除 `v-for poi in pois` 渲染逻辑，改为单按钮 `[POI 交互 ×N]`（N 为当前格 POI 数量）。
- 与 `[脚边道具 ×N]` 并列，行内布局（flex），符合原始方案"右侧"语义（在脚边道具右侧）。
- 仅当 `hasPois` 为真时渲染该按钮。
- 按钮文案：`[POI 交互 ×N]`，N 为可见 POI 数量；N=1 时仍显示（保持入口稳定性，避免单 POI 时按钮消失造成视觉跳动）。
- 点击 → `poiStore.openModal()`（不变）。

#### 3.2.2 PoiModal 列表态卡片按钮文案动态化

当前所有卡片按钮文案为 `[检查]`，应按 POI 类型动态化：

| POI 类型 | 判定条件 | 按钮文案 |
|---------|---------|---------|
| 搜刮型 | `searchable=true && !mechanic` | `[搜刮]` |
| 交互型（F-6 mechanic） | `mechanic` 以 `interact_` 前缀开头 | `[交互]` |
| 机制型（图腾/工作台） | `mechanic` 不以 `interact_` 开头且非空 | `[触碰]` |
| 地标型 | `!searchable && !mechanic` | `[检查]` |

**实现要点**：

- 在 `PoiModal.vue` 中新增 `poiActionButtonText(poi)` computed 函数，按上表判定。
- 按钮点击行为不变（仍调用 `onEnterInteraction(iaid)`）——所有 POI 都进入同一交互态，由 PoiInteraction 内部按 POI 类型自动展示对应区域。

#### 3.2.3 列表态卡片信息密度

按原始方案 §4.2 "每个 POI 为一个带操作按钮的独立卡片"，当前实现已满足。本次重设计仅微调卡片显示：

- 保留：名称、状态徽章、徽章附加信息、描述
- 调整：描述截断为单行省略号（已实现，避免长描述挤占注意力）
- 新增：若 POI 有未拾取道具，徽章附加信息已显示 `N个物品`（已实现，无需改动）

### 3.3 UI 设计要点

1. **入口稳定性**：单按钮 `[POI 交互]` 始终在固定位置（脚边道具右侧），不随 POI 数量变化布局。
2. **数量提示**：按钮文案 `×N` 让玩家在打开模态框前知道有多少 POI 待交互。
3. **滚动支持**：PoiModal 列表态 `.modal-body { max-height: 80vh; overflow-y: auto }` 已实现，多 POI 时可滚动。
4. **视觉风格**：与现有 PoiModal 一致——ASCII 标题、灰阶基底、term-btn 风格按钮。

在 `Dian.md` 的 `#### 框架 L-9：POI 交互模态框` 条目中：

### 4.3 代码锚点

无需调整——L-9 的代码锚点文件集合（`PoiModal.vue` / `PoiInteraction.vue` / `PoiToolSelector.vue` / `PoiFeedbackPanel.vue` / `stores/poi.ts`）保持不变。

### 5.4 冗余检查

- ✅ 无重复状态：`poiStore.modalOpen` / `modalMode` 状态机不变。

### 5.5 全面性检查

按 POI 类型覆盖所有场景：

| POI 类型 | 列表态按钮 | 入口收敛后行为 |
|---------|-----------|---------------|
| 搜刮型（supply_cache、weapon_locker 等） | `[搜刮]` | 进入交互态 → 显示概率条 + PoiToolSelector + 搜索按钮 |
| 交互型（locked_door、locked_chest、campfire_unlit） | `[交互]` | 进入交互态 → 显示 F-6 道具交互区 + 反馈区 |
| 机制型（life_totem、skill_totem、forge_anvil_poi 等 craft_source） | `[触碰]` | 进入交互态 → 显示机制结果区 |
| 地标型（landmark） | `[检查]` | 进入交互态 → 显示 POI 信息区（无可操作区） |

**特殊场景**：

- 营火点（campfire_site，searchable=true + 非interact_ mechanic=null）→ `[搜刮]`：可搜刮的纯掉落型 POI。
- 熄灭的营火（campfire_unlit，searchable=false + mechanic=interact_campfire）→ `[交互]`：F-6 交互型，点燃后 state=ignited。
- 已点燃的营火（campfire_unlit state=ignited）→ 后端 `obl_get_available_interactions_for_poi` 返回空 interactions（state 不匹配 required_state=idle）→ F-6 区不渲染；前端按 state=ignited 显示状态徽章"已点燃"。
- 已搜索的机制型 POI（life_totem searched=true）→ `[触碰]`：按钮文案不变，进入交互态显示已触发的机制结果。

## 七、遗留风险

1. **入口收敛后的视觉密度**：单按钮 `[POI 交互 ×N]` 比多行展开信息密度低，玩家无法在打开模态框前看到每个 POI 的状态徽章。**评估**：可接受——状态徽章在 PoiModal 列表态卡片中显示，玩家点击按钮后立即看到；按钮文案 `×N` 提示数量，避免空模态框意外。

2. **POI 数量=1 时的入口**：单 POI 时仍显示 `[POI 交互 ×1]` 按钮而非直接展开。**评估**：保持入口稳定性更重要——若单 POI 时按钮消失会让玩家困惑"为什么有时是按钮有时是直接列表"。

3. **未来扩展**：若后续需要在地格直接显示某些 POI 的快速操作（如已点燃的营火直接拆除），可在 `[POI 交互 ×N]` 按钮旁增加快捷操作按钮——但当前不实现，避免过度设计。
