# 战斗命令预校验缺失与原因精度丢失修复设计案

> 状态：审查修订与实施待开始
> 日期：2026-07-16
> 关联文档：
> - [`狼狈被动技能与持续状态效果框架设计案.md`](./狼狈被动技能与持续状态效果框架设计案.md) §0.5、§5.2、§10
> - [`逐目标结算与动态参战框架重构设计案.md`](./逐目标结算与动态参战框架重构设计案.md) §6.3、§10.3、§12.2
> - [`战斗上下文视图与动作链失败策略设计案.md`](./战斗上下文视图与动作链失败策略设计案.md) §4.5
> - [`命令锁与战斗瞄准权威判定重构设计案.md`](./命令锁与战斗瞄准权威判定重构设计案.md)
> 适用范围：Oblivions 后端 combat pipeline、command contract、前端 AimMode 候选筛选

> **实际预备的场合（2026-07-16 重校准）**：本设计案起源于 flustered 阻止被动参战所暴露的"`battle.start` 缺失前置 capability 预校验"结构性问题。**flustered 的 `capability_denies` 已于 2026-07-16 移除 `participate_combat`**（设计意图：狼狈只阻止主动行动，不阻止被动参战），因此 flustered 不再触发本设计案所描述的 target-side 预校验路径。但本设计案**仍然保留并预备实施**，因为：
>
> 1. **结构性问题真实存在**：`battle.start` 命令路径缺失 target-side capability 预校验层、第一次 project 静默吞掉失败信息、verify 阶段 reason 被覆盖为 `NO_VALID_TARGET`——这些结构性偏离不因 flustered 而生，也不会因 flustered 移除而消失
> 2. **未来 `participate_combat` 阻塞源**：眩晕、束缚、沉默等"完全无法行动"语义状态将在该状态独立声明 `participate_combat` deny，届时若没有本设计案的预校验层，将复现完全相同的问题
> 3. **`combat_action` 阻塞源仍现存**：flustered active 仍 deny `combat_action`，pipeline actor verify 路径的 reason 精度问题对 flustered 仍然存在
> 4. **`combat_can_engage()` 的接入点保留**：[`combat.preview.php:223`](../include/game/combat/combat.preview.php#L223) 的 `participate_combat` 检查路径不因 flustered 移除而删除，为未来状态保留接入点
>
> 下文以 flustered 为示例的复现日志、链路追踪、验收测试均作为**历史溯源**与**未来状态回归模板**保留，不应被理解为"flustered 当前仍触发该问题"。

## 1. 问题来源

> **历史溯源**：以下复现基于 flustered 仍 deny `participate_combat` 的版本。flustered 已于 2026-07-16 重校准，不再触发该路径，但相同问题将在未来"完全无法行动"语义状态（眩晕/束缚/沉默）出现时复现。本节保留作为问题溯源与未来状态回归模板。

玩家在 flustered active 状态下被作为 throw 目标时，前端未阻止选择、后端未在命令入口预校验，verify 阶段才发现并返回 `NO_VALID_TARGET`。玩家收到的反馈既不及时也不精确，导致玩家与开发者都误以为是"无目标"问题而非"目标被狼狈阻塞"。

复现日志（`oblivions/cache/battles/combat_debug.log` + `obl_battle_log_debug.log`）：

| 阶段 | 事实 |
|------|------|
| 第一次战斗（tick 1-3） | 玩家 pid=19 同时 throw pid=6、pid=4，二者均被加入战斗；pid=6、pid=4 陆续 escape，tick=3 末尾 disband 触发 boundary activation（starts=4, expires=5） |
| tick=4 WORLD_AI 阶段 | pid=4、pid=6 被 `capability:status_blocked` 正确阻止（设计案 §5.2 设计意图正确生效） |
| 第二次战斗（tick=4 末尾 22:26:56） | 玩家再次发起 battle.start 提交 `[throw pid=6, throw pid=4]`；`DISPATCH_CACHE {"19":1,"6":1}`（pid=4 不在 initial roster）；`VERIFY_END verified_count=1`；emit `action_failed reason=NO_VALID_TARGET` |

**flustered 在下一 tick 阻止参战是设计意图，不是 BUG**（现已重校准：狼狈不再阻止被动参战，只阻止主动行动）。本设计案修复的是"为何所有阶段都漏掉了 capability 检查，直到动作执行前才被发现"这一**结构性问题**，以及因此衍生出的"失败原因精度丢失"问题——这些问题对当前 flustered 的 `combat_action` 阻塞、未来状态的 `participate_combat` 阻塞同样适用。

### 2.1 关键代码事实

**`combat_can_engage` 已实现 target capability 检查**（[`combat.preview.php:201-239`](../include/game/combat/combat.preview.php#L201-L239)）：

```php
function combat_can_engage(&$actor_data, &$target_data): array {
    $evaluation_tick = combat_next_action_evaluation_tick();
    $actor_capability = actor_capability_decide($actor_data, 'enter_combat', null, $evaluation_tick);
    if (empty($actor_capability['allowed'])) {
        return [..., 'reason' => 'actor_capability_blocked', 'capability_failure' => ..., 'plan' => null];
    }
    // ...
    $target_capability = actor_capability_decide($target_data, 'participate_combat', null, $evaluation_tick);
    if (empty($target_capability['allowed'])) {
        return [..., 'reason' => 'target_capability_blocked', 'capability_failure' => ..., 'plan' => null];
    }
    // ...reachability plan...
}
```

但 `battle.start` handler 完全没有调用它——它只被 `combat.can_engage` 命令调用（[`obl_command_handlers.php:64-76`](../include/command/obl_command_handlers.php#L64-L76)），即前端"点击敌人发起战斗前的预判"。

**`combat_start_battle` 的第一次 chain_project**（[`combat.core.php:292-296`](../include/game/combat/combat.core.php#L292-L296)）：

```php
$projection = combat_chain_project($actor, $atk_act, $prebattle_cache, $obl_battle_log, [
    'emit_failures' => false,  // ← 静默吞掉所有失败
    'check_ownership' => true,
    'check_cd' => true,
]);
```

这次 project 已经发现 throw pid=4 capability blocked（通过 `combat_target_units_run` → `combat_participation_classify_data`），但因为 `emit_failures=false`，失败信息只保留在 `$projection['actions']` 中，没有任何反馈通道。

**`combat_start_battle` 的失败 action 处理**（[`combat.core.php:297-311`](../include/game/combat/combat.core.php#L297-L311)）：

```php
foreach ($atk_act as $index => $action) {
    $projected = $projection['actions'][$index] ?? ['success' => false];
    if (empty($projected['success'])) continue;  // ← 默默跳过失败 action
    foreach (($projected['target_results'] ?? []) as $target_result) {
        if (($target_result['status'] ?? '') === 'resolved' && (int)($target_result['pid'] ?? 0) > 0) {
            $initial_target_pids[(int)$target_result['pid']] = true;
        }
    }
    if (!empty($initial_target_pids)) {
        $initial_hostile_index = $index;
        break;
    }
}
```

失败 action 被直接 `continue`，玩家以为提交的 N 个 action 都有效，实际只有第一个能 enlist 的被采用。

## 3. 与设计案的偏离

### 3.1 设计案 §10 四层一致性

[`狼狈被动技能与持续状态效果框架设计案.md §10`](./狼狈被动技能与持续状态效果框架设计案.md#L538-L541) 规定的"战斗入口与参战约束四层一致性"：

1. `battle.start` actor gate 检查 `enter_combat` ✅ 实现（[`combat.core.php:265-273`](../include/game/combat/combat.core.php#L265-L273)）
2. `combat_can_engage()` 返回 actor/target capability failure ✅ 实现（[`combat.preview.php:201-239`](../include/game/combat/combat.preview.php#L201-L239)），**但未被 `battle.start` 调用**
3. initial roster 与 `combat.participation.php` 在返回 `joinable` 前检查目标 `participate_combat`；失败时返回 `blocked` ✅ 实现（[`combat.participation.php:65-73`](../include/game/combat/combat.participation.php#L65-L73)），**但只在 verify 阶段执行，不在 initial roster 阶段执行**
4. combat pipeline actor verify 检查 `combat_action` ✅ 实现（在 `combat_target_units_run` 路径中）

**第 3 层的偏离**：设计案要求"initial roster 与 participation 在返回 joinable 前检查"，但当前实现中：
- pid=4 不在 initial roster 中（roster 只含主目标 pid=6）
- pid=4 通过 throw action 在 verify 阶段才走 participation classify
- 设计案 §10 第 3 点的本意是"任何加入战斗的路径都要检查 capability"，但实现层把"initial roster 检查"和"verify 阶段 participation 检查"耦合在 `combat_target_units_run` 内，没有独立的 initial roster capability gate

### 3.2 设计案 §0.5 capability 公开投影

[`狼狈被动技能与持续状态效果框架设计案.md §0.5 第 4 点`](./狼狈被动技能与持续状态效果框架设计案.md#L19)：

> **Capability 组合**：...evaluator 只读 actor。内部 decision 可含完整来源，**公开 projector 必须过滤 hidden status，必要时仅返回 opaque `status_blocked`**。

第 8 点：

> **前端契约**：玩家/NPC 公开投影 pending 与 active；pending 显示"狼狈·待生效"、不限制能力，active 才显示剩余 tick。**capabilities 返回首版完整集合，前端整体替换**；缺键仅在体验层宽容为 allowed。

前端 AimMode 应该消费 capability 公开投影，在候选筛选阶段就过滤掉 `participate_combat` blocked 的目标。当前实现完全没有这一步。

### 3.3 设计案 §10.3 / §12.2 失败事件结构

[`逐目标结算与动态参战框架重构设计案.md §10.3`](./逐目标结算与动态参战框架重构设计案.md) 规定 `target_skipped` 事件结构：

```json
{ "event_type": "target_skipped", "payload": { "action_uid": "...", "target_pid": 12, "reason": "TARGET_IN_OTHER_BATTLE" } }
```

§12.2 规定 `partial/failed` 状态的 action 必须返回 `targets` 数组，每个 target 含 `pid/status/participation/reason`。

当前实现完全没有 emit `target_skipped` 事件，`action_failed` 也不携带 `detail.targets`，per-target 的具体 reason 被统一覆盖为 `NO_VALID_TARGET`。

## 4. 结构性框架基准问题判研

### 4.1 核心问题

**battle.start 命令缺少"前置 capability 预校验"层**。

设计案 §10 规定的四层一致性中，第 2、3 层在 `battle.start` 命令路径上都没有真正生效：
- 第 2 层 `combat_can_engage` 只被 `combat.can_engage` 命令调用，不参与 `battle.start` 命令
- 第 3 层 participation capability 检查发生在 verify 阶段的 `combat_target_units_run`，而不是 initial roster 阶段

这导致 capability 阻塞只能在 verify 阶段发现，玩家已经发起命令、qid 已经创建、actor 已经入列后才发现目标 blocked。

### 4.2 这是框架基准问题

判研依据：

1. **跨层契约偏离**：涉及前端候选筛选、command contract、command handler、battle.start 入口、verify pipeline 五个层级的协同偏离，不是单点 bug
2. **设计案已规定但未实现**：设计案 §10 第 3 点、§0.5 第 4/8 点都有明文规定，但实现层缺失
3. **影响所有 capability_blocked 场景**：flustered 已重校准不再 deny `participate_combat`，但仍 deny `combat_action`（pipeline actor verify 路径的 reason 精度问题对 flustered 仍然存在）；未来眩晕、束缚、沉默等"完全无法行动"语义状态若独立声明 `participate_combat` deny，将完整复现本设计案描述的所有问题
4. **影响命令语义清晰性**：当前 `battle.start` 的语义是"尽力执行，部分失败也接受"，但设计案没有明文这种"部分成功"语义是否合理，需要明确

### 4.3 与"双投影机制"的关系

`combat_start_battle` 中存在两次 `combat_chain_project`：
- 第一次（prebattle_cache）：`emit_failures=false`，目的本是预校验
- 第二次（player_turn）：`emit_failures=true`，实际执行

第一次 project 已经发现 capability blocked，但当前实现把"预校验结果"用作"构建 initial roster"而非"反馈失败"。这是"预校验"语义模糊的结构性根源。

## 5. 目标与非目标

### 5.1 目标

1. **前端候选筛选消费 capability**：AimMode 在展示可选目标时，过滤掉 `participate_combat` blocked 的目标，玩家无法选择狼狈目标
2. **后端 command contract 扩展**：`battle.start` 的 contract 增加 target-side capability 检查声明
3. **后端 battle.start 入口预校验**：在创建 qid 前对所有 action 的 target 预检查 `participate_combat`，整体失败时拒绝命令（不创建 qid）
4. **第一次 project 失败信息反馈**：把第一次 project 中 capability blocked 的 action reason 通过响应返回给前端，而非静默吞掉
5. **第二次 project 失败原因精度**：保留 per-target 的具体 reason（`TARGET_CAPABILITY_BLOCKED` 等），不覆盖为 `NO_VALID_TARGET`（前一份设计案的核心目标保留）
6. **target_skipped 事件 emit**：按设计案 §10.3 emit 结构化事件

### 5.2 非目标

- 不重构"双投影机制"为单投影（属于独立重构任务）
- 不引入 `chain_failure_policy`（属于 [战斗上下文视图与动作链失败策略设计案.md §4.5](./战斗上下文视图与动作链失败策略设计案.md) 的独立任务）
- 不修改 `combat_participation_classify_data` 的 reason 命名
- 不修改 flustered 的 timing 模型（设计案 §5.2 已正确实现）
- 不强制要求前端 capability 公开投影必须实时同步（首版可基于已加载的 player_info.capabilities）

## 6. 设计

### 6.1 battle.start 命令语义明确化

明确 `battle.start` 的命令语义为**严格 gate**：

- 任何一个 action 的 target 在预校验阶段 capability blocked 时，**整个 battle.start 命令失败**，返回 `CAPABILITY_BLOCKED` + 详细 detail
- 不创建 qid、不入列、不进入第二次 project
- 玩家收到明确反馈后修正 actions 再重试

这种语义符合"command contract 是权威 gate"的设计哲学，避免"部分成功 + 部分失败"的模糊状态。

替代方案（已否决）：保留"部分成功"语义，但要求第一次 project 失败信息必须反馈。这种方案保留了"玩家可以一次提交多个 action，部分被跳过"的灵活性，但与"command 是权威 gate"的设计哲学冲突，且前端难以呈现"部分 actions 被默默丢弃"的状态。本设计案选择严格 gate 语义。

### 6.2 后端 contract 扩展

[`obl_command_contract.php`](../include/command/obl_command_contract.php) 的 `battle.start` 条目新增：

```php
'battle.start' => array(
    'allowed_actions' => array('', null),
    'advances_tick' => true,
    'itm0_allowed' => false,
    'required_capabilities' => array('enter_combat'),  // actor-side
    'target_required_capabilities' => array('participate_combat'),  // 新增 target-side
    'command_tags' => array('combat_initiation'),
    'refresh' => array('player_info', 'enemies', 'game_map', 'obl_log'),
),
```

`target_required_capabilities` 是新字段，含义：命令 payload 中每个 action 的 target 都必须满足这些 capability。Command Bus 在分发到 handler 前遍历 actions 预校验。

### 6.3 后端 battle.start 入口预校验

`combat_start_battle` 在 actor gate 通过后、第一次 chain_project 前新增 target 预校验步骤：

```php
// 已有：actor enter_combat gate（行 265-273）

// 新增：target participate_combat gate
$evaluation_tick = combat_next_action_evaluation_tick();
$target_capability_failures = [];
foreach ($atk_act as $index => $action) {
    $target_pid = (int)($action['target']['pid'] ?? 0);
    if ($target_pid <= 0) continue;
    $target_data = obl_fetch_playerdata_by_pid($target_pid);
    if (!$target_data) {
        $target_capability_failures[$index] = ['pid' => $target_pid, 'reason' => 'TARGET_NOT_FOUND'];
        continue;
    }
    $capability = actor_capability_decide($target_data, 'participate_combat', null, $evaluation_tick);
    if (empty($capability['allowed'])) {
        $target_capability_failures[$index] = [
            'pid' => $target_pid,
            'reason' => 'TARGET_CAPABILITY_BLOCKED',
            'capability_failure' => skill_effect_project_capability_decision($target_data, 'participate_combat', $evaluation_tick, true),
        ];
    }
}

if (!empty($target_capability_failures)) {
    return [
        'ok' => false,
        'code' => 'CAPABILITY_BLOCKED',
        'rollback' => true,
        'details' => [
            'target_failures' => array_values($target_capability_failures),
        ],
    ];
}

// 已有：combat_cache_create + 第一次 chain_project
```

约束：
- 该预校验是无副作用查询，不创建 qid、不入列
- 失败时整体回滚，返回 `CAPABILITY_BLOCKED` + 详细 `target_failures`
- `evaluation_tick` 必须用 `combat_next_action_evaluation_tick()`（mutation command 的下一可行动 tick），与 `combat_can_engage` 一致

### 6.4 第一次 project 失败信息保留

即使 §6.3 的预校验通过，第一次 project 仍可能在其他维度失败（aim rule、ap、distance）。当前 `combat_start_battle` 行 297-311 默默跳过失败 action，需要改为：

```php
$first_failed_actions = [];
foreach ($atk_act as $index => $action) {
    $projected = $projection['actions'][$index] ?? ['success' => false];
    if (empty($projected['success'])) {
        $first_failed_actions[$index] = [
            'index' => $index,
            'act_id' => (string)$action['act_id'],
            'reason' => $projected['reason'] ?? 'verification_failed',
            'detail' => $projected['detail'] ?? [],
        ];
        continue;
    }
    // ... 既有 initial_target_pids 提取逻辑
}

if (empty($initial_target_pids)) {
    return [
        'ok' => false,
        'code' => 'NO_BATTLE_STARTED',
        'rollback' => true,
        'details' => ['failed_actions' => array_values($first_failed_actions)],
    ];
}
```

约束：
- 失败 action 的 reason 必须保留 per-target 的具体 reason（依赖 §6.5 的 reason 精度修复）
- 即使有部分 action 成功，失败 action 的信息也要在最终响应中返回（详见 §6.6）

### 6.5 失败原因精度修复（前一份设计案的核心）

按 [原 `动作失败原因传递精度修复设计案-2026-07-16.md`](./动作失败原因传递精度修复设计案-2026-07-16.md) §4 的设计：

2. `combat_chain_failure_result` 新增 `detail` 参数
3. `combat_chain_emit_failure_if_needed` 透传 `$detail`
4. `combat_log_v3_action_failure` 写入 `detail` 字段
5. 新增 `combat_log_v3_target_skipped` 事件，按设计案 §10.3 emit

## 8. 验收测试

> **测试模板说明**：以下用例以 flustered 为示例。flustered 已重校准不再 deny `participate_combat`，因此 §8.1、§8.2、§8.3、§8.4 的"flustered active 阻塞 `participate_combat`"场景需替换为以下两种之一才能复现：
> - **未来状态 mock**：在测试环境注入一个临时状态 effect，其 `capability_denies` 包含 `participate_combat`（如临时 `stunned` 状态）
> - **`combat_action` 路径**：测试 flustered active 仍 deny `combat_action` 的 pipeline actor verify reason 精度（这是当前现存的可触发路径）
>
> §8.5 的 `target_skipped` 事件测试与具体状态无关，可直接执行。

### 8.1 复现场景回归

1. 玩家 throw 处于"完全无法行动"语义状态 active 的目标 pid=4：`battle.start` 命令返回 `ok=false, code=CAPABILITY_BLOCKED, details.target_failures=[{pid:4, reason:TARGET_CAPABILITY_BLOCKED}]`
2. 不创建 qid、不入列、不进入第二次 project
3. 玩家收到明确反馈，前端 toast 显示"目标 4 处于 [状态名] 状态，无法参战"

### 8.2 多目标场景

1. 玩家提交 `[throw pid=6, throw pid=4]`，pid=6 健康、pid=4 处于"完全无法行动"语义状态 active：
   - §6.3 预校验发现 pid=4 blocked → 整个 battle.start 失败
   - `target_failures=[{pid:4, reason:TARGET_CAPABILITY_BLOCKED}]`
   - 玩家必须从 actions 中移除 pid=4 后重试
2. 玩家提交 `[throw pid=6]`，pid=6 健康：正常执行

### 8.3 capability 过期边界

1. "完全无法行动"状态 expires_at_tick=5，当前 obl_tick=4, obl_pretick=4：mutation command evaluation_tick=max(4, 5)=5，状态 expired → 预校验通过 → 战斗正常创建
2. "完全无法行动"状态 expires_at_tick=5，当前 obl_tick=4, obl_pretick=3：evaluation_tick=max(4, 4)=4，状态 active → 预校验失败

### 8.4 前端候选筛选

1. NPC 处于"完全无法行动"语义状态 active 时，AimMode 候选列表中该 NPC 不可选（灰显或隐藏，由前端 UX 决定）
2. NPC capabilities 投影缺失时，宽容为 allowed（设计案 §0.5 第 8 点），不阻塞战斗
3. **当前现存路径**：NPC 处于 flustered active 状态时，`enter_combat` 与 `combat_action` 投影为 blocked，但 `participate_combat` 投影为 allowed——前端不应将 flustered 目标从被动参战候选中过滤掉

### 8.5 target_skipped 事件

1. grenade 对 A/B/C 三个目标中 B 被其他 qid 占用：emit `target_skipped(B) → effect_applied(A) → effect_applied(C)`，action status 为 `partial`
2. whirlwind 对 A/B/C 全部 skipped：emit 三个 `target_skipped` 后 emit `action_failed(NO_VALID_TARGET, detail.targets=[...])`
3. 单目标 throw pid=4 skipped：emit `target_skipped(pid=4) → action_failed(NO_VALID_TARGET, detail.targets=[{pid:4, reason:TARGET_CAPABILITY_BLOCKED}])`

### 8.6 当前现存的 combat_action reason 精度测试

针对 flustered 仍 deny `combat_action` 的路径，无需等待未来状态即可验证 reason 精度修复：

1. 玩家自己处于 flustered active 时发起 `battle.start`：actor gate 检查 `enter_combat` 应返回 `CAPABILITY_BLOCKED:enter_combat`（不进入第二次 project）
2. 玩家在战场内主动行动时 actor 处于 flustered active：pipeline actor verify 应返回 `CAPABILITY_BLOCKED:combat_action`，不被覆盖为 `NO_VALID_TARGET`

### 8.7 边界

1. battle.start 预校验通过但第一次 project 失败（aim rule、distance 等）：仍按 §6.4 返回 `failed_actions`，不创建 qid
2. 第二次 project 阶段 NPC 突然 capability blocked（race condition）：依赖 §6.5 的 reason 精度修复，返回 `TARGET_CAPABILITY_BLOCKED`
3. NPC 不在视野内：`combat_can_engage` 已有 `TARGET_NOT_VISIBLE` 分支，预校验不重复该检查
