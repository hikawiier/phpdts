# 文档与代码双向锚点校验器设计案

> **状态**：已实现。
>
> **规范来源**：[DESIGN.md 2.12 文档与代码双向锚点契约](../DESIGN.md#212-文档与代码双向锚点契约)。本设计只定义如何验证规范，不重新定义规范语义。

---

## 一、目标与边界

### 1.1 目标

提供一个零业务依赖、可重复运行的命令行校验器，把 `DESIGN.md 2.12` 的文字约束转化为确定性检查：

- 验证 `Dian.md` 中框架章节与代码锚点的结构完整性；
- 验证代码文件头 `@module`、`@framework` 标签的格式与归属；
- 验证文档锚点文件集合与代码框架标签文件集合严格相等；
- 验证属于模块 A-N 的生产代码文件均有且只有一个主要 `@module`；
- 为迁移阶段提供模块级检查，但不把局部通过误报为全项目合规；
- 以稳定退出码和结构化错误编号供人工、智能体和未来 CI 使用。

### 1.2 不承担的职责

校验器不判断框架设计本身是否合理，也不推断某个文件应该属于哪个框架。以下内容仍由设计评审和 codebase-memory-mcp 负责：

- 函数、类、调用链和数据流是否正确；
- 文件是否真的实现了其声明的框架语义；
- `Dian.md` 中设计意图和边界案例是否准确；
- 中文框架名称是否优雅或是否需要改名；
- 自动添加、删除或修复标签。

校验器只验证已经声明的关系是否完整、自洽、可定位。首版不提供 `--fix`，避免工具根据路径或文件名猜测语义所有权。

## 二、技术选型与文件位置

### 2.1 运行时

使用 PHP CLI 实现，不引入 Composer 包或其他第三方依赖。

理由：

- Oblivions 后端本身以 PHP 为基础，开发环境必然具备 PHP；
- 工具跨越 `oblivions/`、`vex-vue/src/` 和 Markdown，不应归属于前端 npm 工具链；
- PHP 标准库足以完成目录遍历、正则解析、路径规范化和 JSON 输出；
- 零依赖便于智能体、本地开发和未来 CI 使用同一条命令。

### 2.2 文件布局

```text
oblivions/tools/
├── validate_design_anchors.php
└── tests/
    └── validate_design_anchors_test.php
```

`validate_design_anchors.php` 是唯一正式入口。测试使用临时夹具目录构造最小仓库，不依赖当前工作区是否已经完成迁移。

校验器属于项目治理工具，不属于模块 A-N，因此 `oblivions/tools/**` 不参与 `@module` 覆盖率检查。

### 2.3 标准命令

```powershell
# 全项目严格校验；迁移完成后的唯一验收命令
php oblivions/tools/validate_design_anchors.php

# 迁移阶段只验证一个模块及其框架关系
php oblivions/tools/validate_design_anchors.php --module=A

# 供自动化系统消费
php oblivions/tools/validate_design_anchors.php --format=json

# 校验工具自身测试
php oblivions/tools/tests/validate_design_anchors_test.php
```

校验器从自身路径向上定位同时包含 `oblivions/DESIGN.md`、`oblivions/Dian.md` 和 `vex-vue/` 的仓库根目录，不依赖调用命令时的当前工作目录。

## 三、输入范围

### 3.1 权威文档

- 框架、模块和代码锚点来源：`oblivions/Dian.md`；
- 规范语义来源：`oblivions/DESIGN.md`，首版不解析其自然语言内容；
- `AGENTS.md` 只负责触发校验，不作为校验数据源。

### 3.2 生产代码扫描范围

首版对以下文件执行 `@module` 覆盖率和标签解析：

```text
oblivions/**/*.php
vex-vue/src/**/*.ts
vex-vue/src/**/*.vue
```

排除：

```text
oblivions/tests/**
oblivions/tools/**
oblivions/docs/**
oblivions/cache/**
vex-vue/node_modules/**
vex-vue/dist/**
```

后端测试、治理工具、设计文档与运行时缓存不属于运行时模块 A-N，不要求主要模块标签。`oblivions/cache/**` 必须整棵排除，避免锁文件、日志批次和其他请求期生成的 `.php` 缓存被误判为生产源码。`vex-vue/src/` 下的 fixture 属于产品源代码旁的模块资产，继续参与 `@module` 覆盖率检查。

若未来框架核心实现扩展到 `.css`、`.scss`、`.js`、`.mjs` 等类型，必须先扩展 `DESIGN.md 2.12` 的适用范围和校验器的受支持扩展名，不允许仅在 `Dian.md` 中加入一个无法被校验器解析的锚点。

### 3.3 路径规则

文档锚点路径必须：

- 从仓库根目录开始；
- 使用 `/` 作为分隔符；
- 不以 `/`、`./`、`../` 或盘符开头；
- 大小写与实际仓库路径完全一致；
- 指向普通文件，不指向目录或仓库外部符号链接目标；
- 属于首版支持的生产代码类型。

路径存在性通过校验器枚举得到的规范化仓库相对路径集合判断，不依赖 Windows 的大小写不敏感行为。

## 四、解析模型

### 4.1 Dian.md 状态机

按行读取 `Dian.md`，维护当前模块和当前框架：

```text
### 模块 A：API 层
#### 框架 A-1：HTTP 三层入口隔离架构
**代码锚点：** `oblivions/api/command.php`（命令入口）
```

识别规则：

- 模块标题：`### 模块 {A-N}：{显示名称}`；
- 框架标题：`#### 框架 {A-N}-{正整数}：{显示名称}`；
- 代码锚点：框架章节内以 `**代码锚点：**` 开头的单独一行；
- 锚点文件：代码锚点行中所有反引号包裹的仓库相对路径；
- 框架章节范围：从当前框架标题开始，到下一个同级框架、模块或更高层标题之前结束。

解析器同时维护 Markdown fenced code block 状态。位于三反引号或三波浪号代码块内的模块标题、框架标题和代码锚点文本全部忽略，避免文档示例被识别为真实目录结构。围栏开始和结束必须使用相同字符类型，结束围栏长度不得短于开始围栏。

框架编号是关联主键。中文模块名、框架名和职责说明只保留在诊断信息中，不参与集合关联。

### 4.2 代码标签

标签只在文件前 40 个物理行中有效。超过此范围出现的标签视为非文件头标签并报错，避免业务注释、字符串示例或函数注释被误识别为所有权声明。

接受以下注释载体：

```php
/**
 * @module A API 层
 * @framework A-3 状态查询范围分发
 */
```

```typescript
/**
 * @module K 状态管理层
 * @framework K-3 多层命令门控
 */
```

```vue
<!-- @module L Vue 组件 -->
<!-- @framework L-1 统一交互列表模式 -->
```

每条标签单独占据一个逻辑行。解析器只提取：

- `@module` 后的单个模块编号 A-N；
- `@framework` 后的单个框架编号 `{A-N}-{正整数}`；
- 编号后的中文名称作为显示文本，不作为关联条件。

同一行出现多个框架编号时直接判定为非法格式，而不是尝试拆分。编号后的显示名称允许包含 `/`、逗号等自然语言标点，校验器不把显示名称标点当成关系分隔符。

### 4.3 内部模型

解析完成后构造以下集合：

```text
modules[moduleId] = Dian 模块信息
frameworks[frameworkId] = Dian 框架信息
frameworks[frameworkId].anchorFiles = 文档锚点文件集合

files[path].moduleId = 代码主要模块
files[path].frameworkIds = 代码框架标签集合

taggedFilesByFramework[frameworkId] = 代码标签文件集合
```

所有集合在比较前去除重复并排序，保证 Windows、不同文件遍历顺序和输出格式不会影响结果。

## 五、校验规则与错误编号

错误编号是稳定接口。错误文案可以优化，但编号含义不得随意复用。

### 5.1 文档结构 `DIAxxx`

| 编号 | 条件 |
|---|---|
| `DIA001` | 模块编号重复或模块标题格式非法 |
| `DIA002` | 框架编号重复或框架标题格式非法 |
| `DIA003` | 框架编号前缀与所在模块不一致 |
| `DIA004` | 框架缺少代码锚点行 |
| `DIA005` | 同一框架存在多个代码锚点行 |
| `DIA006` | 代码锚点行没有任何文件路径 |
| `DIA007` | 同一框架重复列出同一文件 |
| `DIA008` | 锚点路径不是规范仓库相对路径 |
| `DIA009` | 锚点路径不存在、大小写错误或不是普通文件 |
| `DIA010` | 锚点文件类型不在校验器支持范围内 |

### 5.2 标签结构 `TAGxxx`

| 编号 | 条件 |
|---|---|
| `TAG001` | 适用范围内的生产代码文件缺少 `@module` |
| `TAG002` | 一个文件声明多个 `@module` |
| `TAG003` | `@module` 编号格式非法或 Dian.md 中不存在该模块 |
| `TAG004` | 同一文件重复声明相同 `@framework` |
| `TAG005` | `@framework` 单行包含多个编号或非法分隔符 |
| `TAG006` | `@framework` 编号格式非法 |
| `TAG007` | 标签位于文件头 40 行之外 |
| `TAG008` | 带 `@framework` 的文件缺少有效 `@module` |

### 5.3 关系一致性 `RELxxx`

| 编号 | 条件 |
|---|---|
| `REL001` | 代码声明的框架编号在 Dian.md 中不存在 |
| `REL002` | 文件 `@module` 与其 `@framework` 所属模块不一致 |
| `REL003` | Dian.md 锚点中存在文件，但该文件未声明对应框架 |
| `REL004` | 代码文件声明了框架，但未出现在对应 Dian.md 锚点集合中 |
| `REL005` | 文档锚点集合与代码标签集合不相等 |

`REL003` 和 `REL004` 给出具体差集，`REL005` 给出框架级汇总。这样人工修复时能直接看到文件，自动化统计时也能按框架判断失败。

### 5.4 工具自身 `SYSxxx`

| 编号 | 条件 |
|---|---|
| `SYS001` | 无法定位仓库根目录 |
| `SYS002` | 无法读取 Dian.md |
| `SYS003` | 命令行参数非法 |
| `SYS004` | 扫描文件时发生不可恢复的 I/O 错误 |

## 六、运行模式

### 6.1 默认严格模式

不传参数时校验全部模块、全部框架和全部生产源文件：

```powershell
php oblivions/tools/validate_design_anchors.php
```

只有默认严格模式通过，才能声明项目满足 `DESIGN.md 2.12`。迁移完成后，`AGENTS.md` 应直接记录这条命令作为完成条件。

### 6.2 模块迁移模式

```powershell
php oblivions/tools/validate_design_anchors.php --module=A
```

模块模式验证：

- 指定模块的 Dian 模块标题和全部框架章节；
- 指定模块所有框架的锚点与代码标签集合；
- 所有参与这些框架关系的文件标签格式和模块一致性；
- 全仓库已出现标签的基本语法与未知编号错误。

模块模式不检查未声明所有权的文件是否本应属于该模块，因为工具不能从路径可靠推断业务所有权。输出必须包含醒目的 `SCOPED VALIDATION` 标识，并明确“局部通过不代表全项目合规”。

不提供 `--allow-incomplete`。迁移状态通过显式 `--module` 表达，避免宽松开关被长期保留在正式验收流程中。

### 6.3 输出格式

默认文本输出按“错误编号 → 框架编号 → 文件路径”稳定排序：

```text
[ERROR][REL004] framework K-3
  code file is tagged but absent from Dian anchor set:
  vex-vue/src/stores/command-capability.ts

Summary: 1 error, 0 warnings, 78 frameworks, 207 source files
Result: FAILED
```

JSON 输出包含：

```json
{
  "mode": "strict",
  "passed": false,
  "errors": [
    {
      "code": "REL004",
      "framework": "K-3",
      "file": "vex-vue/src/stores/command-capability.ts",
      "line": 3,
      "message": "code file is tagged but absent from Dian anchor set"
    }
  ],
  "summary": {
    "modules": 14,
    "frameworks": 78,
    "sourceFiles": 207,
    "errors": 1
  }
}
```

示例中的数量仅说明结构，实际输出必须动态计算，不在代码或文档中断言固定数量。

### 6.4 退出码

| 退出码 | 含义 |
|---|---|
| `0` | 所选运行模式内全部校验通过 |
| `1` | 发现规范违反 |
| `2` | 参数、仓库定位或 I/O 等工具级失败 |

模块模式返回 `0` 只表示指定范围通过，文本和 JSON 中必须保留 `scoped=true`。

## 七、执行流程

```text
定位仓库根目录
  ↓
解析命令行参数
  ↓
解析 Dian 模块、框架与锚点
  ↓
枚举生产代码文件
  ↓
解析文件头 module/framework 标签
  ↓
执行文档结构规则
  ↓
执行标签结构规则
  ↓
执行模块与框架关系规则
  ↓
稳定排序并输出诊断
  ↓
返回退出码
```

解析阶段尽量收集全部问题，不因首个错误提前退出。只有无法定位仓库或无法读取权威文件等 `SYSxxx` 错误才终止后续关系检查。

## 八、测试设计

测试脚本使用临时目录生成最小 `Dian.md`、PHP、TypeScript 和 Vue 文件，并直接调用校验器核心入口。至少覆盖：

1. 单模块单框架完全一致；
2. 一个文件实现两个框架且使用独立标签；
3. 有 `@module` 但没有 `@framework` 的普通模块文件；
4. 文档有文件、代码缺标签；
5. 代码有标签、文档缺文件；
6. 锚点路径不存在；
7. Windows 可找到但大小写错误的路径；
8. 框架编号不存在；
9. 框架前缀与模块不一致；
10. 文件主要模块与框架模块不一致；
11. 多个 `@module`；
12. 使用 `/` 合并多个 `@framework`，同时允许单个框架的显示名称包含 `/`；
13. 标签超过文件头 40 行；
14. Markdown fenced code block 内的伪模块、伪框架和伪锚点被忽略；
15. Vue HTML 注释标签；
16. 严格模式发现未标注的生产文件；
17. 模块模式不把其他未迁移模块误报为当前模块错误；
18. 文本输出排序稳定；
19. JSON 输出可以被 `json_decode` 严格解析；
20. 规范违反返回退出码 1；
21. 参数或仓库结构错误返回退出码 2。
22. `oblivions/cache/**` 中的 PHP 缓存被忽略，同时 `oblivions/cacheable/**` 等相似前缀仍参与严格校验。

测试夹具不复制当前项目的大型文档，防止测试随着真实 `Dian.md` 内容变化而变成快照测试。

## 九、迁移与接入顺序

### 9.1 实现阶段

1. 实现解析器、规则引擎、文本/JSON 报告和退出码；
2. 完成独立夹具测试；
3. 使用 `--module=A` 验证现有试点，确认设计与真实格式一致；
4. 按模块迁移 B-N，每完成一个模块运行对应 `--module=X`；
5. 全部迁移后运行默认严格模式；
6. 严格模式通过后，把标准命令写入 `AGENTS.md` 强制触发条款。

### 9.2 AGENTS.md 最终触发语义

问题 2 的推荐规则应与校验器范围一致：

```markdown
- 新增、移动、重命名或删除 Oblivions/Vex-Vue 生产代码文件，或改变其模块/框架职责时，必须遵守 DESIGN.md 2.12。普通模块文件同步 `@module`；直接实现框架的核心文件同时同步 `@framework` 与 Dian.md 代码锚点。完成前运行 `php oblivions/tools/validate_design_anchors.php`。
```

迁移期间可以在任务内部使用 `--module=X` 获得增量反馈，但不得把该命令替换为 AGENTS.md 中的最终验收命令。

### 9.3 未来 CI

若项目建立 CI，只需运行：

```powershell
php oblivions/tools/tests/validate_design_anchors_test.php
php oblivions/tools/validate_design_anchors.php
```

CI 不使用模块模式，不允许忽略错误，不需要维护另一份框架清单。

## 十、验收标准

校验器实现完成需同时满足：

- 在 Windows PowerShell 下可以从仓库任意目录调用；
- 不依赖数据库、Web 服务器、npm install 或 Composer；
- 模块 A 试点通过 `--module=A`；
- 所有测试夹具通过；
- 错误信息包含稳定编号、框架编号、文件路径和可定位行号；
- 文本输出适合人工阅读，JSON 输出适合自动化处理；
- 默认严格模式能够发现当前尚未迁移的框架和缺失模块标签；
- 全量迁移完成后默认严格模式返回 0；
- 校验器自身目录不会被误判为模块 A-N 的生产代码。

设计的最终判断标准不是“能找到标签”，而是任何一侧发生遗漏、误标、路径漂移或模块错配时，工具都能以确定、可复现的方式阻止任务被视为完成。
