## 一、问题研判

### 1.1 表象与本质

**表象**：战报回放中出现大量未本地化的英文索引信息，例如：
- `你使用了unarmed_strike，目标：史莱姆`
- `史莱姆的unarmed_strike失败：unarmed_strike_target_missing`
- `史莱姆已退出战斗（EFFECT_FAILED）`
- `战斗结束：NO_VALID_TARGET`
- `notice` 事件直接显示 `JSON.stringify(payload.detail)`

**本质**：`battle-director.ts` 的文本生成层（`buildActionText` / `buildEffectText` / `buildNoticeText`）绕开了项目已有的模板字典架构，回到硬编码字符串拼接模式。后端 emit 的 `action_id` / `reason` / `effect_type` 等 snake_case 英文字段被直接拼接到中文叙事文本中，形成"中英混排"的视觉割裂。

### 1.2 框架基准缺失，而非特例

按"提炼概念→判断特例 vs 框架基准"思路梳理，项目已有三套成熟的模板字典架构：

| 已有架构 | 字典文件 | 渲染入口 | 覆盖范围 |
|---|---|---|---|
| 普通日志 | `log-templates.ts` `LOG_TEMPLATES` | `renderLogEntry` | `obl_log` 全部事件 ID |
| 命令反馈 | `command-feedback.ts` + 复用 `LOG_TEMPLATES` | `renderCommandFeedback` | Command API error code + feedback.id |
| 技能显示 | `skill-templates.ts` `SKILL_TEMPLATES` | `getSkillTemplate` | 战斗装填区按钮 + 技能描述 |

战报回放作为第四类文本生成场景，**完全未遵循同一架构模式**：
- `buildActionText` 直接拼接 `actionId`，未查询 `SKILL_TEMPLATES.action_desc`
- `buildEffectText` 硬编码 effect_type 中文映射，未抽离为字典
- `buildNoticeText` 直接使用 `payload.message/text/title/reason` 或 `JSON.stringify(payload.detail)`，无任何模板
- `action_failed` / `combatant_cleared` / `battle_end` 三类 notice 的文本在事件分发主循环中**就地硬编码拼接**，未经过模板层
- `combatant_joined` 事件当前仅收集 `DirectedCombatantJoined` 数据结构，无文本生成——动态参战场景的叙事完整性缺失
- `notice` 事件分支（battle-director.ts:457-468）当前是面向契约的预留处理：前端类型枚举 `BattleLogV3EventType` 含 `'notice'`（[api.ts:483-493](file:///d:/wamp64/www/phpdts/vex-vue/src/types/api.ts#L483-L493)），但生产后端代码无任何 `event_type => 'notice'` emit（仅 [tests/transaction_integration_test.php](file:///d:/wamp64/www/phpdts/oblivions/tests/transaction_integration_test.php) 测试场景出现）。该分支同时存在 `reason` 字段写入 bug：`reason: buildNoticeText(event)` 把渲染文本塞进 `reason: string | null` 字段，与本方案 §2.4 让 `buildNoticeText` 返回 `TextCue` 的计划冲突，必须连带修复

这是框架基准的遗漏，不是局部特例。`OBL_EVENT_LOG_DESIGN.md` §7.2 当时将 battle_log 列为 out-of-scope，意图是"避免本轮重构范围扩大"，并非"battle_log 永久不需要本地化"。当前用户主动提出问题，意味着 out-of-scope 阶段已结束。

### 1.3 与设计哲学的冲突

对照 `DESIGN.md` §3.4 与 §4.1：

- **§3.4 注意力稀缺**：未本地化的英文索引迫使用户在"英文符号"与"中文叙事"两套语言间切换，等同于额外的注意力税，违反"协调性即节省注意力"。
- **§3.4 想象力核心**：英文符号直接破坏叙事沉浸感，无法引发用户联想。"你使用了unarmed_strike"无法激发任何想象，应转化为"你空手击打了"。
- **§4.1 跨层命名契约的静默失败**：当前 battle-director 的"未匹配即拼接原始字符串"行为正是已记录教训警告的"静默失败"模式——前端没有任何告警，用户却看到英文索引。应改为硬错误 + 兜底文案。
- **§3.3 约束是意图的近似**：OBL_EVENT_LOG_DESIGN.md §7.2 "不动 battle_log"的字面约束在意图变化后应回到意图——本轮需要建立 battle_log 文本本地化框架。
- **§2.15 灰阶基底违规**：[battle.css:204-205](file:///d:/wamp64/www/phpdts/vex-vue/src/assets/styles/battle.css#L204-L205) 现存的 `.battle-log-entry .yellow { color: #ddd44; }` 与 `.battle-log-entry .red { color: #ff6b6b; }` 是被遗漏的彩色信号色，直接违反 DESIGN.md §2.15 "灰阶基底"与 §3.4 "唯一强调色"元约束。`terminal.css:430-434` 已将 `.yellow/.red/.grey` 映射为灰阶亮度（`#fff` / `#ccc` 下划线 / `#555`），battle.css 的并行规则属于历史彩色残留，本方案同时承担清理职责。

## 二、设计方案

### 2.1 核心原则

1. **架构对齐**：复用已有"模板字典 + 渲染函数"模式，建立 `BATTLE_TEMPLATES` 字典与 `renderBattleText` 渲染层，与 `LOG_TEMPLATES` / `SKILL_TEMPLATES` 保持一致的架构风格。
2. **跨层契约 1:1 对齐**：后端 emit 的 `action_id` / `reason` / `effect_type` 等 snake_case 字段作为索引锚点，前端字典 key 必须与后端枚举值 1:1 对齐。模板匹配失败视为硬错误（console.warn + 兜底文案）。
3. **叙事化表达**：战报文本以引发联想为核心目标。技术 ID 不出现在用户可见文本中；reason 转化为可读叙事；effect_type 通过模板渲染为完整句子。
4. **排版与视觉层次**：文本生成层同时负责 HTML 排版——通过 `<span class="...">` 包裹关键信息（攻击者、目标、数值、状态名），与普通日志的 `.yellow` / `.red` / `.grey` 高亮类体系对齐。
5. **灰阶基底**：战报文本不引入新的彩色信号色，复用普通日志已有的灰阶高亮类（`.yellow` / `.red` / `.grey` / `.log-content` 等）。

### 2.2 字典架构

新建 `vex-vue/src/data/battle-templates.ts`，承载战报回放所有文本生成规则：

```typescript
// 技能动作文本（act_id → 叙事化动作描述）
// 复用 SKILL_TEMPLATES.action_desc，并扩展动作模板
BATTLE_ACTION_TEMPLATES: Record<string, (ctx: ActionTextContext) => TextCue>

// 效果文本（effect_type → 叙事化效果描述）
BATTLE_EFFECT_TEMPLATES: Record<string, (ctx: EffectTextContext) => TextCue | undefined>

// reason 本地化（reason 字符串前缀 → 中文映射）
// 处理复合 reason：ap_insufficient:need=3,have=2 → 解析前缀 + 参数
BATTLE_REASON_TEMPLATES: Record<string, (params: ReasonParams) => TextCue>

// notice 文本（notice 类型 → 叙事化提示）
BATTLE_NOTICE_TEMPLATES: Record<string, (ctx: NoticeTextContext) => TextCue>
```

**关键设计**：
- 字典 value 为函数而非纯字符串，支持根据上下文（actor / target / value / detail）动态生成 HTML
- `reason` 字段采用"前缀 + 参数"解析：`ap_insufficient:need=3,have=2` 解析为前缀 `ap_insufficient` + 参数 `{need: 3, have: 2}`，再查询字典
- 未匹配的 reason 前缀走兜底模板 + console.warn，避免静默失败

### 2.3 字典内容覆盖

#### 2.3.1 `BATTLE_ACTION_TEMPLATES`（基于 `SKILL_TEMPLATES` 扩展）

#### 2.3.2 `BATTLE_EFFECT_TEMPLATES`

**文本生成策略**：仅 `damage` / `heal` / `status` / `escape` 生成文本；`move` / `ap_change` / `custom` 默认返回 `undefined`（不生成文本），由 HP 条、地图位姿动画、AP 槽位姿变化承担视觉反馈。这是相对当前 [battle-director.ts:790](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle-director.ts#L790) 的行为变更（当前 `move` 生成"{name}发生了位移"文本）——本方案移除该文本，避免与地图位姿动画重复反馈。

| effect_type | 是否生成文本 | 叙事模板 |
|---|---|---|
| `damage` | 是 | `{target}受到{value}点伤害`（`value` 用 `<span class="red">`） |

| `ap_change` | 否 | — （由 AP 槽位姿变化承担） |
| `custom` | 否 | — （由 effect.target.snapshot 的 HP 变化承担） |
| 未匹配 | 否 | `console.warn` + 返回 `undefined` |

#### 2.3.4 `BATTLE_NOTICE_TEMPLATES`

**类型边界澄清**：`diagnostic` 不是 `event_type`，而是 [BattleLogV3Channel](file:///d:/wamp64/www/phpdts/vex-vue/src/types/api.ts#L495)（`'render' | 'debug' | 'diagnostic'`）。前端 [DirectedNotice.type](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle-director.ts#L105) 枚举虽含 `'diagnostic'`，但代码中无任何 push 该类型的逻辑——是预留类型。本方案不新增 `diagnostic` event_type 处理；当 `event.channel === 'diagnostic'` 时统一走 debug-only 渲染（仅 `?debug=ai` 模式可见），与其他 event_type 的文本生成分离。

**notice event_type 定性**：`notice` event_type 当前在生产后端无 emit，仅 [tests/transaction_integration_test.php](file:///d:/wamp64/www/phpdts/oblivions/tests/transaction_integration_test.php) 测试场景出现。前端类型枚举保留 `'notice'` 是面向契约的预留——本方案为其建立模板，作为未来后端扩展演出事件（如 NPC 对白、剧情触发提示）的接入点。

| notice 类型 | 模板 |
|---|---|
| `action_failed` | `{actor}的{action_name}失败：{reason_text}` |
| `combatant_cleared` | `{combatant}已退出战斗（{reason_text}）`，`reason_text` 由 BATTLE_REASON_TEMPLATES 渲染（`death`/`escaped` 等） |
| `battle_end` | 按 `winner_pid` 推断胜负分支，结合 `reason` 表达结束场景（见下表） |
| `notice`（预留） | 优先使用 `payload.message` 本地化（按 §5.3 规则）；`JSON.stringify(detail)` 仅在 debug 模式下显示 |
| `combatant_joined` | `{combatant}加入了战斗` |
| `event.channel === 'diagnostic'` | 灰色 `<span class="grey">[诊断] {detail}</span>`，仅 `?debug=ai` 模式可见 |

**`battle_end` 胜负分支策略**：

后端 [battle_turn.func.php:113-118](file:///d:/wamp64/www/phpdts/oblivions/include/game/battle_turn.func.php#L113-L118) 的 `battle_turn_end_battle` 实际 emit 逻辑：
- `battle_turn_collect_survivors`（[battle_turn.func.php:85-96](file:///d:/wamp64/www/phpdts/oblivions/include/game/battle_turn.func.php#L85-L96)）收集所有 `active=1` 的 combatant snapshot，作为 `payload.survivors`
- 幸存者仅 1 人时 `winner_pid = 幸存者 pid`；否则 `winner_pid = 传入值`
- `reason` 是队列状态值（`queue_empty` / `disband` / `no_candidate`），不直接表达胜负语义

**框架基准设计（非特例补丁）**：胜负判定不依赖"推断 playerPid 后比较 winnerPid"——该模式在两个场景下失败（玩家逃跑时 winnerPid=NPC 误判战败；NPC 全逃跑时事件流无玩家 snapshot 导致 playerPid=0）。改为显式计算 `BattleEndInfo` 上下文：

| 字段 | 来源 | 语义 |
|---|---|---|
| `playerPid` | 扫描事件流中所有 combatant snapshot（actor/combatant/survivors），找 `type===0` | 玩家身份 |
| `playerSurvived` | `battle_end.payload.survivors` 中是否含 `pid===playerPid` 的 combatant | 玩家是否幸存 |
| `playerEscaped` | 事件流中是否存在 `combatant_cleared.reason==='escaped'` 且 `pid===playerPid` | 玩家是否主动逃跑 |
| `winnerPid` | `battle_end.winner_pid` | 胜者 pid |
| `reason` | `battle_end.reason` | 结束原因 |

**分支逻辑**（按语义优先级，无 hack）：

| playerSurvived | playerEscaped | winnerPid === playerPid | 渲染分支 |
|---|---|---|---|
| 是 | — | 是 | `<span class="yellow">你获得了胜利</span>` |
| 是 | — | 否 | `<span class="grey">战斗结束</span>`（多人平局等） |
| 否 | 是 | — | `<span class="yellow">你成功逃离了战斗</span>` |
| 否 | 否 | — | `<span class="red">你战败了</span>` |

**两个场景的自动覆盖**（无需特判）：
- 玩家逃跑：`playerSurvived=false`（玩家不在 survivors 中）+ `playerEscaped=true` → 逃离
- NPC 全逃跑：`playerSurvived=true`（玩家在 survivors 中）+ `winnerPid===playerPid`（幸存者仅 1 人）→ 胜利

`reason` 值通过 BATTLE_REASON_TEMPLATES 渲染为附加说明（如 `queue_empty` → "队列已空"），仅在 debug 模式作为副文本显示，不污染主叙事文本。

function buildNoticeText(event: BattleLogV3Event, battleEndInfo: BattleEndInfo | null): TextCue {

## 五、边界案例与待决策点

### 5.1 复合 reason 的解析边界

`reason` 字段存在多种复合格式：
- `ap_insufficient:need=3,have=2`（键值对参数）
- `rule_forbid:xxx`（裸字符串参数）
- `move_spatial_rejected:unknown`（嵌套 reason）
- `skill_not_found:fire_ball`（带 skill_id 参数）
- `execute_hook_missing:{func}`（带函数名参数）
- `CAPABILITY_BLOCKED:combat_action`（带能力名参数）

**决策**：统一采用"前缀:剩余"解析，前缀匹配字典，剩余部分作为 `reason_detail` 参数传入。`reason_detail` 若仍为英文键，由具体模板决定是否二次查询或直接显示。`combatant_cleared.reason` 与 `battle_end.reason` 是无前缀 enum 值，直接匹配字典。

**与后端 `combat_preview_reason_public` 的边界**：后端 [combat.preview.php:336-342](file:///d:/wamp64/www/phpdts/oblivions/include/game/combat/combat.preview.php#L336-L342) 已对 `target_resolve_failed:` / `AIM_RULE_FAILED:` / `rule_forbid:` 做前缀剥离，但**仅用于 preview 通道**（前端 toast 即时反馈）；BattleLog 通道（`combat_log_v3_action_failed`）未经剥离，前端字典必须覆盖原始 reason 全部前缀。前端解析器不做"是否被后端剥离"的假设，对所有 reason 走统一的"前缀:剩余"解析。

### 5.2 `idle` action 的文本生成

后端 [enemy_ai.func.php:343,359](file:///d:/wamp64/www/phpdts/oblivions/include/game/enemy_ai.func.php#L343-L359) 在 NPC 无可行动作时返回 `act_id => 'idle'`。当前 `buildActionText` 会生成"你使用了idle"——明显错误。字典化后应生成"原地待机"或不生成文本。

**决策**：`BATTLE_ACTION_TEMPLATES.idle` 返回轻量提示"原地待机"，tone 为 `system`，灰阶显示。`idle` 不在 SKILL_TEMPLATES 注册（NPC 不会出现在装填区按钮），是 BATTLE_ACTION_TEMPLATES 独有条目，`validateBattleTemplates()` 应允许此例外。

### 5.3 `notice` 事件 `payload.message` 的语义

当前 `buildNoticeText` 优先取 `payload.message`，但该字段可能是：
- 后端硬编码中文（应直接使用）
- 后端英文键（应查询字典）
- 后端调试字符串（应 debug 模式才显示）

**决策**（修订：放弃"中文字符检测"，改为 message_type 显式标记）：前端建立"中文字符检测"不可靠——英文键可能含 ASCII 数字（如 `battle_entry.empty_actions`）、调试字符串可能含中文标点、后端硬编码中文也可能夹杂英文术语。建议后端在 emit notice 事件时显式标记 `payload.message_type: 'zh' | 'key' | 'debug'`，前端按类型路由：

- `message_type === 'zh'`：直接使用 `payload.message`
- `message_type === 'key'`：查询 BATTLE_NOTICE_TEMPLATES，未匹配走兜底 + console.warn
- `message_type === 'debug'` 或未标记：仅 `?debug=ai` 模式显示

后端契约需在 §3.1 字段契约文档中补 `message_type` 字段。后端若暂未实现该字段，前端回退为"按 `event.channel === 'diagnostic'` 判定 debug"。

### 5.4 `JSON.stringify(payload.detail)` 的去留

当前 `buildNoticeText` 在 `message` 为空时回退到 `JSON.stringify(payload.detail)`，用户会看到原始 JSON。这违反 §3.4 想象力核心。

**决策**：
- 生产模式：`detail` 不直接显示，仅用于 reason 解析或 debug
- debug 模式（`?debug=ai`）：以 `<span class="grey">[detail] {json}</span>` 形式显示

### 5.5 `effect_type = 'custom'` 的处理

后端 emit 的 `effect_type` 可能存在未在 normalizeEffectType 中枚举的值，统一归为 `custom`。当前 `buildEffectText` 对 custom 返回 undefined（不显示文本）。

**决策**：保持不显示文本，由 `effect.target.snapshot` 的 HP 变化 + 地图立绘位姿动画承担视觉反馈。`custom` 不强制生成文本，避免无意义噪声。`move` / `ap_change` effect_type 同此策略（§2.3.2 行为变更）。

8. **`battle_end` 胜负判定正确**：玩家逃跑显示"你成功逃离了战斗"；NPC 全逃跑显示"你获得了胜利"；玩家死亡显示"你战败了"——三个场景均通过 `BattleEndInfo` 显式上下文判定，无特判 hack（§2.3.4）

## 七、与设计哲学的对齐校准

按 `DESIGN.md` §3 设计哲学逐条校准：

- **§3.1 降低理解成本**：本地化叙事文本降低用户认知成本；字典架构降低后续开发者理解成本
- **§3.2 概念引入成本-收益**：`BATTLE_TEMPLATES` 作为新概念承载了"战报文本生成规则"的复杂语义层次，引入成本低于每次解释"为什么 battle-director 不用字典"
- **§3.3 约束是意图的近似**：OBL_EVENT_LOG_DESIGN.md §7.2 的 out-of-scope 约束在意图变化后回到意图——本轮建立本地化框架
- **§3.4 注意力稀缺**：消除中英混排的注意力税；叙事化文本提升扫读效率
- **§3.4 想象力核心**：本地化文本为用户联想腾出空间，英文符号不再破坏叙事沉浸
- **§2.15 灰阶基底**：清理 `battle.css` 彩色信号色残留，回归 `terminal.css` 灰阶映射体系；`move` / `ap_change` / `custom` effect 不生成文本，避免与位姿动画/HP 条/AP 槽反馈重复抢占注意力
- **§4.1 跨层命名契约**：本方案将 battle-director 的"静默拼接"改为"硬错误 + 兜底"，对齐已记录教训
