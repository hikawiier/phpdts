# 战斗上下文视图与动作链失败策略设计案

> 目的：记录当前战斗移动失败、NPC 位置显示不同步、第二轮页面/目标状态错乱三个问题的实证结果，并判断它们是个例修补问题，还是新战斗系统需要补齐的框架基准。

## 1. 问题来源

用户反馈三个体感问题：

1. 玩家战斗移动可能因为 NPC tick 移动或占位冲突失败，移动失败后会引起连锁反应。
2. NPC 移动后，前端地图有时不能正确显示 NPC 的新位置。
3. 第二轮开始时，玩家页面回到主动进入战斗时的“可取消”页面，默认目标仍是旧目标数据，导致射程预判失败；玩家点取消后，前端退出战斗态，但后端仍处于战斗态，最终卡住。

本设计案先记录定位事实，不立即实施修复。

## 2. 已确认事实

### 2.1 战斗移动失败真实存在

`oblivions/cache/battles/combat_debug.log` 中已有真实记录：

1. 玩家提交 `move -> move -> unarmed_strike`。
2. 第一段 `move` 的 `CHAIN_RULES` 返回：
   - `pass=false`
   - `reason=all_targets_skipped:tile_occupied`
3. 后续第二段 `move` 和 `unarmed_strike` 仍继续验证并执行。

另一次记录中：

1. 玩家提交 `move -> unarmed_strike`。
2. `move` 因 `tile_occupied` 被过滤。
3. `unarmed_strike` 仍继续执行，并打死目标。

对应结构：

`oblivions/include/game/combat/combat.chain.php`

在 `combat_chain_project()` 中，单个 action 规则失败后进入 `continue`，不会终止后续 action。该策略对普通技能失败也许合理，但对“改变后续上下文的前置动作”存在连锁风险。

### 2.2 移动占位冲突有双重来源

战斗移动占位检查来自：

1. `combat_tag_derive_tile_occupied()`
   - 文件：`oblivions/include/game/combat/combat.tag.php`
   - 规则阶段通过 `obl_get_pids_in_tile()` 检查目标格是否已有其他单位。
2. `obl_perform_move_core()`
   - 文件：`oblivions/include/game/move.func.php`
   - 真实 execute 阶段再次检查目标格是否被占用。

这意味着：

1. verify 阶段可能通过，execute 阶段仍可能因实时占用变化失败。
2. 只要 NPC 或其他单位在玩家提交前后改变了位置，就可能出现前端预判成功、后端执行失败。

### 2.3 NPC idle 移动真实存在

NPC 非战斗移动由 tick 系统执行：

1. `obl_tick_dispatch()` 会执行 `idle_npc` phase。
2. `obl_tick_phase_idle_npc()` 遍历当前区域 NPC。
3. 非战斗 NPC 调用 `obl_enemy_tick()`。
4. 巡逻/搜寻最终调用 `obl_enemy_move()`。
5. `obl_enemy_move()` 修改 `$enemy['pls']` 并 `obl_save_player($enemy)`。

对应文件：

1. `oblivions/include/game/tick.func.php`
2. `oblivions/include/game/enemy_ai.func.php`

注意：战斗中的敌人 `action === 'battle'` 会跳过 idle tick，但非战斗 NPC 仍会移动，并可能占用玩家计划移动格。

### 2.4 战斗中前端地图 NPC 位置可能不同步

> 本节原始诊断在本轮 TickFrame / changedScopes 更新后已有短期补丁：`battle.ts` 的 `refreshEnemyLocation()` 已会把 `enemies` API 结果回填到 `mapStore.enemies`，heartbeat 的 `changed_scopes` 也会触发地图/敌人刷新。因此“完全不写回 mapStore”不再是当前事实。
>
> 但该补丁只解决“探索态地图数据及时刷新”的症状，并没有把战斗 UI 的真值源从探索地图状态中剥离。Combat ViewModel 仍然必要。

前端地图实体从 `mapStore.enemies` 派生：

1. `vex-vue/src/stores/entities.ts`
2. `vex-vue/src/composables/useMapEntities.ts`

历史问题是战斗刷新过程中：

1. `battle.ts` 的 `refreshEnemyLocation()` 会 `dataManager.fetch('enemies', true)`。
2. 它只把指定 NPC 的位置写到 `battleStore.enemyLocation`。
3. 它没有写回 `mapStore.enemies`。
4. `mapStore.loadMap()` 只在普通移动、战斗结束、部分探索/物品操作后触发。

本轮更新后的当前状态：

1. heartbeat 返回 `changed_scopes`。
2. 命令推进与战斗刷新会消费 `changed_scopes`。
3. `game_map` / `enemies` 变化会触发地图或敌人刷新。
4. `refreshEnemyLocation()` 会把 enemies 列表写回 `mapStore.enemies`。

剩余框架问题：

1. 地图实体层仍主要从探索态 `mapStore.enemies` 派生。
2. 战斗目标、默认目标和射程预判仍混用 `currentEnemyPid` / `mapStore.enemies`。
3. 多敌人战斗、死亡/逃跑/隐藏、玩家战斗移动后的实体投影仍缺少统一战斗上下文。

### 2.5 “取消”是假退出

状态栏战斗按钮逻辑：

`vex-vue/src/components/layout/StatusBar.vue`

当前行为：

1. `battleBtnState === 'normal'` 时调用 `battleStore.startBattle(0)`。
2. `battleBtnState === 'battle'` 时调用 `battleStore.exitBattleMode()`。
3. `battleBtnState === 'aim'` 时广播 `battle:aim-exit`。

问题：

`exitBattleMode()` 是纯前端状态切换：

1. `currentMode = 'normal'`
2. `currentEnemyPid = 0`
3. `battleModalOpen = false`
4. `broadcast('battle:ended')`

它没有向后端提交任何“取消/逃跑/退出战斗”命令。

后端 contract 明确：

1. `battle.submit_turn` 只允许 `action='battle'`。
2. 且需要 `obl_battle_state === PLAYER_TURN`。
3. 如果后端仍在 battle，前端本地退出会造成模式锁和后端状态不一致。

因此“点取消退出战斗状态后卡住”是真实结构问题，不是单纯 UI 文案问题。

### 2.6 默认目标可能是旧目标

`battle.ts` 当前通过 `extractEnemyPid(battleQueue)` 提取当前敌人 PID。

实际逻辑：

1. 遍历 `battle_queue.queue`。
2. 返回第一个 `type > 0` 的 pid。

这个值被写入：

1. `battleStore.currentEnemyPid`
2. `battle:preload-init.enemyPid`
3. `PreloadArea.enemyPid`

然后 `PreloadArea` 在 enemy 目标技能点击时，默认把动作目标设为该 pid。

问题：

1. 它不是“当前玩家回合的目标集合”。
2. 它不是“当前可攻击目标”。
3. 它不是“最新地图位置上的目标”。
4. 多敌人战斗中，它只是队列中的第一个 NPC。

射程判断又依赖 `mapStore.enemies`：

`vex-vue/src/components/battle/PreloadArea.vue`

如果 `mapStore.enemies` 没同步，默认目标和射程预判都会基于旧数据。

## 3. 概念提炼

这三个问题不是孤立个例，而是同一个框架缺口：

当前前端没有独立的“战斗上下文视图”。

前端战斗 UI 目前混用了四类状态源：

1. 后端真实战斗状态
   - `player_info.action`
   - `player_info.obl_battle_state`
   - `battle_queue`
2. 探索地图状态
   - `mapStore.curLoc`
   - `mapStore.curRegion`
   - `mapStore.enemies`
3. 本地 UI 状态
   - `battleStore.currentMode`
   - `uiStore.battleBtnState`
   - `PreloadArea.mode`
4. 单个敌人快捷字段
   - `battleStore.currentEnemyPid`
   - `battleStore.enemyLocation`

这些状态源没有一个明确的战斗中统一真值源。

因此，当发生 NPC 移动、动作失败、队列推进、第二轮开始、多敌人目标变化时，前端会出现：

1. UI mode 与后端 action 不一致。
2. 地图敌人位置与后端敌人位置不一致。
3. 默认目标与真实可选目标不一致。
4. 射程预判与后端验证不一致。
5. 前端“取消”语义与后端战斗状态不一致。

## 4. 应新增的框架基准

### 4.1 Combat ViewModel

需要新增一个战斗上下文视图模型，作为战斗 UI 的唯一数据源。

建议概念：

```ts
interface CombatViewModel {
  qid: number;
  state: 'IDLE' | 'PLAYER_TURN' | 'PROCESSING';
  actorPid: number;
  playerPid: number;
  roundNum: number;
  combatants: CombatantViewModel[];
  currentActorPid: number | null;
  validTargets: CombatTargetViewModel[];
  defaultTargetPid: number | null;
}

interface CombatantViewModel {
  pid: number;
  type: number;
  name: string;
  hp: number;
  maxHp: number;
  ap: number;
  maxAp: number;
  pgroup: number;
  pls: number;
  state: number;
  active: boolean;
}
```

该 ViewModel 应由后端 `player_info` 或独立 `combat_context` API 提供，前端不应从 `battle_queue` 和 `mapStore.enemies` 临时拼。

### 4.2 战斗地图投影层

战斗中地图实体不应直接依赖探索态 `mapStore.enemies`。

建议拆分：

1. 探索地图实体：来自 `mapStore.enemies`。
2. 战斗地图实体：来自 `CombatViewModel.combatants`。
3. `entitiesStore` 根据 `battleStore.currentMode` 选择数据源。

这样 NPC 战斗位置、玩家移动后的计划/实际位置、死亡/逃跑状态都可以从战斗上下文视图统一派生。

### 4.3 目标选择不能再是单个 currentEnemyPid

`currentEnemyPid` 应降级为 UI 辅助字段，不能作为战斗目标真值源。

PreloadArea 应读取：

1. `validTargets`
2. `defaultTargetPid`
3. 每个目标的最新 `pgroup/pls`

射程预判应基于 Combat ViewModel，而不是 `mapStore.enemies`。

### 4.4 前端 UI mode 必须从后端战斗状态派生

当前 `exitBattleMode()` 允许纯前端退出 battle mode，这是错误语义。

新的框架基准：

1. 如果后端 `action='battle'`，前端必须保持 battle mode。
2. `PLAYER_TURN` 显示装填区。
3. `PROCESSING` 显示等待区。
4. `IDLE` 才允许退出 battle mode。
5. UI 的“取消”只能取消本地预装填/瞄准，不能退出后端战斗。

重要例外：

玩家主动攻击的“预装填”阶段允许前端先进入 `currentMode='battle'`，此时后端尚未 `action='battle'`。这是既有设计中明确允许的窗口期：前端需要先显示装填区，玩家提交 `battle.start` 后后端才创建战场。该例外不应被“后端派生 UI mode”规则误伤。

如果需要真正离开战斗，应使用明确后端动作：

1. `escape`
2. 或未来新增 `battle.abort`，但它必须有后端状态机语义。

### 4.5 动作链失败策略

当前动作链策略是：

1. 单 action 失败 -> 记录失败 -> 跳过该 action -> 后续继续。

这对部分动作合理，但对“上下文改变型动作”不一定合理。

建议引入动作链失败策略：

```php
chain_failure_policy:
  - continue       // 默认：失败后继续
  - stop_chain     // 失败后停止后续动作
  - stop_dependent // 停止依赖该动作上下文的后续动作
```

`move` 更适合至少使用 `stop_dependent`，因为它改变：

1. actor 位置
2. 后续攻击距离
3. 后续 tile target 原点
4. 后续 AP 动态成本

如果没有依赖图，短期可对 `move` 使用 `stop_chain`，避免移动失败后继续执行基于错误预期的动作。

## 5. 推荐推进方向

### 5.1 第一阶段：明确状态真值源

先定义 Combat ViewModel 的后端输出结构。

建议优先选项（本轮采用）：

1. 在 `player_info` 增加 `combat_context` 字段。
2. 暂不新增独立 `combat_context` scope，因为战斗刷新链路已经强制拉取 `player_info`，直接挂载可以避免额外 HTTP。
3. 未来如果非战斗页面也需要轻量读取战斗上下文，再拆独立 scope。

内容至少包括：

1. qid
2. battle state
3. current actor pid
4. active combatants with latest position
5. player turn valid target list
6. default target pid

### 5.2 第二阶段：前端战斗 UI 改用 Combat ViewModel

改造点：

1. `battle.ts`
   - 不再从 `battle_queue` 提取第一个 NPC 作为 currentEnemyPid。
   - 改为读取 Combat ViewModel。
2. `PreloadArea.vue`
   - 目标、射程、默认目标改用 Combat ViewModel。
3. `entities.ts`
   - 战斗中使用 Combat ViewModel combatants 作为地图实体来源。
4. `StatusBar.vue`
   - battle 状态下不再允许本地 `exitBattleMode()`。
   - “取消”仅表示取消预装填/退出瞄准；若已在后端战斗中，应显示“战斗中”或“逃跑”。

### 5.3 第三阶段：动作链失败策略

后端新增 action 级失败策略配置：

1. `move`：`stop_dependent` 或 `stop_chain`
2. 普通攻击：`continue`
3. heal：`continue`
4. escape：成功后 actor terminated，已有终止逻辑；失败策略可继续保持明确。

执行时：

1. `combat_chain_project()` 在 action 失败时读取 failure policy。
2. 若 `stop_chain`，停止后续验证。
3. 若 `stop_dependent`，至少在没有依赖图前降级为 `stop_chain`。
4. battlelog 应记录“后续动作因前置动作失败被取消”，供前端解释。

## 6. 当前结论

这不是三个具体 bug 的集合，而是新战斗系统进入多回合、多单位、移动动作链后暴露的框架缺口。

核心问题：

1. 前端缺少独立 Combat ViewModel。
2. 战斗地图显示仍借用探索地图状态。
3. 战斗目标选择仍借用单个 `currentEnemyPid`。
4. 前端 UI mode 可以脱离后端 battle state。
5. 动作链缺少上下文改变型动作的失败策略。

因此，后续不建议分别补：

1. 移动失败 toast。
2. 战斗后刷新一次地图。
3. 禁用取消按钮。

更优雅的方向是建立：

`后端 Combat ViewModel -> 前端 Combat Store -> 战斗地图实体/目标/射程/UI mode 统一派生`

并补齐：

`动作链失败策略`

这两者应成为新战斗系统的框架基准。
