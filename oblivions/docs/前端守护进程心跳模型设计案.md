## 一、核心事实:前端是后端的守护进程

Oblivions 后端是**无状态请求模型**:每次 HTTP 请求跑完一个 PHP 进程就退出,没有任何常驻线程。这意味着:

| 职责 | 旧式后端守护进程会做 | 本系统的实际承担者 |
|---|---|---|
| 何时推进 tick | 后端定时器/循环 | **前端 setInterval 轮询激活 common.inc.php** |
| 何时执行 NPC 先攻轮 | 后端 cron/事件循环 | **前端每次轮询请求触发后端游戏刻调度** |
| 何时玩家可操作 | 后端推送事件 | **前端读 obl_battle_state 字段决定 UI** |
| 何时停止轮询 | 后端发结束信号 | **前端不再停止轮询,无条件持续** |

**设计原则**:前端心跳是后端游戏刻推进的唯一驱动力,但与前端业务数据同步**彻底解耦**。

---

## 二、原设计案的问题回顾

原设计案将心跳 API 调用与 `refreshBattle()` 合并到同一个常驻定时器中,产生以下问题:

| 问题 | 场景 |
|---|---|
| **动画干扰** | 模态框/碰撞动画播放期间,`refreshBattle()` 被 `isProcessingBattle` 挡掉,心跳的 tick 激活也随之丢弃 |
| **职责耦合** | 心跳做 tick 激活,`refreshBattle()` 做业务同步+动画播放,两者间隔需求不同(200ms vs 事件驱动) |
| **动画后竞争** | 动画结束后 `isProcessingBattle=false`,下一跳立即触发 `refreshBattle()`,与上一轮伤害数字残留重叠 |

**解决方向**:心跳只做 tick 激活,与前端所有业务逻辑彻底解耦。

## 三、方案

### 3.1 后端:api_v2.php 新增心跳钩子

```php
switch ($action) {
    case 'heartbeat':
        api_response('success');
        break;
    // ...其他分支不变
}
```

**链路**:
1. `require common.inc.php` → cookie 取 `$cuser`/`$cpass`、游戏刻调度(若 `obl_pretick < obl_tick`)、状态机超时恢复、save_gameinfo
2. `obl_game_entrypoint('api')` → 完整认证闸门
3. switch → `heartbeat` 分支 → 直接返回,不进业务 handler

**省掉的开销**(相对 `action=player_info`):
- 战斗队列查询(`obl_fetch_queue_all_by_qid`)
- 30+ 字段响应组装
- enriched 队列成员拉取
- **响应 body 仅为 `{"status":"success"}`**,心跳关心状态码,不读 body

**保留的必要开销**:
- 1 次 user 表 SELECT(密码校验)
- 1 次 oblplayers SELECT(pid 抓取)

### 3.2 前端:心跳守护进程(纯 tick 激活器)

**新增** `battle.ts` 独立心跳函数,不与 `refreshBattle()` 耦合:

```ts
/** 心跳间隔(毫秒)—纯后端 tick 激活,不涉及任何业务逻辑 */
const DAEMON_BEAT_INTERVAL = 200;

/** 守护进程定时器(不响应式,仅内部使用) */
let daemonTimer: ReturnType<typeof setInterval> | null = null;

/** 心跳拍:fire-and-forget,成功/失败都不影响前端业务 */
async function _daemonBeat(): Promise<void> {
  try {
    await fetch(`${API_BASE}/api_v2.php?action=heartbeat`, { credentials: 'include' });
  } catch {
    // 静默失败,下次心跳重试
  }
}

/** 启动守护进程(页面挂载时调用) */
function startDaemonPoll(): void {
  if (daemonTimer !== null) return;
  daemonTimer = setInterval(_daemonBeat, DAEMON_BEAT_INTERVAL);
}

/** 停止守护进程(页面卸载时调用) */
function stopDaemonPoll(): void {
  if (daemonTimer !== null) {
    clearInterval(daemonTimer);
    daemonTimer = null;
  }
}
```

**设计约束**:
- 不走 `dataManager` 层(去重/缓存/性能标记全多余)
- 不读响应 body(只确保请求到达)
- 失败不弹 toast、不改状态、无重试
- 与所有 store 正交

**间隔选择:200ms** = 每秒 5 次请求
- NPC 先攻轮推进节奏:5 NPC/秒,体感流畅
- 服务器负载:本地 PHP + MySQL,200ms 间隔认证 + 简单查询零压力
- 非战斗时(obl_pretick=obl_tick):只有认证开销,基本零负载

### 3.3 NPC 状态同步轮询保留(不变)

原有的 NPC 定时器**不做任何代码改动**:

| 原有职责 | 归属变化 |
|---|---|
| tick 激活(隐含) | ➜ **心跳承担** |
| 前端状态同步 | ➜ **保留** |

```ts
// battle.ts — 不变
function startNpcTurnRefresh(): void {
  if (npcTurnRefreshTimer !== null) return;
  npcTurnRefreshTimer = setInterval(() => {
    dataManager.invalidate('player_info');
    dataManager.invalidate('battle_log');
    refreshBattle();
  }, NPC_TURN_REFRESH_INTERVAL);
}
```

此时它的隐含双重职责(tick 激活 + 状态同步)被剥离后,变为**纯粹的"状态发现"**:
- 心跳刚跑完 tick(`obl_pretick < obl_tick` 条件已不成立)
- NPC 定时器的 `player_info` fetch 遇到 common.inc.php 的 tick 调度块为 no-op
- 只走认证 + SELECT + 业务字段组装
- `refreshBattle()` 拿到最新的 `obl_battle_state` 做 UI 同步

间隔保持 `NPC_TURN_REFRESH_INTERVAL = 1000`(1 秒),用户感知刷新率无需与心跳同步。

### 3.4 保留的渲染层判断

以下渲染层判断与心跳/NPC 定时器均无关,保留:

- `isPlayerTurn = (state === 'WAITING_PLAYER')` — 决定 UI 显示装填区还是等待提示
- `isNpcActing = (state === 'NPC_ACTING')` — 状态栏"NPC 行动中"提示
- `isInBattle = (action === 'battle')` — 决定模式切换

## 四、动画期间的行为

动画播放(碰撞 450ms + 模态框最长 30s)期间:

| 组件 | 行为 |
|---|---|
| **心跳 200ms** | 持续向后端发送,不受任何影响,NPC tick 继续推进 |
| **refreshBattle()** | `isProcessingBattle` 锁挡住所有调用(事件驱动 + NPC 定时器),不执行 |
| **NPC 定时器** | setInterval 照样触发,但回调执行到 `isProcessingBattle` 守卫处 return |
| **动画结束后** | `isProcessingBattle=false`,下一轮 NPC 定时器或事件驱动触发 `refreshBattle()`,同步最新状态 |

心跳与动画播放**完全正交**——既不会被动画挡掉,也不会干扰动画播放。

---

## 五、两个定时器的独立调优

| 定时器 | 职责 | 建议间隔 | 调优依据 |
|---|---|---|---|
| 心跳 `DAEMON_BEAT_INTERVAL` | 后端 tick 激活 | 200ms | NPC 推进节拍(5 NPC/s) |
| NPC 轮询 `NPC_TURN_REFRESH_INTERVAL` | 前端状态同步 | 1000ms | 用户感知刷新率 |

不再需要因为 tick 激活速度去被迫提高前端刷新频率。

## 六、后端兜底机制(已存在,无需新增)

后端已有的保护机制使前端无条件心跳**安全无副作用**:

| 场景 | 后端反应 | 资源消耗 |
|---|---|---|
| 战斗中 NPC_ACTING | tick 调度跑,NPC 先攻轮推进 1 步 | 正常业务 |
| 战斗中 WAITING_PLAYER | tick 调度 if 不成立(pretick=tick),不跑 | 1 次认证 + 1 次 SELECT |
| 战斗中 PLAYER_ACTING(瞬态) | tick 调度跑但监听器 continue(玩家顺位) | 1 次认证 + 队列扫描 |
| 非战斗状态 | tick 调度 if 不成立,不跑 | 1 次认证 + 1 次 SELECT |
| 战斗结束 ENDED → IDLE | 状态记录已销毁,tick 调度 if 不成立 | 同上 |

**关键证据**:[enemy_ai.func.php:78-86](file:///d:\wamp64\www\phpdts/oblivions/include/game/enemy_ai.func.php#L78) 监听器碰到玩家顺位时:

```php
if ($current['type'] == 0) {
    # 仅当当前状态为 NPC_ACTING 时触发（避免非法转换）
    if (obl_battle_state_get($qid) === OBL_BS_NPC_ACTING) {
        obl_battle_state_transition($qid, 'npc_done_player_turn');
    }
    continue;
}
```

前端在 WAITING_PLAYER 状态继续轮询,后端会扫到玩家是当前顺位者,但因状态不是 NPC_ACTING 直接 continue,不会触发非法转换、不会有副作用、不浪费任何业务计算。

## 七、对 battle_main 解耦的影响

本设计案是 [battle_main解耦设计案v2.md](battle_main解耦设计案v2.md) 的**前置依赖**:

- 心跳守护进程确保 tick 持续激活,解耦 battle_main 时的实测验证更可靠(不受前端轮询策略干扰)
- 前端心跳模型下,后端四系统(战斗-队列-状态机-tick)的关系更清晰:tick 是被动响应前端心跳的脉冲,queue/state 是后端自治的状态层,battle 是 tick 调度内的执行单元
- 前端零改动即可支持后端 battle_main 解耦(解耦纯属后端内部结构重构,API 字段不变)
