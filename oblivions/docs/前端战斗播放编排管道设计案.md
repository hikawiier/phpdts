# 前端战斗播放编排管道设计案

> 目的：记录“战斗移动首轮不播放动画，第二轮攻击开始才播放”背后的前端结构问题，并研判是否应把前端战斗演出从硬编码分支提升为可编排、可等待、可恢复的播放管道。

## 1. 当前触发问题

用户实测结论：

1. `地图移动 -> 空手攻击` 在后端对象定位上已经正确，移动后的攻击目标没有问题。
2. 问题转移到前端表现层：首轮攻击时，战斗移动动画不会播放；第二轮攻击开始时才看到移动。

这说明后端动作链投影与执行链已基本打通，但前端播放链仍没有把“位移动作”当成一等动作阶段处理。

## 2. 已复核事实

### 2.1 后端 battlelog/Director 数据已有移动语义

`vex-vue/src/stores/battle-director-v2.ts` 已把后端 battlelog.v2 转成 `BattlePlayScriptV2`：

1. `directV2()` 按 `round_start / turn_start / action_start / effect_applied / action_end` 组装 segment/action/effect。
2. `effect_applied` 会进入 `toDirectedEffect()`，并由 `decideEffectVisual()` 把 `move` effect 映射为 `move_avatar` visual。
3. `deriveActionAnimationFromEffects()` 发现 tile 目标的 `move` effect 后，会把 action animation 改成 `{ kind: 'move', targetIds: [...] }`。

结论：Director 层已经能识别“这个动作包含位移视觉”，问题不在 battlelog 缺字段。

### 2.2 Store 播放层仍是硬编码流程

`vex-vue/src/stores/battle.ts` 当前 turn 播放顺序是：

1. `playTurnSegment()`
2. `processSegmentEvents()`
3. 对每个 action 调 `processActionAnimation()`
4. 打开 `BattleModal` 播文字
5. 关闭后广播 `battle:play-damage-numbers`

`processActionAnimation()` 的核心问题：

1. 只要 `action.animation.kind !== 'none'` 就广播 `battle:play-action-animation`。
2. 广播后立即寻找 `damageEffect`。
3. 如果没有 damage effect，直接 `return`。
4. 只有 damage action 才会根据 `impactAt` 和 target duration 等待。

因此移动 action 虽然被广播给组件，但播放器不会等待移动动画完成。移动在当前框架中只是 fire-and-forget 副作用，不是一个可等待的播放阶段。

补充复核：`processActionAnimation()` 还同时承担了三类职责：

1. 广播组件动画事件。
2. 直接调用 player / actor 的攻击与受击动画。
3. 用 `sleep()` 猜测 impact 与 target duration。

这使它既不是纯编排器，也不是纯执行器；未来每加一种技能视觉，就会继续往这个函数堆特例。

### 2.3 CollisionAnimation 也是命令式事件消费者

`vex-vue/src/components/battle/CollisionAnimation.vue` 当前职责：

1. `onMounted()` 后监听 `battle:play-action-animation`。
2. 收到事件后根据 `plan.kind` 分支播放。
3. `playMoveAnimation()` 查 `actorRegistry`、目标 tile DOM、`#mapGrid`。
4. 找齐后直接 `actor.moveTo(...)`。

问题：

1. `playMoveAnimation()` 没有完成回调反馈给 store。
2. 找不到 actor / tile / grid 时静默 return。
3. 事件是同步广播，不具备队列、重放、ack、timeout、retry。

首轮切入战斗时，如果 `BattleMode / CollisionAnimation / MapGrid / actorRegistry` 任一环晚一帧准备好，第一条移动动画事件就可能被吞掉。

补充复核：同一段内如果移动后紧接攻击，攻击动画会调用底层 `attackAnim()`，而 `actorAnimations.ts` 的攻击动画开始时会 `gsap.killTweensOf(el)`。因此未被 await 的移动 tween 不只是“看起来太快”，而是可能被后续攻击动画实际杀掉。

### 2.4 actor 动画本身支持完成回调

`vex-vue/src/composables/useActorAnimation.ts` 的 `moveTo()` 已支持 `onDone?: () => void`。

底层动画：

1. `moveActor()` 鸭子步约 0.5s。
2. `jumpActor()` 空中 0.5s + 落地弹性 0.9s，总约 1.4s。

结论：底层演员能力足够，缺的是战斗播放层对“等待动画完成”的协议。

### 2.5 地图实体层已有独立调度体系

`vex-vue/src/composables/useMapEntities.ts` 已经有：

1. actor registry。
2. `isMoving` 锁。
3. `syncEntityPosition()` 跳过移动中的 actor。
4. player / enemy 的地图数据变化 watch。
5. 首次入场、位置同步、短中长距离移动分级。

但战斗动作动画绕过了地图数据 watch，直接从 `CollisionAnimation` 调 actor。也就是说当前前端存在两套移动入口：

1. 地图数据变化驱动的实体调度。
2. 战斗日志驱动的动作动画调度。

这两套入口没有共享“播放计划/完成协议/准备屏障”。

### 2.6 刷新入口也缺少单一播放入口

当前 battlelog 播放可能由多种事件间接触发：

1. `preload:executed`
2. `game:tick-advanced`
3. `game:action-completed`
4. NPC turn refresh timer

`battle.ts` 主要依赖 `isProcessingBattle / isPlayingBattleLog` 防重入。这能避免大部分重复执行，但概念上仍不是“一个明确的播放事务入口”。

这不是当前移动动画 bug 的主因，但说明前端播放系统还没有形成和后端动作链类似的单一 orchestration 层。

## 3. 概念提炼

这不是 `move` 技能特例，而是前端播放框架缺少一等概念：

### 3.1 当前缺失的概念：PlaybackStep

战斗回放不应该只是一段文本脚本加若干组件事件，而应该是按顺序执行的播放步骤：

1. 动作姿态：攻击者冲刺、投掷、移动、逃跑。
2. 命中时点：伤害结算视觉、受击反应、HP 条更新。
3. 文本呈现：动作说明、effect 文本、notice。
4. 残留反馈：伤害数字、清场、死亡/逃跑淡出。
5. 状态同步屏障：地图 actor / DOM / registry 准备完成。

每个步骤至少应有：

1. `kind`
2. `payload`
3. `awaitPolicy`
4. `timeout`
5. `fallback`

### 3.2 当前缺失的概念：可等待动画协议

动画组件不能只是事件消费者。只要某个动画会影响后续动作的视觉位置，它就必须能告诉播放层：

1. 已开始。
2. 已完成。
3. 因 DOM/actor 不可用而跳过。
4. 超时兜底。

移动后攻击尤其依赖这一点：攻击动画的起点必须是移动后的 actor 视觉位置。

### 3.3 当前缺失的概念：播放准备屏障

首轮进入战斗时，`currentMode = battle` 会触发组件渲染，但 `refreshBattle()` 可能很快开始播放 battlelog。

因此播放第一条地图动画前需要一个轻量屏障：

1. `nextTick()`
2. `requestAnimationFrame()`
3. actor/tile/grid 查询重试
4. 超时后降级而不是永久挂起

这不是为了修一个 race condition，而是定义“地图动作播放必须等播放目标可寻址”。

## 4. 对用户抽象的判断

用户提出：“是不是因为现在前端播放机制是硬编码，前端动画播放也需要编排和管道链式播放？”

研判结论：方向成立。

但这里需要进一步校正概念边界：编排本身应属于“导演系统”的职责，而不是播放组件或 battle store 的职责。当前 `battle-director-v2.ts` 名义上是 Director，但实际只完成了第一半：把后端事实日志整理成 `BattlePlayScriptV2`。它还没有完整承担“把事实翻译成前端播放意图与时间结构”的导演职责。

因此，问题不是“Director 外面再加一个无关 Pipeline”，而是 Director 系统需要补齐第二层产物：

1. 后端数据层：`battlelog.v2` 只表达事实。
2. 导演编排层：Director 把事实编排成可播放脚本，包括 segment、action、effect、visual、step、时序、等待策略。
3. 动画播放层：播放器只执行 Director 给出的 playback steps，不再自行判断业务语义。

当前设计案中的 `PlaybackStep / BattlePlaybackRunner` 应理解为 Director 系统的播放编排子层，而不是脱离 Director 的新平行系统。

但建议不要一步到位做一个过重的通用 timeline 引擎。更合适的框架升级路径是：

1. 先把 `battle.ts` 中硬编码的 `processActionAnimation / playTurnSegment` 收敛成可测试的播放编排层。
2. 引入 `PlaybackStep` 作为最小一等概念。
3. 先实现 `action_animation` step 的 completion/timeout/retry。
4. 再把 `modal_text`、`damage_linger`、`combatant_cleared` 逐步纳入同一管道。

这样可以解决当前 bug，同时为 P9 的多效果、多目标、多段动作提供可扩展基准。

## 4.1 Director 系统完整性复核

当前 Director 系统并不完整。

### 已完成部分

`battle-director-v2.ts` 已完成：

1. 过滤 render channel 的 battlelog.v2 事件。
2. 按 log_id 排序。
3. 把 action_start / effect_applied / action_end 聚合成 action。
4. 把 round / turn / battle_end 聚合成 segment。
5. 把后端 target/effect 映射为前端可读的 `CombatTargetView / DirectedEffectV2`。
6. 初步推导 `ActionAnimationPlan` 和 `EffectVisualPlan`。

这些能力说明 Director 已经是“事实整理 + 初步视觉意图推导器”。

### 缺失部分

Director 尚未完成：

1. 没有输出一等 `PlaybackStep`。
2. 没有定义动作动画、文本、残留数字、清场之间的顺序。
3. 没有为每个 step 定义 `awaitPolicy / timeout / fallback`。
4. 没有把 move 后 attack 的依赖关系显式表达为时间结构。
5. 没有把 effect visual 统一编排，只是让不同组件在不同阶段自行消费。
6. 没有把“首轮地图 DOM/actor 准备”定义成播放前置条件。

所以当前 `BattlePlayScriptV2` 仍偏向“渲染素材包”，还不是完整的“播放剧本”。

### 应修正的职责边界

更完整的 Director 系统应分为两层：

1. `BattleDirector`
   - 输入后端 battlelog.v2。
   - 输出语义脚本：segments / actions / effects / notices。
   - 不关心 DOM，不执行动画。

2. `BattlePlaybackDirector` 或 `BattlePlaybackPlanner`
   - 输入语义脚本。
   - 输出 playback steps。
   - 决定播放顺序、并行/串行、等待策略、fallback。
   - 不直接执行 DOM 动画。

播放器/Runner 只负责执行 steps：

1. 找 actor adapter。
2. 调动画函数。
3. await completion。
4. timeout 后降级。

这能保持 Director 纯函数/可测试，同时避免把业务编排散落到组件。

### 结论

原设计案已经指出“需要编排和管道”，但对 Director 系统完整实现的研判不足。准确说，后续任务不应只是新增一个播放 runner，而应补齐前端 Director 系统：

`battlelog.v2 -> semantic script -> playback steps -> runner execution`

当前 bug 暴露的是第二段缺失：`semantic script -> playback steps` 没有成型，导致 `battle.ts` 和组件临时承担导演职责。

## 5. 推荐实施方案

### 5.0 实施边界更新：一步到位补齐导演播放框架

根据最新约束，本轮不再采用“最小兼容修复 / 事件 ack 过渡”作为主线：

1. 不要求兼容旧事件式动画播放结构。
2. 不要求保留 `CollisionAnimation` 作为关键动作的播放入口。
3. 不以修补 `move` 个例为目标。
4. 不让 `battle.ts` 继续承担导演编排职责。

本轮目标调整为一次性补齐：

`battlelog.v2 -> semantic script -> playback plan -> playback runner -> actor executor`

新的职责边界：

1. `battle-director-v2.ts`
   - 继续负责后端事实到语义脚本。
   - 新增语义脚本到 playback plan 的规划能力。
2. `battle-playback-runner.ts`
   - 执行 Director 产出的 playback steps。
   - 管理 step 顺序、await、timeout、fallback。
   - 不再根据 action/effect 重新推导业务语义。
3. `battle-actor-executor.ts`
   - 面向 actorRegistry / playerAvatarStore / DOM anchor 的动画执行器。
   - 所有关键动作返回 Promise。
4. `battle.ts`
   - 只负责刷新状态、拉取 battlelog、调用 Director、调用 Runner、标记已播放。
   - 不再内联 `processActionAnimation()` 这种业务/动画混合函数。

因此，下面的 5.1 事件 ack 方案只作为历史备选，不作为本轮主实施路线。

### 5.1 最小但结构正确的第一阶段：事件 ack 方案

第一阶段目标：让移动动画成为可等待 action phase，并防止首轮事件丢失。

建议改动：

1. 扩展事件类型
   - `PlayActionAnimationEventData` 增加 `animationId?: string`。
   - `AppEvent` 增加 `battle:action-animation-complete`。

2. 在 `battle.ts` 增加动画等待器
   - `playActionAnimationStep(action, npcPid)` 生成 animationId。
   - 监听 `battle:action-animation-complete`。
   - 广播 `battle:play-action-animation`。
   - 对 `move` 等关键动画 await completion。
   - 设置 timeout，避免组件异常导致播放死锁。

3. 在 `CollisionAnimation.vue` 增加完成回传
   - `playMoveAnimation()` 使用 `actor.moveTo(..., onDone)`。
   - onDone 广播 `battle:action-animation-complete`。
   - actor / tile / grid 未就绪时短暂重试若干帧。
   - 重试失败也广播 complete，带 skipped reason，播放层继续推进。

4. 保留现有 damage attack 分支
   - 第一阶段不强行重写所有攻击动画。
   - 但把 `move` 从 fire-and-forget 修正为 awaited action。

这个方案优点是改动较小，能快速验证当前 bug；缺点是关键动作仍通过事件总线跨组件播放，长期仍需要抽出 runner。

### 5.2 更彻底的第一阶段：演员 Promise 方案

如果决定从底层结构上更干净地处理，第一阶段可以直接减少关键动作对 `dataManager.broadcast()` 的依赖：

1. 在 actor 动画层提供 Promise 化 adapter。
   - `moveToAsync()`
   - `playAttackAsync()`
   - `playHitAsync()`
   - `playFadeOutAsync()`
2. 在播放编排层直接调用 actor adapter，而不是先广播给 `CollisionAnimation`。
3. `move` action 必须 await `moveToAsync()`。
4. 攻击 action 按规格执行：
   - 攻击者动作开始。
   - await impact。
   - 受击者 hit reaction。
   - await hit reaction 完成。
5. `CollisionAnimation.vue` 退化为兼容层或只保留非关键 CSS class 动画。

这个方案比事件 ack 更符合长期框架方向，因为它让“关键动作是否完成”回到播放管道本身，而不是依赖外部组件回传。

当前建议：如果目标是尽快恢复测试，先做 5.1；如果目标是趁此机会补齐新战斗系统前端基准，优先做 5.2，并把它作为 `BattlePlaybackRunner` 的第一步。

### 5.3 第二阶段：抽出 BattlePlaybackRunner

当第一阶段验证通过后，把播放编排从 `battle.ts` 中抽成独立模块：

文件建议：

1. `vex-vue/src/stores/battle-playback-runner.ts`
2. `vex-vue/src/types/battle-playback.ts`

核心类型建议：

```ts
export type PlaybackStepKind =
  | 'prepare_map'
  | 'action_animation'
  | 'modal_text'
  | 'effect_visual'
  | 'combatant_cleared'
  | 'damage_linger';

export interface PlaybackStep {
  id: string;
  kind: PlaybackStepKind;
  segment?: BattleSegmentV2;
  action?: DirectedActionV2;
  effects?: DirectedEffectV2[];
  awaitPolicy: 'none' | 'duration' | 'completion';
  timeout?: number;
}
```

`BattlePlaybackRunner` 负责：

1. 从 `BattleSegmentV2` 展开 steps。
2. 顺序执行 steps。
3. 管理 completion/timeout。
4. 不直接操作 DOM，只通过事件或 actor adapter 调组件。

### 5.4 第三阶段：统一 effect visual 消费

当前 `move_avatar` 由 `CollisionAnimation` 消费，`damage_number` 由 `DamageNumber` 消费，`fade_out` 又由 `processCombatantCleared()` 消费。

长期应统一为：

1. Director 只产出 visual plan。
2. PlaybackRunner 决定 visual plan 在哪个 step 播。
3. 组件只负责执行具体视觉，不决定播放顺序。

这样 P9 的 `grenade / whirlwind / vampiric_bite / execute` 不需要继续往 `battle.ts` 塞新分支。

## 6. 为什么不能只加固定 sleep

只在 `processActionAnimation()` 中对 `move` 加 `await sleep(1500)` 能缓解“攻击太快覆盖移动”，但无法解决：

1. 首轮组件尚未 mounted 时事件被吞。
2. actorRegistry 尚未注册时静默 return。
3. 不同移动距离动画时长不同。
4. 后续 escape / area burst / multi hit 仍会继续加分支。
5. 播放层不知道动画到底有没有开始。

因此固定 sleep 是表面修复，不符合当前“从问题提炼框架基准”的约束。

## 7. 当前 bug 的最可能原因

综合现有代码，首轮移动动画不播放、第二轮才播放，最可能由两个因素叠加：

1. `processActionAnimation()` 对没有 damage effect 的 move action 广播后立即返回，下一动作/下一段流程继续推进，移动动画没有成为时间轴上的阻塞阶段。
2. 同段后续攻击可能启动 `attackAnim()`，其 `gsap.killTweensOf(el)` 会杀掉刚开始但未完成的移动 tween。
3. 首轮进入 battle mode 时，`CollisionAnimation` 监听器、`MapGrid` DOM、actor registry 可能还未完成同一帧注册。`playMoveAnimation()` 查询失败会静默 return，事件不会重放；后续地图数据同步或第二轮动作开始时，actor 位置才被实体层 watch 修正。

这两个点都指向同一个结构问题：战斗播放层缺少“可等待、可确认、可重试”的动作动画管道。

## 8. 执行前准确性复核

本设计案基于以下已复核代码事实：

1. `battle-director-v2.ts` 已能从 `move` effect 推导 `move` action animation。
2. `battle.ts` 的 `processActionAnimation()` 只等待 damage effect 分支，move action 无 damage 时不等待。
3. `CollisionAnimation.vue` 的 `playMoveAnimation()` 调用 `actor.moveTo()` 时没有传入完成回调。
4. `useActorAnimation.moveTo()` 已支持 `onDone`。
5. `dataManager.broadcast()` 是同步广播，不提供事件持久化、ack 或重放。
6. `useMapEntities.ts` 的 actor registry 与地图位置同步已有调度和锁，但战斗动画未接入统一播放协议。
7. 攻击动画底层会 `killTweensOf`，未纳入同一播放时间轴的移动动画存在被后续攻击杀掉的真实风险。
8. `BattleModal.vue` 是当前少数具备 Promise 闭环的播放组件，说明“可等待播放协议”在项目内已有局部先例。

因此，“前端播放机制硬编码，动画播放需要编排和管道链式播放”的判断成立；当前最小优雅修复应以可等待动作动画协议为切入口，而不是只补一个 sleep。

## 9. 实施记录（2026-07-09）

本轮按“完整导演播放框架”路线执行，没有采用事件 ack 过渡方案。

### 9.1 Director 补齐 playback plan

已在 `vex-vue/src/stores/battle-director-v2.ts` 中新增：

1. `PlaybackStepKind`
2. `PlaybackAwaitPolicy`
3. `PlaybackStep`
4. `BattlePlaybackPlan`
5. `planPlaybackV2(script)`

新的 Director 输出链路：

## 10. 播放提交屏障补充（2026-07-11）

### 10.1 新发现的结构冲突

实局复核确认后端事件顺序正确，但前端存在两条相互竞争的时间线：

1. heartbeat / `player_info` / `game_map` 表达已经结算完成的权威状态。
2. battlelog.v2 表达用户尚未观看的事实播放顺序。

此前 `refreshBattle()`、守护心跳和命令队列会在播放 battlelog 前立即合并
`combat_context`、刷新地图和敌人列表。死亡或逃跑角色因此先从 CharacterHub 的
`aliveList` 消失，随后播放器才尝试执行投射、受击、逃跑和清场步骤。

这不是某个技能动画的特例，而是缺少“权威状态到视觉投影”的提交边界。

### 10.2 框架基准：Playback Commit Barrier

战斗事务内采用以下规则：

1. heartbeat 的 changed scopes 立即失效缓存并累计，但不立即刷新视觉投影。
2. `player_info` 立即更新状态机真值，但延迟向 CharacterHub 合并玩家和 combat context。
3. battlelog 驱动动作、效果、逃跑和 `combatant_cleared` 的可见顺序。
4. 只有播放追平后端并到达 `PLAYER_TURN` 或 `IDLE`，才统一提交地图、敌人、参战候选和 CharacterHub。
5. `PROCESSING` 表示后端可能已生成下一段尚未播放的事实，必须继续保留屏障。

该屏障明确区分：

`authoritative state -> deferred visual projection -> battlelog playback -> stable-boundary commit`

### 10.3 输入所有权

战斗模式、战斗刷新和 battlelog 播放期间，地图命令输入归战斗 UI 独占：

1. MapGrid 的格子、实体和 hover 不再向探索业务层派发命令。
2. WASD / 方向键不再触发 `map.move`。
3. AimMode 仍是战斗地图交互的唯一合法入口。
4. CommandQueue 保留 `BATTLE_LOG_PLAYING` 等锁作为纵深防御，并返回结构化 `lockReason`。
5. 交互竞态抵达业务层时，对战斗类本地锁静默收敛，不显示“移动失败”。

因此，本次修复同时解决了“角色先消失”和
`移动失败：当前状态不可执行此操作：BATTLE_LOG_PLAYING`，并把状态提交与输入所有权提升为播放框架约束。
