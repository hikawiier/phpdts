# 技能终结性字段驱动 — 设计补丁

> **基准**：补丁针对 `战斗操作区-装填轨道与AP槽-设计案-2026-07-12.md` v4
> **日期**：2026-07-12
> **性质**：框架基准修正（非特例补丁）
> **触发问题**：`escape`（逃跑）在后端配置中标记为 `finisher => true`，但前端硬编码分类表将其归入 `maneuver`，导致终结技约束（最后执行、不可拖拽、唯一性）未施加于逃跑。

---

## 一、根因分析

### 1.1 后端已有的两维分类

后端对技能有两个**独立**的分类维度：

| 维度 | 字段位置 | 值域 | 语义 |
|------|----------|------|------|
| **功能性质** | `skill_definition_config.php` 的 `category` | `utility` / `attack` / `passive` | 表达技能"做什么" |
| **时序约束** | `combat_skill_config.php` 的 `finisher` | `true` / `false` | 表达技能"何时执行"（终结技必须最后、唯一） |

证据（改动前状态）：
- `escape`：`category = 'utility'`，`finisher = true`
- `execute`：`category = 'attack'`，`finisher = true`
- `move`：`category = 'utility'`，`finisher = false`
- `heal`：`category = 'utility'`，`finisher = false`

改动后（§3.1 值域细化）：`utility` 拆为 `maneuver`/`support`，`attack` 改名 `assault`，与前端 1:1 对齐。

### 1.2 前端的混为一谈

前端 `skill-category.ts` 的 `SkillCategory` 枚举把两个维度压成一个：

```
'maneuver'  ─┐
'assault'   ─┤── 功能分类（对应后端 utility/attack 的细分）
'support'   ─┘
'finisher'  ──── 时序约束（对应后端 finisher bool）
```

这导致：
1. `escape` 被硬编码为 `'maneuver'`（凭字面语义猜），忽略了后端 `finisher = true`
2. `execute` 被硬编码为 `'finisher'`（碰巧对了），但并非因为读了后端字段
3. 若后端新增终结技，前端不会自动跟随

### 1.3 API 早已下发，前端未用

`skill_get_available_list()` 第 380 行：
```php
'finisher' => !empty($combat_config['finisher']) ? 1 : 0,
```

前端 `Skill` 类型第 400 行：
```typescript
finisher: number;
```

字段一直存在，前端 `isFinisherSkill()` 却查硬编码映射表，未读此字段。

### 1.4 唯一性校验缺失

后端 `combat_sort_actions()` 的兜底策略："多 finisher 只保留最后一个"。这是**防御性最后一道防线**，前端不应依赖它——UX 层应在用户尝试添加第二个终结技时就阻止，避免用户以为添加成功却被后端默默丢弃。

## 二、设计原则

### 原则 1：所有技能分类维度以后端字段为唯一权威

技能的两个分类维度均以后端下发字段为唯一数据源：
- **终结性**（时序约束）：`Skill.finisher` 字段
- **功能分类**（展示性质）：`Skill.category` 字段

前端不得维护任何独立的硬编码分类判定表。

### 原则 2：后端 category 值域与前端 1:1 对齐

后端 `skill_definition_config.php` 的 `category` 值域从粗粒度 `utility`/`attack`/`passive` 细化为 `maneuver`/`assault`/`support`/`passive`，与前端 `SkillCategory`（minus `finisher`）1:1 对齐。后端新增技能只需配置 `category` 字段，前端自动正确分类，**零双重同步**。

### 原则 3：`finisher` 是派生分类，优先级最高

`getSkillCategory(skill)` 优先检查 `skill.finisher`，为真则返回 `'finisher'`，覆盖功能分类。否则直接返回 `skill.category`。

### 原则 4：唯一性前置校验

前端在 `addToQueue` 入口阻止添加第二个终结技，给出 toast 提示。不依赖后端兜底。

---

## 三、实现方案

### 3.1 后端 `skill_definition_config.php` 值域细化

`category` 字段从 `utility`/`attack`/`passive` 改为 `maneuver`/`assault`/`support`/`passive`：

| 技能 | 旧 category | 新 category |
|------|-------------|-------------|
| move | utility | maneuver |
| escape | utility | maneuver |
| idle | utility | maneuver |
| heal | utility | support |
| unarmed_strike | attack | assault |
| throw | attack | assault |
| whirlwind | attack | assault |
| execute | attack | assault |
| vampiric_bite | attack | assault |
| grenade | attack | assault |
| flustered | passive | passive（不变） |

安全前提：后端无任何代码读取 `category` 字段（grep 确认仅 API 序列化那一行），纯显示元数据。

### 3.2 `skill-category.ts` 重构（删除映射表）

**签名变更**：`isFinisherSkill` 和 `getSkillCategory` 接受 `Skill` 对象，直接读字段。**删除 `SKILL_FUNCTIONAL_CATEGORY` 映射表**。

```typescript
import type { Skill } from '@/types/api';

export type SkillCategory = 'maneuver' | 'assault' | 'support' | 'finisher';

export const SKILL_CATEGORY_LABELS: Record<SkillCategory, string> = {
  maneuver: '机动',
  assault: '攻击',
  support: '辅助',
  finisher: '终结',
};

export const SKILL_CATEGORY_TAB_ORDER: SkillCategory[] = [
  'maneuver', 'assault', 'support', 'finisher',
];

export function getSkillCategory(skill: Skill): SkillCategory {
  if (skill.finisher) return 'finisher';
  const c = skill.category;
  if (c === 'maneuver' || c === 'assault' || c === 'support') return c;
  return 'assault';
}

export function isFinisherSkill(skill: Skill): boolean {
  return Boolean(skill.finisher);
}
```

后端新增技能只需在 `skill_definition_config.php` 配置 `category` 字段，前端自动正确分类，**零双重同步**。

### 3.3 `PreloadArea.vue` 适配

**新增派生集合**（避免每个调用点重复 find）：

```typescript
/** act_id → Skill 映射（从已加载技能表派生） */
const skillByActId = computed<Map<string, Skill>>(() => {
  const map = new Map<string, Skill>();
  for (const s of skills.value) map.set(s.act_id, s);
  return map;
});

/** 终结技 act_id 集合（从 Skill.finisher 字段派生） */
const finisherActIds = computed<Set<string>>(() => {
  const set = new Set<string>();
  for (const s of skills.value) {
    if (s.finisher) set.add(s.act_id);
  }
  return set;
});

/** 按 act_id 判定终结性（用于 QueueItem/PendingItem 等只有 act_id 的场景） */
function isFinisherAct(actId: string): boolean {
  return finisherActIds.value.has(actId);
}
```

**调用点替换**（6 处）：
- `isFinisherSkill(item.act_id)` → `isFinisherAct(item.act_id)`
- `isFinisherSkill(pending.act_id)` → `isFinisherAct(pending.act_id)`
- `isFinisherSkill(actId)` → `isFinisherAct(actId)`
- `isFinisherSkill(q.act_id)` → `isFinisherAct(q.act_id)`
- `isFinisherSkill(skill.act_id)` → `Boolean(skill.finisher)` 或 `isFinisherSkill(skill)`（传 Skill 对象）

**`getSkillCategory` 调用点**：
- 模板中 `getSkillCategory(skill.act_id)` → `getSkillCategory(skill)`（传 Skill 对象）
- `queueWithCost` 中 `getSkillCategory(item.act_id)` → 需先 `skillByActId.value.get(item.act_id)` 取 Skill 对象
- `trackItems` 中 `getSkillCategory(pending.act_id)` → 同上

**`queueWithCost` 优化**（缓存 Skill 对象，避免重复 find）：

```typescript
const queueWithCost = computed(() =>
  queue.value.map((item, index) => {
    const skill = skillByActId.value.get(item.act_id);
    const plannedLoc = getPlannedActorPls(queue.value.slice(0, index));
    return {
      ...item,
      apCost: estimateActionCostFrom(item, plannedLoc),
      isFinisher: isFinisherAct(item.act_id),
      category: skill ? getSkillCategory(skill) : 'assault',
      order: index + 1,
    };
  })
);
```

### 3.3 终结技唯一性校验

**`addToQueue` 入口校验**：

```typescript
function addToQueue(actId: string, target: TargetIntent): void {
  const isFinisher = isFinisherAct(actId);

  // 终结技唯一性：一场战斗只能有一个终结技
  if (isFinisher && queue.value.some(q => isFinisherAct(q.act_id))) {
    useToastStore().showToast('一场战斗只能有一个终结技', 'warning', 3000);
    return;
  }

  if (isFinisher) {
    queue.value.push({ id: ++queueIdSeed, act_id: actId, target, status: 'draft' });
  } else {
    const finisherIdx = queue.value.findIndex((item) => isFinisherAct(item.act_id));
    if (finisherIdx >= 0) {
      queue.value.splice(finisherIdx, 0, { id: ++queueIdSeed, act_id: actId, target, status: 'draft' });
    } else {
      queue.value.push({ id: ++queueIdSeed, act_id: actId, target, status: 'draft' });
    }
  }
}
```

**`onSkillClick` 提前阻止**（UX 优化，避免进入瞄准模式后才失败）：

在 `onSkillClick` 中，若是终结技且队列已有终结技，直接 toast 并 return，不进入瞄准/添加流程。

### 3.4 拖拽约束保持

现有拖拽约束逻辑（`toQueue` 不能超过 `finisherQueueIdx`）保持不变，仅将 `isFinisherSkill` 调用替换为 `isFinisherAct`。

## 四、边界案例

### 4.1 技能表未加载

`skillByActId` 和 `finisherActIds` 为空，`isFinisherAct` 返回 `false`。
- 影响：队列中的终结技约束暂时失效
- 兜底：`fetchSkillList` 在 `initPreloadArea` 中是 `await` 的，技能表加载完成前用户无法点击技能
- 结论：可接受

### 4.2 后端新增终结技

后端在 `combat_skill_config.php` 新增技能并标记 `finisher => true`，前端自动跟随，无需改 `skill-category.ts`。

### 4.3 后端取消某技能的终结性

后端将 `escape` 的 `finisher` 改为 `false`，前端自动跟随，`escape` 归入 `maneuver` 标签页。

### 4.4 重新瞄准时的唯一性

重新瞄准（`onReAim`）是把已有终结技从队列中临时移除进入 pending 态，再插回原位。此时队列中暂时没有终结技，不会触发唯一性校验。这是正确的——用户在修改目标，不是新增。

### 4.5 终结技标签页筛选

`filteredSkills` 中 `getSkillCategory(s) === activeCategory` 会自动把 `finisher` 为真的技能归入 `'finisher'` 标签页。`escape` 和 `execute` 都会出现在"终结"标签页下。

## 五、对原设计案的修订

原设计案 v4 中涉及终结技判定的章节，统一修订为"以后端 `Skill.finisher` 字段为唯一权威"：

- §3.2 标签页：`finisher` 分类由 `skill.finisher` 字段驱动，不硬编码
- §6.x 相关 computed：`isFinisher` 派生自 `skill.finisher`
- §7.1.x 终结技约束：唯一性校验在 `addToQueue` 入口前置

## 六、升降格分析

### 6.1 升格为基准框架

**"终结性字段驱动"** 应升格为基准框架：

> 任何具有"时序约束"语义的技能标记（如终结性、优先级、唯一性），前端必须以后端下发字段为唯一权威，不得维护独立的硬编码判定表。后端配置变更新增/移除标记时，前端自动跟随。

收录位置：`Dian.md` 模块 L（Vue 组件）或 模块 K（Pinia 状态管理层）。

### 6.2 不降格为特例

`escape` 被错误归类不是"escape 的特例补丁"，而是"前端分类体系与后端字段脱节"的框架问题。修正的是分类体系的**数据源**，不是 escape 的分类条目。

## 八、后续延伸（v5 同期实现的 UX 改进）

本补丁聚焦于"字段驱动"框架基准修正。在同一实现周期内，还完成了两项相关的 UX 改进（详见主设计案 v5 §5.2 与 §3.2/§4.2.2）：

1. **拖拽间隙指示线**：替代 v4 的"高亮目标项"视觉，改为根据光标 Y 坐标计算插入点，在两项之间渲染 2px 白色脉冲横线。`dropTargetIndex` 表示插入位置而非目标项索引，消除"高亮项本身"与"插入到它前面"的视觉语义错位。
2. **终结技耗尽视觉反馈**：`hasFinisherInQueue` computed 驱动 `is-finisher-exhausted` CSS 类（opacity 0.35 + grayscale 0.5），耗尽态下终结技按钮黯淡显示。按钮不 disable，点击触发 toast 解释——保留可点击性以解释为何不可用，是更友好的 UX。

两项改进均以本补丁建立的字段驱动派生集合（`finisherActIds`、`hasFinisherInQueue`）为数据源，是字段驱动框架的自然延伸而非独立功能。
