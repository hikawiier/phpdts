## 一、设计目标

围绕 8 个核心问题做整体重构，而非逐项打补丁：

| 问题编号 | 现状 | 本设计案归因 |
|---------|------|------------|
| B1 | 技能列表无分类平铺 | 信息架构缺层级，技能库缺分类基准 |
| B3 | 进入瞄准后无 breadcrumb | 瞄准是"半成品动作"的中间态，未被建模为队列项状态 |
| B4 | 队列项无法重新瞄准，只能删除重加 | 装填轨道的项缺"重新进入半成品态"的能力 |
| B5+ | 只有"清空全部"和"删除某项" | 队列缺原子操作层级（撤销末项、删除指定、修改目标、调整顺序） |
| C2 | AP 进度条无分段刻度 | "进度条"语言本身错误，AP 是离散预算，不是连续血量 |
| D2 | 队列项无序号 | 装填是时序计划，但视觉上时序不可见 |
| D3 | 队列项无 finisher 标记 | 时序约束（终结技必须在末尾）不可见 |
| D4 | 队列项无拖拽重排 | 时序计划应可调整，但调整能力完全缺失 |
| D5 | 队列头无总 AP 徽标 | 总成本需心算，缺聚合信息 |

**重构基线**：把"装填队列"从"已选技能列表"重新定义为"时序动作轨道"。这一概念转换后，B1/B3/B4/D2/D3/D4/D5 都是这一概念的必然视觉/交互要求，B5+ 是轨道操作的原子能力，C2 是配套预算显示的同步重设计。

## 二、概念提炼

### 2.1 时序轨道（替代"已选列表"）

**问题本质**：当前 `queue: QueueItem[]` 数据上是有序数组，但 UI 只把它渲染成"已选技能的纵向列表"，时序信息被抹平。

**新基准**：装填队列是玩家规划的**本回合动作时序**，按顺序入队 → 按顺序执行。所有视觉/交互都围绕"时序可见、可调"展开：

- 序号必须显式可见（D2）
- 时序约束（finisher 必须末尾、CD 技能只能出现一次）必须可见（D3）
- 时序必须可调整（D4 拖拽）
- 总成本必须聚合显示（D5）

**概念分级**：模块 → 基准框架（装填轨道的时序语义）

### 2.2 半成品动作（替代"独立瞄准模式"）

**问题本质**：当前进入瞄准模式后，PreloadArea 没有任何视觉反馈表明"正在为某技能选目标"。瞄准似乎是一个独立"模式"，而非队列项的中间态。

**现有协议约束**（v1 未察觉，v2 修正）：实际代码 [PreloadArea.vue:285-293](file:///d:/wamp64/www/phpdts/vex-vue/src/components/battle/PreloadArea.vue#L285-L293) `onSkillClick` 中，`aimType=tile/enemy` 时**不**立即入队，而是直接 `enterAimMode`。`enterAimMode` [PreloadArea.vue:319-334](file:///d:/wamp64/www/phpdts/vex-vue/src/components/battle/PreloadArea.vue#L319-L334) 把当前 `queue.value` 作为 `prefixActions` 传给 `aimTargetingStore.enter`，后端基于此前缀做射程推算。目标选定后才在 [onTargetSelect:378](file:///d:/wamp64/www/phpdts/vex-vue/src/components/battle/PreloadArea.vue#L378) 调用 `addToQueue` 入队。

若强行让 pending 项入队，`prefixActions` 会包含一个 target 为 `{type:'pending'}` 的无效项，后端射程推算会从空目标出发，得到错误结果。

**v2 新基准**：半成品态**不修改 `queue`**，而是在 PreloadArea 内部维护一个独立的 `pendingItem: Ref<PendingItem | null>`。`PendingItem` 是虚拟显示项，参与轨道渲染但不参与 `prefixActions`。

- **入队流程**（aimType=tile/enemy）：
  1. 用户点击技能 → 创建 `pendingItem = { act_id, target: { type: 'pending' } }`
  2. 轨道顶部渲染该虚拟项（序号 = queue.length + 1，半成品态样式）
  3. `enterAimMode` 的 `prefixActions` 仅传 `queue.value`，不含 pendingItem
  4. `onTargetSelect` 时：`addToQueue(act_id, selectedTarget)` → `pendingItem = null`
  5. 用户点击 Breadcrumb 的 `[取消]` 按钮：`pendingItem = null`，exitAimMode

- **重新瞄准流程**（B4）：
  1. 用户点击已入队项的目标 chip
  2. 该项从 `queue` 中**临时移除**，存入 `pendingItem`，原 target 暂存 `pendingItem._prevTarget`，原位置暂存 `pendingItem._prevIndex`
  3. `enterAimMode` 的 `prefixActions` 传**移除该项后的** `queue.value`（语义正确：射程推算假设此前项已完成）
  4. `onTargetSelect`：把新 target 通过 `splice(_prevIndex, 0, ...)` 回插原位置（保留原 id，不调用 `addToQueue`，详见 §5.3 步骤 5 与 §7.3 决断）
  5. 用户点击 Breadcrumb 的 `[取消]` 按钮：把 `pendingItem._prevTarget` 通过 `splice(_prevIndex, 0, ...)` 回插原位置（同上，保留原 id）

**对 B3 的解决**：`pendingItem` 是渲染层 sticky 显示的来源。Breadcrumb 即该项的视觉表现。

**对 B4 的解决**：任意已入队项的目标 chip 都可点击 → 项临时移入 `pendingItem` → 重新瞄准 → 替换。无需删除重加。

**协议扩展需求**：无需修改 `aimTargetingStore.enter` 的签名。重新瞄准时 PreloadArea 先把该项从 `queue` 中移除，再传**移除后的** `queue.value` 作为 `prefixActions`，语义已正确（射程推算假设此前项已完成）。无需引入 `excludeItemId` 参数—— [aim-targeting.ts:30-34](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/aim-targeting.ts#L30-L34) 的 `AimTargetingSession` 接口也不存在该字段。

**概念分级**：模块 → 基准框架（队列项状态机：草稿/半成品/锁定/已提交）

### 2.3 AP 预算槽（替代"AP 进度条"）

**问题本质**：当前用连续 progress bar + 红色扣除段表达 AP。但 AP 本质是离散预算——N 个 AP 槽，每回合重置，队列锁定 M 个，剩余 N-M 可用。progress bar 语言把离散量当连续量处理，C2 缺分段刻度只是这一概念错位的症状。

**新基准**：AP 显示为 **N 个独立方块**（maxAp 个，超载时额外渲染超出槽），每方块四态：

- **可用**：虚线空槽（灰阶 + 1px 虚线边）
- **队列锁定**：斜线纹理（`repeating-linear-gradient(45deg)` 灰阶）+ 占据该槽的队列项序号（v5 修正：被同一动作占据的多个槽显示**同一个**序号，如动作1消耗2AP则前两个槽都显示"1"，让用户静态下即可看出槽位归属，不依赖 hover 联动）
- **溢出超载**：若 queueCost > playerAp，超出的槽位显示为带 `╳` 标记的禁止槽
- **本回合不可用**（v4 新增）：若 playerAp < playerMaxAp（AP 被减益），playerAp 到 playerMaxAp 之间未被队列锁定的槽位显示为点线 + 低透明度，表示"槽位存在但本回合未充能"

**对 C2 的解决**：N 个独立方块本身就是天然的"分段刻度"——5 个槽就是 5 等分，3 个槽就是 3 等分，无需额外 `::after` 分段。

**视觉联动**（关键）：hover 队列项时，对应的 AP 槽高亮，让"动作 → 消耗"关系一眼可见。

**概念分级**：模块 → 基准框架（预算槽四态编码）

### 2.4 原子队列控制（替代"清空全部"）

**问题本质**：当前只有 `clearQueue()` 和 `removeFromQueue(i)` 两个粗糙操作。但玩家在规划时序时，需要：

- 撤销最后一项（B5+ 核心）
- 删除任意指定项
- 修改任意项的目标（B4）
- 调整任意项的顺序（D4）

**新基准**：装填轨道的每项都是可独立操作的原子单元。操作层级：

| 操作 | 触发方式 | 作用对象 |
|------|---------|---------|
| 撤销末项 | 队列末项的 `[x]` 按钮 | 最后一项 |
| 删除指定项 | 项的 `[x]` 按钮 | 该项 |
| 修改目标 | 点击项的目标 chip | 该项进入半成品态 |
| 调整顺序 | 拖拽项的手柄 | 非 finisher 项 |
| 清空全部 | `[清空]` 按钮（二次确认） | 全部 |

**安全约定**：清空全部需要二次确认（按钮变 `[确认清空?]` 高亮态，3 秒窗口内再次点击执行，详见 §5.1），避免误操作丢失整轮规划。

**概念分级**：模块 → 设计意图（细粒度操作 + 二次确认安全网）

## 三、信息架构

### 3.1 PreloadArea 分区重构

**v3 布局调换**：与探索页面"信息在上、操作在下"的操作习惯同步——装填轨道（已规划信息）在上方，技能库（选择操作源）在下方。原 v2 布局"技能库在上、装填轨道在下"已调换。

```
│  ...                               │
└─────────────────────────────────────┘
```

**分区语义**：
- **信息区（上方）**：Breadcrumb + 装填轨道 + AP 槽。展示"当前规划状态"——已选动作序列、预算消耗、半成品提示。
- **操作区（下方）**：技能库。展示"可选操作源"——按分类分组的技能列表，供用户选择添加到轨道。
- **[执行][清空] 紧邻装填轨道底部**：这两个按钮是"对装填轨道的确认/清空操作"，逻辑上属于信息区而非操作区。规划完轨道后立即点 [执行]，无需滚到最底部。

**滚动行为**：
- 装填轨道通常项数有限（一回合动作数 ≤ maxAp/最小cost），不单独滚动。
- 技能库项数可能较多（9+ 技能 + 分类标题），作为 `flex-1` 区域占据剩余高度并独立滚动。
- 整个 PreloadArea 由 [BattleActionBar.vue:20](file:///d:/wamp64/www/phpdts/vex-vue/src/components/battle/BattleActionBar.vue#L20) 的父容器 `flex-1 overflow-y-auto min-h-0` 托管滚动。

### 3.2 技能库标签页筛选（B1）

**v3 改动**：v2 的"分组渲染"（按分类切片成多个分组块）改为**标签页筛选**（顶部标签栏 + 单一扁平列表）。理由：分组渲染只是"视觉章节标题"，无筛选能力，技能数增加后仍需滚动找；标签页提供主动筛选，且与探索页面"操作区紧凑"的语义更契合。

**标签页结构**：

```
[全部] 机动  攻击  辅助  终结
──
[技能1] AP:.. R:..  [分类小标签]
[技能2] ...
```

- **标签集合**：`全部 | maneuver | assault | support | finisher`，共 5 个
- **默认选中**：`全部`——首次进入保持全局视野，避免默认筛选造成"技能少了"的错觉
- **激活态样式**：先用简单下划线激活态（见 §4.2），后续调整为方案 C 硬投影
- **非激活态**：灰阶文字，hover 显白

**筛选实现**（v5 字段驱动）：

```ts
const activeCategory = ref<'all' | SkillCategory>('all');

const filteredSkills = computed(() => {
  if (activeCategory.value === 'all') return visibleSkills.value;
  return visibleSkills.value.filter(
    s => getSkillCategory(s) === activeCategory.value
  );
});
```

**分类数据源**（v5 重构——删除前端硬编码映射表）：

v4 及之前在 `skill-templates.ts` 维护 `SKILL_CATEGORY: Record<act_id, SkillCategory>` 硬编码映射表，后端新增技能需同步修改前端映射表（双重同步）。v5 删除该映射表，分类完全由后端字段驱动：

- **时序分类（终结性）**：`Skill.finisher` 字段（后端 `combat_skill_config.php` 的 `finisher => true`），优先级最高
- **功能分类**：`Skill.category` 字段（后端 `skill_definition_config.php` 的 `category`），值域与前端 1:1 对齐

后端 `category` 值域从粗粒度 `utility`/`attack`/`passive` 细化为 `maneuver`/`assault`/`support`/`passive`：

| 技能 | 旧 category（v4 前） | 新 category（v5） | finisher |
|------|---------------------|-------------------|----------|
| move | utility | maneuver | false |
| escape | utility | maneuver | true |
| idle | utility | maneuver | false |
| heal | utility | support | false |
| unarmed_strike | attack | assault | false |
| throw | attack | assault | false |
| whirlwind | attack | assault | false |
| execute | attack | assault | true |
| vampiric_bite | attack | assault | false |
| grenade | attack | assault | false |
| flustered | passive | passive（不变） | false |

`getSkillCategory(skill)` 实现见 §6.1，优先检查 `skill.finisher`，为真返回 `'finisher'`（覆盖功能分类），否则返回 `skill.category`。

**未注册 act_id 的 fallback**：`skill.category` 值不在已知值域时，默认归入 `assault`，避免新技能无家可归。**未配置 `category` 字段**时，后端 API 序列化层（`skill.main.php`）兜底返回 `'assault'`。

**终结技耗尽视觉反馈**（v5 新增）：当队列中已存在终结技时（`hasFinisherInQueue` computed 为 true），技能库中所有终结技按钮应用 `is-finisher-exhausted` CSS 类（opacity 0.35 + grayscale 0.5），表示"本场战斗终结技名额已用尽"。按钮不 disable——保留可点击性，点击时触发 toast 解释"一场战斗只能有一个终结技"，让用户理解为何不可用而非单纯禁用。边界：重新瞄准时终结技被临时移出队列进入半成品态，`hasFinisherInQueue` 短暂为 false，其他终结技按钮恢复——这是正确行为（用户在修改目标而非新增）。

**标签顺序**：`全部 → maneuver → assault → support → finisher`。理由：`全部` 在最左作为默认入口；其余按"位置/状态切换 → 主动攻击 → 辅助 → 终结"的认知流程排列；终结技放末尾视觉上呼应"必须最后执行"。

**项尾小标签**：每个技能项右侧显示分类小标签（`机动` / `攻击` / `辅助` / `终结`），灰阶小字。作用：在 `全部` 标签下也能一眼识别分类；在筛选标签下作为视觉冗余确认。finisher 项的项尾小标签可与 `[F]` 标记合并（避免重复）。

**标签栏滚动**：5 个标签在战斗面板宽度内可容纳（每个约 30-40px）。若未来标签数增加，标签栏自身可横向滚动，本设计案不实现。

### 3.4 Breadcrumb 区（B3）

进入瞄准模式（即 `pendingItem !== null` 时），PreloadArea 顶部 sticky 显示：

```

└─────────────────────────────────────────┘
```

样式：方案 C 标题 + 左侧 2px 白色脉冲色条（≤3Hz）。背景半透明遮罩，确保 PreloadArea 内容超出视口滚动时始终可见。

**v3 布局调整后的 sticky 语义**：装填轨道在 Breadcrumb 下方、信息区顶部。Breadcrumb sticky 在 PreloadArea 滚动容器顶部，无论用户滚动浏览技能库还是装填轨道，半成品态提示始终可见。这是 v3 布局的核心收益之一——v2 布局下 Breadcrumb 在技能库上方，滚动技能库时 Breadcrumb 会跟随技能库一起上滚消失；v3 布局下 Breadcrumb 在最顶部，sticky 行为更自然。

**v2 父容器约束补充**（v1 遗漏）：[BattleActionBar.vue:20](file:///d:/wamp64/www/phpdts/vex-vue/src/components/battle/BattleActionBar.vue#L20) 的父容器 `<div class="flex-1 overflow-y-auto min-h-0">` 是滚动容器。`position: sticky; top: 0` 在 `overflow-y-auto` 容器内表现与全屏 sticky 不同——它会粘附在该滚动容器顶部，而非视口顶部。这正是本设计案需要的行为（Breadcrumb 粘附在面板顶部）。但需确保父容器无 `overflow: hidden` 祖先，否则 sticky 失效。

**`[取消]` 按钮**：点击触发 §5.3 的取消流程（恢复原 target 或丢弃 pendingItem）。**v2 修正**：v1 标注为 `[ESC 取消]` 暗示快捷键，v2 改为 `[取消]` 按钮形式，符合本设计案不引入快捷键的策略。

### 5.1 鼠标交互

**技能库项**：
- 点击 → 进入瞄准（aimType=tile/enemy）或直接入队（aimType=none/self）
- hover → 显示边框提亮 + 左色条显白（无射程预览，远期扩展）
- **终结技耗尽态视觉**（v5 新增）：当 `hasFinisherInQueue` 为 true 时，所有终结技按钮应用 `is-finisher-exhausted` 类（opacity 0.35 + grayscale 0.5），表示名额已用尽。按钮不 disable，点击仍触发 toast 解释"一场战斗只能有一个终结技"。详见 §3.2 终结技耗尽视觉反馈。
- **pendingItem 激活时禁用**（v4 补充）：当 `pendingItem !== null`（重新瞄准中）时，技能库整体 `pointer-events: none` + `opacity: 0.4`，禁止交互。pending 态是模态的——必须先完成当前瞄准（选定目标）或取消（点击 `[取消]`），才能选择新技能。理由：允许并发 pending 会破坏 `_prevIndex` 位置语义，且同时只能有一个半成品动作。

**轨道项**：

- 点击 `[x]` → 删除该项
- 拖拽手柄 → 调整顺序（finisher 项不可拖，D4，详见 §5.2）
- **pendingItem 激活时禁用**（v4 补充）：删除、拖拽、其他项的目标 chip 点击均禁用。理由同技能库——pending 态模态，避免 `_prevIndex` 失效。

**AP 槽**：
- hover 队列项 → 对应 AP 槽高亮（联动，事件委托实现见 §5.4）
- 点击 AP 槽 → 无作用（视觉元素，不可交互）

**清空全部的二次确认**（替代 v1 的 ESC 连按）：
1. 点击 `[清空]` 按钮 → 按钮变为 `[确认清空?]` 高亮态（方案 C 边框 + 脉冲）
2. 3 秒内再次点击 → 执行清空
3. 3 秒外或点击其他区域 → 取消确认，按钮复原

### 5.2 拖拽重排规则（D4）

**可拖拽项**：非 finisher 的轨道项。

**可放置位置**：
- 任意非末尾位置（若队列含 finisher，finisher 之前的任意位置）
- 末尾位置（若队列不含 finisher）

**不可放置**：
- finisher 项之后（finisher 必须末尾约束）

**v5 间隙指示线语义**（替代 v4 的"高亮目标项"）：

v4 的拖拽视觉是 `is-drop-target` 类加在目标项上（虚线高亮整个目标项），但实际行为是把拖动项插入到目标项的位置，目标项会后移——视觉与语义不符（高亮的是目标项本身，但动作是"插入到它前面"，目标项的序号会变）。

v5 改为**间隙指示线**：拖拽时根据光标 Y 坐标相对当前悬停项中点的位置，计算插入点（0~N 的整数），在两项之间渲染一条 2px 白色脉冲横线作为指示。

- `dropTargetIndex` 表示**插入位置**（0~N），而非目标项索引
- 光标在项的上半区 → 插入到该项之前（`insertion = trackIndex`）
- 光标在项的下半区 → 插入到该项之后（`insertion = trackIndex + 1`）
- 若队列含 finisher，且计算出的 `insertion > finisherTrackIdx`，钳制为 `finisherTrackIdx`（不可拖到 finisher 之后）
- 若 `insertion === fromTrack` 或 `insertion === fromTrack + 1`（拖回原位置），清空 `dropTargetIndex`（不显示指示线，避免无意义闪烁）

**渲染实现**：使用 `<template v-for>` 包裹每个轨道项，在每个项**之前**条件渲染 `<div class="drop-indicator">`（当 `dropTargetIndex === trackIndex`），并在列表末尾条件渲染一条（当 `dropTargetIndex === trackItems.length`）。指示线 CSS 见 §4（2px 白色 + 1Hz 脉冲）。

**实现**：HTML5 Drag and Drop API（`draggable` + `dragstart`/`dragover`/`drop`）。拖拽中源项 `is-dragging` 半透明，`dropTargetIndex` 驱动间隙指示线渲染。

**drop 时的位置转换**：`dropTargetIndex` 是轨道索引（含 pending 虚拟项的渲染索引），需转换为 `queue.value` 的索引。若 `fromIdx < toQueue`，则 `toQueue -= 1`（移除源项后后续项前移）。若队列含 finisher 且 `toQueue > finisherQueueIdx`，钳制为 `finisherQueueIdx`（双重保险，与 dragover 钳制一致）。

**reduced-motion 降级**：拖拽本身是用户主动操作，不受 reduced-motion 影响。但间隙指示线的脉冲动画在 reduced-motion 下降级为静态 0.6 透明度（见 §4 `prefers-reduced-motion` 块）。

**移动端 fallback**（远期扩展）：mobile 端用"长按 → 弹出操作菜单（上移/下移/删除/重瞄准）"替代拖拽，本设计案不实现。

### 5.3 重新瞄准流程（B4）

依据 §2.2 的"虚拟 pending 项"方案：

1. 用户点击某已入队项的目标 chip
2. 该项从 `queue` 临时移除，存入 `pendingItem`（含 `_prevTarget`）
3. `enterAimMode` 调用，`prefixActions` 传**移除该项后的** `queue.value`
4. Breadcrumb 渲染 `pendingItem`（"瞄准中：[技能名] · R:X · [取消]"）
5. 用户选定新目标：
   - **回原位置**（§7.3 已决断）：与取消恢复同路径，使用 `queue.value.splice(pendingItem._prevIndex, 0, { id: pendingItem.id, act_id: pendingItem.act_id, target: newTarget, status: 'draft' })` 直接插回原位，保留原 id
   - **不调用 `addToQueue`**——同 §6 步骤的理由（避免新 id 与 finisher 插入逻辑误触发）
   - `pendingItem = null`，exitAimMode
6. 用户点击 `[取消]` 按钮（**v4 修正**：删除"点击 Breadcrumb 外区域取消"——瞄准模式下用户需点击地图选择目标，地图也是"Breadcrumb 外区域"，会误触发取消。取消仅通过 `[取消]` 按钮触发）：
   - **保留原 id 与原位置**：使用 `queue.value.splice(pendingItem._prevIndex, 0, { id: pendingItem.id, act_id: pendingItem.act_id, target: pendingItem._prevTarget, status: 'draft' })` 直接插回原位
   - **不调用 `addToQueue`**——`addToQueue` 会通过 `queueIdSeed++` 生成新 id，破坏 id 连续性，且会触发"finisher 插入到末尾前"等特殊逻辑，与"恢复原位置"语义冲突
   - `pendingItem = null`，exitAimMode

**决断（§7.3）**：重新入队回原位置以保留用户的时序规划。`pendingItem._prevIndex` 暂存原位置，使用 `splice(_prevIndex, 0, ...)` 回插，保留原 id。move 类技能重算由 `queueWithCost` computed 自动处理（原位置前的项未变化，plannedLoc 不变，重算结果一致）。

**数据保护**：进入半成品态前，原 target 暂存在 `pendingItem._prevTarget`，取消时恢复。

**目标已死亡/离开的边界**：`findSelectableCombatTarget` 返回 null 时，保持 `pendingItem` 半成品态 + toast 提示"目标不可选，请重新选择"。

### 5.5 快速瞄准（v6 新增）

**痛点**：连续对同一敌人放多个技能（如攻击A → 投掷A → 处决A），每次都要进入瞄准模式、在地图上找到并点击同一敌人。重复操作量大。

**核心规则**：技能库中 `aimType === 'pid'` 的技能，当队列中已存在 pid 类型目标时，项右侧显示 `→[目标名]` 快捷标签。

- **点击快捷标签**：校验射程 + 目标有效性 → 直接入队（跳过瞄准模式）
- **点击技能本身**：正常进入瞄准模式（默认行为不变）
- `@click.stop` 阻止冒泡到技能项 click

**`canQuickAim` 提前过滤原则**：所有在 `onQuickAimClick` 中会导致 toast 失败的校验（CD 重复、终结技耗尽、不可用、射程不足），都应在 `canQuickAim` 中提前过滤——快捷标签的职责是"快速添加"，不能添加就不应出现。`onQuickAimClick` 中的校验保留作为二次防御（防止 `canQuickAim` 到点击期间的竞态）。

**数据派生**：

- `lastPidTarget` computed：队列中最后一个 pid 类型目标。取"最后一个"而非"最频繁"——最近决策最能代表当前意图。如「攻击A → 攻击B」后，快捷标签指向 B；用户若想对 A 快速瞄准，需手动瞄准一次 A，之后快捷标签切换到 A。
- `quickAimPlannedLoc` computed：`getPlannedActorPls()` 无参调用（前缀 = 完整 queue，因为快速瞄准追加到末尾），所有技能共享同一推算位置。

**视觉语言**：快捷标签用 `→` 箭头前缀，与装填轨道项的目标 chip（`→ 位置 7` / `→ 兔子`）视觉一致——"→" 表示"指向某目标"，建立跨区域的视觉关联。耗尽态下技能行不显示快捷标签（`canQuickAim` 已返回 false + CSS 兜底）。

**完整设计**：详见独立设计案 [快速瞄准与战斗标题清理-设计案-2026-07-14.md](快速瞄准与战斗标题清理-设计案-2026-07-14.md) §2，包含 §2.1 痛点目标、§2.2 交互设计、§2.3 数据派生、§2.4 射程与有效性校验、§2.5 UI 与样式、§2.6 边界案例（10 项）、§2.7 概念分级。

**概念分级**：模块级——PreloadArea 的交互增量，不改变装填轨道时序语义或 AP 预算模型。复用现有 `addToQueue` 入队路径、`findSelectableCombatTarget` 目标校验、`isEnemyInSkillRange` 射程校验、`getPlannedActorPls` 位置推算——所有基础设施已存在，只新增一条"跳过瞄准模式"的并行路径。

> - `getSkillCategory(skill: Skill)` — **v5**：优先检查 `skill.finisher`（为真返回 `'finisher'`），否则返回 `skill.category` 字段
> - `estimateActionCostFrom(item, plannedLoc)` — 通用成本估算；对 `move` 类分支调用现有 [estimateMoveActionCost](file:///d:/wamp64/www/phpdts/vex-vue/src/utils/combat-action-cost.ts#L10-L15)（其签名为 `(skill: Skill, distance: number | null)`），其他类按 `act_id` 返回基础或查表成本

```ts
const skillByActId = computed<Map<string, Skill>>(() => {
  const map = new Map<string, Skill>();
  for (const s of skills.value) map.set(s.act_id, s);
  return map;
});

const finisherActIds = computed<Set<string>>(() => {
  const set = new Set<string>();
  for (const s of skills.value) {
    if (s.finisher) set.add(s.act_id);
  }
  return set;
});

function isFinisherAct(actId: string): boolean {
  return finisherActIds.value.has(actId);
}

const hasFinisherInQueue = computed(() =>
  queue.value.some(q => isFinisherAct(q.act_id))
);
```

```ts
const queueWithCost = computed(() =>
  queue.value.map((item, index) => {
    const skill = skillByActId.value.get(item.act_id);
    const plannedLoc = getPlannedActorPls(queue.value.slice(0, index));
    return {
      ...item,
      apCost: estimateActionCostFrom(item, plannedLoc),
      isFinisher: isFinisherAct(item.act_id),
      category: skill ? getSkillCategory(skill) : 'assault',
      order: index + 1,
    };
  })
);

const queueCost = computed(() =>
  queueWithCost.value.reduce((sum, item) => sum + item.apCost, 0)
);

const isOverload = computed(() => queueCost.value > playerAp.value);
```

**move 重算的自动性**：因为 `queueWithCost` 是 computed，队列顺序变化（拖拽）会自动重算所有项的 `apCost`。无需手动调用 `recalcQueueCosts()`——v1 的手动调用是反 Vue 模式。

### 6.2 AP 槽派生

> **v4 重写**：v3 的循环逻辑有两个 bug——(a) 当 `queueCost > playerAp` 且 `playerAp == playerMaxAp` 时，循环只迭代 `playerMaxAp` 次，超载槽位不渲染；(b) 当 `playerAp < playerMaxAp`（AP 被减益）且 `queueCost <= playerAp` 时，`playerAp` 到 `playerMaxAp` 之间的槽位被错误标记为 `overload`，但实际是"本回合不可用"而非"队列超载"。v4 重写为四态模型，总槽位数改为 `max(playerMaxAp, queueCost)` 以容纳超载槽。
>
> **v5 序号语义修正**：v4 的 `lockedByOrder: i + 1` 用槽位索引赋值，导致锁定槽显示"第几槽"而非"被第几个动作占据"。v5 反转遍历逻辑——遍历队列项分配连续槽位，同一动作的多个槽标记同一 `order`，使序号真正表达归属关系。

```ts
interface ApSlotState {
  index: number;
  state: 'available' | 'locked' | 'overload' | 'depleted';
  lockedByOrder?: number;  // v5：占据该槽的队列项 order（同一动作的多个槽相同）
}

const apSlots = computed<ApSlotState[]>(() => {
  const slots: ApSlotState[] = [];
  const maxAp = playerMaxAp.value;
  const curAp = playerAp.value;
  const cost = queueCost.value;
  // 总槽位数：超载时需额外渲染超载槽，故取 max(maxAp, cost)
  const totalSlots = Math.max(maxAp, cost);

  // v5 第一阶段：遍历队列项，为每个项分配连续的 apCost 个槽位
  // 同一动作占据的多个槽都标记为该项的 order
  let slotIndex = 0;
  for (const item of queueWithCost.value) {
    for (let j = 0; j < item.apCost; j++) {
      if (slotIndex >= curAp) {
        // 超出当前 AP → 超载槽（╳，不显示序号）
        slots.push({ index: slotIndex, state: 'overload' });
      } else {
        // 队列锁定且在当前 AP 范围内 → 锁定槽（显示该项 order）
        slots.push({ index: slotIndex, state: 'locked', lockedByOrder: item.order });
      }
      slotIndex++;
    }
  }
  // 注：第一阶段结束后 slotIndex === cost（sum of apCost）

  // v5 第二阶段：剩余槽位按 available / depleted 填充
  for (let i = slotIndex; i < totalSlots; i++) {
    if (i < curAp) {
      // 在当前 AP 范围内但未被队列锁定 → 可用槽（虚线）
      slots.push({ index: i, state: 'available' });
    } else if (i < maxAp) {
      // 超出当前 AP 但在最大 AP 范围内 → 本回合不可用（减益/消耗）
      slots.push({ index: i, state: 'depleted' });
    }
    // i >= maxAp 且 i >= cost：受 totalSlots 约束不会出现
  }
  return slots;
});
```

**v5 算法正确性验证**（队列「动作1(2AP)→动作2(1AP)→动作3(3AP)」，curAp=5，maxAp=5，cost=6，totalSlots=6）：

| 槽位 | 阶段 | 来源 | 状态 | lockedByOrder | 显示 |
|------|------|------|------|---------------|------|
| 0 | 1 | 动作1 j=0 | locked | 1 | 1 |
| 1 | 1 | 动作1 j=1 | locked | 1 | 1 |
| 2 | 1 | 动作2 j=0 | locked | 2 | 2 |
| 3 | 1 | 动作3 j=0 | locked | 3 | 3 |
| 4 | 1 | 动作3 j=1 | locked | 3 | 3 |
| 5 | 1 | 动作3 j=2 | overload（slotIndex≥curAp） | — | ╳ |

结果序列「1 1 2 3 3 ╳」——序号正确表达归属，超载槽显示 ╳。

**apCost 为 0 的技能**：不分配槽位（内层循环不执行），slotIndex 不前进。合理——0 AP 技能不消耗预算槽。

**四态语义对照**（v5 修正序号列）：

| 状态 | 条件 | 视觉 | 含义 |
|------|------|------|------|
| `locked` | 被某队列项占据且在当前 AP 范围内 | 斜线纹理 + 占据项序号 | 队列已锁定，AP 充足；同一动作的多个槽显示同一序号 |
| `overload` | 被某队列项占据但超出当前 AP | 双线边 + `╳` | 队列超出当前 AP，超载；不显示序号（位置已表达归属） |
| `available` | 未被队列占据且在当前 AP 范围内 | 虚线空槽 | 本回合可用，未被锁定 |
| `depleted` | 未被队列占据、超出当前 AP 但在最大 AP 范围内 | 点线 + 低透明度 | 本回合不可用（AP 被减益/消耗） |

**与现有 `playerAp` / `playerMaxAp` 语义对齐**：`playerAp` 是本回合可用 AP（可能因 debuff 小于 maxAp），`playerMaxAp` 是理论最大值。`depleted` 态表示"槽位存在但本回合未充能"。

### 6.3 submitted 状态与 isPlayerTurn 钩子（v2 补充）

**v1 遗漏**：未定义 submitted 状态的进入/退出时机。

**v2 定义**：通过 watch `battleStore.isPlayerTurn` 实现：

```ts
watch(() => battleStore.isPlayerTurn, (isMyTurn, wasMyTurn) => {
  if (wasMyTurn && !isMyTurn) {
    // 玩家回合结束 → 锁定队列
    // v4 补充：若 pendingItem 仍激活（用户未完成瞄准就回合结束），先执行取消流程
    if (pendingItem.value) {
      if (pendingItem.value._prevTarget !== undefined && pendingItem.value._prevIndex !== undefined) {
        // 重新瞄准中的 pending：恢复原 target 到原位置
        queue.value.splice(pendingItem.value._prevIndex, 0, {
          id: pendingItem.value.id,
          act_id: pendingItem.value.act_id,
          target: pendingItem.value._prevTarget,
          status: 'submitted',
        });
      }
      // 新建未完成的 pending（无 _prevTarget）：直接丢弃
      pendingItem.value = null;
      exitAimMode();
    }
    queue.value.forEach(item => { item.status = 'submitted'; });
  } else if (!wasMyTurn && isMyTurn) {
    // 新回合开始 → 清空队列，重新可编辑
    queue.value = [];
    pendingItem.value = null;
  }
});
```

**进入 submitted 的时机**：执行命令成功提交后（`onExecute` 的 await 返回后），所有 queue 项 status 置为 `submitted`。UI 锁定，禁止任何修改操作（拖拽、点击、删除按钮禁用）。

**退出 submitted 的时机**：
- 主路径：`isPlayerTurn` 从 true → false → true（新回合开始），自动清空
- 异常路径：战斗结束（`battleStore.isBattleOver`）或玩家死亡，PreloadArea 卸载

**对应的 `skill_list` 失效**：`onPreloadExecuted` 已在 [battle.ts:1055-1061](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle.ts#L1055-L1061) 调用 `dataManager.invalidate('player_info')` 等。但 `skill_list` 当前只在 `initPreloadArea` 时调用，新回合开始时若 AP/CD 变化需重新拉取。建议在 `isPlayerTurn` watch 中追加 `dataManager.invalidate('skill_list')`。

## 七、边界案例、待决策与已决断

### 7.1 边界案例

1. **move 技能拖拽导致后续 move 距离失效**：move 的 apCost 依赖从 plannedLoc 到目标的距离。`Math.max(baseCost, Math.ceil(distance / movePower))` 的下限保护见 [combat-action-cost.ts:10-14](file:///d:/wamp64/www/phpdts/vex-vue/src/utils/combat-action-cost.ts#L10-L14)。v2 通过 `queueWithCost` computed 自动重算，无需手动 `recalcQueueCosts()`。
   - **字段复用语义**（v1 遗漏）：`movePower` 实际取自 `getSkillBaseRange(skill)` 即 `skill.range.base`，move 类技能的 "range" 同时表示"射程"和"单位 AP 移动距离"。这是历史设计复用，非 bug，但需在开发文档中注明。
2. **重新瞄准时原目标已死亡/离开**：`findSelectableCombatTarget` 返回 null 时，保持 `pendingItem` 半成品态 + toast 提示。
3. **finisher 后插入新项**：当前 `addToQueue` [PreloadArea.vue:399-413](file:///d:/wamp64/www/phpdts/vex-vue/src/components/battle/PreloadArea.vue#L399-L413) 已实现"普通技插入到 finisher 之前"。**v4 措辞修正**：实现阶段在 PreloadArea 内部处理此约束；后续随 `useTemporalPlan` 抽离（见 §10.2 升格分级）升格为该 composable 的内置约束，不再是 PreloadArea 的特殊逻辑。
4. **超载 AP 提交**（v2 修正）：**不**通过 `executeBlock` 实现（[command-queue.ts](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/command-queue.ts) 的 5 层锁体系不含 AP 检查）。改为 PreloadArea 内部 UI 派生：
   ```ts
   const executeDisabled = computed(() =>
     executeBlock.value !== null || isOverload.value || pendingItem.value !== null
   );
   ```
   超载时 `[执行]` 按钮 disabled + tooltip "AP 不足，请减少装填"。
5. **pre-battle 模式 vs in-battle 模式**：两种模式的拖拽/重新瞄准行为一致，差异仅在执行命令不同（`battle.start` vs `battle.submit_turn`）。通过 `executeCommand` 配置注入。
6. **终结技唯一性与重新瞄准的交互**（v5 新增）：重新瞄准时终结技被临时移出队列进入半成品态，此时队列暂无终结技，`hasFinisherInQueue` 为 false，不会误触发唯一性校验，技能库中其他终结技按钮也不会显示耗尽态。这是正确行为——用户在修改目标而非新增。新目标选定后终结技回插原位，`hasFinisherInQueue` 恢复 true。
7. **技能表未加载时的终结性判定**（v5 新增）：技能表加载完成前 `finisherActIds` 集合为空，`isFinisherAct` 对所有 act_id 返回 false，所有项暂时被视为非终结技。由 `initPreloadArea` 中 `await fetchSkillList()` 保证技能表加载完成前用户无法点击技能，可接受。
8. **终结技耗尽态点击行为**（v5 新增）：耗尽态下终结技按钮不 disable，点击触发 toast"一场战斗只能有一个终结技"。不 disable 的理由：disabled 按钮无法触发 click 事件，用户无法得知"为何不可用"；保留可点击性让 toast 解释原因，是更友好的 UX。

### 7.2 待决策

1. **技能分类映射是否由后端返回**：**v5 已决断**——分类完全由后端字段驱动（`Skill.finisher` + `Skill.category`），前端不维护任何硬编码映射表。详见 §3.2 字段驱动与独立补丁 `技能终结性字段驱动-设计补丁-2026-07-12.md`。

### 7.3 已决断
