# 前端战斗导演与演员动画系统结构研判

> 目的：结合战斗播放提交屏障、移动动画、动态参战与清场顺序的实测经验，判断现有 Director / Playback / Actor 动画结构是否需要升级，并明确“小人动画是否区分战斗/非战斗”与“定位方式是否合理”的框架结论。

## 1. 结论摘要

1. Director / Planner / Runner 四层方向成立，不应推倒重来。
2. 当前 ActorExecutor、地图实体调度和玩家意图层对同一 actor 缺少统一所有权，属于框架问题，不是单个动画 bug。
3. 不建议按“战斗动画 / 非战斗动画”复制两套实现；应按动画控制域区分 `world projection`、`battle choreography`、`ambient pose`、`terminal lifecycle`。
4. 当前定位方式确实不够稳健：存在重复锚点算法、混用 grid-local 与 viewport 坐标、直接查询 DOM、把 GSAP transform 当实时位置等问题。
5. 推荐升级为 `SceneGeometry + ActorRuntime + PresentationLease`：统一坐标服务、分离位置与姿态 transform，并让战斗播放显式租用 actor 的表现控制权。

## 2. 当前结构

### 2.1 已经正确的部分

战斗播放主链已经形成：

`battlelog.v2 -> BattlePlayScriptV2 -> BattlePlaybackPlan -> Runner -> ActorExecutor`

职责边界总体正确：

- Director 聚合事实并推导动作语义。
- Planner 生成带等待策略的 PlaybackStep。
- Runner 顺序执行步骤。
- ActorExecutor 调用演员能力。

这套结构解决了过去组件事件 fire-and-forget、移动不等待、动作顺序分散的问题，应保留并继续收敛职责。

### 2.2 同一 actor 当前有三个控制入口

1. `useMapEntities`
   - watch `curLoc`、entities、ResizeObserver。
   - 负责位置同步、探索移动、首次入场、列表移除淡出。
2. `playerAvatarStore -> intentSeq -> useMapEntities`
   - 负责玩家 enter / fall / flee / battle-start / battle-end / HP 意图。
3. `BattlePlaybackRunner -> battle-actor-executor`
   - 直接调用同一个 ActorAnimation 的 move / attack / hit / fadeOut。

三条链最终都操作同一个 `.entity` DOM 和同一组 GSAP transform，但没有“当前谁拥有控制权”的协议。

## 3. 已确认的结构问题

### 3.1 动画域没有隔离

`actorAnimations.ts` 中 idle、move、jump、attack、hit、fall、fadeOut 都会调用 `gsap.killTweensOf(el)`。

同一 DOM 元素同时承载：

- 空间位置：x / y / xPercent / yPercent。
- 姿态：scale / rotation。
- 生命周期：alpha。
- idle 循环。

因此任一新动画都可能终止另一个域的动画。`isMoving` 只保护 move，attack、hit、fade、idle 没有统一 busy/lease/cancel 语义。

这是此前“后续动作杀掉移动 tween”的同类根因，不能靠继续增加 `isMoving` 特例解决。

### 3.2 地图投影与战斗编舞会争抢位置

战斗 move 播放结束后，actor 的 `isMoving` 立即恢复 false；在权威状态提交前，如果 ResizeObserver 或 entities watch 触发 `syncAllPositions()`，地图投影仍可能按旧 `pls` 把演员拉回旧位置。

现有全局 Playback Commit Barrier 延迟了 CharacterHub/map 状态提交，但没有为单 actor 建立表现控制权。它解决了提前消失，尚未从底层阻止地图投影覆盖战斗编舞。

### 3.3 清场存在双重退场所有权

战斗 Runner 在 `combatant_cleared` step 中调用 `actor.playFadeOut()`；随后状态提交从 `aliveList` 移除角色，`useMapEntities` 又会因 entities 列表移除调用一次 `playFadeOut()`。

当前实测可通过，是因为第一次已把 alpha 降为 0，第二次通常只是不可见地重复执行。但语义上仍有两个清场拥有者，未来加入尸体、逃跑轨迹、掉落物或可取消动画时会产生冲突。

### 3.4 超时只放行，不取消旧动画

Runner 的 `withTimeout()` 在超时后继续下一步，但没有取消旧 task。旧动画稍后完成时仍可能执行 callback，调用 `startIdle()` 并杀掉新步骤的 tween。

`moveTo` 有局部 animToken，attack/hit/fade 和 Web Animation delivery 没有统一 cancellation token。这意味着 Planner 虽然声明了 timeout，Actor Runtime 却没有实现完整的超时语义。

### 3.5 坐标与定位服务分裂

当前至少存在三套定位方式：

1. `useMapEntities.getCellAnchor()`：累加 offsetParent，返回 grid-local 坐标。
2. `battle-actor-executor.getTileAnchor()`：重复同一算法。
3. delivery / DamageNumber / AimMode：使用 `getBoundingClientRect()`，返回 viewport 坐标。

同时 `ActorAnimation.getPosition()` 返回 GSAP x/y（grid-local），而部分投射目标来自 viewport rect。当前调用路径多数恰好可用，但接口没有标注坐标空间，滚动、缩放、跨区域、Teleport overlay 和未来多格实体都容易出错。

ActorExecutor 还直接依赖 `document.getElementById('mapGrid')`、`querySelector([data-pls])` 和固定 10 帧重试。它因此不是纯“演员执行器”，而是同时承担 Scene 查询、坐标换算、DOM 生命周期等待和特效挂载。

### 3.6 位置真值仍有多层但未显式建模

当前存在：

- 领域位置：CharacterHub 的 pgroup/pls。
- 地图读模型位置：mapStore curRegion/curLoc。
- DOM 锚点：cell 的 grid-local 坐标。
- 演出位置：GSAP x/y。
- overlay 位置：viewport 坐标。

这些层本身都合理，问题是它们靠调用方约定而不是类型和服务表达。`MapEntity` 只有 `pls`，没有显式 TileRef/ScenePoint；ActorAnimation 接口直接接收裸 `number` x/y，无法阻止坐标空间混用。

### 3.7 玩家与 NPC 的动画入口不对称

玩家死亡/逃跑通过 playerAvatarStore intent，普通攻击/受击由 ActorExecutor 直接调用 ActorAnimation；NPC 全部直接调用 ActorAnimation。`battle-start`、`battle-end`、low-hp、normal-hp 当前又都退化成 idle。

这说明 playerAvatarStore 既不是完整 actor 状态机，也不是纯 UI 意图存储，而是玩家历史特例层。继续向其中加入战斗姿态会扩大双入口问题。

## 4. 是否应区分战斗/非战斗动画

### 4.1 不应复制两套动画实现

move、idle、hit、attack、fade 等基础动作能力应复用。按 battle/normal 建两套函数会造成参数、时长和取消语义再次分裂。

### 4.2 应区分“控制上下文”

真正需要区分的是谁在什么时间拥有表现控制权：

| 控制域 | 示例 | 位置权威 |
|---|---|---|
| world projection | API 状态刷新、resize、区域切换 | CharacterHub / map projection |
| world transition | 玩家探索移动、NPC world AI 移动 | 状态变化对应的过渡计划 |
| battle choreography | move、attack、hit、delivery、clear | battlelog PlaybackPlan |
| ambient pose | idle、low HP、战斗待机 | Actor Runtime 的非阻塞姿态层 |
| terminal lifecycle | death、escaped、unmount | 明确的退场步骤 |

因此“战斗/非战斗阶段”不是最佳抽象。正确基准是：

> 同一 actor 只有一套能力，但每个动画命令必须声明控制域、作用通道、等待/取消策略和表现所有权。

## 5. 推荐目标架构

### 5.1 SceneGeometry：唯一定位服务

由 MapGrid 注入 scene adapter，不允许 ActorExecutor 自行查询 document：

```ts
interface SceneGeometry {
  resolveTile(ref: TileRef): SceneAnchor | null;
  resolveActor(id: ActorId): SceneAnchor | null;
  sceneToViewport(point: ScenePoint): ViewportPoint;
}
```

类型必须区分 `ScenePoint` 与 `ViewportPoint`，TileRef 同时携带 pgroup/pls。

### 5.2 ActorRuntime：统一演员能力和生命周期

ActorRegistry 从 `id -> DOM controller` 升级为 `id -> ActorRuntime`：

- 注册 generation/session，避免旧 DOM 回调影响新实体。
- 返回 `AnimationHandle { finished, cancel }`，不再使用裸 callback。
- 统一 busy、terminal、disposed 状态。
- timeout 必须 cancel handle，再推进下一 step。

### 5.3 分离 transform 通道

建议 DOM 分层：

```html
<div class="actor-anchor">       <!-- 权威锚点 / grid-local position -->
  <div class="actor-motion">     <!-- 路径位移 / 冲撞偏移 -->
    <div class="actor-pose">     <!-- scale / rotation / hit / idle -->
      <img class="actor-image">
    </div>
  </div>
</div>
```

这样：

- projection 只写 anchor。
- move/attack 只写 motion。
- idle/hit/fall 只写 pose。
- fade 写独立 visibility 通道。
- 各通道可独立 cancel，不再 `killTweensOf` 整个 actor。

### 5.4 PresentationLease：显式表现所有权

BattlePlayback 开始 actor step 时取得 lease：

```ts
const lease = actor.acquire({ owner: 'battle', channels: ['motion', 'pose'] });
try {
  await lease.play(command);
} finally {
  lease.release({ reconcile: true });
}
```

lease 期间：

- map projection 可更新目标状态，但不能覆盖被租用通道。
- resize 只重算 geometry，不强制重置战斗 motion。
- release 后统一 reconcile 到最新权威锚点。

这应成为 Playback Commit Barrier 的单 actor 执行层补充。

### 5.5 统一退场协议

`combatant_cleared` 是退场动画唯一所有者。状态投影提交只负责删除数据和 DOM，不再次播放 fade。

可通过 `removalDisposition` 或 ActorRuntime terminal 状态表达：

- `animated`: 已由 playback 完成退场，直接卸载。
- `projected`: 非战斗视野移除，由 world transition 播放淡出。
- `immediate`: 页面销毁/重置，直接卸载。

### 5.6 非战斗动画也进入轻量命令序列

不需要让探索移动走完整 BattleDirector，但应使用同一 ActorCommand/Handle 协议：

- map state diff 生成 world transition command。
- player intent 生成 ambient/lifecycle command。
- battle plan 生成 battle choreography command。
- ActorRuntime 统一仲裁和执行。

## 6. 对 Director / Planner 的判断

### 保留

- battlelog 事实与视觉脚本分层。
- `directV2()` 纯函数聚合。
- `planPlaybackV2()` 输出 PlaybackStep。
- Runner 顺序 await。

### 需要增强

1. Step 执行应依赖注入的 `BattleScenePort`，不直接 import DOM executor 单例。
2. timeout 语义升级为 cancel + fallback，而非只 resolve。
3. PlaybackStep 应声明所需 actor/channel lease。
4. actor 缺失、tile 缺失、generation 变化应返回结构化结果，而不是静默 return。
5. action spec 应与实际 AnimationHandle duration/cue point 绑定，避免手工双写毫秒数。

结论：Director 不需要结构性推倒；需要把 ActorExecutor 从 DOM 工具函数集合升级为 Scene/Actor Runtime 端口。

## 7. 优先级建议

### P0：所有权与取消协议

- ActorAnimation 改为 Promise/AnimationHandle。
- timeout 真正取消。
- 引入 presentation lease，阻止 map sync 覆盖 battle step。

### P1：坐标统一与 transform 分层

- 抽出 SceneGeometry。
- 删除重复 anchor 算法与 ActorExecutor 的 document 查询。
- 拆 actor-anchor / actor-motion / actor-pose / visibility 通道。

### P1：退场单一所有者

- 消除 battle clear 与 entities removal 的双 fade。
- 定义 terminal/removal disposition。

### P2：统一 world transition / player intent

- playerAvatarStore 收敛为 actor command producer 或 actor state projection。
- 探索移动、HP 姿态和战斗待机使用同一 ActorRuntime 协议。

### P2：可观测性和测试

- 记录 command owner/channel/actor/generation/start/end/cancel/fallback。
- 测试 resize 不打断战斗 move。
- 测试 timeout 后旧 callback 不杀下一动画。
- 测试 combatant clear 只 fade 一次。
- 测试滚动/缩放下 scene 与 viewport 锚点一致。
- 测试同 actor 的 world update 在 battle lease 释放后才 reconcile。

## 8. 最终框架基准

1. CharacterHub 管角色领域状态。
2. SceneGeometry 管领域位置到场景/视口坐标的转换。
3. ActorRuntime 管 actor 的表现状态、动画通道和取消语义。
4. WorldTransition 与 BattlePlayback 都生成 ActorCommand，不直接操作 DOM。
5. Battle Director/Planner 决定战斗演出顺序，不承担坐标查询和 tween 生命周期。
6. 同一 actor 的同一表现通道任一时刻只有一个 owner。
7. 权威状态可以先到达，但只有 owner 释放后才能提交到对应表现通道。
8. timeout 必须终止旧工作，不能只让调用方继续。

因此，本次研判结论不是“新增几种战斗小人动画”，而是：

> 保留现有战斗导演主链，结构性重构 Actor/Scene 执行底座，把位置、姿态、生命周期、坐标空间和播放所有权变成一等概念。
