# 队列推进与玩家视角结局收敛-设计案

> 目标：把“具体角色回合收尾”“公共队列生命周期管理”“玩家视角战斗结局”拆成明确层次，解决 `battle_manage_queue` 由不确定 actor 触发、却直接 emit 战斗结果导致前端难以稳定渲染玩家视角结果的问题。

---

## 一、问题背景

当前战斗流程已经完成第一阶段的队列清理职责重构：

- `bid` 保留为队列引用；
- `oblqueue.active` 表示队列成员是否仍可参战；
- `battle_state_clear` 只做个人退出，标记队列行 `active=0`，不提前清空其他成员；
- `battle_disband_cleanup` 在队列解散时统一清理 `bid/action`。

这个方向是正确的。剩余核心问题是：

> 前端需要渲染“玩家视角下的战斗结果”，但后端的 `battle_end` 日志由 `battle_manage_queue` 在队列解散分支中直接 emit；`battle_manage_queue` 的触发者只是“刚刚行动完的人”，可能是玩家，也可能是 NPC。于是 actor / trigger / winner / viewer 被混在一起。

当前典型问题：

```php
$obl_battle_log->setPhase('battle_end');
$obl_battle_log->emit([
    'winner_pid' => (int)$actor_data['pid'],
    'reason'     => 'disband',
]);
```

这里的 `$actor_data['pid']` 实际语义是：

> 刚刚完成回合、触发队列推进的人。

它不是稳定的 winner，也不是稳定的玩家视角主语。

---

## 二、关键业务约束：为什么保留突袭后建队

曾考虑过“突袭前建队”，即 Ambush 也先创建队列，再统一走：

```text
battle_main → battle_main_end → mark_turn_completed → manage_queue → finalize
```

但结合当前实际业务和代码，该方案不适合当前阶段。

### 2.1 突袭前无法可靠确定合法参战者

玩家提交的 actions 里虽然包含 target pid，但这些 pid 尚未经过后端执行期校验。它们可能：

- pid 不存在；
- 不在射程；
- 不符合技能 target_rules；
- 已死亡或状态不合法；
- 多目标动作中只有部分目标合法；
- 前一个动作造成的 `tag_mutations` 会影响后续动作合法性；
- actor 中途死亡/逃跑/不能继续行动；
- 技能可能是 `unattack`，如逃跑/idle，不应把目标拉入队列。

当前合法目标确认发生在 `battle_main` 内部：

```text
battle_execute_verify
→ battle_once_execute
→ battle_state_init(target)
→ battle_state_middle_check
→ 写入 battle_cache.combatants / tag_mutations
```

也就是说：

> 谁真正参与了战斗，只有 `battle_main` 执行后才可靠。

### 2.2 预建队会导致重复校验和时序不一致

若突袭前建队，需要在 `battle_main` 之前做一套“预验证参战者”流程。这会复制：

- target fetch；
- range check；
- target_rules check；
- tag 构建；
- action 校验；
- 多目标合法性过滤。

但真正执行时 `battle_main` 仍需再校验一次，最终形成两套合法性来源。一旦两者不一致，就可能出现：

```text
建队时认为合法，执行时失败；
或建队时排除，执行时本可合法。
```

因此当前“突袭后建队”不是偶然，而是合理的防御性设计：

```text
先执行突袭
→ 由 battle_main 产出可靠 combatants
→ 再决定是否建队
```

### 2.3 结论

本设计保留：

```text
Phase0 Ambush = 无队列执行期
Phase1 Queue  = 有队列标准战斗
```

但限制 Phase0 的特殊性只存在于“是否建队/是否直接结束”这一步；建队后立即汇入 Phase1 标准队列推进链。

## 三、设计目标

### 3.1 核心目标

1. **队列管理去 actor 化**  
   `battle_manage_queue` 不再接收完整 `$actor_data`，也不再把 actor 当 winner。

2. **角色回合收尾独立化**  
   `done / last_acted` 这种落实到具体角色的操作，从公共队列管理中拆出，放到 `battle_main_end` 之后单独执行。

3. **队列管理成为 qid 级公共事件**  
   公共队列管理只接收 `qid`，根据队列表事实决定：解散、重建、确定下一顺位、更新状态机、准备下一回合。

4. **两个 finalize 入口，共用最终契约**  
   Phase0 直接结束和 Phase1 队列结束的上下文与 cleanup 不同，因此保留两个 finalize 入口：
   - `battle_finalize_phase0_direct_end`
   - `battle_finalize_if_queue_ended`

   但它们共同输出统一的 `BattleFinalResult`，并共用 battle end 日志 emit 函数，保证前端契约一致。

5. **前端只消费玩家视角 outcome**  
   前端不再从 `winner_pid` 或 actor 推断胜负。

### 3.2 非目标

本设计案不做以下事情：

- 不扩展 `action` 为 `active/exited/dead/ambush` 等复杂枚举；
- 不强行消灭 Phase0 / Phase1 的生命周期差异；
- 不做突袭前建队；
- 不要求立即重构全部前端导演系统；
- 不要求新增 DB 字段，除非后续确认必须持久记录 `exit_reason`。

## 四、当前职责混杂点

### 4.1 `battle_manage_queue` 当前承担了过多职责

当前 `battle_manage_queue(&$actor_data, &$obl_battle_log, &$battle_cache)` 至少同时做了：

| 职责 | 说明 | 是否应留在公共队列管理 |
|---|---|---|
| 从 actor 取 qid | `$qid = (int)$actor_data['bid']` | 否，直接传 qid |
| 查 actor 的 myorder | 用于 `last_acted` | 否，属于角色回合收尾 |
| 排除 actor 计算 undone | 假设 actor 已完成行动 | 否，done 应先写入 |
| 标记 actor done | `obl_update_queue_done_and_last_acted` | 否，属于角色回合收尾 |
| 判断 active_count / has_player | 队列生命周期判断 | 是 |
| rebuild 队列 | 队列生命周期管理 | 是 |
| 确定 next | 队列推进 | 是 |
| 更新 battle_state | 队列推进 | 是 |
| 给 next 恢复 AP | 下一回合准备 | 暂时保留 |
| emit battle_end | 玩家视角结局 | 否，交给 finalizer |
| disband cleanup | 队列销毁 | 是，但不应传 actor 引用 |

### 4.2 关键混淆

目前 `$actor_data` 被同时当作：

- qid 来源；
- 当前完成回合者；
- `done/last_acted` 的对象；
- 解散 cleanup 时的内存引用对象；
- `winner_pid`；
- 玩家视角结果推断依据。

这导致队列生命周期和玩家视角结局耦合。

## 五、核心拆分方案

### 5.1 三层结果模型

新的流程拆成三类结果：

```text
BattleMainEndResult   —— 本次行动造成了什么事实变化
QueueManageResult     —— 队列生命周期发生了什么变化
BattleFinalResult     —— 从玩家视角看，这场战斗是什么结果
```

### 5.2 两个 finalize 入口，一个最终契约

Phase0 direct end 与 Phase1 queue end 的 cleanup 来源不同，不强行使用一个超级 finalizer。

采用：

```text
battle_finalize_phase0_direct_end
  ├─ battle_build_phase0_final_result
  │    └─ battle_make_final_result
  ├─ battle_emit_final_battle_log
  └─ battle_state_clear(actor)

battle_finalize_if_queue_ended
  ├─ battle_build_queue_final_result
  │    └─ battle_make_final_result
  └─ battle_emit_final_battle_log
```

也就是说：

- **分开的是上下文适配和 cleanup**；
- **共用的是最终结果结构与日志契约**。

## 六、新增/调整函数设计

### 6.1 `battle_queue_mark_turn_completed`

#### 职责

标记“某个 pid 的回合已经完成”。

它是角色级收尾函数，不是公共队列管理函数。

#### 建议签名

```php
function battle_queue_mark_turn_completed(int $qid, int $pid): array
```

#### 行为

1. 读取该 pid 在 qid 中的队列行；
2. 获取 `myorder`；
3. 设置 `done=1`；
4. 设置 `last_acted=myorder`；
5. 返回标记结果。

#### 返回结构

```php
[
    'qid'      => 123,
    'pid'      => 45,
    'marked'   => true,
    'myorder'  => 2,
    'was_done' => false,
    'active'   => 0,
    'reason'   => null,
]
```

如果队列行不存在：

```php
[
    'qid'      => 123,
    'pid'      => 45,
    'marked'   => false,
    'reason'   => 'queue_row_missing',
]
```

#### 注意

`active=0` 不应阻止标记 done。

原因：actor 可能在自己的回合中逃跑或死亡，`battle_main_end` 已经把它标记为 `active=0`，但它确实完成/终止了本回合。

---

### 6.2 `battle_manage_queue`

#### 职责

公共队列生命周期管理。

只基于 `qid` 和队列表事实执行：

1. 读取队列全量行；
2. 计算 active 成员；
3. 判断是否解散；
4. 判断是否一轮结束并 rebuild；
5. 确定下一顺位；
6. 更新 battle state；
7. 为下一顺位者执行 turn start / AP recover；
8. 返回队列管理结果。

#### 建议签名

```php
function battle_manage_queue(int $qid, &$obl_battle_log, &$battle_cache): array
```

> `battle_cache` 暂时保留，因为 `battle_hook_turn_start` / `battle_ap_recover` 当前需要它。后续如果 hook 不再依赖 cache，可以进一步移除。

#### 不再负责

- 不从 actor 取 qid；
- 不标记 done；
- 不更新 last_acted；
- 不排除 actor；
- 不 emit `battle_end`；
- 不判断玩家视角胜负；
- 不把任何 pid 写成 `winner_pid`。

#### 返回结构

```php
[
    'qid' => 123,

    'queue_exists' => true,

    'disbanded' => false,
    'disband_reason' => null,

    'rebuilt' => false,
    'round_num' => 0,

    'next_pid' => 45,
    'next_type' => 1,

    'active_count' => 2,
    'has_player' => true,
    'undone_count' => 1,

    'queue_rows_before_cleanup' => [...],
]
```

解散时：

```php
[
    'qid' => 123,
    'queue_exists' => true,

    'disbanded' => true,
    'disband_reason' => 'active_count_le_1',

    'rebuilt' => false,
    'next_pid' => null,
    'next_type' => null,

    'active_count' => 1,
    'has_player' => true,
    'undone_count' => 0,

    'queue_rows_before_cleanup' => [...],
]
```

队列不存在兜底：

```php
[
    'qid' => 123,
    'queue_exists' => false,
    'disbanded' => true,
    'disband_reason' => 'queue_empty',
    'queue_rows_before_cleanup' => [],
]
```

### 6.3 `battle_disband_cleanup`

#### 当前问题

当前函数接收 actor 引用，以减少当前 actor 的 fetch：

```php
battle_disband_cleanup($qid, $actor_data, $obl_battle_log)
```

这会把 disband cleanup 继续绑在触发者 actor 上。

#### 建议签名

```php
function battle_disband_cleanup(int $qid, &$obl_battle_log): void
```

#### 行为

1. 遍历 qid 的全部队列行，包括 `active=0`；
2. fetch 每个 pid 的 playerdata；
3. 清空 `bid`；
4. 清空 `action`；
5. 恢复 AP；
6. save；
7. 删除队列；
8. 销毁 battle state。

> 即使当前 actor 已经在内存中，也统一 fetch。先保证职责纯净，性能后续再优化。

### 6.4 `battle_queue_rebuild`

#### 当前问题

当前签名：

```php
function battle_queue_rebuild($qid, &$actor_data, &$obl_battle_log): array
```

但 rebuild 本质上只需要 qid。

#### 建议签名

```php
function battle_queue_rebuild(int $qid, &$obl_battle_log): array
```

同时推动：

```php
battle_queue_set_initiative($qid, $obl_battle_log, $ambush_pid = 0)
```

重建队列时 `ambush_pid=0`。

### 6.5 `battle_main_end`

#### 职责

`battle_main_end` 负责本次行动后的事实结算：

1. actor 死亡补充检测；
2. 遍历 `battle_cache['combatants']`；
3. 对 `combatants[pid]=0` 的单位 emit `combatant_cleared`；
4. 调用 `battle_state_clear` 标记个人退出；
5. 返回本次行动结算事实。

#### 建议返回结构

```php
[
    'mode' => 'player_turn',
    'perspective_pid' => 21,

    'actor_pid' => 21,
    'actor_type' => 0,
    'qid' => 123,

    'actor_status' => 'alive',
    'actor_quit_reason' => null,

    'cleared' => [
        [
            'pid' => 45,
            'type' => 1,
            'reason' => 'death',
            'was_actor' => false,
        ],
    ],

    'combatants_after' => [
        21 => 1,
        45 => 0,
    ],

    'ambush_end_reason' => null,
]
```

Phase0 突袭者退出时：

```php
[
    'mode' => 'ambush',
    'actor_pid' => 21,
    'qid' => 0,
    'actor_status' => 'escaped',
    'actor_quit_reason' => 'escaped',
    'ambush_end_reason' => 'ambusher_escaped',
    'cleared' => [],
    'combatants_after' => [...],
]
```

### 6.6 `battle_phase0_decide`

#### 职责

只回答一个问题：

> Ambush Phase0 执行完成后，是直接结束，还是创建队列进入 Phase1？

它不做 cleanup，不 emit，不重新校验前端 target。

#### 建议签名

```php
function battle_phase0_decide(array $main_end_result, array &$battle_cache): array
```

#### 判断来源

只基于 `battle_main` 之后的可靠事实：

- `main_end_result['ambush_end_reason']`；
- `battle_cache['combatants']` 或 `main_end_result['combatants_after']`。

#### 返回结构

```php
[
    'kind' => 'direct_end',
    'reason' => 'ambusher_escaped',
    'alive_pids' => [],
]
```

或：

```php
[
    'kind' => 'create_queue',
    'reason' => null,
    'alive_pids' => [21, 45],
]
```

#### 伪代码

```php
function battle_phase0_decide(array $main_end, array &$battle_cache): array {
    if (!empty($main_end['ambush_end_reason'])) {
        return [
            'kind' => 'direct_end',
            'reason' => $main_end['ambush_end_reason'],
            'alive_pids' => [],
        ];
    }

    $alive_pids = battle_get_alive_pids($battle_cache);

    if (count($alive_pids) < 2) {
        return [
            'kind' => 'direct_end',
            'reason' => 'ambush_killed_all',
            'alive_pids' => $alive_pids,
        ];
    }

    return [
        'kind' => 'create_queue',
        'reason' => null,
        'alive_pids' => $alive_pids,
    ];
}
```

#### 职责

统一最终结果结构，避免两个 finalize 入口输出格式漂移。

function battle_make_final_result(array $params): array

#### 输出结构

    'qid' => null,

### 6.8 `battle_emit_final_battle_log`

#### 职责

统一最终战斗结果日志 payload。

#### 建议签名

```php
function battle_emit_final_battle_log(array $final, &$obl_battle_log, string $phase): void
```

#### 行为

```php
function battle_emit_final_battle_log(array $final, &$obl_battle_log, string $phase): void {
    if (!$obl_battle_log) return;

    $obl_battle_log->setPhase($phase);
    $obl_battle_log->emit([
        'qid'             => $final['qid'] ?? null,
        'perspective_pid' => $final['perspective_pid'] ?? null,
        'trigger_pid'     => $final['trigger_pid'] ?? null,
        'outcome'         => $final['outcome'] ?? 'unknown',
        'reason'          => $final['reason'] ?? 'unknown',
    ]);
}
```

> 兼容期可继续带 `winner_pid`，但新前端不再依赖。

### 6.9 `battle_finalize_phase0_direct_end`

#### 职责

处理 Phase0 未进入队列的直接结束：

- 突袭者死亡；
- 突袭者逃跑；
- 突袭者一轮杀光所有合法参战目标。

#### 建议签名

```php
function battle_finalize_phase0_direct_end(
    array $decision,
    array $main_end_result,
    array &$actor,
    int $perspective_pid,
    &$obl_battle_log,
    array &$battle_cache
): array
```

#### 行为

1. 根据 `decision + main_end_result + perspective_pid` 生成 `BattleFinalResult`；
2. 调用 `battle_emit_final_battle_log($final, ..., 'ambush_battle_end')`；
3. 调用 `battle_state_clear($actor, ...)` 清理突袭者；
4. 返回 final result。

#### 注意

Phase0 direct end 没有 qid、没有队列行、没有 `battle_disband_cleanup`，因此不能依赖队列 finalizer。

---

### 6.10 `battle_finalize_if_queue_ended`

#### 职责

处理 Phase1 队列解散后的最终结果。

#### 建议签名

```php
function battle_finalize_if_queue_ended(
    int $perspective_pid,
    array $main_end_result,
    array $queue_result,
    &$obl_battle_log
): ?array
```

#### 行为

1. 如果 `queue_result['disbanded']` 为空，返回 `null`；
2. 根据 `main_end_result + queue_result + perspective_pid` 生成 `BattleFinalResult`；
3. 调用 `battle_emit_final_battle_log($final, ..., 'battle_end')`；
4. 返回 final result。

#### 注意

Phase1 队列解散 cleanup 由 `battle_manage_queue` / `battle_disband_cleanup` 完成，queue finalizer 不再调用 `battle_state_clear`。

## 七、玩家视角 outcome 规则草案

### 7.1 outcome 枚举

```php
'victory'
'defeat'
'player_fled'
'npc_fled'
'unknown'
```

### 7.2 Phase0 direct end 初步规则

| 条件 | outcome | reason |
|---|---|---|
| `decision.reason = ambusher_escaped` 且 perspective 是 ambusher | `player_fled` | `ambusher_escaped` |
| `decision.reason = ambusher_dead` 且 perspective 是 ambusher | `defeat` | `ambusher_dead` |
| `decision.reason = ambush_killed_all` 且 perspective 是 ambusher | `victory` | `ambush_killed_all` |
| perspective 不是 ambusher | 按后续 NPC 突袭视角规则补充 | `unknown` |

### 7.3 Queue ended 初步规则

以 `perspective_pid` 为玩家视角。

| 条件 | outcome | reason |
|---|---|---|
| 玩家在 `main_end_result.cleared` 中，reason=`death` | `defeat` | `player_dead` |
| 玩家在 `main_end_result.cleared` 中，reason=`escaped` | `player_fled` | `player_escaped` |
| 队列解散前玩家 active=0，且能确认 reason=death | `defeat` | `player_dead` |
| 队列解散前玩家 active=0，且能确认 reason=escaped | `player_fled` | `player_escaped` |
| 队列解散前玩家仍 active，敌方无人 active | `victory` | `enemy_defeated_or_left` |
| 队列解散由最后 NPC 逃跑触发 | `npc_fled` | `npc_escaped` |
| 队列缺失 / 信息不足 | `unknown` | `queue_empty` / `insufficient_context` |

### 7.4 当前信息缺口

`oblqueue.active=0` 只能表示“退出队列”，不能持久区分 death / escaped。

短期可从 `main_end_result.cleared` 获取本次清理原因。

但如果最终结果需要识别“不是本次行动中退出的历史成员原因”，可能需要：

1. 在 `QueueManageResult` 中结合 battle log / battle_cache 暂存原因；或
2. 给 `oblqueue` 增加 `exit_reason` 字段；或
3. 在 `battle_cache` 生命周期内保留 `exit_reasons[pid]`。

本设计案暂不强制新增字段，后续按实际 outcome 需求讨论。

## 八、Phase1 标准流程

### 8.1 玩家回合 / NPC 回合统一流程

```text
1. battle_entry_dispatch(mode, actor, actions, extra)
2. 确定 perspective_pid
3. battle_cache_create(actor, false)
4. battle_main(actor, actions, log, cache)
5. main_end_result = battle_main_end(...)
6. qid = actor.bid
7. turn_completed_result = battle_queue_mark_turn_completed(qid, actor.pid)
8. queue_result = battle_manage_queue(qid, log, cache)
9. final_result = battle_finalize_if_queue_ended(perspective_pid, main_end_result, queue_result, log)
10. 返回 dispatch result
```

### 8.2 dispatch 返回结构草案

```php
[
    'main_end' => $main_end_result,
    'turn_completed' => $turn_completed_result,
    'queue' => $queue_result,
    'final' => $final_result,
]
```

对于 NPC tick，仍可只关心：

```php
$result['queue']['disbanded']
$result['queue']['next_pid']
```

## 九、Ambush Phase0 流程

### 9.1 Ambush 的特殊性

Ambush Phase0 与 Phase1 标准流程不同：

1. Phase0 执行动作时尚未建队列；
2. 发起者 `bid=0`；
3. `battle_cache` 初始只有发起者；
4. 合法参战目标由 `battle_main` 执行期确认；
5. Phase0 结束后有三种方向：
   - 突袭者死亡/逃跑，直接结束；
   - 突袭者一轮杀光目标，直接结束；
   - 仍有至少两名存活 combatant，创建 Phase1 队列。

### 9.2 流程骨架

```text
1. battle_state_init(actor)
2. battle_cache_create(actor, true)
3. battle_main(actor, actions, log, cache)
4. main_end_result = battle_main_end(...)
5. phase0_decision = battle_phase0_decide(main_end_result, cache)
6. if phase0_decision.kind === 'direct_end':
       final_result = battle_finalize_phase0_direct_end(...)
       return
7. qid = battle_queue_create_and_init(actor, phase0_decision.alive_pids, log)
8. turn_completed_result = battle_queue_mark_turn_completed(qid, actor.pid)
9. queue_result = battle_manage_queue(qid, log, cache)
10. final_result = battle_finalize_if_queue_ended(perspective_pid, main_end_result, queue_result, log)
11. return
```

### 9.3 Phase0 direct end 的 cleanup

Phase0 direct end 没有队列，因此 cleanup 只能清理突袭者自身：

```text
battle_finalize_phase0_direct_end
→ battle_emit_final_battle_log(..., 'ambush_battle_end')
→ battle_state_clear(actor)
```

若 Phase0 中存在已进入 `battle_cache.combatants` 但仍存活的目标，是否需要额外清理/离场动画，需要单独确认：

- 方案 A：复用 `combatant_cleared reason=ambush_ended`；
- 方案 B：只清 actor，目标本身由 `battle_state_clear` 或后续逻辑保证未卡战斗；
- 方案 C：新增轻量 `combatants_reset`，但不作为优先方案。

### 9.4 Phase0 进入 Phase1 后

一旦创建队列，后续立即汇入 Phase1 标准链：

```text
battle_queue_mark_turn_completed
→ battle_manage_queue
→ battle_finalize_if_queue_ended
```

这等价于规则化：

> 突袭者已经在 Phase0 行动过；如果进入 Phase1 队列，本轮视为突袭者已完成行动。

## 十、前端影响

### 10.1 battle log 字段

新增或明确以下字段：

```ts
perspective_pid?: number | null;
trigger_pid?: number | null;
outcome?: 'victory' | 'defeat' | 'player_fled' | 'npc_fled' | 'unknown' | null;
reason?: string | null;
```

旧字段：

```ts
winner_pid?: number | null;
```

保留兼容但不再作为结果判断依据。

### 10.2 前端判断方式

旧逻辑：

```ts
// 不推荐
winner_pid === playerPid ? victory : defeat
```

新逻辑：

```ts
switch (entry.outcome) {
  case 'victory':
  case 'defeat':
  case 'player_fled':
  case 'npc_fled':
  case 'unknown':
}
```

### 10.3 ambush_battle_end 与 battle_end

前端可以保留两个段类型：

- `ambush_battle_end`：Phase0 未进入队列的直接结束；
- `battle_end`：有队列后的标准战斗结束。

但两者都应带统一 `outcome/reason/perspective_pid/trigger_pid` 字段，因此前端结果判断逻辑可共用。

## 十一、实施步骤建议

### 阶段 1：拆出角色回合收尾

1. 新增 `battle_queue_mark_turn_completed($qid, $pid)`；
2. 从 `battle_manage_queue` 移除：
   - actor myorder 查找；
   - actor 排除 undone；
   - `obl_update_queue_done_and_last_acted`；
3. dispatch 在 `battle_main_end` 后调用 mark turn。

### 阶段 2：队列管理 qid 化

1. `battle_manage_queue(&$actor_data, ...)` 改为 `battle_manage_queue($qid, ...)`；
2. `undone` 改为纯 `done=0 AND active=1`；
3. `battle_disband_cleanup` 改为只传 qid；
4. `battle_queue_rebuild` / `battle_queue_set_initiative` 去 actor 参数。

### 阶段 3：移除队列管理中的 battle_end emit

1. `battle_manage_queue` 解散时只返回 `disbanded=true`；
2. 不再 emit `winner_pid`；
3. 返回 `queue_rows_before_cleanup` 给 queue finalizer。

### 阶段 4：引入最终结果共用契约

1. 新增 `battle_make_final_result`；
2. 新增 `battle_emit_final_battle_log`；
3. battle log emit 统一带 `outcome/reason/perspective_pid/trigger_pid`。

### 阶段 5：引入两个 finalize 入口

1. 新增 `battle_finalize_if_queue_ended`；
2. 新增 `battle_phase0_decide`；
3. 新增 `battle_finalize_phase0_direct_end`；
4. Phase0 direct end 和 queue end 分别适配自己的上下文，但共用 final result / emit。

### 阶段 6：前端读取 outcome

1. API 类型补充 `perspective_pid/trigger_pid/outcome`；
2. 前端 battle end 判断改读 `outcome`；
3. 兼容期保留 `winner_pid` 但不再依赖。

## 十二、设计原则总结

1. **actor 不是 winner**：actor 只是当前动作执行者或队列推进触发者。
2. **队列管理不说玩家视角结果**：它只说队列是否解散、重建、下一顺位是谁。
3. **具体角色收尾不属于公共队列管理**：`done/last_acted` 必须独立。
4. **突袭后建队是业务约束**：合法参战者只有 `battle_main` 执行后才可靠。
5. **Phase0 和 Phase1 不强行同构**：Phase0 direct end 可以有专门 finalize 入口。
6. **最终契约必须统一**：两个 finalize 入口都输出 `BattleFinalResult`，并共用最终日志 emit。
7. **最终结果必须有 perspective**：没有玩家视角 pid，就不应该生成玩家视角 outcome。
