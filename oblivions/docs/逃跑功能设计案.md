# 逃跑（Flee）功能设计案

> 本文件为最终设计方案。由用户与我逐层分析当前队列系统后收敛。
> 前期探索留存参考：`B2方案——战斗上下文独立于队列.md`（备而不用）。

---

## 一、效果需求

1. **自目标技能** — 加入队列时不需要选择目标（`target=self`，已配置）
2. **不能连续执行多次逃跑** — CD=1，时间戳模型，已实现
3. **逃跑后清理战斗与队列** — 玩家回到探索状态，NPC 不再锁定战斗

---

## 二、从目的反推：问题定位

对整个队列管理系统逐函数分析后，每个函数单独看逻辑都简单，问题出在 `battle_manage_queue` 这条**固定 4 步管道**：

```
ensure → advance(done + update[C/D/E]) → try_end
```

固定管道不允许跳过。逃跑是第一个让这个模型**必须提供跳过路径**的场景。

### 三个具体的架构缺陷

| 编号 | 缺陷 | 表现 |
|------|------|------|
| ① | `battle_queue_ensure` 不知道调用者意图 | bid=0 时不管什么原因都建队列，逃跑后也会重建 |
| ② | `battle_queue_create` 的 `$preserve_qid` 参数 | 新建和重建是不同目的，混用一个函数 |
| ③ | 解散检测人数 ≤ 1 是 proxy，不是语义 | NPC-only 队列不解散 |
| ④ | 状态机销毁在 try_end 而非解散处 | `$last_qid` 偷渡 read-after-delete |

### 状态机审计发现的 3 处设计不精准

| 位置 | 买什么（表面的复杂机制） | 还什么（实际需要的操作） |
|------|------------------------|------------------------|
| `enemy_ai` 过渡前 `get === NPC_ACTING` 防御 if | 看起来双重校验更安全 | transition 内部已有校验，外层为冗余 |
| encounter 用 `reset` 设初始状态 | 看起来在"恢复异常" | 正常初始设值，写误导 error log |
| `npc_done_npc_turn` → NPC_ACTING 自循环 | 看起来是一个状态转换事件 | 刷新时间戳而已 |

## 三、最终方案：四点改动 + 三项清理

不引入新表、不新加概念、不拆 `battle_once_execute`。

### 改动一：`battle_queue_ensure` 加"有人可打"检查

**位置**：`battle.queue.func.php`

**旧行为**：bid=0 → 无条件建队列

**新行为**：

```php
if (empty($actor_data['bid'])) {
    $alive_pids = battle_get_alive_pids($battle_cache);
    $others = array_filter($alive_pids, fn($p) => $p !== (int)$actor_data['pid']);
    if (empty($others)) return; // 无人可打，不建队列
    battle_queue_create($actor_data, $alive_pids, $obl_battle_log);
}
```

### 改动二：`battle_queue_create` 拆出 `battle_queue_rebuild`

**位置**：`battle.queue.func.php`

**旧**：`battle_queue_create(..., $preserve_qid=0)` — 一个函数两个用途

**新**：

```
battle_queue_create($actor_data, $combatants, $obl_battle_log)    ← 新建（设 bid + 建状态机）
battle_queue_rebuild($qid, $combatants, $obl_battle_log)          ← 重建（不设 bid + 不建状态机）
```

移除 `$preserve_qid` 参数。`battle_queue_update` 中的重建调用改为 `battle_queue_rebuild`。

### 改动三：解散检测加"无玩家解散"

**位置**：`battle_queue_update` 的 C 段

**新增 SQL 函数**：`obl_fetch_queue_has_player($qid)` — 查队列中是否存在 `type=0` 的记录

**新解散条件**：

```
解散 if count ≤ 1 OR !has_player
```

| 场景 | count | has_player | 解散？ |
|------|-------|-----------|--------|
| 正常战斗（玩家+NPC） | ≥2 | true | 否 |
| 突袭秒杀，只剩玩家 | 1 | true | 是 |
| 玩家逃跑，只剩 NPC | ≥1 | **false** | **是新修** |

### 改动四：解散时直接销毁状态机（消除 `$last_qid`）

**位置**：`battle_queue_update` 的 C 段 + `battle_queue_try_end`

**问题**：

```
C 段解散（删队列、清 bid）→ try_end 需要 qid 触 battle_end → 但 qid 已丢
→ 用 battle_cache['last_qid'] 偷渡
```

原因：状态机销毁和队列销毁被人为分开在两处，但流水线又保证它们总是依次执行。

**修复**：C 段解散时直接销毁状态机：

```php
// battle_queue_update C 段解散处
obl_queue_delete_by_qid($qid);
obl_battle_state_transition($qid, 'battle_end');
obl_battle_state_destroy($qid);
$actor_data['bid'] = 0;
// 不再设 battle_cache['last_qid']
```

`try_end` 的 bid=0 分支不再需要 `last_qid`，直接 `battle_state_clear` 即可。

**位置**：`battle_queue_update` 的 C 段

**新增 SQL 函数**：`obl_fetch_queue_has_player($qid)` — 查队列中是否存在 `type=0` 的记录

**新解散条件**：

```
解散 if count ≤ 1 OR !has_player
```

| 场景 | count | has_player | 解散？ |
|------|-------|-----------|--------|
| 正常战斗（玩家+NPC） | ≥2 | true | 否 |
| 突袭秒杀，只剩玩家 | 1 | true | 是 |
| 玩家逃跑，只剩 NPC | ≥1 | **false** | **是新修** |

## 四、逃跑 calc 文件

**新建**：`calc/escape.calc.php`

职责按执行顺序：

```
1. emit flee battlelog                ← 前端渲染
2. battle_queue_exit(actor)           ← 从队列删除自己，bid=0
3. combatants 中删 actor 条目          ← 确保 ensure 无人可建
4. actor_data['action'] = ''          ← 清理战斗状态
   actor_data['ap'] = actor_data['max_ap']
5. obl_save_player(actor)
```

> 注：不再设 `last_qid`。队列解散由 `battle_queue_update` C 段直接销毁状态机（改动四）。

### 二次调用保护

`battle_state_clear` 会在 flee calc 和 `try_end` 中各调一次。在 `battle_state_clear` 入口加：

```php
if (empty($actor_data['action']) && empty($actor_data['bid'])) {
    return; // 已清理，跳过
}
```

## 五、完整流水线

```
前端提交 obl_battle_action (act_id=escape, target=self)

cmd_handle_obl_battle_action
  → battle_main
    → battle_verify(CD 通过, lstact=current_tick)
    → battle_execute
      → battle_once_execute(actor, escape, self)
        → skill_execute → escape.calc.php
          emit flee log
          battle_queue_exit(actor) → bid=0
          combatants 删 actor
          last_qid = qid
          action='', ap=max_ap
          save_player
        → damage=0 (damage_type:none)
        → apply_damage(0)
        → alive_check → true (自目标)
        → save_player (重复，无害)

  → battle_manage_queue
    → ensure: bid=0, others 为空 → return    ← 改动一
    → advance: bid=0 → done 无效 → update 内 qid=0 → return
      ← 注意：flee calc 已调用 battle_queue_exit 删除队列记录
        所以 update 找不到 qid → 不解散 → 不触 battle_end
    → try_end: bid=0 → 走结束路径
      → battle_state_clear(已 empty) → return  ← 二次调用保护

obl_command.php [C2d]: WAITING_PLAYER → PLAYER_DONE
  → bid=0 → 状态机查不到 → 无操作

obl_command.php [F]: 推进 tick
  → 战场已销毁 → 无操作

响应 {}（回到探索状态）
```

## 六、状态机清理（3 项不精准设计）

### 6.1 冗余防御 if

**位置**：`enemy_ai.func.php:82-84`

**清理**：去掉 `get === NPC_ACTING` 外层 if，直接调 `transition`。

```
旧: if (get($qid) === NPC_ACTING) { transition($qid, 'npc_done_player_turn'); }
新: transition($qid, 'npc_done_player_turn');
```

transition 内部已有完整的转换表校验，外部 if 是冗余。

### 6.2 误用 reset 做初始设值

**位置**：`battle.entry.php:159/162`

**修复**：改为 `obl_battle_state_set($qid, OBL_BS_WAITING_PLAYER)` 直接写，不走 reset。

> 长远方案：`battle_queue_create` 允许外部传入初始状态，encounter 在建队列时直接设正确状态，无需事后覆盖。

### 6.3 自循环代替刷新函数

**位置**：`battle_state_machine.func.php:134` 转换表特判

**修复**：新增 `obl_battle_state_refresh($qid)`，只更新 `updated_at`。NPC 行动后直接调它。

```php
function obl_battle_state_refresh($qid) {
    global $db, $tablepre, $now;
    if (!isset($now)) $now = time();
    if ($qid <= 0) return;
    $db->query("UPDATE {$tablepre}oblbattle_state SET updated_at = " . (int)$now . " WHERE qid = " . (int)$qid);
}
```

移除转换表中 `NPC_ACTING → NPC_ACTING` 自循环分支。

### 优先级

| 项 | 优先级 | 理由 |
|----|--------|------|
| 6.1 冗余 if | 低 | 无害，代码噪音 |
| 6.2 误用 reset | 中 | 产生误导 error log，但正常流程不受影响 |
| 6.3 自循环 | 低 | 仅在调试时影响 updated_at 的可信度 |

**推荐**：6.2 随逃跑功能修复，6.1 和 6.3 可选。

## 八、安全边界

1. **NPC AI 不会选择逃跑** — `combat_skills` 列表不含 `escape`，自然不被选中
2. **预留失败路径** — `verify/escape.verify.php` 可后续添加失败条件（如概率、障碍检测）
3. **CD 足够** — cd=1 防止同一次行动里塞多个 flee，下轮一定可再试
4. **前端感知** — 命令返回后 `action=''` 自动触发战斗模态框关闭

## 九、设计决策记录

| 决策 | 选项 | 选定 | 理由 |
|------|------|------|------|
| 拆分 `battle_once_execute` | 拆分 / 不拆分 | **不拆分** | 现有路径已覆盖自目标 + 无伤害 |
| CD 模型 | timestamp / 递减计数器 | **timestamp** | 零额外逻辑，实时比较，已实现 |
| 引入新表（B2） | 引入 / 不引入 | **不引入** | 改动量过大，问题可由三点改动解决 |
| 逃跑后队列处理 | ensure 加 guard / 加 intent 参数 / **加 `others` 检查** | **`others` 检查** | 不改 pipeline，只改条件 |
| 二次调用保护 | callee 侧 / caller 侧 | **callee 侧** | 防御性编程，不影响现有调用方 |
| `$preserve_qid` | 保留 / 拆 rebuild | **拆 rebuild** | 语义清晰，消除混用 |
