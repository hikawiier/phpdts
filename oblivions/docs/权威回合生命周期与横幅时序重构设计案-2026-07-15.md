# 权威回合生命周期与横幅时序重构设计案

> 状态：已实施
>
> 日期：2026-07-15
>
> 目标：从领域层重新建立回合身份、回合开放与动作执行的边界，解决第一轮重复显示“战斗开始”和玩家回合宣告晚于装填阶段的问题。

> 实施锚点：`oblivions/include/game/battle_turn.func.php`、`oblivions/include/game/battle_state_machine.func.php`、`vex-vue/src/stores/battle-director.ts`；框架归属与边界案例已同步至 `oblivions/Dian.md`。

---

## 1. 结论与框架分级

这两个问题不是 `BattleBanner.vue` 的显示边界案例，而是同一个框架缺口在两个方向上的表现：系统没有权威、跨请求稳定的“当前回合”，同时把“回合控制权已经交给行动者”和“行动者的动作开始执行”压缩成了同一个 `turn_start`。

因此本任务属于**基准框架重构**，不能通过前端记忆“是否显示过战斗开始”、修改标题条件或为玩家单独补一个提示解决。

主框架归属：

- **E-5 战斗有限状态机**：升级为“权威战斗与回合生命周期状态机”，持久化当前回合身份并拥有回合开放、执行、关闭的状态转换。
- **I-1 先攻队列编排**：降级为纯顺位基础设施，只回答下一位候选行动者，不再切换战斗状态或发射回合事件。
- **D-1 动作生命周期编排**：只执行一个已经开放且校验通过的回合，不再负责创建回合、递增回合序号或恢复回合资源。
- **D-4 结构化战斗事件发射器**：发射带权威回合坐标的领域事实，不再依赖请求级收集器生成回合编号。
- **C-4 事件批量投递**：保持传输层身份，只负责批内排序、打包和投递，不拥有战斗、轮次或回合语义。
- **K-1 战斗回合编排 + 演示播放管道**：消费显式领域事件生成横幅和终局演出，不自行判断战斗开始、回合开始或战斗结束。

跨模块设计意图可概括为**权威回合边界协议**：领域状态决定“现在是谁的第几个回合、处于什么阶段”，事件只陈述该事实，演示层只投影该事实，命令必须引用该事实。

## 2. 从目的反推系统行为

### 2.1 用户实际需要感知的事实

1. 战斗正式建立后的第一个行动者开始其正式回合时，显示一次“战斗开始 + 行动者的回合”。
2. 后续每个行动者获得回合时，显示“第 N 轮 + 行动者的回合”。
3. 玩家回合的宣告由控制权交接触发，而不是由玩家提交动作触发。
4. NPC 与玩家遵守同一套回合生命周期；区别只在于控制者是玩家还是系统。
5. HTTP 请求、heartbeat 次数、presentation batch 切分和重试均不能改变回合身份或造成重复宣告。

### 2.2 由目的导出的强制约束

- 回合编号必须存放在战斗级持久状态中，不能存放在 `BattleLogCollector` 等请求级对象中。
- “战斗开始”必须是后端给出的领域事实，前端不能通过 `roundNum === 1 && turnNum === 1` 猜测。
- 玩家是否处于可操作回合只由权威状态决定；演出期间是否允许提交继续复用通用 presentation gate，不建立回合专用前端状态机。
- `battle.submit_turn` 必须声明它提交的是哪个权威回合，后端使用原子比较拒绝陈旧提交。
- 回合开始资源恢复和 start-of-turn 效果必须在开放玩家输入之前完成，否则前端看到的 AP 和角色状态不是本回合的真实起点。

## 3. 新领域模型：BattleTurn

### 3.1 权威状态存储

`oblbattle_state` 从三态忙闲标记升级为每个战场一行的权威回合记录：

| 字段 | 语义 |
|---|---|
| `qid` | 战场身份，主键 |
| `state` | `IDLE` / `AWAITING_INPUT` / `AUTO_PENDING` / `EXECUTING` |
| `round_num` | 当前轮次，数据库内 0-indexed，对外事件统一 1-indexed |
| `turn_seq` | 战场内单调递增的回合序号，第一回合为 1，跨请求不重置 |
| `active_pid` | 当前回合行动者；替代语义含混的 `next_pid` |
| `opened_at_tick` | 当前回合开放时的 tick，用于诊断和卡死恢复 |
| `updated_at` | 状态最后更新时间 |

稳定回合键定义为 `turn_key = qid + ':' + turn_seq`。数据库不必重复存储拼接字符串，API 和事件层可按需派生。

`turn_seq` 是回合的唯一身份；`round_num` 只承担轮次规则与显示。任何 presentation batch、请求 ID、事件序号都不得替代 `turn_seq`。

### 3.2 状态机

```text
IDLE
  └─ create battle + open turn
       ├─ human actor ──> AWAITING_INPUT
       └─ system actor ─> AUTO_PENDING

AWAITING_INPUT
  └─ submit(expected_turn_seq) ─> EXECUTING

AUTO_PENDING
  └─ tick claims active turn ───> EXECUTING

EXECUTING
  ├─ battle ended ──────────────> IDLE
  └─ close current + open next
       ├─ human actor ──────────> AWAITING_INPUT
       └─ system actor ─────────> AUTO_PENDING
```

状态转换必须通过带当前 `state`、`active_pid`、`turn_seq` 条件的原子更新完成。失败表示其他请求已经推进了战场，调用方必须停止执行，不能继续依赖内存快照。

### 3.3 回合开放事务

`open turn` 是唯一能够创建新 `turn_seq` 的领域操作，流程固定为：

1. 从 I-1 获取下一位仍可行动的候选者。
2. 若队列完成一轮，先重建队列并递增 `round_num`。
3. 原子递增 `turn_seq`，写入 `active_pid`。
4. 执行 start-of-turn 规则：AP 恢复、回合开始状态效果、资格复核。
5. 若行动者在开放过程中死亡、逃离或失去行动资格，关闭该回合并继续选择下一位，不向玩家开放输入。
6. 根据行动者控制类型写入 `AWAITING_INPUT` 或 `AUTO_PENDING`。
7. 发射一次自包含的 `turn_opened` 事件。

AP 恢复从 `combat_dispatch` 移到该事务。这样玩家看到装填区时，权威 AP、能力状态和可用动作已经是本回合状态。

状态写入、队列写入和事件缓冲必须共享同一个事务检查点：事务开始时记录 `BattleLogCollector` checkpoint，数据库回滚时同步 `rollbackTo(checkpoint)`。不允许数据库回滚后仍向 presentation 投递一个不存在的 `turn_opened`。

### 3.4 动作执行事务

玩家提交必须包含：

```json
{
  "qid": 42,
  "expected_turn_seq": 7,
  "actions": []
}
```

后端只有在以下条件同时成立时才接受：

- `state = AWAITING_INPUT`
- `active_pid = command actor pid`
- `turn_seq = expected_turn_seq`

接受后先原子切换为 `EXECUTING`，再进入 D-1 动作排序、校验、执行和持久化流程。D-1 不再调用 `battle_hook_turn_start`，也不再恢复 AP 或创建 `turn_start`。

NPC tick 使用相同契约，只是从 `AUTO_PENDING` 认领当前回合，不携带用户命令。

动作结束后由 E-5 关闭当前回合；I-1 只负责标记队列成员完成并返回下一候选者，E-5 再决定结束战斗、重建轮次或开放下一回合。

## 4. 事件契约重建

### 4.1 请求级元数据与领域坐标分离

`BattleLogCollector` 继续是请求级事件缓冲区，但删除以下领域职责：

- 不保存或递增 `turnNum`。
- 不从当前 phase 推断 `bl_segment_flag`。
- 不为事件填充 `bl_round_num` / `bl_turn_num`。

领域事件创建时必须显式携带权威坐标。收集器只能添加批内 `event_seq` 等传输元数据。

由于现有 `battlelog.v2` 已经把请求级计数暴露为领域字段，新的不兼容契约应升级为 `battlelog.v3`，避免同名字段静默改变语义。

### 4.2 `turn_opened` 事件

```json
{
  "schema": "battlelog.v3",
  "event_type": "turn_opened",
  "event_uid": "battle:42:turn:7:opened",
  "qid": 42,
  "round_num": 1,
  "turn_seq": 7,
  "turn_key": "42:7",
  "payload": {
    "actor": {},
    "controller": "player",
    "opening_kind": "turn",
    "ap_recovered": 2
  }
}
```

字段约束：

- `event_uid` 由权威回合身份确定，重试时保持稳定，用于去重。
- `opening_kind` 只有 `battle_start` 或 `turn`。第一正式回合由后端写入 `battle_start`，前端不再推断。
- `controller` 为 `player` 或 `system`，只描述控制来源，不改变生命周期。
- `round_num` 对外统一为 1-indexed，前端不再执行 `+1`。
- 所有 `action_*`、`effect_*`、退场和战斗结束事件都携带同一个 `turn_seq` / `turn_key`，导演层按 `turn_key` 分组。

### 4.3 首场战斗

`battle.start` 的动作是在战斗正式存在前由玩家预先选择的交战意图。正式战斗建立后：

1. E-5 创建战场并开放 `turn_seq=1`。
2. 发射 `opening_kind='battle_start'` 的 `turn_opened`。
3. 将预先提交的首回合动作认领到该回合并进入 `EXECUTING`。
4. 发射动作事件。

因此同一 presentation 流内仍是“战斗开始横幅 → 首回合动作”，但“战斗开始”不再依赖请求级数字组合。

## 5. 前端只做演出投影

### 5.1 导演层

K-1 导演层改为：

- 只有 `turn_opened` 能创建回合横幅 segment。
- segment 使用 `turn_key` 作为稳定身份。
- `opening_kind='battle_start'` 显示“战斗开始”；其他情况显示“第 N 轮”。
- 横幅 actor 文案继续根据控制对象显示“你的回合”或“XX 的回合”。
- 动作事件只能归入相同 `turn_key` 的 turn segment；缺少 `turn_key` 视为契约错误，不静默猜测。
- 只有显式 `battle_end` 事件能创建终局演出；前端不根据玩家 action、战斗状态或存活人数推断战斗结束。

原 `round_intro` 名称混合了“轮次”和“行动者回合”两个概念，应改名为 `turn_intro`。它表示回合开放的视觉投影，不表示 round 自身是一个可执行段。

### 5.2 权威状态与演出状态互不推导

前端遵守两个独立输入源：

- 权威 `battle_state` 决定当前是否是玩家回合以及装填区是否显示。
- presentation 事件决定是否播放横幅、动作和终局演出。

前端不建立 `presentedTurnKey`、`isTurnPresentationReady`、`canAcceptTurnInput` 等回合专用补偿状态，也不等待横幅回调来确认一个后端已经开放的回合。

演出播放期间的命令阻塞继续由现有 K-3 通用规则承担：presentation scene 非 `idle` 时，战斗命令返回 `PRESENTATION_NOT_CAUGHT_UP`。这是一条演出水位规则，不需要再叠加“当前回合横幅是否完成”的专用判断。

装填区在横幅期间隐藏、显示在遮罩后方或保持预挂载，属于视觉策略。需要隐藏时直接消费通用 `presentationPhase`，不得为此创建新的回合生命周期状态。

前端只保留演出本身必须的生命周期约束：runner 必须按顺序等待横幅 step，`battle_end` 计划完成前 BattleBanner、presentation session 和场景交接资源不能卸载。这个屏障保护的是正在执行的演出资源，不参与判断战斗是否开始或结束。

### 5.3 可靠性边界

正常路径只消费 presentation 事件，不从 `active_turn` 合成或补播演出。`player_info.combat_context` 仍需投影 `qid`、`turn_seq`、`active_pid` 和 `state`，用途是显示权威状态并为 `battle.submit_turn` 提供 `expected_turn_seq`，不是判断横幅是否已经播放。

页面重连或 presentation gap 发生时，前端直接重基准到当前权威状态；已经错过的瞬态横幅不补播。若产品未来要求某类演出绝不能丢失，应在 C-4 增加持久投递或重放能力，而不是让 K-1 同时从事件和状态两个来源推导演出。

因此前端的完整职责是：按 `batch_seq` 消费事件、按事件顺序生成播放计划、执行计划、在场景稳定后恢复现有命令门控。它不是第二个战斗状态机。

## 6. 职责重排

| 当前职责 | 新归属 |
|---|---|
| `BattleLogCollector::$turnNum` | 删除；由 E-5 的 `oblbattle_state.turn_seq` 取代 |
| `battle_manage_queue` 切换 `PLAYER_TURN` / `PROCESSING` | 移交 E-5；I-1 只返回下一候选者 |
| `combat_dispatch` 递增 turn、恢复 AP、emit `turn_start` | 移交 E-5 的 open turn；D-1 只执行动作 |
| 前端用 round/turn 数字判断战斗开始 | 删除；消费 `opening_kind` |
| 前端根据状态推断战斗结束 | 删除；只消费显式 `battle_end` 事件 |
| 提交动作不声明回合身份 | `battle.submit_turn` 必须携带 `expected_turn_seq` |
| `round_intro` 同时表达轮次与行动者回合 | 重命名为 `turn_intro`，只表达回合开放 |
| 前端为丢失横幅合成 presentation | 删除；瞬态演出丢失时直接按权威状态重基准 |

### 6.1 目标实现边界

- `oblivions/include/game/battle_state_machine.func.php`：E-5 的状态持久化、原子状态转换和活动回合读取。
- `oblivions/include/game/battle_turn.func.php`：新增 E-5 回合开放、认领、关闭编排器；这是新生命周期的唯一入口。
- `oblivions/include/game/battle/battle.queue.func.php`、`battle.queue.main.php`：I-1 队列候选、完成标记和轮次重建，不写战斗状态。
- `oblivions/include/game/combat/combat.core.php`：D-1 动作执行入口，要求调用方已经认领活动回合。
- `oblivions/include/game/combat/combat.log.php`：D-4 `battlelog.v3` 领域事件构造器。
- `oblivions/include/game/battle_log.func.php`、`oblivions/include/core/obl_runtime.php`：C-4 请求级缓冲、批次排序和投递。
- `vex-vue/src/stores/battle-director.ts`：消费 v3 契约并移除数字猜测；旧 v2 导演已删除。
- `vex-vue/src/stores/battle.ts`：K-1 批次消费、导演调用和权威玩家回合状态发布，不补建 presentation。
- `vex-vue/src/stores/command-queue.ts`、`command-registry.ts`：继续提供现有通用 presentation 水位门控，不增加回合横幅专用状态。
- `vex-vue/src/components/battle/PreloadArea.vue`：提交时从权威 combat context 携带 `expected_turn_seq`。
- `vex-vue/src/components/battle/BattleActionBar.vue`：继续按权威玩家回合状态渲染；横幅期间的显隐只依赖通用 presentation phase。

玩家动作区不能只观察 `isPlayerTurn` 的布尔跳变来判断新回合。一次刷新可能把“本轮玩家提交 → NPC 行动 → 下一轮玩家开放”完整排空，组件最终只看到 `true → true`。因此装填编辑会话必须以 `qid + turn_seq` 为身份：同一身份提交成功后立即清空动作并进入等待显示；只有后续权威投影发布不同的 `turn_seq`，才重新开放一个空的编辑会话。前端可保留“该回合已提交”的一次性闩锁来覆盖命令响应与投影刷新的竞态窗口，但该闩锁不得生成回合号、推进状态或替代后端认领结果。

横幅播放时长属于 K-1 的视觉节奏参数，不承载领域边界。回合横幅与终局横幅的停留、进出场过渡和过渡兜底统一缩短 50%，runner 仍按完成屏障串行等待，不改变 `turn_opened` / `battle_end` 的事件语义。

新文件与框架职责只有在实施时才同步写入 `Dian.md` 和源文件 `@framework`；本设计案不把尚未存在的实现声明为现行代码锚点。

## 7. 边界案例

以下属于框架建立后的边界案例，不应反向污染主流程：

- **重复提交**：同一 `expected_turn_seq` 第一次认领后状态已变为 `EXECUTING`，后续提交返回 `STALE_TURN`。
- **旧页面提交**：页面持有旧 `turn_seq`，即使仍是同一玩家和同一战场也必须拒绝。
- **回合开放时行动者失效**：start-of-turn 效果导致死亡、逃离或失去行动资格时，不进入 `AWAITING_INPUT` / `AUTO_PENDING`，不播放普通回合横幅，直接关闭并选择下一位。
- **开放回合时战斗结束**：没有下一候选者或只剩一方时直接进入 `IDLE` 并发射 `battle_end`。
- **轮次重建**：先完成 queue rebuild 和 `round_num` 递增，再开放新轮次第一回合；该回合仍是普通 `opening_kind='turn'`。
- **多个 NPC 连续行动**：每次都先生成独立 `turn_opened`，再由后续 tick 认领执行；批次可以不同，但 `turn_seq` 连续且稳定。
- **presentation 重复或乱序**：继续由 K-9 按 `batch_seq` 排序并按事件身份去重；不得按标题文本去重。
- **页面重连**：直接重基准到权威战斗状态，不补播已经错过的瞬态回合横幅。
- **首战预提交**：`battle.start` 的动作只能绑定新建的 `turn_seq=1`，不能复用为后续回合动作。
- **命令执行期间仍有演出播放**：现有 presentation 水位门控拒绝提交；后端 `expected_turn_seq` 校验作为最终防线。
- **一次刷新跨过完整 NPC 回合**：即使组件未观察到 `isPlayerTurn=false`，不同的 `qid + turn_seq` 仍会创建新的空装填会话。
- **成功响应后的重复点击**：同一权威回合在首个成功响应到达时立即关闭动作区并清空队列；后端原子认领继续作为最终防线。

## 8. 明确拒绝的局部修补

- 前端增加 `hasShownBattleStart`：只能遮住标题错误，刷新、重连、多战场和新会话仍会失真。
- 把判断改成“第一轮第一个已知 actor”：前端没有权威先攻边界，仍是在猜测领域事实。
- NPC 继续用 `turn_start`，玩家额外广播本地提示：会形成两套回合语义，后续 AP、状态效果和命令门控继续分叉。
- 在 `battle_manage_queue` 单独 emit 玩家横幅、在 `combat_dispatch` emit NPC 横幅：按角色类型分裂生命周期，无法支持自动战斗、托管或控制权切换。
- 仅把 `turnNum` 保存进 session/global：回合身份仍不属于战场事务，无法处理并发请求、多战场和重启恢复。

## 10. 验收矩阵

### 10.1 后端框架测试

- 两个独立 HTTP 请求依次开放同一战场的两个回合，得到 `turn_seq=1`、`turn_seq=2`，不会重置。
- 第一轮三个行动者的 `opening_kind` 依次为 `battle_start`、`turn`、`turn`。
- `turn_opened` 在 AP 恢复后发射，事件 actor 快照与 player projection 一致。
- 玩家回合开放后状态为 `AWAITING_INPUT`；提交前已经存在 `turn_opened`。
- 正确 `expected_turn_seq` 只能认领一次；旧序号、错误 PID、错误状态均失败。
- NPC 回合经过 `AUTO_PENDING -> EXECUTING`，不走玩家命令路径。
- round rebuild 后 `round_num` 增加而 `turn_seq` 继续单调递增。
- 请求回滚时状态推进与 `turn_opened` 同时消失，不留下半开放回合。

### 10.2 前端导演与投影测试

- 只有 `opening_kind='battle_start'` 显示“战斗开始”。
- 第一轮第二、第三行动者均显示“第 1 轮”。
- `turn_opened` 与动作事件分属不同 batch 时仍只生成一个 `turn_intro`。
- 玩家提交后不再播放同一 `turn_key` 的回合横幅。
- `battle_end` 只由显式事件生成，权威状态变化本身不会合成终局演出。
- 即使权威状态已经进入结束态，`battle_end` 播放计划完成前演出组件和 session 仍保持有效。
- 重复 `event_uid` 和重复 batch 不会重复播放。
- presentation gap 或重连后直接重基准，不补播缺失横幅。
- presentation scene 非 `idle` 时，现有命令门控继续拒绝战斗命令，无需回合专用 ready 状态。
- 玩家提交成功后动作区立即切换为等待显示，旧队列不会跨越到下一 `turn_seq`；投影刷新尚未到达时也不能再次提交同一回合。

### 10.3 端到端场景

- 玩家首攻：提交交战意图后播放“战斗开始 / 你的回合”，随后播放动作。
- NPC 首攻：播放“战斗开始 / NPC 的回合”，随后播放 NPC 动作。
- NPC 转玩家：控制权交接产生“第 N 轮 / 你的回合”，装填区由权威玩家回合状态驱动。
- 玩家转 NPC：玩家动作结束后播放“第 N 轮 / NPC 的回合”，随后播放 NPC 动作。
- 多 NPC 连续回合、跨轮重排和重复提交均保持同一权威回合身份；刷新页面只恢复当前状态，不补播瞬态演出。

## 11. 完成标准

本重构只有同时满足以下条件才视为完成：

- 回合身份由 `oblbattle_state.turn_seq` 权威持久化，任何请求级对象都不再生成回合编号。
- 回合开放与动作执行是两个明确状态边界。
- 横幅只由 `turn_opened` 投影，终局演出只由 `battle_end` 投影，前端不根据状态猜测或补建演出。
- 玩家回合 UI 只消费权威状态；演出期间的提交限制复用现有 presentation 水位门控。
- 命令携带并校验 `expected_turn_seq`。
- 跨请求、跨 batch、重连重基准和重复提交测试通过。
- 相关框架文档、文件头标签和严格双向锚点校验全部通过。
