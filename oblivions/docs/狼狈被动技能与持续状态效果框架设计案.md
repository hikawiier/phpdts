# 狼狈被动技能与持续状态效果框架设计案

> 状态：审查修订与实施完成  
> 日期：2026-07-11  
> 关联文档：[战斗演出事件消费与权威投影解耦研判.md](./战斗演出事件消费与权威投影解耦研判.md) §12.4  
> 适用范围：Oblivions 后端、vex-vue 前端、新战斗 effect/preview/presentation 管道

## 0. 审查修订约束

本节是实施时的最高优先级约束；后文若仍保留旧措辞，以本节为准。

1. **配置真值源**：`skill_definition_config.php` 只承载身份、类别、生命周期、可见性、stacking 和 capability 规则；`combat_skill_config.php` 是 AP、CD、射程、伤害、finisher 与 Aim/Capture/Execution 的唯一真值源。新增 `skill_get_definition()`，主动机制调用方全部迁移到 `combat_skill_get_config()`，旧 `skill_config.php` 和旧读取 API 在迁移完成后删除。`skill_get_available_list()` 只返回存在 combat config 且可装填的主动技能，effect-lifetime passive 只走 `statuses` 投影。
2. **实例激活真值源**：duration/stacking/capability 来自 definition；具体 activation boundary、boundary_id、delay 来自 effect operation，并经过 schema 校验。definition 不硬编码 `battle_disband_next_tick`。
3. **幂等与 stacking**：首版 effect skill 是 per-actor/per-skill singleton。相同 `instance_uid` 重放为 no-op；`refresh` 时 pending->pending 替换来源和 boundary，active->active 从 evaluation tick 刷新时长，active->pending 保持当前 active 到期并登记下一 pending，不能让已生效限制被意外取消。actor-scope effect 的 UID 由稳定 action operation key + actor pid + skill id 派生，不能因多目标迭代产生重复实例或演出。
4. **Capability 组合**：合法 capability 有集中 registry；unknown capability fail closed；provider 默认 allow、deny-wins、来源去重，provider 异常 fail closed 并记录错误。evaluator 只读 actor。内部 decision 可含完整来源，公开 projector 必须过滤 hidden status，必要时仅返回 opaque `status_blocked`。
5. **判定 Tick**：TickFrame 内 combat/world AI 使用当前 frame tick；mutation command gate 与 player-facing capability projection 使用“下一可行动 tick” `max(obl_tick, obl_pretick + 1)`。当存在未处理 tick 时仍判定该 pending frame，不能再额外跳一 tick。evaluator 必须接收显式 `evaluation_tick`。因此 qid 在 tick 13 解散后，存储实例仍是 starts=14/expires=15；tick 14 未处理或正在处理时按 14 阻断，tick 14 处理完成后下一命令按 15 恢复。
6. **生命周期传播**：boundary activation 返回 changed scopes，并通过 battle/combat/tick response 合并到统一 invalidation collector。`combat_queue_disband()`、正常 disband、queue-empty/stale-qid 和无 qid 出口都必须走同一 cleanup + boundary API，禁止直接清 bid/删队列绕过激活。
7. **GC 范围**：post GC 只扫描当前玩家与当前区域/本帧已加载 NPC，禁止每 tick 全表扫描。任何 evaluator/projector 都忽略已过期实例；离区 actor 只在后续可写领域上下文惰性持久清理，纯 state API 不写 DB。
8. **前端契约**：玩家/NPC 公开投影 pending 与 active；pending 显示“狼狈·待生效”、不限制能力，active 才显示剩余 tick。capabilities 返回首版完整集合，前端整体替换；缺键仅在体验层宽容为 allowed。多来源阻断返回过滤后的全部 status IDs，恢复 tick 取最大有效 expires 上界。
9. **等待出口**：`world.wait` 是 itm0 锁的明确例外，并在探索主界面提供不会被 itm0 modal/抽屉遮挡的常驻入口。即使 SP=0、无 POI、不可探索、itm0 非空，也必须可执行。
10. **拒绝与刷新**：`CAPABILITY_BLOCKED` 使用现有客户端可消费的 `changed_scopes`，不能另造 `refresh` 字段。gate failure response 必须保留 details、feedback 与 changed_scopes，并触发权威 `player_info` 刷新。
11. **Read-only**：command contract/registry 明确 `read_only`。`combat.can_engage` 不受 mutation capability gate并可返回结构化 capability failure；preview 仍要求合法战斗上下文。不得仅凭现有 `item.pickup` 等错误/历史 read_only 标记跳过 mutation capability，是否 mutation 以本轮修正后的 contract 为准。
12. **Presentation schema**：status operation 统一放在 `payload.detail`；target 必须带 combatant snapshot。`DirectedEffectV2` 保留 detail，status visual 为 none，文本从 snapshot 解析名称。apply pending 的文本使用“获得了狼狈，战斗结束后生效”，activation 才使用“陷入了狼狈”。
13. **原始 skillpara**：后端可继续持久保存 effect instance，但前端不得依赖 raw effect state。若 player_info 暂时仍返回 `skillpara`，TypeScript 类型必须扩展；状态 UI 与门控只读 `statuses/capabilities`。

## 1. 设计结论与共识

双方达成以下设计共识：

1. 当前 `post_combat_handoff_pending + world_ai_resume_tick` 是为解决战斗演出与世界 AI 连续性而临时引入的领域约束，不应成为长期的逃跑专用协议。
2. 逃跑的相邻格退避已经属于正确的技能 effect：`skill_escape_execute()` 声明 `escape`，`combat_effect_escape()` 负责选择退避落点并写入权威位置；这部分不回退、不搬回战斗主流程。
3. 长期方案是：玩家或 NPC 成功逃跑后，由 `escape` 技能施加一个 effect-lifetime 被动技能实例“狼狈”。
4. “狼狈”在 actor 真正脱离所属 qid 的 `battle_disband` 边界激活，覆盖首个可参与世界行为的 TickFrame，随后自然到期。
5. 战后 AI 冷却不再是独立技术补丁，而是“狼狈”对 `world_ai` 能力的正常限制结果。
6. “狼狈”不能通过在各 handler、AI 和 UI 中判断 `status_id` 实现；必须先建立通用的持续效果实例、生命周期和 capability evaluator。
7. 前端演出只展示“获得狼狈”的文字/状态变化，不负责修改或倒计时删除权威状态。

因此，本设计不是把 `world_ai_resume_tick` 改名为 `flustered`，而是补齐一个可供后续眩晕、束缚、沉默、流血等机制复用的框架基准。

## 2. 当前代码事实

### 2.1 已经正确的部分

- `oblivions/gamedata/combat_skills/skill_escape.php` 只声明 `escape` effect。
- `oblivions/include/game/combat/combat.effect.php` 的 `combat_effect_escape()`：
  - 选择确定性的相邻退避落点；
  - 更新 actor 的 `pls`；
  - 更新 NPC discovered；
  - 写入本场战斗的 `escaped` mutation；
  - emit `retreat_target` 和 visual policy。
- `combat.effect_projector.php` 已为 dry-run/preview 提供 `escape` 投影。

逃跑的空间结果已经属于技能效果，不是需要迁移的硬编码。

### 2.2 临时协议

当前连续性约束分散在三个位置：

```text
combat_state_clear(reason=escaped)
  -> oblpara.post_combat_handoff_pending = true

battle_disband_cleanup(qid)
  -> world_ai_resume_tick = current_tick + 1

obl_actor_world_ai_block_reason()
  -> current_tick <= world_ai_resume_tick 时拒绝 world AI
```

主要问题：

- battle cleanup 直接认识 escape 专用状态。
- world AI 直接认识 escape 专用字段。
- 玩家逃跑也会写入该字段，但当前只有 NPC world AI 会消费，玩家字段可能长期残留。
- 状态没有统一名称、来源、生命周期、叠加规则和前端投影。
- 无法复用于其他限制移动或战斗的效果。
- `escape_skip_tick` 仍有消费者和旧文档说明，但当前代码没有可靠写入点，属于应清理的遗留协议。

### 2.3 已有可复用基础

- `skillpara` 是玩家与 NPC 共用的技能状态 JSON，已有统一 format/save。
- `skill_config.php` 已预留 `lifetime = permanent | equipment | effect`。
- `skill_strip_temporary()` 明确保留 effect-lifetime 技能，但目前没有真实 effect 实例和到期处理。
- TickFrame 已有 `combat_domain -> world_ai_domain -> post_domain`。
- combat effect 已有 applier/projector 注册表和 FIFO 应用顺序。
- Command Bus 与前端 command registry 都有集中式命令 contract。
- combat participation 已有 `member/joinable/left/other_battle/blocked`，适合接入能力判定。
- 前端 Director 已承认 `status` effect 类型，但尚无正式文本和状态投影。

## 3. 目标与非目标

### 3.1 目标

- 实现 effect-lifetime 被动技能实例框架。
- 支持 pending、active、expired 三段生命周期。
- 支持在领域边界激活，而不只支持“施加时立即激活”。
- 用统一 capability evaluator 约束玩家命令、NPC AI、战斗入口和战斗行动。
- 让 escape 技能显式施加“狼狈”。
- 删除逃跑专用的战后 AI 冷却字段和判断。
- 提供权威状态投影、前端状态展示和结构化拒绝反馈。
- 保证 F5 后只从权威状态恢复，不重播历史状态演出。

### 3.2 非目标

- 本轮不实现通用数值 modifier 计算，例如攻击力降低、速度降低或持续伤害。
- 本轮不实现任意复杂触发器、光环、驱散、免疫或状态抗性。
- 本轮不允许前端自行计算状态到期。
- 本轮不把 PresentationBatch 当作状态真值源。
- 本轮不保留旧 `world_ai_resume_tick` 协议的兼容层或数据迁移。

## 4. 术语与框架边界

### 4.1 技能定义

`SkillDefinition` 描述一个永久技能、装备技能或 effect-lifetime 被动技能的静态规则。

现有 `gamedata/skill_config.php` 虽然包含 `lifetime` 预留，但文件已经标记 deprecated，不能成为新框架的长期真值源。新增 `oblivions/gamedata/skill_definition_config.php`，承载技能身份、类别、生命周期、可见性和叠加规则；`combat_skill_config.php` 独占 AP、CD、射程、伤害及 Aim/Capture/Execution 主动机制。

“狼狈”是一个被动技能定义，不是玩家主动装填的 combat action：

```php
'flustered' => array(
    'category'       => 'passive',
    'lifetime'       => 'effect',
    'hidden'         => false,
    'stacking'       => 'refresh',
    'duration_ticks' => 1,
    'capability_denies' => array(
        'world_ai',
        'voluntary_move',
        'enter_combat',
        'participate_combat',
        'combat_action',
        'free_mutation',
    ),
)
```

静态定义放在 `oblivions/gamedata/skill_definition_config.php`。主动技能通过相同 skill ID 关联 `combat_skill_config.php` 的机制配置；不得为了让“狼狈”进入 UI 而伪造一套无意义的 combat pipeline 配置。现有主动机制调用方改读 `combat_skill_config.php`，定义调用方改读 `skill_get_definition()`；旧 `skill_config.php` 与旧读取 API 在调用方迁移完成后删除。

### 4.2 效果实例

`EffectSkillInstance` 是 `skillpara` 中的运行时事实。推荐结构：

```json
{
  "flustered": {
    "lstact": 0,
    "effect_instances": {
      "fx-61-14-207": {
        "instance_uid": "fx-61-14-207",
        "state": "pending",
        "source": {
          "kind": "skill",
          "skill_id": "escape",
          "action_uid": "q61-t14-a2"
        },
        "activation": {
          "boundary": "battle_disband",
          "boundary_id": 61,
          "delay_ticks": 1
        },
        "duration_ticks": 1,
        "applied_tick": 14,
        "starts_at_tick": null,
        "expires_at_tick": null,
        "stacks": 1
      }
    }
  }
}
```

约束：

- `instance_uid` 在一次 action 内稳定，用于日志、投影和幂等。
- `state` 只允许 `pending | active`；expired 实例由 GC 删除，不持久保存墓碑。
- `expires_at_tick` 为排他上界：`current_tick < expires_at_tick` 才有效。
- `stacking=refresh` 表示同 actor 的同一 status 再次施加时替换来源并刷新生命周期，不增加层数。
- pending 实例不会限制能力，只有 active 实例参与 capability 聚合。
- `skillpara` 顶层仍以 skill ID 为 key，符合现有“一切皆技能”和 `lifetime=effect` 预留。

### 4.3 Capability

Capability 是 actor 是否可以执行某类领域行为的统一判定，不等于前端按钮名。

首版能力集合：

| Capability | 含义 |
|---|---|
| `world_ai` | NPC 是否可以执行世界 AI |
| `voluntary_move` | actor 是否可以主动改变世界位置 |
| `enter_combat` | actor 是否可以主动发起战斗 |
| `participate_combat` | actor 是否可以被纳入新战场或动态参战 |
| `combat_action` | actor 是否可以在现有战场主动执行技能 |
| `free_mutation` | actor 是否可以执行不推进时间的状态修改命令 |
| `time_pass` | actor 是否可以执行用于消耗时间的恢复动作 |

强制位移不检查 `voluntary_move`。逃跑退避、击退、传送等 effect 必须继续可以修改位置，否则“狼狈阻止移动”会反向阻断施加它的逃跑动作。

## 5. “狼狈”的最终游戏语义

### 5.1 施加条件

- 玩家和 NPC 成功结算 `escape` effect 后都获得一个 pending “狼狈”实例。
- effect 失败、action 回滚或 target SAVEPOINT 回滚时，实例不得留下。
- 死亡不是逃跑，不获得“狼狈”。
- 普通战斗胜利幸存者不获得“狼狈”。

### 5.2 激活边界

逃跑 actor 可能提前离场，而原 qid 继续战斗多个 tick，因此不能在 escape effect 执行时直接开始倒计时。

```text
escape effect at tick T0
  -> flustered pending(boundary=battle_disband, qid=Q)

Q disband at tick T1
  -> starts_at_tick = T1 + 1
  -> expires_at_tick = starts_at_tick + 1

first eligible post-battle TickFrame
  -> flustered active

current_tick >= expires_at_tick
  -> flustered expired and GC
```

若 qid 在 tick 13 解散：

```text
starts_at_tick  = 14
expires_at_tick = 15
```

它只在 tick 14 有效。tick 13 的同帧重复行动已经由 BattleActorScope 防止；tick 14 的 world AI、移动和战斗被“狼狈”阻止；tick 15 恢复。

### 5.3 受限行为

active “狼狈”拒绝：

- NPC world AI；
- 玩家/NPC 主动移动；
- 主动发起战斗；
- 被纳入新战斗或动态参战；
- 在战斗中执行主动技能；
- 不推进时间的持久状态修改命令。

### 5.4 允许行为

active “狼狈”允许：

- `map.explore`；
- `poi.search`；
- 新增的 `world.wait`；
- 纯读请求和纯前端界面操作；
- heartbeat、权威刷新和演出消费。

玩家执行任一合法推进时间的动作后，tick 推进到到期边界，下一次权威刷新移除“狼狈”。

本设计采用用户提案的严格语义：会修改持久状态但不推进时间的 item/inventory/craft 命令也被阻止；纯读请求和本地打开抽屉不受影响。若后续产品判断希望狼狈期间仍可整理背包，只需从状态配置的 `capability_denies` 移除 `free_mutation`，不得修改 Command Bus 特判。

### 5.5 防软锁命令 `world.wait`

不能假设玩家始终有足够 SP、可搜索 POI 或合法 explore 动作。必须提供一个零资源、无目标、只推进时间的保底命令：

```php
'world.wait' => array(
    'allowed_actions' => array('', null),
    'advances_tick' => true,
    'itm0_allowed' => true,
    'required_capabilities' => array('time_pass'),
    'command_tags' => array('recovery_time_action'),
    'refresh' => array('player_info', 'enemies', 'game_map', 'obl_log'),
)
```

`world.wait` 不移动、不探索、不恢复额外资源，只 emit `wait.success` 并推进一个 tick。任何未来会限制玩家常规操作的持续状态，都必须保留至少一个可执行的时间推进出口。

## 6. 后端模块设计

新增目录：

```text
oblivions/include/game/skill_effect/
  skill_effect.main.php
  skill_effect.lifecycle.php
  skill_effect.projector.php

oblivions/include/game/actor/
  actor.capability.php
```

职责：

| 文件 | 职责 |
|---|---|
| `skill_effect.main.php` | 实例格式化、创建、刷新、查询、删除 |
| `skill_effect.lifecycle.php` | 领域边界激活、tick 有效性、post GC |
| `skill_effect.projector.php` | API 状态投影、capability 投影、公开可见性过滤 |
| `actor.capability.php` | capability provider 注册表与统一决策；持续技能、装备、地形都可贡献规则 |

`actor.capability.php` 不得依赖具体 `flustered` 或 skill ID。`skill_effect` 模块在 bootstrap 时向 capability registry 注册 provider；Command Bus、AI 和 combat 只调用 actor capability API。

### 6.1 核心接口

```php
skill_effect_apply(
    array &$actor,
    string $skill_id,
    array $source,
    array $activation,
    ?string $instance_uid = null
): array;

skill_effect_activate_boundary(
    array &$actor,
    string $boundary,
    int $boundary_id,
    int $current_tick
): array;

skill_effect_is_active(array $instance, int $current_tick): bool;

skill_effect_gc(array &$actor, int $current_tick): bool;

actor_capability_decide(
    array $actor,
    string $capability,
    ?array $context = null,
    ?int $evaluation_tick = null
): array;

actor_capability_register_provider(string $provider_id, callable $provider): void;
```

Capability decision：

```php
array(
    'allowed' => false,
    'capability' => 'voluntary_move',
    'reason' => 'status_blocked',
    'sources' => array(
        array(
            'skill_id' => 'flustered',
            'instance_uid' => 'fx-61-14-207',
            'expires_at_tick' => 15,
        ),
    ),
)
```

调用方不得自行遍历 `skillpara` 或判断 `flustered`。

### 6.2 format/save

调整 `skill_format_skillpara()`：

- 保留现有永久/装备技能格式。
- 对 `lifetime=effect` 技能规范化 `effect_instances`。
- 丢弃结构非法、skill config 不存在或 instance UID 为空的实例，并记录错误日志。
- 不在 format 阶段按本地时间删除实例；有效性只认权威 tick。

`skill_strip_temporary()`：

- equipment 技能继续在 save copy 中剥离。
- effect 技能只有在 `effect_instances` 为空时删除整个 skill key。
- active/pending effect 实例必须持久保存。

## 7. Combat Effect 接入

### 7.1 通用 effect 类型

新增：

```text
effect type: skill_effect_apply
```

payload：

```php
array(
    'skill_id' => 'flustered',
    'scope' => 'actor',
    'activation' => array(
        'boundary' => 'battle_disband',
        'boundary_id' => $ctx->qid,
        'delay_ticks' => 1,
    ),
)
```

必须同时注册：

- execute applier：真实写入 actor `skillpara`；
- planned-state projector：在 dry-run actor state 上创建相同 pending 实例；
- v2 log：emit `effect_type=status`，detail 包含 operation、skill_id、instance_uid、state。

### 7.2 Escape 技能

`skill_escape_execute()` 改为按顺序声明：

```php
$ctx->declareEffect('escape', array());
$ctx->declareEffect('skill_effect_apply', array(
    'skill_id' => 'flustered',
    'scope' => 'actor',
    'activation' => array(
        'boundary' => 'battle_disband',
        'boundary_id' => $ctx->qid,
        'delay_ticks' => 1,
    ),
));
```

约束：

- `escape` 继续只负责空间退避和 escaped mutation。
- `skill_effect_apply` 只负责状态实例。
- 两者属于同一 action transaction；后一个发生致命错误时，target unit SAVEPOINT/外层事务必须回滚前一个 effect 的持久写入。
- preview 必须同时展示退避结果和 pending “狼狈”，不得只投影其中之一。
- 当前 `combatant_cleared` 不能继续用 `v2_effect_uids` 的最后一项关联 escape。追加 `skill_effect_apply` 后，最后一项会变成状态 effect。TargetResolutionUnit 必须按 `effect_type='escape'` 保存/查找 `escape_effect_uid`，清理事件显式引用该 UID。

## 8. 生命周期与 TickFrame

### 8.1 Battle disband

`battle_disband_cleanup()` 不再调用 escape 专用函数，统一调用：

```php
skill_effect_activate_boundary(
    $actor,
    'battle_disband',
    $qid,
    obl_tick_get()
);
```

该函数只激活匹配 boundary + boundary_id 的 pending 实例。其他 qid 的 pending 实例不得被误激活。

正常 disband、queue-empty/stale-qid 兜底出口和 `combat_queue_disband()` 都必须调用同一个 cleanup + boundary API。无 qid 的 escape 使用 immediate boundary：在退出清理完成时计算下一 TickFrame 的 starts/expires tick，不能留下永久 pending 实例。

### 8.2 World AI

`obl_actor_world_ai_block_reason()` 删除 `world_ai_resume_tick` 分支，改为：

```php
$decision = actor_capability_decide($actor, 'world_ai', $ctx);
if (!$decision['allowed']) return 'capability:' . $decision['reason'];
```

BattleActorScope、`action='battle'`、`bid>0` 和 ActorBehaviorLedger 仍保留，它们解决的是 TickFrame 归属和单帧单行为，不由状态系统取代。

### 8.3 Post GC

在 `post_domain` 注册 effect GC listener：

- 只删除 `current_tick >= expires_at_tick` 的 active 实例。
- pending 实例不按普通 tick 过期；它等待明确 boundary。
- 若 boundary 所属 qid 被异常清理，battle cleanup 的兜底分支也必须触发同一 boundary。
- GC 修改 player/NPC 时必须走 `obl_save_player()`，并把对应权威 scope 标记为 changed。

加载顺序必须避免 listener 被重置：`tick.func.php` 当前会初始化全局 listener 表，因此先加载 skill-effect 核心定义，再由 bootstrap 在 tick registry 初始化完成后显式调用 `skill_effect_register_tick_listener()`。

GC 只负责存储清理。任何能力检查在读到已过期实例时都必须视为无效，不能依赖 GC 已经运行。

## 10. 战斗入口与参战约束

“不能战斗”在本设计中定义为：active “狼狈”既不能主动发起战斗，也不能成为新战场或动态参战的参与者。

需要四层一致性：

1. `battle.start` actor gate 检查 `enter_combat`。
2. `combat_can_engage()` 返回 actor/target capability failure。
3. initial roster 与 `combat.participation.php` 在返回 `joinable` 前检查目标 `participate_combat`；失败时返回 `blocked`。
4. combat pipeline actor verify 检查 `combat_action`，作为异常并发或错误状态下的最终兜底。

NPC 因“狼狈”不能被玩家立刻重新拉回战斗。这与“战后 AI 冷却”的视觉目标一致，也让状态具备玩家可理解的游戏规则。

## 12. 前端设计

### 12.1 类型与 Store

- 不弹额外模态框，不添加地图全屏遮罩。
- 前端可显示 remaining tick，但不得自行删除状态；只在新的权威 `player_info` 到达后移除。

## 17. 验收场景

### 场景 A：NPC 逃跑

1. 玩家与 NPC 战斗。
2. NPC 使用 escape，退避到相邻格并退出战斗。
3. 战斗结束遮罩下完成 PresentationScene handoff。
4. 首个战后 tick 中 NPC 不巡逻、不重新参战。
5. 下一 tick NPC 恢复普通 AI。

预期：视觉上只看到一次逃跑退避；领域上原因是 NPC 处于“狼狈”，而不是 world AI 识别 escape 专用字段。

### 场景 B：玩家逃跑

1. 玩家使用 escape 并结束战斗。
2. player_info 显示 `狼狈 1T`。
3. 地图移动、战斗按钮、敌人点击和即时状态修改不可用。
4. 探索、搜索、等待可用。
5. 玩家执行等待，推进一个 tick。
6. 权威刷新移除“狼狈”，全部正常能力同时恢复。

### 场景 C：提前逃跑但战斗继续

1. 三方战斗中某 NPC 在 tick 10 逃跑。
2. 其他 actor 战斗持续到 tick 14。
3. qid 在 tick 14 解散。
4. 狼狈只在 tick 15 有效，不能在 tick 11 提前到期。

### 场景 D：直接 API 绕过 UI

1. 玩家处于 active 狼狈。
2. 直接请求 `map.move` 或 `battle.start`。
3. Command Bus 返回 `CAPABILITY_BLOCKED`。
4. 不推进 tick、不修改位置、不创建战场。

## 18. 最终架构关系

```text
escape skill
  -> escape effect
       -> retreat target / escaped mutation / presentation
  -> skill_effect_apply(flustered, pending@battle_disband)

battle lifecycle
  -> boundary: battle_disband(qid)
       -> activate matching effect instances

active effect-lifetime skills
  -> capability evaluator
       -> Command Bus
       -> combat entry / participation / actor verify
       -> NPC world AI
       -> API capability projection

authoritative statuses/capabilities
  -> player_info / enemies / combat_targets
       -> commandQueue / StatusBar / PlayerDrawer

PresentationBatch status event
  -> text only
  -> never mutates authoritative status
```

这使“逃跑后休整一 tick”同时具备游戏规则、领域事实、前端解释和演出表达；战后 AI 冷却由通用规则自然产生，不再需要系统层面的逃跑专用补偿。
