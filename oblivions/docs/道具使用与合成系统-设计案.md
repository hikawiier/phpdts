# Oblivions 道具系统设计案（Tag + 使用 + 合成）

> 道具 Tag 系统、道具使用、道具合成三者是一体的，作为一个方案内解决。
> 本案整合 [合成系统设计讨论记录](./合成系统设计讨论记录.md) 的核心方案、[第一幕-庇护所与新手区资源案](./第一幕-庇护所与新手区资源案.md) 的 Tag 体系、[框架优先级推导表](./框架优先级推导表.md) 的资源层准备清单。
>
> 完成后玩家可体验完整核心循环：捡素材 → 在工作台放素材合成 → 道具入背包 → 使用道具（应用效果）→ 效果驱动新的合成需求。

---

## 一、设计目标与范围

### 1.1 设计目标

| 目标 | 实现方式 |
|------|---------|
| 道具有"性质描述 Tag" | 新增 `item_table.tags` 字段，描述 itmk 无法表达的物理性质（锐器、可燃物等） |
| 玩家能"使用"背包道具 | 新增 `obl_use_item` 命令 + use_effect 分发框架 |
| 玩家能合成新道具 | 新增 `obl_craft` 命令 + 配方表 + 工作台 POI |
| 工作台是"确认函"不是"搜索引擎" | 放素材→判断指向性→亮灯，不展示完整配方清单 |
| 工作台就是素材 | 工作台/工具是 `materials` 里 `consume='none'` 的素材，不做独立过滤维度 |
| 合成有软锁分批显示 | `item_recipe_visibility_filter` 按**全局事件状态**分批显示已发现配方（详见 §2.5.3），不拦截合成本身 |
| 素材匹配支持三维度 | 配方 `materials` 支持 `item_id`（精确）/ `itmk`（类别）/ `tag`（性质）三种形式 |

### 1.2 范围边界

**在本案范围内**：
- item_table.tags 字段（数据层，性质描述 Tag）
- recipe_table 配方表（数据层，支持 item_id / itmk / tag 三种素材形式）
- 工作台 POI（载体，`mechanic_value` 存储 `item_id` 指向工作台道具）+ 工作台素材模型（详见 §2.3）
- obl_use_item 命令 + use_effect 分发框架（消费层，纯框架不预定义效果）
- obl_craft 命令 + 工作台确认函机制（生产层）
- 合成/使用的后端 API 与数据结构
- 前端 API 端点、TS 类型、store 接口约定

**不在本案范围内**（归属其他系统）：
- 猫在合成循环中的提醒 → 对话系统/教程系统（通过订阅 `craft.success` 等事件介入）
- 食物经验系统 → 独立设计案（通过注册 `item_use_effect_restore_sp` 等函数介入 use_effect 框架）
- Body Status Tag 联动 → 健康系统（通过注册 `item_use_effect_cure_bs` 函数介入 use_effect 框架）
- 抗性跃迁 → 被动技能系统（通过注册 `item_use_effect_gain_resistance` 函数介入）
- 鉴定系统 → 独立设计案
- 猫背包系统 → 独立设计案
- 工作台升级 → 猫背包系统 / 庇护所升级系统
- 前端合成 UI 具体设计（CraftModal 的展示形式、是否显示已发现配方列表等）→ 前端独立模块设计案
- 系统钩子 Tag（`tag_equippable` / `tag_poi_interactive`）→ 见《道具-系统钩子Tag设计案.md》

### 1.3 流程函数的介入点设计原则

本案不为未实现的系统预留通用 hook（如 `do_action('after_craft')`）。而是在设计每个流程函数时，明确"哪个节点是其他系统介入的合适位置"，通过 **emit 结构化事件** 让其他系统订阅消费：

- `obl_use_item` 在应用效果后 emit `use_item.success` → 食物经验系统/健康系统自行订阅
- `obl_craft` 在合成完成后 emit `craft.success` → 对话系统自行订阅触发猫提醒
- use_effect 框架本身支持任意系统注册 `item_use_effect_{name}()` 函数 → 健康系统注册 `cure_bs`、食物经验系统注册 `restore_sp` 等

**关键区分**：本案定义事件 ID 和 use_effect 函数命名约定，但不实现具体效果函数。其他系统在自己的设计案里实现并注册。

### 1.4 文案分离

遵循 [DESIGN.md §2.19 道具数据三层分离](../DESIGN.md)：所有配置文件（`recipe_table.php` 等）不含 name/desc。`item_table.php` / `poi_table.php` 的 itm/desc 字段标记为 deprecated，新代码不依赖。前端通过 `item-locale.ts` / `recipe-locale.ts` / `poi-locale.ts` 查询文案。

### 1.5 前端模块独立

本案只定义前端需要的 API 端点、TS 类型、store 接口约定。前端合成 UI（CraftModal 等）的具体设计——是否显示已发现配方列表、配方列表的展示形式、灰亮区分策略等——独立成前端设计案，本案不约束。

## 二、核心概念

### 2.1 道具 Tag 系统

每个道具有一组**性质描述 Tag**，描述 itmk 无法表达的物理性质或使用形态。Tag 主要服务于合成系统的"大类素材"匹配。

**为什么不用 itmk 替代所有 Tag**：
- `itmk` 天然描述道具大类（武器 WP / 防具 AR / 食物 HH / 素材 MT / 工具 TK 等），适合"任何某类道具"的匹配（如"任何金属"→ `itmk='MT'`）
- 但 itmk 无法表达跨类别的物理性质（如"锐器"可能跨武器 WK 和素材 MT；"可燃物"可能跨素材 MT 和消耗品 HH）
- 因此性质描述 Tag 只定义 itmk 无法覆盖的物理性质，避免与 itmk 冗余

**Tag 的消费方**：

| Tag 类别 | 消费方 | 示例 |
|---------|--------|------|
| 性质描述 Tag（§2.2） | 合成系统：配方的 `materials` 用性质描述 Tag 作为"大类素材" | `tag_sharp` 匹配所有锐器 |
| 系统钩子 Tag | 装备系统：`tag_equippable` 判断可装备 | 撬棍可装备当武器 |
| 系统钩子 Tag | 道具使用系统：`tag_usable` 判断可使用（`use_effect` 记录具体效果） | 面包可使用恢复 SP |
| 系统钩子 Tag | 地图交互系统：`tag_poi_interactive` 判断可与 POI 互动 | 撬棍可撬门 |
| 两类 Tag | 鉴定系统（后续）：未鉴定道具的真实 Tag 决定性质 | — |

> 系统钩子 Tag 的定义见《道具-系统钩子Tag设计案.md》。两类 Tag 存储在同一个 `item_table.tags` 字段中。

### 2.2 Tag 列表

本案只定义配方实际使用的性质描述 Tag。后续系统需要的新 Tag 由各系统自行设计案定义。

| Tag ID | 名称 | 用途 | 典型道具 |
|--------|------|------|---------|
| `tag_sharp` | 锐器 | 裁剪、切割类配方的素材大类 | 刀片碎片、布包刀刃 |
| `tag_combustible` | 可燃物 | 火把、燃料类配方的素材大类 | 布 |
| `tag_raw_food` | 生食材 | 烹饪类配方的素材大类 | 生兔肉、沼泽草药 |
| `tag_tool_cooking` | 烹饪器具 | 配方 `materials` 中作为烹饪工具类素材（配合 `min_level` 使用，详见 §2.7） | 煎锅、精密炉灶 |
| `tag_forge` | 锻造器具 | 配方 `materials` 中作为锻造工具类素材（配合 `min_level` 使用） | 铁砧 |

**性质描述 Tag 的设计原则**：
- 描述道具的"物理属性"或"使用形态"，不描述 itmk 已表达的大类身份
- 同一道具可拥有多个性质描述 Tag（如煎锅：`tag_tool_cooking`）
- 性质描述 Tag 主要用于合成系统的"大类素材"匹配，让配方不必穷举所有 item_id

### 2.3 合成入口与工作台素材

合成是全局可访问的功能。玩家随时点击合成按钮进入合成界面，把素材放入素材池。

**素材池的两类素材**：

| 类型 | 来源 | 占背包 | consume 限制 |
|------|------|--------|-------------|
| **背包素材** | 玩家背包槽位 | ✅ | `all` / `durability` / `none` |
| **工作台素材** | POI / 猫 / 被动技能 | ❌ | 只能 `none`（不消耗） |

**工作台素材的三种来源**：

| 来源 | 标识 | 可用条件 |
|------|------|---------|
| **被动技能** | `passive` | 永久可用（玩家自带的基础合成能力） |
| **猫身上** | `cat` | 猫在身边时可用（便携工作站） |
| **地图格 POI** | `poi` | **玩家必须站在工作台 POI 上** |

**核心观念**：工作台就是素材。一碗饭 = 米 + 水 + 锅——锅跟米、水没有本质区别，唯一的区别是锅不消耗（`consume='none'`）。工作台不需要"选择"或"过滤配方"这样的独立步骤，直接放入素材池参与匹配。

**工作台素材的实时计算**：
- 不存储在 `oblpara`，每次进入合成界面时实时计算
- 计算函数 `item_get_available_workbench_materials(&$pdata)` 返回 `[{source, id, item_id, tool_level}]` 列表
- `item_id` 关联到 `item_table` 查询 `tags`、`itmk` 和 `tool_level`，与背包素材统一匹配
- 前端把这些工作台素材列在素材池候选区，玩家选择后放入素材池

**为什么这样设计**：
- 统一模型——所有合成输入都是素材，不需要"工作台选择"独立步骤
- 工作台素材不占背包槽位——大型工作台（炉灶、铁砧、精密机床）不能塞进背包
- 背包工具（如锅）也可以当工作台素材用——只要配方需要，锅可以从背包放入素材池
- 玩家站在工作台 POI 上时，该工作台自动加入可用工作台素材列表

### 2.4 合成是"确认函"

合成的核心交互模式是"确认函"——玩家放素材到素材池（背包素材 + 工作台素材），系统判断"这个组合能不能出东西"，能就亮合成按钮，不能就灰着。

**核心规则**：
- **不放东西在素材池里，什么都看不到**
- **没有完整配方清单**——不主动展示所有可合成配方（软锁的体现，详见 §2.5）
- **素材无数量限制**——玩家想放多少放多少，没有"槽位"概念，只有"素材池"
- **指向性判断**：遍历配方表，找哪些配方的 materials 完全匹配当前素材池的素材组合
  - 0 个匹配 → 不亮
  - 1 个匹配 → 亮灯，显示合成按钮（不显示产物名称，保持探索感）
  - 2+ 个匹配 → 不亮（指向性不明确，玩家需放更多/调整组合）
  - **多放素材也不亮**——所有放置的素材必须都被配方消耗，多放一个不相关的素材会导致 0 匹配（详见 §5.5.7 第 5 步）
- 猫不在合成界面中出现（她的提醒由对话系统在 `craft.success` 事件后自行触发）

**匹配规则**（背包素材和工作台素材统一匹配）：
- 具体 `item_id` 素材：素材的 item_id 必须精确匹配
- `itmk` 素材：素材的 itmk 必须匹配（如 `itmk='MT'` 匹配所有金属类素材）
- `tag` 素材：素材只要拥有该 Tag 即可匹配
- `min_level` 检查：如果配方 material 指定了 `min_level`，素材的 `tool_level` 必须 ≥ `min_level`（高级工具兼容低级配方）
- `consume` 约束：工作台素材只能匹配 `consume='none'` 的 material 槽位（不能被消耗）
- 匹配优先级：`item_id` > `itmk` > `tag`（精确匹配优先，避免同一素材被重复计数）
- 匹配算法详见 §5.5.2 `item_match_recipes_by_slots`

**示例**：
- `cloth × 3` → 唯一指向绷带（亮）
- `cloth × 2` → 多个配方匹配（不亮，指向不明确）
- `[tag_sharp] + cloth × 1` → 任何锐器 + 1 布 → 唯一指向布包刀刃（亮）
- `[tag_tool_cooking, min_level=1] + roasted_rabbit × 1 + [tag_raw_food] × 2` → 任何 ≥1 级烹饪工具 + 烤兔肉 + 2 生食材 → 唯一指向简易炖菜（亮）

**前端展示形式**：由前端独立模块设计案决定。本案只提供 `craft_preview` API 返回 `match_count` + `craftable`，不约束 UI 如何呈现。

### 2.5 配方分批显示（软锁）

#### 2.5.1 软锁的本质：显示控制，不是合成拦截

**关键区分**：软锁控制的是"已发现配方列表"的显示范围，不是合成的可行性。

| 维度 | 软锁控制 | 软锁不控制 |
|------|---------|----------|
| 已发现配方列表的显示 | ✅ 通过 `item_recipe_visibility_filter` 按**全局事件状态**分批显示 | — |
| "放素材试组合"的合成 | — | ✅ 任何配方都能试，即使配方尚未在列表中显示 |

**这意味着**：
- 玩家在游戏前期用素材试出了后期配方 → **合成成功**，配方被发现加入 `discovered_recipes`
- 但该配方在"已发现配方列表"中不显示（全局事件未触发，软锁隐藏）
- 玩家推进剧情/触发全局事件后，该配方在列表中显示
- 这符合"软锁避免信息爆炸"的理念——列表不爆炸，但探索不被拦截

#### 2.5.2 已发现配方记录

`oblpara.discovered_recipes` 数组记录玩家已发现的配方 ID：

```json
{
  "discovered_recipes": ["craft_bandage", "craft_roasted_rabbit", "craft_simple_stew"]
}
```

**配方的"发现"途径**：
- 玩家"放素材试组合"合成成功 → 自动加入 `discovered_recipes`
- 猫提醒/教程引导（对话系统未来实现）
- 剧情事件触发（后续）

**配方的"显示"逻辑**（前端）：
1. 读取 `oblpara.discovered_recipes`（已发现配方）
2. 调用 `item_recipe_visibility_filter($recipe, $pdata)` 判断每个配方是否可见
3. 显示过滤后的列表，供玩家快速调用

**配方的"合成"逻辑**（后端）：
- `obl_craft` 命令**不做配方显示过滤检查**
- 只做"素材是否匹配某个配方"的判断
- 匹配就合成成功，不管配方是否在列表中显示
- 如果合成的是未发现配方 → 加入 `discovered_recipes` + emit `craft.new_recipe_discovered` 事件

#### 2.5.3 软锁的价值

软锁解决的是"信息爆炸"问题，不是"能力限制"问题：
- 玩家一开始只看到第 1 批配方（3-5 个，不爆炸）
- 触发全局事件后，第 2 批配方在列表中显示（8-10 个，仍然可控）
- 但玩家随时可以"放素材试组合"——探索不被拦截
- 这让"推进游戏进度"的价值是"列表更丰富"，不是"解锁合成权限"

**升级路径不是线性的**——前期配方在后期仍然有用（回头研究旧素材）。

**过滤依据的演进**：`item_recipe_visibility_filter` 是一个可替换的过滤接口。P0 默认返回 true（所有已发现配方都可见）。后续设计案确定过滤依据（全局事件/剧情节点/玩家进度等）后，只需替换此函数的实现。

### 2.6 use_effect 分发框架

道具的"使用"行为通过效果函数分发，模式与 POI 的 `obl_mechanic_*` 完全对齐：

```
item_table.use_effect = 'restore_sp'
                         ↓
item_use_effect_restore_sp($item, &$pdata)  ← 框架自动分发
```

**框架本身是纯分发器，不预定义任何具体效果**。所有效果函数由归属系统自行注册：

| use_effect 名称 | 归属系统 | 行为 |
|----------------|---------|------|
| `restore_sp` | 食物经验系统 | 恢复 SP + 触发食物经验发放 |
| `restore_hp` | 食物经验系统 | 恢复 HP（面包/生命药剂/补给包等恢复生命的道具） |
| `cure_bs` | 健康系统 | 解除 Body Status Tag |
| `gain_resistance` | 被动技能系统 | 抗性跃迁 |

**本案只定义分发框架的调用约定**：`item_execute_use_effect($item, &$pdata)` 根据 `$item['use_effect']` 调用对应 `item_use_effect_{name}()` 函数。具体效果函数的实现由各系统在自己的设计案里完成。

### 2.7 素材匹配三维度

配方的 `materials` 支持三种素材形式，匹配优先级 `item_id` > `itmk` > `tag`：

```php
'materials' => [
    ['item_id' => 'cloth', 'count' => 2, 'consume' => 'all'],                              // 精确匹配：指定道具 ID
    ['itmk'    => 'MT',    'count' => 1, 'consume' => 'all'],                              // 类别匹配：任何金属类素材
    ['tag'     => 'tag_sharp', 'count' => 1, 'consume' => 'durability'],                   // 性质匹配：任何带 tag_sharp 的道具
    ['tag'     => 'tag_tool_cooking', 'count' => 1, 'min_level' => 1, 'consume' => 'none'], // 工具类素材：≥1 级的烹饪工具
],
```

**三种维度的分工**：

| 维度 | 语义 | 适用场景 | 示例 |
|------|------|---------|------|
| `item_id` | 精确匹配指定道具 | 配方需要特定道具 | `cloth × 3`（需要布这种具体道具） |
| `itmk` | 匹配道具大类 | "任何某类道具都行" | `itmk='MT'`（任何金属类素材：废铁、齿轮、电路板） |
| `tag` | 匹配物理性质 | itmk 无法表达的跨类别性质 | `tag_sharp`（锐器：可能跨武器 WK 和素材 MT） |

**匹配优先级**：`item_id` > `itmk` > `tag`
- 先匹配 `item_id` 素材（精确匹配优先，避免被 itmk/tag 槽位误消耗）
- 再匹配 `itmk` 素材（类别匹配次之）
- 最后匹配 `tag` 素材（性质匹配最后）
- 同一素材只能消耗一次，不能同时满足多个槽位

**`min_level` 与 `consume`**：
- `min_level`：可选，要求素材的 `tool_level >= min_level`（高级工具兼容低级配方）
- `consume`：可选，默认 `'all'`
  - `'all'`：合成后素材全部消耗（仅背包素材可匹配）
  - `'durability'`：合成后素材不消耗，只扣 1 点耐久（仅背包素材可匹配）
  - `'none'`：合成后素材完全返还（背包素材和工作台素材均可匹配）

**为什么需要 itmk 维度**：
- itmk 天然描述道具大类，"任何金属""任何食物"这类需求用 `itmk` 比 `tag` 更自然
- 避免定义 `tag_metal`、`tag_food` 等与 itmk 冗余的 Tag
- itmk 是 item_table 既有字段，无需额外维护

**约定**：
- 配方 ID 以 `craft_` 前缀，避免与 item_id 混淆
- `category` 字段：配方的分类标识（如 `'tool'` / `'armor'` / `'food'` / `'weapon'`），用于前端显示过滤（如选择炉灶时只显示 `category='food'` 的已发现配方）。后端不基于 `category` 做合成拦截
- 工作台/工具就是 `materials` 里的素材，不存在 `workbench_lvl` 和 `required_tool` 字段
- `materials` 每个元素是以下三种形式之一：
  - `['item_id' => xxx, ...]`：精确匹配指定道具
  - `['itmk' => xxx, ...]`：匹配道具类别（如 `'MT'` 匹配所有金属类素材）
  - `['tag' => xxx, ...]`：匹配性质描述 Tag
- 可选字段：
  - `count`：数量（默认 1）
  - `consume`：消耗模式，默认 `'all'`
    - `'all'`：合成后素材全部消耗（仅背包素材可匹配）
    - `'durability'`：合成后素材不消耗，只扣 1 点耐久（仅背包素材可匹配）
    - `'none'`：合成后素材完全返还（背包素材和工作台素材均可匹配）
  - `min_level`：可选，要求素材的 `tool_level >= min_level`（高级工具兼容低级配方）
- `materials` 中每个 item_id 必须在 `item_table.php` 中存在
- `materials` 中每个 itmk 应是 `item_table.php` 中实际使用的类别值
- `materials` 中每个 tag 必须在 §2.2 Tag 列表中存在
- `results` 是数组，支持多产物：每个元素 `['item_id' => xxx, 'count' => n]`
- `results` 中每个 item_id 必须在 `item_table.php` 中存在
- 同一道具不能同时匹配多个槽位（避免重复计数，由匹配优先级 `item_id` > `itmk` > `tag` 保证）
- 工作台素材（来自 POI/猫/被动技能）只能匹配 `consume='none'` 的槽位

### 3.4 工作台道具的等级与 Tag

工作台/工具就是道具，通过 `item_table` 的 `tags`、`itmk` 和 `tool_level` 字段参与合成匹配。不存在独立的"工作台类型"维度——工作台类型就是 Tag。

**本案配方涉及的工作台道具**：

| item_id | tags | tool_level | 来源 |
|---------|------|-----------|------|
| `forge_t1` | `tag_forge` | 1 | 铁砧 POI（虚拟素材） |
| `stove_t1` | `tag_tool_cooking` | 1 | 废弃排风口 POI（虚拟素材，庇护所火炉） |
| `stove_t2` | `tag_tool_cooking` | 2 | 精密炉灶 POI（虚拟素材） |
| `frying_pan` | `tag_tool_cooking` | 1 | 合成产物（背包素材，可作工作台素材放入） |
| `precision_stove` | `tag_tool_cooking` | 2 | 合成产物（背包素材，可作工作台素材放入） |
| `innate_craft_t0` | — | 0 | 被动技能（虚拟素材） |

> 工作台/工具类素材的性质描述 Tag 定义见 §2.2。工具等级兼容规则（高级工具替代低级）见 §2.7。

**烹饪和合成使用同一系统**：后端不做"烹饪 vs 合成"的区分。配方需要炉灶就在 materials 写 `tag_tool_cooking`，需要铁砧就写 `tag_forge`。前端可基于工作台素材的 Tag 做显示过滤（如选择炉灶时只显示 `category='food'` 的已发现配方），但后端不做此过滤。

### 3.5 `poi_table.php` 工作台 POI

工作台 POI 是**工作台素材的来源之一**。玩家站在工作台 POI 上时，该工作台作为工作台素材加入可用列表（详见 §2.3）。

新增工作台 POI 模板（不含文案）：

```php
'forge_anvil_poi' => [
    'searchable'      => false,
    'repeatable'      => false,
    'mechanic'        => 'craft_source',              // 工作台素材来源
    'mechanic_value'  => 'forge_t1',                  // 关联的 item_id（用于查询 tags/itmk/tool_level）
],
'vent_stove' => [
    'searchable'      => false,
    'repeatable'      => false,
    'mechanic'        => 'craft_source',
    'mechanic_value'  => 'stove_t1',                  // 废弃排风口火炉（tool_level=1 烹饪工具）
],
'precision_stove_poi' => [
    'searchable'      => false,
    'repeatable'      => false,
    'mechanic'        => 'craft_source',
    'mechanic_value'  => 'stove_t2',                  // 精密炉灶道具
],
```

> POI ID 与 item_id 分属不同命名空间（`poi_table` 和 `item_table`），但采用不同名称可避免阅读混淆：`forge_anvil_poi` 是地图上的铁砧 POI，`forge_t1` 是它关联的工作台道具。

**工作台素材的地图分布**：
- `tool_level=0`（被动技能）：玩家自带，无需探索
- `tool_level=1`（工作台 POI）：金属平原/垃圾山脉的据点（需探索发现该地图）
- `tool_level=2`（工作台 POI）：深层区域（需击败特定敌人或解谜才能进入该地图）

**与 `item_get_available_workbench_materials` 的关系**：
- 该函数查询玩家当前格子（`$pdata['pls']`）上的 POI 实例
- 如果该 POI 的 `mechanic='craft_source'`，则将其 `mechanic_value`（item_id）作为工作台素材加入列表
- 返回 `[{source: 'poi', id: 'poi:'.$iaid, item_id: $mechanic_value, tool_level: ...}]`
- `tool_level`、`tags` 和 `itmk` 从 `item_table` 查询，与背包素材统一匹配

### 4.1 `obl_use_item` 命令

**请求**：
```
POST command.php
mode=command&command=obl_use_item&slot=3
```

**参数**：
- `slot` (int, 1~itemmaxslots) — 背包槽位号

**状态过滤**：
- 战斗状态下禁止
- 死亡状态下禁止

**Tick 推进**：**不推进**

**响应**：`{}`（标准 Oblivions 命令响应，具体效果通过日志输出）

### 4.2 `obl_craft` 命令

**请求**：
```
POST command.php
mode=command&command=obl_craft&slots=1,3,5,7&workbench_materials=poi:123
```

**参数**：
- `slots` (string) — 逗号分隔的背包槽位号，表示玩家放入素材池的背包素材。**数量不限**，玩家想放多少放多少。

**可选参数**：
- `workbench_materials` (string) — 逗号分隔的工作台素材 ID（如 `poi:123` / `passive:innate_t0` / `cat:portable_t1`）。玩家选择放入素材池的工作台素材。工作台素材参与配方匹配，但不消耗。

**状态过滤**：
- 战斗状态下禁止
- 死亡状态下禁止

**Tick 推进**：**不推进**

**响应**：`{}`

**设计说明**：
- `obl_craft` 不接收 `recipe_id` 参数——玩家提交的是"素材池的素材列表"，后端根据素材的 item_id、itmk、Tag、tool_level 组合做指向性判断，自动匹配配方
- `obl_craft` 不做配方显示过滤检查——软锁是显示控制，玩家可以"放素材试组合"合成任何配方
- 工作台素材和背包素材统一参与匹配，只是工作台素材的 `consume` 固定为 `none`
- 如果合成的是未发现配方 → 加入 `discovered_recipes` + emit `craft.new_recipe_discovered` 事件
- `workbench_materials` 参数中的 ID 用于从 `item_get_available_workbench_materials` 返回的列表中查找对应的工作台素材

### 4.3 `craft_preview` API（前端预判用）

**请求**：`GET api_v2.php?action=craft_preview&slots=1,3,5,7&workbench_materials=poi:123`

**参数**：
- `slots` (string) — 逗号分隔的背包槽位号，数量不限
- `workbench_materials` (string, 可选) — 逗号分隔的工作台素材 ID

**响应**：
```json
{
  "status": "success",
  "data": {
    "match_count": 1,
    "craftable": true,
    "is_new_recipe": false
  }
}
```

- `match_count = 0` → 不亮（无匹配）
- `match_count = 1` → 亮灯（可合成）
- `match_count >= 2` → 不亮（指向不明确）
- `is_new_recipe = true` → 匹配的配方玩家未发现过（前端可显示"发现新配方！"提示）

**不返回产物名称**——保持探索感，玩家点击合成按钮后才知道出了什么。

### 4.4 `craft_workbench_materials` API（前端查询可用工作台素材）

**请求**：`GET api_v2.php?action=craft_workbench_materials`

**响应**：
```json
{
  "status": "success",
  "data": {
    "workbench_materials": [
      {"source": "passive", "id": "passive:innate_t0",   "item_id": "innate_craft_t0", "tool_level": 0},
      {"source": "poi",     "id": "poi:123",             "item_id": "forge_t1",        "tool_level": 1}
    ]
  }
}
```

前端用此列表渲染素材池候选区的工作台素材。玩家选择后，`id` 传给 `obl_craft` / `craft_preview` 的 `workbench_materials` 参数。

**`item_id` 的作用**：前端可基于 `item_id` 查询 `item-locale.ts` 获取工作台名称和图标，基于 `tags` 判断工作台类型（如 `tag_tool_cooking` → 烹饪类、`tag_forge` → 锻造类），用于前端显示过滤。

### 4.5 `craft_recipes` API（前端查询已发现配方列表）

**请求**：`GET api_v2.php?action=craft_recipes`

**响应**：
```json
{
  "status": "success",
  "data": {
    "recipes": [
      {"recipe_id": "craft_bandage",       "category": "tool", "materials": [...], "results": [{"item_id": "bandage", "count": 1}]},
      {"recipe_id": "craft_roasted_rabbit", "category": "food", "materials": [...], "results": [{"item_id": "roasted_rabbit", "count": 1}]}
    ]
  }
}
```

**过滤逻辑**：
1. 读取 `oblpara.discovered_recipes`
2. 对每个已发现配方调用 `item_recipe_visibility_filter($recipe, $pdata)` 判断是否可见
3. 只返回可见的已发现配方

**前端用途**：渲染"已发现配方列表"供玩家快速调用。玩家点击列表中的配方 → 前端自动从背包扣素材 → 调用 `obl_craft`。

### 5.1 文件组织与命名规范

**目录结构**（仿效 `battle/` 和 `skill/` 子文件夹规范）：

```
oblivions/include/game/
├── item/                       ← 新建道具系统子文件夹
│   ├── item.tag.func.php       ← 道具 Tag 系统
│   ├── item.use.func.php       ← 道具使用系统（含 use_effect 分发框架）
│   └── item.craft.func.php     ← 合成系统
```

#### 5.4.3 `item_consume_durability` 耐久扣减

耐久字段 `itms` 约定：
- 纯数字字符串 → 有限耐久，每次使用扣 1
- `"999"` 或 `"∞"` → 无限耐久，不扣减
- 耐久扣到 0 → 道具破坏（从背包移除，emit `durability.broken` 日志）

```php
function item_consume_durability(&$item, $amount = 1) {
    global $obl_log;
    if (!isset($item['itms'])) return;
    $s = (string)$item['itms'];
    if ($s === '' || $s === '0' || $s === '∞' || $s === '999') return;
    $cur = (int)$s;
    $cur = max(0, $cur - $amount);
    $item['itms'] = (string)$cur;
    if ($cur === 0) {
        // 道具破坏：emit 事件（从背包移除由调用方 item_use 负责）
        $obl_log->emit('durability.broken', 'system', ['item_id' => $item['itmid'] ?? '']);
    }
}
```

**职责分工**：`item_consume_durability` 只负责扣减耐久和 emit 事件。**从背包移除**已损坏道具的逻辑由调用方 `item_use` 在步骤 4.5 处理（`unset($pdata['itempara'][$slot])`），因为本函数签名只接受 `&$item`，无法获取 `$slot`。

#### 5.5.1 `item_craft` 流程

**关键概念区分**：
- **不能合成**：后端配方表没有对应配方（素材组合不匹配任何配方）。这是"指向性判断失败"，不算合成失败。
- **合成失败**：未来可能扩展的合成失败事件与触发条件（如"合成有概率失败损失素材"等机制）。P0 不实现，但预留 `craft.fail` 事件接口。

```
1. 解析 $slots 数组，读取每个槽位的背包素材
   - 槽位为空 → 跳过
   - 数量不限，玩家想放多少放多少
2. 解析 $workbench_materials 数组，读取工作台素材
   - 通过 item_get_available_workbench_materials($pdata) 验证每个 ID 有效
   - 工作台素材不占背包槽位，consume 固定为 'none'
3. 调用 item_match_recipes_by_slots($pdata, $slots, $workbench_materials)
   - 返回匹配的配方 ID 列表 $matched
   - 匹配时统一处理背包素材和工作台素材
4. 根据 count($matched) 分支：
   - 0 个 → emit craft.fail_no_match（不能合成），返回
   - 2+ 个 → emit craft.fail_ambiguous {match_count}（不能合成，指向不明确），返回
   - 1 个 → 继续
5. 取唯一匹配的 $recipe
6. 检查背包剩余空间（所有产物入背包）
   - 满包 → emit craft.fail_bag_full，返回
7. ──【介入点 1：合成失败检查（P0 预留）】─────────
   未来合成失败机制可在此处介入：
   - 检查合成失败概率（如配置了 fail_chance）
   - 失败 → emit craft.fail {recipe_id, reason}，按失败规则处理素材（如部分消耗），返回
   - P0 阶段：不实现，直接跳过此步
   ─────────────────────────────────────────────────
8. 调用 item_consume_materials($pdata, $recipe['materials'], $slots, $workbench_materials)
   ──【介入点 2：素材扣减前】─────────────────────
   鉴定系统未来可在此处检查素材的真实 Tag，影响产物隐藏属性
   ─────────────────────────────────────────────────
   素材消耗按 materials 的 consume 字段处理：
   - 'all' → 从背包移除素材（工作台素材不能匹配此模式）
   - 'durability' → 素材保留，扣 1 点耐久（工作台素材不能匹配此模式）
   - 'none' → 素材完全保留（背包素材和工作台素材均可匹配）
9. 添加所有产物到背包（遍历 $recipe['results'] 数组）
10. 检查 $recipe_id 是否在 oblpara.discovered_recipes 中
    - 不在 → 调用 item_discover_recipe($pdata, $recipe_id)
             emit craft.new_recipe_discovered {recipe_id}
             （前端可显示"发现新配方！"提示）
11. emit craft.success {recipe_id}
    ──【介入点 3：供对话系统订阅触发猫提醒】─────────
    对话系统可订阅 craft.success，根据 recipe_id 查配方表获知产物类型触发猫的台词
    （如"诶，你上次捡的那堆旧齿轮还在吗？"）
    ─────────────────────────────────────────────────

```

**介入点说明**：
- **介入点 1（合成失败检查）**：未来合成失败机制（如"合成有概率失败"）的介入位置。P0 不实现，直接跳过。预留 `craft.fail` 事件。
- **介入点 2（素材扣减前）**：鉴定系统未来可在此处检查素材的真实 Tag，影响产物隐藏属性。本案不实现，只通过流程顺序明示介入位置。
- **介入点 3（合成成功事件）**：emit `craft.success` 结构化事件。对话系统订阅此事件，在合适情境下触发猫的提醒台词。

#### 5.5.2 `item_match_recipes_by_slots` 指向性判断

```php
function item_match_recipes_by_slots(&$pdata, $slots, $workbench_materials = []) {
    // 1. 读取背包素材（item_id + itmk + tags + tool_level + itms + source='bag'）
    $placed_items = [];
    foreach ($slots as $slot) {
        $item = $pdata['itempara'][$slot] ?? null;
        if ($item && $item['itmid']) {
            $placed_items[] = [
                'item_id'    => $item['itmid'],
                'itmk'       => item_get_itmk($item['itmid']),
                'tags'       => item_get_tags($item['itmid']),
                'tool_level' => item_get_tool_level($item['itmid']),
                'itms'       => (int)($item['itms'] ?? 1),   // 堆叠数量/耐久（参与 count 求和）
                'source'     => 'bag',
            ];
        }
    }

    // 2. 读取工作台素材（通过 item_get_available_workbench_materials 验证并获取元数据）
    $available_wb = item_get_available_workbench_materials($pdata);
    foreach ($workbench_materials as $wb_id) {
        foreach ($available_wb as $wb) {
            if ($wb['id'] === $wb_id) {
                $placed_items[] = [
                    'item_id'    => $wb['item_id'],
                    'itmk'       => item_get_itmk($wb['item_id']),
                    'tags'       => item_get_tags($wb['item_id']),
                    'tool_level' => $wb['tool_level'],
                    'itms'       => 0,                        // 工作台素材无数量概念，仅参与类型匹配
                    'source'     => 'workbench',
                ];
                break;
            }
        }
    }

    // 3. 遍历所有配方，找 materials 完全匹配的
    //    软锁是显示控制，不是合成拦截（详见 §2.5.1）
    $matched = [];
    foreach (item_get_all_recipes() as $recipe_id => $recipe) {
        if (item_materials_match($recipe['materials'], $placed_items)) {
            $matched[] = $recipe_id;
        }
    }

    return $matched;  // 0 个=不亮，1 个=亮，2+=不亮
}
```

**数量匹配规则**：`item_materials_match` 在比对 `count` 时，将同一 `item_id` / `itmk` / `tag` 的 `$placed_items` 的 `itms` 求和，再与配方 `materials[].count` 对比。例如槽1 布料×3 + 槽3 布料×5 → `itms` 合计 8 ≥ 配方所需 2 → 匹配。

> 注：`itms` 在此处语义为"可用数量"（堆叠道具显示剩余份数），非耐久值。工作台素材 `itms=0` 表示不计入数量求和，仅通过 `item_id` / `itmk` / `tag` 参与类型匹配。

**匹配规则**（详见 §5.5.7 `item_resolve_material_mapping`）：
- 背包素材和工作台素材统一参与匹配
- 工作台素材只能匹配 `consume='none'` 的 material 槽位
- `min_level` 检查：素材的 `tool_level` 必须 ≥ material 的 `min_level`
- 匹配优先级：`item_id` > `itmk` > `tag`
- **数量求和**：同一 `item_id` / `itmk` / `tag` 的背包素材 `itms` 求和后与配方 `count` 对比，同一素材不能被多个配方槽位重复计数

#### 5.5.6 `item_materials_match` 素材多重集匹配

`item_materials_match` 是 `item_resolve_material_mapping`（§5.5.7）的布尔包装，仅返回是否匹配，不返回映射细节。指向性判断和素材消耗共用同一个映射算法，避免逻辑分裂。

```php
function item_materials_match($materials, $placed_items) {
    $mapping = item_resolve_material_mapping($materials, $placed_items);
    return $mapping !== null;
}
```

**匹配规则总结**（详见 §5.5.7）：
1. 先匹配具体 `item_id` 素材（精确匹配优先）
2. 再匹配 `itmk` 素材（类别匹配次之）
3. 最后匹配 `tag` 素材（性质匹配最后）
4. `min_level` 检查：素材的 `tool_level` 必须 ≥ material 的 `min_level`（高级工具兼容低级配方）
5. `consume` 约束：工作台素材只能匹配 `consume='none'` 的槽位
6. 所有放置的素材必须都被消耗（多放也算不匹配，避免指向不明确）
7. 同一素材不能同时满足多个槽位（避免重复计数，由匹配优先级保证）

#### 5.5.7 `item_resolve_material_mapping` 素材-槽位映射

**共享辅助函数**：`item_materials_match`（指向性判断）和 `item_consume_materials`（素材扣减）共用此函数。返回每个被消耗的素材及其对应的 `consume` 模式，或 `null` 表示不匹配。

```php
/**
 * 解析素材-槽位映射
 *
 * @param array $materials   配方的 materials 数组
 * @param array $placed_items [['item_id'=>xxx, 'itmk'=>xxx, 'tags'=>[...], 'tool_level'=>n, 'source'=>'bag'|'workbench'], ...]
 * @return array|null  匹配成功返回 [['placed_index'=>i, 'consume'=>mode], ...]；
 *                     匹配失败返回 null
 */
function item_resolve_material_mapping($materials, $placed_items) {
    // 1. 复制 placed_items 用于消耗标记
    $available = [];
    foreach ($placed_items as $i => $p) {
        $available[] = [
            'index'      => $i,
            'item_id'    => $p['item_id'],
            'itmk'       => $p['itmk'] ?? '',
            'tags'       => $p['tags'],
            'tool_level' => $p['tool_level'] ?? 0,
            'source'     => $p['source'] ?? 'bag',
            'used'       => false,
        ];
    }

    $mapping = [];

    // 2. 先匹配具体 item_id 素材（精确匹配优先）
    foreach ($materials as $mat) {
        if (isset($mat['item_id'])) {
            $need = $mat['count'];
            $consume = $mat['consume'] ?? 'all';
            $min_level = $mat['min_level'] ?? 0;
            for ($i = 0; $i < count($available) && $need > 0; $i++) {
                if (!$available[$i]['used']
                    && $available[$i]['item_id'] === $mat['item_id']
                    && $available[$i]['tool_level'] >= $min_level
                    && item_can_consume($available[$i], $consume)) {
                    $available[$i]['used'] = true;
                    $mapping[] = ['placed_index' => $available[$i]['index'], 'consume' => $consume];
                    $need--;
                }
            }
            if ($need > 0) return null;
        }
    }

    // 3. 再匹配 itmk 素材（类别匹配次之）
    foreach ($materials as $mat) {
        if (isset($mat['itmk'])) {
            $need = $mat['count'];
            $consume = $mat['consume'] ?? 'all';
            $min_level = $mat['min_level'] ?? 0;
            for ($i = 0; $i < count($available) && $need > 0; $i++) {
                if (!$available[$i]['used']
                    && $available[$i]['itmk'] === $mat['itmk']
                    && $available[$i]['tool_level'] >= $min_level
                    && item_can_consume($available[$i], $consume)) {
                    $available[$i]['used'] = true;
                    $mapping[] = ['placed_index' => $available[$i]['index'], 'consume' => $consume];
                    $need--;
                }
            }
            if ($need > 0) return null;
        }
    }

    // 4. 最后匹配 tag 素材（性质匹配最后）
    foreach ($materials as $mat) {
        if (isset($mat['tag'])) {
            $need = $mat['count'];
            $consume = $mat['consume'] ?? 'all';
            $min_level = $mat['min_level'] ?? 0;
            for ($i = 0; $i < count($available) && $need > 0; $i++) {
                if (!$available[$i]['used']
                    && in_array($mat['tag'], $available[$i]['tags'])
                    && $available[$i]['tool_level'] >= $min_level
                    && item_can_consume($available[$i], $consume)) {
                    $available[$i]['used'] = true;
                    $mapping[] = ['placed_index' => $available[$i]['index'], 'consume' => $consume];
                    $need--;
                }
            }
            if ($need > 0) return null;
        }
    }

    // 5. 检查是否所有放置的素材都被消耗（多放也不匹配）
    foreach ($available as $a) {
        if (!$a['used']) return null;
    }

    return $mapping;
}

/**
 * 检查素材是否可匹配指定 consume 模式
 * 工作台素材（source='workbench'）只能匹配 consume='none'
 */
function item_can_consume($item, $consume) {
    if ($consume === 'none') return true;
    if ($item['source'] === 'workbench') return false;
    return true;
}
```

**匹配规则总结**：
1. 先匹配具体 `item_id` 素材（精确匹配优先）
2. 再匹配 `itmk` 素材（类别匹配次之）
3. 最后匹配 `tag` 素材（性质匹配最后）
4. `min_level` 检查：素材的 `tool_level` 必须 ≥ material 的 `min_level`（高级工具兼容低级配方）
5. `consume` 约束：工作台素材只能匹配 `consume='none'` 的槽位
6. 所有放置的素材必须都被消耗（多放也算不匹配，避免指向不明确）
7. 同一素材不能同时满足多个槽位（避免重复计数，由匹配优先级 `item_id` > `itmk` > `tag` 保证）

**返回值结构**：`[['placed_index' => 0, 'consume' => 'all'], ['placed_index' => 2, 'consume' => 'none'], ...]`
- `placed_index`：在 `$placed_items` 数组中的索引（对应背包槽位或工作台素材列表中的位置）
- `consume`：该素材的消耗模式（`'all'` / `'durability'` / `'none'`）

#### 5.5.8 `item_consume_materials` 素材扣减

按 `consume` 字段处理每个被消耗的素材。调用 `item_resolve_material_mapping` 获取映射，再按模式分别处理。工作台素材只能匹配 `consume='none'`（由 `item_can_consume` 保证），所以实际不需要扣减。

```php
/**
 * 扣除合成素材
 *
 * @param array &$pdata     玩家数据
 * @param array $materials  配方的 materials 数组
 * @param array $slots      玩家放入素材池的背包槽位号列表
 * @param array $workbench_materials  工作台素材 ID 列表
 * @return bool  扣除成功返回 true
 */
function item_consume_materials(&$pdata, $materials, $slots, $workbench_materials = []) {
    // 1. 读取背包素材 + 工作台素材，合并为 placed_items
    $placed_items = [];
    $slot_map = [];     // placed_items 索引 → 背包槽位号（仅背包素材有）
    $bag_count = 0;     // 背包素材数量（用于区分 placed_index 对应背包还是工作台）
    foreach ($slots as $slot) {
        $item = $pdata['itempara'][$slot] ?? null;
        if ($item && $item['itmid']) {
            $placed_items[] = [
                'item_id'    => $item['itmid'],
                'itmk'       => item_get_itmk($item['itmid']),
                'tags'       => item_get_tags($item['itmid']),
                'tool_level' => item_get_tool_level($item['itmid']),
                'source'     => 'bag',
            ];
            $slot_map[] = $slot;
            $bag_count++;
        }
    }

    // 工作台素材追加到 placed_items 末尾
    $available_wb = item_get_available_workbench_materials($pdata);
    foreach ($workbench_materials as $wb_id) {
        foreach ($available_wb as $wb) {
            if ($wb['id'] === $wb_id) {
                $placed_items[] = [
                    'item_id'    => $wb['item_id'],
                    'itmk'       => item_get_itmk($wb['item_id']),
                    'tags'       => item_get_tags($wb['item_id']),
                    'tool_level' => $wb['tool_level'],
                    'source'     => 'workbench',
                ];
                break;
            }
        }
    }

    // 2. 调用共享映射函数
    $mapping = item_resolve_material_mapping($materials, $placed_items);
    if ($mapping === null) {
        return false;  // 理论上不会走到这里（item_craft 流程已确认匹配）
    }

    // 3. 按 consume 模式处理每个被消耗的素材
    //    工作台素材只匹配 consume='none'，无需操作
    //    只有背包素材需要处理 consume='all' / 'durability'
    foreach ($mapping as $m) {
        if ($m['placed_index'] >= $bag_count) {
            // 工作台素材，consume 必为 'none'，跳过
            continue;
        }
        $slot = $slot_map[$m['placed_index']];
        $item = &$pdata['itempara'][$slot];

        switch ($m['consume']) {
            case 'all':
                // 从背包移除（unset 槽位，与 obl_find_empty_slot 兼容）
                unset($pdata['itempara'][$slot]);
                break;

            case 'durability':
                // 素材保留，扣 1 点耐久
                item_consume_durability($item, 1);
                break;

            case 'none':
                // 素材完全保留（不消耗不扣耐久）
                break;
        }
    }

    return true;
}
```

**`consume` 字段三种模式**：

| 模式 | 行为 | 可匹配的素材来源 |
|------|------|----------------|
| `'all'`（默认） | 从背包移除素材 | 仅背包素材 |
| `'durability'` | 素材保留，扣 1 点耐久 | 仅背包素材 |
| `'none'` | 素材完全保留 | 背包素材 + 工作台素材 |

**与 `item_consume_durability` 的关系**：`consume='durability'` 模式直接调用 `item_consume_durability($item, 1)`（§5.4.3），复用耐久扣减逻辑。若耐久归零，`item_consume_durability` 内部会触发 `durability.broken` 事件。

## 七、日志 ID 清单（结构化事件）

> 这些事件是其他系统介入的"接口"。其他系统通过订阅这些事件触发自己的逻辑（如对话系统订阅 `craft.success` 触发猫提醒）。

### 7.1 道具使用事件

| ID | logcategory | params | 触发场景 | 消费方 |
|----|------------|--------|---------|--------|
| `use_item.empty_slot` | system | `{slot}` | 使用空槽位 | — |
| `use_item.not_usable` | system | `{item_id}` | 道具不可使用（无 `tag_usable`） | — |
| `use_item.effect_not_registered` | system | `{effect}` | use_effect 函数未注册（归属系统未实现） | 开发期警告 |
| `use_item.success` | system | `{item_id, slot}` | 道具使用成功 | **对话系统订阅**（触发猫台词） |
| `durability.broken` | system | `{item_id}` | 道具因耐久归零破坏 | — |

### 7.2 合成事件

"不能合成"与"合成失败"的区分见 §5.5.1。

| ID | logcategory | params | 触发场景 | 消费方 |
|----|------------|--------|---------|--------|
| `craft.success` | system | `{recipe_id}` | 合成成功 | **对话系统订阅**（触发猫提醒）；前端从 recipe_id 查配置表获知产物 |
| `craft.new_recipe_discovered` | system | `{recipe_id}` | 合成了未发现过的配方 | 前端显示"发现新配方！"提示 |
| `craft.fail_no_match` | system | — | 素材池组合无匹配配方（不能合成） | — |
| `craft.fail_ambiguous` | system | `{match_count}` | 指向不明确，多个匹配（不能合成） | — |
| `craft.fail_bag_full` | system | — | 背包满（不能合成） | — |
| `craft.fail` | system | `{recipe_id, reason}` | 合成失败（P0 预留，未来扩展） | 未来合成失败机制 |

**`craft.success` 的参数精简**：只传 `recipe_id`，不传 `results`（产物列表）。配方是固定的→产物是固定的，前端/对话系统从 `recipe_id` 查配方配置表即可获知产物。避免后端发送冗余信息，也避免整理失败时 `results` 与实际入背包产物不一致的问题。

**事件解耦**：合成成功（`craft.success`）与整理失败（`organize.fail`，见堆叠设计案 §11.5）是独立事件。合成成功表示素材已扣减、产物已生成（在 itm0 或背包）；整理失败表示产物卡在 itm0 需要玩家手动处理。前端可同时收到两个事件。

**注**：不存在 `craft.fail_no_tool` / `craft.fail_workbench_lvl` / `craft.fail_not_at_workbench` 事件——工具/工作台就是素材，工具不足表现为素材不匹配走 `craft.fail_no_match`；软锁是显示控制不是合成拦截。`craft.success` 参数不含 `workbench_id`——工作台是素材，不需要单独记录。

## 十一、预留扩展点

### 11.1 鉴定系统

介入位置见 §5.5.1 介入点 2（`item_craft` 第 8 步，素材扣减前）。鉴定系统上线时：
- 道具的 `itmpara.identified` 字段记录鉴定状态
- 未鉴定道具的 `tags` 字段显示通用 Tag，鉴定后揭示真实 Tag
- 合成时检查素材的真实 Tag，可能影响产物属性

**P0 阶段不实现 `hidden_bonus` 字段**（越级合成隐性加成由鉴定系统设计案定义），只在介入点 2 预留检查位置，无需修改本案框架代码。

### 11.2 猫背包系统

猫背包的"胃酸腐蚀"机制复用 `item_consume_durability` 函数——道具在猫肚子里每隔一段时间扣减耐久。

猫背包的"便携工作站"升级表现为：猫身上提供一条**工作台素材**（`source='cat'`），由 `item_get_available_workbench_materials()` 在合成界面实时计算时返回。升级机制=把猫这条工作台素材的 `item_id` 换成更高 `tool_level` 的工作台道具。猫背包系统只负责"猫当前挂着哪件工作台道具"这条数据，不参与合成匹配逻辑。

### 11.3 被动技能系统

被动技能系统注册 `item_use_effect_gain_resistance` 函数到 use_effect 框架：
- 道具的 `itmpara` 存放 `{ "resistance_tag": "tag_arc_resistance", "chance": 0.3 }`
- `oblpara.passive_skills` 数组记录已获得的被动技能
- 战斗系统查询 `oblpara.passive_skills` 应用抗性

### 11.4 道具堆叠

当前 `obl_pickup_item` 命令未实现堆叠合并。后续实现堆叠时，扩展：
- `obl_pickup_item` — 同类道具合并到已有槽位
- `item_count_material_in_inventory` — 按 `itms` 累加而非按槽位计数
- `item_consume_materials` — 按数量优先扣减最满的槽位

### 11.5 工作台升级

工作台 POI 的 `mechanic_value` 存储 `item_id`（字符串，指向 `item_table` 中的工作台道具），不再是数值等级。工作台道具的等级由 `item_table.tool_level` 字段定义。

**升级路径**=换为更高级 `tool_level` 的工作台 `item_id`：
- 庇护所升级：消耗素材把 POI 的 `mechanic_value` 从 `workbench_t1` 改写为 `workbench_t2`（POI 本身不变，改的是它指向的工作台道具）
- 猫背包便携工作站：见 §11.2，把猫身上的工作台素材 `item_id` 换成更高级

**关键点**：升级是改数据指向，不是改数据结构。`item_get_available_workbench_materials()` 读 `mechanic_value` 拿到 `item_id`，再查 `item_table` 得到 `tool_level`、`tags` 和 `itmk`——这条链路对任意 `item_id` 都成立，升级后无需改函数代码。

### 11.6 Buff 系统

Buff 系统可注册 `item_use_effect_apply_buff` 函数到 use_effect 框架，写入 `oblpara.buffs` 数组（带 expire_tick）。

### 11.7 合成系统的性质描述 Tag 扩展

本案只定义了 5 个性质描述 Tag（配方实际使用的）。后续合成配方需要的新性质描述 Tag 由配方扩展设计案定义：

- 如需要"钝器""柔性物""绝缘体"等物理性质 Tag，由配方扩展设计案定义

**扩展原则**：
- 新 Tag 只在它被实际消费时才定义（避免过度设计）
- 新 Tag 优先考虑能否用 itmk 替代（如"任何武器"用 itmk='WP' 而非 tag_weapon）
- 只有 itmk 无法表达的跨类别性质才定义新 Tag

**系统钩子 Tag**（`tag_equippable` / `tag_poi_interactive` 及后续扩展）见《道具-系统钩子Tag设计案.md》。
