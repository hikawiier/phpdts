# 角色数据分发中心设计案

> **⚠️ 状态警告（2026-07-11 更新）**
> 
> 本文最初的 `mergeEnemies + aliveList 直接渲染` 可见性模型已被 [`战斗演出事件消费与权威投影解耦研判.md` §13.4](./战斗演出事件消费与权威投影解耦研判.md#134-实机回归后的投影边界修正) **修正**。
> 
> **现行基准**：`Character 资料缓存 + enemies 完整 map roster + PresentationScene Actor 生命周期` 三层分离模型。
> 
> **本文后续章节**（§4-§9）中出现的旧 `mergeEnemies/aliveList` 方案仅作为**历史迁移记录**，**不再是现行实现依据**。阅读时请结合 `vex-vue/CODEBASE.md` 和 `src/stores/character.ts` 理解当前实现。

## 1. 问题陈述

### 1.1 体验降级

探索模式下玩家能看到所有敌人（`mapStore.enemies`），可自由瞄准。进入战斗后 `entities.ts` 切换到 `combatContext.combatants`，非战斗 NPC 全部消失。玩家在探索模式能瞄准所有敌人，战斗中反而只能看到同在战斗中的敌人——体验降级。

### 1.2 敌人数据来源分裂

当前角色数据散落在多处，按场景切换：

| 数据源 | 字段（key 字段加粗） | 来源 API |
|--------|----------------------|----------|
| `mapStore.enemies` | **pid**, type, name, icon, gd, pgroup, pls, hp, mhp, lvl, state, discovered | enemies scope |
| `combatContext.combatants` | **pid**, type, name, hp, maxHp, ap, maxAp, pgroup, pls, state, active, done, myorder | player_info.combat_context |
| `combatContext.validTargets` | **pid**, type, name, pgroup, pls, hp, maxHp, state | player_info.combat_context（经战斗规则过滤：type>0、state=0、active、非玩家） |
| `battleStore.enemyLocation` | 单个 pls 值（当前 NPC 位置，供 BattleHeader 显示） | `refreshEnemyLocation` 调用 `refreshMapEnemies()` 从 enemies API 提取 |
| `battleStore.currentEnemyPid` | number（当前战斗目标 PID，状态机判断字段） | 从 battle_queue / combatContext.defaultTargetPid 提取 |
| `battleStore.currentSegment` 中的 snapshot | **pid**, type, name, hp, max_hp（事件流快照） | battle_log v2 事件流（BattleModal 播放时使用） |

同一个敌人（同 pid）的属性被拆到多个源，字段命名不统一（Enemy 用 `mhp`，CombatantViewModel/CombatantView 用 `maxHp`，CombatantSnapshot 用 `max_hp`），类型不统一（Enemy 是 `string|number`，CombatantViewModel 是 `number`）。消费者各取所需，未来每加一个需求就多一处临时读取。

> **注意**：`battleStore.enemyLocation` 并非 `pid → pls` 的 Map，而是单个 `string | number | null` 值，存储当前 NPC 的 pls，专门供 BattleHeader 显示敌人位置。`refreshEnemyLocation` 的实际数据源是 enemies API（经 `refreshMapEnemies()`），不是 `battleStore.enemyLocation` 自身。

### 1.3 类型定义重叠

项目中实际存在 **6 个**有重叠字段的角色类型，各自独立定义，命名和类型不统一：

| 类型 | 定义位置 | max-HP 字段名 | pid/type 字段类型 | 用途 |
|------|----------|---------------|-------------------|------|
| `Enemy` | `types/api.ts` | `mhp` | `string \| number` | enemies scope 返回的探索态敌人 |
| `PlayerInfo` | `types/api.ts` | `mhp` | `string`（数值字段均为字符串） | player_info scope 返回的玩家自身 |
| `CombatantViewModel` | `types/api.ts` | `maxHp` | `number` | combat_context.combatants 元素 |
| `CombatTargetViewModel` | `types/api.ts` | `maxHp` | `number` | combat_context.validTargets 元素 |
| `CombatantView` | `stores/battle-director-v2.ts` | `maxHp` | `number` | battlelog v2 事件流派的演出视图（BattleModal / battle-actor-executor 使用） |
| `CombatantSnapshot` | `types/api.ts` | `max_hp` | `number` | battlelog v2 事件 payload 中的原始快照 |

仅 max-HP 字段就存在 **三种命名风格**：`mhp`（表字段名）、`maxHp`（驼峰）、`max_hp`（下划线小写）。这是后端按 scope 切分数据 + 前端各模块各自定义类型的直接映射——前端没有做统一抽象。

> **范围声明**：`CombatantView` 和 `CombatantSnapshot` 来自 battlelog v2 事件流，是"事件快照"而非"状态"。它们与 CharacterHub 的关系见 §3.5 末尾的范畴声明。

## 2. 根因分析

### 2.1 后端 scope 切分被直接映射到前端 store

后端按 API scope 返回数据：`enemies` scope 返回探索态薄数据，`player_info` scope 返回 `combat_context` 厚数据。前端直接把后端的 scope 结构映射到不同的 store（mapStore / battleStore），没有在中间做统一抽象。

结果：同一个敌人（同 pid）的数据被拆到多个 store，消费者需要知道"去哪个 store 读哪个字段"，且不同 store 的字段命名/类型不一致。

### 2.2 combatContext 被误用为实体列表

`combatContext.combatants` 的设计初衷是"战斗上下文视图"（谁在战斗、谁的回合、可瞄准谁），但 `entities.ts` 把它当成了"战斗中的实体列表"，用 combatants 替代 mapStore.enemies。这导致非战斗 NPC 在战斗中消失、实体位置有两个真值源。

### 2.3 消费者调研（按实际代码核实）

| 消费者 | 实际需求 | 当前数据源 |
|--------|----------|-----------|
| `stores/entities.ts` | pid, type, pls, state, active（战斗中过滤 active && state===0） | 战斗模式：`combatContext.combatants`；探索模式：`mapStore.curLoc`（玩家）+ `mapStore.enemies`（敌人） |
| `components/battle/PreloadArea.vue` | pid, pls, pgroup, name, state, hp, maxHp, defaultTargetPid | `combatContext.validTargets`（射程判断优先）→ `combatContext.combatants`（回退）→ `mapStore.enemies`（兜底）；`mapStore.curLoc`/`curRegion`（玩家位置/区域）；`data.combatContext.defaultTargetPid`（默认目标） |
| `components/battle/BattleModal.vue` | pid, name, hp, maxHp（双方 HP 条） | **不读 combatContext**。HP 来自 `battleStore.currentSegment` 的 `effect.delta.hp_before/hp_after` 和 `CombatantView.snapshot`（battlelog v2 事件流） |
| `stores/battle-actor-executor.ts` | pid → actor 控制器（用于动画） | **不查 pid → pls**。通过 `combatantEntityId(combatant)` 拼出 actor ID（`enemy-${pid}` / `player`），用 `getActorById(id)` 拿控制器，调用 `actor.getPosition()` 取实时 DOM 位置；移动目标位置来自 battlelog effect 的 `target.kind === 'tile'` + `target.pls`（DOM querySelector 定位） |
| `stores/battle.ts` `refreshEnemyLocation` | npcPid → pls（供 BattleHeader 显示） | 调用 `refreshMapEnemies()` 从 enemies API 拿到敌人列表，遍历找 pid 匹配的 enemy.pls，写入 `battleStore.enemyLocation`（单个值） |
| `components/battle/BattleHeader.vue`（隐含） | 敌人名称、敌人位置 pls | `battleStore.enemyName`、`battleStore.enemyLocation`（由 `refreshEnemyLocation` 和 `updateEnemyNameFromSegment` 写入） |

**结构信号**：`entities.ts`、`PreloadArea.vue`、`refreshEnemyLocation`、`BattleHeader` 都以 pid 为核心查找键，且都因数据源分裂而需要切换/兜底——这是建立以 pid 为 key 的统一角色数据中心的强烈信号。

**不在 CharacterHub 范畴的消费者**：`BattleModal.vue` 和 `battle-actor-executor.ts` 的数据来自 battlelog v2 事件流（`currentSegment` 中的 snapshot/effect），是"事件回放数据"而非"当前状态"。它们不需要从 CharacterHub 读取——详见 §3.5 末尾的范畴声明。

## 3. 设计方向：CharacterHub

### 3.1 核心概念

新增 `characterStore`（CharacterHub），以 pid 为 Map key 存储所有角色的完整状态。它是角色数据的唯一真值源。

```
后端 API 响应（enemies / player_info / combat_context）
    ↓ 统一写入
CharacterHub（以 pid 为 key 的角色数据中心，存储"当前状态"）
    ↓ 统一读取
当前状态消费者（entities / PreloadArea / BattleHeader / battle.ts / playerStore）

不在 CharacterHub 范畴：
  battlelog v2 事件流消费者（BattleModal / battle-actor-executor）
  —— 它们读 currentSegment 的 snapshot/effect，是"事件回放数据"，见 §3.5
```

### 3.2 角色数据结构

后端 `oblplayers` 表是玩家+敌人统一存储，所有标准字段共用。`SELECT *` 已返回全部字段，当前 enemies scope 的"薄数据"是 `obl_state_simplify_enemy_data()` 主动丢弃的结果，不是数据模型限制。

Character 类型应包含 oblplayers 的所有标准标量字段，消除 §1.3 列出的 5 个类型的字段重叠和命名不一致。

**类型设计**：Character 只含 oblplayers 标准标量字段；战斗上下文派生字段（inCombat/active/done/myorder）拆到独立的 `CombatState` 类型，挂在 Character 的可选字段上。这样 `mergeEnemies` 不需要碰战斗字段，`mergeCombatContext` 不需要碰标准字段，职责清晰：

```ts
/** oblplayers 标准标量字段（玩家与 NPC 共用） */
interface Character {
  // 身份
  pid: number;
  type: number;           // 0 = player, >0 = enemy type
  name: string;
  gd: string;             // 性别
  icon: string;

  // 战斗状态
  action: string;         // '' / 'battle' / ...
  bid: number;            // 战场编号（qid）

  // 属性（玩家与NPC共用）
  hp: number;
  mhp: number;            // max hp（统一用 oblplayers 表字段名 mhp）
  sp: number;
  msp: number;            // max sp
  att: number;
  def: number;

  // AP
  ap: number;
  max_ap: number;         // 统一用表字段名 max_ap

  // 位置
  pgroup: number;
  pls: number;

  // 进度
  lvl: number;
  exp: number;
  state: number;          // 0 = alive, 其他 = 死亡/逃跑/隐藏

  // 道具
  itemmaxslots: number;

  // 装备索引（7 槽模板 ID，轻量级标量，供快速查询角色装备了什么）
  wepid: string;           // 主武器
  wep2id: string;          // 副武器
  arbid: string;           // 身体防具
  arhid: string;           // 头部
  araid: string;           // 饰品1
  arfid: string;           // 饰品2
  artid: string;           // 特殊

  // 道具索引（从 itempara[].itmid 提取的模板 ID 列表，轻量级）
  itemIds: string[];

  // 发现状态（仅 enemies scope 返回；player_info 不返回此字段，见 §3.3）
  discovered: boolean;

  // 战斗上下文派生（由 combat_context 派生，非 oblplayers 字段）
  combat?: CombatState;
}

/** 战斗上下文派生状态（由 mergeCombatContext 写入，mergeCombatContext(null) 时置 undefined） */
interface CombatState {
  inCombat: boolean;      // 是否在当前战斗中
  active: boolean;        // 战斗中是否活跃（entities 过滤用）
  done: number;           // 战斗队列完成标记
  myorder: number;        // 先攻顺序
}
```

**装备索引 vs 装备 JSON 大字段**：

oblplayers 表的 7 个装备槽各有 7 个字段（以武器槽为例：`wepid` 模板 ID + `wep`/`wepk`/`wepe`/`weps`/`wepsk`/`weppara` 运行时参数）。Character 只纳入**轻量级的模板 ID 索引**（`wepid`/`wep2id`/`arbid`/`arhid`/`araid`/`arfid`/`artid`），不纳入完整的运行时参数 JSON。同理，`itempara` 是复杂嵌套数组，Character 只纳入从中提取的 `itemIds`（`itempara[].itmid` 列表），不纳入完整的道具参数。

| 层级 | 字段 | 所属 | 加载方式 |
|------|------|------|----------|
| **装备索引**（轻量，纳入 Character） | `wepid`/`wep2id`/`arbid`/`arhid`/`araid`/`arfid`/`artid`/`itemIds` | oblplayers 标量/提取数组 | enemies scope + player_info scope 均返回 |
| **装备运行时参数**（重，不纳入 Character） | `wep`/`wepk`/`wepe`/`weps`/`wepsk`/`weppara`（各槽同理） | oblplayers 各字段 | player_info scope 按需加载，playerStore 解析 |
| **道具完整参数**（重，不纳入 Character） | `itempara`（完整嵌套结构） | oblplayers text 字段 | player_info scope 按需加载，playerStore 解析 |
| **其他 JSON 大字段**（重，不纳入 Character） | `tacpara`/`skillpara`/`oblpara` | oblplayers text 字段 | player_info scope 按需加载，playerStore 解析 |

装备索引和道具索引是"角色装备了什么"的关键标识，消费者（如战斗判断、装备检视入口）需要它们来决定后续行为。完整运行时参数是"装备的具体属性"，只在玩家自身查看装备详情时需要，按需通过 `player_info` scope 加载。

这不是"玩家专属属性"——NPC 行也有这些字段，只是当前前端不需要解析 NPC 的装备运行时参数 JSON。未来如果需要 NPC 装备检视，可通过扩展 API scope 实现。

**命名统一**：Character 类型统一使用 oblplayers 表字段名（mhp / max_ap）。后端 API 改造需同时统一三处命名（详见 §6.2）：
- `combat_context.combatants` 的 `maxHp` / `maxAp` → `mhp` / `max_ap`（`CombatantViewModel` / `CombatTargetViewModel` / `CombatantView` 同步）
- battlelog v2 事件流中 `CombatantSnapshot` 的 `max_hp` → `mhp`（前后端同步）

**类型转换**：API 返回的数值字段在 enemies/player_info scope 中是字符串（如 `"hp":"398"`），在 combat_context 中是数字（PHP `(int)` 强转）。`merge*` 方法在写入 Character 时统一做 `Number()` 转换，使 Character 的数值字段始终是 `number` 类型。消费者不再需要 `parseInt(String(...))` 兜底。

### 3.3 数据流入路径

CharacterHub 是写入的唯一入口，后端所有数据源统一写入：

```ts
// 来自 enemies scope（完整地图投影 roster）
characterStore.replaceMapEnemies(enemies: Enemy[])

// 来自 combat_targets（只补资料，不拥有地图可见性）
characterStore.mergeEnemyPatches(enemies: Enemy[])

// 来自 player_info scope（玩家自身 + 战斗上下文）
characterStore.mergePlayer(playerInfo: PlayerInfo)
characterStore.mergeCombatContext(context: CombatViewModel | null)

// 来自 heartbeat changed_scopes（增量刷新）
// enemies 变化 → dataManager.fetch('enemies') → replaceMapEnemies
// player_info 变化 → dataManager.fetch('player_info') → mergePlayer + mergeCombatContext
```

`merge*` 方法的语义：

- **replaceMapEnemies**：合并角色资料，并原子替换 authoritative map enemy PID 集合。当前区域同一 NPC 从完整快照缺席，语义就是不再可见；Character 资料记录可以继续缓存。
- **mergeEnemyPatches**：只补角色资料，不修改地图 PID 集合；供 `combat_targets` 等候选投影使用。
- **mergePlayer**：合并更新——已存在的角色更新字段，新角色插入。
- **mergeCombatContext**：替换更新——用新数据完整覆盖 `Character.combat` 字段。

### enemies 完整快照与地图 roster（关键）

enemies scope 返回当前地图允许投影的 NPC：探索态是 `discovered=1`；战斗态还可包含当前 qid 的 active combat-visible NPC。它是完整 roster，不是增量 patch。NPC 在同一 pgroup 内移出视野后也会从列表缺席，因此不能只清理跨区域记录。

因此当前实现不再用“只清跨区”的 `mergeEnemies` 推断可见性，而是直接替换 roster：

```ts
function replaceMapEnemies(enemies: Enemy[]): void {
  mergeEnemyPatches(enemies);
  mapEnemyPids.value = new Set(enemies.map(e => Number(e.pid)));
}
```

MapGrid 的实体集合由“存活玩家 + `mapEnemyPids` 对应的存活角色”派生。`aliveList` 只表示资料缓存中的存活角色，不再等价于地图 roster。数据库标量必须用数值语义归一化，不能用 `Boolean(enemy.discovered)`，因为字符串 `"0"` 在 JavaScript 中为 true。

### enemies roster 的战斗中特殊行为

后端 `obl_state_handle_enemies()` 在玩家处于战斗中时，可把当前 qid 的 **active** NPC 加入 enemies 列表，即使 `discovered=0`，用于 combat-visible 权威投影。inactive/dead/left actor 不应靠 authoritative roster 保活，而由 PresentationScene/session 维持到退场演出结束。这意味着：

1. 战斗 NPC 同时出现在 enemies 列表和 combat_context.combatants 中——两个数据源分别补标准字段与战斗派生字段。
2. `combat_targets` 包含 left/blocked/joinable 等候选时只能调用 `mergeEnemyPatches`，不能改变 `mapEnemyPids`。

### mergePlayer 的字段处理

`player_info` 与 `enemies` scope 对装备索引的返回格式不同，`mergePlayer` 需要做格式适配：

| 字段 | enemies scope（标量） | player_info scope（结构化对象） |
|------|----------------------|-------------------------------|
| `wepid` | `enemy.wepid`（标量） | `playerInfo.equipment.wep.item_id` |
| `arbid` | `enemy.arbid` | `playerInfo.equipment.arb.item_id` |
| 其他装备槽 | `enemy.wep2id`/`arhid`/... 同理 | `playerInfo.equipment.wep2.item_id`/`arh.item_id`/... 同理 |
| `itemIds` | `enemy.itemIds`（后端已提取数组） | 从 `playerInfo.itempara[].itmid` 提取 |

`mergePlayer` 的处理：
- **装备索引**：从 `playerInfo.equipment.{slot}.item_id` 提取 7 槽模板 ID，从 `playerInfo.itempara` 提取 `itemIds`。
- **设置 `discovered: true`**：`player_info` 不返回此字段，mergePlayer 主动为玩家角色设置 `discovered: true`（玩家自身始终可见，enemies 列表不含玩家不会由 mergeEnemies 设置）。
- **其他标准标量字段**（hp/mhp/sp/msp/att/def/ap/max_ap/pgroup/pls/lvl/exp/state/itemmaxslots）正常写入。

### mergeCombatContext 的替换语义

> **combatants 包含玩家自身**：后端 `obl_state_build_combat_context` 遍历战斗队列（`obl_fetch_queue_all_by_qid`）生成 combatants，玩家是战斗发起者在队列中，因此 combatants 包含 type===0 的玩家元素（仅 `valid_targets` 在构建时跳过玩家，见 [obl_state_handlers.php:185](file:///d:/wamp64/www/phpdts/oblivions/include/api/obl_state_handlers.php#L185)）。这意味着 mergeCombatContext 会为玩家写入 `CombatState.inCombat=true`，entities 渲染时玩家 actor 不会半透明。

`mergeCombatContext(context)` 完整覆盖 `Character.combat` 字段：

1. 将 combatants 的 pid 集合收集为 `combatantPids`。
2. 对 `combatantPids` 中的角色：用 combatant 的 `active/done/myorder` 写入 `Character.combat = { inCombat: true, active, done, myorder }`。同时用 combatant 的标准字段（hp/mhp/ap/max_ap/pls/state）覆盖 Character 的对应字段（combat_context 是 `(int)` 强转的数字，比 enemies scope 的字符串更准确）。
3. 对不在 `combatantPids` 中的角色：`Character.combat = undefined`（置空，而非保留旧值）。
4. `context === null` 时：所有角色 `Character.combat = undefined`。

### 3.4 数据流出路径

消费者从 CharacterHub 读取，不再直接访问 mapStore.enemies / combatContext.combatants：

```ts
// entities.ts — 派生地图实体列表（含 inCombat 标记供渲染层半透明）
const entities = computed(() => characterStore.aliveList.map(c => ({
  id: c.type === 0 ? 'player' : `enemy-${c.pid}`,
  kind: 'actor',
  actorKind: c.type === 0 ? 'player' : 'enemy',
  pls: c.pls,
  img: c.type === 0 ? '/img/1.png' : `/img/n_${c.type}.png`,
  imgHeightRatio: 1.25,
  inCombat: c.combat?.inCombat ?? false,
})));

// PreloadArea — 射程判断与目标显示
// getCombatPlayer() → characterStore.player（玩家位置/区域）
// getCombatTarget(pid) → characterStore.getCharacter(pid)（目标 pls/pgroup/state）
// isEnemyInSkillRange() 射程判断逻辑保留，数据源改为 CharacterHub
const player = computed(() => characterStore.player);
// defaultTargetPid 仍来自 combatContext.defaultTargetPid（§4.4 改造表：不变）
// data.enemyPid 由 battle.ts 的 resolveEnemyPid 决定（§4.6 第 4 点：保持原逻辑）

// refreshEnemyLocation / BattleHeader — 敌人位置/名称显示
const enemyChar = computed(() => characterStore.getCharacter(battleStore.currentEnemyPid));
const enemyLocation = computed(() => enemyChar.value?.pls ?? null);
// enemyName 优先用 battleStore.enemyName（来自 battlelog segment，更及时），回退到 CharacterHub
const enemyName = computed(() => battleStore.enemyName || enemyChar.value?.name || '');
```

### 3.5 combatContext 的角色与范畴声明

`combatContext` 不再直接被消费者读取实体字段。它的 combatants 数据被 `mergeCombatContext` 消费后写入 CharacterHub，消费完即丢。

`battleStore.combatContext` 仍保留，用于：
1. `defaultTargetPid`（PreloadArea 默认目标）
2. `state / currentActorPid / canSubmitTurn`（战斗状态机）
3. `roundNum`（回合显示）
4. `validTargets`（**保留**，PreloadArea 射程判断的优化数据源——见下方）

不用于实体可见性、位置、HP/AP 显示——这些全部从 CharacterHub 读取。

#### validTargets 的处理

`combatContext.validTargets` 是后端经过战斗规则过滤的合法目标子集（type>0、state=0、active、非玩家）。它不是"过滤"，而是"经过战斗规则筛选后的合法目标集合"，包含 pgroup/pls/hp 等数据。

CharacterHub 建立后，validTargets 的处理有两种方案：

- **方案 A（采用）**：保留 `combatContext.validTargets` 不动，PreloadArea 的 `getCombatTarget()` 仍优先查 validTargets，回退到 `characterStore.getCharacter(pid)`。validTargets 作为"战斗规则结果"的快照，CharacterHub 作为"角色完整状态"。
- **方案 B（已否决）**：移除 validTargets，PreloadArea 直接从 `characterStore.enemyList` 读取并自行做战斗规则判断（pgroup 匹配 + active + state）。否决理由：把后端规则搬到前端，维护成本高且易不一致。

本设计案采用方案 A：validTargets 保留在 combatContext 中，PreloadArea 继续用它做射程判断的目标查找。

**方案 A 的时序差说明**：validTargets（来自 combat_context）和 CharacterHub（来自 enemies scope）对同一敌人的 pgroup/pls/state 可能因刷新时序差不一致。但 PreloadArea 的 `isEnemyInSkillRange` 用 CharacterHub 判断射程，`getCombatTarget` 优先查 validTargets——两者分别用于"射程计算"和"目标信息显示"，不构成逻辑冲突。后端 `battle.submit_turn` 不依赖 validTargets（靠 tag 规则逐 action 校验，见 [combat.target.php](file:///d:/wamp64/www/phpdts/oblivions/include/game/combat/combat.target.php) `combat_target_resolve_pid` 直接按 pid 查 DB），所以前端时序差不影响后端验证。

#### battlelog v2 事件流 snapshot 的范畴声明

`BattleModal.vue` 和 `battle-actor-executor.ts` 的数据来自 `battleStore.currentSegment` 中的 `CombatantView.snapshot` 和 `effect.delta`，是**事件回放数据**（历史快照 + 增量 delta），不是"当前状态"。

**这些数据不在 CharacterHub 统一范围内**。原因：
1. snapshot 是事件发生时的瞬时状态，CharacterHub 是当前状态——两者性质不同。
2. BattleModal 播放 battlelog 时按事件流顺序回放 HP 变化，如果从 CharacterHub 读会丢失"事件顺序"语义。
3. battle-actor-executor 通过 actor 控制器的 DOM 位置驱动动画，不需要 pls 查找。

因此 BattleModal 和 battle-actor-executor **不改造**，保持从 currentSegment 读取。CharacterHub 只统一"当前状态"数据源，不统一"事件回放"数据源。

### 4.1 新增 characterStore

文件：`vex-vue/src/stores/character.ts`

```ts

  const characters = reactive<Map<number, Character>>(new Map());

  // ── 写入 ──

  function mergePlayer(playerInfo: PlayerInfo): void { /* 见 §3.3 discovered 跳过 */ }
```

**computed 设计要点**：
- `aliveList` 只过滤 `state === 0`，不过滤 `active`——这是"所有存活可见实体"，供 entities 渲染。
- 不设 `combatantList`——当前无消费者，违反"不为假设未来需求设计"原则。需要"战斗中活跃角色"列表时，消费者可自行从 `aliveList` 按 `c.combat?.inCombat && c.combat.active` 过滤。
- entities.ts 改造后用 `aliveList`（显示所有存活实体），不再区分战斗/探索模式。**行为变化**：原代码战斗模式过滤 `!combatant.active || Number(combatant.state) > 0`（[entities.ts:33](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/entities.ts#L33)），改造后用 `aliveList`（过滤 `state === 0`，语义等价但实现位置不同），非 active 的战斗 NPC（如已退出战斗但未死亡的逃跑者）会显示在地图上，通过半透明表达"非活跃"状态。这符合设计案 1.1"消除战斗中实体消失"的目标。

## 5. 边界情况

### 5.1 预装填窗口期

`currentMode='battle'` 但后端 `action` 尚未 `'battle'` 时 `combatContext` 为 null。`mergeCombatContext(null)` 会将所有角色 `Character.combat` 置 `undefined`（`inCombat` 隐含为 false）。实体正常显示，所有敌人可瞄准——与探索态一致。

### 5.2 战斗中敌人死亡/逃跑

`mergeCombatContext` 会将死亡敌人的 `state` 更新到 CharacterHub。`characterStore.aliveList` 自动过滤掉 `state !== 0` 的角色，死亡敌人从地图消失（触发淡出动画）。

> **注意**：后端 `enemies` scope 在玩家战斗中时会强制把战斗队列里的所有 NPC 加入列表（包括 `state>0` 的死亡 NPC，见 §3.3）。这些死亡 NPC 会被 `mergeEnemies` 写入 CharacterHub，但 `aliveList` 的 `state===0` 过滤会排除它们——不会错误显示。

### 5.3 非战斗 NPC 的 idle 移动

heartbeat `changed_scopes: enemies` 触发 `refreshMapEnemies()` → `mergeEnemies()`。非战斗 NPC 的位置更新到 CharacterHub，entities 自动刷新。战斗中玩家能看到非战斗 NPC 移动。

### 5.4 玩家位置同步（curLoc 与 player_info.pls 的分裂）

玩家位置有两个来源：
- `mapStore.curLoc`：来自 `game_map` scope 的 `currentLocation`（[map.ts:93](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/map.ts#L93)）
- `playerStore.pls` / `playerInfo.pls`：来自 `player_info` scope

两者是同义字段但来源不同。CharacterHub 中玩家角色的 `pls` 由 `mergePlayer(playerInfo)` 写入（来自 player_info.pls）。

**刷新时序**：玩家移动后，`commandQueue` 动作触发 `game:action-completed` / `game:tick-advanced` 事件 → `refreshBattle` 同时拉取 player_info 并经 `loadMap` 刷新 game_map。game_map 通常先到（地图切换是移动的主效果），player_info 后到（包含战斗上下文等重数据）。在两次刷新之间，`mapStore.curLoc` 已更新但 `characterStore.player.pls` 仍是旧值。

**处理策略**：
- entities 渲染玩家 actor 时用 `characterStore.player?.pls ?? mapStore.curLoc`（player 未加载时回退到 curLoc，避免初始化或极端时序下玩家 actor 消失）。
- `mapStore.curLoc` 仍保留，用于地图渲染本身（地图背景、区域切换）和上述回退。
- 接受短暂不一致窗口（通常 < 1 个 heartbeat 周期）——`player_info` 刷新后自动对齐。
- 如果不一致导致体验问题，可在 `mergePlayer` 时同步更新 `mapStore.curLoc`，但这会引入 store 间耦合，不推荐。

### 5.5 数据一致性

后端 API 改造后（§6.1），enemies scope 和 combat_context 都返回完整标准字段。`mergeEnemies` / `mergePlayer` 是"合并更新"语义：用新数据中的字段覆盖旧值（§3.3）。`mergeCombatContext` 是"替换更新"语义：完整覆盖 `Character.combat` 字段。

`mergeCombatContext(null)` 时（战斗结束），将 `Character.combat` 置 `undefined`（`inCombat`/`active`/`done`/`myorder` 全部隐含为 falsy/undefined）。标准属性字段（hp/mhp/ap/max_ap 等）不清空——它们仍是角色的当前状态，只是不再标记为战斗中。下次 enemies scope 刷新会更新这些字段。

### 5.6 战斗中 enemies scope 的写入顺序与类型安全

战斗中 enemies scope 的特殊行为（后端强制把战斗队列 NPC 加入 enemies 列表）已在 §3.3"mergeEnemies 的战斗中特殊行为"说明。此处补充写入顺序的类型安全问题：

**写入顺序与类型安全**：enemies scope 返回字符串数值，combat_context 返回 `(int)` 强转的数字。无论哪个先到，§3.2 要求所有 `merge*` 方法统一做 `Number()` 转换，确保 Character 字段始终是 `number` 类型，避免字符串覆盖数字导致的类型回退。

## 6. 后端 API 改造

### 6.1 enemies scope 返回完整标准字段

当前 `obl_state_simplify_enemy_data()` 主动丢弃了大部分字段。改造为返回所有标准标量字段（与 player_info 一致），使前端 CharacterHub 能从单一数据源获取完整角色数据：

```php
function obl_state_simplify_enemy_data(&$enemy) {
    return array(
        'pid'        => $enemy['pid'],
        'type'       => $enemy['type'],
        'name'       => $enemy['name'],
        'gd'         => $enemy['gd'],
        'icon'       => $enemy['icon'],
        'action'     => $enemy['action'],
        'bid'        => $enemy['bid'],
        'hp'         => $enemy['hp'],
        'mhp'        => $enemy['mhp'],
        'sp'         => $enemy['sp'],
        'msp'        => $enemy['msp'],
        'att'        => $enemy['att'],
        'def'        => $enemy['def'],
        'ap'         => $enemy['ap'],
        'max_ap'     => $enemy['max_ap'],
        'pgroup'     => $enemy['pgroup'],
        'pls'        => $enemy['pls'],
        'lvl'        => $enemy['lvl'],
        'exp'        => $enemy['exp'],
        'state'      => $enemy['state'],
        'itemmaxslots' => $enemy['itemmaxslots'],
        // 装备索引（7 槽模板 ID，轻量级）
        'wepid'      => $enemy['wepid'],
        'wep2id'     => $enemy['wep2id'],
        'arbid'      => $enemy['arbid'],
        'arhid'      => $enemy['arhid'],
        'araid'      => $enemy['araid'],
        'arfid'      => $enemy['arfid'],
        'artid'      => $enemy['artid'],
        // 道具索引（从 itempara 提取 itmid 列表）
        // itempara 是 JSON 数组，下标 0 = itm0 手持缓存槽，1~itemmaxslots = 普通槽
        // array_filter 过滤空槽位（itmid 为空字符串/null），itemIds 含所有有道具的槽位（含 itm0）
        'itemIds'    => isset($enemy['itempara']) && is_array($enemy['itempara'])
                        ? array_values(array_filter(array_column($enemy['itempara'], 'itmid')))
                        : array(),
        'discovered' => $enemy['discovered'],
    );
}
```

**返回装备索引，不返回装备运行时参数 JSON**：装备索引（`wepid`/`wep2id`/`arbid`/`arhid`/`araid`/`arfid`/`artid`/`itemIds`）是轻量级标量/数组，enemies scope 返回它们供 CharacterHub 快速查询角色装备了什么。不返回的是装备运行时参数（`wep`/`wepk`/`wepe`/`weps`/`wepsk`/`weppara` 各槽同理）和完整 `itempara`/`tacpara`/`skillpara`/`oblpara` JSON 大字段——这些按需通过 player_info 或未来新增的 inspection scope 加载。

### 6.2 统一 max-HP / max-AP 字段命名（三处）

项目中有三种 max-HP 命名风格（见 §1.3）：`mhp`（表字段名）、`maxHp`（驼峰，combat_context）、`max_hp`（下划线小写，battlelog v2 snapshot）。统一为 oblplayers 表字段名 `mhp` / `max_ap`，需改三处后端函数 + 前端类型：

#### 6.2.1 `obl_state_combatant_view()` — combat_context.combatants

```php
// 修改前（obl_state_combatant_view，变量名 $pdata）
'maxHp' => isset($pdata['mhp']) ? (int)$pdata['mhp'] : 0,
'maxAp' => isset($pdata['max_ap']) ? (int)$pdata['max_ap'] : 0,

// 修改后
'mhp'    => isset($pdata['mhp']) ? (int)$pdata['mhp'] : 0,
'max_ap' => isset($pdata['max_ap']) ? (int)$pdata['max_ap'] : 0,
```

前端 `CombatantViewModel` 类型（[api.ts:93-95](file:///d:/wamp64/www/phpdts/vex-vue/src/types/api.ts#L93-L95)）同步：`maxHp` → `mhp`，`maxAp` → `max_ap`。

#### 6.2.2 `obl_state_target_view()` — combat_context.validTargets

validTargets 元素（`CombatTargetViewModel`）也用 `maxHp`。该函数接收的是 `obl_state_combatant_view` 的输出数组（含 `maxHp` 键），不是原始 pdata（含 `mhp` 键）。同样改为 `mhp`（validTargets 无 maxAp 字段，仅改 maxHp）：

```php
// 修改前（obl_state_target_view）
'maxHp' => (int)$combatant['maxHp'],

// 修改后（combatant_view 输出键名已改为 mhp，此处同步读取 mhp）
'mhp'    => (int)$combatant['mhp'],
```

前端 `CombatTargetViewModel` 类型同步。

#### 6.2.3 battlelog v2 事件流 snapshot — CombatantSnapshot

battlelog v2 事件 payload 中的 `CombatantSnapshot` 用 `max_hp`（下划线小写，[api.ts:365-376](file:///d:/wamp64/www/phpdts/vex-vue/src/types/api.ts#L365-L376)）。后端构造位置在 [combat.log.php](file:///d:/wamp64/www/phpdts/oblivions/include/game/combat/combat.log.php) 第 39-56 行 `combat_log_v2_combatant_snapshot`，字段映射 `max_hp ← $data['mhp']`、`max_ap ← $data['max_ap']`。把 `max_hp` 改为 `mhp`（`max_ap` 已是目标命名，不变）。

前端 `CombatantSnapshot` 类型同步：`max_hp` → `mhp`，`max_ap` 保持不变。

#### 6.2.4 前端 `CombatantView` 类型同步

`CombatantView`（[battle-director-v2.ts:12-21](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle-director-v2.ts#L12-L21)）也用 `maxHp` / `maxAp`。虽然它由前端 battle-director 从 battlelog 派生，但字段命名应与 CharacterHub 一致：`maxHp` → `mhp`，`maxAp` → `max_ap`。

#### ⚠️ 破坏性提示

这三处改动是 **breaking change**（字段重命名，非"多返回字段"）。前端类型定义和所有访问点（`combatTarget.maxHp`、`target.maxHp`、`snapshot.max_hp` 等）必须与后端同步修改，否则会读到 `undefined`。这与 §6.1 的 enemies scope 字段扩展（确实是"多返回字段，前端暂时忽略"）性质不同——**不能放在同一阶段**，必须独立成阶段（见 §9 阶段 0 拆分）。

### 6.3 combat_context.combatants 可精简

CharacterHub 建立后，`combat_context.combatants` 的角色数据（hp/ap/state/pls 等）已被 `mergeCombatContext` 消费并写入 CharacterHub。combatants 可以精简为只返回 pid 列表 + 战斗专属字段（active/done/myorder），不再重复返回 hp/mhp/ap/max_ap/pls 等标准字段（这些从 CharacterHub 读取）。

但这不是必须的——保留完整 combatants 数据作为 merge 的数据源也可以，只是有数据冗余。当前保留完整 combatants（不精简），未来如 combatants 数据量成为性能瓶颈再考虑精简。

**精简后的影响**：§3.3 mergeCombatContext 当前依赖 combatants 的标准字段（hp/mhp/ap/max_ap/pls/state，`(int)` 强转的数字）覆盖 enemies scope 的字符串值，提供"更准确的数字"。若精简 combatants，这层数字覆盖消失，Character 的数值字段完全依赖 enemies scope（经 `Number()` 转换）。由于 §3.2 已要求所有 merge 方法做 `Number()` 转换，字符串与数字的语义一致，精简后数值准确性可接受——enemies scope 的值同样是后端真值，只是表现形式不同。

### 6.4 player_info 标准字段迁移到 CharacterHub（收益与代价）

player_info 返回的玩家标准字段（hp/mhp/sp/msp/att/def/ap/max_ap/...）也是 Character 数据。CharacterHub 建立后，`mergePlayer(playerInfo)` 会将这些字段写入玩家自身的 Character 记录。

**当前状态**：[player.ts:26-37](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/player.ts#L26-L37) 中这些字段已是 computed（从 `playerInfo` 派生），不是独立 ref：

```ts
const hp = computed(() => playerInfo.value?.hp ?? 0);
const mhp = computed(() => playerInfo.value?.mhp ?? 0);
// ... 等
```

**迁移收益**：
- 所有 HP 显示统一从 `characterStore.player?.hp` 读取，消除"玩家 HP 从 playerStore、敌人 HP 从 combatContext"的分裂。
- BattleHeader / BattleModal 等需要"双方 HP"的场景可以统一数据源（BattleModal 仍用 battlelog snapshot，但 BattleHeader 可统一）。

**迁移代价**：
- 所有 `playerStore.hp` 访问点需改为 `characterStore.player?.hp`，引入 `undefined` 检查（player 可能未加载）。
- playerStore 的 computed 是同步的（playerInfo 已加载即返回），`characterStore.player` 是 Map 查找，性能差异可忽略但有响应式依赖变化。

**迁移决策**：建议迁移，但作为阶段 3 的收尾工作（§9 阶段 3 第 4 点）。playerStore 保留装备运行时参数解析（equipment 各槽的 name/kind/exp/sk/skk/para + itempara 完整结构 + skills/tacpara/oblpara）和玩家 UI 派生状态（如 `isInBattle` / `canAct` 等）。标准标量字段 + 装备索引字段全部从 CharacterHub 读取。迁移前需列出所有 `playerStore.hp` 等访问点清单，逐个替换。

**命名统一**：[player.ts:31](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/player.ts#L31) 的 `maxAp` computed（从 `playerInfo.value?.max_ap` 派生）命名是 `maxAp`，与 Character 类型的 `max_ap`（§3.2）不一致。迁移后所有 `playerStore.maxAp` 访问点改为 `characterStore.player?.max_ap`，命名统一为表字段名 `max_ap`。

### 阶段 1：新增 CharacterHub（不破坏现有逻辑）
