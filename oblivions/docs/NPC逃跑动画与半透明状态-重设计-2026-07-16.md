## 1. 原设计案的偏差

2026-07-14 设计案的目标仍然成立——逃跑 NPC 应在 `combatant_cleared` 阶段先播退场动画，再让战报回放（`modal_text`）出场；逃跑 NPC 在战斗期间应保持半透明。但原方案的实现路径已与当前代码基准脱节，主要偏差有三处。

### 1.1 引入 `escape-relocate` 新动画 kind 是过度设计

原方案在 `ActorCommand` 联合类型中新增 `escape-relocate` 变体，并在 `useActorRuntime.play` 中实现 `fadeOut → gsap.set anchor → arriveAnim` 三段串行 timeline。

**但该三段语义可由现有两个 command 组合达成**：先 `lease.play({ kind: 'fade' })`，`await finished` 后再 `lease.play({ kind: 'move', target, tier: 'long' })`。`move` 的 `tier='long'` 路径已经做了 `gsap.set(anchor, { x, y }) + arriveAnim(elements)`，与原方案的 teleport + arrive 完全等价；`fade` 已经做了 `fadeOut(elements.visibility)`。两段组合的最终视觉效果与 `escape-relocate` 一致：alpha 1→0（原格淡出）→ teleport → alpha 0→1 + scale 0.3→1（退避格弹起）。

`escape-relocate` 唯一独有的代码是 `onCompleted = () => { this.currentAnchor = command.target }`，但这个语义已经被 `move` 的 `onCompleted` 覆盖——`move` 完成时同样将 `currentAnchor` 设为 `command.target`。

引入新 kind 还会污染 `ActorCommand` 联合类型、`requiredChannels` 映射、`debugCommandName`，并要求 `actor-runtime.fixture.ts` 增加新 case 的契约测试。这是为 1 个调用点（`playCombatantCleared` retreat 分支）扩展全局动画语法，违反"最小实现"原则。

### 1.2 半透明机制与动画耦合，导致语义被"半透明地淡出"绑死

原方案 4.4 节明确写出："半透明地淡出比不透明地淡出更自然——NPC 已经不活跃了"。这个判断把"半透明状态"和"逃跑动画"绑成了一个不可分割的视觉单元。

但实际上这两层信号是正交的：

- **半透明状态**：表达"该 NPC 已不是战斗成员"，由后端 `active=false` 字段驱动，应在战斗期间持续生效，与动画进度无关。
- **逃跑动画**：表达"NPC 从战斗格退到退避格"，是一次性位移演出。

把二者解耦后，半透明在动画开始前就已生效（`mergeCombatContext` 同步执行早于 battlelog 异步播放），动画期间自然叠加 `filter: opacity(0.5) × GSAP alpha`。原方案的视觉结果（半透明地淡出、半透明地弹起、持续半透明）在解耦后依然成立，且不依赖任何额外协调逻辑。

### 1.3 边界案例（动画被取消）被推迟处理

原方案 6.4 节承认：`escape-relocate` 被 cancel 时若 alpha<1，NPC 可能在退避格不可见；方案选择"暂不处理，后续观察是否需要补"。

这个推迟不必要。`startCommit` 的现有 fall-through 路径已经会播 `reset-visible`（alpha→1），能完美兜底取消场景。原方案中 `startCommit` retreat 路径需要"跳过 move 直接 release"，反而绕过了 `reset-visible` 兜底，才需要单独讨论取消风险。**让 retreat 路径复用现有 fall-through 的 `reset-visible` 兜底**，边界案例自然消解。

## 2. 框架基准研判：多人战斗中逃跑 NPC 的视觉状态缺失

### 2.1 问题描述

多人战斗中，玩家与 NPC A 继续战斗，NPC B 逃跑。在 NPC B 逃跑后的后续战斗回合里，NPC B 视觉上依然被视作参战 NPC（不半透明），玩家无法直观区分"已逃跑"和"仍活跃"的 NPC。

### 2.2 数据流追踪与根本原因

**后端链路（已正确实现）**：

1. `combat_effect_escape` → `combat_state_mark_escaped`（[combat.state.php](file:///d:/wamp64/www/phpdts/oblivions/include/game/combat/combat.state.php#L67)）：写 `battle_cache['combatants'][pid]=0` + `tag_mutations[pid]['escaped']=true`，**不修改 `state` 字段**；同时 `combat_effect_escape` 修改 `$ctx->actor_data['pls'] = $retreat_target`（退避格）
2. `combat_state_clear`（[combat.state.php#L119](file:///d:/wamp64/www/phpdts/oblivions/include/game/combat/combat.state.php#L119)）：`reason='escaped'` 时 `state=0`（存活）、`action=''`（清空战斗状态）、`ap=max_ap`；调 `battle_queue_exit` + `obl_save_player`（**写入数据库**，下一回合 `obl_fetch_playerdata_batch` 能读到新 pls）
3. `battle_queue_exit`（[battle.queue.func.php#L233](file:///d:/wamp64/www/phpdts/oblivions/include/game/battle/battle.queue.func.php#L233)）：调 `obl_queue_set_active(pid, qid, 0)`，标记 `active=0`，**不删行、不清 bid**（bid 保留由队列解散时统一清理 `battle_disband_cleanup`）
4. 下一回合 `obl_state_build_combat_context`（[obl_state_handlers.php#L167](file:///d:/wamp64/www/phpdts/oblivions/include/api/obl_state_handlers.php#L167)）：遍历 `obl_fetch_queue_all_by_qid($qid)`（不过滤 `active=0`）——逃跑 NPC 仍在 queue 中（行未删除），仍被加入 `combatants` 数组；`obl_fetch_playerdata_batch` 从数据库读到逃跑 NPC 的新 pls（退避格）
5. `obl_state_combatant_view`（[obl_state_handlers.php#L136](file:///d:/wamp64/www/phpdts/oblivions/include/api/obl_state_handlers.php#L136)）：`'active' => $qrow ? ((int)(isset($qrow['active']) ? $qrow['active'] : 1) === 1) : ...`——逃跑 NPC 的 `qrow['active']=0`，所以 `active=false` ✓；`pls` 字段返回退避格 ✓

**前端数据层链路（已正确实现）**：

8. `CombatState.active`（[types/character.ts](file:///d:/wamp64/www/phpdts/vex-vue/src/types/character.ts)）：字段声明正确 ✓
9. `entities` computed（[entities.ts#L35](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/entities.ts#L35)）：映射 `inCombat: c.combat?.inCombat ?? false`——数据层正确响应 `characterStore` 变化

**前端视图层链路（断裂点——`displayEntities` 冻结）**：

10. `useMapEntities.stopAuthorityWatch`（[useMapEntities.ts#L330](file:///d:/wamp64/www/phpdts/vex-vue/src/composables/useMapEntities.ts#L330)）：`entitiesStore.entities` 变化时调用 `presentationScene.syncAuthoritative(entities, revision)`
11. **根本原因**：`presentationScene.syncAuthoritative`（[presentation-scene.ts#L97](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/presentation-scene.ts#L97)）：在 `phase !== 'idle'`（战斗中 `phase='playing'`）时**不 apply snapshot**，存入 `pendingAuthoritativeSnapshot`，等到 `finishRebase` 恢复 idle 时才 apply
12. `useMapEntities.stopEntitiesWatch`（[useMapEntities.ts#L336](file:///d:/wamp64/www/phpdts/vex-vue/src/composables/useMapEntities.ts#L336)）：监听 `presentationScene.snapshot.entities`，战斗中 snapshot 不变，watch 不触发，`displayEntities` 不更新

**关键观察**：
- 逃跑 NPC 的 `state` 字段仍为 0（存活），所以 `mapVisibleList`（[character.ts#L262](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/character.ts#L262)）仍包含它，`displayEntities` 仍渲染它
- NPC B 在后续回合确实出现在地图上，且 `entity.inCombat=true`（`displayEntities` 冻结的旧值）但不半透明——**问题真实存在**
- `presentationScene` 的 phase 机制是为了隔离 pls 变化（防止 `useMapEntities` 触发 `playWorldMove` 与战斗动画冲突），但同时也冻结了 `displayEntities` 中的所有字段（包括 `inCombat`），导致视图层无法响应数据层的变化

### 2.3 框架基准 vs 边界案例研判

**这是框架基准问题，不是边界案例**。理由：

1. **核心战斗流程**：多人战斗中部分 NPC 逃跑、剩余 NPC 继续战斗是大逃杀游戏的常见场景，不是异常路径。

2. **持续状态而非瞬态**：`mergeCombatContext` 在战斗中每个回合都被调用（链路：`flushAuthoritativeStores` → `publishAuthoritativePlayerInfo` → `setPlayerInfo` → `syncCharacterProjection` → `mergeCombatContext`，见 [player.ts#L102-106](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/player.ts#L102)），逃跑 NPC 每回合都被重新设为 `inCombat=true, active=false`。这不是单次动画的边界情况，而是贯穿多个回合的持续视觉状态。

3. **视图层与数据层脱节**：后端已正确传递 `active=false` 信号到 `Character.combat.active`（`CombatantViewModel.active` → `mergeCombatContext` → `CombatState.active`），前端数据层已正确接收。但 `presentationScene` 的 phase 机制为了隔离 pls 变化（防止 `useMapEntities` 触发 `playWorldMove`），同时冻结了 `displayEntities` 中的所有字段（包括 `inCombat`），导致视图层无法响应数据层的变化。这是框架应该正确处理的核心状态层级——phase 机制的 pls 隔离是正确的，但它不应该阻断 `inCombat`/`active` 字段的视图更新。

4. **与死亡 NPC 的对比**：死亡 NPC 的 `state` 被后端设为 1（[combat.state.php#L125](file:///d:/wamp64/www/phpdts/oblivions/include/game/combat/combat.state.php#L125)），`mapVisibleList` 过滤掉它，不渲染。逃跑 NPC 的 `state` 仍为 0（[combat.state.php#L127](file:///d:/wamp64/www/phpdts/oblivions/include/game/combat/combat.state.php#L127)），仍渲染——但渲染时需要视觉降级。两种退场方式的视觉表达不同：死亡=消失，逃跑=半透明残留。当前框架只处理了死亡（靠 `state` 过滤），未处理逃跑（需要 `active` 半透明）。

**关于 `presentationScene` phase 机制的正确性**：phase 机制的 pls 隔离是正确的——战斗中 `entity.pls` 变化不应触发 `playWorldMove`（会与战斗动画冲突，`projectAnchor` 在 `spatial` 通道被占用时只设置 `pendingAnchor` 不立即跳转，见 [useActorRuntime.ts#L200](file:///d:/wamp64/www/phpdts/vex-vue/src/composables/useActorRuntime.ts#L200)）。逃跑 NPC 的 pls 变化会在战斗结束后通过 `enemies` scope 刷新 + `beginRebase` 机制传递（`deriveRebaseMoveActorIds` 检测 pls 差异，但逃跑 NPC 被 `excludedActorIds` 排除，由 handoff 机制处理）。修复方案不是破坏 phase 机制，而是让 `MapGrid.vue` 的 `entity-dimmed` 绕过 `displayEntities` 冻结，直接查询 `characterStore`。

**结论**：修复 A 不是"补一个边界 case"。`presentationScene` 的 phase 机制正确隔离了 pls 变化，但同时也阻断了 `inCombat`/`active` 字段的视图更新。修复方案是让 `MapGrid.vue` 的 `entity-dimmed` 直接查询 `characterStore`，绕过 `displayEntities` 冻结，而不破坏 phase 机制的 pls 隔离。

## 3. 重设计核心思路

### 3.1 两个正交修复，互不依赖

**修复 A：半透明状态贯通（框架基准修复）**

`active=false` 信号已通过 `CombatState.active` 和 `mergeCombatContext` 正确传到 `Character.combat.active`。问题在于 `MapGrid.vue` 的 `entity-dimmed` 依赖 `displayEntities`（被 phase 机制冻结），无法响应 `characterStore` 的变化。

修复方案：让 `entityClass` 函数直接查询 `characterStore.getCharacter(entity.characterPid)?.combat`，绕过 `displayEntities` 冻结：

- `dimmed` 条件改为：`inBattle && hasActiveCombat && (combat?.inCombat !== true || combat?.active === false)`
- `combat` 从 `characterStore.getCharacter(pid)?.combat` 获取，而非 `entity.inCombat`

修复后：
- 逃跑 NPC（`inCombat=true, active=false`）触发半透明 ✓
- 非战斗 NPC（`inCombat=false`）仍触发半透明 ✓
- 活跃战斗员（`inCombat=true, active=true`）不半透明 ✓
- 逃跑 NPC 在整个战斗期间持续半透明，与是否在播动画无关
- 不破坏 `presentationScene` 的 pls 隔离机制

**修复 B：逃跑动画前置到 `combatant_cleared`**

现有代码中 `playCombatantCleared` retreat 分支返回 `completedTask()`——**不播任何动画**（[battle-actor-executor.ts#L344](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle-actor-executor.ts#L344)），动画推迟到 `startCommit` 阶段。重设计改为在 `combatant_cleared` 阶段**串行组合两个现有 command**：

1. `lease.play({ kind: 'fade' })` —— 原格淡出（复用 `fadeOut`，duration 0.35）
2. `await finished` 后 `lease.play({ kind: 'move', target: retreatAnchor, tier: 'long' })` —— teleport + arriveAnim（复用 `move` tier='long' 路径）

lease 通道已经包含 `['spatial', 'pose', 'visibility']`，足以承载这两个 command；`requiredChannels`、`ActorCommand`、`actorAnimations.ts` 全部无需改动。

### 3.2 `startCommit` retreat 路径：删除特例，复用 fall-through

现有 `startCommit` 的 retreat 路径有特例块（[battle-presentation-session.ts#L148-162](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle-presentation-session.ts#L148)）：

```ts
if (handoff.visualPolicy === 'retreat') {
  const target = actor.getProjectedAnchor();
  if (lease && target) {
    // 计算 tier，播 move
    animations.push(lease.play({ kind: 'move', target, tier }));
    continue;  // 跳过 reset-visible
  }
}
```

重设计**直接删除该特例块**。retreat 自然落入其后已存在的 fall-through：

```ts
if (handoff.visualPolicy === 'hidden-relocate-arrive' || handoff.visualPolicy === 'retreat') {
  lease?.release({ reconcile: true });              // 释放 combatant_cleared 阶段的旧 lease
  lease = actor.acquire({ ..., channels: ['pose', 'visibility'] });  // 新 lease
}
if (lease) animations.push(lease.play({ kind: 'reset-visible' }));  // alpha→1 兜底
```

这同时完成三件事：

- 旧 lease 释放（`spatial` 通道空闲，等待后续 `syncAllPositions` 修正位置——见下文"位置修正机制"）
- 新 lease 仅持有 `['pose', 'visibility']`，不再操作 `spatial`
- `reset-visible` 把 alpha 强制拉回 1，无论 `combatant_cleared` 阶段的 `fade + move` 是否被取消

**位置修正机制**：`beginRebase`（[presentation-scene.ts#L113](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/presentation-scene.ts#L113)）中 `applySnapshot(entities)` 已更新 `snapshot.entities` 为新位置（逃跑 NPC 的 pls=退避格），但 `stopEntitiesWatch`（[useMapEntities.ts#L336](file:///d:/wamp64/www/phpdts/vex-vue/src/composables/useMapEntities.ts#L336)）是 Vue watch，在下一 tick 触发。而 `beginRebase` 与 `startCommit` 在 [battle.ts#L348-351](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle.ts#L348) 是同步调用的，所以 `startCommit` 中 `lease.release({ reconcile: true })` 时 `pendingAnchor` 仍为 null（战斗中 `projectAnchor` 未被调用），`releaseLease` 的 `reconcile` 分支不生效。位置修正实际发生在 `stopEntitiesWatch` 触发后的 `syncAllPositions`（[useMapEntities.ts#L149](file:///d:/wamp64/www/phpdts/vex-vue/src/composables/useMapEntities.ts#L149)）：为逃跑 NPC（不在 `rebaseMoveActorIds` 中）调用 `syncEntityPosition` → `projectAnchor(退避格)`（此时 `spatial` 通道已释放）→ `writeAnchor(退避格)`。

### 3.3 视觉时序

`mergeCombatContext` 在收到后端响应时同步执行，早于 battlelog 异步播放。因此逃跑动画开始时，NPC 已经是 `active=false`，`filter: opacity(0.5)` 已生效：

| 阶段 | GSAP alpha | filter opacity | 视觉 |
|------|-----------|----------------|------|
| `fade` 期间 | 1 → 0 | 0.5 | 0.5 → 0（半透明淡出）|
| `move` teleport 瞬间 | 0（arriveAnim 重置）| 0.5 | 0 |
| `arriveAnim` 期间 | 0 → 1 | 0.5 | 0 → 0.5（半透明弹起）|
| 动画结束 | 1 | 0.5 | 0.5（持续半透明）|
| 战斗结束 `mergeCombatContext(null)` | 1 | 不应用（`currentMode` 离开 battle）| 1（正常）|

## 4. 边界案例

### 4.1 `fade` 被取消（alpha 停在 0~1 之间）

- `fade` 只操作 `visibility.alpha`，不操作 `anchor.x/y`，DOM 仍在战斗格
- `startCommit` 中 `lease.release({ reconcile: true })`：`pendingAnchor` 为 null（战斗中 `projectAnchor` 未被调用），reconcile 不改变位置
- `reset-visible` 把 alpha 拉回 1
- `beginRebase` 的 `applySnapshot` 已更新 `snapshot.entities`，`stopEntitiesWatch` 在下一 tick 触发 `syncAllPositions`，为逃跑 NPC 调用 `projectAnchor(退避格)`（`spatial` 通道已释放），DOM 跳到退避格
- 最终：NPC 在退避格，alpha=1，filter 0.5 = 视觉 0.5（半透明）

### 4.2 `move` 被取消（anchor 已 teleport，arriveAnim 中途停止）

- `gsap.set(elements.anchor, { x: target.x, y: target.y })` 已同步执行，DOM 已在退避格
- `arriveAnim` 内部 `gsap.set(elements.visibility, { alpha: 0 })` 也已同步执行，alpha 被设为 0
- `arriveAnim` 的 timeline 被取消后，alpha 停在 0 或 timeline 已执行的部分；`currentAnchor` 仍是战斗格（`onCompleted` 未执行）
- `startCommit` 中 `lease.release({ reconcile: true })`：`pendingAnchor` 为 null，reconcile 不改变位置（DOM 已在退避格，不受影响）
- `reset-visible` 把 alpha 拉回 1
- `stopEntitiesWatch` 触发 `syncAllPositions`，`projectAnchor(退避格)` 将 `currentAnchor` 设为退避格，`writeAnchor(退避格)` 确认 DOM 位置
- 最终：NPC 在退避格，alpha=1，filter 0.5 = 视觉 0.5

### 4.3 `settle-in-place` 模式（退到同格）

不受影响。`playCombatantCleared` 中 `settle-in-place` 路径仍播 `fade`（原格淡出）。`active=false` 后半透明生效，但 `fade` 已让 alpha→0，NPC 视觉上消失。`startCommit` 的 `settle-in-place`（非 retreat）走 `reset-visible`，恢复 alpha=1 + filter 0.5 = 0.5 半透明。

### 4.4 战斗中多个逃跑 NPC

每个逃跑 NPC 独立走 `fade + move` 序列，独立持有 lease 与 `active=false` 标记，互不干扰。

### 4.5 逃跑 NPC 被追上再次进入战斗

新一轮 `mergeCombatContext(newContext)` 重建 `combat` 字段。若 NPC 重新加入 combatants，`inCombat=true, active=true`，半透明消失；若未加入，`combat` 置 undefined，`inCombat=false`，仍半透明（与非战斗 NPC 一致）。

function entityClass(entity: MapEntity): Record<string, boolean> {
  const inBattle = battleStore.currentMode === 'battle';
  // 直接查询 characterStore，绕过 displayEntities 的 phase 冻结
  const character = entity.characterPid != null
    ? characterStore.getCharacter(entity.characterPid)
    : undefined;
  const combat = character?.combat;
  const dimmed = inBattle && hasActiveCombat.value
    && (combat?.inCombat !== true || combat?.active === false);
  const pid = entity.characterPid;
  const aimState = pid != null ? aimTargetingStore.getEnemyAimState(pid) : null;

    'entity-player': entity.id === 'player',
    'entity-dimmed': dimmed,
    // ...
  };

```ts
const retreatTarget = readRetreatTarget(notice);
const retreat = notice.detail?.visual_policy === 'retreat' && retreatTarget !== null;
const lease = context.presentation.getLease(
  actorId,
  retreat ? ['spatial', 'pose', 'visibility'] : ['visibility'],
);
if (!lease) return completedTask();
context.presentation.markBattleExit(actorId, 'escaped', retreatTarget);
if (!retreat) return taskFromHandle(lease.play({ kind: 'fade' }));

// retreat 路径：串行 fade + move tier='long'
const retreatAnchor = context.scene.resolveTile(retreatTarget!);
if (!retreatAnchor) return completedTask();
return createTask(async scope => {
  const fadeHandle = scope.add(lease.play({ kind: 'fade' }));
  await fadeHandle.finished;
  if (scope.cancelled) return;
  const moveHandle = scope.add(lease.play({ kind: 'move', target: retreatAnchor, tier: 'long' }));
  await moveHandle.finished;
});
```

**关键点**：
- `createTask` 已在 [battle-actor-executor.ts#L50](file:///d:/wamp64/www/phpdts/vex-vue/src/stores/battle-actor-executor.ts#L50) 定义，接收 `async (scope) => Promise<void>`
- `scope.add(handle)` 注册 handle 以便取消时清理
- `scope.cancelled` 检查防止 `fade` 被取消后继续播 `move`
- `retreatTarget` 需用 `context.scene.resolveTile(retreatTarget)` 转为 `SceneAnchor`，与 `playMoveAction` 中 `context.scene.resolveTile({ pgroup, pls })` 的用法一致
- `markBattleExit(actorId, 'escaped', retreatTarget)` 调用保留不变——`startCommit` 仍依赖 `consumeBattleExitAnimated(this.id)` 判断该 actor 是否由本会话标记退场

## 6. 设计哲学自校准

- **框架基准优先于边界补丁**：多人战斗中逃跑 NPC 的视觉状态缺失是框架基准问题，不是边界案例。`presentationScene` 的 phase 机制正确隔离了 pls 变化，但同时也阻断了 `inCombat`/`active` 字段的视图更新。修复 A 是让视图层绕过冻结直接查询数据层，而非打补丁。
- **解耦正交关注点**：半透明状态（持续信号）与逃跑动画（一次性演出）解耦。半透明由 `Character.combat.active` 字段驱动，动画由 command 组合实现，二者不互相依赖。
- **绕过冻结而非破坏隔离**：修复 A 不修改 `presentationScene` 的 phase 机制，而是让 `MapGrid.vue` 直接查询 `characterStore`。phase 机制的 pls 隔离保持不变，只有 `inCombat`/`active` 字段绕过冻结。这是最小侵入的修复——不改变 `presentationScene` 的状态机，不改变 `entities.ts` 的数据流，只在视图层最后一步查询数据层。
- **复用既有 command**：`fade` + `move tier='long'` 已能表达"淡出 + teleport + 弹起"三段语义，无需引入新 `ActorCommand` 变体。新 kind 是为 1 个调用点扩展全局语法，违反最小实现。
- **边界案例由现有兜底消解**：`startCommit` fall-through 的 `reset-visible` 是天然的取消兜底；原方案绕过它（`continue` 跳过）才需要单独讨论取消风险。
- **删除优于新增**：`startCommit` retreat 改动是删除特例块，让 retreat 复用 `hidden-relocate-arrive` 已建立的 `release + acquire + reset-visible` 模式，而不是新增"retreat 跳过 move"的特例逻辑。
- **锚点保留**：保留 `active`、`entity-dimmed`、`filter: opacity()`、`playCombatantCleared`、`startCommit`、`combatant_cleared`、`visual_policy === 'retreat'`、`obl_queue_set_active`、`battle_queue_exit`、`mapVisibleList`、`presentationScene.phase`、`syncAuthoritative`、`displayEntities`、`createTask`、`completedTask` 等索引锚点，便于从文档反查代码。
