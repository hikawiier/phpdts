# 状态栏 · 动作区 · 抽屉 视觉重设计案

> 范围：Header 第三行三按钮（属性/战斗/背包）、动作区等待/探索按钮合并、左右抽屉视觉呈现。
>
> 性质：UI/UX 视觉层重构，不涉及后端契约、命令规格、状态机变更。
>
> 美学基线：遵循 [前端美学风格-设计案.md](./前端美学风格-设计案.md) 的"ASCII 终端 + 剪纸舞台 + 黑白漫画"三层语言；遵循灰阶优先、形状冗余、`prefers-reduced-motion` 兜底。
>
> 关联审计：[前端美学风格-现状审计-2026-07-11.md](./前端美学风格-现状审计-2026-07-11.md) §5.3 已识别"Drawer 剪纸层次不足"为本设计案第三项的先验问题。
>
> 关联约束：[DESIGN.md §2.14 键盘快捷键统一引入策略](../DESIGN.md#214-键盘快捷键统一引入策略)。本设计案承担 2.14 过渡期的遗留清理职责——删除 [App.vue](../../vex-vue/src/App.vue) `onKeydown` 中已存在的 `ESC`/`i`/`p` 三类快捷键（ESC 同时关闭模态框，详见 §3.4.2），为统一键盘管理层的建立扫清遗留监听。同时按 §3.5 删除所有方括号字母前缀（`[W]`/`[E]`/`[P]`/`[I]`/`[B]`/`[G]`/`[S]`/`[T]`/`[F]`）——不仅不绑定 keydown，连视觉暗示也彻底清除；数字槽位标识 `[0]`/`[1]`/... 与日志类别标签 `[MOV]`/`[EXP]` 等不暗示快捷键的 ASCII 装饰元素保留（详见 §3.5.5）。

## 一、设计意图

三个独立调整在视觉表达层面共享同一目标：**让核心交互的视觉权重与其语义重要性匹配，并消除"语义重叠但视觉割裂"的结构**。

- **属性/战斗/背包**是玩家最高频访问的三个核心入口，当前以纯文本 `[属性]` 形式呈现，视觉权重等同于装饰文本，玩家难以感知为可点击的核心功能。
- **探索/等待**在命令规格层共享 `time_pass` capability，但 `map.explore` 要求 `itm0Allowed: false`、`world.wait` 允许 `itm0Allowed: true`——语义上"等待是探索不可用时的回退动作"，但当前两者在动作区独立并列，未表达这一优先级关系。
- **属性/背包抽屉**是"参考面板"而非"模态动作"，但当前以 `bg-black/70` 全屏遮罩 + 滑入实现，强制中断玩家对地图的感知；同时审计已指出抽屉缺乏剪纸层次。

## 二、现状分析

### 2.1 Header 第三行（[StatusBar.vue](../../vex-vue/src/components/layout/StatusBar.vue) L192-210）

```
[属性] [战斗] [背包]   <status-effect-chips>
```

- 按钮样式 `.status-bar-btn`（terminal.css L725-736）：无背景、无边框、`color: #bbb`、`font-size: 12px`、`padding: 0`——纯文本样式
- 与右侧状态效果 chip 共享 `.status-bar-row`，`justify-content: space-between` 让按钮组靠左、chip 靠右
- 战斗按钮已有三态逻辑（normal/battle/aim），但视觉上与其他两按钮完全一致，无差异
- `P`/`I` 快捷键已在 [App.vue](../../vex-vue/src/App.vue) L76-96 绑定抽屉切换，但按 [DESIGN.md §2.14](../DESIGN.md#214-键盘快捷键统一引入策略) 这些遗留监听应删除——本设计案不暴露快捷键，且按 §3.5.4 删除所有方括号字母前缀，UI 中不存在任何暗示快捷键的视觉元素

**问题**：
1. 视觉权重不足——核心入口被装饰化
2. 三按钮无差异——战斗按钮的三态语义无视觉表达
3. 抽屉开关状态不可见——玩家无法从状态栏感知"当前哪个抽屉是打开的"
4. 遗留快捷键未清理——App.vue 的 `ESC`/`i`/`p` 监听违反 2.14 约束的过渡期清理职责

### 2.2 动作区按钮（[TileActionBar.vue](../../vex-vue/src/components/actions/TileActionBar.vue) L236-265）

```
[W] 等待                    ← 独占一行，常驻
[E] 探索周围  [合成]  [区域切换]   ← 第二行
```

- `[W] 等待` 常驻顶行，`flex:1` 满宽，`disabled` 由 `commandQueue.canExecute('world.wait')` 控制
- `[E] 探索周围` `flex:3`、`[合成]` `flex:1`、`[区域切换]` `flex:2`（条件显示）
- 命令规格（[command-registry.ts](../../vex-vue/src/stores/command-registry.ts) L30-33）：

| 命令 | mode | advancesTick | itm0Allowed | requiredCapabilities |
|------|------|--------------|-------------|----------------------|
| `map.explore` | explore | true | **false** | `['time_pass']` |
| `world.wait` | explore | true | **true** | `['time_pass']` |

**关键差异**：探索要求 itm0 为空，等待允许 itm0 锁定。即"itm0 锁定时探索被禁、等待可用"——这正是"探索不可用时显示等待"的语义基础。

**附加观察**：[WorldWaitButton.vue](../../vex-vue/src/components/actions/WorldWaitButton.vue) 是独立浮动按钮，`needsRecoveryExit = itm0 !== null || statuses.some(phase === 'active')` 时显示。其触发条件与"探索被 itm0 锁定禁用、等待可用"高度重叠，存在语义冗余。

**问题**：
1. 等待独占一行——视觉上与探索并列，未表达"主次/回退"关系
2. 当 itm0 锁定时，玩家看到"等待可用 + 探索禁用"两个并列按钮，需自行推断"应该等待"——决策成本未优化
3. WorldWaitButton 浮动按钮与主动作区等待按钮功能重叠

### 2.3 抽屉（[PlayerDrawer.vue](../../vex-vue/src/components/layout/PlayerDrawer.vue)、[InventoryDrawer.vue](../../vex-vue/src/components/layout/InventoryDrawer.vue)）

- PlayerDrawer：左侧 280px，`transform: translateX(-100%)` → `translateX(0)` 滑入，遮罩 `bg-black/70` z-250
- InventoryDrawer：右侧 300px，`transform: translateX(100%)` → `translateX(0)` 滑入，遮罩 `bg-black/70` z-350
- 互斥：开一关另一（[ui.ts](../../vex-vue/src/stores/ui.ts) L51-88）
- 关闭：遮罩点击、ESC 键、`[X]` 按钮

**问题**：
1. 全屏 `bg-black/70` 遮罩完全阻断地图感知——玩家查阅背包时看不到游戏状态
2. 抽屉是"参考面板"语义，却被"模态对话框"形式呈现——形式与语义错位
3. 审计 §5.3 已识别剪纸层次不足：仅细边框 + 轻发光 + translate，缺乏"堆叠纸片"层次感
4. 280/300px 在 3 列背包网格下略显拥挤

## 三、方案设计

### 3.1 Header 第三行：核心入口按钮组

#### 3.1.1 设计要点

将三按钮提升为视觉权重明确的核心入口组，表达战斗三态、反映抽屉开关状态。按钮**无字母前缀**（§3.5.4 删除所有方括号字母前缀），只显示纯中文文字。

#### 3.1.2 视觉规格

**结构**：

```
┌─ status-bar-row ────────────────────────────────────────┐
│ ┌─ status-nav-group ──┐                                 │
│ │  属性  │  战斗  │  背包  │   <spacer>   <chips>       │
│ └─────────────────────┘                                 │
└─────────────────────────────────────────────────────────┘
```

**按钮样式**（新增 `.status-nav-btn`，区别于现有 `.status-bar-btn` 纯文本）：

```css
.status-nav-group {
  display: inline-flex;
  gap: 0;                    /* 无 gap，按钮间共享边框形成"按钮组" */
  flex: 0 0 auto;
}
.status-nav-btn {
  box-sizing: border-box;
  padding: 3px 10px;
  border: 1px solid #555;    /* 比常规 .term-btn 的 #888 更内敛 */
  background: #0a0a0a;
  color: #bbb;
  font-family: inherit;
  font-size: 11px;
  letter-spacing: 0.05em;
  cursor: pointer;
  transition: border-color 0.12s, color 0.12s, background 0.12s;
  /* 相邻按钮共用边框：左侧按钮右边框透明，避免双线 */
}
.status-nav-btn + .status-nav-btn {
  border-left-color: transparent;
}
.status-nav-btn:hover:not(:disabled) {
  border-color: #fff;
  color: #fff;
  background: rgba(255,255,255,0.06);
  /* hover 时整组边框统一白色：相邻按钮左 border 需同步 */
}
.status-nav-btn:disabled {
  opacity: 0.4;
  cursor: not-allowed;
}
/* 抽屉打开时对应按钮高亮 */
.status-nav-btn.is-active {
  border-color: #fff;
  color: #fff;
  background: rgba(255,255,255,0.08);
}
/* 战斗按钮在 battle/aim 态：白边 + 内填提示当前模式 */
.status-nav-btn.is-battle-active {
  border-color: #fff;
  color: #fff;
  background: rgba(255,255,255,0.12);
}
```

**hover 边框同步问题**：相邻按钮通过 `border-left-color: transparent` 共用边框，hover 时需将整组边框同步变白。方案：hover 时设 `border-color: #fff` 并将 `+ .status-nav-btn` 的 `border-left-color` 在 hover 态下恢复白色：

```css
.status-nav-group:hover .status-nav-btn { border-color: #555; }
.status-nav-group:hover .status-nav-btn:hover { border-color: #fff; }
.status-nav-group:hover .status-nav-btn:hover + .status-nav-btn { border-left-color: #fff; }
```

或更简单：直接给 `.status-nav-group` 加外边框，按钮间用 `border-left: 1px solid #555` 分隔。**推荐此方案**——结构更简洁：

```css
.status-nav-group {
  display: inline-flex;
  border: 1px solid #555;
  flex: 0 0 auto;
}
.status-nav-btn {
  border: none;              /* 移除自身边框，由 group 容器统一 */
  border-left: 1px solid #555;  /* 分隔线 */
  background: #0a0a0a;
  /* ... 其他同上 ... */
}
.status-nav-btn:first-child { border-left: none; }
.status-nav-group:hover { border-color: #888; }
.status-nav-btn:hover { background: rgba(255,255,255,0.08); color: #fff; }
.status-nav-group:has(.status-nav-btn.is-active) { border-color: #fff; }
```

#### 3.1.3 按钮语义状态

| 按钮 | 默认 | 抽屉/模式打开 | 禁用 |
|------|------|--------------|------|
| `属性` | 灰底灰字 | `.is-active` 白边白字（playerDrawerOpen=true） | — |
| `战斗` | 灰底灰字 | `.is-battle-active`（battleBtnState≠'normal'） | `.disabled`（enter_combat 受阻或常态战斗中） |
| `背包` | 灰底灰字 | `.is-active` 白边白字（inventoryDrawerOpen=true） | — |

战斗按钮文案三态保留现有逻辑（[StatusBar.vue](../../vex-vue/src/components/layout/StatusBar.vue) L110-116）：normal=`战斗`、battle=`战斗中`/`取消`、aim=`取消瞄准`。

#### 3.1.4 状态效果 chip 兼容

保留 chip 在右侧，但与按钮组之间加视觉分隔：

```css
.status-bar-row:last-child {
  justify-content: space-between;
  gap: 12px;
}
```

`<spacer>` 由 flexbox 自动填充，chip 列表保持现有 `.status-effects` 样式。

#### 3.1.5 边界案例

- **窄屏（< 900px）**：按钮组可能挤压 chip 空间。窄屏下 chip 已有 `max-width: 45%`，按钮组应保持 `flex: 0 0 auto` 不收缩；若 chip 区域不足则允许其横向滚动（已实现）。
- **chip 为空**：按钮组靠左，无 chip 时 spacer 把按钮组推到最左、空白延伸到行尾——视觉上略显空。可考虑无 chip 时让按钮组居中或保持靠左（推荐保持靠左，与第一/二行 locationName 对齐）。
- **战斗中按钮**：常态战斗中按钮 `disabled`，文案 `战斗中`，title 提示"战斗进行中，无法主动退出"——保持现有逻辑。
- **快速连续切换抽屉**：`openPlayerDrawer`/`openInventoryDrawer` 已实现互斥（开一关另一），按钮 `.is-active` 状态由 store 派生，响应式自动同步。
- **按钮无字母前缀**：按 §3.5.4 约定，Header 按钮只显示纯中文（`属性`/`战斗`/`背包`），无 `[P]`/`[I]`/`[B]` 前缀——UI 中不存在任何暗示快捷键的字母前缀，与 2.14 约束完全对齐。

### 3.2 动作区：探索/等待合并

#### 3.2.1 设计要点

将探索与等待合并为**单一主操作按钮槽位**，探索为主操作，等待为探索不可用时的回退。消除"决策并列"，让主操作意图一目了然。

#### 3.2.2 视觉与行为

**布局变化**：

```
当前：
等待                               ← 独占一行（原 [W] 等待，§3.5.4 删除前缀）
探索周围  [合成]  [区域切换]        ←（原 [E] 探索周围，§3.5.4 删除前缀）

重设计：
[主操作]  [合成]  [区域切换]       ← 单行
其中 [主操作] = 探索周围  OR  等待（无字母前缀）
```

**主操作按钮逻辑**（[ExploreButton.vue](../../vex-vue/src/components/actions/ExploreButton.vue) 改造）：

```typescript
const exploreBlocked = computed(() => !commandQueue.canExecute('map.explore'));
const waitAvailable = computed(() => commandQueue.canExecute('world.wait'));
// 探索可用 → 探索；探索禁用 + 等待可用 → 等待；都禁用 → 探索（disabled，显示禁用原因）
const mode = computed<'explore' | 'wait'>(() =>
  exploreBlocked.value && waitAvailable.value ? 'wait' : 'explore'
);
const label = computed(() => mode.value === 'wait' ? '等待' : '探索周围');
const title = computed(() => {
  if (mode.value === 'wait') {
    return commandQueue.getBlockDecision('map.explore')?.message
         || '探索暂不可用，等待推进 1 tick';
  }
  return commandQueue.getBlockDecision('map.explore')?.message || '探索当前位置周围';
});
const disabled = computed(() =>
  mode.value === 'explore' ? exploreBlocked.value : !waitAvailable.value
);
function onClick() {
  if (mode.value === 'wait') tileActionStore.handleWait();
  else tileActionStore.handleExplore();
}
```

**视觉差异**：主操作按钮在 explore 模式与 wait 模式下应有可感知的差异，让玩家意识到"当前是回退模式"：

```css
.term-btn.primary-action { flex: 3; position: relative; }
.term-btn.primary-action.is-fallback {
  /* 等待回退模式：边框虚线，提示"非首选操作" */
  border-style: dashed;
  color: #888;
}
.term-btn.primary-action.is-fallback:hover {
  color: #fff;
  border-color: #fff;
  border-style: solid;   /* hover 恢复实线 */
}
```

#### 3.2.3 移除独占的等待行

[TileActionBar.vue](../../vex-vue/src/components/actions/TileActionBar.vue) L236-244 的 `action-buttons` div（独占的 `[W] 等待`）整体删除。原第二行（[E] 探索周围 + [合成] + [区域切换]）变为第一行，ExploreButton 升级为合并主操作。

#### 3.2.4 WorldWaitButton 浮动按钮的处置

**问题**：WorldWaitButton 触发条件（`itm0 !== null || statuses.phase === 'active'`）与"探索被 itm0 锁定禁用、等待可用"高度重叠，功能上与合并后的主操作 wait 模式重复。

**两种处置方案**：

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. 删除浮动按钮** | 主操作 wait 模式已覆盖恢复退出场景 | 消除冗余，UI 更干净 | 失去"强制提示玩家需要恢复"的视觉提醒 |
| **B. 保留作为提示徽章** | 浮动按钮不再可点击，改为被动指示器（如 `!` 图标），点击触发主操作按钮 | 保留提醒，不冗余 | 实现复杂，需调整事件流 |

**推荐方案 A**：删除浮动按钮。理由：
1. 合并后的主操作 wait 模式已通过虚线边框、文案变化明确提示"回退模式"，玩家能感知到需要等待
2. itm0 锁定时 [Itm0Modal.vue](../../vex-vue/src/components/inventory/Itm0Modal.vue) 已有更直接的模态提示
3. 浮动按钮位置（右下角）与状态栏、动作区距离远，玩家注意力分散
4. 减少一层 z-index（z-500）管理

#### 3.2.5 边界案例

- **探索与等待都被禁用**：主操作显示"探索周围"禁用态，title 提示禁用原因（HTTP_LOCKED / COOLDOWN / capability 受阻等）。等待按钮不再独立可见，但其禁用语义已被主操作吸收。
- **itm0 锁定瞬间**：探索从可用变禁用、等待从禁用变可用——主操作按钮即时从 explore 模式切换为 wait 模式。Vue 响应式保证视觉同步。
- **战斗模式下**：`TileActionBar` 在战斗模式下不渲染（[RightPanel.vue](../../vex-vue/src/components/layout/RightPanel.vue) v-if 切换 BattleMode），主操作按钮不存在。WorldWaitButton 已有 `battleStore.currentMode === 'normal'` 守卫，删除浮动按钮不影响战斗模式。
- **区域切换按钮显示**：原第二行有 `[区域切换]` 条件显示（switchRegionVisible），合并后仍保留在同一行，`flex:2` 比例不变。
- **POI 列表渲染**：原"独占等待行"删除后，POI 列表上移一行，可视密度提升。

### 3.3 抽屉：从模态遮罩 → 侧栏面板

#### 3.3.1 设计要点

抽屉的语义是"参考面板"而非"模态动作"。让形式回归语义——移除全屏遮罩，让抽屉成为"贴边的侧栏面板"，玩家查阅背包/属性时仍能感知地图状态。同时落实审计 §5.3 的剪纸层次诉求。

#### 3.3.2 视觉规格

**结构变化**：

```
当前：
                              ┌─ bg-black/70 overlay（全屏遮罩）
┌─────────────┐               │
│             │               │
│  地图       │   ← 完全黑化  │
│             │               │
└─────────────┘               ↓
                              ┌─ drawer ──┐
                              │           │
                              │  内容     │
                              │           │
                              └───────────┘

重设计：
┌─────────────┐  ┌─ drawer ──┐
│             │  │           │
│  地图       │  │  内容     │   ← 地图仍可见
│             │  │           │
└─────────────┘  └───────────┘
                 ↑
                 硬投影 + 软阴影（剪纸层次）
```

**移除遮罩 + 添加剪纸层次**（terminal.css L981-1028 调整）：


CSS 调整：

```css
.drawer-overlay {

  opacity: 0;                        /* 透明 */
  visibility: hidden;
  transition: visibility 0.25s;      /* 移除 opacity transition */
  pointer-events: none;

  visibility: visible;
```

**关键**：`pointer-events: auto` 让透明 overlay 仍能捕获点击；`visibility: visible` 让点击事件能命中。视觉上完全不遮挡，交互上保留模态关闭语义。

#### 3.3.4 抽屉打开时的地图交互决策

**问题**：抽屉打开时，玩家点击地图应如何处理？

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **A. 拦截点击，仅关闭抽屉** | 透明 overlay 捕获点击 → 关闭抽屉，地图移动指令不触发 | 行为可预测：先关抽屉再操作地图 | 多一次点击 |
| **B. 透传点击，地图正常响应** | 移除 overlay 的 click 捕获，地图点击直接生效 | 操作流畅 | 抽屉保持打开，可能遮挡部分地图；玩家可能不知道抽屉还开着 |
| **C. 拦截 + 自动关闭 + 提示** | 点击地图 → 关闭抽屉 + toast 提示"已关闭面板，再次点击可移动" | 明确反馈 | 实现复杂，toast 噪音 |

**推荐方案 A**：透明 overlay 拦截点击关闭抽屉。理由：
1. 行为可预测——"点击外部关闭"是模态/抽屉的通用语义
2. 玩家查阅完抽屉信息后，自然点击外部关闭，再操作地图，符合"先观察后行动"的认知节奏
3. 实现简单，复用现有 overlay DOM
4. 抽屉打开时是"查阅态"，不期望同时操作地图——查阅与行动是认知上分离的两个阶段

**方案 A 的指针事件拦截范围**：`pointer-events: auto` 让透明 overlay 拦截**所有**指针事件（`mousedown` / `mousemove` / `mouseup` / `click`），因此：
- **点击地图区域** → 触发 overlay 的 `@click` → 关闭抽屉（地图移动指令不触发）
- **拖动地图** → `mousedown` 被 overlay 拦截，地图拖动不响应——这是设计决策，非缺陷
- **玩家若要操作地图**：先点击外部关闭抽屉，再操作地图（多一次点击是可接受代价）

**与 2.14 删除 ESC 的协同**：删除 [App.vue](../../vex-vue/src/App.vue) `onKeydown` 中的 ESC 关闭抽屉后，玩家关闭抽屉的路径只剩两条——点击透明 overlay（外部）+ 点击抽屉内 `[X]` 按钮。两条路径都是显式可见的，无隐藏依赖。

#### 3.3.5 边界案例

- **Toast 位置适配**：[useToastPosition.ts](../../vex-vue/src/composables/useToastPosition.ts) 现有逻辑根据抽屉开关切换 toast 位置（pos-left/pos-center）。移除视觉遮罩后，抽屉仍占据侧边空间，toast 位置策略不变——仍需让 toast 不被抽屉遮挡。
- **模态框 + 抽屉同时打开**：现有优先级（模态 > 抽屉）不变。模态框 z-450 仍在抽屉 z-300/z-400 之上。
- **战斗模式 + 抽屉**：战斗模式下 [RightPanel.vue](../../vex-vue/src/components/layout/RightPanel.vue) 切换为 BattleMode，但抽屉是 App.vue 顶层浮动组件，不受影响。玩家可在战斗中查阅属性/背包——保留现有行为。

```css

    transition: transform 0.01s, box-shadow 0.01s;
  }
  .drawer-overlay, .inv-drawer-overlay {
    transition: visibility 0.01s;
  }
}
```

（此降级也补齐了审计 §3.4 指出的"Drawer 过渡无 reduced-motion"问题。）

### 3.4 删除已有快捷键（2.14 过渡期清理）

#### 3.4.1 设计要点

[DESIGN.md §2.14](../DESIGN.md#214-键盘快捷键统一引入策略) 要求"已有的 3 处独立监听在统一层建立后应统一收编"——但其中 [App.vue](../../vex-vue/src/App.vue) 的 `onKeydown` 是从旧 `vex/js/app.js` 迁移的遗留，绑定了 `ESC`/`i`/`p` 三类与抽屉相关的快捷键。本设计案在重构抽屉视觉的同时，将这处遗留监听一并删除，为统一键盘管理层的建立扫清障碍。

**不在本设计案范围内**：
- [useMapInteraction](../../vex-vue/src/composables/useMapInteraction.ts) 的 keydown 监听（地图交互专用，属另一模块）
- [AimMode.vue](../../vex-vue/src/components/battle/AimMode.vue) L416-428 的 keydown 监听（战斗瞄准专用，由战斗快捷键层建立时收编）

这两处监听属其他模块的现有功能，删除它们需要单独评估对其各自模块的影响，不纳入本设计案。

#### 3.4.2 删除范围

[App.vue L76-96](../../vex-vue/src/App.vue#L76-L96) 的 `onKeydown` 函数处理三类按键：

| 按键 | 当前行为 | 删除后替代路径 |
|------|---------|--------------|
| `Escape` | 按**优先级**关闭（craftStore.craftModalOpen > uiStore.modalOpen > inventoryDrawerOpen > playerDrawerOpen） | CraftModal/Modal：overlay 点击 + `[X]`/`[取消]` 按钮（**ESC 退化，可接受**）；InventoryDrawer/PlayerDrawer：透明 overlay（§3.3）+ 抽屉内 `[X]` 按钮 |
| `i` / `I` | toggle inventoryDrawer | 点击 Header `背包` 按钮（§3.1） |
| `p` / `P` | toggle playerDrawer | 点击 Header `属性` 按钮（§3.1） |

**ESC 删除对模态框的影响**：[CraftModal.vue](../../vex-vue/src/components/craft/CraftModal.vue) / [Itm0Modal.vue](../../vex-vue/src/components/inventory/Itm0Modal.vue) / [Modal.vue](../../vex-vue/src/components/layout/Modal.vue) **全部没有**自己的 keydown 监听（grep 验证 2026-07-16），其 ESC 关闭完全依赖 App.vue 的 onKeydown。删除后：

- **Modal.vue**：保留 overlay 点击 + 模态内按钮（确认/取消）
- **Itm0Modal**：设计上**不可关闭**（注释 L18 明确"无 [X] 按钮、无遮罩点击关闭"），ESC 对其本来就无效——删除 ESC 对 Itm0Modal **零影响**

**ESC 退化的可接受性论证**：
1. ESC 是**隐藏快捷键**，新玩家不可发现；overlay 点击 + `[X]` 按钮是**显式可见路径**，可发现性更高
2. 模态框是**强制焦点**的交互场景，玩家视线锁定模态内，关闭按钮就在视线内
3. 与 2.14"统一管理层建立前不引入键盘快捷键"策略完全一致——删除 ESC 即清除遗留快捷键

**同步清理**：

- [App.vue L102](../../vex-vue/src/App.vue#L102) `onMounted` 中的 `document.addEventListener('keydown', onKeydown)`

### 3.5 UI 文本中文化与前缀清理

#### 3.5.1 设计要点

前端 UI 存在大量中英文混杂显示——ASCII 标题（`CHRONICLE`/`ACTIONS`/`COMBAT`/`CARTOGRAPHY`/`INVENTORY`/`ARMAMENT`/`SURVIVOR`）、行内标识（`LOC:`/`REGION:`/`ATK:`/`DEF:`/`KILLS:`/`POS:`/`STATE:`）、区段标题（`VITALITY`/`STAMINA`/`ACTION POINTS`/`EXPERIENCE`/`STATUS EFFECTS`/`PROFILE`）。同时操作按钮和列表项存在方括号字母前缀（`[W]`/`[E]`/`[G]`/`[S]`/`[P]`/`[T]`/`[F]`），会误导玩家以为是快捷键。

#### 3.5.6 [F] 终结技标记的替代方案

`[F]` 终结技标记与其他列表项标签不同——它是**功能性标识**，删除后玩家无法区分终结技道具/技能。删除 `[F]` span 后，改用 CSS 类 `finisher-item` 为终结技项添加视觉区分：

```css
/* 终结技视觉标识——替代原 [F] 标签 */
.finisher-item {
  border-left: 2px solid #fff;
  padding-left: 6px;
  background: rgba(255, 255, 255, 0.05);  /* 可选：背景高亮 */
}
```

模板调整：原 `<span v-if="item.isFinisher" class="finisher-tag">[F]</span>` 删除，改为在列表项容器上添加 `:class="{ 'finisher-item': item.isFinisher }"`。

**设计理由**：终结技是战斗机制中的重要区分，需保持视觉可辨性。用 CSS 类替代文字标签既清除了字母前缀，又保留了功能性标识——形状冗余编码（边框/背景）比文字标签更隐蔽，不暗示快捷键。

#### 3.5.7 边界案例

- **ui-locale.ts 的 key 命名**：key 用英文大写（如 `CHRONICLE`）保留与原硬编码文本的索引对应关系——这不是"保留英文显示"，是"作为字典 key 供反查"。玩家看到的是 `{{ UI_TEXT.CHRONICLE }}` 渲染后的中文"战报"。
- **行内拼接文本的可读性**：PlayerDrawer L143 `├─ {{ UI_TEXT.ATK }}: {{ att }} | {{ UI_TEXT.DEF }}: {{ def }}` 模板稍显冗长，但保持了 key→中文 的统一查询路径。若未来此类拼接增多，可考虑引入 `getUiText('ATK')` 函数式查询。
- **[F] 终结技 CSS 替代的兼容性**：`finisher-item` 类是新增的，不与现有 CSS 冲突。实施时需确认 PreloadArea 列表项的现有样式不会被覆盖。
- **注释中的英文**：组件注释（如 PlayerDrawer L11 `┌─ SURVIVOR ────────── [X]`）是开发者文档，不是用户可见 UI，不在本设计案范围内——不强制清理。
- **`loading...` 小写**：PlayerDrawer L170 `loading...` 是小写，与其他大写英文不同。ui-locale.ts 的 key 用 `LOADING`，渲染为"加载中..."。

## 五、设计自校准

### 5.1 与设计哲学的对齐（[DESIGN.md §3](../DESIGN.md#三跨任务沉淀的设计哲学)）

- **3.1 降低理解成本**：三个调整都让"核心交互的视觉权重"与"语义重要性"对齐——属性/战斗/背包作为核心入口获得按钮组视觉权重；探索作为主操作获得唯一槽位；抽屉作为参考面板失去模态遮罩。视觉表达不再与语义错位。
- **3.2 概念引入成本-收益**：未引入新概念名词。"主操作槽位"、"回退模式"、"剪纸硬投影"都是对现有概念（按钮、disabled、drop-shadow）的组合描述，无新学习成本。
- **3.3 约束是意图的近似**：审计 §5.3"Drawer 剪纸层次不足"是设计案 §1.1"剪纸舞台"约束的字面外延——本设计案通过硬投影+软阴影落实这一意图，回到"纸片堆叠"的视觉表达。

### 5.2 与现有约束的兼容

- **灰阶优先**：所有新增视觉（按钮组边框、阴影、active 态）均使用灰阶（#555/#888/#fff/#000），不引入彩色信号色
- **形状冗余**：主操作 explore/wait 模式区分不仅靠文案，还靠边框线型（实线/虚线）——形状冗余编码
- **prefers-reduced-motion**：抽屉过渡降级补齐审计 §3.4 的部分缺口
- **z-index 层级**：本设计案不改变现有 z-index 层级表（drawer z-300/z-400、modal z-450、toast z-500）
- **2.14 键盘快捷键统一引入策略**：本设计案不引入任何键盘快捷键，且**删除所有方括号字母前缀**（`[W]`/`[E]`/`[P]`/`[I]`/`[B]`/`[G]`/`[S]`/`[T]`/`[F]`）——不仅不绑定 keydown，连视觉暗示也彻底清除。同时承担过渡期清理职责，删除 [App.vue](../../vex-vue/src/App.vue) `onKeydown` 中 `ESC`/`i`/`p` 三类遗留监听（详见 §3.4）。`useMapInteraction` 与 `AimMode.vue` 的 keydown 监听不在本设计案范围，待各自模块或统一键盘管理层建立时收编。
- **2.10 命名约定作为索引锚点**：ui-locale.ts 的 key 用英文大写（如 `CHRONICLE`）保留与原硬编码文本的索引对应关系——这是字典 key 供反查，不是"保留英文显示"。玩家看到的是 `{{ UI_TEXT.CHRONICLE }}` 渲染后的中文"战报"。
- **2.6 配置驱动而非硬编码**：ui-locale.ts 把 UI 文本从模板硬编码降格为字典查询，新增 UI 文本时只需加 key，符合配置驱动哲学。

### 5.3 未覆盖范围

- 不涉及后端命令契约、状态机、 capability 规格
- 不涉及 Itm0Modal 内文本中文化（Itm0Modal 已是中文 UI，仅有 `[!]` 警告符号与 `[0]` 槽位标识——按 §3.5.5 保留）
- 不涉及 BattleModal 内其他英文 UI 文本（除 HP/HP: 已纳入 §3.5.3，BattleModal 内其他可能文本需另行审计——本设计案仅覆盖 grep 验证可见的 HP 行）
- 不涉及地图层 z-index 重构
- 不涉及纹理系统、天穹层（属 [前端美学风格-设计案.md](./前端美学风格-设计案.md) P0/P1 范畴）
- 不涉及 `useMapInteraction` / `AimMode.vue` 现有 keydown 监听的收编（属其他模块，待统一键盘管理层建立）
- 不涉及统一键盘管理层（`useBattleKeyboard` / `KeyboardManager`）本身的设计与实现
- 不涉及 vue-i18n 等国际化框架的引入（ui-locale.ts 复用现有 `*-locale.ts` 模式，保持轻量）
- 不涉及组件注释中的英文清理（注释是开发者文档，非用户可见 UI）
- 不涉及 LOGCATEGORY_TAGS 字典值的中文化（MOV/EXP/SYS 等 3 字母缩写按 §3.5.5 保留为 ASCII 装饰）
