# 战斗入口设计案

> 将战斗入口流程独立为 `battle.entry.php`，与 `battle.main.php`（执行）+ `battle.func.php`（队列）三层分离。
>
> **状态**：设计阶段，未实施。
> **关联**：[battle_main解耦设计案.md](battle_main解耦设计案.md)
>
> 本设计案定义 4 种战斗入口的边界、参数、衔接关系，并指定独立文件位置。

---

## 一、入口定义

| 编号 | 入口名 | 触发者 | 触发源 | 是否建队列 | 是否接收 actions | 谁先打 |
|------|--------|--------|--------|----------|----------------|--------|
| 1 | 玩家突袭 NPC | 玩家 | 命令 `obl_battle_start` | 否（后补票） | 是 | 玩家 |
| 2 | NPC 突袭玩家 | NPC | `enemy_ai.func.php` AI 决策 | 否（后补票） | 是 | NPC |
| 3 | 遭遇战 | 系统 | 移动系统（`move.func.php`）检测目的地重叠 | 是 | 否 | 先攻判定决定 |
| 4 | NPC 先攻准备 | 系统 | 入口 3 走 NPC 先攻的后续分支 / 已有队列下一轮 NPC 先攻 | 已有队列 | 是（NPC AI 生成） | NPC |

---

## 二、核心要素

### 2.1 入口 1/2（突袭）：A 不建立队列直接执行 + B 接收 actions 合集

- 建立 `ambush_flag` 标记谁是突袭者
- 直接调用伤害判定（不建队列）
- 执行完后"后补票"建立先攻队列
- `ambush_flag` 在 `battle_queue_create()` 内一次性清除

### 2.2 入口 3（遭遇战）：A 先建队列 + 判先攻

- **参战者列表必须显式传入**（非从 actions 推导）
- 不执行动作，只建队列 + 先攻判定
- 判定后分支：
  - 玩家先攻 → 状态机 → `WAITING_PLAYER`（等玩家输入）
  - NPC 先攻 → 调用入口 4

### 2.3 入口 4（NPC 先攻准备）

- **不是独立入口**，是入口 3 / 已有队列下一轮 NPC 先攻的统一后续分支
- 由 NPC AI 行为树生成 actions 合集 → 调用执行

---

## 三、入口差异表

| 维度 | 入口 1 | 入口 2 | 入口 3 | 入口 4 |
|------|--------|--------|--------|--------|
| 命令触发 | 前端 HTTP | 否（AI tick） | 否（移动系统） | 否（入口 3 后续 / tick） |
| 参数 | `$actions` (前端 JSON) | `$actions` (AI 生成) | `$combatants` (显式) | `$actions` (AI 生成) |
| ambush_flag | 玩家 set | AI set（需新增） | 无 | 无 |
| 建队列时机 | 后补票 | 后补票 | 立即（先打前） | 已有队列 |
| 调用入口位置 | `oblivions_commands.php` | `enemy_ai.func.php` | `move.func.php` | `enemy_ai.func.php` / 入口 3 分支 |

## 四、文件结构

### 4.1 文件位置

```
oblivions/include/game/battle/
├── battle.main.php            ← 执行 + 队列管理（解耦后）
├── battle.func.php            ← 队列底层函数
├── battle.calc.php            ← 伤害计算
├── battle_state_machine.func.php
└── battle.entry.php           ← 4 个入口函数（本设计案）
```

### 4.2 4 个入口函数签名

```php
/**
 * 入口 1：玩家突袭 NPC
 *
 * 由 cmd_handle_obl_battle_start 调用（命令 -> 入口层校验 -> 本函数）。
 * 校验目标合法性（存在/未死亡/已发现/同区域/射程内）由调用方完成，
 * 本函数只负责设置 ambush_flag + battle_state_init + 调用战斗主流程。
 *
 * @param array     &$pdata   玩家数据
 * @param array|null $actions 预装填动作数组 [{act_id, target}, ...]
 */
function battle_entry_player_ambush(&$pdata, $actions);

/**
 * 入口 2：NPC 突袭玩家
 *
 * 由 enemy_ai.func.php 的 AI 决策层调用。
 * NPC AI 判断选择突袭时,生成 actions 合集后调用本函数。
 *
 * @param array &$npc    NPC 数据（actor）
 * @param array $actions AI 生成的动作数组 [{act_id, target}, ...]
 */
function battle_entry_npc_ambush(&$npc, $actions);

/**
 * 入口 3：遭遇战
 *
 * 由 move.func.php 检测到移动目的地与对手重叠时调用。
 * 不执行动作,只建队列 + 先攻判定,然后分支到入口 4 或 WAITING_PLAYER。
 *
 * @param array &$actor       触发者（玩家或 NPC,谁移动到此格）
 * @param array $combatants   显式参战者列表 [pid, pid, ...]
 */
function battle_entry_encounter(&$actor, $combatants);

/**
 * 入口 4:NPC 先攻准备
 *
 * 由入口 3 走 NPC 先攻的后续分支,或已有队列下一轮 NPC 先攻（tick 系统触发）调用。
 * NPC AI 行为树生成 actions 合集后调用本函数。
 *
 * @param array &$npc    NPC 数据
 * @param array $actions AI 生成的动作数组 [{act_id, target}, ...]
 */
function battle_entry_npc_prepare_actions(&$npc, $actions);
```

## 五、调用方改造

### 5.1 oblivions_commands.php（入口 1）

```php
function cmd_handle_obl_battle_start(&$pdata, $actions = null) {
    // ... 目标合法性校验（保留,这是命令层职责）...
    include_once GAME_ROOT . './oblivions/include/game/battle/battle.entry.php';
    battle_entry_player_ambush($pdata, $actions);
}
```

校验逻辑（存在/未死亡/已发现/同区域/射程内）保留在命令层,因为这是 HTTP 输入校验,与战斗入口概念分离。

### 5.2 enemy_ai.func.php（入口 2 / 4）

```php
// NPC 决策突袭时
include_once GAME_ROOT . './oblivions/include/game/battle/battle.entry.php';
battle_entry_npc_ambush($npc, $actions);

// NPC 已有队列下一轮先攻（原 obl_tick_phase_battle_npc）
include_once GAME_ROOT . './oblivions/include/game/battle/battle.entry.php';
battle_entry_npc_prepare_actions($npc, $actions);
```

### 5.3 move.func.php（入口 3）

```php
// 移动到目的地检测到对手重叠
include_once GAME_ROOT . './oblivions/include/game/battle/battle.entry.php';
battle_entry_encounter($actor, $combatants);
```

`move.func.php` 当前可能尚未实现遭遇战检测,本设计案定义接入点,实际触发逻辑由移动系统设计案决定。

## 六、入口内部流程

### 6.1 入口 1 完整流程

```
battle_entry_player_ambush($pdata, $actions)
  ├── 1. 解析 $actions -> $atk_act + $ambush_target_pid
  ├── 2. 初始化 battle_log（如尚未初始化）
  ├── 3. $pdata['oblpara']['ambush_flag'] = true
  ├── 4. battle_state_init($pdata)
  ├── 5. battle_main($pdata, $atk_act, $obl_battle_log)
  │       └── battle_queue_check 后补票建队列,ambush_flag 在此清除
  └── 6. 返回（命令层负责后续 save + tick 推进）
```

### 6.2 入口 2 完整流程

```
battle_entry_npc_ambush($npc, $actions)
  ├── 1. 解析 $actions -> $atk_act
  ├── 2. $npc['oblpara']['ambush_flag'] = true   ← 新增设置点
  ├── 3. battle_state_init($npc)
  ├── 4. battle_main($npc, $atk_act, $obl_battle_log)
  │       └── 后补票建队列
  └── 5. 返回（tick 系统负责后续 save）
```

### 6.3 入口 3 完整流程

```
battle_entry_encounter($actor, $combatants)
  ├── 1. battle_state_init($actor)
  ├── 2. battle_queue_create($actor, $combatants, $obl_battle_log)
  │       └── 内部先攻判定,决定队列顺序
  ├── 3. 判定谁先攻
  │   ├── 玩家先攻 -> obl_battle_state_transition($qid, 'player_wait')
  │   │              状态机变为 WAITING_PLAYER,等玩家下个命令
  │   └── NPC 先攻 -> battle_entry_npc_prepare_actions($first_npc, $ai_actions)
  └── 4. 返回
```

### 6.4 入口 4 完整流程

```
battle_entry_npc_prepare_actions($npc, $actions)
  ├── 1. 解析 $actions -> $atk_act
  ├── 2. battle_main($npc, $atk_act, $obl_battle_log)
  │       └── battle_queue_check 更新队列 done 状态
  │       └── battle_finish_check 检查战斗是否结束 / 进入新一轮
  └── 3. 返回（tick 系统负责后续 save + 推进下一 tick）
```

## 七、与 battle_main 解耦的衔接

本设计案定义"入口层",入口函数内部调用 `battle_main($actor, $atk_act, $obl_battle_log)`。当 [battle_main解耦设计案.md](battle_main解耦设计案.md) 实施后,改为：

```php
// 入口 1/2/4 内部
$ctx = [
    'combatants' => [$actor['pid'] => 1],
    'last_qid'   => 0,
    'is_ambush'  => true,  // 入口 3 设为 false
];
battle_execute_turn($actor, $atk_act, $obl_battle_log, $ctx);
battle_manage_queue($actor, $obl_battle_log, $ctx);
```

入口 3 内部（不执行动作,只建队列）：

```php
$ctx = [
    'combatants' => array_fill_keys($combatants, 1),
    'last_qid'   => 0,
    'is_ambush'  => false,
];
// 入口 3 不调用 battle_execute_turn,直接调用 battle_manage_queue
battle_manage_queue($actor, $obl_battle_log, $ctx);
```
