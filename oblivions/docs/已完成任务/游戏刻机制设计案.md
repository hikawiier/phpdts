# Oblivions 游戏刻机制设计案

> 游戏刻（Tick）是 Oblivions 模式的核心时间驱动单元。本设计案阐述游戏刻的定义、推进机制、事件处理流程，以及战斗系统与游戏刻的集成关系。
>
> **核心隐喻**：世界前进了一秒，本该行动的玩家没行动，NPC 替他走出了这一步。

---

## 一、设计目标

### 1.1 核心目标

1. **统一的时间驱动模型**：所有世界状态变化（NPC 行为、buff 结算、时效事件）都由游戏刻推进触发
2. **玩家行为驱动**：游戏刻由玩家行为推进，非定时驱动，符合 PHPDTS 的请求驱动架构
3. **战斗与非战斗统一**：战斗中的 NPC 先攻轮与非战斗中的 NPC AI 行为共用同一套游戏刻更新机制
4. **前端自动刷新**：战斗中 NPC 先攻轮推进游戏刻后，前端自动发请求触发下次游戏刻更新，玩家无需操作

### 1.2 设计原则

- **时间是资源**：每次请求只有 1 单位时间（1 游戏刻），只有 1 个角色可以消耗它
- **并行 vs 串行**：并行动作（非战斗 NPC 行为）不干涉其他人，可以同时完成；串行动作（先攻轮）互相干涉，有人先动了他就不能动
- **最多推进 1 游戏刻**：一次 `obl_resolve_tick_events()` 最多推进 1 游戏刻，体现"所有 NPC 动作在同 1 游戏刻内完成"的事实

## 二、核心概念

### 2.1 游戏刻（Tick）

游戏世界的行为驱动单元，由玩家行为或 NPC 先攻轮推进：

- **1 游戏刻 = 1 单位时间 = 1 次请求**
- 游戏刻推进触发 `obl_resolve_tick_events()`，处理所有 NPC 行为和时效事件
- 游戏刻存储在 `game` 表的 `gamevars` 字段，`gamevars['obl_tick']` 为当前游戏刻，`$gamevars['obl_pretick']` 记录上次处理的游戏刻

### 2.2 时间消耗模型

**消耗时间的动作**（串行，推进游戏刻）：

- 玩家行动（移动/探索）：`obl_command.php` [F] 段推进游戏刻
- 玩家先攻轮：`obl_command.php` [F] 段推进游戏刻
- NPC 先攻轮：`obl_resolve_tick_events()` 末尾推进游戏刻

**不消耗时间的动作**（并行，不推进游戏刻）：

- 非战斗 NPC AI 行为（移动、巡逻、遭遇战触发）：与玩家或 NPC 的步同时发生

### 2.3 并行 vs 串行


| 动作类型              | 并行/串行 | 消耗时间 | 推进游戏刻   | 说明                      |
| --------------------- | --------- | -------- | ------------ | ------------------------- |
| 玩家行动（移动/探索） | 串行      | 是       | 是（[F] 段） | 玩家走了一步              |
| 玩家先攻轮            | 串行      | 是       | 是（[F] 段） | 玩家走了一步              |
| NPC 先攻轮            | 串行      | 是       | 是（末尾）   | NPC 替玩家走了一步        |
| 非战斗 NPC AI 行为    | 并行      | 否       | 否           | 与玩家或 NPC 的步同时发生 |

**关键区分**：

- 串行动作：互相干涉，有人先动了他就不能动（先攻队列中的角色）
- 并行动作：不干涉其他人，可以同时完成（非战斗 NPC 各自移动）

## 三、游戏刻推进机制

### 3.1 两个推进位置

游戏刻推进只有两个触发点：

**位置 1：`obl_command.php` [F] 段**（玩家行为）

- 玩家行动（移动/探索）→ `obl_tick++`
- 玩家先攻轮（`obl_battle_action` 命令）→ `obl_tick++`
- 现有逻辑，无需修改

**位置 2：`obl_resolve_tick_events()` 末尾**（NPC 先攻轮）

- NPC 先攻轮执行后设置"游戏刻已推进"标记
- `obl_resolve_tick_events()` 末尾检测标记，推进 1 游戏刻（`obl_tick++`）
- 最多推进 1 游戏刻

### 3.2 标记机制

**"游戏刻已推进"标记**：

- NPC 先攻轮执行后设置标记（不直接 `obl_tick++`）
- 后续战斗中 NPC 检测到标记，跳过（不执行先攻轮）
- `obl_resolve_tick_events()` 末尾检测标记，推进 1 游戏刻
- 清除标记，`obl_pretick = obl_tick`

**标记的存储位置**：

- 全局变量或静态变量（同一请求内有效）
- 不需要持久化（每次请求开始时清除）

### 3.3 最多推进 1 游戏刻

**设计理由**：体现"所有 NPC 动作在同 1 游戏刻内完成"的事实。

- 一次 `obl_resolve_tick_events()` 最多推进 1 游戏刻
- 无论有多少 NPC 先攻轮，只推进 1 次
- 非战斗 NPC AI 行为不推进游戏刻（并行，同时发生）

## 四、游戏刻事件处理流程

### 4.1 两阶段处理

`obl_resolve_tick_events()` 采用两阶段处理：

**阶段 1：战斗中 NPC 先攻轮**（串行，检测标记）

- foreach 遍历所有 NPC
- 战斗中 NPC 且是当前先攻者 → 执行先攻轮 → 设置标记
- 检测到标记 → 跳过后续战斗中 NPC
- 非战斗 NPC → 跳过
- 最多处理 1 个 NPC 先攻轮

**阶段 2：非战斗 NPC AI 行为**（并行）

- foreach 遍历所有 NPC
- 非战斗 NPC → AI 行为（移动、巡逻、遭遇战触发）
- 战斗中 NPC → 跳过
- 所有非战斗 NPC 同时行动（不干涉）

**末尾：统一游戏刻推进**

- 检测"游戏刻已推进"标记
- 已设置 → `obl_tick++`（推进 1 游戏刻）
- 未设置 → 不推进
- 清除标记，`obl_pretick = obl_tick`

### 4.2 完整流程图

```
═══════════════════════════════════════════════════════════
游戏刻更新：obl_resolve_tick_events()
═══════════════════════════════════════════════════════════

obl_resolve_tick_events()
│
├─ 阶段 1：战斗中 NPC 先攻轮（串行，检测标记）
│   └─ foreach ($enemies as &$enemy):
│       ├─ 检查"游戏刻已推进"标记
│       │   ├─ 未推进 →
│       │   │   └─ 战斗中 NPC 且是当前先攻者 →
│       │   │       ├─ 【prebattle 阶段】（AP 恢复 + 行为树读取）
│       │   │       ├─ 【NPC 先攻轮结算】
│       │   │       ├─ 设置"游戏刻已推进"标记（不直接 obl_tick++）
│       │   │       └─ 更新先攻队列（done=1）
│       │   └─ 已推进 → 跳过
│       └─ 非战斗 NPC → 跳过
│
├─ 阶段 2：非战斗 NPC AI 行为（并行）
│   └─ foreach ($enemies as &$enemy):
│       ├─ 非战斗 NPC → AI 行为（移动、巡逻、遭遇战触发）
│       │   └─ 触发遭遇战 → 加入先攻队列末尾（done=0）
│       └─ 战斗中 NPC → 跳过
│
├─ 末尾：统一游戏刻推进
│   ├─ 检测"游戏刻已推进"标记
│   │   ├─ 已设置 → obl_tick++（推进 1 游戏刻）
│   │   └─ 未设置 → 不推进
│   ├─ 清除"游戏刻已推进"标记
│   └─ obl_pretick = obl_tick
│
└─ 返回
```

### 4.3 阶段顺序的设计理由

**先战斗，后非战斗**：

- 战斗是更紧急的事件，应该优先处理
- 非战斗 NPC 的行为（如增援）在战斗之后，符合"增援到达"的逻辑
- 非战斗 NPC 在阶段 2 移动到玩家格触发遭遇战，加入先攻队列末尾（done=0），本游戏刻不执行先攻轮（阶段 1 已结束，自然不会触发战斗事件）

## 五、前端自动刷新机制

### 5.1 核心思路

战斗中 NPC 先攻轮推进游戏刻后，需要有人触发 `obl_resolve_tick_events()` 来处理下一个 NPC 先攻轮。但玩家没有操作，没有新的命令提交。

**解决方案**：前端播放完 battlelog 后自动发 `api_v2` 请求，触发 `common.inc.php` 加载，从而触发游戏刻更新。

### 5.2 自动刷新循环

```
玩家先攻轮（obl_battle_action 命令）
  → obl_command.php [F] 段推进游戏刻（obl_tick++）
  → 命令返回
  → 前端 fetch played=0 → 三阶段播放 → 自动刷新

→ obl_resolve_tick_events()
  ├─ 阶段 1：NPC 先攻轮 → 设置标记
  ├─ 阶段 2：非战斗 NPC AI 行为
  └─ 末尾：检测标记 → obl_tick++（推进 1 游戏刻）
  → 前端 fetch played=0 → 三阶段播放 → 自动刷新

→ obl_resolve_tick_events()
  ├─ 阶段 1：下一个 NPC 先攻轮 → 设置标记
  ├─ 阶段 2：非战斗 NPC AI 行为
  └─ 末尾：检测标记 → obl_tick++（推进 1 游戏刻）
  → 前端 fetch played=0 → 三阶段播放 → 自动刷新

→ ...循环...

→ obl_resolve_tick_events()
  ├─ 阶段 1：当前先攻者是玩家 → 不执行先攻轮 → 不设置标记
  ├─ 阶段 2：非战斗 NPC AI 行为
  └─ 末尾：检测标记 → 未设置 → 不推进游戏刻
  → 前端 fetch played=0 → 无新日志 → 停止自动刷新
  → 等待玩家操作
```

### 5.3 循环终止条件

前端自动刷新的循环在以下情况停止：

1. **下一个先攻者是玩家**：通过 `player_info` 的 `oblpara.battle.queue` 判断
2. **战斗结束**：`action=''`
3. **没有新的 played=0 日志**：说明没有新的 NPC 行动

### 5.4 健壮性

**玩家中途刷新页面**：

- 玩家刷新页面会触发 `common.inc.php` 加载，从而触发游戏刻更新
- 游戏刻更新的执行不依赖于前端动画播放是否完成
- played 标记的幂等性：玩家中途刷新，`played=0` 的日志会再次被获取，重新播放

**关键结论**：游戏刻更新的触发条件只有一个——有请求加载 `common.inc.php`。请求的来源不重要（自动刷新、手动刷新、重新打开页面、提交命令），只要 `obl_pretick < obl_tick`，游戏刻更新就会执行。

### 6.2 关键设计点

1. **移除 `obl_battle_auto_npc()`**：战斗流程不再直接调用 NPC 先攻轮，NPC 先攻轮由游戏刻更新驱动
2. **`obl_battle_resolve_round()` 只处理玩家先攻轮**：结算完玩家先攻轮后直接返回
3. **`obl_resolve_tick_events()` 增加战斗中 NPC 处理**：阶段 1 处理战斗中 NPC 先攻轮
4. **NPC 先攻轮由游戏刻更新驱动**：与非战斗 NPC 行为统一处理

### 6.3 prebattle 阶段

**独立函数** `obl_battle_preload_phase(&$actor, &$target, $actions)`：

- 玩家先攻轮：`$actions` 从命令参数接收
- NPC 先攻轮：`$actions` 传 null，内部从行为树读取

**职责**：

1. 触发 AP 恢复事件（`AP = min(AP + maxAP, maxAP)`）
2. 接收装填技能（玩家从命令参数，NPC 从行为树）
3. AP 校验、目标校验

**执行位置**：在先攻轮结算之前，每次先攻轮（玩家和 NPC）都执行。

### 6.4 AP 恢复机制

**公式**：`AP = min(AP + maxAP, maxAP)`

- AP 是数据库持久化字段，初次战斗直接读取玩家数据里的 AP 和 maxAP
- 玩家进入战斗时 AP 可能不是满的（之前战斗消耗了 AP，还没恢复）
- prebattle 阶段触发 AP 恢复事件
- AP 恢复后封顶 maxAP，但负数时不封底

**示例**：

- AP = -5, maxAP = 10 → min(-5+10, 10) = 5
- AP = 3, maxAP = 10 → min(3+10, 10) = 10
- AP = -15, maxAP = 10 → min(-15+10, 10) = -5（仍为负，只能放 AP 消耗为 0 的动作）

## 七、增援机制

### 7.1 非战斗 NPC 加入战斗

战斗中，非战斗 NPC 可以在阶段 2 移动到玩家格，触发遭遇战，加入战场。这创造了"增援"的体验：战斗中其他 NPC 可以走过来加入战场。

**流程**：

```
玩家与 NPC_A 战斗中
→ 游戏刻更新
→ 阶段 1：NPC_A 先攻轮（如果 NPC_A 是当前先攻者）
→ 阶段 2：非战斗 NPC 并行行动
│   └─ NPC_B 移动到玩家格 → 触发遭遇战 → NPC_B 加入战斗（先攻队列末尾，done=0）
→ 末尾：推进游戏刻
→ 下一个游戏刻：NPC_B 的 done=0，可以执行先攻轮
```

### 7.2 新加入者的处理

- 新加入的 NPC 排入先攻队列末尾
- `done=0`，表示在当前先攻队列中未行动过
- 本游戏刻不执行先攻轮（阶段 1 已结束，事件结算器自然不会再处理战斗事件）
- 下一个游戏刻，NPC 按队列顺序成为当前先攻者时，正常执行先攻轮

**done 的真实含义**：NPC 在**当前的先攻队列**中有没有行动过。
- 加入队列时默认 `done=0`（未行动）
- 完成先攻轮后 `done=1`（已行动）
- 所有参战者都 `done=1` 时，重新生成先攻队列，所有人 `done=0`

**为什么不设置 done=1**：如果新加入者设置 `done=1`，会被错误地标记为"已行动过"，导致它必须等到当前队列所有参战者都行动完、重新生成队列时才能出手。实际上它本游戏刻只是"加入"了队列，并没有"行动"过，应该在下一个游戏刻按队列顺序正常行动。阶段 1 已结束这一事实，已经天然保证了它本游戏刻不会执行先攻轮，无需用 done 来限制。

## 八、1v1v1v1 架构

### 8.1 不是 1vN，而是 1v1v1v1

**1vN 的问题**：一个玩家同时对抗多个敌人，存在"群体反击"等复杂判断。

**1v1v1v1 的设计**：

- 每个敌人是独立的战斗单元
- 后端逻辑始终遵循"1个敌人、1个敌人的单独战斗处理"
- 先攻队列可以有多个参战者，但每次攻击都是 1对1
- 群体伤害（未来）实际上是分别判定"攻击 A 的事件"、"攻击 B 的事件"，每个事件独立处理

### 8.2 先攻队列的触发场景

- 玩家主动攻击敌人 A → 队列：[玩家, 敌人A]
- 遭遇战：敌人 A 移动到玩家格 → 队列：[敌人A, 玩家]
- 多敌人遭遇：敌人 A、B 同 tick 移动到玩家格 → 队列：[敌人A, 玩家, 敌人B]（1v1v1v1）
- 战斗中新敌人加入：敌人 C 移动到玩家格 → 加入队列末尾

### 8.3 每次攻击 1对1

- `obl_battle_execute($actor, $target, $action_id)` 的 `$target` 始终是单个目标
- 群体伤害技能在内部循环调用单个目标处理逻辑
- 不会出现"攻击 A，B/C 是否反击"的问题——B/C 的反击只发生在它们自己的先攻轮

### 9.2 标记机制的实现

**"游戏刻已推进"标记**：

- 全局变量 `$obl_tick_advanced`（同一请求内有效）
- `obl_resolve_tick_events()` 开始时清除标记
- NPC 先攻轮执行后设置标记
- 末尾检测标记，推进游戏刻

```php
// 伪代码
function obl_resolve_tick_events() {
    global $obl_tick_advanced;
    $obl_tick_advanced = false;  // 清除标记
  
    // 阶段 1：战斗中 NPC 先攻轮
    foreach ($enemies as &$enemy) {
        if ($obl_tick_advanced) break;  // 已推进，跳过
        if ($enemy['action'] === 'battle' && is_current_initiator($enemy)) {
            obl_battle_preload_phase($enemy, $player, null);
            obl_battle_execute($enemy, $player, $actions);
            $obl_tick_advanced = true;  // 设置标记
            update_initiative_queue($enemy);
        }
    }
  
    // 阶段 2：非战斗 NPC AI 行为
    foreach ($enemies as &$enemy) {
        if ($enemy['action'] !== 'battle') {
            obl_enemy_tick($enemy);
        }
    }
  
    // 末尾：统一游戏刻推进
    if ($obl_tick_advanced) {
        global $obl_tick;
        $obl_tick++;
    }
    $obl_pretick = $obl_tick;
}
```
