## 三、前后端字段契约

> 前端代码审阅发现的关键依赖。后端修复时必须保证这些字段契约不被破坏。

### 3.1 BattleLogEntry 字段契约

前端 `battle.js` / `battle-render.js` / `battle-modal.js` 依赖以下字段：

| 字段 | 前端用途 | 后端来源 |
|------|----------|----------|
| `log_id` | 按 log_id 排序 + 标记 played | `obl_battle_log_persist` 分配 |
| `action_id` | switch 分支渲染（`unarmed_strike`/`escape`/`battle_end`/`ap_recover`/`queue_create`/`queue_update`） | `BattleLogCollector::emit` 第 3 参数 |
| `action_name` | default 分支显示 | `BattleLogCollector::emit` 第 4 参数 |
| `phase` | 过滤 `excute` 播放动画 + 检测 `finish_check` 战斗结束 | `BattleLogCollector::setPhase` |
| `enemy_pid` | 分组播放（`enemy_pid=0` 的日志不播放动画） | `BattleLogCollector::emit` 第 9 参数 |
| `actor_type` | 判断玩家/敌人 + CSS 类名（0=玩家 yellow, 非0=敌人 red） | `BattleLogCollector::emit` 第 11 参数 |
| `actor_name` | 显示攻击方名称（actor_type=0 且 name=玩家名时显示"你"） | `BattleLogCollector::emit` 第 10 参数 |
| `turn` | 回合分隔符（turn=0 显示"战斗开始"，turn>=1 显示"回合 N"） | `BattleLogCollector::emit` 第 1 参数 |
| `effect_value` | 伤害数值显示 | `BattleLogCollector::emit` 第 6 参数 |
| `extra.success` | 逃跑成功/失败判断 | `BattleLogCollector::emit` 第 7 参数（extra 数组） |
| `extra.ended` | 战斗结束检测（`extra.ended === true`） | `BattleLogCollector::emit` 第 7 参数（extra 数组） |
| `extra.enemy_hp_after` | 更新敌人 HP 条 | `BattleLogCollector::emit` 第 7 参数（extra 数组） |
| `extra.player_hp_after` | 更新玩家 HP 条 | `BattleLogCollector::emit` 第 7 参数（extra 数组） |

### 3.2 battle_queue 字段契约

前端 `battle.js` 依赖 `player_info` API 返回的 `battle_queue` 字段：

| 字段 | 前端用途 |
|------|----------|
| `queue[].pid` | 提取敌人 PID（第一个 type>0 的参战者） |
| `queue[].type` | 判断玩家(0)/NPC(>0) |
| `queue[].done` | 判断当前顺位（第一个 done=0 的是当前顺位者） |

### 3.3 NPC 回合自动刷新机制

前端 [battle.js:170-178](file:///d:/wamp64/www/phpdts/vex/js/battle.js#L170-L178) NPC 顺位时每 2 秒刷新 `player_info` 触发后端 `common.inc`，从而推进 NPC 行动。

**关键依赖**：NPC 先攻轮的执行依赖于前端定时刷新。S-1 修复后，NPC 先攻轮将正常触发，前端定时刷新会拉取到 NPC 行动后的最新状态。

### 3.4 已验证的字段契约

- **V-1**：`battle_state_clear` emit 的战斗结束日志已包含 `action_id='battle_end'` + `extra.ended=true`，前端可正确检测战斗结束
- **V-2**：`battle_once_excute` 的 `enemy_pid` 设置逻辑正确，玩家攻击和 NPC 攻击两种情况下 `enemy_pid` 都是 NPC 的 PID，前端可正确分组播放

### 3.5 设计不一致点（E-1，独立任务，本次不参与）

`battle_once_excute` 的 enemy_pid 逻辑是"enemy 是对方 PID"，而 `battle_state_clear`、`battle_ap_recover`、`battle_act_verify` 的逻辑是"actor 是玩家时 enemy_pid=0"。

**评估**：enemy_pid 是一个旧的待清理设计，涉及内容很多（前后端字段契约、日志分组逻辑、前端播放机制等），需要单独开新任务执行。本次仅标记，不参与修复。

这个不一致不影响当前功能（前端通过 action_id switch 分支处理系统事件），但应在 E-1 任务中统一清理。

### 任务 3：修复 NPC AI 阶段 1 fetch 跳过第一行 + 按 qid 分组（S-1 + M-7）

**文件**：`oblivions/include/game/enemy_ai.func.php`

**位置**：第 244-287 行（`obl_resolve_all_enemy_ai` 阶段 1）

**问题**：
1. 第 245 行 `$qdata = $db->fetch_array($result);` 预读第一行，导致 while 循环从第二行开始，第一行被跳过
2. `SELECT *` 未按 qid 分组，同一队列的多条记录会重复处理

**前端影响**：S-1 导致 NPC 先攻轮永远不会触发，前端 [battle.js:170-178](file:///d:/wamp64/www/phpdts/vex/js/battle.js#L170-L178) 会无限刷新等待 NPC 行动。

**修复方案**：

将原代码：
```php
# 阶段 1：战斗中 NPC 先攻轮（串行，最多 1 个）

# 载入先攻队列
$result = $db->query("SELECT * FROM {$tablepre}oblqueue");
$qdata = $db->fetch_array($result);

# 存在先攻队列的情况下
if($qdata)
{
    $npc_battle_flag = false;
    while($qdata = $db->fetch_array($result))
    {
        //obl_format_playerdata($pdata);

        $qid = (int)$qdata['qid'];
        if ($qid <= 0) continue;

        # 获取当前顺位者（myorder 最小且 done=0）
        $current = obl_fetch_queue_current_initiator($qid);
        if (!$current) continue;

        # 当前顺位者是玩家 → 不执行 NPC 先攻轮（等待玩家提交 obl_battle_action）
        if ($current['type'] == 0) continue;

        # 当前顺位者是 NPC → 执行 NPC 先攻轮
        $npc_data = obl_fetch_playerdata_by_pid($current['pid']);
        if (!$npc_data) continue;

        # 初始化 battle_log（入口处局部初始化，设置入口标识）
        if (!$obl_battle_log) {
            include_once GAME_ROOT . './oblivions/include/game/battle_log.func.php';
            $obl_battle_log = new BattleLogCollector();
        }
        $obl_battle_log->setEntryType('npc_turn');

        # 构造 NPC 动作（MVP 固定 unarmed_strike，目标为玩家）
        $atk_act = array(
            array('act_id' => 'unarmed_strike', 'target' => $pdata['pid']),
        );

        # 调用 battle_main（内部会更新先攻队列）
        battle_main($npc_data, $atk_act, $obl_battle_log);

        $obl_tick_advanced = true;
        break;  # 最多处理 1 个 NPC 先攻轮
    }
}
```

替换为：
```php
# 阶段 1：战斗中 NPC 先攻轮（串行，最多 1 个）

# 载入所有活跃的先攻队列 qid（DISTINCT 去重，避免同队列多记录重复处理）
$result = $db->query("SELECT DISTINCT qid FROM {$tablepre}oblqueue WHERE qid > 0");

while($qdata = $db->fetch_array($result))
{
    $qid = (int)$qdata['qid'];
    if ($qid <= 0) continue;

    # 获取当前顺位者（myorder 最小且 done=0）
    $current = obl_fetch_queue_current_initiator($qid);
    if (!$current) continue;

    # 当前顺位者是玩家 → 不执行 NPC 先攻轮（等待玩家提交 obl_battle_action）
    if ($current['type'] == 0) continue;

    # 当前顺位者是 NPC → 执行 NPC 先攻轮
    $npc_data = obl_fetch_playerdata_by_pid($current['pid']);
    if (!$npc_data) continue;

    # 初始化 battle_log（入口处局部初始化，设置入口标识）
    if (!$obl_battle_log) {
        include_once GAME_ROOT . './oblivions/include/game/battle_log.func.php';
        $obl_battle_log = new BattleLogCollector();
    }
    $obl_battle_log->setEntryType('npc_turn');

    # 构造 NPC 动作（MVP 固定 unarmed_strike，目标为玩家）
    $atk_act = array(
        array('act_id' => 'unarmed_strike', 'target' => $pdata['pid']),
    );

    # 调用 battle_main（内部会更新先攻队列）
    battle_main($npc_data, $atk_act, $obl_battle_log);

    $obl_tick_advanced = true;
    break;  # 最多处理 1 个 NPC 先攻轮
```

**改动要点**：
1. 去掉预 fetch（第 245 行），直接 while 循环
2. `SELECT *` 改为 `SELECT DISTINCT qid`，按 qid 分组

### 任务 6：重构 battle_queue_update 死亡者扫描（M-3）

**文件**：`oblivions/include/game/battle/battle.func.php`

**位置**：第 151-162 行（B 步骤兜底扫描）

**问题**：兜底扫描的 `UPDATE oblplayers SET bid=0` 会覆盖 `battle_state_clear` 已保存的 `action=''` 状态。

**设计需求**：保留兜底扫描的防御性设计，但避免覆盖已保存的状态。

**修复方案**：重构扫描逻辑，加条件判断

将：
```php
# A. 更新当前先攻者的 done=1
$db->query("UPDATE {$tablepre}oblqueue SET done = 1 WHERE pid = " . (int)$actor_data['pid'] . " AND qid = " . $qid);

# B. 兜底扫描：清理队列中的死亡参战者（battle_queue_exit 已处理的情况会跳过）
$queue_all = obl_fetch_queue_all_by_qid($qid);
foreach ($queue_all as $qrow) {
    $pid = (int)$qrow['pid'];
    if ($pid == $actor_data['pid']) continue; # 跳过自己
    $combatant_data = obl_fetch_playerdata_by_pid($pid);
    if (!$combatant_data || $combatant_data['state']) {
        # 参战者不存在或已死亡，从队列移除并清空 bid
        $db->query("DELETE FROM {$tablepre}oblqueue WHERE pid = " . $pid . " AND qid = " . $qid);
        $db->query("UPDATE {$tablepre}oblplayers SET bid = 0 WHERE pid = " . $pid);
    }
}

# C. 检查队列是否需要解散
```

改为：
```php
# A. 更新当前先攻者的 done=1
$db->query("UPDATE {$tablepre}oblqueue SET done = 1 WHERE pid = " . (int)$actor_data['pid'] . " AND qid = " . $qid);

# B. 兜底扫描：清理队列中可能残留的死亡参战者（防御性设计）
#    正常路径由 battle_target_alive_check → battle_state_clear → battle_queue_exit 处理
#    这里处理异常路径的残留，不覆盖已保存的 action 状态
$queue_all = obl_fetch_queue_all_by_qid($qid);
foreach ($queue_all as $qrow) {
    $pid = (int)$qrow['pid'];
    if ($pid == $actor_data['pid']) continue; # 跳过自己
    $combatant_data = obl_fetch_playerdata_by_pid($pid);
    if (!$combatant_data) {
        # 参战者数据不存在，直接从队列移除
        $db->query("DELETE FROM {$tablepre}oblqueue WHERE pid = " . $pid . " AND qid = " . $qid);
        continue;
    }
    if ($combatant_data['state']) {
        # 参战者已死亡
        if ((int)$combatant_data['bid'] === $qid) {
            # bid 仍指向当前队列，说明 battle_state_clear 未处理，清理 bid
            # 不更新 action 字段，避免覆盖 battle_state_clear 已保存的 action=''
            $db->query("UPDATE {$tablepre}oblplayers SET bid = 0 WHERE pid = " . $pid . " AND bid = " . $qid);
        }
        # 从队列移除
        $db->query("DELETE FROM {$tablepre}oblqueue WHERE pid = " . $pid . " AND qid = " . $qid);
    }
}

# C. 检查队列是否需要解散
```

**关键改动**：
1. 保留扫描逻辑（防御性设计）
2. `UPDATE` 加 `AND bid = $qid` 条件，只清空指向当前队列的 bid
3. 不再更新 `action` 字段（避免覆盖 `battle_state_clear` 已保存的 `action=''`）
4. 数据不存在的异常情况单独处理

## 附录：逃跑系统修复设计原则（暂不执行）

> 以下原则供后续逃跑系统修复时参考，本次不执行。

### 核心原则

1. **逃跑的 target 是自己**：逃跑不是无目标动作，而是目标为自己的动作。严格遵守目标选择设计，`battle_excute` 中 escape 动作的 `target` 应为 `$actor_data['pid']`。`battle_target_check` 检测到 target=自己时，走"目标是自己"的分支（不检测距离）。

2. **不建立新分支处理队列事件**：逃跑成功不应该新建独立函数处理队列事件（如直接清除参战者状态、解散队列）。而应该：
   - 在 `battle_once_excute` 内部根据 act_id 分支处理（escape 时执行逃跑判定）
   - 逃跑结果记录到 `$battle_cache`（如 `escape_success` 标记）
   - `battle_main` 的现有流程中（如 `battle_queue_check` 或 `battle_finish_check`）检查这个标记，走对应的队列处理逻辑

3. **严格遵守流程设计**：逃跑完全在现有 `battle_main` 流程框架内处理，不引入新的函数处理队列事件。流程为：
   ```
   battle_main:
     1. battle_prepare (AP恢复)
     2. battle_verify (校验)
     3. battle_excute (执行先攻轮)
        └─ battle_once_excute 根据 act_id 分支
           └─ escape: 执行逃跑判定，记录到 $battle_cache
     4. battle_queue_check (队列校验)
        └─ 检查 $battle_cache['escape_success']，处理队列
     5. battle_finish_check (战斗结束检测)
        └─ 检查 $battle_cache['escape_success']，处理结束
   ```

## 附录：M-2 qid 竞态问题分析（暂不修复）

### 问题

`battle_queue_create` 使用 `SELECT MAX(qid)+1` 生成新 qid，不是原子操作，存在竞态风险。

### 暂不修复的原因

1. **单玩家设计**：该模式仅有 1 名玩家，不存在多玩家并发创建队列
2. **flock 保护**：`obl_command.php` 有 flock 并发锁，同玩家请求串行执行
3. **NPC AI 串行**：NPC AI 在 `common.inc` 中串行执行，不会与玩家命令并发

### 如果未来需要修复

方案：给 `bra_oblqueue` 表增加 AUTO_INCREMENT 列作为 qid 生成器

```sql
ALTER TABLE bra_oblqueue ADD COLUMN qid_seq INT NOT NULL AUTO_INCREMENT PRIMARY KEY FIRST;
ALTER TABLE bra_oblqueue DROP PRIMARY KEY, ADD UNIQUE KEY uk_pid (pid);
```

代码变更：
```php
# 生成新的 qid（使用 AUTO_INCREMENT 序列，避免 MAX+1 竞态）
$db->query("INSERT INTO {$tablepre}oblqueue (pid, qid, type, qorder, myorder, done) VALUES (0, 0, 0, 0, 0, 0)");
$qid = $db->insert_id();
$db->query("DELETE FROM {$tablepre}oblqueue WHERE qid_seq = " . $qid);
```

**注意**：此方案不会破坏现有功能，因为 `qid_seq` 只是内部生成器，`qid` 字段语义不变（同一队列多行共享相同 qid）。
