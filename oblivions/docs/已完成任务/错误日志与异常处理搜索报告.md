## 四、关键发现总结

### Oblivions 模式错误处理现状

1. **零原生错误函数**：Oblivions 目录下**完全没有** `error_log(`/`app_log(`/`trigger_error(` 调用，代码非常干净。
2. **零主动抛异常**：Oblivions 目录下**完全没有** `throw new` 调用，不主动抛异常。
3. **唯一 try/catch**：仅 `tick.func.php:268-301` 一处，且已正确接入 obl_error_log。
4. **obl_error_log 利用率极低**：整个 Oblivions 后端只有 1 处业务调用（`tick.dispatch.error`），而设计文档已为前端准备了渲染器扩展位（`command.rejected`、`battle.fatal`），说明**设计意图与代码现状存在差距**。

### 应迁移项优先级排序

| 优先级 | 文件:行号 | 当前实现 | 建议迁移 |
|--------|-----------|----------|----------|
| **高** | `tick.func.php:334` | 静默 return | emit `'tick.player_fetch.error'` |
| **高** | `obl_command.php:50,66` | `$obl_log->emit('command.rejected',...)` | 迁移到 `$obl_error_log->emit('command.rejected',...)`（设计文档已要求） |
| **中** | `explore.func.php:329` | `$obl_log->emit('search.data_error',...)` | 额外 emit 到 obl_error_log（数据配置错误） |
| **中** | `enemy_ai.func.php:125` | 静默 return false | emit `'enemy_ai.config_missing'` |
| **低** | `obl_command.php:30` | echo JSON 退出 | 可选 emit `'command.concurrent_rejected'` 作审计 |

### 设计文档与代码的差距

设计文档 `vex-vue 错误日志检测与展示设计方案.md` 第 192-199 行明确预留了扩展位：
```ts
'command.rejected': (p) => `操作被拒绝：${p.reason}`,
'battle.fatal': (p) => `战斗系统异常：${p.error}`,
```
但代码中：
- `command.rejected` 仍走 obl_log（未迁移）
- `battle.fatal` 完全没有对应的 emit 调用（战斗系统目前无任何 fatal 错误日志）

这表明错误日志系统的前端展示层已就绪，但后端 emit 端的迁移工作尚未完成。

调研完成。两份报告揭示了错误日志系统的现状与设计意图之间的差距。

## 迁移建议

我建议分两阶段处理：

**阶段一：后端 emit 迁移**（与错误日志系统直接相关）
- 高优先级 2 项：`tick.player_fetch.error` + `command.rejected` 迁移
- 同步在前端 `error-log.ts` 的 `ERROR_RENDERERS` 补充对应渲染器
- 中优先级 2 项可选

**阶段二：前端错误展示增强**（独立于错误日志系统，属于前端健壮性改进）
- 关键 store 的 console.error 补充 Toast 提示
- 注册全局错误处理器
- 这个阶段与 obl_error_log 系统无直接关系，是前端自身的错误展示改进
