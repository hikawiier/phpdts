> 关联框架：L-9 POI 交互模态框、E-10 POI 搜刮三档判定系统、F-4 战利品表引擎、A-3 状态查询范围分发

## 一、任务背景

### 1.1 原始方案要求

原始方案 §4.2 中上部交互区规定：

> 中上部交互区：显示实时物资概率条、事件概率条和**可能搜刮出的道具列表**/交互结果。

§6 战利品池规则要求：

> 每个 POI 关联一张"战利品表"，表由若干**物品组**构成，每组独立掷骰；每组内可列出多个**互斥选项**，根据权重选择其中一个；每个选项指定：物品类型、出现概率、数量范围。

### 1.2 当前实现差距

| 维度 | 原始方案要求 | 当前实现 | 差距 |
|------|-------------|----------|------|
| 三档概率条 | ✓ | ✓ 已暴露 `base_loot_chance` / `base_good_event_chance` / `base_bad_event_chance`，前端 `PoiInteraction.vue` 已渲染三档概率条 | 无 |
| **可能产出预览** | ✓ | ✗ **后端未投影 loot_table 结构，前端无预览区** | **本次填补** |

### 1.3 范围与边界

**本案仅覆盖"可能产出预览"**——把 POI 模板关联的 F-4 战利品表（`loot_table_id`）的结构投影到前端，在 `PoiInteraction.vue` 中上部交互区的概率条下方新增"可能产出"区。

**不在本案范围：**
- 工具/技能 `loot_table_overrides` 路由后的预览切换（仅显示默认表，文案提示"选择工具可改良"）
- `prob_mods` 实时修正后的概率条联动（继续维持基础值展示，与现有 §2.6 占位策略一致）
- 嵌套表/容器装填（原方案 §6.2/§6.3 已声明占位不实现）
- 事件池（`event_pool`）的恶性事件物品不投影（信息安全：不暴露陷阱类 item_id）

## 二、研判：当前实现与原始方案的差距

### 2.1 后端现状

`obl_state_handle_tile_actions`（`oblivions/include/api/obl_state_handlers.php`）当前已为每个 POI 投影：

- 概率字段：`base_loot_chance` / `base_good_event_chance` / `base_bad_event_chance`
- 工具有效性：`prob_mods_source`（白名单 ID 数组）+ `loot_table_overrides`（override 表 ID 的 keys）
- 交互列表：`interactions`（F-6 道具交互）
- 耐久字段：`placed_by_pid` / `placed_at_day` / `ttl_days` / `ttl_remaining_days`
- 拆除返还：`dismantle_returns`

**未投影**：POI 模板的 `loot_table_id` 字段、`loot_tables.php` 表内的 `groups[]` 结构。

### 2.2 前端现状

`PoiInteraction.vue` 中上部交互区现有结构：

```
[搜索概率]
  ├─ 概率条：物资 / 良性事件 / 恶性事件
  └─ 提示：基础概率（未应用工具/技能修正）
[PoiFeedbackPanel]（搜索结果 + 道具列表 + 拾取按钮）
```

**缺少"可能搜刮出的道具列表"区**——这是 §4.2 明确要求的"决策辅助"信息。

### 2.3 关键研判结论

1. **loot_table 数据源**：`oblivions/gamedata/loot_tables.php` 已是纯数据配置，后端可直接读取并投影；无需新增命令或独立 scope。
2. **投影时机**：`tile_actions` scope 是天然载体——POI 列表已在此投影，新增 `loot_preview` 字段即可，无独立请求开销。
3. **信息安全**：loot_table 内只包含"普通掉落"物品（医疗品、素材、装备等），不包含 `event_pool` 的陷阱/恶性事件 ID。**恶性事件概率已通过 `base_bad_event_chance` 暴露**（不暴露具体陷阱 item_id，符合安全要求）。
4. **投影策略**：投影**默认 loot_table_id** 的结构，不应用 `loot_table_overrides`——因为 tile_actions scope 调用时机早于玩家选工具，工具选择是前端状态。前端在 `loot_table_overrides` 非空时显示提示文案"选择工具可改良掉落表"。
5. **概念边界**：loot_table 预览 ≠ 已物化掉落物列表（`items[]`）——前者是"可能"，后者是"已搜出"。两者在视觉上需明确区分（预览区在概率条下方，已物化道具列表在 PoiFeedbackPanel 中）。

## 三、设计决策

### 3.1 后端投影策略

#### 3.1.1 新增辅助函数 `obl_build_loot_preview_for_poi`

放置位置：`oblivions/include/game/poi/poi.search.func.php`（与 E-10 概率计算同文件，归属 E-10 框架；该文件已 `@framework E-10`，扩展不引入新框架）。

**职责**：根据 POI 模板的 `loot_table_id`，从 `loot_tables.php` 读取表结构，投影为前端可消费的预览结构。

**投影规则**：

1. **入参**：POI 实例行 + POI 模板
2. **状态过滤**：
   - `searchable=false` → 返回 `null`（机制型/地标型 POI 无产出预览）
   - `state='exhausted'` → 返回 `null`（POI 已耗尽，预览无意义；玩家应看 `items[]`）
   - 模板 `loot_table_id` 缺失或对应表在 `loot_tables.php` 不存在 → 返回 `null`
   - 表 `groups` 为空（如 `empty_loot`） → 返回 `null`
3. **结构投影**：
   - 表级 `table_name`：直接读 `loot_tables[$id]['name']`
   - 组级 `chance`：归一化为 0-1 浮点
   - 组内 entries：每个 entry 计算 `probability = weight / Σweight`（组内归一化，组级 chance 已独立表达"是否掷骰"语义）
   - count：`int` 投影为 `{min: n, max: n}`；`[min, max]` 投影为 `{min, max}`；自动 swap 反向区间
4. **item_id 安全性**：直接投影 `entry['item_id']`——loot_table 配置中不含陷阱/恶性事件 ID，安全。

#### 3.1.2 在 `obl_state_handle_tile_actions` 中调用

在现有 `$poi_data` 构造流程末尾，调用 `obl_build_loot_preview_for_poi($poi, $template)` 并写入 `loot_preview` 字段。

**性能考量**：`loot_tables.php` 与 `poi_table.php` 在同一 scope 内已被加载（`include` 受 PHP 操作码缓存保护，无重复 IO）；投影是纯计算，开销可忽略。

### 3.2 前端展示策略

#### 3.2.1 TypeScript 类型扩展（`vex-vue/src/types/api.ts`）

新增三类型：

```typescript
export interface PoiLootPreviewEntry {
  item_id: string;
  probability: number;   // 0-1，组内 weight 归一化
  count_min: number;
  count_max: number;
}

export interface PoiLootPreviewGroup {
  chance: number;        // 0-1，组级掷骰概率
  entries: PoiLootPreviewEntry[];
}

export interface PoiLootPreview {
  table_name: string;
  groups: PoiLootPreviewGroup[];
}
```

扩展 `Poi` 接口，新增字段：

```typescript
loot_preview?: PoiLootPreview | null;
```

#### 3.2.2 PoiInteraction.vue 新增"可能产出"区

放置位置：在概率条区下方、PoiFeedbackPanel 上方，归属于中上部交互区。

**视觉结构**：

```
[搜索概率]
  ├─ 概率条：物资 / 良性事件 / 恶性事件
  └─ 提示：基础概率（未应用工具/技能修正）
[可能产出]                                ←── 新增
  ├─ 提示：（选择工具可改良掉落表）        ←── 仅 loot_table_overrides 非空时显示
  └─ 物品组 × N
      ├─ 组级 chance 标签 + 第 N 组序号
      └─ 条目列表
          [物品名] [组内概率%] [×数量范围]
[PoiFeedbackPanel]
```

**显示条件**：

- `showLootPreview = currentPoi.searchable && !isMechanic && currentPoi.loot_preview !== null`
- 已与 `showProbabilityBars` 同条件（可搜索且非机制型），保证概率条与产出预览同时呈现

**物品名渲染**：复用 `getItemName(item_id)`（`vex-vue/src/data/item-locale.ts`），与 PoiFeedbackPanel 同一 locale 源。

**数量范围文案**：
- `count_min === count_max` → `×N`（如 `×1`）
- `count_min !== count_max` → `×min-max`（如 `×2-4`）

**组级 chance 文案**：
- `chance === 1.0` → `必出`
- `chance < 1.0` → `NN%概率`

**组序号**：使用 `第 N 组`（1-indexed），不投影组名（`loot_tables.php` 的 group 配置无 name 字段，仅表级有 name）。

**视觉冲突规避**：
- 与 F-6 道具交互区（中列下部"道具操作"）视觉分离——产出预览在中上部、道具操作在中下部，由 `poi-interaction-zone` 与 `poi-interact-zone` 两个独立容器天然分隔
- 与右列"可用工具（搜刮辅助）"语义不同——右列是"玩家有什么工具可用"，产出预览是"POI 能产出什么"，关注点互补不重叠

### 3.3 边界处理

| 边界场景 | 处理方式 |
|---------|---------|
| **冷却中（state='cooldown'）** | 仍展示产出预览——玩家可规划"冷却到期后是否值得搜" |
| **已搜空（state='exhausted'）** | 后端返回 `loot_preview=null`，前端 `showLootPreview=false`，区域隐藏；玩家应看 `items[]` 已物化道具 |
| **机制型 POI（mechanic 非空且非 interact_）** | `searchable=true` 但走 `obl_execute_mechanic` 分发，`loot_table_id='empty_loot'`，后端检测到空 groups 返回 `null`，前端隐藏产出预览 |
| **F-6 交互型 POI（mechanic 以 interact_ 开头）** | `searchable=false`，后端直接返回 `null` |
| **地标型 POI（无 mechanic、searchable=false）** | 后端返回 `null` |
| **已搜索且无重复（searched=true && repeatable=false）** | 后端通常已将 state 推进到 `exhausted`；若状态机异常停留在 searched，预览仍展示（但前端 `searchLimitReached=true` 时搜索按钮禁用，玩家无法执行） |
| **loot_table_id 配置缺失/表不存在** | 后端 emit error 日志（防御性），返回 `null`；前端隐藏产出预览 |
| **count 配置反向（如 `[5, 2]`）** | 后端投影时 swap 为 `{min: 2, max: 5}`，与 F-4 引擎 `obl_roll_group` 的 swap 行为一致 |
| **weight 全 0 的组** | F-4 引擎会均匀随机选一（`obl_weighted_pick` 兜底）；后端投影时按均匀分布计算 `probability = 1 / count(entries)` |

### 3.4 信息安全

- loot_table 配置只含普通掉落物品（医疗品、素材、装备等），**不含** `event_pool` 的陷阱/恶性事件 item_id
- 陷阱类信息通过 `base_bad_event_chance` 概率值暴露（不暴露具体 item_id）
- 玩家可见"恶性事件概率 30%"但不知具体是什么事件——符合"风险感知但保留惊喜/惊吓"的废土生存体验

### 3.5 设计自校准

#### 错误检查
- ✓ TypeScript 类型 `PoiLootPreview` 与后端投影字段一一对应：`table_name` / `groups[].chance` / `groups[].entries[].{item_id, probability, count_min, count_max}`
- ✓ 后端 `obl_build_loot_preview_for_poi` 返回字段名与 TS 类型字段名一致（snake_case 与 camelCase 通过 `loot_preview` 单字段统一为 snake_case，与现有 `base_loot_chance` 等字段同模式）

#### 遗漏检查
- ✓ 冷却中：保留预览（决策辅助价值）
- ✓ 已搜空：隐藏预览（避免误导，引导玩家看 `items[]`）
- ✓ 机制型 POI：隐藏预览（无实际掉落）
- ✓ loot_table_id 缺失：隐藏预览（防御性兜底）

#### 冲突检查
- ✓ 与 F-6 道具交互区视觉分离：产出预览在中上部交互区（`poi-interaction-zone`），道具操作在中下部（`poi-interact-zone`），由布局天然分隔
- ✓ 与右列"可用工具"语义互补：右列是"玩家有什么"，产出预览是"POI 能出什么"

#### 冗余检查
- ✓ 不与右列"可用工具"重复——两者数据源、关注点、视觉容器均不同
- ✓ 不与 `items[]`（已物化道具列表）重复——前者是"可能"，后者是"已搜出"

#### 全面性检查
- ✓ 后端：新增投影函数 + tile_actions scope 调用
- ✓ 前端：类型扩展 + PoiInteraction.vue 新增区域
- ✓ 边界处理：4 类 POI 状态 + 配置异常均覆盖

### 3.6 设计哲学对齐（DESIGN.md §3）

- **3.1 降低理解成本**：预览结构按"组级 chance → 组内 entries 概率"两层呈现，与 F-4 引擎掷骰流程对齐，玩家通过视觉直接理解"先掷组，再在组内掷 entry"的语义
- **3.2 概念引入成本-收益**：不引入新概念，复用 `loot_table` / `groups` / `entries` / `weight` / `chance` 等已有术语，前端只增加一个 `loot_preview` 字段
- **3.3 字面贴近意图**：区域标题"可能产出"直白表达"这里列出 POI 可能搜刮出的道具"，不引入"战利品预览"等抽象术语
- **3.4 少即是多**：灰阶色阶复用现有 `.dim` / `#ddd` / `#888` 调色板，不新增颜色；组级 chance 用百分比文本而非进度条（避免与三档概率条视觉冲突）；物品名 + 概率 + 数量三列布局，无装饰元素

## 六、Dian.md 更新评估

本次修改属于 L-9 框架内中上部交互区的展示扩展，未引入新框架概念（loot_preview 仅是 tile_actions scope 的字段扩展，未升格为独立框架）。

**结论**：不更新 Dian.md L-9 框架描述。理由：

1. L-9 框架描述中已包含"基础概率展示"语义，本次扩展属于该语义的细化（增加产出预览），未改变框架边界
2. loot_preview 投影属于 A-3 tile_actions scope 的常规字段扩展，与现有 `interactions` / `dismantle_returns` / `ttl_remaining_days` 等字段同模式，未引入新框架
3. 按 Dian.md 写入约束"普通模块文件同步 @module；直接实现框架的核心文件同时同步 @framework 与 Dian.md 代码锚点"——本次修改的两个核心文件（`poi.search.func.php` 与 `obl_state_handlers.php`）已分别归属 E-10 与 A-3 框架，@framework 标签无需变更
