# 战斗演出事件消费与权威投影解耦研判

> 日期：2026-07-11  
> 状态：响应直带、F5 快进、持续权威投影、独立演出场景、战斗结束交接与战后连续性已实施并完成自动化验收（2026-07-11）；待最终实机视觉边界回归。  
> 范围：Oblivions `battlelog.v2` 生产、持久化、Director/Planner/Runner 消费、F5 冷启动与地图状态刷新
>
> 第 2-8 节及 §12.1-12.6 保留实施前事实快照与推导过程；当前实现基准见 §12.7 与第 13 节。

## 1. 结论摘要

用户提出的三个观察都指向真实问题，但严重程度和正确解法不同：

| 观察 | 是否真实 | 判断 |
|---|---|---|
| played 后不清理，文件持续增长 | 是 | 当前实现单局内持续增长，且所有操作都整文件读写；不是立即爆炸的问题，但属于确定的存储与并发债务 |
| F5 后必须重播未读日志可能过度设计 | 是 | 对瞬时动画而言是错误的可靠性目标；当前实际是 at-least-once 重播，并不能保证 exactly-once，也不能保证重播时视觉基线正确 |
| 刷新与播放争抢，需要不断加屏障 | 是 | 根因不是“刷新太积极”，而是权威状态和演出状态共用同一套响应式投影；现有屏障是在补偿所有权边界缺失 |

总体建议：需要架构级解决，但不应把问题简化为“播放后删除日志”或“F5 时直接标记 played”。正确方向是拆分三种职责：

1. **权威状态快照**：决定当前真实世界、战斗状态和命令权限，可随时刷新。
2. **实时演出事件流**：只为当前前端运行时提供有序动画提示，允许跳过和快进，不承担游戏正确性。
3. **持久历史/诊断记录**：用于日志区、审计和调试，有独立保留策略，不参与动画是否必须播放的判断。

## 2. 当前链路事实

### 2.1 后端存储不是归档，而是整局单文件队列

当前每个玩家使用一个文件：

```text
oblivions/cache/battles/obl_battle_log_{groomid}_{pid}.json
```

该文件不是“一场战斗一个文件”，而是该玩家当前整局游戏的所有 battle log：

- `obl_battle_log_persist()` 读取全部旧条目，扫描最大 `log_id`，合并新条目，再覆盖写回整个文件。
- `obl_battle_log_load()` 读取并解析整个文件，再筛选 `played=0`。
- `obl_battle_log_mark_played()` 读取并解析整个文件，修改部分条目，再覆盖写回整个文件。
- 只有新一局 `obl_rs_game()` 才调用 `obl_battle_log_clear_all()` 整体删除。

因此单次操作为 `O(N)`，整局不断追加时累计成本接近 `O(N²)`。

配置 `battle_log_old_max=10` 和 `obl_battle_log_get_old_max()` 当前没有任何调用方，不存在实际“保留最近 10 批”的归档机制。

### 2.2 debug 条目永远不会被当前前端确认

`obl_battle_log_load(..., false)` 会过滤 `debug=true`，前端只能标记实际返回的 render 条目。结果是 debug 条目一直保持 `played=0`，但又永远不会被正常消费。

当前实机文件样本：

| 指标 | 数值 |
|---|---:|
| 条目总数 | 35 |
| render 条目 | 31 |
| debug 条目 | 4 |
| played=1 | 31 |
| played=0 | 4 |
| 未播放 debug | 4 |
| 文件大小 | 41,729 bytes |

这证明 `played` 不是文件生命周期标记，只是 render 消费状态；用它承担归档职责在概念上已经失配。

### 2.3 当前文件锁不能保护完整读改写事务

`file_put_contents(..., LOCK_EX)` 只锁住最终写入，不锁住此前的 `file_get_contents -> decode -> merge/mark`。

若 heartbeat 正在追加日志，同时前端调用 mark endpoint：

```text
请求 A：读取旧文件 -> 追加新事件 -> 写回
请求 B：读取旧文件 -> 标记 played -> 写回
```

最后写入者可能覆盖另一请求的结果。当前 daemon heartbeat 在播放期间仍可运行，多标签页也共享同一玩家文件，因此这不是纯理论并发。

## 3. 对问题一的判断：文件增长是否需要解决

### 3.1 真实，但不是“跨局无限增长”

文件会在单局内持续增长，新局初始化会删除，所以不存在无限跨局累积。但长局、多次多目标战斗、debug 事件较多时，文件会显著增大。

真正风险不只是磁盘容量：

- 每次 persist/load/mark 都整文件 JSON 编解码。
- 每次 mark 都重写所有历史数据。
- 文件越大，并发读改写窗口越长。
- debug 条目无法自然进入完成态。
- 文件损坏会同时影响该玩家整局的全部演出事件。

### 3.2 不建议只做 played 条目删除

“mark 时把 played 条目过滤掉”能降低文件大小，但仍有问题：

- 仍然是整文件读改写。
- append 与 mark 的并发覆盖仍存在。
- F5 重播语义没有解决。
- render 事件和诊断历史仍混在同一存储。
- 无法表达批次、战斗、客户端游标和冷启动策略。

它可以作为短期止血，但不应成为目标架构。

## 4. 对问题二的判断：F5 强制重播是否过度设计

### 4.1 当前并不是可靠的 exactly-once 播放

当前协议是：

```text
获取 played=0 -> 播完整批 -> 标记整批 played=1
```

它只能提供近似 at-least-once：

- 播放中 F5：整批未确认，会从头再播。
- 播完但 mark 请求失败：下次再播。
- 两个标签页同时拉取：两边都可能播放；一边确认后另一边仍在播放。
- mark 和 append 并发：可能丢确认或丢事件。

因此“玩家必须看过一次”这一目标既付出了高复杂度，也没有真正实现。

### 4.2 动画是提示，不是权威事实

战斗 HP、位置、存活、队列、命令权限都来自后端权威状态。battlelog 动画的职责是解释“状态如何变化”，不能成为状态正确性的前置条件。

F5 后页面已经用最新 `player_info/game_map/enemies/combat_context` 建立当前世界，再把旧事件应用到这个最新视觉基线，会产生天然矛盾：

- 已经死亡并从快照消失的角色无法可靠重演死亡过程。
- 已经移动到新位置的角色可能从错误起点播放旧移动。
- 多个旧批次可能跨越当前 qid、round 或场景 generation。
- 页面销毁后旧 ActorRuntime、PresentationSession 和中间姿态都不存在。

因此冷启动时强制重播详细动画，不是可靠恢复，而是用事件增量重建一个已经丢失的演出上下文。

### 4.3 应保留的信息不等于应重播的动画

建议按信息性质分流：

- 战斗开始、胜负、死亡、获得物品等长期重要信息进入 `obl_log`，可在日志区回看。
- 当前仍需玩家处理的选择必须成为后端显式状态，例如 `pending_decision`，由快照驱动 UI；不能靠重播 notice 重新制造交互。
- battlelog.v2 保持为短生命周期演出事件，冷启动默认跳到 head。
- 可选提供“查看战斗回顾”，但它是独立 replay viewer，使用完整历史和独立场景，不污染当前地图 ActorRuntime。

### 4.4 推荐的启动策略

| 场景 | 策略 |
|---|---|
| 同一 JS 运行时正常战斗 | 顺序播放尚未消费的实时批次 |
| 短暂网络中断但页面未销毁 | 若 cursor 连续且仍是同一 qid，可补播；差距过大则快进 |
| F5 / 新标签页 /浏览器重启 | 从权威快照直接建立当前画面，presentation cursor 跳到 server head，不强制重播 |
| 玩家主动点击回顾 | 在独立回顾视图播放归档，不控制当前世界 |

## 5. 对问题三的判断：刷新是否在与播放争抢生态位

### 5.1 现象真实，根因是双重职责共用同一投影

当前 `CharacterHub -> entities -> MapGrid` 同时承担：

1. 最新后端状态的响应式投影。
2. 当前动画正在操作的可见演员集合。

heartbeat 刷新最新状态时，Vue 会立刻增删、移动 Actor；Director 同时假设旧 Actor 和旧位置仍存在。为避免冲突，系统逐步增加了：

- `isPlayingBattleLog` 全局命令锁。
- `isProcessingBattle` 刷新互斥。
- 地图点击、键盘移动和 command queue 多处屏障。
- `DeferredVisualScopes` 延迟 CharacterHub/map 写入可见投影。
- `BattlePresentationSession` 和 channel lease。
- stable boundary commit/reconcile。

其中 Actor channel lease 是合理的局部动画所有权；但广泛延迟权威刷新和全局封锁输入，说明数据层与演出层边界仍不完整。

### 5.2 页面刷新不应被建模成演出系统的竞争者

F5 会销毁整个 JS runtime。旧播放任务无法也不应该跨页面恢复。正确语义是：

```text
旧页面：presentation session 终止
新页面：读取 authoritative snapshot -> 创建新的 presentation baseline
```

它不是“旧计划与刷新争抢”，而是旧计划已经不存在。若新页面仍必须接手旧计划，就必须持久化完整演出状态机，包括 step cursor、Actor 姿态、场景 generation 和 modal 进度；当前系统没有这些数据，也没有必要承担这项成本。

### 5.3 需要双投影，而不是更多屏障

目标前端结构：

```text
Server authoritative snapshot
           |
           v
AuthoritativeStore  ----> command capability / HP / battle state / panels
           |
           | explicit rebase at presentation boundary
           v
PresentationSceneStore --> MapGrid entities --> ActorRuntime

Presentation event batches --> Director --> Planner --> Runner
                                      |             |
                                      +------ mutate PresentationScene/ActorRuntime
```

规则：

- AuthoritativeStore 始终允许刷新，不因动画暂停。
- MapGrid 不直接渲染最新 AuthoritativeStore，而渲染 PresentationSceneStore。
- 实时事件只推进 PresentationScene；一个批次完成后可 rebase 到最新 authoritative snapshot。
- 差距过大、场景失效或冷启动时直接 rebase + cursor=head，不尝试补做所有历史动画。
- 命令权限来自后端 capability/state，不来自 `currentMode` 或“动画是否结束”。
- Actor lease 只解决同一 PresentationScene 内的动画通道竞争，不负责阻挡数据刷新。

## 6. 推荐后端协议：响应直带 Presentation Batch

### 6.1 不再把实时演出建成可靠消息队列

当前所有战斗演出事件都由 `command.php` 或 `heartbeat.php` 请求产生。这两个入口都在领域事务 COMMIT 后、发送 HTTP response 前调用 `obl_runtime_persist_logs()`；此时 `BattleLogCollector` 的完整 entries 仍在内存中。

因此实时演出的首选 delivery 不需要第三次 `battle_log` 轮询，也不需要服务端 played/ack 队列。应把本请求产生的事件直接附加到当前 command/heartbeat response：

```text
PresentationBatch {
  batch_seq
  groomid
  recipient_pid
  qid
  request_id
  tick
  state_after
  events[]
}
```

约束：

- `batch_seq` 在房间或玩家维度单调递增，可在 `oblgame` 保存轻量 head。
- `events[]` 内保留现有 battlelog.v2/event_uid/action_uid/effect_uid。
- `presentation` 字段只在领域 COMMIT 后附加到 response，批次只描述已经提交的事实。
- 前端收到 command/heartbeat response 时同时更新 AuthoritativeStore，并把 batch 放入 PresentationQueue。
- 前端只维护本 JS runtime 的 `presentationCursor`，完成或主动跳过批次后前移。
- response 丢失时不重取旧动画；下一次权威快照直接 reconcile，并通过 `head_seq` 识别发生过 gap。

该语义承认演出是 best-effort：事件丢失可以导致少看一次动画，但不能导致状态错误、命令重放或页面阻塞。

### 6.2 持久记录从 live delivery 中拆出

如果产品需要战斗回顾、开发调试或审计，可以在 response delivery 之外 best-effort 写入不可变 archive。archive 不能参与“当前动画是否已经播放”的判断。

首选 MySQL 批次表：

- 并发插入、序号和查询边界更明确。
- 不需要整文件改写。
- 可以按玩家、qid、seq 查询独立回顾。
- 可按 battle_end、TTL 或数量批量归档/清理。
- 单批 events JSON 保留现有灵活事件结构，避免拆成大量字段表。

与领域事务的关系保持现有原则：领域 COMMIT 成功后再 best-effort 写 archive；失败只返回诊断 warning，不影响 response 中已经可以发送的 presentation batch，也不自动重放命令。

若暂时坚持文件存储，最低要求是：

- 一批一行 NDJSON 或一批一文件，只追加、不改历史。
- 使用覆盖完整 read/append 的 `flock`，不能只锁最终 write。
- battle_end 后旋转为归档文件，不再维护在线 played 文件。

### 6.3 保留与清理

建议：

- 在线 delivery：只存在于当前 HTTP response 和前端内存队列，无服务端清理问题。
- 完成战斗：保留摘要和可选 replay archive；没有回顾需求时无需持久化详细 render 事件。
- debug/diagnostic：进入独立诊断流或 archive 保留策略，不使用 presentation cursor。
- 新局初始化仍可整体清理，但不再是唯一清理时机。

### 6.4 何时才需要服务端 cursor 拉取

只有产品明确要求“页面关闭后仍能继续从断点播放详细动画”时，才应增加短期 PresentationBatch journal 和 `GET after_seq`。这意味着同时承担 step cursor、场景重建和跨设备消费语义，成本很高。

当前需求没有证明这项能力有价值，因此不应默认建设。冷启动快进 + 独立战斗回顾比跨页面恢复当前演出更清晰。

## 7. 前端目标语义

### 7.1 不再使用 played 作为强制完成条件

前端状态应区分：

- `authoritativeRevision`：最新权威快照版本。
- `presentationCursor`：本运行时已经呈现或主动跳过的 batch_seq。
- `presentationPhase`：`idle | playing | rebasing`，只描述表现层，不冒充后端战斗状态。
- `presentationSceneRevision`：当前 MapGrid 正在呈现的场景版本。

`presentationCursor < head_seq` 只表示当前运行时观察到演出序号缺口，不表示游戏状态不完整，也不应阻止权威刷新。缺口默认触发 rebase/快进，不请求强制补播。

### 7.2 输入锁需要收缩

建议保留：

- HTTP 请求互斥和防重复提交。
- 后端 PROCESSING/capability 对推进 tick 命令的约束。
- battle mode 对探索命令的领域约束。
- ActorRuntime channel lease。

建议移除或降级：

- `isPlayingBattleLog` 对所有命令的一刀切全局锁。
- 地图、command queue、组件三处重复的同义播放屏障。
- 用延迟权威状态刷新保护动画。

若 UX 要求玩家看完当前动作再提交下一回合，应使用局部 `presentationCaughtUp` 禁用战斗提交按钮；后端仍是最终权限裁决。它不应冻结无关 UI、日志、状态栏和后台同步。

### 7.3 stable boundary 的新含义

当前 stable boundary 同时承担“允许刷新数据”和“释放动画 lease”。目标结构中应改为：

1. 权威状态早已更新。
2. 当前 batch 播放结束。
3. PresentationScene rebase 到最新 authoritative snapshot。
4. 释放/重建必要的 Actor lease。
5. cursor 前移并处理下一批。

这样 stable boundary 是表现层内部提交点，不再是网络刷新许可。

## 8. 与现有设计的冲突与修正

现有《前端战斗退出后端校验设计案》把“导演播放完”设为退出战斗页面的必要前置，并认为 F5 时重新进入 `refreshBattle` 是正确恢复入口。这个设计解决了当时“后端先结束导致动画被吞”的直接 bug，但将动画播放提升成了状态机门槛。

新的判断是：

- “不能让权威投影在 live 动画中途拆掉演员”仍然正确。
- “必须播放完历史日志才能接受后端状态”不再成立。
- live runtime 应让 PresentationScene 完成或显式快进后 rebase。
- cold boot 应直接接受权威状态，不恢复旧演出。

这不是否定 Director/Planner/Runner。相反，四层演出架构继续保留，只是它的输入改为短生命周期 batch/cursor，输出改为 PresentationScene，而不是直接与 AuthoritativeStore 争夺同一 Actor。

## 9. 实施优先级

| 阶段 | 预计代价 | 主要收益 | 风险 |
|---|---|---|---|
| Phase 0 | 低，当前已具备 | 保持现有战斗播放正确性 | 继续背负 played/屏障债务 |
| Phase 1 | 中 | 删除额外 battle_log 拉取和实时 ack，先解决存储与 F5 语义 | response 契约与多入口接线遗漏 |
| Phase 2 | 高 | 从根源消除刷新与 Actor 演出争抢 | MapGrid/CharacterHub/战斗 UI 投影边界调整面较大 |
| Phase 3 | 中 | 冷启动、断线、快进语义明确 | 需要完整浏览器工作流验证 |
| Phase 4 | 中 | 删除旧文件、mark endpoint 和重复屏障 | 必须确认所有消费者已迁移 |

这不是必须立即插入所有开发工作的紧急故障，但已经持续制造动画竞态、补丁和调试成本。建议在当前 ActorRuntime 修复完成并通过实机回归后，将其作为下一项框架重构，而不是继续扩展 played/DeferredVisualScopes。

### Phase 0：维持当前正确性

- 保留现有 PROCESSING 日志排空和 BattlePresentationSession 修复。
- 保留调试轨迹，继续验证同 qid 不跨错误 session。
- 不在本阶段简单删除 played 条目，以免掩盖并发和冷启动语义问题。

### Phase 1：建立新 delivery 协议

1. 定义 command/heartbeat response 的 `presentation` 字段和 `batch_seq/head_seq`。
2. API 在 COMMIT 后直接附加当前 BattleLogCollector render events。
3. 前端响应处理统一把 batch 送入 PresentationQueue，Director 直接消费 batch events。
4. 迁移期双发 response batch 与旧 battle_log 文件，验证一致后停止 live 文件消费。

### Phase 2：拆分 AuthoritativeStore 与 PresentationSceneStore

1. MapGrid entities 改从 PresentationSceneStore 读取。
2. heartbeat/player_info/map/enemies 始终更新 AuthoritativeStore。
3. Runner 在表现层显式应用事件和 rebase。
4. 删除 DeferredVisualScopes 对网络刷新时机的控制职责。

### Phase 3：修改冷启动与恢复语义

1. App 启动先加载 snapshot + presentation head。
2. F5 默认 cursor=head，直接呈现当前状态。
3. 同 runtime 网络恢复按连续性选择补播或快进。
4. 重要战斗结果通过 obl_log/摘要呈现。

### Phase 4：删除旧机制

1. 删除 per-entry `played`。
2. 删除 `mark_battle_log_played.php`。
3. 删除旧整文件 mutable JSON 存储。
4. 收缩 `isPlayingBattleLog` 全局锁和重复地图屏障。
5. 更新 DESIGN/CODEBASE 和旧设计案状态。

## 10. 最终判断

1. **问题需要解决。** 当前 played 文件模型在生命周期、并发和复杂度上都存在确定缺陷。
2. **用户关于 F5 过度约束的方向正确。** 详细动画不应成为持久、强制、跨页面的消费义务。
3. **用户关于刷新与播放争抢的判断正确。** 但解法不是禁止刷新，而是让权威状态与演出场景拥有不同投影。
4. **不建议马上只做日志删除。** 那只解决文件体积，无法解决重播语义和刷新屏障。
5. **建议进入架构重构。** 核心目标应定为“响应直带不可变 PresentationBatch + runtime queue/cursor + Authoritative/Presentation 双投影 + 冷启动快进”。

## 12. 战斗结束到世界 AI 的视觉连续性

> §12.1-12.6 保留修复前问题事实与方案推导；其中 `world_ai_resume_tick` 仅是已删除的过渡方案。现行结果见 §12.7、§13.3 与《狼狈被动技能与持续状态效果框架设计案》实施结果。

### 12.1 用户描述的问题真实存在

当前后端只保证同一 TickFrame 不让战斗 actor 再执行 world AI：

- TickFrame 入口通过 `BattleActorScope` 快照战斗成员。
- actor 即使在 combat domain 中逃跑、清除 action/bid，也会在本 TickFrame 的 world AI domain 被 `battle_scope` 阻挡。
- 下一 TickFrame 中，若 actor 已不在队列，`BattleActorScope` 不再包含它，便恢复普通 world NPC 资格。

逃跑效果本身只做：

- `tag_mutations[pid].escaped=true`。
- `combatants[pid]=0`。
- cleanup 时保持 `state=0`、清除 `action`、退出队列、恢复 AP。

它不改变 `pls`，不生成世界退避目标，也没有 `world_ai_resume_tick` 或“刚退出战斗”的冷却状态。所以下一 TickFrame 只要 `action_chance` 随机判定通过，NPC 就可以巡逻移动。

当前前端的 escaped 演出为：

```text
fade alpha 1 -> 0
stable commit 发现 actor 仍在权威投影
reset-visible alpha 0 -> 1
若下一世界快照位置变化，再播放普通 world move
```

因此玩家可能看到：

```text
敌人逃跑消失 -> 在原格重新出现 -> 很快又移动一格
```

此前“同一战斗被错误拆成两个 PresentationSession，world AI 在尾随 clear 前介入”的问题已由 PROCESSING 日志排空修复；本节讨论的是战斗真正结束后下一 TickFrame 的合法 world AI，二者不能混为一谈。

### 12.2 通用整图过渡只能缓解，不能解决

战斗结束时给整个地图加黑场、模糊或统一 crossfade，确实能降低玩家对位置跳变的敏感度，但有三个缺点：

- 所有未变化的 actor 和地图也会闪烁，视觉代价过大。
- 它掩盖“逃跑动作没有世界落点、下一 tick 又随机移动”的语义断裂。
- 地图交互恢复时，玩家仍可能面对视觉位置与权威位置短暂不一致。

整图转场只适合区域切换、场景重建或大量实体同时变化，不应成为普通战斗结束的默认方案。

### 12.3 推荐：PostCombatHandoff

应在 PresentationScene 引入 Actor 级的 `PostCombatHandoff`，把战斗退场和恢复世界身份视为一次连续状态迁移：

```text
battle actor
  -> combat exiting
  -> post-combat handoff
  -> world actor
```

建议状态：

```text
PostCombatDisposition {
  actorId
  reason: escaped | survived | player_fled
  from: TileRef
  target?: TileRef
  worldAiResumeTick
  visualPolicy: retreat | hidden-relocate-arrive | settle-in-place
}
```

PresentationScene rebase 时不立即对 escaped actor 调 `reset-visible`，而是由 handoff coordinator 根据权威 diff 决定：

1. **已有 retreat target，且短距离可见**：把逃跑和世界位移合并为一次鸭子步/跳跃退避，完成后转 world idle。
2. **目标为长距离或视野外**：保持隐藏，先把 presentation anchor 对齐目标，再在目标位置播放 arrive；不能在原格先复现。
3. **位置未变化**：不做完全消失再出现；使用短暂降透明、解除战斗高亮、恢复 world idle 的 settle-in-place。
4. **handoff 期间又收到新的 world 位置**：合并到最新目标，只播放一次连续过渡，不串联“复现 + move + move”。

这是双投影的具体收益：AuthoritativeStore 可以立即记录 NPC 已移动，PresentationScene 则用一次 handoff 把玩家看到的位置平滑追到最新权威位置。

### 12.4 后端需要提供最小连续性约束

只做前端过渡仍会让同一个 NPC 在极短时间内完成“战斗逃跑 + 下一 tick 随机巡逻”两个空间行为。视觉可以合并，但领域语义仍含混。

建议后端至少增加：

- escaped actor 在首个 post-battle TickFrame 禁止 world AI，其他 NPC 和世界 tick 正常推进。
- 施加 effect-lifetime 被动 `flustered`，在 qid disband boundary 激活并通过 capability evaluator 限制 actor；不能通过全局暂停世界实现。
- 若 escape 未来有明确退避目标，escape 结算时直接选择/保留该目标，并 emit 到 PresentationBatch。

推荐最终语义：逃跑动作本身决定一次世界退避，持久位置在同一结算中更新；首个 post-battle tick 只用于场景稳定，不让该 actor 再随机移动。这样后端事实和前端动画共享同一个目标点。

### 12.5 方案比较

| 方案 | 成本 | 效果 | 判断 |
|---|---:|---|---|
| 整图 crossfade | 低 | 遮住跳变，但所有内容闪烁 | 不推荐作为默认方案 |
| 仅前端 Actor handoff | 中 | 视觉连续，可合并位置差 | 可作为第一阶段 |
| 仅后端 post-battle 冷却 | 低到中 | 避免立即二次移动，但逃跑仍可能原地淡出/复现 | 必要的最低约束 |
| 后端 retreat target + 冷却 + 前端 handoff | 高 | 领域和视觉完全一致 | 推荐目标方案 |

### 12.6 交互边界

handoff 不应恢复全局 `isPlayingBattleLog` 屏障。可使用短生命周期、局部的 `presentationPhase='rebasing'`：

- 状态栏、日志、后台权威刷新继续工作。
- 只暂时禁用依赖地图 Actor 位置的点击/瞄准，或把输入排队到 handoff 完成。
- 目标时长应是数百毫秒级，并有超时后直接 rebase 的降级路径。

这类局部过渡锁是场景一致性约束，与当前“一播放日志就冻结所有命令”的全局屏障性质不同。

### 12.7 以战斗结束遮罩作为场景交接窗口

现有战斗结束模态框提供了比额外整图 crossfade 更自然的场景切换边界：遮罩覆盖地图后，玩家的视觉注意力已经转移到战斗结果，地图仍可在遮罩下完成权威投影 rebase 和 post-combat 动画。遮罩关闭时，玩家回到的应当已经是连续、可交互的世界场景。

这里的语义边界不是“模态框组件挂载”或“模态框最终关闭”，而是 `battle_end` 遮罩已经达到覆盖态：

```text
battle action / damage / death / escape 演出完成
  -> battle_end overlay 开始淡入
  -> overlayCovered（淡入完成，地图已被 75% 黑色遮罩覆盖）
  -> PresentationSession 结束接收战斗演出写入
  -> PresentationScene 对齐最新 AuthoritativeStore
  -> exit actor 的 PostCombatHandoffRun 与普通 actor 的 RebaseMoveRun 在遮罩下启动
  -> 战斗结果文本展示与 world animation 并行
  -> overlay 淡出
  -> overlay.closed；若 handoff 尚未完成，world animation 继续且位置相关交互保持局部锁定
  -> handoff.finished
  -> 地图以 world scene 身份恢复位置相关交互
```

“演出场景结束”在此指战斗投影的所有权完成移交，不代表强制终止地图动画，也不要求 world animation 在模态框关闭前全部播放完。短动画可以完全藏在遮罩下；较长且连续的移动可以在遮罩淡出后自然继续。这样既利用了遮罩降低位置变化的突兀感，又不会在模态框停留时间过长时人为冻结世界。

实现时应把场景交接建模为播放协议中的显式步骤，而不能让 store 猜测组件 CSS 时长：

```text
step: battle_end_overlay_enter
await: overlay.covered(sessionId)
step: presentation_scene_handoff
effect: publish authority + start PostCombatHandoffRun
step: battle_end_modal_content
await: overlay.closed(sessionId) + handoff.finished(sessionId, sceneGeneration)
```

职责边界：

- Director 只在 `battle_end` segment 生成 `presentation_scene_handoff`，普通 turn/round 模态框不得触发。
- BattleModal 在淡入完成并确认仍属于同一 session 后发出 `overlay.covered`；关闭信号继续只负责模态框生命周期。
- Battle store 收到 handoff step 后封存旧战斗投影写入，确认对应 response/batch 的 authoritative watermark，将已取得的权威实体状态 rebase 到 PresentationScene，并启动 actor 级 `PostCombatHandoffRun`；启动完成即允许结果正文出现，不等待 world animation 播完。
- `beginRebase` 同时冻结普通 world actor 的位置 diff。MapGrid 对非 exit actor 使用 world-owner、rebase token 与 ActorRuntime generation 绑定的 `RebaseMoveRun`，不得在 `rebasing` 分支直接同步 anchor 瞬移；exit actor 必须从普通 diff 中排除，继续只由 `PostCombatHandoffRun` 管理。
- MapGrid 在一帧内完成普通 move run 注册后封口；battle store 合并普通 move barrier 与 exit handoff barrier，两类 world animation 都与结果正文并行。
- `battle_end_modal_content` 同时等待 modal closed 与 handoff finished；只有两个屏障都完成后 Runner 才能推进战斗退出。
- MapGrid 在 `presentationPhase='rebasing'` 期间只锁定依赖 actor 位置的交互；全屏遮罩本身继续拦截点击。
- 若权威快照尚未到达，handoff 等待对应 response/batch 的 authoritative watermark，不能把旧快照当作新世界提交。
- 若 `overlay.covered` 丢失或组件异常卸载，使用短超时直接 rebase；不能因纯视觉组件失败让播放队列永久卡住。
- `beginRebase` 一旦发布权威 snapshot，后续动画失败或取消只能结束该次 rebase、释放 lease 并提交对应 deferred scopes，不能 rollback 到旧战斗投影；只有权威发布前失败才保留旧 PresentationScene。

当前遮罩为全屏 75% 黑色，适合让背景变化保留轻微动态感。如果实机观察仍能清楚看到 actor 瞬移，应先提高 battle-end 阶段的遮罩不透明度或延长约 100-200ms 的覆盖稳定期，而不是叠加第二套全地图转场。最终仍应由 `PostCombatHandoff` 保证 actor 轨迹连续，遮罩只负责降低权威场景交接的感知强度，不能替代正确的空间语义。

### 13.1 后端协议

- command/heartbeat 在事务内冻结 render events，并事务性递增 `oblgame.vars_json.obl_presentation_head_seq`。
- COMMIT 成功后响应顶层附加 `presentation_head_seq` 和可选 `presentation.v1`；事务回滚不消耗 batch sequence。
- `player_info.presentation_head_seq` 支持 F5/冷启动 cursor=head。
- 已删除 `battle_log` State scope、mutable played JSON、`mark_battle_log_played.php`、旧 refresh scope 与该旧 endpoint 的 Vite proxy；command/heartbeat/state/img 的开发代理继续保留。
- `BattleLogCollector` 仅保留请求内事件、checkpoint/rollback 职责；可选 archive writer 与在线 delivery 解耦。
- response event 暂时保留 `log_id=event_seq`、`played=1` 作为 Director/type 兼容字段；二者不再代表持久记录或确认状态，在线顺序与去重只认 `batch_seq/event_seq`。

### 13.2 前端投影与播放

- `PresentationInbox` 统一接收 command/heartbeat batch，按 `batch_seq` 去重、连续消费；发现 gap 时强制刷新权威状态并快进 rebase。
- live batch 一旦被 Inbox 接受，必须在发布同一响应的 `player_info/game_map/enemies` 权威变化前立即 claim PresentationScene。`beginPlayback` 不能等到 Director 真正执行首个 step，否则入战 tick 或 `combat_context` 的位置修正会提前泄漏为普通 world move。
- `PresentationSceneStore` 已成为 MapGrid 的直接数据源。command/heartbeat changed scopes 进入串行 `PendingAuthorityScopes` worker，按 `player_info -> game_map/enemies -> combat_targets` 尽快更新 PlayerStore、CharacterHub、MapStore 与候选权威状态。
- PresentationScene 在 `playing/rebasing` 时保持自己的可见 snapshot，同时记录最新 pending authority；authority watch 在 `idle` 直接发布，covered/stable boundary 使用已经更新好的最新 authority 显式 rebase，动画期间继续到达的 authority 在 `finishRebase()` 自动追平。handoff 不再以表现层名义推迟或发起网络刷新，只会 join 已在运行的 authority worker 以满足 batch watermark。
- `battle_end` 计划拆为 `battle_end_overlay_enter -> presentation_scene_handoff -> battle_end_modal_content`。
- `presentation_scene_handoff` 只负责原子发布并启动 token/generation 绑定的 `PostCombatHandoffRun`；结果正文与 run 并行，content step 持有 modal closed + run finished 双完成屏障。
- 普通 actor 的 authoritative 位置变化由通用 `RebaseMoveRun` 播放；无位置 diff 不创建动画，generation 替换或场景取消会取消旧 run 并 reconcile 到已发布的权威 anchor。
- BattleModal 通过真实 opacity `transitionend` 发出 covered/closed token；超时只作为防卡死降级。
- commandQueue 不再用 `isPlayingBattleLog` 冻结所有命令；战斗提交受 presentation caught-up 约束，地图位置输入只在 `rebasing` 阶段局部锁定。

### 13.3 战后连续性

- escape 结算时确定相邻、可通行、未占用且尽量远离活跃对手的确定性 retreat target，并在同一目标结算中持久化位置。
- escape effect 与 `combatant_cleared` 都携带 `pls_before/pls_after`、`retreat_target` 和 visual policy。
- escaped actor 在逃跑结算时获得 pending `flustered`，qid 真正解散时激活；因此早退后即使战斗继续多个 tick，仍只在首个真正的战后 TickFrame 受 capability 限制，世界其他 actor 不暂停。
- PostCombatHandoff 支持 `retreat`、`settle-in-place`、`hidden-relocate-arrive` 和 `remove`，并校验 ActorRuntime generation。

### 13.4 实机回归后的投影边界修正

#### 入战时不应凭空播放 world move

`battle.start` 会推进 tick，未参战 NPC 在该 tick 发生世界移动是合法领域事实；如果动作链本身包含 move effect，也应由战斗 Runner 正常播放。错误的是 live presentation 已经到达后，PresentationScene 仍处于 `idle`，使权威 worker 在演出接管前把位置差发布为普通 world move。

最终边界：

1. command/heartbeat response 的新 batch 先 claim PresentationScene；
2. 再启动该响应 changed scopes 的权威刷新；
3. Director/Runner 接管同一个 playing scene；
4. stable boundary 或 battle-end covered handoff 再显式 rebase；
5. rebase move 还必须比较 Actor 当前场景坐标，当前点已经等于权威目标时直接 settle，不能补播零距离鸭子步。

#### `discovered` 不能由 Character 资料缓存隐式推导

`CharacterHub` 同时承担资料缓存与地图 roster 会破坏发现机制：同区域 NPC 从 `enemies` 完整快照缺席时旧记录仍在；`Boolean('0')` 还会把数据库字符串 `"0"` 解析为 true；`combat_targets` 候选再调用 `mergeEnemies` 会把不可见候选重新注入地图。

最终模型拆为三层：

- **Character records**：按 PID 缓存已知角色资料，可保留当前不可见 NPC。
- **Authoritative map roster**：由 `enemies` scope 的完整快照原子替换；缺席即不属于当前地图投影。玩家恒在 roster，当前战斗 active NPC 可由后端 enemies scope 以 combat-visible 身份返回。
- **Presentation actor lifetime**：由 PresentationScene snapshot 和 session lease 保活；权威 roster 移除 actor 时，正在播放的死亡/逃跑动画不能被 CharacterHub 删除打断。

`combat_targets` 只能 patch 角色资料和候选/Participation 信息，不能修改 authoritative map roster。MapGrid 只消费“玩家 + authoritative visible enemy PID 集合”，不再直接消费 CharacterHub 的全部 `aliveList`。

地图 roster 还可能在一次淡出未结束前再次包含同一 PID。此时 projected removal 必须是可取消且按 PID 独占的 run：重新发现时同步撤销旧 run 的 ownership、取消淡出并恢复可见性；旧 run 随后异步结束时，只能结算自身，不能删除重新出现的投影，也不能清除后继 removal run 的 ownership。组件卸载或场景销毁只取消 run，不启动恢复动画。

### 13.5 验收证据

- Oblivions PHP：33/33 domain/battle/transaction tests 通过。
- vex-vue：`npm run type-check`、`npm test`、`npm run build` 通过；fixture 覆盖 live batch 提前 claim、同区域 roster 缺席移除、candidate patch 不污染 roster、字符串 `discovered=0`、combat-visible roster、零距离 rebase move 抑制，以及“淡出取消后旧 run 晚于后继 run 完成”时不得误删新投影。
- 本地浏览器：实际完成一次玩家 escape 战斗结束；权威位置从原格更新到 retreat target，F5 后无历史模态框重播，直接显示新位置，控制台无 error/warn。
