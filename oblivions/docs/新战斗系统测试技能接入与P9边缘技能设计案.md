# 新战斗系统测试技能接入与 P9 边缘技能设计案

> 范围：Oblivions 新战斗系统后端、旧技能展示适配层、vex-vue 战斗装填区。
> 目的：确认当前“6 个验收技能 + P9 边缘技能”的真实落地状态，并给出后续推进方案。

---

## 1. 复核结论

本次复核先确认事实，再形成推进方案。结论如下：

1. `oblivions/docs/` 是当前仓库实际文档目录；不存在 `oblivions/doc/` 或 `obilivions/doc/`。
2. 新战斗系统 Phase 6 的 6 个基线技能已经在新系统层实现：
   - `move`
   - `unarmed_strike`
   - `escape`
   - `heal`
   - `throw`
   - `whirlwind`
3. 玩家开场技能池尚未完整暴露这 6 个技能。
   - 默认技能注入仍只有 `unarmed_strike`、`escape`。
   - 玩家创建记录时的初始 `skillpara` 也只有 `unarmed_strike`、`escape`。
   - `throw` 主要依赖初始武器 `throwing_spear` 作为测试入口。
4. 前端技能列表仍依赖旧 `skill_config.php` 的展示/列表适配层，因此“新系统配置已存在”不等于“前端可见、可测”。
5. `whirlwind` 的新系统配置为 `target='all'`，但前端装填逻辑目前没有 `skill.target === 'all'` 分支，会落入 enemy/pid 分支，导致提交目标语义不正确。
6. P9 的 3 个边缘测试技能尚未实现：
   - `execute`
   - `vampiric_bite`
   - `grenade`

因此，用户描述中的“剩下 3 个需要先加入玩家开场技能池”和“P9 边缘测试技能完全没有实现”总体成立；但实际推进时不能只改开场 `skillpara`，还必须补齐旧展示适配层和前端目标提交逻辑。

## 2. 事实依据

### 2.1 新系统 6 个基线技能已存在

`oblivions/gamedata/combat_skill_config.php` 已配置：

| 技能 | 新系统状态 | 验证边界 |
|------|------------|----------|
| `move` | 已配置、模块存在 | utility 管道、tile 目标、动态 AP |
| `unarmed_strike` | 已配置、模块存在 | attack 管道、pid 目标、死亡检测 |
| `escape` | 已配置、模块存在 | none 目标、逃跑效果、状态清理 |
| `heal` | 已配置、模块存在 | self 目标引用、治疗上限 |
| `throw` | 已配置、模块存在 | 自定义 AP 计算、远程射程 |
| `whirlwind` | 已配置、模块存在 | all 多目标、per-target effects |

模块目录 `oblivions/gamedata/combat_skills/` 当前存在：

- `skill_escape.php`
- `skill_heal.php`
- `skill_move.php`
- `skill_throw.php`
- `skill_unarmed_strike.php`
- `skill_whirlwind.php`

### 2.2 玩家默认技能池不足

`oblivions/include/game/skill/skill.main.php` 的 `skill_ensure_defaults()` 当前默认注入：

```php
$defaults = array('unarmed_strike', 'escape');
```

`oblivions/include/game/player.func.php` 创建玩家记录时，初始 `skillpara` 也是：

```php
'skillpara' => json_encode(array(
    'unarmed_strike' => array('lstact' => 0),
    'escape'         => array('lstact' => 0),
), JSON_UNESCAPED_UNICODE),
```

`oblivions/valid.php` 当前给玩家初始装备 `throwing_spear`，用于投掷测试。这解释了为什么“空手攻击、逃跑、投掷”已较容易测试，而 `heal / whirlwind / move` 没有同等直接入口。

### 2.3 前端技能列表仍受旧配置影响

`skill_get_available_list()` 仍遍历玩家 `skillpara`，并通过旧 `skill_get_config()` 读取 `oblivions/gamedata/skill_config.php`。

当前旧 `skill_config.php` 只包含：

- `unarmed_strike`
- `throw`
- `escape`
- `idle`
- `heal`
- `wep_range`

其中：

- 没有 `move`
- 没有 `whirlwind`
- `heal` 配置偏旧式技能参数，不完整表达新战斗系统的 `target/self/apcost/range` 语义
- P9 的 `execute / vampiric_bite / grenade` 均不存在

这意味着仅把技能写进玩家 `skillpara`，前端列表未必能正确展示或计算可用状态。

### 2.4 前端展示模板不完整

`vex-vue/src/data/skill-templates.ts` 当前只显式配置：

- `unarmed_strike`
- `escape`
- `throw`

未配置：

- `move`
- `heal`
- `whirlwind`
- `execute`
- `vampiric_bite`
- `grenade`

未配置技能会退回显示 skill id，可测试但体验与辨识度较差。

### 2.5 `whirlwind` 的 all 目标提交缺口

`vex-vue/src/components/battle/PreloadArea.vue` 的 `TargetIntent` 类型已包含：

```ts
| { type: 'all' }
```

显示函数也支持：

```ts
if (target.type === 'all') return '全部敌人';
```

但技能点击逻辑没有：

```ts
skill.target === 'all'
```

因此 `whirlwind` 会落入 enemy 分支。新后端 `target='all'` 解析逻辑应收到 `{ type: 'all' }`，然后从 `battle_cache['combatants']` 解析全部有效目标。

### 2.6 P9 边缘技能未实现

设计任务中 Phase 9 规划了 3 个边缘场景技能：

| 技能 | 验证目标 |
|------|----------|
| `execute` | 终结技排序，多个 finisher 只保留最后一个 |
| `vampiric_bite` | damage + heal 多效果 FIFO、效果间数据共享 |
| `grenade` | tile 目标、多 pid damage 展开、effects target_pid 持久化 |

当前 `combat_skill_config.php` 无对应配置，`combat_skills/` 目录无对应模块。

## 3. 问题定义

当前问题不是“新战斗系统是否搭建完成”，而是“验证入口是否足以覆盖新系统能力边界”。

新系统核心和 6 个基线技能已基本具备，但测试入口分散在三层：

1. 后端新战斗配置：`combat_skill_config.php`
2. 后端旧技能列表适配：`skill_config.php` + `skill_get_available_list()`
3. 前端装填与展示：`PreloadArea.vue` + `skill-templates.ts`

如果只修改其中一层，会出现下列偏差：

- 只加 `skillpara`：后端可能允许拥有，但前端不显示或显示不完整。
- 只加旧 `skill_config.php`：前端显示了，但新战斗执行仍取 `combat_skill_config.php`，配置不一致会造成测试误判。
- 只加前端模板：只是名称好看，不代表技能可用。
- 不修 `all` 目标：`whirlwind` 即使显示出来，也无法正确验证多目标能力。

## 4. 推进方案

### 4.1 第一阶段：补齐 6 个基线技能测试入口

目标：让玩家开场即可完整测试 Phase 6 的 6 个基线技能。

建议改动：

1. 更新玩家默认技能池。
   - `skill_ensure_defaults()` 加入 `move / heal / whirlwind`。
   - `obl_create_player_record()` 的初始 `skillpara` 同步加入这 3 个技能。
   - 是否把 `throw` 也加入永久默认技能需要单独决策：当前它依赖投掷武器注入，更贴近装备技能模型；若本轮目标是测试便利，可以临时加入默认池，但要标注为测试态。
2. 更新旧 `skill_config.php` 的展示适配配置。
   - 为 `move / heal / whirlwind` 补齐 `apcost / cd / target / range_mode / range_max / category / finisher` 等前端需要字段。
   - 尽量与 `combat_skill_config.php` 保持语义一致。
3. 更新前端 `skill-templates.ts`。
   - 增加 `move / heal / whirlwind` 的名称、描述、动作文案。
4. 修复 `PreloadArea.vue` 的 `all` 目标提交。
   - 在 `self` / `tiles` 分支前后加入 `skill.target === 'all'` 判断。
   - 对 all 技能直接 `addToQueue(actId, { type: 'all' })`。

### 4.2 第二阶段：实现 P9 三个边缘测试技能

目标：补齐完整验证新战斗系统边缘能力的技能套件。

#### execute

配置建议：

- `pipeline='attack'`
- `target='enemy'`
- `ap_calc='fixed'`
- `apcost=1`
- `range.mode='fixed'`
- `range.max=1`
- `finisher=true`

模块行为：

- 读取当前 target HP / MHP。
- 若 target HP < 30% MHP，伤害翻倍。
- 声明 damage 效果到 target pid。

验证重点：

- `combat_sort_actions()` 将 finisher 后置。
- 多个 finisher 只保留最后一个。
- L2 动作链模拟中的 finisher 覆盖行为正确。

#### vampiric_bite

配置建议：

- `pipeline='attack'`
- `target='enemy'`
- `ap_calc='fixed'`
- `apcost=2`
- `range.mode='fixed'`
- `range.max=1`
- `finisher=false`

模块行为：

- 计算 damage。
- 计算 `heal = ceil(damage * 0.5)`。
- 先声明 damage，后声明 heal。

验证重点：

- 同一 action 声明多个效果。
- FIFO 顺序：先伤害，后治疗。
- heal 值依赖 damage 计算结果。
- damage target 是敌人，heal target 是 actor。

注意：

当前 `combat_effect_heal()` 默认从当前 target 取 `target_data`，对“heal 指向 actor”的跨 target_pid 语义可能不够，需要在实现前确认效果系统是否已支持按 `target_pid` 重定向应用。若不支持，需要先补效果目标解析能力，否则 `vampiric_bite` 会暴露真实框架缺口。

#### grenade

配置建议：

- `pipeline='attack'`
- `target='tiles'`
- `ap_calc='fixed'`
- `apcost=2`
- `range.mode='fixed'`
- `range.max=3`
- `rules.forbid=['tile_impassable','tile_out_of_range']`

模块行为：

- 当前 target 是 tile。
- 调 `obl_get_pids_in_tile($tile['pgroup'], $tile['pls'])` 查找图格内 pid。
- 对每个 pid 声明 damage 效果。

验证重点：

- tile 目标解析不查 DB。
- execute 钩子内从 tile 派生多个 pid。
- post_check 能通过 effects 的 `target_pid` 检测死亡。
- persist 能通过 effects 的 `target_pid` 收集受影响 pid。

注意：

当前 damage 应用器默认从当前 target 的 `target_data` 扣 HP；tile target 本身没有 HP。若不支持 `target_pid` 重定向，grenade 的多 pid damage 无法正确落地，需要先补“effect target_pid 解析并取得内存目标数据”的能力。

## 5. 风险与决策点

### 5.1 旧技能配置与新技能配置双源风险

短期为了测试，可继续让 `skill_config.php` 作为前端列表适配层。但长期看，这是明显双源：

- 新系统执行读 `combat_skill_config.php`
- 前端列表读 `skill_config.php`

建议后续将 `skill_get_available_list()` 改造为在 `combat_engine='new'` 时读取 `combat_skill_config.php`，旧 `skill_config.php` 只服务旧战斗系统。

### 5.2 `throw` 的技能来源决策

`throw` 当前更像装备技能，靠 `throwing_spear` 注入测试。如果为了完整测试方便，也可以临时加入默认池；但这会弱化“投掷技能来自投掷武器”的装备语义。

建议：

- 若目标是开发验证：临时默认开放 `throw` 可接受。
- 若目标是接近正式玩法：保持装备注入，仅确保入场武器稳定给到。

### 5.3 P9 会暴露 effect 系统真实边界

`execute` 基本只验证 finisher 和伤害倍率，风险较低。

`vampiric_bite` 和 `grenade` 更关键，它们都要求效果可以作用到“非当前 target”的 pid。当前代码中 post_check 和 persist 已经为 `effect.target_pid` 做了前向兼容，但 damage/heal 应用器是否真正按 `target_pid` 重定向，需要在实现时重点确认。

如果应用器只操作当前 target，则：

- `vampiric_bite` 的 heal 可能错误作用到敌人。
- `grenade` 的 damage 可能作用到 tile target，导致失败。

因此 P9 不是单纯加 3 个技能文件，可能需要小幅补强 effect 应用层。

## 7. 验收标准

### Phase 6 测试入口验收

- 新玩家开场可看到并装填需要测试的基线技能。
- `heal` 显示为自我目标技能，提交 `{ type: 'self' }`。
- `whirlwind` 显示为多目标技能，提交 `{ type: 'all' }`。
- `move` 若作为战斗技能开放，应显示为 tile 目标技能，提交 `{ type: 'tile', id }`。
- 旧系统回退路径不因新增展示配置直接崩坏。

### P9 验收

- `execute` 能作为 finisher 被排序到最后，多个 finisher 只保留最后一个。
- `vampiric_bite` 在一次 action 中先扣敌人 HP，再治疗 actor。
- `grenade` 对目标 tile 内多个 pid 分别造成伤害，并正确触发死亡检测与持久化。
- L1/L2 preview 不因新增技能目标类型或多效果崩溃。

## 8. 结论

当前任务的真实状态是：

- 新战斗系统主体和 Phase 6 技能实现基本完成。
- 测试入口尚未完整接通，尤其是默认技能池、旧技能展示适配和 `all` 目标提交。
- P9 三个边缘技能确实未实现。
- P9 中 `vampiric_bite` / `grenade` 可能需要先补 effect target_pid 重定向能力，这会是完整验证新战斗系统的关键一环。

后续应先让 6 个基线技能稳定可测，再实现 P9。这样可以把“接入问题”和“框架边缘能力问题”分开验证，避免多个变量同时变化导致误判。

### 9.1 新发现：tile 瞄准点击会触发真实地图移动

玩家测试发现：

> 前端预装填时选择“战斗移动”再选择图格，会错误触发真实移动后的部分效果，例如清除地图迷雾；可能还有其他副作用待发现。

初步判断这是前端交互层问题，不是战斗后端 `move` 技能本身已经执行：

- `AimMode.vue` 当前把点击监听挂在 `#mapGrid` 上。
- 地图格本身在 `MapGrid.vue` 中也绑定了 `@click="onCellClick(cell)"`。
- Vue 组件上的 cell click 很可能先触发真实地图移动逻辑；随后 AimMode 的 grid 冒泡监听才收到事件。
- 因此 tile 瞄准点击需要在底层交互结构中和普通地图点击互斥，而不是只在 AimMode 里 `stopPropagation()`。

后续调查重点：

1. 确认事件顺序是否为 cell `@click` 先触发真实移动，再冒泡到 `#mapGrid` 的 AimMode click。
2. 检查真实移动入口是否来自 `MapGrid.vue` → `onCellClick` → `clickMove` / `commandQueue.execute('map.move')`。
3. 设计更底层、更优雅的互斥方案：
   - 瞄准模式应成为地图交互模式的一部分。
   - 普通地图点击在瞄准模式下应被统一拦截。
   - tile 选择不应复用会触发真实移动的 click path。

### 9.2 调查结论与结构修复

调查确认该问题真实存在：

1. `MapGrid.vue` 的每个地图格使用 Vue `@click="onCellClick(cell)"`。
2. `onCellClick` 对可达格调用 `triggerCellClick(cell.pls)`。
3. `useMapBusiness.ts` 中的 `onCellClick` 回调最终调用 `clickMove(pls)`。
4. `clickMove` 会提交真实 `map.move`，成功后失效并重新加载地图，从而触发移动后的地图迷雾/视野等副作用。
5. `AimMode.vue` 原本把 click 监听挂在父级 `#mapGrid`，事件在冒泡阶段才进入 AimMode，因此子元素 Vue click 有机会先执行真实移动。

这说明问题根因不是后端战斗移动提前执行，而是前端缺少“地图输入消费方”的统一状态。AimMode 和 MapGrid 同时监听同一张地图，但没有底层互斥。

已采用的结构修复：

1. 在 `useUiStore` 新增 `mapInputMode: 'normal' | 'aim'`。
2. `battle:aim-mode` 时设置 `mapInputMode='aim'`。
3. `battle:aim-exit` / `battle:ended` 时恢复 `mapInputMode='normal'`。
4. `MapGrid.vue` 的 `onCellClick / onCellEnter / onCellLeave` 在 `aim` 模式下直接返回，不再触发普通地图移动、探索、hover 预览。
5. `useMapInteraction.ts` 的键盘移动在 `aim` 模式下直接返回，避免瞄准中按方向键触发真实移动。

该方案比单纯在 `AimMode.vue` 上使用 capture/click 阻止事件更底层：

- MapGrid 明确知道当前地图输入由 AimMode 消费。
- 普通地图点击和键盘移动共享同一互斥状态。
- 后续如果新增 AOE 预览、路径选择、放置陷阱等地图选择模式，可继续扩展 `mapInputMode`，不用每个模式都抢 DOM 事件。

仍需手动验证：

- 战斗移动 tile 瞄准点击只加入装填队列，不触发 `map.move`。
- grenade tile 瞄准点击只加入装填队列，不触发 `map.move`。
- enemy 瞄准仍可正常选敌人。
- 退出瞄准后普通地图点击、hover、键盘移动恢复正常。

### 9.3 新发现：战斗移动动态距离/AP/动画缺口

玩家进一步测试发现：

预期：

1. 战斗移动瞄准模式下，最远可选择“单次最大移动距离 × 当前可支付 AP 次数”的图格。
2. 装填区能正确预测战斗移动的动态 AP 消耗。
3. 执行战斗移动动作后，前端在战斗动作阶段播放角色移动动画，而不是等战斗结束刷新地图时才同步位置。

实际：

1. 前端只能选择单次最大移动距离内的图格。
2. 战斗移动不播放动作阶段移动动画，只在后续地图数据同步时跳到新位置。

调查结论：

1. 前端 tile 瞄准复用了 `skill.action_range`，而旧列表适配里 `move` 的 `action_range` 是单次移动力 3，未乘以可支付 AP。
2. 后端 `combat_tag_derive_tile_out_of_range()` 对 tile 目标也按技能射程直接拦截。对 `move_distance` 技能来说，这会把战斗移动限制在单次移动力内，无法发挥动态 AP 模型。
3. battle director 已能把 `move` effect 识别为 `move_avatar` visual，但现有播放链只处理攻击动画与伤害数字，没有消费 `move_avatar`。
4. `decideActionAnimation()` 原先对有 target 的非特殊 action 默认当成 `melee_hit`，没有为 `move` 建立 action 阶段的移动动画计划。

已采用的修复：

1. 后端 `tile_out_of_range` 对 `ap_calc='move_distance'` 特判：
   - `max_range = move_power × floor(actor.ap / apcost)`
   - 这样后端规则层允许当前 AP 可支付的移动距离。
   - 真正 AP 消耗仍由 `combat_ap_calc_move_distance()` 计算并由 wallet 扣除。
2. 前端 `PreloadArea.vue`：
   - tile 瞄准进入时，如果技能是 `move`，使用 `action_range × floor(predictedAp / apcost)` 作为可选范围。
   - 队列 AP 预测改为按目标距离动态估算：`max(apcost, ceil(distance / action_range))`。
   - 队列项显示每个动作估算 AP，战斗移动可直接看到动态消耗。
   - 进一步补入“计划位置”概念：队列中的 `move` 会推进后续动作的预测 origin，连续移动、移动后攻击、移动后瞄准 tile 都按计划位置计算。
   - `battle:aim-mode` 事件新增 `originPls`，AimMode 从该原点计算 enemy/tile 射程，而不是固定使用当前地图位置。
3. 前端 `battle-director-v2.ts`：
   - 先前用 `actionId === 'move'` 产出 `ActionAnimationPlan.kind='move'`，已进一步改为 effect 驱动。
   - 当 action 收到 `move` effect 且 effect 目标为 tile 时，由 `move` effect 提升出 `ActionAnimationPlan.kind='move'`。
4. 前端 `CollisionAnimation.vue`：
   - 消费 `kind='move'` 的 action plan。
   - 优先从 `move` effect 的 `visual.kind='move_avatar'` 和 tile target 取得目标格。
   - 查找 actor 控制器和目标 tile DOM，调用 actor 的 `moveTo()` 在动作阶段播放移动动画。

### 9.4 新增约束：先提炼概念，再反推实现

玩家补充了本阶段后续修复的核心约束：

1. 解决问题不能停留在表面修补，必须先从问题中提炼概念，判断问题是特例，还是应该成为新的框架基准。
2. 再从需求目标反推实现方式；如有必要，可以重构或抛弃旧结构，不被旧框架“静态为基准”的现状束缚。

据此重新审视本轮修复：

1. tile 瞄准误触真实移动不是 `move` 技能特例，而是“地图输入同一时刻应只有一个消费方”的框架问题。已上升为 `mapInputMode`，由地图交互底层统一互斥普通点击、hover 和键盘移动。
2. 战斗移动可选范围不是“射程多乘几格”的 UI 特例，而是动态 AP 技能的瞄准预算问题。当前 `move_distance` 按既有公式 `max(apcost, ceil(distance / move_power))` 处理，前后端都按同一语义估算。
3. 装填队列不是静态动作列表，而是会改变后续判断上下文的“计划状态”。因此 PreloadArea 现在维护计划位置，AimMode 通过 `originPls` 按计划位置计算瞄准范围。
4. 战斗移动动画不是 `move` 技能特例，而是“位移效果应有位移视觉”的播放框架问题。已把前端 director 从 `actionId === 'move'` 调整为由 `move` effect 产出动作阶段移动动画，`CollisionAnimation` 也优先消费 effect visual 的 tile 目标。

这个方向保留了当前验证成本最低的实现，但避免把新能力绑定死在单个技能 ID 上。后续如果出现冲锋、击退、牵引、传送等技能，应继续沿用 effect 驱动，而不是继续在前端按 actionId 增加特判。

仍需手动验证：

- 当前 AP=10、移动力=3 时，战斗移动瞄准范围应约为 30 格内可达格。
- 选择距离 4~6 的格子，队列应显示 AP:2。
- 执行战斗移动后，应在战斗动作阶段看到角色移动到目标格。
- 战斗结束/刷新地图后，角色最终位置不应回弹或二次异常跳动。

### 9.5 日志定位：后端 verify 缺少计划状态

根据 `oblivions/cache/battles/combat_debug.log`，玩家提交了两个动作：

1. `move` 到 tile 3。
2. `unarmed_strike` 攻击 pid 12。

日志显示：

1. `move` 在 verify 阶段通过，`ap_cost=1`。
2. `unarmed_strike` 在 verify 阶段失败，原因是 `out_of_range`。
3. 最终 `VERIFY_END verified_count=1`，execute 只执行了 `move`。

这说明问题不在移动技能执行失败，也不在前端没有提交攻击动作，而是后端 `combat_verify()` 在验证动作队列时只维护 AP 预扣，没有维护“计划 actor 状态”。因此第二个动作仍按移动前位置计算射程，导致“移动后攻击”被提前过滤。

概念提炼：

1. 装填队列不是静态动作列表，而是一个顺序计划。
2. verify 不能只做单动作校验或只累计 AP；它必须维护 `sim_actor`，让后续动作读取前序动作投影后的 AP/位置等计划状态。
3. 真正执行阶段仍需要强校验兜底，因为 NPC/并发/死亡/占用等状态可能在 verify 后变化。

已采用的后端修复：

1. `combat_verify()` 新增 `sim_actor = $actor_data`，verify 阶段所有 context 都基于 `sim_actor` 构建。
2. 通过的 action 会写入 `_ap_cost`，并调用 `combat_verify_project_action()` 推进计划状态。
3. `combat_verify_project_action()` 当前投影两类框架基准状态：
   - AP：`sim_actor.ap -= ap_cost`。
   - 位移：如果技能声明了 `move` effect 且目标为 tile，则把 `sim_actor.pgroup/pls` 推进到目标格。
4. 真实 `actor_data` 不在 verify 阶段被写入；execute/persist 仍是唯一真实状态修改路径。

预期结果：

- `move -> unarmed_strike` 队列中，`unarmed_strike` 的 verify 射程会按移动后的 tile 计算。
- 如果移动后确实进入射程，`VERIFY_END verified_count` 应为 2，execute 会依次执行移动和攻击。
- 如果执行阶段因为真实状态变化导致仍然超距，管道 `check_rules` 会继续兜底失败。
