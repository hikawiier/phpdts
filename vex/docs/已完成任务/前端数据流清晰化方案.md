# Vex 前端数据流清晰化方案

> 版本：1.0 | 日期：2026-06-22
>
> 目标：让前后端数据流结构更清晰，修复已知 bug，清理技术债
>
> 前置文档：[前端代码审阅报告](../前端代码审阅报告.md) | [前端架构重构设计案](./前端架构重构设计案.md)（已归档，本方案替代其执行）

---

## 第一部分：方案定位

### 1.1 方案背景

经过前后端代码审阅，确认 Vex 前端**不需要完整的架构重构**。理由：

1. **后端架构决定前端优化空间**：command.php 返回空 JSON，前端必须"通知拉取"，真正的"数据推送"需要后端支持 WebSocket/SSE，不是前端重构能突破的限制
2. **投入产出比**：完整重构需改动 300+ 行，但核心收益（数据流清晰）用 50-80 行即可达到 80%
3. **实际痛点集中**：当前最大痛点是 P2（误判成功）和读取路径双轨制，小改动即可解决

### 1.2 方案范围

本方案聚焦"让数据流更清晰"，不涉及架构升级。具体包括：

- 修复 P2：COMMAND_IN_PROGRESS 误判 bug
- 统一读取入口：消除 gameApi / dataManager.fetch 双轨制
- 白名单缓存：替代全量缓存，避免数据不一致
- 精准失效：替代全量失效，减少不必要的缓存清空
- 清理死代码：删除 subscribe/notify 机制

### 1.3 不做的事

| 项目 | 理由 |
|------|------|
| 启用 subscribe/notify 数据推送 | 后端 PHP+文件存储，"通知拉取"已是最务实选择 |
| mapData → mapStore 响应式 | 改动量大（150 行），收益低，`broadcast('map:loaded')` 够用 |
| fetchBatch 批量请求 | 后端不支持 batch action，`Promise.all` 并行已够用 |
| 渲染节流 | 当前性能问题不严重，10x10 地图全量重绘影响可控 |
| 战斗本地增量更新 | 改动复杂，battle_log 消费式设计已够用 |

## 第二部分：后端架构关键事实

本方案基于以下后端架构事实，这些事实决定了前端数据流的边界。

### 2.1 命令/读取分离设计

```
command.php  →  写入：执行命令，返回空 JSON {}（不携带业务数据）
api_v2.php   →  读取：返回业务数据（前端主动拉取）
```

**关键点**：
- command.php 成功执行返回 `{}`
- command.php 并发冲突返回 `{ "error": "COMMAND_IN_PROGRESS" }`
- command.php 命令被拒绝仍返回 `{}`（前端无法区分"成功"和"被拒绝"）
- 前端必须通过 api_v2.php 拉取数据才能得知命令结果

### 2.2 COMMAND_IN_PROGRESS 触发机制

[obl_command.php:23-33](file:///d:/wamp64/www/phpdts/oblivions/include/core/obl_command.php#L23-L33)：

```php
$obl_lock_fp = fopen($obl_lock_file, 'w');
if (!$obl_lock_fp || !flock($obl_lock_fp, LOCK_EX | LOCK_NB)) {
    echo compatible_json_encode(array('error' => 'COMMAND_IN_PROGRESS'));
    exit;
}
```

- **锁机制**：文件锁 `flock(LOCK_EX | LOCK_NB)`，非阻塞
- **锁粒度**：玩家级别（per room + per pid）
- **锁生命周期**：请求级别（进程结束 OS 自动释放）
- **触发场景**：多标签页同时操作、脚本攻击、动画播放期间用户再次点击

### 2.3 日志系统的两层设计

| 维度 | obl_log（结构化日志） | battle_log（战斗日志） |
|------|----------------------|----------------------|
| **存储** | `obl_log_{groomid}_{pid}.json` | `obl_battle_log_{groomid}_{pid}.json` |
| **读取模式** | **累积式**：返回全部日志 | **消费式**：只返回 `played=0` |
| **played 标记** | 无 | 有（0=未播放，1=已播放） |
| **轮转** | 正式 200 条 / debug 50 条 | 不轮转，保留历史 |
| **缓存适合度** | ❌ 不适合（累积式，缓存漏新日志） | ❌ 不适合（消费式，缓存致重复播放） |

### 2.4 API 响应统一格式

api_v2.php 所有 action 返回：
```json
{ "status": "success", "data": {...}, "message": "" }
```
错误时：
```json
{ "status": "error", "message": "...", "code": "ERROR_CODE" }
```

### 2.5 各 action 的数据特性与缓存决策

| action | 数据来源 | 变化频率 | 缓存决策 | 理由 |
|--------|---------|---------|---------|------|
| `game_map` | oblmapstates 表 + move.func.php | 极低（仅移动时） | ✅ 5s | 低频变化，移动后 invalidate |
| `tile_actions` | oblmappoi + oblmapitem 表 | 低（移动/搜索时） | ✅ 3s | 低频变化，移动后 invalidate |
| `player_inventory` | $pdata['itempara'] | 中（拾取/丢弃时） | ✅ 2s | 中频变化，操作后 invalidate |
| `player_info` | $pdata 全量 | 高（战斗中 HP 变化） | ❌ | 高频变化，需强一致性 |
| `enemies` | oblplayers 表 | 中（战斗/移动时） | ❌ | 战斗中敌人状态变化 |
| `obl_log` | 文件（累积式） | 高（每次操作） | ❌ | 累积式存储，缓存漏新日志 |
| `battle_log` | 文件（消费式） | 极高（战斗中） | ❌ | 消费式存储，缓存致重复播放 |

## 第三部分：具体改动方案

### 3.1 改动 1：修复 P2 — COMMAND_IN_PROGRESS 误判

**问题**：[utils.js](file:///d:/wamp64/www/phpdts/vex/js/utils.js) submitCommand 在 HTTP 200 + JSON 响应时无条件返回 `success: true`，即使 `gamedata.error` 存在也误判为成功。

**影响**：当后端返回 `{ "error": "COMMAND_IN_PROGRESS" }` 时，调用方（如 clickMove）误判为成功并触发 loadMap 刷新，浪费网络请求且可能导致状态不一致。

**改动文件**：`vex/js/utils.js`

**改动内容**：

```javascript
// utils.js submitCommand 修复
export async function submitCommand(params) {
    // ... 省略 fetch 逻辑 ...

    if (contentType.includes('application/json')) {
        const gamedata = await resp.json();
        const hasError = !!gamedata.error;
        return {
            success: !hasError,           // ← 有 error 时 false
            gamedata: gamedata,
            redirect: gamedata.redirect || null,
            timer: gamedata.timer || null,
            error: gamedata.error || null,
            message: hasError ? '命令执行中，请稍候' : null
        };
    }

    return { success: true };
}
```

**改动量**：5 行

**验证标准**：
- 模拟后端返回 COMMAND_IN_PROGRESS，前端 `result.success` 为 `false`
- 正常命令执行不受影响

**附带改动**：移除这 4 个文件中对 `gameApi` 的 import（改为从 data-manager.js 导入 dataManager）

**验证标准**：

### 3.3 改动 3：白名单缓存

**问题**：当前 DataManager 全量缓存所有 action，但 9 处 fetch 中 8 处用 `forceRefresh=true` 绕过缓存，全量缓存形同虚设。且统一 TTL 2000ms 无法兼顾低频数据（game_map 适合长 TTL）和高频数据（player_info 不该缓存）。

**改动文件**：`vex/js/data-manager.js`

**改动内容**：全量缓存 → 白名单缓存

```javascript
// data-manager.js 重构
class DataManager {
    constructor() {
        this._cache = new Map();        // action -> { data, timestamp }
        this._pending = new Map();       // action -> Promise（去重，所有 action 都生效）
        this._subscribers = new Map();   // action -> Set<callback>（暂保留，改动 5 决定是否删除）
        this._listeners = new Map();     // event -> Set<callback>

        // 白名单：只缓存这些 action，TTL 各自不同
        this._cacheable = new Map([
            ['game_map', 5000],           // 地图结构，5s（移动后 invalidate）
            ['tile_actions', 3000],       // 当前格交互，3s（移动后 invalidate）
            ['player_inventory', 2000],   // 背包，2s（拾取/丢弃后 invalidate）
        ]);
        // player_info, enemies, obl_log, battle_log 不缓存
    }

    async fetch(action, forceRefresh = false) {
        const ttl = this._cacheable.get(action);

        // ── 非白名单 action：不缓存，但保留去重 ──
        if (ttl === undefined) {
            if (this._pending.has(action)) {
                return this._pending.get(action);
            }
            const promise = gameApi(action).then(result => {
                this._pending.delete(action);
                this._notify(action, result);
                return result;
            }).catch(err => {
                this._pending.delete(action);
                throw err;
            });
            this._pending.set(action, promise);
            return promise;
        }

        // ── 白名单 action：走缓存逻辑 ──
        const now = Date.now();
        const cached = this._cache.get(action);

        if (!forceRefresh && cached && (now - cached.timestamp < ttl)) {
            return cached.data;
        }

        if (this._pending.has(action)) {
            return this._pending.get(action);
        }

        const promise = gameApi(action).then(result => {
            this._cache.set(action, { data: result, timestamp: Date.now() });
            this._pending.delete(action);
            this._notify(action, result);
            return result;
        }).catch(err => {
            this._pending.delete(action);
            throw err;
        });

        this._pending.set(action, promise);
        return promise;
    }

    invalidate(action) {
        // 白名单内才需要清缓存；非白名单本就无缓存
        if (this._cacheable.has(action)) {
            this._cache.delete(action);
        }
    }

    invalidateAll() {
        // 只清白名单缓存
        this._cache.clear();
    }

    // broadcast / listen / unlisten 保持不变
    // subscribe / unsubscribe / _notify 在改动 5 中决定是否删除
}
```

**白名单模式的核心设计**：

1. **去重对所有 action 生效**：无论是否白名单，`_pending` 去重都工作
2. **缓存仅对白名单生效**：非白名单 action 不缓存，总是发新请求
3. **每个 action 独立 TTL**：game_map 5s，tile_actions 3s，player_inventory 2s
4. **invalidate 对非白名单无操作**：非白名单本就无缓存

**解决的问题**：
- 全量缓存形同虚设 → 白名单只缓存适合缓存的数据
- 统一 TTL 不合理 → 每个 action 独立 TTL
- 缓存 + forceRefresh 混合导致数据不一致 → 高频数据不缓存，根本不存在缓存不一致

**改动量**：约 30 行

**验证标准**：
- 白名单 action 在 TTL 内不重复请求
- 非白名单 action 每次都发请求
- 同一 action 并发请求被去重（Network 面板验证）

### 3.4 改动 4：精准失效

**问题**：当前所有写操作都用 `invalidateAll()` 清空全部缓存，过于粗暴。

**改动文件**：`vex/js/map.js`、`vex/js/tile-action.js`、`vex/js/inventory.js`、`vex/js/battle.js`

**改动内容**：根据命令类型精准失效相关白名单 action

**各命令的失效清单**（仅列出白名单 action，非白名单无需 invalidate）：

| 命令 | 失效的白名单 action | 理由 |
|------|-------------------|------|
| `move` | game_map, tile_actions, player_inventory | 移动改变地图、动作条、可能拾取 |
| `obl_pickup` | player_inventory, tile_actions | 拾取改变背包和动作条 |
| `obl_search` | tile_actions, player_inventory | 搜索改变动作条和背包 |
| `obl_explore` | tile_actions, player_inventory, game_map | 探索可能改变地图 |
| `obl_discard` | player_inventory | 丢弃只改变背包 |
| `battle` | （无白名单 action） | 战斗不涉及白名单数据 |

**代码示例**：

```javascript
// map.js clickMove
async function clickMove(areaId) {
    // ...
    const result = await commandQueue.execute({ command: 'move', ... });
    if (result.success) {
        // 旧：dataManager.invalidateAll();
        // 新：精准失效
        dataManager.invalidate('game_map');
        dataManager.invalidate('tile_actions');
        dataManager.invalidate('player_inventory');
        dataManager.broadcast('game:action-completed');
        // ...
    }
}

// tile-action.js handlePickupAll
async function handlePickupAll() {
    // ...
    // 旧：dataManager.invalidateAll();
    // 新：精准失效
    dataManager.invalidate('player_inventory');
    dataManager.invalidate('tile_actions');
    // ...
}
```

**改动量**：约 10 行（4-5 处 invalidateAll 替换为精准 invalidate）

**验证标准**：
- 移动后只刷新 game_map/tile_actions/player_inventory 的缓存
- 战斗后不触发白名单缓存失效（本就无白名单数据）
- 非白名单数据不受影响（本就无缓存）

### 3.5 改动 5：清理死代码（可选）

**问题**：DataManager 的 subscribe/notify/_subscribers 机制全项目零调用，是死代码。

**决策**：本方案不启用 subscribe/notify 数据推送（理由见 1.3），因此删除死代码。

**改动文件**：`vex/js/data-manager.js`

**改动内容**：删除以下方法和相关状态

```javascript
// 删除以下代码
this._subscribers = new Map();   // 构造函数中

subscribe(action, callback) { ... }
unsubscribe(action, callback) { ... }
_notify(action, data) { ... }

// fetch 中删除 this._notify(action, result) 调用
```

**改动量**：约 15 行删除

**验证标准**：
- 全项目搜索 `subscribe` 无结果
- 全项目搜索 `_notify` 无结果
- 功能无回归（broadcast/listen 机制不受影响）

**注意**：如果未来计划启用数据推送机制，可保留死代码。但本方案明确不做数据推送，建议删除以保持代码清晰。
