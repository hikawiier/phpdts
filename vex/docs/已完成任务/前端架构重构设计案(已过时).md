## 第一部分：重构背景与目标

### 1.1 三个核心需求

作为一款网页游戏，Vex 前端必须满足：

| 需求 | 描述 | 当前满足度 |
|------|------|-----------|
| 需求 1 | 有绝对明确的指令路径，能精确向后端请求自己所需要的信息 | 50% |
| 需求 2 | 有绝对清晰的信息处理与分发机制，用来处理后端传来的复杂信息 | 30% |
| 需求 3 | 有绝对安全的指令过滤，确保能处理指令并发、阻塞问题 | 60% |

### 1.2 重构目标

```
重构前：通知拉取模式 + 读取路径双轨制 + 全量缓存 + 指令过滤缺陷

重构后：数据推送模式 + 统一读取入口 + 白名单缓存 + 完整指令过滤
```

## 第二部分：当前架构问题分析

### 2.1 需求 1 不满足：指令路径不明确

#### 问题：读取路径双轨制

当前存在两条并行的数据读取路径：

```
路径 A（直接调用，无缓存无去重）：
  map.js ──────→ gameApi('game_map')
  map.js ──────→ gameApi('enemies')
  inventory.js ─→ gameApi('player_inventory')
  tile-action.js→ gameApi('tile_actions')
  log.js ──────→ gameApi('obl_log')

路径 B（经过 DataManager，有缓存有去重）：
  battle.js ───→ dataManager.fetch('player_info', true)
  battle.js ───→ dataManager.fetch('enemies', true)
  battle.js ───→ dataManager.fetch('battle_log', true)
  player.js ───→ dataManager.fetch('player_info', true)
  inventory.js ─→ dataManager.fetch('player_info')  // 装备数据，用缓存
```

**影响**：
- 开发者不确定该用哪条路径
- 缓存和去重效果被 4 个模块绕过
- 同一数据（如 `player_info`）被 battle.js 和 player.js 分别拉取

#### 写入路径（已统一）

```
所有模块 ────→ commandQueue.execute() ──→ submitCommand() ──→ POST /command.php
```

写入路径是统一的，但 `submitCommand` 存在 P2 缺陷（见 2.3）。

### 2.2 需求 2 不满足：信息分发不清晰

#### 问题 1：通知拉取模式（非数据推送）

当前事件总线只传通知，不传数据：

```
当前模式（通知拉取）：
  操作成功 → broadcast('game:action-completed')  // 只传事件名，不传数据
                    ↓
          ┌─────────┼─────────┐
          ↓         ↓         ↓
      loadInv()  loadLog()  loadPlayer()  // 各模块再分别拉取数据
```

**影响**：`game:action-completed` 事件触发后，inventory/log/player/tile-action 各发一次请求，产生 4 次重复请求。

#### 问题 2：subscribe/notify 是死代码

DataManager 设计了数据推送机制但完全没用上：

```javascript
// data-manager.js 中已实现但零调用
subscribe(action, callback)   // 注册数据订阅
_notify(action, data)         // 数据变化时推送
```

全项目搜索 `dataManager.subscribe` 调用次数：**0 次**。

#### 问题 3：mapData 全局可变状态无响应式

```javascript
// data.js 导出可变对象
export const mapData = { curLoc: null, curRegion: null, links: null, enemies: [] };

// map.js 直接修改属性（通过 updateMapData 封装，但仍无订阅机制）
updateMapData({ curLoc: d.currentLocation, ... });

// 其他模块直接读取，无订阅
if (mapData.links) { ... }
```

状态变更依赖显式 `broadcast('map:loaded')`，容易遗漏。

### 2.3 需求 3 不满足：指令过滤不安全

#### 问题 1：P2 — COMMAND_IN_PROGRESS 未处理

```javascript
// utils.js submitCommand 当前实现
if (contentType.includes('application/json')) {
    const gamedata = await resp.json();
    return {
        success: true,  // ← BUG：即使 gamedata.error 存在也返回 true
        gamedata: gamedata,
        error: gamedata.error || null
    };
}
```

当后端返回 `{ "error": "COMMAND_IN_PROGRESS" }` 时，前端误判为成功。

#### 问题 2：无命令超时机制

`commandQueue.execute()` 中 `await submitCommand(params)` 无超时限制。如果后端长时间不响应，队列会永久阻塞。

#### 问题 3：无命令重试机制

当后端返回 `COMMAND_IN_PROGRESS` 时，前端应该等待并重试，而非直接报错。当前无此机制。

---

### 2.4 缓存机制问题：全量缓存形同虚设

#### 当前缓存使用情况

| 调用方 | action | forceRefresh | 是否用缓存 |
|--------|--------|-------------|-----------|
| battle.js ×6 | player_info, enemies, battle_log | **全部 true** | ❌ 不用 |
| player.js ×2 | player_info | **全部 true** | ❌ 不用 |
| inventory.js ×1 | player_info | **false** | ✅ 唯一用缓存的 |

**关键发现**：9 处 fetch 调用中，**8 处用 `forceRefresh=true` 绝过缓存**。全量缓存形同虚设。

#### 各 action 的数据特性

| action | 变化频率 | 强一致性需求 | 缓存价值 | 缓存风险 |
|--------|---------|------------|---------|---------|
| `game_map` | 极低（仅移动时） | 低 | **高** | 低 |
| `tile_actions` | 低（仅移动时） | 低 | **高** | 低 |
| `player_inventory` | 中（拾取/丢弃时） | 中 | 中 | 中 |
| `enemies` | 中（战斗/移动时） | 中 | 中 | 中 |
| `player_info` | **高**（战斗中 HP 变化） | **高** | 低 | **高** |
| `obl_log` | **高**（每次操作） | **高** | 低 | **高**（漏新日志） |
| `battle_log` | **极高**（战斗中持续） | **高** | 极低 | **极高** |

**问题**：统一 TTL 2000ms 无法兼顾低频数据（game_map 适合长 TTL）和高频数据（player_info 不该缓存）。

### 3.1 总体架构

#### 3.2.2 CommandQueue 增加超时 + 重试

```javascript
// command-queue.js 重构
class CommandQueue {
    constructor() {
        this._locked = false;
        this._cooldown = 0;
        this._cooldownTimer = null;
        this._timeout = 10000;          // 新增：超时 10s
        this._maxRetry = 3;             // 新增：最大重试 3 次
        this._retryDelay = 500;         // 新增：重试间隔 500ms
    }

    async execute(params) {
        if (this._locked) {
            return { success: false, error: 'LOCKED', message: '操作进行中' };
        }
        if (this._cooldown > Date.now()) {
            return { success: false, error: 'COOLDOWN', message: '冷却中' };
        }

        this._locked = true;
        try {
            return await this._executeWithRetry(params);
        } finally {
            this._locked = false;
        }
    }

    async _executeWithRetry(params) {
        let lastResult;
        for (let attempt = 0; attempt <= this._maxRetry; attempt++) {
            lastResult = await this._executeWithTimeout(params);

            // COMMAND_IN_PROGRESS 时等待重试
            if (lastResult.error === 'COMMAND_IN_PROGRESS' && attempt < this._maxRetry) {
                await this._sleep(this._retryDelay);
                continue;
            }

            // 其他情况（成功或非 IN_PROGRESS 错误）直接返回
            return lastResult;
        }
        return lastResult;
    }

    async _executeWithTimeout(params) {
        return Promise.race([
            submitCommand(params),
            new Promise((_, reject) =>
                setTimeout(() => reject(new Error('TIMEOUT')), this._timeout)
            )
        ]).catch(e => {
            if (e.message === 'TIMEOUT') {
                return { success: false, error: 'TIMEOUT', message: '命令超时' };
            }
            return { success: false, error: 'NETWORK_ERROR', message: e.message };
        });
    }

    _sleep(ms) {
        return new Promise(resolve => setTimeout(resolve, ms));
    }
}
```

#### 3.2.3 精准失效替代全量失效

当前所有写操作都用 `invalidateAll()` 清空全部缓存，过于粗暴。改为精准失效：

```javascript
// 移动命令后：只需刷新地图、敌人、动作条、日志
async function clickMove(areaId) {
    // ...
    // 旧：dataManager.invalidateAll();
    // 新：精准失效（仅白名单 action 需要失效，非白名单本就无缓存）
    dataManager.invalidate('game_map');
    dataManager.invalidate('tile_actions');
    dataManager.invalidate('player_inventory');
    dataManager.broadcast('game:action-completed');
    // ...
}
```

**各命令的失效清单**（仅列出白名单 action，非白名单无需 invalidate）：

| 命令 | 失效的白名单 action |
|------|-------------------|
| `move` | game_map, tile_actions, player_inventory |
| `obl_pickup` | player_inventory, tile_actions |
| `obl_search` | tile_actions, player_inventory |
| `obl_explore` | tile_actions, player_inventory, game_map |
| `obl_discard` | player_inventory |
| `battle` | （无白名单 action，全靠 forceRefresh） |

### 3.3 阶段二：统一读取入口 + 白名单缓存（需求 1）

#### 3.3.1 DataManager 白名单缓存重构

```javascript
// data-manager.js 重构
class DataManager {
    constructor() {
        this._cache = new Map();        // action -> { data, timestamp }
        this._pending = new Map();       // action -> Promise（去重，所有 action 都生效）
        this._subscribers = new Map();   // action -> Set<callback>
        this._listeners = new Map();     // event -> Set<callback>

        // 白名单：只缓存这些 action，TTL 各自不同
        this._cacheable = new Map([
            ['game_map', 5000],           // 地图结构，5s（移动后 invalidate）
            ['tile_actions', 3000],       // 当前格交互，3s（移动后 invalidate）
            ['player_inventory', 2000],   // 背包，2s（拾取/丢弃后 invalidate）
        ]);
        // player_info, enemies, obl_log, battle_log 不缓存
    }

    async fetch(action, forceRefresh = false) {
        const ttl = this._cacheable.get(action);

        // ── 非白名单 action：不缓存，但保留去重 ──
        if (ttl === undefined) {
            if (this._pending.has(action)) {
                return this._pending.get(action);
            }
            const promise = gameApi(action).then(result => {
                this._pending.delete(action);
                this._notify(action, result);
                return result;
            }).catch(err => {
                this._pending.delete(action);
                throw err;
            });
            this._pending.set(action, promise);
            return promise;
        }

        // ── 白名单 action：走缓存逻辑 ──
        const now = Date.now();
        const cached = this._cache.get(action);

        if (!forceRefresh && cached && (now - cached.timestamp < ttl)) {
            return cached.data;
        }

        if (this._pending.has(action)) {
            return this._pending.get(action);
        }

        const promise = gameApi(action).then(result => {
            this._cache.set(action, { data: result, timestamp: Date.now() });
            this._pending.delete(action);
            this._notify(action, result);
            return result;
        }).catch(err => {
            this._pending.delete(action);
            throw err;
        });

        this._pending.set(action, promise);
        return promise;
    }

    invalidate(action) {
        // 白名单内才需要清缓存；非白名单本就无缓存
        if (this._cacheable.has(action)) {
            this._cache.delete(action);
        }
    }

    invalidateAll() {
        // 只清白名单缓存
        this._cache.clear();
    }

    // subscribe / unsubscribe / _notify / broadcast / listen / unlisten 保持不变
}
```

**白名单模式的核心设计**：

1. **去重对所有 action 生效**：无论是否白名单，`_pending` 去重都工作，避免并发重复请求
2. **缓存仅对白名单生效**：非白名单 action 不缓存，总是发新请求
3. **每个 action 独立 TTL**：`game_map` 5s，`tile_actions` 3s，`player_inventory` 2s
4. **invalidate 对非白名单无操作**：非白名单本就无缓存，invalidate 是空操作

**白名单模式解决了之前分析的"缓存 + forceRefresh 混合导致数据不一致"问题**：`player_info` 等高频数据不缓存，根本不存在缓存不一致。

#### 3.4.2 模块改为订阅模式 + 渲染节流

```javascript
// inventory.js 重构后
export function initInventory() {
    // 订阅 player_inventory 数据变化
    dataManager.subscribe('player_inventory', throttleRender(renderInventory));
    dataManager.subscribe('player_info', throttleRender(renderEquipment));
}

// 渲染节流：同一帧内的多次 notify 只触发一次渲染
function throttleRender(renderFn) {
    let scheduled = false;
    let latestData = null;
    return (data) => {
        latestData = data;
        if (scheduled) return;
        scheduled = true;
        requestAnimationFrame(() => {
            renderFn(latestData);
            scheduled = false;
        });
    };
}

function renderInventory(data) {
    inventoryData = data;
    const drawer = document.getElementById('invDrawer');
    if (drawer && drawer.classList.contains('open')) {
        renderCurrentTab();
    }
}

// 不再需要 loadInventory() 函数，改为触发 fetch
export function refreshInventory() {
    dataManager.fetch('player_inventory', true);
}
```

#### 3.4.3 事件流重构

```
重构前（通知拉取）：
  clickMove 成功
    → invalidateAll()
    → broadcast('game:action-completed')
        → inventory.listen → loadInventory() → gameApi('player_inventory')
        → log.listen → refreshLog() → gameApi('obl_log')
        → player.listen → loadPlayerInfo() → dataManager.fetch('player_info')
        → tile-action.listen → loadTileAction() → gameApi('tile_actions')

重构后（数据推送 + 白名单缓存）：
  clickMove 成功
    → invalidate('game_map', 'tile_actions', 'player_inventory')  // 精准失效
    → broadcast('game:action-completed')
        → inventory.listen → fetch('player_inventory', true) → notify → throttleRender
        → log.listen → fetch('obl_log', true) → notify → throttleRender
        → player.listen → fetch('player_info', true) → notify → throttleRender
        → tile-action.listen → fetch('tile_actions', true) → notify → throttleRender
```

**关键区别**：
- 重构前：每个模块各自调用 `gameApi`，无缓存无去重
- 重构后：每个模块调用 `dataManager.fetch`，白名单有缓存、所有 action 有去重、notify 自动推送、渲染节流

#### 3.4.4 mapData 响应式改造

```javascript
// data.js 重构
class MapStore {
    constructor() {
        this._data = { curLoc: null, curRegion: null, links: null, enemies: [] };
        this._subscribers = new Set();
    }

    get data() { return this._data; }

    update(patch) {
        const prevRegion = this._data.curRegion;
        this._data = { ...this._data, ...patch };
        this._notify(patch, prevRegion);
    }

    subscribe(callback) {
        this._subscribers.add(callback);
    }

    _notify(patch, prevRegion) {
        this._subscribers.forEach(cb => cb(this._data, patch, prevRegion));
    }
}

export const mapStore = new MapStore();
// 不再导出 mapData，改为 mapStore.data
```

### 3.5 战斗场景专项优化

战斗场景的高频请求需要额外优化，避免缓存失效后的请求风暴。

#### 3.5.1 批量请求（减少网络往返）

```javascript
// data-manager.js 新增
async fetchBatch(actions, forceRefresh = false) {
    // 过滤出需要请求的 action
    const needFetch = actions.filter(a => {
        if (forceRefresh) return true;
        const cached = this._cache.get(a);
        const ttl = this._cacheable.get(a);
        if (!ttl || !cached) return true;
        return Date.now() - cached.timestamp >= ttl;
    });

    if (needFetch.length === 0) {
        return actions.map(a => this._cache.get(a).data);
    }

    // 调用后端 batch 接口
    const result = await gameApi('batch&actions=' + needFetch.join(','));
    // 分别缓存并 notify
    for (let i = 0; i < needFetch.length; i++) {
        const action = needFetch[i];
        const data = result[i];
        if (this._cacheable.has(action)) {
            this._cache.set(action, { data, timestamp: Date.now() });
        }
        this._notify(action, data);
    }
    return actions.map(a => this._cache.get(a)?.data || result[needFetch.indexOf(a)]);
}
```

**使用场景**：

```javascript
// 探索后批量刷新（4 次请求合并为 1 次）
async function handleExplore() {
    const result = await commandQueue.execute({ command: 'obl_explore' });
    if (result.success) {
        dataManager.invalidate('tile_actions');
        dataManager.invalidate('player_inventory');
        // 批量请求：4 个 action 合并为 1 次网络请求
        await dataManager.fetchBatch(
            ['player_inventory', 'obl_log', 'player_info', 'tile_actions'],
            true
        );
    }
}
```

#### 3.5.2 战斗动画期间本地增量更新

战斗中不需要每个 damage entry 都 fetch `player_info`，改为动画完成后一次性刷新：

```javascript
// battle.js 重构
async function playBattleLog(entries) {
    // 阶段 1：只播放动画，本地增量更新 HP，不 fetch
    for (const entry of entries) {
        await playAnimation(entry);
        // 本地更新 HP 显示（从 entry 中提取）
        if (entry.type === 'damage' && entry.target === 'player') {
            updateLocalHp(entry.value);  // 本地增量更新，无网络请求
        }
    }
    // 阶段 2：动画全部完成后，一次性刷新
    await dataManager.fetch('player_info', true);
}
```

## 第五部分：风险评估与回滚策略

### 5.1 风险评估

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 阶段一超时机制误杀正常请求 | 中 | 高 | 超时设为 10s（后端正常响应 < 1s） |
| 阶段二白名单遗漏导致数据不新鲜 | 低 | 中 | 白名单仅含低频数据，TTL 内变化后立即 invalidate |
| 阶段二非白名单数据请求频率上升 | 低 | 低 | 去重机制兜底，且原代码本就 forceRefresh=true |
| 阶段三 subscribe 时序问题 | 中 | 高 | 保留 broadcast 作为兜底，渐进式迁移 |
| mapStore 响应式改造遗漏订阅者 | 中 | 高 | 全量搜索 mapData. 访问点，逐一替换 |
| 后端 batch 接口未实现 | 中 | 中 | 阶段三可先不实现 fetchBatch，后续后端支持后再加 |

### 5.2 回滚策略

每个阶段独立提交，若出现问题可单独回滚：

- **阶段一回滚**：恢复 submitCommand 和 command-queue.js 原始代码
- **阶段二回滚**：恢复 DataManager 全量缓存 + 5 处 gameApi 调用
- **阶段三回滚**：恢复 broadcast 通知拉取模式 + mapData 全局可变

### 5.3 测试策略

每个阶段完成后执行：
1. VS Code 诊断零错误
2. 浏览器控制台零错误
3. 功能验证：移动、探索、搜索、拾取、丢弃、战斗、区域切换
4. Network 面板验证：无重复请求、无遗漏请求、白名单缓存命中
